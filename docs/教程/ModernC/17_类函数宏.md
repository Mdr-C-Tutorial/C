# 第 17 章：类函数宏

[[toc]]

本章涵盖：

- 核验宏实参
- 访问宏调用语境
- 使用可变实参宏
- 为函数调用提供默认实参

我们已经显式（见第 10.2.1 节）或隐式地遇到过类函数宏。C 标准库中的某些接口通常用它们实现，例如 <code>&lt;tgmath.h&gt;</code> 中的类型泛型接口。我们也已经看到，类函数宏很容易让代码晦涩难懂，而且必须遵守一套严格的规则。要避开类函数宏带来的诸多问题，最简单的策略是：只在不可替代时才用它们；凡是能替代的地方，都改用合适的其他手段。

::: tip 要点 17 #1
只要可能，就优先选择内联函数，而非类函数宏。
:::

也就是说，当实参数量固定且类型已知时，应当以函数原型的形式提供真正类型安全的接口。假设有一个带副作用的简单函数：

~~~c
unsigned count(void) {
  static counter = 0;
  ++counter;
  return counter;
}
~~~

现在考虑用一个宏来求平方：

~~~c
#define square_macro(X) (X*X) // 糟糕：不要使用。
...
unsigned a = count();
unsigned b = square_macro(count());
~~~

这里，<code>square_macro(count())</code> 会被替换为 <code>count()\*count()</code>，于是 <code>count</code> 会执行两次。缺乏经验的读者大概想不到会是这样。

::: details 练习 7
证明 <code>b == a\*a + 3\*a + 2</code>。
:::

要取得与类函数宏相同的性能，在头文件中提供内联定义就完全足够：

~~~c
inline unsigned square_unsigned(unsigned x) { // 良好
  return x*x;
}
...
unsigned c = count();
unsigned d = square_unsigned(count());
~~~

这里，<code>square_unsigned(count())</code> 只会执行一次 <code>count</code>。

::: details 练习 8
证明 <code>d == c\*c + 2\*c + 1</code>。
:::

不过，许多情况下，类函数宏确实能完成函数做不到的事情。它们可以：

- 强制执行某些类型映射与实参核验；
- 跟踪执行；
- 提供实参数量可变的接口；
- 提供类型泛型接口；
- 为函数提供默认实参。

本章将说明怎样实现这些特性。我们还会讨论另外两项需要明确区分开来的 C 特性：一是 <code>_Generic</code>，它在宏中很有用，离开宏用起来会十分繁琐；二是可变实参函数，它如今基本已经过时，不应再用于新代码。

这里还要先提个醒：宏程序设计很快就会变得丑陋，几乎无法阅读，因此要读懂这里的部分代码，需要你拿出一些耐心和善意。来看一个示例：

~~~c
#define MINSIZE(X, Y) (sizeof(X)<sizeof(Y) ? sizeof(X) : sizeof(Y))
~~~

右侧的替换序列相当复杂，包含四次 <code>sizeof</code> 求值，以及把它们组合起来的若干运算符。不过，这个宏用起来应当毫不费力：它只是求出两个实参大小中较小的那个。

::: tip 要点 17 #2
类函数宏应当为复杂任务提供简单接口。
:::

## 17.1 类函数宏怎样工作

为了提供前面列出的特性，C 选择了一条与其他流行编程语言大不相同的道路：文本替换。如前所述，宏替换发生在编译的一个很早的阶段，即预处理阶段。替换遵循 C 标准规定的一套严格规则；对于任意源代码，同一平台上的所有编译器都应当预处理出完全相同的中间代码。

我们在示例中再加入一个宏：

~~~c
#define BYTECOPY(T, S) memcpy(&(T), &(S), MINSIZE(T, S))
~~~

现在有两个宏定义，分别对应 <code>MINSIZE</code> 和 <code>BYTECOPY</code>。第一个带有形参列表 <code>(X, Y)</code>，定义了两个形参 <code>X</code> 和 <code>Y</code>，替换文本为：

~~~c
(sizeof(X)<sizeof(Y) ? sizeof(X) : sizeof(Y))
~~~

其中引用了 <code>X</code> 和 <code>Y</code>。类似地，<code>BYTECOPY</code> 有两个形参 <code>T</code> 和 <code>S</code>，其替换文本以 <code>memcpy</code> 开头。

这些宏满足我们对类函数宏的要求。每个实参只求值一次，所有实参都用 <code>()</code> 括起来，也没有意外的控制流之类的隐藏效果。

::: details 练习 9
为什么每个实参只求值一次？
:::

宏的形参必须是标识符。一项特殊的作用域规则把这些标识符的有效范围限制在替换文本内部。

当编译器遇到一个类函数宏的名称，且其后紧跟一对闭合的 <code>()</code> 时——例如 <code>BYTECOPY(A, B)</code>——它会把这视为宏调用，并按照以下规则执行文本替换：

1. 暂时禁用该宏定义，以避免无限递归。
2. 扫描 <code>()</code> 内的文本，也就是实参列表，以查找括号和逗号。每一个左括号 <code>(</code> 都必须有一个 <code>)</code> 与之匹配。不在这类内层 <code>()</code> 中的逗号，用来把实参列表分隔成各个实参。实参的数量必须与宏定义中形参的数量一致。
3. 递归展开各实参中可能出现的宏。在示例中，<code>A</code> 本身可能是另一个宏，并展开成某个对象名，例如 <code>redA</code>。
4. 把实参展开得到的文本片段赋给相应形参。
5. 复制替换文本，并把形参的每次出现替换为相应定义。
6. 再次对所得替换文本执行宏替换。
7. 在源代码中用最终替换文本取代宏调用。
8. 重新启用该宏定义。

这套过程乍看有些复杂，实际却很容易实现，而且替换次序可靠。它保证不会出现无限递归，也不涉及复杂的局部对象赋值。在本例中，展开 <code>BYTECOPY(A, B)</code> 会得到：

~~~c
memcpy(&(redA), &(B),
       (sizeof((redA))<sizeof((B)) ? sizeof((redA)) : sizeof((B))))
~~~

我们已经知道，宏的标识符（无论是否为类函数宏）有自己独立的命名空间。原因很简单：

::: tip 要点 17.1 #1
宏替换发生在很早的翻译阶段，早于对组成程序的记号赋予任何其他解释。
:::

因此，预处理阶段对后续翻译阶段的关键字、类型、对象或其他构造一无所知。

由于宏展开显式禁用递归，函数甚至可以与类函数宏使用同一个标识符。例如，下面的代码是有效的 C：

~~~c:line-numbers
inline
char const* string_literal(char const str[static 1]){
  return str;
}
#define string_literal(S) string_literal("" S "")
~~~

它定义了接收字符数组实参的函数 <code>string_literal</code>，同时还定义了同名宏：宏先以一种古怪的方式整理实参，再调用该函数。为什么要这样做，稍后就会看到。还有一条更专门的规则，可以帮助我们处理宏与函数同名的情况，它与函数退化（要点 11.4 #1）类似。

::: tip 要点 17.1 #2（宏保留）
类函数宏后面如果没有 <code>()</code>，就不会展开。
:::

在前面的示例中，函数定义与宏定义能否成立，取决于二者出现的先后次序。如果宏定义在前，函数定义就会立即展开，变成类似下面的样子：

~~~c:line-numbers
inline
char const* string_literal("" char const str[static 1] ""){ // 错误
  return str;
}
~~~

这段代码是错误的。不过，如果把名称 <code>string_literal</code> 用括号括起来，它就不会展开，定义仍然有效。完整示例如下：

~~~c:line-numbers
// 头文件
#define string_literal(S) string_literal("" S "")
inline char const* (string_literal)(char const str[static 1]){
  return str;
}
extern char const* (*func)(char const str[static 1]);
// 一个翻译单元
char const* (string_literal)(char const str[static 1]);
// 另一个翻译单元
char const* (*func)(char const str[static 1]) = string_literal;
~~~

也就是说，内联定义和用于实例化的函数声明都受外围 <code>()</code> 的保护，类函数宏不会在这里展开。最后一行展示了这一特性的另一种常见用法：<code>string_literal</code> 后面没有 <code>()</code>，因此两条规则都会生效——先由宏保留阻止宏展开，再由函数退化（要点 11.4 #1）把对函数的这次使用求值为指向该函数的指针。

## 17.2 实参核验

如前所述，如果实参数量固定，其类型又能用 C 的类型系统妥善描述，就应当使用函数，而非类函数宏。我们甚至可以为 C 库函数另外提供更便于核验实参的接口：

::: info <code>snprintf_swapped</code>

与 <code>snprintf</code> 类似，但会依据大小核验缓冲区实参。

为实现这种核验，函数先接收大小实参，再接收缓冲区；于是可以把缓冲区指定为依赖该大小的数组形参。

~~~c
[[maybe_unused, __gnu__::__format__(__printf__, 3, 4)]]
static inline
int snprintf_swapped(size_t n, char s[restrict static n],
                     char const* restrict form, ...) {
  va_list ap;
  va_start(ap);
  int ret = vsnprintf(s, n, form, ap);
  va_end(ap);
  return ret;
}
~~~

:::

这个函数只是一个小包装器，所以把它声明为 <code>static</code> 和 <code>inline</code>，放在头文件中。这样几乎可以确定，它在每个调用位置都会内联，额外开销很小。对该函数的调用可以核验第一和第二个实参是否一致，尤其可以核验所提供的缓冲区是否至少有第一个实参所指明的大小。（译者注：原书此处作“第二个实参”，与 <code>snprintf_swapped</code> 的形参顺序不符，已改正。）

稍后（见第 18.2 节）会看到，怎样在一个更通用的包装器中使用这个函数，以取代 C 库函数 <code>snprintf</code>。此外，该函数用 <code>&lt;stdarg.h&gt;</code> 中的宏 <code>va_start</code> 把可变形参列表的信息存入 <code>ap</code>，再把这些信息整体转发给 C 库函数 <code>vsnprintf</code>；后者专门用来处理这种 <code>va_list</code> 信息（见第 17.4.2 节）。

遗憾的是，C 的类型系统无法涵盖我们可能想要区分的所有特殊情况。字符串字面量就是一例：我们希望把它们传给 <code>printf</code> 等存在潜在危险的函数。如第 5.6.1 节所述，字符串字面量是只读的，却没有 <code>const</code> 限定。此外，像前面 <code>string_literal</code> 函数那样使用 <code>[static 1]</code> 的接口，语言也不会强制执行，因为不带 <code>[static 1]</code> 的原型与之等价。

在 C 中，无法规定函数接口的形参 <code>str</code> 必须满足以下约束：

- 是字符指针；
- 必须非空；
- 必须不可修改；[^10]
- 必须以 0 结尾。

这些性质都特别适合在编译期核验，可是函数接口根本无法表达它们。

宏 <code>string_literal</code> 填补了语言规约中的这项空白。其展开中那对古怪的空字符串字面量 <code>"" X ""</code>，保证调用 <code>string_literal</code> 时只能传入字符串字面量：

~~~c
string_literal("hello"); // "" "hello" ""
char word[25] = "hello";
...
string_literal(word);    // "" word "" // 错误
~~~

宏与函数 <code>string_literal</code> 只是这项策略的简单示例。下面是更有用的例子。

::: info <code>TRACE_PRINT0</code>

一个简单版本的宏：要么调用 <code>fprintf</code>，要么什么也不做。

~~~c
#if NDEBUG
# define TRACE_PRINT0(F, X) do { /* 什么也不做 */ } while (false)
#else
# define TRACE_PRINT0(F, X) fprintf(stderr, F, X)
#endif
~~~

:::

在程序的调试构建中，可以用这个宏插入调试输出：

~~~c
TRACE_PRINT0("my favorite variable: %g\n", sum);
~~~

它看起来既无害又高效，却暗藏一个陷阱：实参 <code>F</code> 可以是任意 <code>char</code> 指针，尤其可能是位于可修改内存区域的格式字符串。这样一来，一旦该字符串遭到错误或恶意的修改，就可能产生无效格式，进而导致程序崩溃或泄露秘密。第 17.4 节会更详细地说明，为什么这对 <code>fprintf</code> 之类的函数格外危险。

像示例这样把简单字符串字面量传给 <code>fprintf</code> 的简单代码，不应出现这些问题。现代编译器实现能够追踪传给 <code>fprintf</code>（及类似函数）的实参，核验格式说明符与其余实参是否匹配。

如果传给 <code>fprintf</code> 的格式不是字符串字面量，而只是任意 <code>char</code> 指针，这项核验就不起作用。为杜绝这种情况，可以强制要求使用字符串字面量：

::: info <code>TRACE_PRINT1</code>

一个简单版本的宏，确保 <code>fprintf</code> 的格式是字符串字面量。

此外，它还会在输出末尾自动加上换行符，使用者不必每次自己指定。

~~~c
#if NDEBUG
# define TRACE_PRINT1(F, X) do { /* 什么也不做 */ } while (false)
#else
# define TRACE_PRINT1(F, X) fprintf(stderr, "" F "\n", X)
#endif
~~~

:::

现在，<code>F</code> 只能接收字符串字面量，编译器就能完成它的工作，对不匹配发出警告。

宏 <code>TRACE_PRINT1</code> 仍有一个弱点：如果在设置了 <code>NDEBUG</code> 时使用它，实参会被忽略，一致性也就无从核验。久而久之，不匹配可能一直潜伏下来，直到调试时才突然暴露。

因此，宏的下一个版本分两步定义。第一步使用类似构造定义新宏 <code>TRACE_ON</code>。

::: info <code>TRACE_ON</code>

根据是否设置 <code>NDEBUG</code>，求得 0 或 1 的宏。

~~~c
#ifdef NDEBUG
# define TRACE_ON 0
#else
# define TRACE_ON 1
#endif
~~~

:::

程序员可能把 <code>NDEBUG</code> 宏设为任意值，而这个新宏保证只取 1 或 0。第二步，使用普通的 <code>if</code> 条件定义 <code>TRACE_PRINT2</code>。

::: info <code>TRACE_PRINT2</code>

一个简单版本的宏，确保始终对 <code>fprintf</code> 调用求值。

~~~c
#define TRACE_PRINT2(F, X)                         \
do { if (TRACE_ON) fprintf(stderr, "" F "\n", X); } \
while (false)
~~~

:::

只要条件实参为 0，任何现代编译器都应当能把 <code>fprintf</code> 调用优化掉；但它不应省略对形参 <code>F</code> 和 <code>X</code> 的实参核验。因此，无论是否在调试，传给宏的实参都必须始终匹配，因为 <code>fprintf</code> 要求如此。

除了前面用空字符串字面量 <code>""</code> 的做法，还有其他技巧可以强制宏实参具有特定类型。其中一种是加上适当的 0：<code>+0</code> 强制实参是标量类型（整数、浮点数或指针）；<code>+0.0F</code> 之类的写法则把任意算术类型提升为浮点类型。

例如，如果调试时只想用更简单的方式打印某个值，而不想操心它的类型，下面的宏也许就够了：

::: info <code>TRACE_VALUE0</code>

跟踪一个值，无须指定格式。

~~~c
#define TRACE_VALUE0(HEAD, X) \
  TRACE_PRINT2(HEAD " %Lg", (X)+0.0L)
~~~

:::

只要值 <code>X</code> 是整数或浮点数，它就能工作。用于 <code>long double</code> 的格式 <code>"%Lg"</code> 能保证任何值都以合适的方式呈现。现在，实参 <code>HEAD</code> 不得包含任何 <code>fprintf</code> 格式；一旦出现不匹配，编译器会告诉我们。

用复合字面量可以方便地核验形参 <code>X</code> 的值是否与类型 <code>T</code> 赋值兼容。先看第一次尝试打印指针值的版本：

::: warning <code>TRACE_PTR0</code>

跟踪指针，无须指定格式。

该版本把 <code>X</code> 强制转换为 <code>void\*</code>。

~~~c
#define TRACE_PTR0(HEAD, X) \
  TRACE_PRINT2(HEAD " %p", (void*)(X))
~~~

:::

它尝试用格式 <code>"%p"</code> 打印指针值，该格式期望接收 <code>void\*</code> 类型的通用指针。因此，宏用强制转换把 <code>X</code> 的值和类型转为 <code>void\*</code>。与大多数强制转换一样，如果 <code>X</code> 不是指针，这里的转换就可能出错；而且强制转换等于告诉编译器“我们清楚自己在做什么”，所有类型核验实际上都关闭了。

为避免这一点，可以先把 <code>X</code> 赋给一个 <code>void\*</code> 类型的对象。赋值或初始化只允许有限的几种隐式转换，其中就包括从指向任意对象类型的指针转换到 <code>void\*</code>：

::: info <code>TRACE_PTR1</code>

跟踪指针，无须指定格式。

~~~c
#define TRACE_PTR1(HEAD, X) \
  TRACE_PRINT2(HEAD " %p", ((void*){ (X) }))
~~~

:::

其中的技巧是用形如 <code>((T){ (X) })</code> 的构造来核验 <code>X</code> 是否与类型 <code>T</code> 赋值兼容。复合字面量 <code>((T){ })</code> 先创建一个类型为 <code>T</code> 的临时对象，再用 <code>X</code> 初始化它。同样，现代优化编译器应当把这个临时对象优化掉，只替我们完成类型核验。[^11]

[^10]: <code>const</code> 只约束被调用函数，不约束调用方。
[^11]: 不过，C 中有一处较为古怪的规定，这个宏仍然防不住：值为零的整数常量表达式同时也是空指针常量。因此，单独的 <code>0</code>（与单独的 <code>1</code> 不同）仍会被这个宏接受。第 18 章会介绍连这一潜在缺陷也能捕捉的工具。

## 17.3 访问调用语境

由于宏只是文本替换，它们与调用语境的交互可以紧密得多。对于一般功能，这通常并不可取；最好把调用方语境（对函数实参求值）与被调用方语境（使用函数形参）清楚地分开。

不过在调试时，我们常常想打破这种严格的分隔，以便观察代码中某个位置的部分状态。原则上，宏内部可以访问任意对象；但我们通常需要的是有关调用环境的更具体的信息：某条调试输出究竟来自哪里。

C 为此提供了几种构造。特殊宏 <code>__LINE__</code> 始终展开成一个整数常量，表示源代码中的实际行号：

::: info <code>TRACE_PRINT3</code>

向跟踪信息加入当前行号。

~~~c
#define TRACE_PRINT3(F, X)                            \
do {                                                  \
  if (TRACE_ON)                                       \
    fprintf(stderr, "%lu: " F "\n", __LINE__+0UL, X); \
} while (false)
~~~

:::

类似地，宏 <code>__DATE__</code>、<code>__TIME__</code> 与 <code>__FILE__</code> 分别包含表示编译日期、编译时间和当前 TU 名称的字符串字面量。另一个构造 <code>__func__</code> 是一个局部 <code>static</code> 对象，保存当前函数的名称：

::: info <code>TRACE_PRINT4</code>

向跟踪信息加入当前函数的名称。

~~~c
#define TRACE_PRINT4(F, X)                           \
do {                                                 \
  if (TRACE_ON)                                      \
    fprintf(stderr, "%s:%lu: " F "\n",               \
            __func__, __LINE__+0UL, X);              \
} while (false)
~~~

:::

如果以下调用位于源文件第 24 行，而且所在函数是 <code>main</code>：

~~~c
TRACE_PRINT4("my favorite variable: %g", sum);
~~~

相应输出类似：

~~~console
main:24: my favorite variable: 889
~~~

像本例这样自动使用 <code>fprintf</code> 时，还要牢记另一个陷阱：实参列表中的每个实参都必须具有说明符所要求的正确类型。对 <code>__func__</code> 来说这不成问题：按定义，它是字符数组，所以说明符 <code>"%s"</code> 是正确的。

<code>__LINE__</code> 则不同。我们知道它是表示行号的整数常量，大多数时候只是一个十进制字面量。回顾第 5.3 节中十进制字面量的类型规则可知，它的类型取决于它的值。在嵌入式平台上，<code>INT_MAX</code> 可能只有 32,767，而非常大的源文件（也许由程序自动生成）行数可能更多。遇到这种情况，好的编译器应当发出警告。

::: tip 要点 17.3 #1
<code>__LINE__</code> 中的行号可能无法装入 <code>int</code>。
:::

::: tip 要点 17.3 #2
使用 <code>__LINE__</code> 本身就带有危险。
:::

在宏中，我们通过两种方式避免该问题：要么把类型固定为 <code>unsigned long</code>，[^12] 要么在编译期间把数字转换成字符串。

调用语境中还有另一类信息常常有助于跟踪：实际作为宏实参传入的表达式。由于它常用于调试，C 专门为此提供了特殊运算符 <code>#</code>。在宏展开中，如果 <code>#</code> 出现在某个宏形参之前，传给该形参的实参就会字符串化，也就是把它的全部文本内容放进一个字符串字面量。

下面这个跟踪宏版本包含 <code>#X</code>：

::: info <code>TRACE_PRINT5</code>

加入被求值表达式的文本形式。

~~~c
#define TRACE_PRINT5(F, X)                              \
do {                                                    \
  if (TRACE_ON)                                         \
    fprintf(stderr,                                     \
            "%s:" STRGY(__LINE__) ":(" #X "): " F "\n", \
            __func__, X);                               \
} while (false)
~~~

:::

每次调用宏时，<code>#X</code> 都会替换为第二个实参的文本。对于以下调用：

~~~c
TRACE_PRINT5("my favorite variable: %g", sum);
TRACE_PRINT5("a good expression: %g", sum*argc);
~~~

相应输出类似：

~~~console
main:25:(sum): my favorite variable: 889
main:26:(sum*argc): a good expression: 1778
~~~

由于预处理阶段对这些实参的解释一无所知，这种替换纯粹是文本性的；除空白可能略有调整外，结果应当与源代码中的写法相同。

::: tip 要点 17.3 #3
使用运算符 <code>#</code> 字符串化时，不会展开实参中的宏。
:::

考虑到前面提到的 <code>__LINE__</code> 的潜在问题，我们还希望直接把行号转换成字符串。这样做有两个好处：避开了类型问题，字符串化也完全在编译期完成。如前所述，<code>#</code> 运算符只作用于宏实参，所以直接写 <code># __LINE__</code> 达不到预期效果。

现在考虑下面的宏定义：

~~~c
#define STRINGIFY(X) #X
~~~

字符串化发生在实参替换之前，因此 <code>STRINGIFY(__LINE__)</code> 的结果是 <code>"__LINE__"</code>；宏 <code>__LINE__</code> 没有展开。所以，单靠这个宏还不够。

现在，<code>STRGY(__LINE__)</code> 会先展开成 <code>STRINGIFY(25)</code>（假定当前位置是第 25 行），后者再展开成 <code>"25"</code>，也就是字符串化后的行号：

~~~c
#define STRGY(X) STRINGIFY(X)
~~~

::: tip 要点 17.3 #4
嵌套宏定义可以多次展开宏实参。
:::

我们已经见过另一种只在预处理阶段有效的运算符：记号拼接运算符 <code>##</code>。后文会看到，在编写完整的宏库、需要自动生成其他宏名或函数名时，它能派上什么用场。

[^12]: 希望没有源文件会超过 40 亿行。

## 17.4 可变长度实参列表

我们已经见过接受可变长度实参列表的函数：<code>printf</code>、<code>scanf</code> 及相关函数。它们在形参列表末尾用记号 <code>...</code> 表示这一特性：在若干已知的开头实参（例如 <code>printf</code> 的格式）之后，还可以再跟一个任意长度的实参列表。

第 17.4.2 节会简要讨论怎样定义这类函数。这一特性不具备类型安全性，因而很危险，也近乎过时，所以我们不会着重介绍，而是转而介绍一种类似的特性——可变实参宏。它在很大程度上已经取代了函数的这一特性。

### 17.4.1 可变实参宏

可变长度实参宏，简称“可变实参宏”，用同一个记号 <code>...</code> 表示这一特性。与函数一样，该记号必须出现在形参列表末尾：

::: info <code>TRACE_PRINT6</code>

允许在同一条跟踪信息中打印多个实参。

~~~c
#define TRACE_PRINT6(F, ...)                             \
do {                                                     \
  if (TRACE_ON)                                          \
    fprintf(stderr, "%s:" STRGY(__LINE__) ": " F "\n",   \
            __func__, __VA_ARGS__);                      \
} while (false)
~~~

:::

对 <code>TRACE_PRINT6</code> 而言，这意味着调用时可以在格式实参 <code>F</code> 之后再跟任意的附加实参列表。[^13] 在宏展开中，可以通过标识符 <code>__VA_ARGS__</code> 访问展开后的这个实参列表。因此，下面的调用：

~~~c
TRACE_PRINT6("a collection: %g, %i", sum, argc);
~~~

会把实参转发给 <code>fprintf</code>，并产生输出：

~~~console
main:27: a collection: 889, 2
~~~

遗憾的是，按这个宏现在的写法，<code>__VA_ARGS__</code> 中的列表既不能为空，也不能省略，否则 <code>printf</code> 调用中就会出现空实参。最简单的解决办法是为省略列表的情况单独写一个宏：

::: info <code>TRACE_PRINT7</code>

只跟踪一条文本消息，不打印值。

~~~c
#define TRACE_PRINT7(...)                                \
do {                                                     \
  if (TRACE_ON)                                          \
    fprintf(stderr,                                      \
            "%s:" STRGY(__LINE__) ": " __VA_ARGS__ "\n", \
            __func__);                                   \
} while (false)
~~~

:::

利用 C23 的 <code>__VA_OPT__</code> 特性，可以把两项功能合并进一个宏：

::: info <code>TRACE_PRINT8</code>

既能跟踪值，也能在没有值时跟踪。

该实现使用 C23 特性 <code>__VA_OPT__</code>，在 <code>fprintf</code> 实参末尾加入一个可能为空的可变列表。

~~~c
#define TRACE_PRINT8(F, ...)                             \
do {                                                     \
  if (TRACE_ON)                                          \
    fprintf(stderr, "%s:" STRGY(__LINE__) ": " F "\n",   \
            __func__ __VA_OPT__(,) __VA_ARGS__);         \
} while (false)
~~~

:::

这里，<code>__VA_OPT__(,)</code> 确保只有当可变实参列表 <code>__VA_ARGS__</code> 非空时，才插入逗号。因此，<code>printf</code> 的实参列表始终有效：

~~~c
TRACE_PRINT8("a collection: %g, %i", sum, argc);
TRACE_PRINT8("another string");
~~~

恰好得到我们想要的输出：

~~~console
main:29: a collection: 889, 2
main:30: another string
~~~

实参列表的 <code>__VA_ARGS__</code> 部分也可以像其他宏形参一样字符串化：

::: info <code>TRACE_PRINT9</code>

跟踪时先给出实参的文本表示。

~~~c
#define TRACE_PRINT9(F, ...) \
  TRACE_PRINT8("(" #__VA_ARGS__ ") " F __VA_OPT__(,) __VA_ARGS__)
~~~

:::

下面这些实参的文本表示：

~~~c
TRACE_PRINT9("a collection: %g, %i", sum*acos(0), argc);
~~~

会连同分隔实参的逗号一起插入：

~~~console
main:31: (sum*acos(0), argc) a collection: 1396.44, 2
~~~

还可以利用 <code>__VA_OPT__</code> 特性在两个不同的目标宏之间分派：

~~~c
#define fprintf(STREAM, FORMAT, ...) \
  FPRINTF_II ## __VA_OPT__(Iplus) \
  (STREAM, FORMAT __VA_OPT__(,) __VA_ARGS__)
#define FPRINTF_II(STREAM, FORMAT) fputs(FORMAT, STREAM)
#define FPRINTF_IIIplus(STREAM, FORMAT, ...) \
  fprintf(STREAM, "" FORMAT "", __VA_ARGS__)
~~~

这里，构造 <code>FPRINTF_II ## __VA_OPT__(Iplus)</code> 会把标识符 <code>FPRINTF_II</code> 与 <code>Iplus</code> 拼接起来（形成 <code>FPRINTF_IIIplus</code>），或者与空记号拼接、保持原样。

宏 <code>FPRINTF_II</code>（带两个实参的 <code>fprintf</code>）把调用分派给 <code>fputs</code>；<code>FPRINTF_IIIplus</code>（带三个或更多实参的 <code>fprintf</code>）则分派回 <code>fprintf</code>。后者还用空字符串字面量 <code>""</code> 围住格式字符串，所以只有 <code>FORMAT</code> 展开成字符串字面量时，展开才有效。

到目前为止，实参数量可变的跟踪宏仍要求在格式实参 <code>F</code> 中给出正确的格式说明符。这项工作可能相当繁琐，因为我们必须时刻留意待打印列表中每个实参的类型。把内联函数与宏结合起来，可以帮上忙。先看函数 <code>trace_values</code>。

::: info <code>trace_values</code>

打印值列表的函数。

**备注：** 只通过宏 <code>TRACE_VALUES</code> 调用该函数；宏会提供必要的语境信息。

~~~c
inline
void trace_values(FILE* s,
                  char const func[static 1],
                  char const line[static 1],
                  char const expr[static 1],
                  char const head[static 1],
                  size_t len,
                  long double const arr[len]) {
  fprintf(s, "%s:%s:(%s) %s %Lg", func, line,
          trace_skip(expr), head, arr[0]);
  for (size_t i = 1; i < len-1; ++i)
    fprintf(s, ", %Lg", arr[i]);
  fputc('\n', s);
}
~~~

:::

该函数打印一个 <code>long double</code> 值列表，并在前面加上与此前相同的头部信息。只是这一次，值列表以一个长度已知为 <code>len</code> 的 <code>long double</code> 数组传入。出于稍后会说明的原因，函数总是跳过数组的最后一个元素。它还用函数 <code>trace_skip</code> 跳过形参 <code>expr</code> 的开头部分。

负责把语境信息传给函数的宏分为两层。第一层 <code>TRACE_VALUES</code> 用几种方式整理实参列表：先借助稍后介绍的 <code>ALEN</code> 求出列表的元素个数，再把列表字符串化，最后附上列表本身。这些内容全部传给 <code>TRACE_VALUES0</code>。

::: info <code>TRACE_VALUES</code>

跟踪实参列表，无须指定每个实参的类型。

**备注：** 该宏用所有实参构造一个临时数组，并把它们全部转换为 <code>long double</code>。因此，总能保证隐式转换为该类型。

~~~c
#define TRACE_VALUES(...)              \
TRACE_VALUES0(ALEN(__VA_ARGS__),       \
              #__VA_ARGS__,            \
              __VA_ARGS__              \
              )

#define TRACE_VALUES0(NARGS, EXPR, HEAD, ...)                 \
do {                                                          \
  if (TRACE_ON) {                                             \
    if (NARGS > 1)                                            \
      trace_values(stderr, __func__, STRGY(__LINE__),         \
                   "" EXPR "", "" HEAD "", NARGS,             \
                   (long double const[NARGS]){ __VA_ARGS__ }); \
    else                                                      \
      fprintf(stderr, "%s:" STRGY(__LINE__) ": %s\n",         \
              __func__, HEAD);                                \
  }                                                           \
} while (false)
~~~

:::

这里，去掉 <code>HEAD</code> 后的列表用作类型为 <code>long double const[NARGS]</code> 的复合字面量的初始化器。请注意，计数中包含了 <code>HEAD</code> 字符串，所以 <code>NARGS</code> 至少为 1，数组类型总是有效的。其次，如果 <code>NARGS</code> 为 1，初始化器列表为空；自 C23 起，这是合法的初始化器形式。知道了实参列表的长度，我们还能区分唯一的实参是否只是格式字符串。最后来看宏 <code>ALEN</code>。

::: info <code>ALEN</code>

返回可变列表中的实参数量。

这个版本适用于最多包含 31 个元素的列表。

**备注：** 空实参列表视为含有一个空实参。

~~~c
#define ALEN(...) ALEN0(__VA_ARGS__, \
  0x1E, 0x1F, 0x1D, 0x1C, 0x1B, 0x1A, 0x19, 0x18, \
  0x17, 0x16, 0x15, 0x14, 0x13, 0x12, 0x11, 0x10, \
  0x0E, 0x0F, 0x0D, 0x0C, 0x0B, 0x0A, 0x09, 0x08, \
  0x07, 0x06, 0x05, 0x04, 0x03, 0x02, 0x01, 0x00)
#define ALEN0(_00, _01, _02, _03, _04, _05, _06, _07, _08, \
              _09, _0A, _0B, _0C, _0D, _0F, _0E, _10, _11, \
              _12, _13, _14, _15, _16, _17, _18, _19, _1A, \
              _1B, _1C, _1D, _1F, _1E, ...) _1E
~~~

:::

思路是在 <code>__VA_ARGS__</code> 列表后面附加一个递减数列：31、30、…、0，再用 <code>ALEN0</code> 返回新列表中的第 31 个元素。根据原列表长度的不同，这个元素会是数列中的某个数。事实上不难看出，只要原列表至少有一个元素，返回的数就恰好等于原列表的长度。在我们的用法中，格式字符串总是存在，所以不会遇到空列表这一边界情况。

[^13]: C23 以前，这样的列表不得为空。

### 17.4.2 题外话：可变实参函数

现在简要看一下可变实参函数，也就是带有可变长度实参列表的函数。如前所述，这类函数在声明中用运算符 <code>...</code> 来指定，例如：

~~~c
int printf(char const format[static 1], ...);
~~~

这类函数的接口定义有一个根本问题：与普通函数不同，在调用一侧并不清楚某个实参应当转换成哪种形参类型。例如，调用 <code>printf("%d", 0)</code> 时，编译器无法一下子知道被调用函数期望的是哪一种 0。针对这类情况，C 用一套规则来确定实参要转换成的类型，这套规则与算术运算的规则几乎相同。

::: tip 要点 17.4.2 #1
传给可变形参时，所有算术类型都会像参与算术操作时那样转换；唯一例外是 <code>float</code> 实参，它会转换为 <code>double</code>。
:::

因此，特别是 <code>char</code> 和 <code>short</code> 这样的类型，传给可变形参时会转换成更宽的类型，通常是 <code>int</code>。

到这里还算顺利：我们知道了这类函数是怎样调用的。遗憾的是，这些规则丝毫没有告诉被调用函数，它应当期待哪种类型。

::: tip 要点 17.4.2 #2
可变实参函数必须获得有关可变列表中每个实参类型的有效信息。
:::

<code>printf</code> 系列函数的办法是在格式实参中指明类型，以此绕开这一难题。来看一小段代码：

~~~c
unsigned char zChar = 0;
printf("%hhu", zChar);
~~~

它会对 <code>zChar</code> 求值，将其提升为 <code>int</code>，再把它作为实参传给 <code>printf</code>；后者读取这个 <code>int</code>，并把值重新解释为 <code>unsigned char</code>。这套机制：

**复杂**：函数实现必须为所有基本类型提供专门代码。

**容易出错**：每次调用都要靠实参类型被正确地告知函数。

**苛刻**：程序员必须核验每个实参的类型。

尤其是最后一点，可能造成严重的可移植性缺陷，因为同一个字面量在不同平台上可能具有不同类型。例如，下面这个看似无害的调用：

~~~c
printf("%d: %s\n", 65536, "a small number"); // 不可移植
~~~

在大多数平台上（也就是 <code>int</code> 超过 16 位的平台）都工作良好。但在某些平台上，<code>65536</code> 是 <code>long</code>，它就可能在运行时出错。这类潜在故障中最糟糕的例子是宏 <code>NULL</code>：

~~~c
printf("%p: %s\n", NULL, "print of NULL"); // 不可移植
~~~

第 11.1.5 节已经看到，标准只保证 <code>NULL</code> 是空指针常量，具体采用哪种形式由编译器实现者自行决定：有的选用类型为 <code>void\*</code> 的 <code>(void\*)0</code>；大多数选用类型为 <code>int</code> 的 <code>0</code>。在指针与 <code>int</code> 宽度不同的平台上——例如所有现代 64 位平台——结果就是程序崩溃。[^14]

::: tip 要点 17.4.2 #3
除非把每个实参强制为特定类型，否则使用可变实参函数不具备可移植性。
:::

前面 <code>TRACE_VALUES</code> 使用可变实参宏的情况与此截然不同：那里把可变列表用作数组初始化器，所有元素都会自动转换成正确的目标类型。

::: tip 要点 17.4.2 #4
新接口应避免使用可变实参函数。
:::

为它们受这份罪，实在不值得。不过，如果非实现可变实参函数不可，就需要 C 库头文件 <code>&lt;stdarg.h&gt;</code>。它定义了类型 <code>va_list</code> 和四个类函数宏，用来访问隐藏在 <code>va_list</code> 背后的各个实参。这些宏的伪接口如下：

~~~c
void va_start(va_list ap, ...);
void va_end(va_list ap);
type va_arg(va_list ap, type);
void va_copy(va_list dest, va_list src);
~~~

传统上，<code>va_start</code> 还有第二个实参，也就是被调用函数中 <code>...</code> 之前最后一个形参的名称。自 C23 起，不再需要这项信息，可以省略 <code>va_start</code> 的第二个实参。

与 <code>snprintf_swapped</code> 一样，下面的示例展示了怎样避免自己实现可变实参函数的核心部分。凡是涉及格式化打印的功能，都已经有现成的函数可用。

::: info <code>printf_debug</code>

向调试流 <code>iodebug</code> 打印。

~~~c
[[gnu::format(printf, 1, 2)]]
int printf_debug(const char *format, ...) {
  int ret = 0;
  if (iodebug) {
    va_list va;
    va_start(va);
    ret = vfprintf(iodebug, format, va);
    va_end(va);
  }
  return ret;
}
~~~

:::

这里，<code>iodebug</code> 是一个线程局部指针，可能指向某个有效的 IO 流，也可能不指向任何流：

::: info <code>iodebug</code>

一个简单的调试流。

按照约定，它为空时不产生输出。

它可以在当前线程内设置，这样不同线程就能把各自的调试消息打印到不同的文件或流。

~~~c
thread_local FILE* iodebug = nullptr;
~~~

:::

该函数用 <code>va_start</code> 和 <code>va_end</code> 所做的只有一件事：创建 <code>va_list</code> 实参列表，并把它传给 C 库函数 <code>vfprintf</code>。这样我们就完全不必自己分情况处理、跟踪各个实参。

属性中的 <code>gnu</code> 前缀表明该属性是编译器特有的（这里指 GCC 及相关编译器）。如果函数采用某种已知的形参约定，编译器又能据此给出有用的诊断、确保实参有效，这类附加特性就会非常有用。

现在来看一个接收 n 个 <code>double</code> 值并求和的可变实参函数。

::: details 练习 15
如果可变实参函数只接收类型完全相同的实参，就可以用可变实参宏和接收数组的内联函数替换它。请完成这种替换。
:::

::: info <code>sumIt</code>

一个小而无用的函数，用来展示可变实参函数怎样工作。

~~~c
double sumIt(size_t n, ...) {
  double ret = 0.0;
  va_list va;
  va_start(va);
  for (size_t i = 0; i < n; ++i)
    ret += va_arg(va, double);
  va_end(va);
  return ret;
}
~~~

:::

<code>va_list</code> 由 <code>va_start</code> 调用初始化。请注意，<code>va_start</code> 通过某种魔法直接操纵 <code>va</code>，这里并没有使用取地址运算符 <code>&amp;</code>。随后在循环中，通过 <code>va_arg</code> 宏取得列表中的每个值；该宏要求显式给出它的类型实参，这里是 <code>double</code>。

列表长度也必须由我们自己维护，并作为实参传给函数。实参类型的编码（这里是隐式的）以及列表末尾的判定，都由函数的编写者负责。

::: tip 要点 17.4.2 #5
<code>va_arg</code> 机制无法取得 <code>va_list</code> 的长度。
:::

::: tip 要点 17.4.2 #6
可变实参函数需要一项专门约定来表示列表长度。
:::

[^14]: 这正是完全不应使用 <code>NULL</code> 的原因之一（要点 11.1.5 #1）。

## 17.5 默认实参

C 库中有些函数带有若干形参，可绝大多数时候，传给它们的都是同样乏味的实参。<code>strtoul</code>、<code>strtod</code> 及相关函数就是如此。回想一下，它们接收多个实参：

~~~c
unsigned long int strtoul(char const nptr[restrict],
                          char** restrict endptr,
                          int base);
double strtod(char const nptr[restrict],
              char** restrict endptr);
~~~

第一个实参是待转换的字符串；<code>endptr</code> 会指向字符串中数字结束的位置。此外，对 <code>strtoul</code> 而言，<code>base</code> 是解释字符串时所用的整数进制。

这里有两项特殊约定：<code>endptr</code> 可以是空指针；如果 <code>base</code> 为 0，就根据字符串前缀选择解释方式——以 <code>"0b"</code> 开头时为二进制，以 <code>"0x"</code> 开头时为十六进制，以 <code>"0"</code> 开头时为八进制，否则为十进制。

绝大多数时候，使用这些函数时都用不到 <code>endptr</code> 特性；如果有进制实参，通常也只是把它设为符号值 0。例如：

~~~c:line-numbers
int main(int argc, char* argv[argc+1]) {
  if (argc < 3) return EXIT_FAILURE;
  size_t len = strtoul(argv[1], nullptr, 0);
  double piv = strtod(argv[2], nullptr);
  ...
}
~~~

为了避免这种重复，让读代码的人专注于重要内容，可以引入一层中间宏，在省略 <code>nullptr</code> 和 0 实参时自动补上它们。<code>strtod</code> 只有一个实参需要我们补上，所以事情相对简单：

~~~c:line-numbers=111
#define strtod(NPTR, ...) \
  STRTOD_I __VA_OPT__(I) (NPTR __VA_OPT__(,) __VA_ARGS__)
#define STRTOD_I(NPTR) strtod(NPTR, nullptr)
#define STRTOD_II(NPTR, ENDPTR) strtod(NPTR, ENDPTR)
#define strtof(NPTR, ...) \
  STRTOF_I __VA_OPT__(I) (NPTR __VA_OPT__(,) __VA_ARGS__)
#define STRTOF_I(NPTR) strtof(NPTR, nullptr)
#define STRTOF_II(NPTR, ENDPTR) strtof(NPTR, ENDPTR)
#define strtold(NPTR, ...) \
  STRTOLD_I __VA_OPT__(I) (NPTR __VA_OPT__(,) __VA_ARGS__)
#define STRTOLD_I(NPTR) strtold(NPTR, nullptr)
#define STRTOLD_II(NPTR, ENDPTR) strtold(NPTR, ENDPTR)
~~~

与前例中的 <code>printf</code> 一样，这些宏至少接收一个实参 <code>NPTR</code>；其余实参（如果有）通过 <code>__VA_OPT__(,)</code> 和 <code>__VA_ARGS__</code> 构造附加到列表中。展开结果再分派给不同版本的宏：后缀 <code>_I</code> 表示接收一个实参，<code>_II</code> 表示接收两个实参。

<code>strtoul</code> 的情形更复杂，因为它有两个可以取默认值的实参：<code>endptr</code> 默认为 <code>nullptr</code>，<code>base</code> 默认为 0。我们用更通用的方式来处理它：先做些准备，编写几个为空实参提供默认值的宏。第一个宏处理只有一个预期形参的情况：

::: info <code>DEFAULT1</code>

如果存在第二个实参，就输出它；否则输出默认值 <code>DEF0</code>。

给出超过两个实参时产生错误。

~~~c
#define DEFAULT1(DEF0, ...)          \
  ID_I ## __VA_OPT__(Iplus_DEFAULT)  \
  (DEF0 __VA_OPT__(,) __VA_ARGS__)
#define ID_IIplus_DEFAULT(_01, ...) ID_I(__VA_ARGS__)
~~~

:::

这里的基本思想与前面相同：使用 <code>__VA_OPT__</code> 在两个不同的目标宏之间分派。这些宏的名称以 <code>ID_</code> 开头，后面 <code>I</code> 的个数表示它们期望接收的实参数量。

~~~c:line-numbers=133
#define ID_()
#define ID_I(_01)          _01
#define ID_II(_01, _2)     _01, _2
#define ID_III(_01, _2, _3) _01, _2, _3
~~~

这些宏原样输出收到的实参，所以 <code>ID_I</code> 输出的就是它唯一的实参。<code>DEFAULT</code> 宏收到两个或更多实参时，会进入非空分支 <code>ID_IIplus_DEFAULT</code>；这一分支同样分派给 <code>ID_I</code>，只是传入的是第二个实参。

总之，无论调用 <code>DEFAULT1</code> 时走哪个分支，最终都会调用 <code>ID_I</code>：

~~~text
DEFAULT1(a)       → ID_I(a)          → a
DEFAULT1(a,)      → ID_I(a)          → a
DEFAULT1(a, A)    → ID_IIplus_DEFAULT(A)
                  → ID_I(A)          → A
DEFAULT1(a, A, B) → ID_IIplus_DEFAULT(A, B)
                  → ID_I(A, B)       → 错误
~~~

尤其可以看到，用超过两个实参调用会产生错误，而有效调用都会按预期展开。

对于含有两个默认值的实参列表，我们使用 <code>DEFAULT2</code>：

::: info <code>DEFAULT2</code>

从第三个位置开始输出以逗号分隔的实参，并用前两个位置提供的默认值填充。

给出超过四个实参时产生错误。

~~~c
#define DEFAULT2(DEF0, DEF1, ...)     \
  ID_II ## __VA_OPT__(Iplus_DEFAULT)  \
  (DEF0, DEF1 __VA_OPT__(,) __VA_ARGS__)
#define ID_IIIplus_DEFAULT(DEF0, DEF1, _01, ...) \
  DEFAULT1(DEF0, _01), DEFAULT1(DEF1, __VA_ARGS__)
~~~

:::

这里，<code>ID_IIIplus_DEFAULT</code> 分派到对 <code>DEFAULT1</code> 的两次调用：

~~~text
DEFAULT2(a, b)
  → ID_II(a, b)
  → a, b

DEFAULT2(a, b,)
  → ID_II(a, b)
  → a, b

DEFAULT2(a, b, A)
  → ID_IIIplus_DEFAULT(a, b, A)
  → DEFAULT1(a, A), DEFAULT1(b, )
  → A, b

DEFAULT2(a, b, A,)
  → ID_IIIplus_DEFAULT(a, b, A)
  → DEFAULT1(a, A), DEFAULT1(b, )
  → A, b

DEFAULT2(a, b, A, B)
  → ID_IIIplus_DEFAULT(a, b, A, B)
  → DEFAULT1(a, A), DEFAULT1(b, B)
  → A, B

DEFAULT2(a, b,, B)
  → ID_IIIplus_DEFAULT(a, b, , B)
  → DEFAULT1(a, ), DEFAULT1(b, B)
  → a, B

DEFAULT2(a, b,,, C)
  → ID_IIIplus_DEFAULT(a, b,,, C)
  → DEFAULT1(a,), DEFAULT1(b,, C)
  → a, 错误
~~~

有三个默认实参时，宏 <code>DEFAULT3</code> 能更清楚地展现一般模式：

::: info <code>DEFAULT3</code>

从第四个位置开始输出以逗号分隔的实参，并用前三个位置提供的默认值填充。

给出超过六个实参时产生错误。

~~~c
#define DEFAULT3(DEF0, DEF1, DEF2, ...) \
  ID_III ## __VA_OPT__(Iplus_DEFAULT) \
  (DEF0, DEF1, DEF2 __VA_OPT__(,) __VA_ARGS__)
#define ID_IIIIplus_DEFAULT(DEF0, DEF1, DEF2, _01, ...) \
  DEFAULT1(DEF0, _01), DEFAULT2(DEF1, DEF2, __VA_ARGS__)
~~~

:::

<code>ID_IIIIplus_DEFAULT</code> 把第一个默认值 <code>DEF0</code> 与第一个一般实参 <code>_01</code> 分离出来，传给 <code>DEFAULT1</code>。随后，它去掉一个默认值（<code>DEF0</code>）和一个实参（<code>_01</code>），用剩下的部分“递归”调用 <code>DEFAULT2</code>。

::: details 练习 16
像处理 <code>DEFAULT2</code> 一样，计算 <code>DEFAULT3</code> 所有可能实参组合的结果。
:::

为了更通用地使用这些宏，还要用宏 <code>CALLN</code> 把对 <code>DEFAULTN</code> 的调用包装起来，由 <code>CALLN</code> 实际完成函数调用：

~~~c:line-numbers=160
#define CALL1(FUNC, DEF0, ...) \
  FUNC(DEFAULT1(DEF0, __VA_ARGS__))
#define CALL2(FUNC, DEF0, DEF1, ...) \
  FUNC(DEFAULT2(DEF0, DEF1, __VA_ARGS__))
#define CALL3(FUNC, DEF0, DEF1, DEF2, ...) \
  FUNC(DEFAULT3(DEF0, DEF1, DEF2, __VA_ARGS__))
~~~

有了这些宏，包装 <code>strto</code> 系列函数调用的目标宏如下：

~~~c:line-numbers=167
#define strtoul(...) \
  CALL3(strtoul, "0", nullptr, 0, __VA_ARGS__)
#define strtoull(...) \
  CALL3(strtoull, "0", nullptr, 0, __VA_ARGS__)
#define strtol(...) \
  CALL3(strtol, "0", nullptr, 0, __VA_ARGS__)
#define strtoll(...) \
  CALL3(strtoll, "0", nullptr, 0, __VA_ARGS__)
~~~

调用这些函数时，凡是省略的实参，都会补上默认值 <code>"0"</code>、<code>nullptr</code> 和 <code>0</code>。因此，只用一个实参调用 <code>strtoul</code> 时，替换序列如下：

~~~text
strtoul(argv[1])
  → CALL3(strtoul, "0", nullptr, 0, argv[1])
  → strtoul(DEFAULT3("0", nullptr, 0, argv[1]))
  → strtoul(argv[1], nullptr, 0)
~~~

如果改用三个非空实参调用 <code>strtoul</code>：

~~~text
strtoul(argv[1], ptr, 10)
  → CALL3(strtoul, "0", nullptr, 0, argv[1], ptr, 10)
  → strtoul(DEFAULT3("0", nullptr, 0, argv[1], ptr, 10))
  → strtoul(argv[1], ptr, 10)
~~~

整个替换过程最终得到的，实际上就是开始时的那个记号序列。

## 小结

- 类函数宏比内联函数更加灵活。
- 它们允许我们实现具有可变实参列表的类型安全特性。
- 它们可以为函数接口补充编译期实参核验。
- 它们可以提供来自调用环境的信息。
- 它们可以提供默认实参。
