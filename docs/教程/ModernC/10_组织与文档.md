# 第 10 章：组织与文档

[[toc]]

::: info 本章内容

- 如何为接口编写文档
- 如何解释实现

:::

编程是一项重要的社会、文化和经济活动，要取得成功，就需要某种形式的组织。与编码风格一样，组织代码和项目、编写文档所需的精力，也常常被初学者低估。遗憾的是，我们许多人都经历过这样的时刻：代码写完一段时间后再回来读，却完全想不起它在做什么。

为程序代码编写文档，或者更一般地说，解释程序代码，并非易事。既要提供上下文和必要的信息，又不能乏味地陈述显而易见的事，我们必须在两者之间找到恰当的平衡。请看下面两行：

```c:line-numbers=1
u = fun4you(u, i, 33, 28); // ;)
++i;                      // 递增 i
```

第一行不好：它用了魔数；函数名看不出在做什么；名称 `u` 至少对我来说也没有多少含义。笑脸注释表明程序员写这段代码时很开心，但对偶然读到它的人或维护者没有多少帮助。

第二行的注释多此一举：`++` 运算符的含义，任何稍有经验的程序员都知道。

再与下面的代码比较：

```c:line-numbers=1
/* 33 和 28 很合适，因为二者互素。 */
u = nextApprox(u, i, 33, 28);
/* 定理 3 保证我们可以进入下一步。 */
++i;
```

从这里可以推断出更多内容。我会猜想 `u` 是浮点值，很可能是 `double`，正处于某个近似过程之中。该过程分步进行，`i` 标出当前步骤；此外还需要几个满足互素条件的附加实参。

一般来说，我们要按重要性从高到低，遵循“做什么、为何做、怎样做、以何种方式做”的规则。

::: tip 要点 10 #1（做什么）
函数接口描述要做什么。
:::

::: tip 要点 10 #2（为何做）
接口注释记录函数的用途。
:::

::: tip 要点 10 #3（怎样做）
函数代码展示函数如何组织。
:::

::: tip 要点 10 #4（以何种方式做）
代码注释解释函数细节以何种方式实现。
:::

设想一个供他人使用的大型库项目：所有用户大概都会阅读接口规范（例如手册页的概要部分），大多数用户还会阅读这些接口的说明（手册页的其余部分）。会去查看源代码、了解某个接口的实现怎样或以何种方式完成工作的用户，则要少得多。

从这些规则首先可以得出：代码结构与文档相辅相成。接口规定与实现之间的区别尤其重要。

::: tip 要点 10 #5
分离接口与实现。
:::

这条规则体现为两种不同的 C 源文件：通常以 `".h"` 结尾的**头文件**，以及以 `".c"` 结尾的**翻译单元**（translation unit，TU）。

语法注释在这两种源文件中扮演不同的角色，二者应当明确区分开来。

::: tip 要点 10 #6
为接口编写文档；对实现作出解释。
:::

## 10.1 接口文档

与 Java、Perl 等较新的语言不同，C 没有“内置”的文档标准。不过近年来，许多项目广泛采用了一个跨平台的公有领域工具：[Doxygen](https://www.doxygen.nl/)。它可以自动生成网页、PDF 手册、依赖图等大量内容。即使不使用 Doxygen 或其他同等工具，也应采用它的语法为接口编写文档。

::: tip 要点 10.1 #1
详尽记录接口。
:::

Doxygen 提供许多有助于编写文档的类别，展开讨论则远远超出了本书的范围。这里只看一个示例：

```c:line-numbers=116 [heron_k.h]
/**
 ** @brief 使用 Heron 过程，求 @a a 的 `1/k` 次幂近似值
 **
 ** 换言之，这会计算 @a a 的 @f$k^{th}@f$ 次方根。
 ** 一项特殊功能是：如果 @a k 为 `-1`，则计算
 ** @a a 的乘法逆元。
 **
 ** @param a 必须大于 `0.0`
 ** @param k 不应为 `0`，否则应介于
 ** `DBL_MIN_EXP*FLT_RDXRDX` 和
 ** `DBL_MAX_EXP*FLT_RDXRDX` 之间。
 **
 ** @see FLT_RDXRDX
 **/
double heron(double a, signed k) [[__unsequenced__]];
```

Doxygen 会为该函数生成类似图 10.1 的在线文档，还能生成可纳入本书的格式化文本：

::: info 图 10.1：Doxygen 生成的文档
**`heron_k.h`**

### `heron`

使用 Heron 过程，求 `a` 的 $1/k$ 次幂近似值。

换言之，这会计算 `a` 的 $k$ 次方根。一项特殊功能是：如果 `k` 为 `-1`，则计算 `a` 的乘法逆元。

**形参：**

- `a`：必须大于 `0.0`；
- `k`：不应为 `0`，否则应介于 `DBL_MIN_EXP*FLT_RDXRDX` 和 `DBL_MAX_EXP*FLT_RDXRDX` 之间。

**另见：** `FLT_RDXRDX`

```c
double heron(double a, signed k) [[__unsequenced__]];
```

### `FLT_RDXRDX`

`FLT_RADIX` 的以 2 为底的基数。

后面的一些代码在内部需要它。

```c
#define FLT_RDXRDX something
```
:::

你大概已经猜到，以 `@` 开头的单词对 Doxygen 具有特殊含义：它们引出关键字。这里有 `@param`、`@a` 和 `@brief`。第一个记录函数形参，第二个在文档的其他部分引用这类形参，最后一个提供函数的简短概要。

此外可以看到，注释内部可以使用一定的标记；Doxygen 还能找出翻译单元 `"heron_k.c"` 中定义该函数的位置，以及实现所涉及各函数的调用图。

要让项目组织良好，关键在于代码的使用者能够轻松找到相互关联的内容，而不必四处搜寻。

::: tip 要点 10.1 #2
把代码组织成语义联系紧密的单元。
:::

最常见的做法很简单：把处理某个特定数据类型的所有函数放入同一个头文件。用于 `struct brian` 的典型头文件 `"brian.h"` 如下：

```c:line-numbers=1 [brian.h]
#ifndef BRIAN_H
#define BRIAN_H 1
#include <time.h>

/** @file
 ** @brief 跟随松鸦 Brian
 **/

typedef struct brian brian;
enum chap { sct, en, };
typedef enum chap chap;

struct brian {
    struct timespec ts; /**< 时刻 */
    unsigned counter;  /**< 财富 */
    chap masterof;      /**< 职业 */
};

/**
 ** @brief 取得下一个时刻的数据
 **/
brian brian_next(brian);

// ...
#endif
```

这个文件包含使用该结构体所需的全部接口。它还包含编译这些接口可能需要的其他头文件，并用**包含防护**（这里是宏 `BRIAN_H`）防止重复包含。

## 10.2 实现

阅读优秀程序员写的代码时（你应当经常这样做！），你会发现其中的注释往往很少。不过，只要读者掌握 C 语言基础，这些代码仍可能相当易读。优秀的程序只需解释那些不显而易见的思路和前提（这才是难点）。代码结构本身会展示它做什么以及怎样做。

::: tip 要点 10.2 #1
按字面直接实现。
:::

C 程序是对“要做什么”的描述性文本。前面介绍的实体命名规则，对这段描述性文本是否可读、清晰起着关键作用。另一项要求是让控制流一目了然：复合语句用 `{}` 分组，在视觉上形成清楚可辨的结构，再由表意完整的控制语句连接起来。

::: tip 要点 10.2 #2
控制流必须一目了然。
:::

混淆控制流有许多方法，其中最重要的如下。

**深埋跳转。** `break`、`continue`、`return` 和 `goto`[^6] 语句深埋在 `if` 或 `switch` 语句的复杂嵌套结构中，有时还与循环结构组合在一起。

**蝇斑表达式。** 控制表达式以不同寻常的方式组合大量运算符（例如 `!!++*p--` 或 `a --> 0`），以至于必须用放大镜检查，才能理解控制流接下来去往何处。

以下各节将集中讨论几项对 C 代码可读性和性能至关重要的概念：

- 宏可以方便地简写某项功能；但若使用不慎，也会让使用它的代码变得晦涩，并引入隐蔽的缺陷（10.2.1 节）。
- 如前所述，函数是 C 中实现模块化的首选手段。这里尤其值得关注的是某些函数的一项特殊性质：纯函数只通过接口与程序的其余部分相互作用。因此，无论人还是编译器，都容易理解纯函数，而且纯函数通常能实现得相当高效（10.2.2 节）。
- 我们已经看到，可以用属性把更多信息附在代码上。10.2.3 节将更详细地讨论属性。

[^6]: 这些语句将在 13.2.2 节和 15.6 节讨论。

### 10.2.1 宏

我们已经认识了一种可能被滥用来混淆控制流的工具：宏。希望你还记得 5.6.3 节和 8.1.2 节的内容：宏定义的是文本替换，替换文本几乎可以是任何 C 文本。由于下面要展示的问题，许多项目完全禁止使用宏。不过，C 标准的演进方向并非如此。例如，我们已经看到，类型泛型宏是数值函数的现代接口（见 8.3 节）。宏应当用于初始化常量（5.6.3 节），或者用于实现编译器魔法（如 `errno`，见 8.1.3 节）。

所以，与其拒绝宏，不如试着驯服这头野兽：制定几条简单规则，把可能的损害控制住。

::: tip 要点 10.2.1 #1
宏不应以出人意料的方式改变控制流。
:::

与初学者讨论时，偶尔会冒出下面这个臭名昭著的例子：

```c:line-numbers=1
#define begin {
#define end }
#define forever for (;;)
#define ERRORCHECK(CODE) if (CODE) return -1

forever
begin
    // 做某件事
    ERRORCHECK(x);
end
```

不要这样做。C 程序员的视觉习惯和工具都难以适应这种代码；在复杂代码中使用它们，几乎肯定会出错。

这里的 `ERRORCHECK` 宏尤其危险。从名称上看不出其中可能藏着 `return` 这样的非局部跳转，而它的实现更加危险。考虑下面两行：

```c:line-numbers=1
if (a) ERRORCHECK(x);
else puts("a is 0!");
```

它们展开后会变成：

```c:line-numbers=1
if (a) if (x) return -1;
else puts("a is 0!");
```

`else` 子句（所谓的**悬空 else**）会与我们看不见的最内层 `if` 结合。因此，这等价于：

```c:line-numbers=1
if (a) {
    if (x) return -1;
    else puts("a is 0!");
}
```

这大概会令偶然读到代码的人相当意外。

这并不意味着宏中完全不该使用控制结构，只是这些控制结构不应隐藏起来，也不应产生出人意料的效果。下面这个宏本身也许并不那么直观，但它的**使用**不会带来意外：

```c:line-numbers=1
#define ERROR_RETURN(CODE) \
    do {                   \
        if (CODE) return -1; \
    } while (false)
```

这个宏的名称明确表明其中可能有 `return`。替换文本还处理了悬空 `else` 问题：

```c:line-numbers=1
if (a) ERROR_RETURN(x);
else puts("a is 0!");
```

与前面悬空 `else` 的情形不同，下面展开后的代码结构符合预期，`else` 与第一个 `if` 关联：

```c:line-numbers=1
if (a) do {
    if (CODE) return -1;
} while (false);
else puts("a is 0!");
```

`do-while(false)` 技巧显然很丑，不应滥用。不过，这是一个标准技巧：用 `{}` 复合语句包围一条或多条语句，既不改变肉眼可见的程序结构，也不会引发悬空 `else` 等问题。

::: tip 要点 10.2.1 #2
类函数宏在语法上应当表现得像函数调用。
:::

可能的陷阱包括：

**有 `if` 而没有 `else`。** 前面已经演示过。

**尾随分号。** 它可能以出人意料的方式终止外层控制结构。

**逗号运算符。** 逗号在 C 中含义不唯一。多数上下文把它用作列表分隔符，例如函数调用、枚举项声明或初始化式；在表达式上下文中，它却是控制运算符。请避免使用。

**可继续结合的表达式。** 把表达式放入非平凡上下文后，它会以意想不到的方式与运算符结合。[练习 7] 在替换文本中，用圆括号包围形参和表达式。

**多次求值。** 宏是文本替换。如果宏形参使用两次（或更多次），其效果也会发生两次。[练习 8]

::: details 练习 7
设宏 `sum(a, b)` 实现为 `a+b`。`sum(5, 2)*7` 的结果是什么？
:::

::: details 练习 8
设 `max(a, b)` 实现为 `((a) < (b) ? (b) : (a))`。对 `max(i++, 5)` 求值会发生什么？
:::

### 10.2.2 纯函数

我们自行声明的 C 函数，如 `size_min`（4.5 节）和 `gcd`（7.3 节），在表达能力上受到限制：它们不操作对象，而是操作值。从某种意义上说，它们扩展的是表 4.1 中的值运算符，而不是表 4.2 中的对象运算符。

::: tip 要点 10.2.2 #1
函数形参按值传递。
:::

也就是说，调用函数时，所有实参都会先求值，所得的值用来初始化各个形参（函数的局部对象）。随后函数完成自己的工作，再通过返回值送回计算结果。

目前，要让两个函数操作同一个对象，唯一办法是声明一个对两个函数都可见的对象。这样的**全局对象**缺点很多：它们使代码缺乏灵活性（所操作的对象固定不变），使行为难以预测（修改位置四处分散），也难以维护。

::: tip 要点 10.2.2 #2
全局对象不受欢迎。
:::

具有以下两项性质的函数称为**纯函数**：

- 除返回值外，函数没有其他效果；
- 函数的返回值只取决于形参。

执行纯函数时，我们唯一关心的是结果，而结果只取决于传入的实参。从优化角度看，纯函数可以挪动位置，甚至可以与其他任务并行执行。只要形参已经可用，它就可以随时开始执行，只需在结果被使用之前完成即可。

函数只要通过返回值以外的途径改变了抽象状态机，就不再是纯函数。例如：

- 函数不通过实参，而以其他方式读取程序的可变状态；
- 函数修改全局对象；
- 函数在各次调用之间保留持久的内部状态；[^9]
- 函数执行 IO。[^10]

[^9]: 可以使用局部 `static` 对象，在对同一函数的各次调用之间建立持久状态。13.2 节将介绍这一概念。
[^10]: 例如，使用 `printf` 就会发生这种 IO。

纯函数是完成小任务的绝佳模型，但面对更复杂的任务时就相当受限。另一方面，优化器偏爱纯函数，因为它们对程序状态的影响只需用形参和返回值就能描述。纯函数对抽象状态机的影响十分局部，很容易描述。

::: tip 要点 10.2.2 #3
只要可能，就把小任务表述为纯函数。
:::

如果先接受在各处复制一点数据的做法，借助纯函数就能走得出人意料地远，甚至能实现面向对象的编程风格。考虑下面用于有理数算术的结构体类型 `rat`：

```c:line-numbers=8 [rationals.h]
struct rat {
    bool sign;
    size_t num;
    size_t denom;
};
```

这是该类型的一种朴素实现，只供这次学习使用，不应把它当作库。为简单起见，分子和分母采用相同类型（`size_t`），并在成员 `sign` 中记录数的符号。第一个纯函数 `rat_get` 接收两个数，并返回表示二者之商的有理数。

```c:line-numbers=5 [rationals.c]
rat rat_get(signed sign, size_t num, size_t denom)
    [[__unsequenced__]] {
    rat ret = {
        .sign = (sign < 0),
        .num = num,
        .denom = denom,
    };
    return ret;
}
```

可以看到，这个函数相当简单。它只是用正确的符号、分子和分母值初始化局部对象 `ret`，再将其返回。（译者注：原书此处称“初始化一个复合字面量”，与代码不符，已改正。）请注意，按这种方式定义有理数时，同一个有理数可以有多种表示。例如，$6/15$ 与 $2/5$ 是同一个数。

为处理表示之间的这种等价关系，需要一些维护函数。核心思想是，这类有理数应当始终**规范化**，也就是采用让分子和分母所含因子最少的表示。这样不仅更便于人理解，也可能避免算术运算期间发生溢出。这里的 `gcd` 就是此前介绍过的那个函数。

```c:line-numbers=14 [rationals.c]
rat rat_get_normal(rat x) [[__unsequenced__]] {
    size_t c = gcd(x.num, x.denom);
    x.num /= c;
    x.denom /= c;
    return x;
}
```

另一个函数执行规范化的逆操作，把分子和分母同乘一个冗余因子：

```c:line-numbers=21 [rationals.c]
rat rat_get_extended(rat x, size_t f) [[__unsequenced__]] {
    x.num *= f;
    x.denom *= f;
    return x;
}
```

这样便可定义供他人使用的函数 `rat_get_prod` 和 `rat_get_sum`。`rat_get_prod` 先用简单的办法算出结果的表示：分子乘分子，分母乘分母。所得表示可能尚未规范化，所以返回前要调用 `rat_get_normal`。

```c:line-numbers=27 [rationals.c]
rat rat_get_prod(rat x, rat y) [[__unsequenced__]] {
    rat ret = {
        .sign = (x.sign != y.sign),
        .num = x.num * y.num,
        .denom = x.denom * y.denom,
    };
    return rat_get_normal(ret);
}
```

`rat_get_sum` 稍微复杂一些。必须先找出公分母，才能计算结果的分子；还必须跟踪两个有理数的符号，判断分子应当怎样相加。

```c:line-numbers=36 [rationals.c]
rat rat_get_sum(rat x, rat y) [[__unsequenced__]] {
    size_t c = gcd(x.denom, y.denom);
    size_t ax = y.denom / c;
    size_t bx = x.denom / c;
    x = rat_get_extended(x, ax);
    y = rat_get_extended(y, bx);
    assert(x.denom == y.denom);

    if (x.sign == y.sign) {
        x.num += y.num;
    } else if (x.num > y.num) {
        x.num -= y.num;
    } else {
        x.num = y.num - x.num;
        x.sign = !x.sign;
    }
    return rat_get_normal(x);
}
```

可以看到，这些函数全都是纯函数，因此很容易使用，在我们自己的实现中也是如此。[练习 11][练习 12] 唯一要注意的是，必须始终把函数返回值赋给某个对象，例如第 40 行对 `x` 的赋值。否则，由于我们操作的不是对象 `x` 本身，而只是它的值，函数执行期间所做的改动就会丢失。[^13]

如前所述，反复复制可能使编译所得的代码不如理论上那么高效。不过这根本算不上大问题：优秀的编译器可以把复制操作的开销保持在相当低的水平。启用优化后，编译器在处理这类函数时，通常可以直接就地操作要返回的结构体。此外，这种担忧可能完全为时过早：程序也许本来就短小精悍，或者真正的性能问题在别处。以我们目前的编程水平，这样通常已经完全够用。以后我们会学习如何借助内联函数（16.1 节）和许多现代工具链提供的链接时优化，高效运用这项策略。

清单 10.1 列出了目前见过的所有 `rat` 类型接口（第一组）。我们也已经看过操作 `rat` 指针的其他函数接口，11.2 节会更详细地解释它们。

### 10.2.3 属性

属性是 C23 新近引入的特性，设计初衷是作为一种重要的注解工具，帮助编译器和工具的实现者开发新特性。例如，清单 10.1 中的 `[[__unsequenced__]]` 属性表示其中大多数函数都具有未定序性质，这是纯函数性质的推广。这样一来，即使编译应用程序代码时只能看到这个头文件，编译器仍可对这些函数作出很强的假设。如果函数没有指针形参，也不返回指针，它就是纯函数，返回值只取决于调用时传入的实参值。如果它有指针形参或返回指针（例如 `rat_normalize`，见后文讨论），函数调用可能带来的相互干扰，也只限于通过这些指针可见的对象。

C23 引入了少量标准属性，每个属性还另有一个带双下划线、在宏面前更安全的变体，如 `__unsequenced__`：

```text
deprecated   fallthrough  maybe_unused  nodiscard
noreturn     unsequenced  reproducible
```

我们已经见过其中大多数属性的实际用法。目前只有两个属性 `[[deprecated]]` 和 `[[nodiscard]]` 可以接收字符串形式的实参：

```c
[[deprecated("tell me all about it")]]
```

这些属性的含义如下：

- `[[deprecated]]` 属性表示不应直接使用它所附着的特性。原因可能有多种，主要原因大概是该特性已经过时（将来可能被删除），或者并非公共接口的一部分。使用带有该属性的特性时，编译器通常会发出诊断。不过，与类似的实现定义属性不同，在另一个同样弃用的特性内部使用弃用特性时，不应发出诊断。13.1.1 节有一个完整示例，突出展示 `[[deprecated]]` 的这一性质。
- 如 3.3 节所见，`switch` 语句的控制流可能非常复杂。为避免错误，许多编码风格试图限制控制流，把没有 `break` 就从一个 `case` 贯穿到另一个 `case` 视为错误。`[[fallthrough]]` 属性表明这种控制流是有意为之，不应发出诊断。
- 有时我们会声明或定义一些后面不一定用到的标识符，例如为了文档而写出的未使用形参名，或者头文件中的 `static` 函数（包含该头文件的代码未必都会用到它们）。`[[maybe_unused]]` 可以避免在这些情形中发出诊断。
- `[[nodiscard]]` 属性的主要用途，是表明函数的返回值很重要，始终不应忽略。对存储分配而言，这一点尤其重要；13.1.1 节也展示了这种用法。
- 如 8.8 节所见，`[[noreturn]]` 属性同样与函数关联。它表示函数**绝不会**返回调用方，编译器因而可以优化周围代码。
- `[[unsequenced]]` 和 `[[reproducible]]` 属性将在 16.3 节详细讨论。

除标准属性外，还有**带前缀的属性**，其名称形式如下：

```text
prefix::suffix
```

其中 `prefix` 是一个标识符，通常由编译器或工具的实现者选定；`::` 是 C 中其他地方都没有出现过的新语法记号；`suffix` 是表示具体特性或性质的标识符。我目前所知的前缀来自三大编译器家族：`clang`、`gnu` 和 `msvc`。但也许出人意料的是，它们之间并没有严格的界限。例如，Clang 编译器实现了 GNU 编译器的许多属性，并继续为它们保留 `gnu` 前缀。

一般来说，这类带前缀的属性也可以接收实参；唯一的语法约束，是实参中的 `()`、`[]` 和 `{}` 必须正确嵌套、成对平衡。实现显然可以拒绝任何无法理解的内容，但从标准角度看，这就是唯一限制。例如，GCC 和 Clang 支持 `format` 属性：

```c
#if __has_c_attribute(__gnu__::__format__)
[[__gnu__::__format__(__printf__, 3, 4)]]
#endif
int snprintf(char *buf, size_t size, const char *frmt, ...);
```

这里的属性表明，`snprintf` 在位置 3 接收一项 `printf` 风格的格式规定，可变参数列表从位置 4 开始。有了这些信息，如果格式不是字符串字面量，或者格式说明符收到错误类型的实参，编译器就可以发出警告。

C23 在引入属性特性的同时，还提供属性检验特性 `__has_c_attribute`。它可以像宏所用的 `defined` 一样，用在预处理条件指令中。在前面的示例中，只有平台支持这个特有属性 `__gnu__::__format__` 时，才会使用它。

检验特性本身是否存在，也可以查询。为了照顾尚未实现该特性的平台，我们的后备头文件 `<c23-fallback.h>` 包含以下代码。如果编译器没有 `__has_c_attribute` 特性，它几乎肯定也完全没有实现属性。

请注意，无论是标准属性，还是带前缀属性中的标识符，都不是关键字。因此，它们可以而且必然会与应用程序宏相互作用，后果可能是灾难性的。

::: tip 要点 10.2.3 #1
属性中的标识符可能被预处理替换。
:::

```c:line-numbers=319 [c23-fallback.h]
#ifndef __has_c_attribute
#define __has_c_attribute(X) 0
#endif
```

因此，C23 为所有标准属性另行规定了前后都带双下划线的形式，并建议带前缀的属性也都另外提供这种形式。带双下划线的标识符是保留标识符，因而保证不会与应用程序定义的宏发生相互作用。

::: tip 要点 10.2.3 #2
在头文件中使用属性的双下划线形式。
:::

## 小结

- 对程序的每个部分，都必须区分对象（我们在做什么？）、目的（为何做？）、方法（怎样做？）和实现（以何种方式做？）。
- 函数接口和类型接口是软件设计的精髓，日后修改代价高昂。
- 实现应当尽可能按字面直接表达，控制流应当尽可能一目了然。应避免复杂的推理；确有必要时，应把推理明确写出来。
- 属性可以为接口和实现增添宝贵信息，从而改善诊断、安全性、安保能力和性能。
