# 6.6 编码规范、静态分析与评审

在许多嵌入式项目的代码评审中，常常会出现一种令人疲惫的循环：同一个项目在不同迭代阶段被反复指出同质化的低级缺陷——将 16 位整数隐式赋值给 8 位对象导致的溢出截断、有符号数与无符号数混合比较引发的逻辑倒转、中断服务函数与主循环共享标志时遗漏了 `volatile` 限定符、或是试图用 `1 << 31` 构造最高位掩码而触发未定义行为。这些隐患的本质特征非常一致：在肉眼审查时极易被忽略，而编译器与静态分析工具若配置得当则能够百分之百在构建期拦截。

让稀缺的人工反复去充当编译器的“肉眼过滤器”，是对工程效率的严重损耗。合理的质量保障链条应当实现明确的层次分工：依托严密的编码规范明确界定受限的 C 语言安全子集；借助编译器告警矩阵与静态分析引擎将能够被语法树识别的潜在缺陷彻底拦截在自动化流水线中；将宝贵的人工代码评审带宽收拢至工具无法触达的系统级上下文——审查软硬件交互的原子性、超时退出的完备性以及中断临界区的保护边界。

## 1. 为什么嵌入式需要编码规范

桌面程序里一个未定义行为，通常表现为某个输入下崩溃，用户重开一次就好了。固件里同样一个未定义行为，可能表现为设备在某个温度、某个电压、某个恰好到来的中断组合下死机；现场没有调试器，复现条件说不清，唯一的补救办法是升级——而升级本身正是 [6.4](/教程/正文/嵌入式/6_质量_安全与交付/6_4_Bootloader与固件升级) 要保证不出错的那件事。

未定义行为与实现定义行为在 C 里到处都是，编译器不会为每一个都报警告。`int` 溢出是未定义行为，编译器可以假定它不发生，于是 `if (x + 1 < x)` 这样的检查会被优化掉。有符号右移、位域的内存布局、`char` 是否有符号是实现定义行为，换编译器或换优化等级，结果就变了。结构体里成员的填充字节、联合体的读写顺序、`volatile` 的访问次数，这些细节在 [语法和标准库 16.5 遵从性和行为](/教程/正文/语法和标准库/16_对象与内存模型/16_5_遵从性和行为) 里有系统讲解。

编码规范把语言子集收窄到「不容易出错的那部分」。规则定下来，团队里每个人的写法趋同，评审时不用再讨论风格，工具也能照着规则自动检查。

工具只能自动检查规范的一部分。查不出来的规则只能靠人执行，所以这部分规则最该写成文字。

## 2. 三个常用规范

嵌入式 C 有三份常见的规范，定位不同。

**MISRA C** 是汽车工业发起、现在由 MISRA 协会维护的规范，2025 年 3 月发布的 C:2025 是当前版本。它分「指令」（directive）与「规则」（rule）两类，每条有强制（mandatory）、必需（required）、建议（advisory）三个等级。规则原文受版权保护，要完整执行得购买文档；执行时还要为每条不适用或无法执行的规则写偏离记录（deviation）。它的强项是把语言里容易出错的角落几乎全部覆盖，代价是规则多、学习曲线陡。

**SEI CERT C** 由卡内基梅隆大学软件工程研究所维护，免费在线，按「安全」组织：每条规则对应一类可被利用的缺陷（缓冲区溢出、整数溢出、格式化字符串、竞争条件），编号形如 INT30-C、STR31-C。它比 MISRA 宽松，但每条规则都配了正例、反例与后果说明，适合当学习材料。

**BARR-C:2018** 由 Barr Group 发布，免费，偏重风格与可读性：命名、缩进、注释、函数长度、魔数。它不深入语言细节，与 MISRA 可以共存——很多团队用 BARR-C 管风格、用 MISRA 的子集管正确性。

| 方面 | MISRA C:2025 | SEI CERT C | BARR-C:2018 |
| --- | --- | --- | --- |
| 定位 | 安全相关系统的语言子集 | 安全漏洞的防范规则 | 风格与可读性 |
| 获取方式 | 购买（规则原文受版权保护） | 免费在线 | 免费下载 |
| 规模 | 规则与指令合计上百条，按等级分类 | 上百条规则，按缺陷类别分章 | 一百多条风格与可读性条款 |
| 是否要求偏离记录 | 是，完整流程的一部分 | 不强制 | 不要求 |
| 适用场合 | 汽车、医疗、工业安全 | 任何 C 项目，尤其联网设备 | 所有项目的风格基线 |

三份规范都覆盖不到的一类问题，是「业务逻辑对不对」。规范管的是「这样写会不会出错」，评审管的是「这样做对不对」。

::: concept emb-rule-deviation title="偏离规则必须记录"

采用一份规范的必需规则时，如果某条规则在项目里确实无法执行（例如某个第三方库必须原样使用），正确的做法是写一条偏离记录：说明规则编号、涉及的代码位置、不能执行的原因、替代的防范措施、批准人。偏离记录本身也是评审对象。悄悄关掉一条规则、不留下任何文字，等于这条规则从来没有存在过。

:::

### 2.1 最常被违反的几条

MISRA C 的规则里，嵌入式项目最常撞上的几条都与「C 的整数提升」有关。下面三条先记住：

- 本质类型（essential type）：MISRA 把每个表达式归类为有符号、无符号、布尔、字符、浮点、枚举之一，「本质类型」比 C 的声明类型更严格。`uint8_t` 与 `uint16_t` 相加，在 C 里都被提升为 `int`，结果是有符号的；MISRA 认为这是有符号与无符号的混合运算，报规则 10.x。
- `switch` 必须有 `default`：没有 `default` 的 `switch` 在新增枚举值后会静默走空，MISRA 规则 16.4 要求每个 `switch` 都有 `default` 分支。
- 运行期不使用动态内存：`malloc`/`free` 在嵌入式里带来的碎片与不确定性，MISRA 规则 21.3 直接禁止。这与 [4.5 内存与资源管理](/教程/正文/嵌入式/4_RTOS与固件架构/4_5_内存与资源管理) 的静态分配主张一致。

在通常的商业产品开发中，一种兼顾工程质量与落地成本的务实策略是采用“BARR-C 格式规范 + 精选的 MISRA 核心规则集 + 严苛的编译器告警”这一组合拳。这种方案既能以较低的维护成本收回大部分安全性收益，又不会给团队带来过度繁重的文档负担。唯有当项目涉及汽车电子（ISO 26262）或功能安全认证时，才需要严格落实 MISRA 全集并建立完备的偏离归档流程。

## 3. 编译器警告是第一道工具

静态分析的第一道工具不需要安装，编译器自带。默认的 `-Wall -Wextra` 只打开了常用的一部分，嵌入式项目应该再加几个：

| 选项 | 查什么 | 为什么嵌入式需要 |
| --- | --- | --- |
| `-Wall -Wextra` | 常用警告集合 | 基线 |
| `-Wconversion` | 隐式转换可能改变值 | 整型宽度不一致、截断 |
| `-Wsign-conversion` | 有符号与无符号之间的隐式转换 | 比较与位移最容易出错的地方 |
| `-Wshadow` | 内层对象遮蔽外层同名对象 | 大函数里改错了对象 |
| `-Wcast-align` | 强制转换后对齐要求变高 | 把字节缓冲区当 32 位字访问时，LDM/STM 与独占访问会出错 |
| `-Wdouble-promotion` | `float` 被隐式提升为 `double` | Cortex-M3 没有 FPU，双精度全靠软件 |
| `-Wundef` | 在 `#if` 里使用未定义的宏 | 拼错的配置宏静默取 0 |
| `-Wformat=2` | 格式串与实参不匹配，含 `%n` 相关 | 打印调试信息时的常见错误 |
| `-Wshift-overflow=2` | 移位量超出类型宽度 | `1 << 31` 这类写法 |
| `-Wswitch-default` | `switch` 缺少 `default` 分支 | 新增枚举值后静默走空 |
| `-Wnull-dereference` | 可能解引用空指针 | 初始化顺序问题 |

CI 里再加 `-Werror`，让警告直接变成构建失败。团队里常有的顾虑是「第三方代码报一堆警告」。可行的做法是用 `-isystem` 引入第三方头文件、对第三方源文件单独编译并关掉这套选项；把警告整个关掉，自家代码的问题也会一起被吞掉。

`-Wdouble-promotion` 在没有 FPU 的 Cortex-M3 上尤其该打开。C 的算术转换规则规定：`float` 与 `double` 运算时，`float` 被提升为 `double`；一个不带 `f` 后缀的浮点常量是 `double`。于是 `x * 3.14159265358979` 里的 `x` 先被转成 `double`，乘法在双精度里做完，结果再转回 `float`。F103 没有任何浮点指令，双精度乘法要调用 __aeabi_dmul，代码体积与执行时间都是单精度的好几倍：

::: terminal title="bash - 同一个函数，常量带不带 f 后缀的链接体积"

```text
# return x * 3.14159265f;  （单精度）
   text	   data	    bss	    dec	    hex	filename
    380	      0	      0	    380	    17c	fp_a.elf

# return x * 3.14159265358979;  （常量是 double，x 被提升）
   text	   data	    bss	    dec	    hex	filename
   1684	      0	      0	   1684	    694	fp_b.elf
```

:::

一个字符的差别，链接进固件的代码多了 1.3 KiB。用 `objdump` 看符号表，双精度版本引入了 `__aeabi_dmul`、`__aeabi_dadd`、`__aeabi_f2d`、`__aeabi_d2f` 一整套软件浮点例程；在没有 FPU 的 M3 上，每一次乘法都要执行其中一段软件循环。

### 3.1 一段有问题的固件

下面这段代码每一处都对应一个真实项目里见过的错误，全部在开启上述警告后编译。这里省掉了头文件与 `main`，警告里的行号对应完整文件：

```c
static uint8_t g_rx_flag; /* ISR 写、主循环读，但不是 volatile */

void isr_rx(void) {
    g_rx_flag = 1;
}

int buffer_full(int used, unsigned capacity) { /* 1. 有符号与无符号比较 */
    if (used > capacity) {
        return 1;
    }
    return 0;
}

void store_length(uint8_t *dst, uint16_t len) { /* 2. 隐式截断 */
    dst[0] = len;
}

float scale(float x) { /* 3. float 被提升为 double */
    return x * 3.14159265358979;
}

uint32_t high_bit(void) { /* 4. 1 << 31 是未定义行为 */
    return 1 << 31;
}

int command_period(int cmd) { /* 5. switch 没有 default */
    switch (cmd) {
    case 0:
        return 10;
    case 1:
        return 100;
    }
    return -1;
}

void log_count(int count) { /* 6. 格式串按无符号解释有符号实参 */
    char line[32];
    snprintf(line, sizeof line, "count=%u\n", count);
    puts(line);
}
```

逐条看。第一条，`used` 是 `int`、`capacity` 是 `unsigned`，比较时 `used` 被转成 `unsigned`，`-1` 变成 0xFFFFFFFF，`buffer_full(-1, 8)` 返回 1——语义完全反了。第二条，`len` 是 300 时 `dst[0]` 存进去的是 44，高字节被丢掉，这种错误在协议实现里最致命。第三条，两行警告指的是同一件事：常量是 `double`，所以乘法在双精度里做，结果再截回 `float`。第四条，`1 << 31` 对 `int` 是未定义行为，GCC 在这里给出的是「需要 33 位」的诊断，换个编译器可能什么都不说；写成 `1u << 31` 就没有这个问题。第五条 `switch` 缺 `default`，GCC 默认不报，要单独加 `-Wswitch-default`。第六条，`%u` 期待 `unsigned`，实参是 `int`，负数会被打印成一个巨大的无符号数。

这段代码里还有一个警告没出现，但它是最危险的：`g_rx_flag` 没有 `volatile`。GCC 不会为缺少 `volatile` 的对象报警告，因为从语言角度它是合法的。用一个最小的等待循环对比两种写法：

```c
static uint8_t g_flag_plain;
static volatile uint8_t g_flag_vol;

void wait_plain(void) {
    while (g_flag_plain == 0u) {
    }
}

void wait_vol(void) {
    while (g_flag_vol == 0u) {
    }
}
```

`-O2` 编出来的结果完全不同：

```text
   4:	4a02      	ldr	r2, [pc, #8]	@ (10 <wait_vol+0xc>)
   6:	7813      	ldrb	r3, [r2, #0]            ; 每一轮都重新读
```

没有 `volatile` 的那一版，编译器把 `while (g_flag_plain == 0)` 优化成了 `b.n 0` 的无条件跳转——它「知道」`g_flag_plain` 在循环里没被修改，所以只读一次。ISR 改了这个对象，循环也看不见。这类问题只能靠 `volatile` 的使用规范加上人工评审解决，工具帮不上忙。

## 4. 静态分析器

编译器只做局部检查，跨函数、跨路径的问题要靠静态分析器。三种免费工具覆盖的深度不同。

### 4.1 GCC -fanalyzer

`-fanalyzer` 是 GCC 10 起内置的路径敏感分析器：它把函数的控制流展开成图，沿着路径检查空指针解引用、释放后使用、内存泄漏、重复释放。它不需要额外安装，与编译器用同一套语法，缺点是慢——对一个中型工程可能慢十倍。

下面这段代码有两处问题，都是只有沿着特定路径才能看到的：

```c
typedef struct node {
    char name[16];
    struct node *next;
} node_t;

int append_command(const char *name) {
    node_t *n = malloc(sizeof *n);
    if (n == NULL) {
        return -1;
    }

}
```

### 4.2 clang-tidy

clang-tidy 基于 Clang 的 AST 做检查，规则丰富得多，分几个命名空间：`bugprone-*` 查易错写法，`cert-*` 实现 CERT C 的规则，`readability-*` 查可读性，`modernize-*`、`performance-*` 面向 C++。它需要一个 `compile_commands.json` 才知道每个文件的编译选项，CMake 加 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` 就会生成。

工程根目录放一份 `.clang-tidy`：

```yaml

Checks: >
  bugprone-*,
  cert-*,
  readability-*,
  -readability-magic-numbers,
  -readability-identifier-length,
  -readability-function-cognitive-complexity,
  -bugprone-easily-swappable-parameters,
  -bugprone-narrowing-conversions,
  -cert-err33-c,
  -readability-uppercase-literal-suffix
WarningsAsErrors: ''
HeaderFilterRegex: '.*'
FormatStyle: file
CheckOptions:
  - key: readability-identifier-naming.FunctionCase
    value: lower_case
  - key: readability-identifier-naming.VariableCase
    value: lower_case
  - key: readability-identifier-naming.GlobalConstantCase
```

### 4.4 误报管理

静态分析器一定会有误报，判断是不是误报本身也要花时间。三条做法能让这件事可控：

- 行内抑制必须写理由。`// cppcheck-suppress arrayIndexOutOfBounds` 后面跟一句为什么这里安全，否则下一个人不知道是误报还是没看见。
- 维护基线。老代码里已有的告警记进基线文件，CI 只要求「新增代码零告警」，避免一次引入工具就要求全工程整改。
- 只让高置信度的检查进入 CI。`-fanalyzer` 适合本地跑；`bugprone-*` 与 cppcheck 的 `warning` 级别适合进 CI；`readability-*` 不进 CI，留在编辑器的格式化里。

::: tip 抑制注释写理由

```c
/* MISRA 10.1 偏离：这里的位掩码必须按无符号处理，
   上游协议规定该字段为无符号数，见 PROTO-42。 */
uint32_t mask = (uint32_t)value & 0x0000FFFFu;
```

一句理由加一个工单号，比任何口头约定都管用。

## 5. 代码评审

工具能查的都查完之后，人看的应该是工具看不到的东西：这段代码在中断里做了什么、这个共享数据有没有保护、这个等待有没有可能永远不返回。

评审的第一步是看 CI 有没有绿，然后才读代码。警告、静态分析、单元测试、体积预算都过了再安排人看，否则评审者会把时间花在本来能自动发现的问题上。

### 5.2 一条评审意见的写法

评审意见要让人能改。结构是「问题 + 依据 + 建议」，三句话说完：

::: compare left-title="只说有问题" right-title="给出依据与建议"

```text
这里是不是有问题？
```

---

```text
USART1_IRQHandler 里调用了 printf，会把 newlib 的格式化代码
与串口发送拉进中断上下文，发送一个字节要等 TXE，中断可能
持续几毫秒，期间同优先级或更低优先级的中断都被推迟（4.4）。
建议在 ISR 里只把字节放进环形缓冲区并置一个标志，打印
留给任务或在调试构建里才开。
```

:::

第一句话说了位置与问题，第二句给出影响与依据，第三句给出可行的改法。评审者不需要自己猜「他希望我改成什么样」，被评审者也不用反复问「为什么」。

评审意见里避免「我觉得」「不太好吧」这类措辞，也避免只说「这样写不对」却不说明理由。评审意见针对代码本身，别去评价写代码的人。

### 5.3 几个常被漏掉的问题

有些问题工具查不出、评审时也容易一眼带过，这里单独说几条：

**`volatile` 不能当同步原语用。** 两个任务共享一个 `volatile` 计数器，`++` 仍然是读-改-写三步，不加锁就会丢更新。`volatile` 只保证每次真的访存，不保证原子性。

**等待没有超时。** `while (!(USART1->SR & USART_SR_TC)) {}` 在时钟配置错误时永远不返回，看门狗复位之后现场什么都没留下。加一个循环计数上限，超时返回错误码。

**ISR 里访问非原子的大对象。** 32 位对象在 Cortex-M3 上一条指令读写完；64 位对象和大数组要拆成几条指令，中途可能被打断。ISR 写一个结构体、任务读同一个结构体，读到一半被打断就是撕裂读。

**位操作写错寄存器。** `GPIOA->ODR |= 1 << 5` 是读-改-写，如果另一个中断同时在改同一个端口，可能丢掉对方的修改；`GPIOA->BSRR = 1u << 5` 是单次写，没有这个问题。

**错误处理吞掉了错误码。** `(void)flash_write(...)` 之后继续往下跑，写失败时后续操作全在错误的前提上。

## 6. 接入流程

三件事按顺序接进开发流程，每件都在最早能拦住问题的位置：

```mermaid
flowchart LR
    A["写代码"] --> B["pre-commit<br/>clang-format"]
    B --> C["CI：编译<br/>-Werror + 静态分析"]
    C --> D["CI：单元测试<br/>+ 体积预算"]
    D --> E["人工评审<br/>检查清单"]
    E --> F["合并"]
```

`clang-format` 在提交前把格式统一，评审时就不用讨论缩进与空格。仓库根目录的 `.clang-format` 按 README 的约定写成 LLVM 风格、4 空格：

```yaml
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
```

CI 里做的检查依次是：`-Wall -Wextra` 加第 3 节那套选项，`-Werror`；clang-tidy 的 `bugprone-*` 与 `cert-*`；cppcheck 的 `warning` 级别；单元测试；体积预算（[6.1](/教程/正文/嵌入式/6_质量_安全与交付/6_1_固件架构_配置与资源预算) 定的上限，超出就失败）。CI 配置本身不在这一页展开，[18 持续集成](/教程/正文/开发与工程基础/18_持续集成) 讲怎么写。

在存量工程中推行静态检查时，切忌采取“一刀切”的休克疗法。如果将全套严苛的 MISRA 规则无差别套用到数万行存量代码上，瞬间弹出的数千条告警往往会令团队产生严重的抵触心理，最终甚至导致工具被全盘放弃。行之有效的方法是建立“存量守底线、增量零容忍”的基线演进策略：为新增源码文件配置最高等级的静态检查规则，将既有文件的存量告警导入白名单基线；在后续日常维护和功能演进中，要求每次提交在满足增量零新增告警的同时，顺手清理改动区域内的存量技术债务。

7. Cppcheck, [*Cppcheck manual*](https://cppcheck.sourceforge.io/manual.pdf)：`--enable`、`--addon`、`--suppress` 与基线文件的用法。
8. Memfault, [*The Best and Worst GCC Compiler Flags For Embedded*](https://interrupt.memfault.com/blog/best-and-worst-gcc-clang-compiler-flags)：嵌入式项目推荐警告集的取舍。
9. Google, [*Google Engineering Practices: Code Review*](https://google.github.io/eng-practices/review/)：评审意见的写法与评审者应关注什么。
10. 本页的编译器警告、`-fanalyzer` 诊断、clang-tidy 与 cppcheck 输出、代码体积均为本机实测：示例代码用 MinGW gcc 13.2 与 Arm GNU Toolchain 13.3 编译，clang-tidy 为 LLVM 19.1.7，cppcheck 为 2.14.0，体积用 arm-none-eabi-size 量取。
