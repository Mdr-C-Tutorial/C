# 3. 散列表

在线性表（数组或链表）中，若按关键字查找一个元素，无序时需线性扫描 $\Theta(n)$，有序数组二分查找也需 $\Theta(\log n)$。**散列表 (Hash Table)** 通过把关键字直接映射到数组下标，在散列分布均匀且装载因子受控的前提下，能够将查找、插入和删除的**期望时间复杂度**降至 $O(1)$。

## 1. 直接寻址与散列思想

如果关键字集合直接取自小范围非负整数 $\{0, 1, \dots, m - 1\}$，我们可以分配长度为 $m$ 的数组 `T`，把键为 $k$ 的元素直接存放在 `T[k]` 中。这种**直接寻址表 (Direct-Address Table)** 的查找、插入与删除均为严格的最坏情况 $O(1)$。

然而，当关键字的全域 $U$ 非常庞大（例如任意 64 位整数或任意长度的字符串），直接分配大小为 $|U|$ 的数组在空间上完全不可行。此时，我们引入**散列函数 (Hash Function)**：

$$h: U \to \{0, 1, \dots, m - 1\}$$

其中 $m$ 是底层槽数组（桶数组）的容量。散列函数将庞大的键空间映射到有限的槽下标范围。由鸽巢原理可知，只要 $|U| > m$，就必然存在两个不同的键 $k_1 \neq k_2$ 满足 $h(k_1) = h(k_2)$，这一现象称为**散列冲突 (Collision)**。

## 2. 散列函数与相等性判据

一个良好的散列函数应当满足以下三条性质：

1. **确定性**：同一运行期内，相等的键必须始终计算出相同的散列值，即 $k_1 = k_2 \implies h(k_1) = h(k_2)$。
2. **均匀性**：不同键的散列值应当尽可能均匀、独立地分布在 $\{0, 1, \dots, m - 1\}$ 上，减少聚集。
3. **高效性**：计算散列值本身的耗时应当很小（对于长度为 $L$ 的字节序列为 $O(L)$，对于定宽整数为 $O(1)$）。

对于字节串或以 `'\0'` 结尾的字符串，工程上常用多项式滚动散列或 **FNV-1a** 算法：

```c
#include <stddef.h>
#include <stdint.h>

static uint64_t fnv1a_hash_str(const char *s) {
    uint64_t h = UINT64_C(14695981039346656037);
    for (const unsigned char *p = (const unsigned char *)s; *p != '\0'; ++p) {
        h ^= (uint64_t)(*p);
        h *= UINT64_C(1099511628211);
    }
    return h;
}
```

::: warning 严禁用散列值相等代替键相等

散列值相等（$h(k_1) == h(k_2)$）只是两个键可能相等的**必要条件**而非充分条件。在散列表的查找、去重与删除中，即使散列值（或槽下标）匹配，也**必须**继续调用键本身的相等比较函数（如字符串的 `strcmp`）确认键确实相等。

反之，散列函数与相等判据还必须满足**等价一致性契约**：若相等比较函数认为两个键相等（`equal(k1, k2) == true`），则散列函数对二者必须产出完全相同的散列值（`hash(k1) == hash(k2)`）。例如实现不区分 ASCII 大小写的散列表时，散列函数内部也必须先将大写字母折叠为小写（或统一大小写）后再参与散列计算。

:::

### 2.1 常见散列函数构造方法

在实际工程中，通常将“键到槽下标的映射”拆分为两步：先通过**散列函数**将键映射为位分布均匀的 64 位无符号整数 `uint64_t`，再通过**取模或位掩码**映射到 $\{0, 1, \dots, m - 1\}$。常见构造方法包括：

1. **除法散列法 (Division Method)**：

   $$h(k) = k \bmod m$$

   - 若 $m = 2^p$，$k \bmod 2^p$ 等价于直接截取 $k$ 的最低 $p$ 位 `k & (m - 1)`。虽然位与运算极快，但如果输入键的低位具有规律（例如内存地址常按 8 或 16 字节对齐、业务编号全为偶数），高位的熵会被完全丢弃，导致大量键聚集在少数槽中。
   - 因此，若直接使用未经混合的除法散列，$m$ 通常应选择**不接近 2 的幂的素数**；若为了位与掩码的高效性选择 $m = 2^p$，则必须先对整数键执行全位宽混淆。

2. **乘法散列法与 Fibonacci 散列 (Multiplicative / Fibonacci Hashing)**：
   先将键乘以一个常数 $A \in (0, 1)$，取小数部分再乘以 $m$。在 64 位整数运算中，Knuth 建议取黄金分割比 $\phi = \frac{1 + \sqrt{5}}{2}$ 的倒数所对应的 64 位无符号奇常数：

   $$C = \left\lfloor \frac{2^{64}}{\phi} \right\rfloor = \text{11400714819323198485} = \text{0x9e3779b97f4a7c15}$$

   当槽容量 $m = 2^p$（$1 \le p \le 64$）时，将 64 位无符号乘积右移 $(64 - p)$ 位即可取出分布极佳的高 $p$ 位作为桶下标：

   $$h(k) = \frac{(k \cdot \text{0x9e3779b97f4a7c15}) \bmod 2^{64}}{2^{64 - p}} = \texttt{(k * UINT64\_C(0x9e3779b97f4a7c15)) >> (64 - p)}$$

3. **定宽整数雪崩位混合器 (Bit Mixer)**：
   通过“右移异或（xorshift）+ 乘以大奇常数”的多轮交替变换，使输入键任意一位的翻转都能以约 $50\%$ 的概率影响到输出的所有位（称为**雪崩效应，Avalanche Effect**）。例如 SplitMix64 的终态混合函数：

   ```c
   static inline uint64_t splitmix64_hash(uint64_t x) {
       x = (x ^ (x >> 30)) * UINT64_C(0xbf58476d1ce4e5b9);
       x = (x ^ (x >> 27)) * UINT64_C(0x94d049bb133111eb);
       return x ^ (x >> 31);
   }
   ```

   由于在模 $2^{64}$ 环上乘以奇数以及与自身高位移位异或都是**可逆双射**，不同的 64 位输入经过 `splitmix64_hash` 后绝不会在 64 位散列值层面发生碰撞，仅在最后截断到 $m$ 个桶时才会因鸽巢原理产生冲突。

4. **散列洪泛攻击（HashDoS）与带密钥散列**：
   若散列表使用公开、确定性的散列函数（如无种子的 FNV-1a 或固定模运算），攻击者可以离线构造数万个散列到同一槽的恶意键（如精心构造的 HTTP 请求头或 JSON 键名），使单次查找和插入从期望 $O(1)$ 退化为最坏 $\Theta(n)$，导致批量插入总耗时膨胀至 $\Theta(n^2)$。现代语言运行时与网络服务普遍采用**全域散列 (Universal Hashing)** 或带 128 位随机密钥的伪随机函数（如 **SipHash**），在进程启动时从操作系统熵源读取随机种子参与散列计算，使外部攻击者无法预测冲突集合。

## 3. 冲突解决策略一：分离链接法 (Separate Chaining)

**分离链接法**将散列表表示为长度为 $m$ 的链表头指针数组，散列到同一个槽 $j = h(k)$ 的所有元素串成一条单向（或双向）链表。

设表中当前存储的元素个数为 $n$，槽数组长度为 $m$，定义**装载因子 (Load Factor)** 为：

$$\alpha = \frac{n}{m}$$

在**简单一致散列假设 (Simple Uniform Hashing Assumption, SUHA)** 下，每个键等概率独立地散列到 $m$ 个槽中的任意一个，每条链表的期望长度为 $\alpha$：

- **未命中查找**：计算散列值耗时 $O(1)$，扫描对应链表全部元素平均耗时 $\alpha$，期望时间复杂度为 $\Theta(1 + \alpha)$。
- **命中查找**：平均扫描链表中排在该元素之前的半数节点，期望时间复杂度同样为 $\Theta(1 + \alpha)$。

当通过动态扩容保持 $n = O(m)$（即 $\alpha \le \alpha_{\max}$，通常取 $\alpha_{\max} = 0.75$ 或 $1.0$）时，$\Theta(1 + \alpha) = \Theta(1)$。

## 4. 冲突解决策略二：开放寻址法与墓碑机制

**开放寻址法 (Open Addressing)** 不分配链表节点，而是将所有元素直接存放在槽数组内部（因此装载因子始终满足 $\alpha = n / m < 1$）。当插入或查找键 $k$ 在初始槽 $h(k, 0)$ 发生冲突时，按确定的探测序列依次检查槽：

$$h(k, 0), \; h(k, 1), \; \dots, \; h(k, m - 1)$$

其中最常用的是**线性探测 (Linear Probing)**：

$$h(k, i) = (h_0(k) + i) \bmod m \quad (i = 0, 1, \dots, m - 1)$$

当 $m$ 取 2 的整数次幂时，模运算可写为位与 `(h0 + i) & (m - 1)`。

除线性探测外，开放寻址法还有另外两种经典探测序列与两种现代变体：

- **二次探测 (Quadratic Probing)**：

  $$h(k, i) = (h_0(k) + c_1 i + c_2 i^2) \bmod m \quad (c_2 \neq 0)$$

  线性探测虽然具有极佳的缓存局部性，但容易产生**一次聚集 (Primary Clustering)**——连续占用的槽块越长，新键落入该块并使其进一步膨胀的概率就越高；在装载因子为 $\alpha$ 时，线性探测命中与未命中查找的期望探测次数分别约为 $\frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right)$ 与 $\frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)$。二次探测通过二次步长跳出相邻聚集区，缓解了一次聚集，但初始散列槽相同的键仍会沿完全相同的探测轨迹前进（称为**二次聚集，Secondary Clustering**）。此外，二次探测必须谨慎选择 $(m, c_1, c_2)$ 才能保证遍历全表，例如当 $m = 2^p$ 时，取三角形数增量 $c_1 = c_2 = 1/2$（即 $h(k, i) = (h_0(k) + i(i+1)/2) \bmod 2^p$）可恰好无重复地访问全部 $2^p$ 个槽。
- **双重散列 (Double Hashing)**：

  $$h(k, i) = (h_1(k) + i \cdot h_2(k)) \bmod m$$

  使用第二个独立的散列函数 $h_2(k)$ 决定探测步长，使初始位置相同的不同键也拥有不同的探测步长，同时消除一次聚集与二次聚集。为使探测序列遍历全部 $m$ 个槽，步长 $h_2(k)$ 必须与容量 $m$ **互素**（$\gcd(h_2(k), m) = 1$）：若 $m$ 取素数，可令 $h_2(k) = 1 + (k \bmod (m - 1))$；若 $m = 2^p$，可令 $h_2(k)$ 恒取 $\{1, 3, \dots, 2^p - 1\}$ 中的奇数。
- **Robin Hood 散列与反向移位删除 (Backward-Shift Deletion)**：
  在每个槽中额外记录或在线计算当前元素偏离其初始散列槽的**探测序列长度 (Probe Sequence Length, PSL)**。插入时若当前待插元素的 PSL 大于槽内已有元素的 PSL，则置换（“劫富济贫”）两者并继续为被置换元素寻找槽位，从而大幅降低探测长度的方差，并在查找遇到 `psl > target.psl` 时提前终止（Early Exit）。同时，在线性探测或 Robin Hood 散列中，删除槽 $i$ 时也可不使用墓碑，而是将后续连续占用簇中初始散列位置不在有效区间内的元素依次向前移动一格（Knuth Algorithm R，反向移位删除），从根源上消除墓碑累积。
- **布谷鸟散列 (Cuckoo Hashing)**：
  维护两个散列函数 $h_1, h_2$（对应两个表 $T_1, T_2$ 或单表的两处候选槽），保证任意键 $k$ 只可能出现在 $T_1[h_1(k)]$ 或 $T_2[h_2(k)]$ 之一，从而使查找与删除达到**严格最坏情况 $O(1)$**。插入时若目标槽已被占用，则踢出原住户并将其移至其备用位置；若交替踢出步数超过预设阈值（出现置换环），则更换散列种子并重建表。

### 4.1 为什么开放寻址删除必须使用墓碑 (Tombstone)

在线性探测中，同义词和后续冲突元素会连成一片连续占用的槽，只有遇到真正的**空槽 (`EMPTY`)** 时，查找才能断定目标键不在表中并提前终止。

假设键 $k_1$ 与 $k_2$ 散列到同一初始位置 $j$：$k_1$ 放入槽 $j$，$k_2$ 顺延放入槽 $j + 1$。如果此后删除 $k_1$ 时直接把槽 $j$ 恢复为 `EMPTY`，那么随后查找 $k_2$ 时，在初始槽 $j$ 看到 `EMPTY` 就会错误地停止探测，报告 $k_2$ 不存在！

因此，开放寻址表的每个槽必须区分**三种状态**：

| 槽状态 | 含义 | 查找 (`contains`) 行为 | 插入 (`insert`) 行为 |
| --- | --- | --- | --- |
| `SLOT_EMPTY` | 从未使用过（或重建后清空） | 目标键必然不存在，立即终止探测 | 若此前未记录墓碑，则在此槽插入新键；否则在记录的首个墓碑处插入 |
| `SLOT_OCCUPIED` | 当前存有有效键 | 若键相等则命中返回；否则继续向后探测 | 若键相等则为重复插入，直接返回；否则继续向后探测 |
| `SLOT_TOMBSTONE` | 曾存有键但已被删除 | **不能终止**，必须继续向后探测 | 记录遇到的**第一个**墓碑位置备选，但**必须继续向后探测**直到遇到相同键或 `SLOT_EMPTY` |

### 4.2 扩容与墓碑清理（Rehashing）

随着删除操作累积，墓碑槽会同样拉长探测链，使查找退化。因此开放寻址表应当同时监控有效元素数 `size` 与墓碑数 `tombstones`：

1. 当下一次插入会使 `(size + tombstones + 1)` 超过装载上限（例如容量的 $3/4$）时，将容量翻倍（若有效元素很少而墓碑过多，也可保持原容量重建）；
2. 分配新槽数组并全部初始化为 `SLOT_EMPTY`，仅将旧表中状态为 `SLOT_OCCUPIED` 的键重新散列插入新表，所有墓碑在重建过程中自然消除。

## 5. C 语言实现示例：支持删除与墓碑清理的开放寻址散列表

下面展示一个完整的开放寻址整数集合实现，演示三态槽、墓碑复用以及重散列清理机制：

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

typedef enum {
    SLOT_EMPTY = 0,
    SLOT_OCCUPIED = 1,
    SLOT_TOMBSTONE = 2
} SlotState;

typedef struct {
    int64_t key;
    SlotState state;
} HashSlot;

typedef struct {
    HashSlot *slots;
    size_t capacity;
    size_t size;
    size_t tombstones;
} IntHashSet;

static uint64_t hash_i64(int64_t key) {
    uint64_t x = (uint64_t)key;
    x = (x ^ (x >> 30)) * UINT64_C(0xbf58476d1ce4e5b9);
    x = (x ^ (x >> 27)) * UINT64_C(0x94d049bb133111eb);
    return x ^ (x >> 31);
}

static bool int_hash_set_rehash(IntHashSet *set, size_t new_cap) {
    HashSlot *new_slots = (HashSlot *)calloc(new_cap, sizeof(HashSlot));
    if (new_slots == NULL) {
        return false;
    }
    size_t mask = new_cap - 1;
    for (size_t i = 0; i < set->capacity; ++i) {
        if (set->slots[i].state == SLOT_OCCUPIED) {
            int64_t k = set->slots[i].key;
            size_t idx = (size_t)(hash_i64(k) & mask);
            while (new_slots[idx].state == SLOT_OCCUPIED) {
                idx = (idx + 1) & mask;
            }
            new_slots[idx].key = k;
            new_slots[idx].state = SLOT_OCCUPIED;
        }
    }
    free(set->slots);
    set->slots = new_slots;
    set->capacity = new_cap;
    set->tombstones = 0;
    return true;
}

static bool int_hash_set_insert(IntHashSet *set, int64_t key, bool *out_inserted) {
    if ((set->size + set->tombstones + 1) * 4 > set->capacity * 3) {
        size_t next_cap = (set->capacity == 0) ? 8 : set->capacity * 2;
        if (!int_hash_set_rehash(set, next_cap)) {
            return false;
        }
    }
    size_t mask = set->capacity - 1;
    size_t idx = (size_t)(hash_i64(key) & mask);
    size_t first_tomb = SIZE_MAX;

    for (;;) {
        SlotState st = set->slots[idx].state;
        if (st == SLOT_EMPTY) {
            size_t target = (first_tomb != SIZE_MAX) ? first_tomb : idx;
            if (first_tomb != SIZE_MAX) {
                set->tombstones--;
            }
            set->slots[target].key = key;
            set->slots[target].state = SLOT_OCCUPIED;
            set->size++;
            *out_inserted = true;
            return true;
        }
        if (st == SLOT_OCCUPIED && set->slots[idx].key == key) {
            *out_inserted = false;
            return true;
        }
        if (st == SLOT_TOMBSTONE && first_tomb == SIZE_MAX) {
            first_tomb = idx;
        }
        idx = (idx + 1) & mask;
    }
}

static bool int_hash_set_contains(const IntHashSet *set, int64_t key) {
    if (set->capacity == 0) {
        return false;
    }
    size_t mask = set->capacity - 1;
    size_t idx = (size_t)(hash_i64(key) & mask);
    for (size_t step = 0; step < set->capacity; ++step) {
        SlotState st = set->slots[idx].state;
        if (st == SLOT_EMPTY) {
            return false;
        }
        if (st == SLOT_OCCUPIED && set->slots[idx].key == key) {
            return true;
        }
        idx = (idx + 1) & mask;
    }
    return false;
}

static bool int_hash_set_remove(IntHashSet *set, int64_t key) {
    if (set->capacity == 0) {
        return false;
    }
    size_t mask = set->capacity - 1;
    size_t idx = (size_t)(hash_i64(key) & mask);
    for (size_t step = 0; step < set->capacity; ++step) {
        SlotState st = set->slots[idx].state;
        if (st == SLOT_EMPTY) {
            return false;
        }
        if (st == SLOT_OCCUPIED && set->slots[idx].key == key) {
            set->slots[idx].state = SLOT_TOMBSTONE;
            set->size--;
            set->tombstones++;
            return true;
        }
        idx = (idx + 1) & mask;
    }
    return false;
}

int main(void) {
    IntHashSet set = {NULL, 0, 0, 0};
    bool inserted = false;
    int_hash_set_insert(&set, 42, &inserted);
    int_hash_set_insert(&set, 106, &inserted);
    int_hash_set_remove(&set, 42);
    printf("contains(42) = %d, contains(106) = %d, size = %zu\n",
           int_hash_set_contains(&set, 42),
           int_hash_set_contains(&set, 106),
           set.size);
    free(set.slots);
    return 0;
}
```

### 6.1 基础与巩固

利用长度为 $256$ 的直接寻址表（`size_t` 频次数组），在线性时间与常数辅助空间下实现以下两个字节与字符串统计函数：

```c
#include <stdbool.h>
#include <stddef.h>

size_t byte_first_unique_index(const unsigned char *data, size_t len);
bool str_is_anagram(const char *a, const char *b);
```

要求：

```c
bool rh_map_get(
    const RobinHoodMap *map,
    int64_t key,
    int64_t *out_value
);
bool rh_map_remove(
    RobinHoodMap *map,
    int64_t key,
    bool *out_removed
);
size_t rh_map_size(const RobinHoodMap *map);
size_t rh_map_max_psl(const RobinHoodMap *map);
```

要求：

1. 每个占用槽记录其当前元素偏离初始散列槽 $h(k) \bmod m$ 的探测步数 `psl`（在初始槽处 `psl == 0`）。
2. **插入与更新**：沿线性探测序列前进，每走一步待插项的 `curr_psl` 加 1。若在发生交换前遇到相同键，则原地更新其值并返回；一旦遇到某个占用槽满足 `curr_psl > slot.psl`（“劫富济贫”条件），先在剩余探测段确认目标键是否已存在（或在插入前先查找），随后将待插项与该槽元素交换，继续为被置换出的元素寻找后续槽位，直至放入空槽。
3. **早停查找**：在 `rh_map_get` 与 `rh_map_remove` 的定位阶段，若当前探测步数 `psl` 严格大于当前槽内元素的 `slot.psl`，立即终止探测并返回未命中。证明为什么在 Robin Hood 不变式下，后续槽中绝不可能再出现目标键。
4. **后移删除**：删除槽 `idx` 后，只要下一个槽 `next = (idx + 1) & mask` 被占用且 `slot[next].psl > 0`，就将其前移到 `idx` 并令其 `psl` 减 1；遇到空槽或 `psl == 0` 的槽时停止，并将最后的空洞置为空槽。
5. `rh_map_max_psl` 返回当前表中所有占用槽的最大 `psl`（空表返回 `0`）。

实现保证**最坏情况查找与删除时间复杂度为严格 $O(1)$** 的 **布谷鸟散列集合 (Cuckoo Hash Set)**，并分析散列洪泛攻击（HashDoS）的构造与防御：

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct CuckooIntSet CuckooIntSet;

CuckooIntSet *cuckoo_set_create(void);
void cuckoo_set_destroy(CuckooIntSet *set);
bool cuckoo_set_contains(const CuckooIntSet *set, int64_t key);
bool cuckoo_set_insert(
    CuckooIntSet *set,
    int64_t key,
    bool *out_inserted
);
bool cuckoo_set_remove(
    CuckooIntSet *set,
    int64_t key,
    bool *out_removed
);
size_t cuckoo_set_size(const CuckooIntSet *set);
```

要求：

1. 维护两张容量均为 $m$（$2$ 的幂）的子表 $T_1, T_2$ 以及两个带独立 64 位随机种子的散列函数 $h_1(k), h_2(k)$。任意已存在键 $k$ 必须且仅能存放在 $T_1[h_1(k) \bmod m]$ 或 $T_2[h_2(k) \bmod m]$ 之一。
2. `cuckoo_set_contains` 与 `cuckoo_set_remove` **最多只允许检查这两个槽位**（严格最坏情况 $O(1)$ 次比较），不得进行任何线性扫描或链表遍历。
3. `cuckoo_set_insert`：若键已存在于 $T_1[h_1(k)]$ 或 $T_2[h_2(k)]$，置 `*out_inserted = false` 并返回 `true`；若两槽之一为空，直接放入。若两槽均满，将新键放入 $T_1[h_1(k)]$ 并踢出原住户 $x$，再将 $x$ 放入其位于 $T_2[h_2(x)]$ 的位置并踢出其中原住户，如此在 $T_1$ 与 $T_2$ 之间交替踢出。
4. 若单次插入的交替踢出次数达到上限（例如 `MAX_KICKS = 64`）仍未找到空槽，或者总元素数超过容量阈值（$2m$ 的 $45\%$），则将子表容量扩容（或更新随机种子 `seed1, seed2`）并将全部元素（含当前被踢出的悬空键）重新散列插入新表；重散列失败时必须保持原集合与输出对象不变。
5. 在题解中回答：为什么无密钥确定性散列函数容易遭受碰撞洪泛攻击（HashDoS），以及布谷鸟散列在遭遇小规模环路冲突时为什么必须支持**更换散列种子重散列**而不能仅靠固定散列函数扩容。
