# 2.4 标识符

## 1. 标识符

1. 标识符是字符序列 (Character Sequence)，可以指代一个实体（对象，函数，宏等）。
2. 翻译限度（不需要记，实际往往支持更多）：
   1. 实现至少应支持：内部标识符或宏名中 **63** 个有意义的初始字符，外部标识符中 **31** 个有意义的初始字符；
   2. 一个翻译单元中最多 **4095** 个外部标识符；
   3. 一个块中最多声明 **511** 个拥有块作用域的标识符；
   4. 一个预处理翻译单元中最多同时定义 **4095** 个宏标识符。

::: concept identifier-reserved-ub title="保留标识符与未定义行为"

有些标识符叫保留标识符，用户代码声明这类标识符属于未定义行为：翻译阶段 7 中会被识别为关键字的预处理记号；以一个下划线开始，并出现在文件作用域普通名字空间或标记名字空间中的标识符；所有以一个下划线后随一个大写字母或另一下划线开始的标识符，如 `_Mdr`、`__mdr`；标准库所定义的所有外部标识符。

:::

::: concept identifier-translation-limits title="翻译限度只是最低保证"

上面列出的数字表示标准规定的最低支持规模。真实工具链通常支持更多，可移植讨论只应依赖标准保证或目标实现文档。

:::

::: generate identifier-overview kind=explanation concepts=identifier-reserved-ub,identifier-translation-limits

面向刚开始学习 C 的读者，解释标识符可以指代哪些实体；说明为什么实现要保留上述四类名字（编译器内建、标准库内部需要不受用户干扰的名字），以及声明保留标识符为什么归入未定义行为（编译器不一定会报错）；教读者正确解读翻译限度数字——它们是可移植性的底线，不能当成编码目标。保留标识符的命名模式细节在 2.5 节展开，本节建立规则意识即可。

:::

## 2. 标识符、实体与名字空间

::: concept identifier-namespaces title="名字空间区分同名标识符"

同一个字符序列在不同上下文中可能属于不同名字空间。C 中至少要区分普通标识符、标记名（`struct`、`union`、`enum` 的标签）、成员名和标号名等类别。结构体成员名只在对应结构体或联合体内部解释。

:::

```c
struct item {
    int value;
};

int item = 1; /* 普通标识符，与 struct item 的标记名不冲突 */
```

::: generate identifier-namespace-tour kind=explanation concepts=identifier-namespaces

面向刚开始学习 C 的读者，借助上面的示例解释为什么 `struct item` 的标记名 `item` 与普通对象名 `item` 不冲突——它们处在不同名字空间；同时提醒：虽然合法，同名仍会在后续使用中增加阅读成本，工程上应谨慎使用。

:::

## 3. 关键字

1. **类型**：`_Bool(bool)` `char` `double` `float` `int` `long` `short` `signed` `unsigned` `void` `_Complex`
   `_Decimal32` `_Decimal64` `_Decimal128` `_Imaginary` `_BitInt(n)`
2. **指定符和限定符**：`const` `volatile` `inline` `restrict` `_Noreturn` `_Alignas(alignas)` `_Atomic` `_Generic`
3. **常量**：`true` `false` `nullptr`
4. **控制语句** 相关：`break` `case` `continue` `default` `do` `else` `for` `goto` `if` `return` `switch` `while`
5. **存储类** 说明符：`auto` `extern` `register` `static` `constexpr` `_Thread_local(thread_local)`
6. **运算符**：`sizeof` `typeof` `typeof_unqual` `_Alignof(alignof)`
7. **类型的声明**：`enum` `struct` `union`
8. **类型推断**：`auto`
9. **其他**：`_Static_assert(static_assert)` `typedef`

上面的列表按 C23 列出。括号中的 `bool`、`alignas`、`thread_local`、`alignof`、`static_assert`，以及 `true`、`false`，在 C23 之前是标准头中定义的宏，C23 起成为关键字；`nullptr`、`constexpr`、`typeof`、`typeof_unqual`、`_BitInt`、`_Decimal32` 等以及 `auto` 的类型推断用法是 C23 新增的。

关键字在语法中有固定用途。到了翻译阶段 7，能够被识别为关键字的记号会按关键字处理。因此，用户代码不能把 `int`、`return`、`struct` 这类词重新声明成自己的名字。

## 4. 习题

### 4.1 巩固

<Exercise id="10222" :d="2" :w="2">

下面八个写法，哪些能在函数体内用作普通对象名，哪些不能？逐个给出判断和理由，再用编译器核对。

```text
count_
2nd
Int
double
my-var
_ok
mdr_count
case
```

要求：

1. 判断分三类：合法、关键字、词法上不成立（根本不是一个标识符记号）。
2. 把判断为合法的名字写进一个程序，各声明一个 `int` 对象并打印它们的值。用 `gcc -std=c17 -Wall -Wextra` 编译，编译器不能给出任何诊断。
3. 把不合法的名字逐个单独写进一条 `int` 声明，编译，抄下第一条 error，说明编译器把它当成了什么。
4. 说明 `Int` 与 `int` 的关系，以及为什么关键字不能靠改名的大小写绕开。

验收：合法的一组恰好四个；`2nd` 的 error 与整数后缀有关，`my-var` 的 error 说明它被切成了三个记号。

</Exercise>

<Exercise id="10223" :d="3" :w="2">

先读下面的程序，写出输出，再回答后面的问题。

```c
#include <stdio.h>

struct item {
    int item;
    int value;
};

int item = 1;
int value = 4;

int main(void) {
    struct item value = {2, 3};
    int total = item + value.item;

    goto value;
value:
    printf("%d %d %d %d\n", item, value.item, value.value, total);
    return 0;
}
```

1. 写出输出，并说明 `total` 是怎么算出来的。
2. `item` 在这个程序里出现了三次：结构体标记、成员名、文件作用域对象。它们分别属于哪个名字空间？`struct item` 与 `int item` 为什么能共存？
3. `value` 同时是文件作用域对象、自动对象和标号。`value.item` 里的 `value` 指哪个对象？`goto value` 用的是哪个名字空间？
4. 删掉 `int value = 4;` 这一行，程序还能编译吗？输出是否改变？
5. 在 `main` 开头加一行 `int item = 10;`，重新写出输出，并说明 `item + value.item` 里的 `item` 换成了谁。

验收：原程序输出 `1 2 3 3`；第 5 问输出 `10 2 3 12`。先写答案再编译。

</Exercise>

### 4.2 编程

<Exercise id="10224" :d="4" :w="3">

本节列出的 511、4095 是翻译限度，不是编译器的实际上限。用实验核对这句话。

要求：

1. 写一个生成器（C、Python 或 shell 均可），生成 `many_vars.c`：在 `main` 的同一个块里声明 600 个对象，名字从 `v0` 到 `v599`，初值等于编号，再逐个累加进 `total` 并打印。用 `gcc -std=c17 -Wall -Wextra` 编译，要求没有警告，运行输出 `179700`。
2. 生成 `many_macros.c`：连续写 5000 个宏定义，编号从 0 到 4999，末尾用 `#if M4999 != 4999` 配 `#error` 自检。编译并运行，确认通过。
3. 回答：600 超过了哪一个限度？程序通过说明了什么，又不能说明什么？判断一段代码是否可移植时应该依据什么？
4. 把对象数改成 6000 再编译一次，记录结果（不要求通过）。

验收：第 1、2 步编译时没有任何输出，第 1 步运行打印 `179700`；第 3 问要写清「标准保证的下限」与「本机工具链的实际上限」的区别，并说明不能拿本机结果当作可移植性依据。

</Exercise>

### 4.3 综合与挑战

<Exercise id="10225" :d="5" :w="3">

下面这段程序在 C17 下不加任何头文件时能编译运行：

```c
#include <stdio.h>

int bool = 1;
int true = 2;
int alignas = 3;
int static_assert = 4;
int nullptr = 5;
int constexpr = 6;

int main(void) {
    printf("%d %d %d %d %d %d\n", bool, true, alignas, static_assert, nullptr,
           constexpr);
    return 0;
}
```

要求：

1. 用 `gcc -std=c17 -Wall -Wextra` 编译运行，记录输出。
2. 在 `#include <stdio.h>` 后面依次加上 `<stdbool.h>`、`<stdalign.h>`、`<assert.h>`，每加一个重新编译一次，记录哪些名字从这一步开始报错，以及报错把它当成了什么。
3. 改用 `gcc -std=c2x` 编译原程序。GCC 13 不认识 `-std=c23` 这个写法，C23 模式要写 `c2x`。记录哪些名字在这个模式下变成关键字。
4. 列出六个名字在三种条件下的可用性：C17 无头文件、C17 带上述头文件、C23。
5. 改写程序，使它在 `-std=c17` 和 `-std=c2x` 下都能无警告通过，输出不变。改写后的名字要符合工程习惯。

验收：第 2 步中 `bool`、`true`、`alignas`、`static_assert` 报错，`nullptr`、`constexpr` 不报错；第 3 步六个名字全部报错；第 5 步两种标准下 `-Wall -Wextra` 均无输出。

</Exercise>
