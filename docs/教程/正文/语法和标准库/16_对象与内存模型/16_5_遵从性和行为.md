# 16.5 遵从性和行为

## 1. 为什么先讲行为分类

C 语言当中的行为不只分为“对”或“错”。它会区分“好”、“实现决定”、“结果不唯一”、“完全无保证”等多种情况。

## 2. 常见行为类别

### 2.1 实现定义行为

::: concept implementation-defined-behavior title="实现定义行为"

标准要求实现给出一种明确行为，并在文档中说明。例如 `char` 默认是有符号还是无符号，属于实现定义行为。工程上可以使用这类能力，但要通过文档或编译选项把前提写清楚。

:::

### 2.2 未指定行为

::: concept unspecified-behavior title="未指定行为"

标准允许出现若干种结果，但不要求实现每次都做同样选择。例如某些表达式中子表达式的求值先后次序并未固定。代码如果依赖某一种求值次序，就会在不同编译器或不同优化级别下表现不一致。

:::

### 2.3 未定义行为

::: concept undefined-behavior title="未定义行为"

一旦触发未定义行为，标准不再提供任何结果保证。越界访问、悬垂指针解引用、对同一标量对象进行无序修改都属于这一类。它最危险的地方在于：有时“看起来能跑”，但平台或优化变化后会立即失效。

**存在未定义行为的程序是错误的，编写代码时要规避未定义行为。**

:::

```c
#include <stdio.h>

int main(void) {
    int a[5] = {1, 2, 3, 4, 5};
    printf("%d\n", a[10]); /* 越界访问：未定义行为 */
    return 0;
}
```

这里 `a[10]` 越过了数组的有效下标范围（最大为 `a[4]`），标准对该访问的结果不作任何保证。

::: generate behavior-categories kind=explanation concepts=implementation-defined-behavior,unspecified-behavior,undefined-behavior

面向刚开始学习 C 的读者，对比讲解实现定义行为、未指定行为和未定义行为：各自的标准要求、典型例子和工程风险；借助上面的越界示例说明“能跑不代表正确”；给出判断顺序——先查标准是否有保证，再查实现文档，绝不把观察到的行为当作语言规则。

:::

## 3. 遵从性 (Conformance)

::: concept conformance title="遵从实现与遵从程序"

遵从实现 (Conforming implementation) 是指满足标准约束的编译器和库实现。严格遵从程序 (Strictly conforming program) 只使用标准规定的特性，不依赖任何未指定、未定义或实现定义的行为。遵从程序 (Conforming program) 的要求宽松得多：只要能被某个遵从实现接受即可，因此可以依赖实现定义行为和编译器扩展。

:::

::: generate conformance-value kind=explanation concepts=conformance

面向关心代码可移植性的读者，解释遵从性为什么有价值：严格遵从的程序可以在任何遵从实现上得到标准保证的行为；说明“减少实现细节依赖”与“代码在更多平台上稳定工作”之间的因果关系。

:::

写一个 `impl_probe.c`，在程序里定义 `enum color { RED, GREEN, BLUE };`，输出下面五项在你所用平台上的取值：

```c
#include <limits.h>
#include <stdio.h>

enum color { RED, GREEN, BLUE };

int main(void) {
    printf("CHAR_MIN = %d, CHAR_MAX = %d\n", CHAR_MIN, CHAR_MAX);
    printf("(int)(char)0xFF = %d\n", (int)(char)0xFF);
    printf("-8 >> 1 = %d\n", -8 >> 1);
    printf("sizeof(enum color) = %d\n", (int)sizeof(enum color));
    printf("sizeof(long) = %d\n", (int)sizeof(long));
    return 0;
}
```

用 `gcc -std=c17 -Wall -Wextra` 编译运行，把结果记成一张表。再分别加上 `-funsigned-char`、`-fshort-enums` 各编译一次，标出发生变化的行。前者让 `char` 按无符号处理，后者让枚举使用能容纳其全部取值的最小整数类型。

然后把程序依赖的两条前提写成 `_Static_assert`（C11，见 [15.1.3](/教程/正文/语法和标准库/15_声明_名称与生存期/15_1_声明/15_1_3_static_assert)），例如把「`char` 有符号」写成 `_Static_assert(CHAR_MIN < 0, "char 必须有符号");`。用同样的三组选项各编译一次，确认前提不成立时编译器直接报 `static assertion failed`。

验收：三组输出齐全；两条断言在默认选项下通过，在对应选项下失败；能说明这两条断言把哪一种行为从运行时才暴露的问题提前到了编译期。

```c
#include <stdio.h>

static int f(void) {
    printf("f ");
    return 1;

static int g(void) {
    printf("g ");

int main(void) {
```

<Exercise id="11630" :d="5" :w="4">

下面是一个做小样本检查的 `report.c`。它在同一台机器上换优化级别或换编译选项，输出就会变，其中一处甚至跑不完。先用 `gcc -std=c17 -Wall -Wextra -O0` 和 `-O2` 各编译运行一次，再加上 `-funsigned-char` 试一次（跑不完就终止它，不必等）。

```c
#include <limits.h>
#include <stdio.h>
#include <string.h>

struct sample {
    char tag;
    int value;
};

static long count_bytes(const char *path) {
    FILE *f = fopen(path, "rb");
    if (f == NULL) {
        return -1;
    }
    long n = 0;
    char c;
    while ((c = getc(f)) != EOF) {
        n++;
    }
    fclose(f);
    return n;
}

static unsigned long checksum(const unsigned char *p, size_t n) {
    unsigned long h = 0;
    for (size_t i = 0; i < n; i++) {
        h = h * 31u + (char)p[i];
    }
    return h;
}

static int add_would_overflow(int a, int b) {
    return a + b < a;
}

static int same(const struct sample *a, const struct sample *b) {
    return memcmp(a, b, sizeof *a) == 0;
}

int main(void) {
    const unsigned char data[] = {0x41, 0xFF, 0x42, 0x50};
    FILE *out = fopen("sample.bin", "wb");
    if (out == NULL) {
        return 1;
    }
    fwrite(data, 1, sizeof data, out);
    fclose(out);

    struct sample a = {'x', 7};
    struct sample b = {'x', 7};

    printf("count = %ld\n", count_bytes("sample.bin"));
    printf("checksum = %lu\n", checksum(data, sizeof data));
    printf("overflow = %d\n", add_would_overflow(INT_MAX, 1));
    printf("same = %d\n", same(&a, &b));
    return 0;
}
```

1. 四处问题分别在 `count_bytes`、`checksum`、`add_would_overflow`、`same` 里。逐处指出它属于哪一类行为，以及它在换选项或换优化级别后的具体表现。
2. 修正这四处，要求下面四种构建的输出逐字节相同：`-O0`、`-O2`、`-O0 -funsigned-char`、`-O2 -funsigned-char`。修好后应稳定输出 `count = 4`、`checksum = 2183596`、`overflow = 1`、`same = 1`。
3. 说明每处修改消除了哪一种依赖。`same` 一处的修改与 [16.2](/教程/正文/语法和标准库/16_对象与内存模型/16_2_对象表示) 讲的填充字节有关，写清 `memcmp` 为什么会把填充字节读进来，以及为什么同样的两个结构体在不同构建下会得出不同的比较结果。
4. 修改后的程序是不是严格遵从程序？对照第 3 节的定义，逐条说明它还在哪些地方依赖实现，或者为什么已经不再依赖。

验收：四种构建的输出完全一致；`gcc -std=c17 -Wall -Wextra -pedantic-errors` 编译无诊断；第 4 问的结论有具体依据，不只是一句「是」或「不是」。

</Exercise>
