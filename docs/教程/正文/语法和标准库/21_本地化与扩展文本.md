# 21. 本地化与扩展文本

本地化 (localization) 指程序按地区的习惯处理数字格式、货币符号、字符串排序和字符分类等。C 标准库通过区域设置 (locale) 支持本地化：头文件 `<locale.h>` 提供查询和修改区域设置的接口，`<ctype.h>`、`<string.h>`、`<wchar.h>` 等头文件中的部分函数，其行为受当前区域设置影响。

## 1. 核心接口 `setlocale`

`setlocale` 用于查询或修改当前的区域设置。设置失败时返回空指针，因此每次修改都应检查返回值。

```c
#include <locale.h>
#include <stdio.h>

int main(void) {
    const char *result = setlocale(LC_ALL, "");
    if (result == NULL) {
        puts("setlocale failed");
        return 1;
    }

    puts(result);
    return 0;
}
```

成功时，程序打印实现用于标识当前区域设置的字符串；失败时打印固定的错误信息。例如：

::: code-group

```text [成功示例]
en_US.UTF-8
```

```text [失败]
setlocale failed
```

:::

成功时打印的名称由操作系统和 C 库决定，不能假定它在各平台上一致。传入空字符串 `""` 表示按运行环境（通常是操作系统的环境变量）选择区域设置。

## 2. 数字与货币格式

`localeconv` 返回指向 `struct lconv` 对象的指针，该对象描述当前区域设置下的数字和货币格式，例如 `decimal_point`（小数点字符）和 `currency_symbol`（货币符号）。这些信息用于输出给人看的文本；程序内部的计算逻辑应与区域设置无关，只在输入输出时按地区习惯处理。

## 3. 排序与比较

字符串排序若需要遵循地区规则，应使用 `strcoll` 和 `strxfrm`，而不是用 `strcmp` 直接按字节比较。按字节比较只适合协议字段和机器可读数据，不适合人类语言文本。

## 4. 区域设置是全局状态

`setlocale` 修改的是整个程序的区域设置，而不是某个函数或模块私有的状态。程序的一部分修改区域设置后，其他部分的格式化输出、字符分类和排序结果都会随之改变。

## 5. 与多字节字符和宽字符的关系

区域设置还决定多字节字符的编码方式，从而影响 `mbtowc`、`wcrtomb` 等多字节与宽字符之间的转换函数，以及 `<wctype.h>` 中宽字符分类函数的结果。处理 UTF-8 等多字节文本前，通常需要先调用 `setlocale(LC_ALL, "")` 或选择一个具体的区域设置。

### 5.1 多字节字符与宽字符转换（`<stdlib.h>` 与 `<wchar.h>`）

在多字节编码（如 UTF-8 或 GB18030）中，一个字符可能占用 1 到多个字节。标准库通过两个宏描述单个多字节字符的最大字节数：

- **`MB_LEN_MAX`**（定义于 `<limits.h>`）：编译期整型常量表达式，表示当前实现支持的所有区域设置下，单个多字节字符可能占用的最大字节数上界。
- **`MB_CUR_MAX`**（定义于 `<stdlib.h>`）：运行期求值的宏（展开为 `size_t` 表达式），表示**当前 `LC_CTYPE` 区域设置**下单个多字节字符的最大字节数。例如在 `"C"` 区域设置下通常为 `1`，而在 UTF-8 区域设置下通常为 `4`。

标准库提供两套转换接口：

1. **`<stdlib.h>` 中的内建状态接口**：`mblen`、`mbtowc`、`wctomb`、`mbstowcs`、`wcstombs`。它们在内部维护隐式的转换状态，不可重入，也不适合多线程并发调用。
2. **`<wchar.h>` 中的可重入接口（C95/C99）**：`mbrlen`、`mbrtowc`、`wcrtomb`、`mbsrtowcs`、`wcsrtombs`。它们要求调用方显式传入指向 `mbstate_t` 转换状态对象的指针（可用 `mbstate_t ps = {0};` 初始化为初始转换状态）。

其中最核心的逐字符解码函数是 `mbrtowc`：

```c
size_t mbrtowc(wchar_t * restrict pwc, const char * restrict s, size_t n, mbstate_t * restrict ps);
```

它至多检查从 `s` 开始的 `n` 个字节，尝试还原出一个宽字符并写入 `*pwc`（若 `pwc` 非空），其返回值具有四种语义：

| 返回值 | 含义 |
| --- | --- |
| 正整数 $k$（$1 \le k \le n$） | 成功还原一个非零宽字符，本次消费了 $k$ 个字节 |
| `0` | 遇到了空字符 `'\0'`，已将 `L'\0'` 写入 `*pwc`，且 `*ps` 恢复为初始状态 |
| `(size_t)-2` | 前 `n` 个字节构成一个尚未结束但合法的多字节前缀，需要继续读入更多字节 |
| `(size_t)-1` | 字节序列违反当前区域设置的编码规则；置 `errno = EILSEQ`，`*ps` 状态未指定 |

利用 `mbrtowc` 可以在不截断多字节字符的前提下按字符数截断字符串：

```c
#include <locale.h>
#include <stdio.h>
#include <string.h>
#include <wchar.h>

// 返回在不超过 max_chars 个字符的前提下，s 中安全前缀的字节数
size_t utf8_safe_prefix(const char *s, size_t max_chars) {
    mbstate_t ps = {0};
    size_t offset = 0;
    size_t remaining = strlen(s);
    size_t count = 0;

    while (count < max_chars && remaining > 0) {
        wchar_t wc;
        size_t ret = mbrtowc(&wc, s + offset, remaining, &ps);
        if (ret == 0 || ret == (size_t)-1 || ret == (size_t)-2) {
            break;
        }
        offset += ret;
        remaining -= ret;
        count++;
    }
    return offset;
}
```

### 5.2 宽字符分类与流定向（`<wctype.h>` 与 `fwide`）

`<ctype.h>` 中的 `isalpha`、`isdigit` 等函数只接受可表示为 `unsigned char` 的单字节值或 `EOF`。对于解码得到的宽字符 `wchar_t`，应包含 `<wctype.h>` 并使用对应的宽字符分类与大小写映射函数：

- **分类函数**：`iswalpha`、`iswdigit`、`iswalnum`、`iswspace`、`iswprint`、`iswpunct`、`iswcntrl`、`iswupper`、`iswlower`、`iswxdigit`。
- **大小写映射**：`towlower`、`towupper`。

这些函数的形参类型为 `wint_t`，可直接传入任意合法宽字符或宽文件结束标志 `WEOF`（无需像 `<ctype.h>` 那样先强制转换为 `unsigned char`）。

此外，`<wchar.h>` 还提供宽字符流输入输出函数（如 `fgetwc`、`fputwc`、`fwprintf`）。C 标准为每个 `FILE` 流定义了**流定向 (stream orientation)**：

- 刚打开的流处于**无定向**状态；
- 第一次在该流上调用字节读写函数（如 `fgetc`、`printf`、`fread`）会将其锁定为**字节定向流**；
- 第一次在该流上调用宽字符读写函数（如 `fgetwc`、`wprintf`）会将其锁定为**宽定向流**。

可通过 `fwide(stream, mode)` 查询或设置未定向流的定向。一旦流有了定向，除非调用 `freopen` 重新打开，否则**严禁在字节定向流上调用宽字符读写函数，也严禁在宽定向流上调用字节读写函数**。在现代跨平台工程中，通常推荐保持流为字节定向，在内存中统一使用 UTF-8 字节串，仅在需要按码点处理时做显式转换。

### 5.3 Unicode 定宽编码与 `<uchar.h>`（C11/C23）

C 标准并未规定 `wchar_t` 的具体位宽和编码：在 Windows 平台上 `wchar_t` 为 16 位（使用 UTF-16LE 编码，超出基本多文种平面的字符需拆分为一对代理项），而在 Linux 和 macOS 等平台上 `wchar_t` 为 32 位（使用 UTF-32 编码）。这使得依赖 `wchar_t` 的代码在跨平台处理非 BMP 字符（如罕见汉字或 Emoji）时容易产生偏差。

为了提供与平台无关的固定宽度 Unicode 表示，C11 引入并在 C23 完善了头文件 `<uchar.h>`：

- **`char8_t`**（C23）：底层类型为 `unsigned char`，专用于表示 UTF-8 编码单元（对应 `u8"..."` 字符串字面量与 `u8'a'` 字符常量）。
- **`char16_t`**（C11）：底层类型为 `uint_least16_t`，专用于表示 UTF-16 编码单元（对应 `u"..."` 与 `u'中'`）。
- **`char32_t`**（C11）：底层类型为 `uint_least32_t`，专用于表示 UTF-32 编码单元（对应 `U"..."` 与 `U'😀'`，每个元素直接对应一个 Unicode 标量值）。

`<uchar.h>` 同时提供了基于 `mbstate_t` 的转换函数：`mbrtoc8` / `c8rtomb`（C23）、`mbrtoc16` / `c16rtomb`、`mbrtoc32` / `c32rtomb`。它们的返回值约定与 `mbrtowc` 一致，额外增加了 `(size_t)-3`：当一个多字节字符转换出多个编码单元（例如 `mbrtoc16` 输出 UTF-16 代理对的后半部分，或 `mbrtoc8` 输出后续字节）时，函数不再消费新的输入字节，而是返回 `(size_t)-3` 表示本次写出了前一次转换缓存中的后续编码单元。

## 6. 多线程程序中的区域设置

在多线程程序运行期间调用 `setlocale`，可能与其他线程中受区域设置影响的函数调用产生数据竞争。应在创建其他线程之前完成区域设置，此后不再修改。

### 7.3 综合与挑战

<Exercise id="12105" :d="2" :w="1">

下面这段库代码有两处问题：它擅自改写了调用方的区域设置，还把 `setlocale` 返回的指针存了起来。

```c
#include <locale.h>
#include <stdio.h>

static const char *g_locale;

void library_format(double value) {
    g_locale = setlocale(LC_ALL, "");
    if (g_locale == NULL) {
        return;
    }
    printf("%.2f\n", value);
}
```

要求：

1. 写一个测试程序：主程序先把区域设置设为 `"C"`，记录 `localeconv()->thousands_sep`，调用 `library_format(1234.5)`，再记录一次。把 `library_format` 里的 `setlocale` 改成 `setlocale(LC_ALL, "en_US.UTF-8")`（或本机存在的英文区域设置）以便复现，此时返回后 `thousands_sep` 会从空串变成 `,`，主程序之后的格式化输出随之改变。
2. 修改 `library_format`，使调用返回后主程序的区域设置与调用前相同：进入时保存当前的 `LC_ALL` 字符串，退出前用它恢复。保存时必须把字符串复制到自己的缓冲区，不能只存指针。
3. 打印切换前后 `g_locale` 指向的内容。标准允许后续的 `setlocale` 调用覆盖上一次返回的字符串，因此旧指针不能依赖；`localeconv` 返回的 `struct lconv` 也一样，下一次调用可能改写其中的内容。MinGW 上能直接看到旧指针指向的内容已经变成乱码，glibc 上可能仍然读到旧值。无论观察到哪一种，结论都是同一个：要长期保存就复制。结合这一点说明第 2 步为什么要求复制。
4. 再写一个不调用 `setlocale` 的版本：库函数只按当前区域设置格式化，由程序在启动时设置一次。在注释里写明多线程程序为什么只能采用这一版。
5. 验收：测试程序打印的区域设置字符串在调用前后相同，`thousands_sep` 也相同。

</Exercise>
