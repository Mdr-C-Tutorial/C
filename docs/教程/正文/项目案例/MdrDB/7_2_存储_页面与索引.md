# 7.2 MdrDB：存储、页面与索引

在 `mdrdb` 里插入 `(1, alice, alice@example.com)`，数据库文件里会多出 30 个字节，起点是文件偏移 8162，也就是第 1 页（从 4096 开始）的页内偏移 4066：

::: terminal title="bash - xxd"

```text
$ xxd -s 8162 -l 30 fmt.db
00001fe2: 0000 0001 0018 0561 6c69 6365 1161 6c69  .......alice.ali
00001ff2: 6365 4065 7861 6d70 6c65 2e63 6f6d       ce@example.com
```

:::

开头的 `0000 0001` 是主键 1，`0018` 是负载长度 24，后面依次是长度 5 的 `alice` 和长度 0x11 的邮箱。同一页的页头记着这一页是叶子、有两个单元格、内容区从 4036 开始；第 0 页的文件头记着页大小 4096、页数 2。`.page` 和 `xxd` 说的是同一件事，只是一个替你把字节解释成了字段。

这一页沿着这条路径自底向上读代码：文件层怎样按偏移读写整页，整数怎样写成字节，pager 怎样缓存、钉住和分配页，一页之内的槽式布局长什么样，记录怎样编码，B+ 树怎样查找、分裂、删除和自检。读完应该能手算 `.page` 输出里的每一个偏移，能由一串十六进制还原出一页的结构，能预测插入若干行之后 `.tree` 的形状，也能在 pager 或 B+ 树上做修改并用现有测试检验。

页面里的代码都摘自 `code/项目/MdrDB/src`。构建和命令行用法见 7.1，[7.3](/教程/正文/项目案例/MdrDB/7_3_查询路径_恢复与测试) 讲查询路径、回滚日志与测试。

## 1. 文件层：按偏移读写整页

数据库文件被看成一串 4096 字节的页，第 n 页从偏移 n × 4096 开始。打开数据库文件的只有 `src/file.c`，其他模块拿到的 `FILE *` 只用来打印输出，不碰数据文件：

```c
db_status file_read_at(db_file *f, long offset, void *buf, size_t size,
                       size_t *nread) {
    *nread = 0;
    if (fseek(f->fp, offset, SEEK_SET) != 0) {
        return DB_IO_ERROR;
    }
    size_t n = fread(buf, 1, size, f->fp);
    if (n < size && ferror(f->fp)) {
        clearerr(f->fp);
        return DB_IO_ERROR;
    }
    *nread = n;
    return DB_OK;
}
```

先 `fseek` 再 `fread`，读满一页就返回。`*nread` 比请求的字节数少，说明文件比页数记的短，pager 的 `read_page` 据此返回 `DB_CORRUPT`，上层不会拿半页旧数据继续解析。`clearerr` 是必要的：出过错之后流上的错误标志会一直挂着，后面每次读写都失败。

打开方式决定了语义。`file_open` 用 `"rb+"`，以读写方式打开一个必须存在的文件；`file_create` 用 `"wb+"`，新建或清空。二进制模式不是可选项：Windows 上文本模式会把 `\r\n` 和 `\n` 互相转换，按偏移定位就不再对得上字节。`file_exists` 用 `fopen(path, "rb")` 试探，能打开就关闭并返回真。

`file_write_at` 多了一件事，故障注入：

```c
db_status file_write_at(db_file *f, long offset, const void *buf, size_t size) {
    if (fault.crashed) {
        return DB_IO_ERROR;
    }
    bool crash_here = at_crash_point();
    /* 崩溃点上的写只写进前一半，模拟断电时只写进一部分的撕裂写。 */
    size_t n = crash_here ? size / 2 : size;
    if (fseek(f->fp, offset, SEEK_SET) != 0 || fwrite(buf, 1, n, f->fp) != n) {
        clearerr(f->fp);
        return DB_IO_ERROR;
    }
    if (crash_here) {
        crash();
        return DB_IO_ERROR;
    }
    return DB_OK;
}
```

故障注入本身在 7.3 讲，这里只需要注意它对文件层提出的约束：每次 `fwrite` 必须真的落到文件里，不能攒在 stdio 的缓冲区里。

`wrap` 里做的第一件事就是关掉缓冲：

```c
    /*
     * 关掉 stdio 的缓冲，每次 fwrite 都立即交给操作系统。页本来就是
     * 整块读写，缓冲省不了几次系统调用；更重要的是，数据到达操作系统
     * 的顺序从此与代码中写的顺序一致，"在第 n 次写入时崩溃"才名副其实。
     */
    if (setvbuf(fp, NULL, _IONBF, 0) != 0) {
        fclose(fp);
        return DB_IO_ERROR;
    }
```

页本来就按整页读写，缓冲攒不出更大的一批写，省不下系统调用。真正的理由是顺序：带缓冲时，程序以为写了的字节可能还躺在用户空间的缓冲区里，测试里「第 3 次写操作处崩溃」就和实际到达文件系统的顺序对不上，崩溃测试也就失去了意义。

::: tip `fseek` 的偏移类型

`page_offset` 返回 `long`，`fseek` 的参数也是 `long`。Windows 上 `long` 只有 32 位，页数上限 `DB_MAX_PAGES` 因此定为 524288（524288 × 4096 = 2^31），文件不超过 2 GiB。要支持更大的文件，得先把偏移换成 64 位接口。

:::

## 2. 大端序：把整数写成字节

文件里的多字节整数一律按大端序（big-endian）存放，高位字节在前。`src/format.h` 只有四个小函数负责这件事：

```c
/* 先转成 uint32_t 再移位：uint8_t 会提升为 int，左移 24 位可能溢出。 */
static inline uint32_t get_u32(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}

static inline void put_u32(uint8_t *p, uint32_t v) {
    p[0] = (uint8_t)(v >> 24);
    p[1] = (uint8_t)(v >> 16);
    p[2] = (uint8_t)(v >> 8);
    p[3] = (uint8_t)v;
}
```

页大小 4096 是 0x00001000，`put_u32` 把它写成 `00 00 10 00`，用 `xxd` 看就是从左到右这样排。换一台小端机器，文件内容不变，这正是「同一个文件在任何机器上都是同一串字节」的意思。

注释里那句「先转成 `uint32_t`」不是形式主义。`p[0]` 是 `uint8_t`，参与运算时先提升为 `int`，`0xFF << 24` 就变成有符号整数左移溢出，标准上属于未定义行为；先转成 `uint32_t`，左移在无符号类型里进行，结果才有定义。

::: compare left-title="把结构体直接写进文件" right-title="逐字节编码"

```c
typedef struct header {
    char magic[14];
    uint32_t page_size;
    uint32_t page_count;
} header;

header h = {"MdrDB format 1", 4096, 2};
fwrite(&h, sizeof h, 1, fp);
```

---

```c
static void fresh_header(uint8_t *data) {
    memset(data, 0, DB_PAGE_SIZE);
    memcpy(data, header_magic, HEADER_MAGIC_SIZE);
    put_u32(data + HEADER_PAGE_SIZE_OFFSET, DB_PAGE_SIZE);
    put_u32(data + HEADER_PAGE_COUNT_OFFSET, 1);

```

:::

左边这段在本机写出的文件是这样的：

::: terminal title="bash - 结构体与逐字节编码"

```text
$ ./struct_write
sizeof(header) = 24
$ xxd -l 24 struct.db
00000000: 4d64 7244 4220 666f 726d 6174 2031 0000  MdrDB format 1..
00000010: 0010 0000 0200 0000                      ........
```

:::

14 字节的 `char` 数组后面补了 2 个字节，`uint32_t` 按本机的小端序写成 `00 10 00 00`。同一个程序换到另一台机器上，填充和字节序都可能变，文件就不再通用。右边那段是 `fresh_header` 与 `init_header` 的做法：先把整页清零，再按固定偏移写字段，4096 写出来就是 `00 00 10 00`，与 `xxd -l 32 fmt.db` 里的第二行一致。

::: concept fmt-endianness title="磁盘格式由代码决定"

文件里的每个字段写在哪个偏移、占几个字节、按什么字节序，全部由 `format.h` 和调用它的代码决定，与编译器的结构体布局、平台字节序无关。读文件时也必须逐字段取，不能把一页 `memcpy` 到结构体上再看成员。

:::

## 3. pager：页框、钉住与换出

pager 把文件抽象成一组编号的页，负责三件事：缓存、分配新页、事务。上层只认页号，不碰文件偏移。

### 3.1 页框

缓存由固定数量的页框（frame）组成，每个页框是一页的空间加上几个字段：

```c
typedef struct page {
    uint32_t pgno;
    int pins;           /* 钉住计数，大于 0 时不能换出 */
    bool in_use;        /* 页框里是否装着一页 */
    bool dirty;         /* 内容改过，还没写回文件 */
    uint64_t last_used; /* 最近一次被取用的时刻，用于 LRU */
    uint8_t data[DB_PAGE_SIZE];
} page;
```

`pager` 结构本身定义在 `pager.c` 里，对外不透明。它持有 `page *frames` 数组、页框数 `frame_count`、一个每取页加 1 的计数器 `clock`，以及当前页数 `page_count`。默认页框数是 64，最少 4：

```c
#define PAGER_DEFAULT_FRAMES 64

/*
 * B+ 树同时钉住的页不超过 2 个，分配新页时还要临时钉住文件头。
 * 再留一个可以换出的页框，最少需要 4 个。
 */
#define PAGER_MIN_FRAMES 4
```

### 3.2 三条使用规则

取页的入口是 `pager_get`：

```c
db_status pager_get(pager *p, uint32_t pgno, page **out) {
    *out = NULL;
    if (p->state == PAGER_ERROR) {
        return DB_IO_ERROR;
    }
    if (pgno >= p->page_count) {
        return DB_CORRUPT; /* 指向文件末尾之外，只能来自损坏的数据 */
    }
    page *pg = find_frame(p, pgno);
    if (pg != NULL) {
        p->stats.hits++;
    } else {
        db_status rc = take_frame(p, &pg);
        if (rc != DB_OK) {
            return rc;
        }
        rc = read_page(p, pgno, pg->data);
        if (rc != DB_OK) {
            return rc;
        }
        p->stats.misses++;
        pg->pgno = pgno;
        pg->in_use = true;
        pg->dirty = false;
        pg->pins = 0;
    }
    pg->pins++;
    pg->last_used = ++p->clock;
    *out = pg;
    return DB_OK;
}
```

返回的指针指向页框里的 `data`，所以调用者拿到的不是拷贝，而是缓存里的那一页本身。为了保证它在这期间不被换出，`pins` 加 1，这叫钉住（pin）。用完之后必须 `pager_unpin` 把计数减回去：

```c
void pager_unpin(page *pg) {
    if (pg != NULL && pg->pins > 0) {
        pg->pins--;
    }
}
```

修改内容之前则要先声明：

```c
db_status pager_write(pager *p, page *pg) {
    if (p->state == PAGER_ERROR) {
        return DB_IO_ERROR;
    }
    if (p->state != PAGER_WRITING) {
        return DB_MISUSE;
    }
    /*
     * 事务开始后才分配的页（页号不小于 orig_page_count）没有需要保存
     * 的原始内容：回滚后页数恢复原值，这些页落在页数之外，自然作废。
     * 位图保证每页只记一次：同一页第二次修改时，日志里已经是它的原貌。
     */
    if (pg->pgno < p->orig_page_count && !test_bit(p->journaled, pg->pgno)) {
        db_status rc = journal_append(&p->journal, pg->pgno, pg->data);
        if (rc != DB_OK) {
            return fail(p, rc);
        }
        set_bit(p->journaled, pg->pgno);
        p->stats.journaled++;
    }
    pg->dirty = true;
    return DB_OK;
}
```

`pager_write` 做两件事：把这一页的原始内容送进回滚日志（每页只送一次），再把页标成脏。标脏之后，提交时才会把它写回文件。

::: concept pager-rules title="pager 的三条使用规则"

1. `pager_get` 返回的页处于钉住状态，用完必须 `pager_unpin`。没归还的页框不能换出，钉住的页一多，`pager_get` 会返回 `DB_CACHE_FULL`。
2. 修改页的内容之前必须先调用 `pager_write`。它负责把原始内容写进日志并把页标脏；漏掉它，修改既不会进日志，也不会在提交时写回文件。
3. `pager_write` 和 `pager_allocate` 只能在 `pager_begin` 之后调用。没有事务时返回 `DB_MISUSE`。

:::

::: warning 先 `pager_write`，再改字节

`pager_get` 只保证页在缓存里，不保证改动会被记录。拿到页之后直接往 `pg->data` 里写而不调用 `pager_write`，这一页不会被标脏，提交时不会写回文件，日志里也没有它的原貌。进程内读起来一切正常（读的就是同一块缓存），重新打开后修改消失。第 10 节有一个这样的实验。

:::

### 3.3 换出：LRU 与脏页写回

页框用完要换入新页。先按页号找已经在缓存里的页框：

```c
/* 页框不多，顺序查找足够快。页框多起来时应当改用散列表。 */
static page *find_frame(pager *p, uint32_t pgno) {
    for (size_t i = 0; i < p->frame_count; i++) {
        page *pg = &p->frames[i];
        if (pg->in_use && pg->pgno == pgno) {
            return pg;
        }
    }
    return NULL;
}
```

找不到就挑一个牺牲者：

```c
/*
 * 找一个页框装新页：有空闲的就用空闲的，否则换出最久没用、也没被
 * 钉住的那一页。被换出的页若是脏的，要先写回文件。事务还没提交，
 * 修改就进了数据库文件，这是允许的：原始内容在日志里，随时能撤销。
 */
static db_status take_frame(pager *p, page **out) {
    page *victim = NULL;
    for (size_t i = 0; i < p->frame_count; i++) {
        page *pg = &p->frames[i];
        if (!pg->in_use) {
            victim = pg;
            break;
        }
        if (pg->pins == 0 &&
            (victim == NULL || pg->last_used < victim->last_used)) {
            victim = pg;
        }
    }
    if (victim == NULL) {
        return DB_CACHE_FULL;
    }
    if (victim->in_use && victim->dirty) {
        db_status rc = write_back(p, victim);
        if (rc != DB_OK) {
            return rc;
        }
        p->stats.spills++;
    }
    victim->in_use = false;
    *out = victim;
    return DB_OK;
}
```

牺牲者取「没有被钉住、`last_used` 最小」的那一页，这就是最近最少使用（least recently used，LRU）。`last_used` 不取时间戳，取每次取页加 1 的计数器，比调用时钟便宜，也不会因为系统时间跳变而出错。`take_frame` 有两条路径：有空闲页框就直接用；没有空闲页框时，被选中的脏页要先写回文件，这次提前写回记在 `spills` 里。事务还没提交就把修改写进数据库文件，在回滚日志的方案里是允许的，因为原始内容已经在日志里；`write_back` 每次写之前都会先同步日志，这条规则在 7.3 展开。

### 3.4 分配新页与文件头

文件只增不减，新页总是追加在末尾，页数记在第 0 页的文件头里：

```c
db_status pager_allocate(pager *p, page **out) {
    *out = NULL;
    if (p->state == PAGER_ERROR) {
        return DB_IO_ERROR;
    }
    if (p->state != PAGER_WRITING) {
        return DB_MISUSE;
    }
    if (p->page_count >= DB_MAX_PAGES) {
        return DB_FULL;
    }

    /* 页数记在文件头里，改它和改别的页一样：先 pager_write，后修改。 */
    page *header;
    db_status rc = pager_get(p, 0, &header);
    if (rc != DB_OK) {
        return rc;
    }
    rc = pager_write(p, header);
    if (rc != DB_OK) {
        pager_unpin(header);
        return rc;
    }
    uint32_t pgno = p->page_count;
    put_u32(header->data + HEADER_PAGE_COUNT_OFFSET, pgno + 1);
    pager_unpin(header);
    p->page_count = pgno + 1;

    /* 新页不用从文件读：它的内容从全零开始。 */
    page *pg;
    rc = take_frame(p, &pg);
    if (rc != DB_OK) {
        return rc;
    }
    memset(pg->data, 0, DB_PAGE_SIZE);
    pg->pgno = pgno;
    pg->in_use = true;
    pg->dirty = true;
    pg->pins = 1;
    pg->last_used = ++p->clock;
    *out = pg;
    return DB_OK;
}
```

改文件头和改别的页走同一套流程：先 `pager_write`，再改字节。若省掉 `pager_write`，页数变了却没进日志、没标脏，回滚时文件头恢复不了，提交后文件里也可能还是旧页数。新页不读文件，直接清零；返回时已经钉住，调用者用完同样要 `pager_unpin`。

`btree_create` 就是调用 `pager_allocate` 拿到第 1 页，检查页号是 `BTREE_ROOT` 之后 `node_init(root->data, NODE_LEAF)`，最后 `pager_unpin`。所以新库有两个页：第 0 页文件头，第 1 页是 B+ 树的根，根页号恒为 `BTREE_ROOT`。

### 3.5 观察：页框多少影响什么

在一个已经有 300 行（7 页）的库上，用一个事务再插入 300 行：`more.txt` 里是 `begin`、300 行 `insert`、`commit` 和 `.info`。分别用默认的 64 个页框和 4 个页框跑一遍：

命中、未命中和页数完全相同，`.tree` 也逐字相同，唯一变化的是 `spills`：4 个页框装不下事务的工作集，有 4 次脏页在提交之前被换出，提前写回了文件。缓存大小不改变结果，只改变换出次数。

对照一下每条插入各自成事务的情形（`rows_info.txt` 是 300 条 `insert` 加一行 `.info`）：


:::

`spills` 是 0。每个自动提交的事务只碰叶子和文件头两三页，4 个页框就够。代价在日志：300 个事务各把叶子的原始内容写一次日志，加上分配新页时记下的文件头，一共 308 页；而一个大事务只记了 3 页。两种写法各有各的开销。

### 3.6 漏掉 `pager_unpin` 会怎样

页框是有限的，钉住不放的页无法换出。`test_pager` 里的 `test_pins_and_cache_full` 先建一个 5 页的库，用 4 个页框把第 1～4 页全部取出来钉住，再取第 5 页。省略了开头几行之后，函数的下半段是这样：

```c
    page *again;
    CHECK_OK(pager_get(p, 1, &again)); /* 已在缓存中：同一个页框 */
    CHECK(again == held[0] && again->pins == 2);
    pager_unpin(again);
    page *extra;
    CHECK_STATUS(pager_get(p, 5, &extra), DB_CACHE_FULL);
    for (int i = 0; i < PAGER_MIN_FRAMES; i++) {
        pager_unpin(held[i]);
    }
    CHECK_OK(pager_get(p, 5, &extra));
    pager_unpin(extra);
    CHECK(pager_pinned(p) == 0);
```

已经缓存的页再取一次不会占新页框，只是把 `pins` 加到 2，算一次命中。全部钉住之后，`pager_get` 只能返回 `DB_CACHE_FULL`；只要归还一个，立刻就能取到。这也解释了为什么 `test_btree` 每次检查树之后都断言 `pager_pinned(p) == 0`：钉住计数漏减不会立刻让结果出错，而是等到页框耗尽才以别处的失败暴露出来，越早发现越好。

## 4. 节点页面：槽式布局

B+ 树的每个节点占一整页，叶子和内部节点用同一种布局，差别只在单元格的内容和 `link` 的含义。这种布局通常叫槽式页面（slotted page）。

### 4.1 页头

`src/node.h` 开头把布局写成了注释：

```text
 *   偏移 0，1 字节：节点类型，1 = 叶子，2 = 内部节点
 *   偏移 1，1 字节：保留，写 0
 *   偏移 2，2 字节：单元格数量
 *   偏移 4，2 字节：单元格内容区的起点
 *   偏移 6，2 字节：保留，写 0
 *   偏移 8，4 字节：叶子：右边相邻叶子的页号（0 表示没有）；
 *                   内部节点：最右孩子的页号
 *   偏移 12 起：单元格指针数组，每项 2 字节，按键升序排列
```

前 12 个字节这样排，有两处是刻意的。第一处是「保留，写 0」：类型字段只用了 1 个字节，后面留 1 个字节，让 2 字节的数量字段对齐；`link` 前面再留 2 个字节，让 4 字节的页号从偏移 8 开始。第二处是偏移 4 的 `content_start` 用 16 位存放，`node.c` 用一句 `_Static_assert` 记下了这个约束：

```c
/* C11：内容区起点用 16 位存放，页不能大于 65535 字节。 */
_Static_assert(DB_PAGE_SIZE <= 65535, "page offsets are stored in 16 bits");
```

4096 字节的页里，偏移最大 4095，16 位绰绰有余；页大小若改成 65536，这个字段就不够用，编译时就会停下来。

::: concept node-header-layout title="节点页的四个区域"

一页从低地址到高地址分成四段：

1. 页头：12 字节，定长。
2. 单元格指针数组：每个单元格 2 字节，存放该单元格在本页内的偏移，按键升序排列。
3. 空闲空间：指针数组末尾到内容区起点之间的整块区域。
4. 单元格内容区：从页尾往前放，`content_start` 指向这段的第一个字节。

空闲空间的大小由 `node_free_space` 算出，就是内容区起点减去指针数组末尾：

```c
size_t node_free_space(const uint8_t *node) {
    size_t pointers_end =
        NODE_HEADER_SIZE + CELL_POINTER_SIZE * (size_t)node_cell_count(node);
    return content_start(node) - pointers_end;
}
```

:::

### 4.2 两种单元格

叶子单元格由三部分组成：键 4 字节、负载长度 2 字节、负载。内部单元格是键 4 字节、孩子页号 4 字节，定长 8 字节。两种都以键开头，所以 `node_key` 不用区分节点类型：

```c
uint32_t node_key(const uint8_t *node, int i) {
    return get_u32(node_cell(node, i));
}
```

内部节点的第 i 个孩子存放在第 i 个单元格里，最右孩子不占单元格，存在 `link` 里：

```c
uint32_t internal_child(const uint8_t *node, int i) {
    if (i == node_cell_count(node)) {
        return node_link(node);
    }
    return get_u32(node_cell(node, i) + 4);
}
```

「孩子比键多一个」就体现在这里：n 个键对应 n + 1 个孩子，多出来的那个用 `link` 表示。

### 4.4 插入单元格

插入分两步：字节放到内容区前面，指针数组腾出位置。

```c
void node_insert_cell(uint8_t *node, int i, const uint8_t *cell, size_t size) {
    int count = node_cell_count(node);
    size_t start = content_start(node) - size;
    memcpy(node + start, cell, size);
    /* 指针数组里第 i 项及之后的项后移一格，空出第 i 项。 */
    memmove(pointer_slot(node, i + 1), pointer_slot(node, i),
            CELL_POINTER_SIZE * (size_t)(count - i));
    put_u16(pointer_slot(node, i), (uint16_t)start);
    put_u16(node + COUNT_OFFSET, (uint16_t)(count + 1));
    put_u16(node + CONTENT_OFFSET, (uint16_t)start);
}
```

`content_start` 减去 `size`，新的单元格紧贴旧的内容区放；指针数组从第 i 项起整体后移一格，空出来的第 i 项写入新偏移。`memcpy` 拷贝新单元格没问题（源在调用者的栈上），`memmove` 处理指针数组则是因为源和目的在同一块内存里且重叠，用 `memcpy` 是未定义行为。最后三个字段一起更新：数量加 1，内容区起点前移。

调用之前必须用 `node_has_room` 确认放得下，`node_insert_cell` 自己不做检查：

```c
bool node_has_room(const uint8_t *node, size_t cell_size) {
    return node_free_space(node) >= cell_size + CELL_POINTER_SIZE;
}
```

要留出 `cell_size + CELL_POINTER_SIZE`，因为除了单元格本身，指针数组还要多占 2 字节。

### 4.5 删除与紧凑

删除的做法与插入相反，但多了一步搬动：

```c
void node_remove_cell(uint8_t *node, int i) {
    int count = node_cell_count(node);
    size_t start = content_start(node);
    size_t offset = pointer_at(node, i);
    size_t size = node_cell_size(node, i);

    /*
     * 让内容区保持连续：把地址低于被删单元格的内容整体后移 size 字节，
     * 再给指向这些内容的指针加上 size。空闲空间因此总是一整块，插入时
     * 不用整理碎片。代价是每次删除都要搬动数据，一页之内，搬得起。
     */
    memmove(node + start + size, node + start, offset - start);
    memset(node + start, 0, size);
    memmove(pointer_slot(node, i), pointer_slot(node, i + 1),
            CELL_POINTER_SIZE * (size_t)(count - i - 1));
    memset(pointer_slot(node, count - 1), 0, CELL_POINTER_SIZE);
    for (int k = 0; k < count - 1; k++) {
        size_t p = pointer_at(node, k);
        if (p < offset) {
            put_u16(pointer_slot(node, k), (uint16_t)(p + size));
        }
    }
    put_u16(node + COUNT_OFFSET, (uint16_t)(count - 1));
    put_u16(node + CONTENT_OFFSET, (uint16_t)(start + size));
}
```

被删单元格之上（地址更低）的那些内容整体往后挪 `size` 字节，把洞补上；指向这些内容的指针都要加 `size`。效果是内容区始终连续，`content_start` 一路后移，空闲空间永远是一整块。删掉 bob 之后：

::: terminal title="bash - 删除之后"

```text
mdrdb> delete 2
ok
mdrdb> .page 1
page 1: leaf
  cells 2, free bytes 4020, content start 4036, next leaf 0
  cell 0: offset 4066, size 30, key 1
  cell 1: offset 4036, size 30, key 3
```

:::

删之前 carol 的单元格在 4010，是内容区的最低处；删之后它整体后移 26 字节到 4036，内容区起点也随之变成 4036。空闲空间从 3992 增加到 4020，正好多出 bob 的 26 字节单元格和 2 字节指针。`4010 + 26 = 4036`，free bytes 是 `4036 − 12 − 4 = 4020`，都能手算。

另一种做法是维护空闲块链表，删除时只把单元格标成空闲，插入时找一块放得下的。SQLite 的页面格式就是这样，页头里存第一个空闲块的偏移，每条空闲块记着下一块的偏移和大小。它省掉了删除时的搬动，代价是插入时要找块、块太小要合并，页内会留下碎片。MdrDB 选紧凑：一页之内搬动最多几千字节，而代码简单得多，`node_validate` 也能用一句 `used == DB_PAGE_SIZE - start` 检查整个内容区。

### 4.6 校验：磁盘上的字节不可信

从文件读回的页面可能已经损坏，任何按它解析的代码都可能越界。`node_validate` 是防线：

```c
bool node_validate(const uint8_t *node) {
    if (node[KIND_OFFSET] != NODE_LEAF && node[KIND_OFFSET] != NODE_INTERNAL) {
        return false;
    }
    int count = node_cell_count(node);
    size_t start = content_start(node);
    size_t pointers_end = NODE_HEADER_SIZE + CELL_POINTER_SIZE * (size_t)count;
    if (pointers_end > start || start > DB_PAGE_SIZE) {
        return false;
    }
    size_t header =
        node_is_leaf(node) ? LEAF_CELL_HEADER_SIZE : INTERNAL_CELL_SIZE;
    size_t used = 0;
    for (int i = 0; i < count; i++) {
        size_t offset = pointer_at(node, i);
        if (offset < start || offset + header > DB_PAGE_SIZE) {
            return false;
        }
        size_t size = cell_size_at(node, offset);
        if (offset + size > DB_PAGE_SIZE) {
            return false;
        }
        used += size;
    }
    /* 内容区紧凑：所有单元格加起来正好填满 [start, 页尾)。 */
    return used == DB_PAGE_SIZE - start;
}
```

它检查四件事：类型是两个合法值之一；指针数组末尾不超过内容区起点；每个单元格的偏移和长度都在页内；所有单元格加起来正好填满 `[start, 页尾)`，也就是内容区紧凑、没有重叠的洞。最后一条最省事，一条等式把「重叠」和「碎片」一并排除了。

B+ 树的每个入口都用 `load_node` 取页，验证不过就按损坏处理：

```c
/* 取一页并确认它是格式正确的节点。文件可能损坏，先验证再解析。 */
static db_status load_node(pager *p, uint32_t pgno, page **out) {
    if (pgno == 0) {
        return DB_CORRUPT; /* 第 0 页是文件头，不会是树节点 */
    }
    db_status rc = pager_get(p, pgno, out);
    if (rc != DB_OK) {
        return rc;
    }
    if (!node_validate((*out)->data) || !payloads_fit((*out)->data)) {
        pager_unpin(*out);
        *out = NULL;
        return DB_CORRUPT;
    }
    return DB_OK;
}
```

`payloads_fit` 是后来补上的一道检查，理由在 7.6 讲：只检查页内布局还不够，超长的负载会让分裂算法的前提失效。

::: tip 先用 `.page`，再下断点

`.page n` 打印的就是 `node_print` 的结果，与调试器里看 `pg->data` 是同一份东西。写入错误时，先 `.page` 看偏移是否对得上，能省掉大半的调试时间。

:::

## 5. 记录编码：varint

主键已经作为单元格的键，负载里只放 `name` 和 `email`。两个字段的长度都用一个变长整数（variable-length integer，varint）编码：

```c
/*
 * varint：每字节低 7 位存数据，最高位为 1 表示后面还有字节，低位组
 * 在前（与 Protocol Buffers 相同）。小于 128 的数只占 1 字节，名字和
 * 邮箱的长度大多在这个范围内，比固定用 2 字节省空间。
 */
size_t varint_encode(uint32_t value, uint8_t *out) {
    size_t n = 0;
    while (value >= 0x80) {
        out[n++] = (uint8_t)(value | 0x80);
        value >>= 7;
    }
    out[n++] = (uint8_t)value;
    return n;
}
```

前几组值编出来是这样的：

::: terminal title="bash - varint 编码"

```text
$ ./varint_demo
   5: 05
 127: 7F
 128: 80 01
 300: AC 02
```

:::

300 的二进制是 `1 0010 1100`，低 7 位是 `010 1100`，置上最高位成 `AC`；剩下 `10`，写成一个字节 `02`。127 是单字节能表示的最大值，128 就要两个字节，所以 `test_record` 专门用 0、1、127、128、300、16383、16384 一直到 `UINT32_MAX` 这一串值做往返测试。

用 varint 的理由是长度分布：`name` 最长 32 字节，`email` 最长 255，绝大多数不超过 127。定长的话每个字段要占 2 字节，短名字的空间就白扔了。

记录本身只有两段：`record_encode` 先求两个字段的长度，再依次调用 `put_text`，每个字段写成「长度、字节」，文本不带结尾的 `'\0'`。求长度用 `text_length`，这里有一个细节：

```c
static db_status text_length(const char *text, size_t capacity, size_t *len) {
    const char *end = memchr(text, '\0', capacity);
    if (end == NULL) {
        return DB_TOO_LONG;
    }
    *len = (size_t)(end - text);
    return DB_OK;
}
```

用 `memchr` 在数组范围内找 `'\0'`，不用 `strlen`。`db_row` 的字段是 `char name[DB_NAME_MAX + 1]`，如果调用者把 33 个字节都填满而没有结尾的 `'\0'`，`strlen` 会一直读到数组之外。`memchr` 最多看 `capacity` 个字节，找不到就返回「太长」，不会越界。`test_record` 的 `test_record_rejects_unterminated_field` 就是这条路径。

解码一侧把文件里的每个数字都当成不可信的输入：

```c
/* 读一个文本字段。长度是否超限、是否越过记录末尾、内容里有没有 '\0'，
 * 逐项核对：文件里的任何数字都不可信。 */
static db_status get_text(const uint8_t *in, size_t size, size_t *pos,
                          char *out, size_t max) {
    uint32_t len;
    size_t n = varint_decode(in + *pos, size - *pos, &len);
    if (n == 0 || len > max || len > size - *pos - n) {
        return DB_CORRUPT;
    }
    const uint8_t *text = in + *pos + n;
    if (memchr(text, '\0', len) != NULL) {
        return DB_CORRUPT; /* 文本里有 '\0'，读出来会被截断 */
    }
    memcpy(out, text, len);
    out[len] = '\0';
    *pos += n + len;
    return DB_OK;
}
```

四个检查各挡一种损坏：`n == 0` 是 varint 本身不合法（被截断或超过 32 位）；`len > max` 是字段超过目标数组的容量；`len > size - *pos - n` 是长度字段把读取位置推出记录末尾；`memchr` 找到内嵌的 `'\0'`，说明文本里藏着截断点。最后 `record_decode` 还要求读完之后位置正好等于记录长度，多余字节也按损坏处理：

```c
db_status record_decode(const uint8_t *in, size_t size, db_row *row) {
    size_t pos = 0;
    db_status rc = get_text(in, size, &pos, row->name, DB_NAME_MAX);
    if (rc == DB_OK) {
        rc = get_text(in, size, &pos, row->email, DB_EMAIL_MAX);
    }
    if (rc == DB_OK && pos != size) {
        rc = DB_CORRUPT; /* 记录末尾多出了字节 */
    }
    return rc;
}
```

`test_record` 把这些情况逐条覆盖：`{10, 'a', 'b'}`（长度越过末尾）、`{1, 'a', 1, 'b', 0xEE}`（末尾多一字节）、`{1, 'a'}`（缺 email）、`{2, 'a', 0, 0}`（内嵌 `'\0'`）、长度为 40 的名字（超过 `DB_NAME_MAX`）。

`varint_decode` 对超过 32 位的输入也有交代：

```c
size_t varint_decode(const uint8_t *in, size_t size, uint32_t *value) {
    uint32_t result = 0;
    for (size_t i = 0; i < size && i < VARINT_MAX_SIZE; i++) {
        uint32_t bits = in[i] & 0x7Fu;
        if (i == VARINT_MAX_SIZE - 1 && bits > 0x0Fu) {
            return 0; /* 第 5 个字节只剩 4 位可用，再多就超出 32 位 */
        }
        result |= bits << (7 * i);
        if ((in[i] & 0x80u) == 0) {
            *value = result;
            return i + 1;
        }
    }
    return 0;
}
```

第 5 个字节左移 28 位，只有低 4 位能落进 32 位，高 3 位非零就说明数字超出 `uint32_t`。返回 0 表示解码失败，与「一个字节都没读掉」在调用者那里是同一个处理。

## 6. B+ 树的查找

树的分层约定很简单：内部节点的每个单元格存一个分隔键和一个孩子页号，键 i 之前的那个孩子里的键都小于键 i；等于分隔键的键走右边。

### 6.1 内部节点的约定

```c
typedef struct tree_path {
    int depth;                      /* 层数，pgno[depth - 1] 是叶子 */
    uint32_t pgno[BTREE_MAX_DEPTH]; /* 每一层经过的页 */
    int slot[BTREE_MAX_DEPTH];      /* 每一层走的是第几个孩子 */
} tree_path;
```

```c
/*
 * 在内部节点里为 key 选孩子。第 i 个孩子里的键都小于第 i 个分隔键，
 * 且不小于第 i - 1 个分隔键；等于分隔键的 key 属于它右边的孩子。
 */
static int child_slot(const uint8_t *node, uint32_t key) {
    bool found;
    int i = node_search(node, key, &found);
    return found ? i + 1 : i;
}
```

`node_search` 返回第一个键不小于 `key` 的位置。没有正好相等时，那个位置的键就是第一个大于 `key` 的，孩子取左边那个（下标 i），其中的键都小于这个分隔键。正好相等时，把键留在右边那个孩子（下标 i + 1）。这正好对应插入时叶子分裂的约定：右半的第一个键复制一份上推，那一行本身留在右叶，所以「等于分隔键」必须走右边。

叶子链也是这样接起来的。右叶接替左叶原来的右邻，左叶的右邻指向新叶：

```c
        node_set_link(right->data, link);       /* 右叶接替原来的右邻 */
        node_set_link(left->data, right->pgno); /* 左叶的右邻是新叶 */
```

### 6.2 下降到叶子

```c
static db_status find_leaf(pager *p, uint32_t key, tree_path *path) {
    uint32_t pgno = BTREE_ROOT;
    for (int level = 0; level < BTREE_MAX_DEPTH; level++) {
        page *pg;
        db_status rc = load_node(p, pgno, &pg);
        if (rc != DB_OK) {
            return rc;
        }
        path->pgno[level] = pgno;
        if (node_is_leaf(pg->data)) {
            path->depth = level + 1;
            pager_unpin(pg);
            return DB_OK;
        }
        path->slot[level] = child_slot(pg->data, key);
        pgno = internal_child(pg->data, path->slot[level]);
        pager_unpin(pg);
    }
    return DB_CORRUPT; /* 树不可能这么深，多半是页之间形成了环 */
}
```

每下降一层，把当前页号和走的是第几个孩子记进 `tree_path`，然后立刻 `pager_unpin` 再取下一层。不钉住父页是一个重要的取舍：路径全部钉住的话，三层树就要占三个页框，`PAGER_MIN_FRAMES` 那 4 个就不够用了。

不在节点里存父指针，理由与分裂有关：

::: info 用路径而不是父指针

如果在每个节点里记住父节点页号，那么叶子或内部节点分裂、根长高时，所有搬家页面的父指针都要改。根长高尤其麻烦：根的内容搬到新页，原来所有「父节点是第 1 页」的孩子都要改成新页号。用路径 `tree_path` 的话，一次查找已经记下了从根到叶经过的每一层，插入时沿着它逐层修改，页面里不需要存任何反向信息。代价是查找要带一个 `tree_path` 的栈上数组，`BTREE_MAX_DEPTH` 为 16，一层 4 + 4 字节，一百多字节。

:::

`BTREE_MAX_DEPTH` 是防御损坏文件的上限。正常的三层树用不到它，深度超限只可能来自页之间形成了环。

### 6.3 叶子内二分查找

```c
int node_search(const uint8_t *node, uint32_t key, bool *found) {
    int count = node_cell_count(node);
    int lo = 0;
    int hi = count;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (node_key(node, mid) < key) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }
    *found = lo < count && node_key(node, lo) == key;
    return lo;
}
```

返回第一个键不小于 `key` 的位置，`*found` 说明该位置是否恰好相等。这个返回值同时被三处使用：`btree_find` 拿它判断是否找到，`btree_insert` 拿它当插入位置，`child_slot` 拿它在内部节点里选孩子。一个函数三种用途，所以它返回位置而不是布尔值。

`mid = lo + (hi - lo) / 2` 而不是 `(lo + hi) / 2`，是二分查找的标准写法，两者在 `lo`、`hi` 非负时结果相同，前一种不会因为加法溢出而出错。

`btree_find` 把「下降」和「叶内查找」连起来：

```c
db_status btree_find(pager *p, uint32_t key, uint8_t *payload, size_t *size) {
    tree_path path;
    db_status rc = find_leaf(p, key, &path);
    if (rc != DB_OK) {
        return rc;
    }
    page *leaf;
    rc = load_node(p, leaf_of(&path), &leaf);
    if (rc != DB_OK) {
        return rc;
    }
    bool found;
    int i = node_search(leaf->data, key, &found);
    if (!found) {
        rc = DB_NOT_FOUND;
    } else {
        const uint8_t *src = leaf_payload(leaf->data, i, size);
        if (*size > BTREE_MAX_PAYLOAD) {
            rc = DB_CORRUPT;
        } else {
            memcpy(payload, src, *size);
        }
    }
    pager_unpin(leaf);
    return rc;
}
```

`find_leaf` 已经把叶子页号记在 `path.pgno[path.depth - 1]` 里，但返回时已经 unpin 了，所以这里要重新 `load_node` 取一次。如果是刚取过的叶子，`load_node` 会命中缓存，不读文件。

## 7. 插入与分裂

插入分三种情形：叶子放得下；叶子放不下要分裂；分裂一路传到根，根要长高。

### 7.1 放得下就插入

```c
/* 节点放得下就把 cell 插到第 index 个位置，*done 置为 true。 */
static db_status insert_if_room(pager *p, uint32_t pgno, int index,
                                const uint8_t *cell, size_t size, bool *done) {
    *done = false;
    page *pg;
    db_status rc = load_node(p, pgno, &pg);
    if (rc != DB_OK) {
        return rc;
    }
    if (node_has_room(pg->data, size)) {
        rc = pager_write(p, pg);
        if (rc == DB_OK) {
            node_insert_cell(pg->data, index, cell, size);
            *done = true;
        }
    }
    pager_unpin(pg);
    return rc;
}
```

`pager_write` 在 `node_insert_cell` 之**前**调用。这个顺序不能反：`pager_write` 要的是页的原始内容，等改完了再调用，进日志的就是改过的内容，回滚反而会把修改留下。

### 7.2 叶子分裂

放不下时，把原单元格和新单元格一起取出来，排好序，按字节数一分为二：

```c
/*
 * 分裂用的临时区：节点原有的单元格加上新单元格，按键的顺序排好。
 * 合计可能超过一页，所以不能在页面里原地操作。
 */
typedef struct cell_list {
    int count;
    size_t used;
    uint16_t offset[NODE_MAX_CELLS + 1];
    uint16_t size[NODE_MAX_CELLS + 1];
    uint8_t bytes[2 * DB_PAGE_SIZE];
} cell_list;
```

`bytes[2 * DB_PAGE_SIZE]` 容纳两页的字节：原页里最多一页的单元格，加上新单元格最多 `LEAF_CELL_HEADER_SIZE + BTREE_MAX_PAYLOAD` 字节，一定装得下。`offset` 数组比 `NODE_MAX_CELLS` 多一项，是为了容纳新加的那一个。

`collect_cells` 把原单元格和新单元格按顺序排好：

```c
static void collect_cells(const uint8_t *node, int index, const uint8_t *cell,
                          size_t size, cell_list *list) {
    int count = node_cell_count(node);
    list->count = 0;
    list->used = 0;
    for (int i = 0; i <= count; i++) {
        if (i == index) {
            cell_list_add(list, cell, size);
        }
        if (i < count) {
            cell_list_add(list, node_cell(node, i), node_cell_size(node, i));
        }
    }
}
```

循环写成 `i <= count`，因为新单元格可能插在最后（`index == count`）。每一轮先把新单元格放在第 `index` 个位置，再放原有的第 i 个，下标正好对齐。

`split_point` 选分裂位置：

```c
static int split_point(const cell_list *list) {
    size_t total = 0;
    for (int i = 0; i < list->count; i++) {
        total += list->size[i] + CELL_POINTER_SIZE;
    }
    size_t left = 0;
    int m = 0;
    while (2 * left < total) {
        left += list->size[m] + CELL_POINTER_SIZE;
        m++;
    }
    return m;
}
```

按字节数而不是按单元格个数对半分。单元格大小可以差很多，比如一条长记录 290 字节、一条短记录 30 字节，按个数分会让一半塞不下。`2 * left < total` 是「左半还不到一半」的整数写法，避免除法；循环到左半第一次达到或超过一半就停，`m` 是左半拿走的单元格数。

```c
static void fill_node(uint8_t *node, node_kind kind, const cell_list *list,
                      int from, int to) {
    node_init(node, kind);
    for (int i = from; i < to; i++) {
        /* split_point 保证放得下；断言把这条推理写进代码。 */
        assert(node_has_room(node, list->size[i]));
        node_insert_cell(node, i - from, list->bytes + list->offset[i],
                         list->size[i]);
    }
}
```

那句断言不是装饰：它是「两半都装得下」这条推理在代码里的落脚点。7.6 会讲它成立的条件。

### 7.3 内部节点分裂

内部节点放不下时，做法与叶子不同：第 m 个单元格整个移进父节点，它的孩子归左半：

```c
    } else {
        /* 内部节点：第 m 个单元格整个移进父节点，它的孩子归左半。 */
        fill_node(left->data, NODE_INTERNAL, &list, 0, m);
        node_set_link(left->data, list_child(&list, m));
        fill_node(right->data, NODE_INTERNAL, &list, m + 1, list.count);
        node_set_link(right->data, link);
    }
```

左半拿前 m 个单元格（下标 0 到 m−1），右半拿 m + 1 之后。第 m 个单元格被父节点拿走，它原来的孩子（`list_child(&list, m)`）成为左半的最右孩子，用 `node_set_link` 记在 `link` 里。右半的最右孩子接替原来的 `link`。

为什么叶子是复制、内部是上移？因为键在孩子里的分布不同。叶子里的每一行都必须留在某个叶子里，右叶的第一个键天然可以「兼任」分隔键，复制一份没有歧义。内部节点的第 m 个键原本在左半和右半之间分界，它自己进了父节点之后，左半不需要它、右半也不需要它：左半的最右孩子里所有键都小于它，右半的所有键都大于它。上移过去正好。

### 7.4 根长高

根装不下时，根页号不能变，否则整个数据库都要改「根在哪一页」。做法是把根的内容搬到新页，根变成只有一个孩子的内部节点：

```c
static db_status grow_root(pager *p, uint32_t *child_pgno) {
    page *root;
    page *child;
    db_status rc = load_node(p, BTREE_ROOT, &root);
    if (rc != DB_OK) {
        return rc;
    }
    rc = pager_write(p, root);
    if (rc == DB_OK) {
        rc = pager_allocate(p, &child);
    }
    if (rc == DB_OK) {
        memcpy(child->data, root->data, DB_PAGE_SIZE);
        node_init(root->data, NODE_INTERNAL);
        node_set_link(root->data, child->pgno);
        *child_pgno = child->pgno;
        pager_unpin(child);
    }
    pager_unpin(root);
    return rc;
}
```

三件事：整页复制到新页，根重新初始化成空的内部节点，`link` 指向新页。新根没有单元格，只有一个孩子，这是树里唯一允许「内部节点没有键」的时刻，下一次分裂就会给它填上分隔键。

SQLite 的 `balance_deeper` 做的也是这件事，只是它还要处理页头里与 `BtShared` 有关的状态。

### 7.5 沿路径向上递归

```c
/* 把 cell 插入路径第 level 层节点的第 index 个位置，必要时向上分裂。 */
static db_status insert_cell(pager *p, const tree_path *path, int level,
                             int index, const uint8_t *cell, size_t size) {
    bool done;
    db_status rc =
        insert_if_room(p, path->pgno[level], index, cell, size, &done);
    if (rc != DB_OK || done) {
        return rc;
    }

    uint32_t node = path->pgno[level];
    uint32_t parent = BTREE_ROOT;
    int slot = 0;
    if (level == 0) {
        rc = grow_root(p, &node); /* 之后根就是 node 的父节点 */
    } else {
        parent = path->pgno[level - 1];
        slot = path->slot[level - 1];
    }
    uint32_t right = 0;
    uint32_t separator = 0;
    if (rc == DB_OK) {
        rc = split_node(p, node, index, cell, size, &right, &separator);
    }
    /*
     * 父节点里原来指向 node 的位置改指右半，再在它前面插入
     * (separator, node)：
     *     ... [slot] -> node ...
     *  => ... (separator, node) [slot + 1] -> right ...
     * 先改指针再插入：插入若引起父节点分裂，这个指针会随单元格一起搬走。
     */
    if (rc == DB_OK) {
        rc = set_child(p, parent, slot, right);
    }
    if (rc != DB_OK) {
        return rc;
    }
    uint8_t parent_cell[INTERNAL_CELL_SIZE];
    internal_cell_build(parent_cell, separator, node);
    /* level 为 0 时，父节点是刚长高的根，里面是空的，一定插得进去。 */
    int parent_level = level > 0 ? level - 1 : 0;
    return insert_cell(p, path, parent_level, slot, parent_cell,
                       sizeof parent_cell);
}
```

一个节点的变化被压成两步。父节点里原来第 `slot` 个位置指向 `node`；先把这个位置改指 `right`（`set_child`），再在第 `slot` 个位置插入单元格 `(separator, node)`。插入把原来的第 slot 项连同它指向的 `right` 一起挤到 slot + 1，于是变成「第 slot 个单元格 (separator, node)，第 slot + 1 个位置指向 right」。`internal_set_child` 在索引等于单元格数量时改的是 `link`，所以「最右孩子」这个位置也能被这两步覆盖。

顺序有讲究：先 `set_child`，再 `insert_cell`。反过来的话，如果父节点本身满了、插进新单元格会触发父节点分裂，那个要改的指针会随单元格一起搬到新页，`set_child` 拿旧页号就改错了地方。先改指针，指针待在原位置，插单元格时随单元格一起搬走，不会丢。

递归的终止条件是 `insert_if_room` 成功。每往上一层，`level` 减 1；到根（`level == 0`）时，父节点是刚长高的新根，里面是空的，一定放得下，所以递归一定会在根处结束。

### 7.6 为什么负载上限是可用空间的四分之一

分裂算法成立的前提是「两半都装得下」。`split_point` 只保证左半第一次达到总字节数的一半，如果某个单元格特别大，右半就可能只剩一个超大单元格；如果这个单元格本身就超过半页，`fill_node` 里的断言就会失败。

`BTREE_MAX_PAYLOAD` 把前提写成了常量：

```c
/*
 * 负载上限：一个单元格（连同指针）不超过页内可用空间的 1/4。这样
 * 一个叶子至少放得下 4 个单元格，分裂后的两半也一定都装得下。
 */
#define BTREE_MAX_PAYLOAD                                                      \
    ((DB_PAGE_SIZE - NODE_HEADER_SIZE) / 4 - CELL_POINTER_SIZE -               \
     LEAF_CELL_HEADER_SIZE)
```

代入 4096 和 12：`(4096 − 12) / 4 − 2 − 6 = 1021 − 8 = 1013`。一个单元格连同指针最多 1013 + 2 = 1015 字节。

::: details 「两半都装得下」的推导

可用的空间是 4084 字节（4096 − 12）。设所有单元格连同指针总共 S 字节，第 i 个记为 s_i。

`split_point` 选出的 m 满足：左半 L = s_0 + … + s_{m−1} 是第一个达到或超过 S/2 的前缀。去掉最后一个单元格之后不足一半，所以 L < S/2 + s_{m−1}；右半 R = S − L，于是 R ≤ S/2。

S 的上界是原页可用的 4084 加上新单元格。新单元格也受 `BTREE_MAX_PAYLOAD` 限制，s_{m−1} ≤ 1013 + 2 = 1015，所以 S ≤ 5099，R ≤ 2549.5，远小于 4084。

L < S/2 + s_{m−1} 的两项分别不超过 2549.5 和 1015，加起来不超过 3564.5，也小于 4084。两半都装得下。

:::

`test_node` 里有一条测试验证一页能放多少个。用 100 字节的负载填满一页，每个单元格 106 字节，加指针 108 字节：

```c
    /* 每个单元格 106 字节，加指针 108 字节：(4096 - 12) / 108 = 37。 */
    CHECK(node_cell_count(node) == 37);
```

37 是 4084 / 108 的整数部分，与 `node_has_room` 每次都要留 2 字节指针的算法一致。

这条推导依赖「页里的每个单元格都不超过 `BTREE_MAX_PAYLOAD`」。插入时 `btree_insert` 检查了这一条：

```c
    if (size > BTREE_MAX_PAYLOAD) {
        return DB_TOO_LONG;
    }
```

但磁盘上的页可能已经损坏，`load_node` 因此除了 `node_validate`，还要调用 `payloads_fit`：

```c
/*
 * 叶子单元格的负载不超过 BTREE_MAX_PAYLOAD。插入时检查过的数据一定
 * 满足这一条，损坏的文件却未必；分裂算法要靠它保证两半都装得下（见
 * split_point），所以取页时要与页内布局一起检查。
 */
static bool payloads_fit(const uint8_t *node) {
    if (!node_is_leaf(node)) {
        return true; /* 内部单元格是定长的 */
    }
    for (int i = 0; i < node_cell_count(node); i++) {
        size_t size;
        (void)leaf_payload(node, i, &size);
        if (size > BTREE_MAX_PAYLOAD) {
            return false;
        }
    }
    return true;
}
```

这不是防御性的多余代码，10.4 节有一个真实的例子说明少了它会写到页外。

### 7.8 顺序插入的填充率

`split_point` 永远对半分，这个选择对随机插入很合适，对顺序插入则浪费空间：只有最右边那个叶子是逐渐长满的，左边的叶子都在半满左右。`test_btree` 的 `test_ascending_and_descending` 用 3000 个键顺序插入再逆序插入，就是为了把这条路径走到。

SQLite 在这里有一个优化叫 `balance_quick`：溢出发生在最右边的叶子、而且只有最后一个单元格溢出时，不重新分配，而是新建一个右兄弟页，把溢出的那个单元格直接放进去。效果是左边的叶子保持满，只有新页从空开始逐步填满。README 扩展任务第 4 条就是这个，比较 300 行顺序插入后的 `.tree` 与页数，能看到明显差别。

## 8. 删除与游标

### 8.1 删除不合并

```c
db_status btree_delete(pager *p, uint32_t key) {
    tree_path path;
    db_status rc = find_leaf(p, key, &path);
    if (rc != DB_OK) {
        return rc;
    }
    page *leaf;
    rc = load_node(p, leaf_of(&path), &leaf);
    if (rc != DB_OK) {
        return rc;
    }
    bool found;
    int index = node_search(leaf->data, key, &found);
    if (!found) {
        rc = DB_NOT_FOUND;
    } else {
        rc = pager_write(p, leaf);
        if (rc == DB_OK) {
            node_remove_cell(leaf->data, index);
        }
    }
    pager_unpin(leaf);
    return rc;
}
```

删除只做两件事：找到叶子，`node_remove_cell`。不借位，不合并，不回收页。这就留下一个问题：如果删掉的正好是分隔键，父节点里的那个键还在，它还是对的吗？

::: concept btree-delete-no-merge title="删除后分隔键仍然正确"

假设父节点里的分隔键是 62，左边叶子的键都小于 62，右边叶子的键都大于等于 62。删掉左叶的最后一个键 61 或右叶的第一个键 62 之后，剩下的键仍在原来的范围内，分隔键仍然划分着两边。范围只会变窄，不会跨界。因此查找、插入都不受影响，`btree_check` 的「键落在父节点给出的范围内」也不会失败。

:::

这样安排的好处很实在：删除不需要向上递归，不需要碰父节点，一次页修改就结束了。代价是空间不回收：文件只增不减，删光所有行之后，5 个叶子页还在，根也还是内部节点。删完 300 行的 `.tree`：

::: terminal title="bash - 删光之后"

```text

internal 1: 4 keys
  leaf 2: 0 keys
  key 62
  leaf 3: 0 keys
  key 122
  leaf 4: 0 keys
  key 179
  leaf 5: 0 keys
  key 236
  leaf 6: 0 keys
mdrdb> .check
ok: rows 0, leaf pages 5, internal pages 1, height 2
mdrdb> select
(0 rows)
```

:::

`select` 仍然工作，因为游标跳过空叶子。README 扩展任务第 3 条是把删除时的借位与合并补上，并且把释放的页挂到一个空闲页链表里复用，`btree_check` 也要相应增加最小填充率与空闲页链表的检查。

### 8.2 游标与范围扫描

游标记录「哪个叶子、第几个单元格」和这个单元格的键，不钉住页面：

```c
typedef struct btree_cursor {
    pager *pager;
    uint32_t leaf;
    int index;
    uint32_t key; /* 当前单元格的键，用来确认每走一步键都变大 */
    bool valid;   /* false 表示已经走过最后一个键 */
} btree_cursor;
```

每走一步都重新取页，好处是游标的生命周期不受事务限制：调用者可以在两次 `btree_next` 之间做别的读写，不用担心页框被钉住耗尽。代价是遍历期间不能修改树：一旦某个单元格被删掉，`index` 指向的位置可能已经不是原来那个键。`db_scan` 的回调注释里写着「回调里不能修改数据库」，根源就在这。

```c
static db_status settle(btree_cursor *c) {
    uint32_t steps = 0;
    for (;;) {
        page *pg;
        db_status rc = load_node(c->pager, c->leaf, &pg);
        if (rc != DB_OK) {
            return rc;
        }
        bool leaf = node_is_leaf(pg->data);
        int count = node_cell_count(pg->data);
        uint32_t next = node_link(pg->data);
        uint32_t key = c->index < count ? node_key(pg->data, c->index) : 0;
        pager_unpin(pg);
        if (!leaf) {
            return DB_CORRUPT;
        }
        if (c->index < count) {
            if (c->valid && key <= c->key) {
                return DB_CORRUPT; /* 键没有变大：叶子链接错了或成了环 */
            }
            c->key = key;
            c->valid = true;
            return DB_OK;
        }
        if (next == 0) {
            c->valid = false;
            return DB_OK;
        }
        if (++steps >= pager_page_count(c->pager)) {
            return DB_CORRUPT; /* 走过的叶子比总页数还多：链表成了环 */
        }
        c->leaf = next;
        c->index = 0;
    }
}
```

`settle` 的职责是把游标挪到一个实际存在的单元格上。当前叶子走完了就沿 `link` 去下一个叶子；删除不合并留下的空叶子可能连着好几个，所以要循环。两项检查保证它在损坏的文件上也会结束：连续走过的空叶子不能超过总页数，每停一次键都必须比上一次大。后者是复核时补的：只有前一条时，一个有键的环会让 `select` 永远转下去。

看一个具体的范围查询。删掉 1、61、62 之后，第 2 页从键 2 开始，第 3 页从 63 开始：

::: terminal title="bash - 跨叶子的范围查询"

```text
mdrdb> select 60 63
(60, user60, user60@example.com)
(63, user63, user63@example.com)
(2 rows)
```

:::

`btree_seek(p, 60, &c)` 下降到第 2 页，`node_search` 找到键 60 的位置；`btree_read` 读出一行；`btree_next` 把 `index` 加 1，超出这一页的单元格数，`settle` 沿 `link` 走到第 3 页，`index` 归零，停在键 63 上。`db_scan` 再读一行，键 64 大于 `last`（63），循环结束。

写错了会怎样：`settle` 没有起步时的键检查时，一个有键的环会转不停。复核报告里记录了一次：一个字节的损坏让第 13 页的叶子链指回前面，`select` 在 5 秒内输出了 14,376,692 行。

### 8.3 空叶子与两种遍历

空叶子对两种遍历的影响不同。`btree_seek` 之后的 `btree_next` 走的是叶子链，会跳过空叶子；`btree_check` 走的是中序（先递归左子树，再访问节点），也会遇到空叶子。两者都必须接受空叶子，因为 `btree_delete` 会把叶子删空。`test_btree` 的 `test_random_insert_and_delete` 有一条：全部删光之后重新插入 100 个键，树依然可用。

`print_node` 打印空叶子时只印页号和键数，不印键的范围：

```c
    fprintf(out, "%*s%s %" PRIu32 ": %d key%s", level * 2, "",
            leaf ? "leaf" : "internal", pgno, count, count == 1 ? "" : "s");
    if (leaf && count > 0) {
        fprintf(out, " (%" PRIu32 "..%" PRIu32 ")", node_key(pg->data, 0),
                node_key(pg->data, count - 1));
    }
```

所以删光之后的 `.tree` 里，叶子行只有 `leaf 2: 0 keys`，没有括号。

## 9. 一致性检查

`btree_check` 从根递归下降，检查一整套不变式。它不只是给测试用的，`.check` 元命令、`test_crash` 的每一次恢复之后都要跑一遍。

::: concept btree-invariants title="B+ 树必须满足的不变式"

1. 页号在 `[1, page_count)` 内，0 是文件头，不会是树节点。
2. 每一页只被引用一次：树是一棵真正的树，不是图。
3. 页内布局通过 `node_validate`，且单元格之间不重叠。
4. 叶子单元格的负载不超过 `BTREE_MAX_PAYLOAD`。
5. 每个键都落在父节点给出的范围内；页内的键严格升序。
6. 内部节点至少有一个键。
7. 所有叶子在同一层。
8. 按中序访问叶子得到的顺序与叶子链一致。
9. 除文件头外，每一页都属于这棵树。

:::

```c
static const char *node_problem(const uint8_t *node, uint64_t low,
                                uint64_t high) {
    if (!node_validate(node)) {
        return "bad page layout";
    }
    if (!payloads_fit(node)) {
        return "payload is too long";
    }
    if (cells_overlap(node)) {
        return "cells overlap";
    }
    int count = node_cell_count(node);
    if (!node_is_leaf(node) && count == 0) {
        return "internal node has no keys";
    }
    for (int i = 0; i < count; i++) {
        uint32_t key = node_key(node, i);
        if (key < low || key >= high) {
            return "key outside the range given by the parent";
        }
        if (i > 0 && key <= node_key(node, i - 1)) {
            return "keys are not in ascending order";
        }
    }
    return NULL;
}
```

每一项对应一条不变式。「至少有一个键」有一个例外：`grow_root` 造出来的新根是空的内部节点。这个例外不会让检查失败，因为根长高之后紧接着就分裂，新根马上得到第一个单元格，`grow_root` 也不会单独提交。`test_btree` 的 `test_root_grows` 插入 3 个键时 `height` 是 1，插入 8 个之后是 2。

递归本身：

```c
static db_status check_node(check_state *s, uint32_t pgno, int level,
                            uint64_t low, uint64_t high) {
    if (level >= BTREE_MAX_DEPTH) {
        return corrupt(s, pgno, "tree is too deep");
    }
    if (pgno == 0 || pgno >= pager_page_count(s->pager)) {
        return corrupt(s, pgno, "page number out of range");
    }
    if ((s->seen[pgno / 8] >> (pgno % 8)) & 1u) {
        return corrupt(s, pgno, "page is referenced twice");
    }
    s->seen[pgno / 8] = (uint8_t)(s->seen[pgno / 8] | (1u << (pgno % 8)));
    s->visited++;

    page *pg;
    db_status rc = pager_get(s->pager, pgno, &pg);
    if (rc != DB_OK) {
        return rc;
    }
    const char *problem = node_problem(pg->data, low, high);
    bool leaf = node_is_leaf(pg->data);
    int count = node_cell_count(pg->data);
    uint32_t link = node_link(pg->data);
    pager_unpin(pg);
    if (problem != NULL) {
        return corrupt(s, pgno, problem);
    }

    if (leaf) {
        if (s->leaf_level < 0) {
            s->leaf_level = level;
        } else if (level != s->leaf_level) {
            return corrupt(s, pgno, "leaves are at different depths");
        }
        /* 叶子是按键的顺序访问的，叶子链必须与这个顺序一致。 */
        if (s->last_leaf != 0 && s->last_link != pgno) {
            return corrupt(s, s->last_leaf, "leaf chain skips a leaf");
        }
        s->last_leaf = pgno;
        s->last_link = link;
        s->stats.leaves++;
        s->stats.keys += (uint32_t)count;
        return DB_OK;
    }

    s->stats.internals++;
```

内部节点这一支走一个 `i <= count` 的循环，第 i 个孩子的键范围是 `[child_low, child_high)`：下界取第 i − 1 个分隔键，上界取第 i 个分隔键；第一孩子的下界和最右孩子的上界沿用父节点传下来的 `low`、`high`。每个孩子都重新 `pager_get` 取一次本页再读孩子页号，递归期间不钉住本页。

`low`、`high` 用 `uint64_t` 传递，因为根的上界是 `UINT32_MAX + 1`，32 位放不下；`high` 是开区间上界，与 `child_slot` 的「等于分隔键走右边」一致。检查完叶子后，`leaf_level` 记下第一个叶子的层，后续叶子必须同层，这保证了树是平衡的。

递归里不钉住本页，每次取孩子时重新 `pager_get`。这看起来低效，实际上命中的是缓存；好处是 `btree_check` 对一个三层、几百页的树也只需要几个页框。`test_btree` 的 `test_tiny_cache` 用 4 个页框验证了这一点。

结尾三条检查：

```c
    db_status rc = check_node(&s, BTREE_ROOT, 0, 0, (uint64_t)UINT32_MAX + 1);
    if (rc == DB_OK && s.last_link != 0) {
        rc = corrupt(&s, s.last_leaf, "last leaf points to another leaf");
    }
    if (rc == DB_OK && s.visited != pages - 1) {
        /* 除文件头外每一页都属于这棵树：MdrDB 从不释放页。 */
        snprintf(message, message_size,
                 "%" PRIu32 " pages are not part of the tree",
                 pages - 1 - s.visited);
        rc = DB_CORRUPT;
    }
```

中序访问的最后一个叶子，`link` 必须是 0，否则叶子链比树还长。`visited != pages - 1` 检查没有孤儿页，这条只在「从不释放页」的前提下成立；11.2 的合并习题要加空闲页链表，就必须把它改成「每一页要么属于树，要么在空闲链表里」。

`.check` 的输出：

::: terminal title="bash - .check"

```text
mdrdb> .check
ok: rows 300, leaf pages 5, internal pages 1, height 2
```

:::

`db_check` 在 `btree_check` 之后还会再遍历一遍，逐行 `record_decode`，确保每一行都能解出来。结构对但记录坏的情况也能报出来，消息形如 `row 7: record cannot be decoded`。

### 10.1 分隔键加 1

把 `split_node` 里的分隔键改成右半第一个键加 1：


用这个版本插入 20 行长记录，执行 `.check`：

分隔键 9 把右叶划成「大于等于 9」，但右叶里还有键 8。查找 8 时会走左叶，而 8 不在左叶，返回值是「不存在」。`test_btree` 跑起来有 1770 处检查失败：

```text

  btree_check: page 536: key outside the range given by the parent
  ...
FAIL test_root_grows
FAIL test_ascending_and_descending
```

中间省掉了九百多条 `check failed`，页号有 3、84、536、992 等等。

这一条错误信息就定位到了页号和原因，不用逐步调试。

### 10.2 删除时漏掉指针修正

去掉 `node_remove_cell` 里的那个修正循环：

```c
    for (int k = 0; k < count - 1; k++) {
        size_t p = pointer_at(node, k);
        if (p < offset) {
            put_u16(pointer_slot(node, k), (uint16_t)(p + size));
        }
    }
```

内容整体后移了，但指针还是旧值，指向已经挪走的位置。`test_node` 的 `test_remove_compacts_content` 立刻失败，随后程序崩溃：

::: terminal title="bash - test_node 的输出"

```text
tests/test_node.c:75: check failed: node_key(node, 0) == 10 && node_key(node, 1) == 30
tests/test_node.c:76: check failed: payload_is(node, 0, "aaaa") && payload_is(node, 1, "cccccc")
tests/test_node.c:79: check failed: node_validate(node)
```

:::

三次检查失败之后进程收到 SIGSEGV 终止，shell 在命令行上打出 `Segmentation fault`，退出码 139。

原因是一次删除之后，后面的 `node_remove_cell` 拿到的偏移已经无效，`memmove` 的长度算成了一个很大的数。这也说明 `node_validate` 只能拦住布局层面的错误，指针本身指向错地方时它未必当场报错，得等到下一次操作才以崩溃的形式暴露。

### 10.3 漏掉 `pager_write`

在 `insert_if_room` 里把 `pager_write` 去掉，直接改页：

```c
    if (node_has_room(pg->data, size)) {
        node_insert_cell(pg->data, index, cell, size);
        *done = true;
    }
```

两次自动提交的插入，同一个进程里读得到，重新打开就没了：

::: terminal title="bash - 漏掉 pager_write"

```text
mdrdb> insert 1 alice alice@example.com
ok
mdrdb> insert 2 bob bob@example.com
ok
mdrdb> select
(1, alice, alice@example.com)
(2, bob, bob@example.com)
(2 rows)
mdrdb>
```

:::

::: terminal title="bash - 重新打开"

```text
mdrdb> select
(0 rows)
mdrdb>
```

:::

第一次进程里读得到，因为读的正是被改过的缓存；页没有被标脏，提交时不会写回文件，重新打开就是空的。`test_btree` 在这种改动下也会大面积失败（6357 处），因为每一轮 `pager_begin` 和 `pager_commit` 之间没标脏的修改都消失了。这个例子值得记住：「读得到」不等于「写下去了」。

### 10.4 去掉 `payloads_fit`

复核时发现的那个真实缺陷：删掉 `load_node` 里的 `payloads_fit` 检查，构造一个布局自洽、但有一个 3074 字节负载的叶子，再插入一行触发分裂。`fill_node` 里的断言立刻中止：

::: terminal title="bash - 去掉负载长度检查"

```text
Assertion failed: node_has_room(node, list->size[i]), file src/btree.c, line 228
```

:::

断言在调试构建里中止进程，这正是它的用途。如果构建时定义了 `NDEBUG`（断言被去掉），`node_insert_cell` 会算出负的内容区起点，写到页外。复核记录里的 UBSan 报告是 `pager.c:299:15: runtime error: load of value 120, which is not a valid value for type '_Bool'`，插入还返回了 `ok`。

所以 `payloads_fit` 不是防御性编程，而是补上一条 `node_validate` 无法检查的前提：布局自洽不等于负载长度合法。`btree_check` 也相应增加了 `payload is too long` 这条消息，`test_btree` 的 `test_rejects_oversized_payload` 在修复后才通过。
