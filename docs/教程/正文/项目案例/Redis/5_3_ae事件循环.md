# 5.3 源码阅读：Redis ae 事件循环

在许多复杂的网络服务架构中，事件驱动库往往伴随着繁复的线程池封装、平台抽象适配与深层回调队列。然而 Redis 自带的事件循环库 ae（A simple event-driven library）却走向了极致的精简主义：其核心驱动代码仅有约 500 行 C 语言实现，即便加上 Linux epoll、macOS kqueue 等底层多路复用适配层，整体规模也不过 700 行上下。正是这套结构极简、完全摒弃过度设计的单线程事件引擎，支撑起了整个 Redis 服务器每秒数十万次的高吞吐网络 I/O 与毫秒级定时任务调度。

> 本节研读基于 Redis 稳定版本的 `src/ae.h`、`src/ae.c` 与 `src/ae_epoll.c` 等文件。软件许可证提供 RSALv2 / SSPLv1 / AGPLv3 供选择。

## 1. 核心数据结构

ae 库将整个事件循环运行时的生命周期状态收敛在一个紧凑的 `aeEventLoop` 结构体中：

```c
typedef struct aeEventLoop {
    int maxfd;                   /* 当前注册的最大文件描述符 */
    int setsize;                 /* 能跟踪的 fd 上限 */
    long long timeEventNextId;   /* 下一个时间事件的 ID */
    int nevents;                 /* events 与 fired 数组当前的长度 */
    aeFileEvent *events;         /* 按 fd 索引的文件事件数组 */
    aeFiredEvent *fired;         /* 本轮 poll 返回的就绪事件 */
    aeTimeEvent *timeEventHead;  /* 时间事件链表头 */
    int stop;                    /* 非零则退出主循环 */
    void *apidata;               /* 平台 I/O 多路复用的私有数据 */
    aeBeforeSleepProc *beforesleep;
    aeBeforeSleepProc *aftersleep;
    int flags;
    void *privdata[3];
} aeEventLoop;
```

该结构体在逻辑上统一调度两类不同维度的驱动信号：文件事件与时间事件。

::: concept ae-file-event title="文件事件：fd + mask + 回调"

文件事件用 `aeFileEvent` 表示，每个文件描述符对应数组中的一个槽位：

```c
typedef struct aeFileEvent {
    int mask;              /* AE_READABLE | AE_WRITABLE | AE_BARRIER */
    aeFileProc *rfileProc; /* 可读时的回调 */
    aeFileProc *wfileProc; /* 可写时的回调 */
    void *clientData;      /* 传给回调的用户数据 */
} aeFileEvent;
```

在设计上，`events` 数组直接采用文件描述符 fd 作为下标进行直接寻址，`events[fd]` 即可精确定位该套接字所绑定的事件信息。这种以空间换时间的设计完全省去了哈希散列计算或树形检索的开销，确保了每次事件查询均拥有极为稳定的 O(1) 性能。其折中代价在于预分配数组的大小严格受限于 `setsize`（在 Redis 中通常预设为 `maxclients + 128`）。

:::

::: concept ae-time-event title="时间事件：链表 + 单调时钟"

时间事件用双向链表串联，每个节点记录触发时刻和回调：

```c
typedef struct aeTimeEvent {
    long long id;
    monotime when;                  /* 触发时刻（微秒级单调时钟） */
    aeTimeProc *timeProc;           /* 回调函数 */
    aeEventFinalizerProc *finalizerProc;
    void *clientData;
    struct aeTimeEvent *prev;
    struct aeTimeEvent *next;
    int refcount;                   /* 防止递归调用时提前释放 */
} aeTimeEvent;
```

与海量的套接字文件事件不同，Redis 服务端在生命周期中常驻的时间事件极少（在绝大部分生产场景下仅有 `serverCron` 这一个全局时钟心跳），因此基于双向链表的 O(N) 线性遍历开销几乎可以忽略不计。源码注释中也探讨过引入跳表或最小堆进行有序优化的可能性，但同时明确指出基于 Redis 自身的实际运行负荷，极简的双向链表已是工程性价比最高且易于维护的选择。

:::

::: generate ae-data-structures-overview kind=explanation concepts=ae-file-event,ae-time-event

面向有一定 C 基础的读者，解释 ae 为什么用"数组按 fd 索引"的方式存放文件事件：fd 本身就是连续小整数，可以直接当下标，换成哈希表反而多一次计算。时间事件用无序链表也是同样的考虑：Redis 的时间事件数量极少，通常只有 serverCron 一个，最小堆的维护成本换不来收益。点明这是"按实际负载选数据结构"的典型例子。

:::

## 2. 主循环：aeMain 与 aeProcessEvents

驱动 Redis 运行的核心引擎在最外层呈现为一个结构极其精悍的顶层循环：

```c
void aeMain(aeEventLoop *eventLoop) {
    eventLoop->stop = 0;
    while (!eventLoop->stop) {
        aeProcessEvents(eventLoop, AE_ALL_EVENTS|
                                   AE_CALL_BEFORE_SLEEP|
                                   AE_CALL_AFTER_SLEEP);
    }
}
```

整个事件调度的核心控制逻辑均被收敛在 `aeProcessEvents` 函数内。在循环的单次迭代中，系统依次推进四个阶段的动作：

::: concept ae-process-events title="aeProcessEvents 的四步流程"

1. **调用 beforesleep 钩子**：Redis 在这里向客户端写出待发送的回复、刷写 AOF 缓冲区等。
2. **计算 poll 超时**：遍历时间事件链表，找到最近一个定时器的剩余时间，作为 `aeApiPoll` 的超时参数。没有定时器则无限等待；设了 `AE_DONT_WAIT` 则超时为 0（立即返回）。
3. **调用 aeApiPoll 阻塞等待**：底层调用 `epoll_wait` / `kevent` / `select`，返回就绪的文件描述符。
4. **分发事件**：先遍历就绪的文件事件并调用回调，再处理到期的时间事件。

:::

超时计算的核心是 `usUntilEarliestTimer`：

```c
static int64_t usUntilEarliestTimer(aeEventLoop *eventLoop) {
    aeTimeEvent *te = eventLoop->timeEventHead;
    if (te == NULL) return -1;

    aeTimeEvent *earliest = NULL;
    while (te) {
        if ((!earliest || te->when < earliest->when) && te->id != AE_DELETED_EVENT_ID)
            earliest = te;
        te = te->next;
    }
    if (earliest == NULL) return -1;

    monotime now = getMonotonicUs();
    return (now >= earliest->when) ? 0 : earliest->when - now;
}
```

在计算等待时间跨度时，系统底层严格采用单调时钟（`getMonotonicUs`）而非容易受外部干扰的日历时钟（如 `gettimeofday`）。日历时钟在发生管理员手动校时或 NTP 时间步进同步时会出现向前跳变或回拨，极易导致定时器陷入长时间睡眠或瞬间被大量错误触发；而单调时钟从操作系统引导起线性递增，为定时事件提供了坚实的时间基准保证。

::: generate ae-timeout-calculation kind=example concepts=ae-process-events

面向读者，用一个具体的场景走一遍 aeProcessEvents 的超时计算过程：假设当前有两个时间事件，分别在 50ms 和 200ms 后触发，同时有若干文件事件在监听。描述 aeProcessEvents 如何选择 50ms 作为 poll 超时，epoll_wait 如何在这 50ms 内既能被文件事件唤醒、又能在超时后让时间事件得到处理。

:::

## 3. 文件事件的注册与分发

### 3.1 注册

当网络层需要对特定套接字开启数据监听时，统一调用 `aeCreateFileEvent` 完成读写事件与回调函数的挂载：

```c
int aeCreateFileEvent(aeEventLoop *eventLoop, int fd, int mask,
        aeFileProc *proc, void *clientData)
{
    if (fd >= eventLoop->setsize) {
        errno = ERANGE;
        return AE_ERR;
    }

    aeFileEvent *fe = &eventLoop->events[fd];

    if (aeApiAddEvent(eventLoop, fd, mask) == -1)
        return AE_ERR;
    fe->mask |= mask;
    if (mask & AE_READABLE) fe->rfileProc = proc;
    if (mask & AE_WRITABLE) fe->wfileProc = proc;
    fe->clientData = clientData;
    if (fd > eventLoop->maxfd)
        eventLoop->maxfd = fd;
    return AE_OK;
}
```

值得注意的代码细节是：`fe->mask |= mask` 采用按位或运算来累加监听掩码，这意味着单个文件描述符可以同时独立注册可读与可写事件，并各自挂接不同的回调逻辑。辅助函数 `aeApiAddEvent` 会自动感知该描述符当前的登记状态：对于初次加入的描述符触发 `epoll_ctl(EPOLL_CTL_ADD)`，而对于已在监听集合中仅做事件变更的描述符则平滑转为 `epoll_ctl(EPOLL_CTL_MOD)`。

### 3.2 分发与 AE_BARRIER

文件事件的分发集中在 `aeProcessEvents` 的核心循环中。当底层多路复用系统调用（如 `epoll_wait`）返回就绪的文件描述符后，循环逐一取出已触发的事件并派发给注册的回调：

```c
for (j = 0; j < numevents; j++) {
    int fd = eventLoop->fired[j].fd;
    aeFileEvent *fe = &eventLoop->events[fd];
    int mask = eventLoop->fired[j].mask;
    int fired = 0; /* 当前 fd 已触发的回调数 */

    int invert = fe->mask & AE_BARRIER;

    /* 正常顺序：先读后写 */
    if (!invert && fe->mask & mask & AE_READABLE) {
        fe->rfileProc(eventLoop, fd, fe->clientData, mask);
        fired++;
        fe = &eventLoop->events[fd]; /* 数组可能已扩容，重新取 */
    }

    if (fe->mask & mask & AE_WRITABLE) {
        if (!fired || fe->wfileProc != fe->rfileProc) {
            fe->wfileProc(eventLoop, fd, fe->clientData, mask);
            fired++;
        }
    }

    /* AE_BARRIER：先写后读 */
    if (invert) {
        fe = &eventLoop->events[fd]; /* 数组可能已扩容，重新取 */
        if ((fe->mask & mask & AE_READABLE) &&
            (!fired || fe->wfileProc != fe->rfileProc))
        {
            fe->rfileProc(eventLoop, fd, fe->clientData, mask);
            fired++;
        }
    }

    processed++;
}
```

在常规的网络服务模型下，事件分发默认遵循“先读后写”的顺序。服务端首先读取套接字缓冲区中客户端送来的请求命令，在内存中执行完毕并将生成的响应载入写缓冲区；紧接着若套接字具备写就绪条件，就可以在同一个循环周期内顺道将响应数据写回网络，从而省去等待下一次轮询的延迟。

然而在需要保证落盘持久化的严苛场景下，这一顺序需要反转。比如某些模块或事务处理要求先通过写回调把应答数据或同步日志 `fsync` 到磁盘，确认持久化成功后，才允许继续读取该连接后续排队的新命令。标志位 `AE_BARRIER` 正是为此而设：当掩码中设置了 `AE_BARRIER`，`invert` 标志为真，主循环便会打破默认顺序，转为“先写后读”，阻断未落盘前读取后续命令的可能性。

这段分发逻辑里还有两处耐人寻味的实现细节：

一是在调用回调函数之后，代码立即执行了 `fe = &eventLoop->events[fd]` 重新获取指针。这是因为回调函数内部可能调用了 `aeResizeSetSize` 等管理接口，导致事件表数组发生了内存重分配（`zrealloc`）；此时旧的指针可能已经悬空，重新寻址能够确保后续操作基于最新的有效内存地址。

二是 `fe->wfileProc != fe->rfileProc` 这重判断条件。在某些特定抽象下，读回调与写回调可能被注册为同一个函数入口。增加这一校验并配合 `fired` 计数器，能够保证在同一个就绪轮次中，同一个函数不会因同一次就绪状态被无意调用两次。

## 4. 时间事件的管理

### 4.1 创建

```c
long long aeCreateTimeEvent(aeEventLoop *eventLoop, long long milliseconds,
        aeTimeProc *proc, void *clientData,
        aeEventFinalizerProc *finalizerProc)
{
    long long id = eventLoop->timeEventNextId++;
    aeTimeEvent *te = zmalloc(sizeof(*te));

    te->id = id;
    te->when = getMonotonicUs() + milliseconds * 1000;
    te->timeProc = proc;
    te->finalizerProc = finalizerProc;
    te->clientData = clientData;
    te->prev = NULL;
    te->next = eventLoop->timeEventHead;
    te->refcount = 0;
    if (te->next)
        te->next->prev = te;
    eventLoop->timeEventHead = te;
    return id;
}
```

新事件插入链表头部，时间复杂度为 $O(1)$。这里调用方传入的 `milliseconds` 是相对时间差（即“从当前起算多少毫秒后触发”），函数内部通过单调时钟读取当前绝对时刻并完成换算，将其存储为微秒精度的绝对时间戳。

### 4.2 处理与重调度

`processTimeEvents` 遍历时间事件链表，逐个检查并执行所有到期的事件：

```c
if (te->when <= now) {
    int retval;

    id = te->id;
    te->refcount++;
    retval = te->timeProc(eventLoop, id, te->clientData);
    te->refcount--;
    processed++;
    now = getMonotonicUs();                         /* 回调可能耗时，刷新当前时间 */
    if (retval != AE_NOMORE) {
        te->when = now + (monotime)retval * 1000;   /* 重调度 */
    } else {
        te->id = AE_DELETED_EVENT_ID;               /* 标记删除 */
    }
}
```

定时器回调函数的返回值直接决定了该事件后续的调度行为：若返回一个正整数，代表这是一个周期性任务，数值即下一次触发与当前时刻的时间间隔（毫秒），主循环据此直接更新 `te->when`；若返回 `AE_NOMORE`（即 -1），则表明这是一次性任务，执行完毕后即可结束生命周期。Redis 的核心守护任务 `serverCron` 每次返回 `1000/server.hz`，在默认配置（`hz = 10`）下维持着每秒 10 次的稳定调度节拍。

删除操作则采用了惰性清理策略。主动注销或者一次性事件执行完毕时，事件对象的 `id` 首先被标记为 `AE_DELETED_EVENT_ID`。只有在主循环安全遍历且节点引用计数 `refcount` 归零时，链表才会将其真正脱链并释放内存。这种机制有效规避了在回调执行期间修改链表拓扑导致的悬空指针与迭代器失效。

## 5. 平台抽象层

I/O 多路复用的平台适配完全在编译期敲定。在 `ae.c` 源码顶部，预处理器通过条件编译指令检测当前系统的系统调用支持，从高到低挑选性能最优的底层后端：

```c
#ifdef HAVE_EVPORT
#include "ae_evport.c"
#else
    #ifdef HAVE_EPOLL
    #include "ae_epoll.c"
    #else
        #ifdef HAVE_KQUEUE
        #include "ae_kqueue.c"
        #else
        #include "ae_select.c"
        #endif
    #endif
#endif
```

各个实现文件的选型优先级由高到低依次为：Solaris 的 evport、Linux 的 epoll、macOS 与 BSD 系列的 kqueue，最后以 POSIX 标准普遍支持的 select 作为全平台兜底。每一个平台适配文件都遵循约定，分别实现一组签名完全一致的内部静态函数：

| 函数 | 职责 |
|:---|:---|
| `aeApiCreate` | 初始化底层数据结构（如 `epoll_create`） |
| `aeApiResize` | 调整容量 |
| `aeApiFree` | 释放资源 |
| `aeApiAddEvent` | 注册 fd 监听（如 `epoll_ctl`） |
| `aeApiDelEvent` | 取消监听 |
| `aeApiPoll` | 阻塞等待事件（如 `epoll_wait`） |
| `aeApiName` | 返回名字（`"epoll"`、`"kqueue"` 等） |

::: concept ae-platform-abstraction title="用 #include .c 实现编译期多态"

ae 在架构上没有借助虚函数指针表（vtable）或策略结构体来完成运行时多态分发，而是直接利用预处理器 `#include` 对应的 `.c` 源码文件。被包含的代码直接融入 `ae.c`，使得所有平台相关的 `static` 函数与事件循环主逻辑共处同一个编译翻译单元。这一设计带来了三项直接优势：

- 零间接寻址开销：所有底层调用均为直接调用，现代编译器能够直接进行跨函数内联优化，消除了虚表跳转的寻址延迟。
- 约定优于配置：无需定义繁杂的抽象基类或结构体接口，仅依赖同名函数的隐式签名约定即可完成平台替换。
- 目标体积精简：产出的可执行文件仅包含目标系统所需的那一种系统调用逻辑，绝不打包无关平台的冗余代码。

:::

以 Linux 下的 epoll 实现为例，`aeApiPoll` 的内部处理非常直观：

```c
static int aeApiPoll(aeEventLoop *eventLoop, struct timeval *tvp) {
    aeApiState *state = eventLoop->apidata;
    int retval, numevents = 0;

    retval = epoll_wait(state->epfd, state->events, eventLoop->setsize,
            tvp ? (tvp->tv_sec*1000 + (tvp->tv_usec + 999)/1000) : -1);
    if (retval > 0) {
        numevents = retval;
        for (int j = 0; j < numevents; j++) {
            int mask = 0;
            struct epoll_event *e = state->events + j;

            if (e->events & EPOLLIN) mask |= AE_READABLE;
            if (e->events & EPOLLOUT) mask |= AE_WRITABLE;
            if (e->events & EPOLLERR) mask |= AE_WRITABLE|AE_READABLE;
            if (e->events & EPOLLHUP) mask |= AE_WRITABLE|AE_READABLE;
            eventLoop->fired[j].fd = e->data.fd;
            eventLoop->fired[j].mask = mask;
        }
    }
    return numevents;
}
```

该函数的核心职责是将内核返回的 `EPOLLIN` 与 `EPOLLOUT` 事件，无损转换为 ae 统一的 `AE_READABLE` 与 `AE_WRITABLE` 掩码，并整齐地排入 `eventLoop->fired` 数组供上层分发。

值得留意的细节是错误处理：内核派发的 `EPOLLERR` 与 `EPOLLHUP`（连接挂断）被同时映射为读与写双重就绪。这样一来，无论上层在当前文件描述符上仅注册了读回调还是仅注册了写回调，都能够立刻被唤醒并感知到异常状态，进而执行套接字关闭与清理流程，避免连接在错误状态下无声挂死。

::: generate ae-multiplexing-apis kind=comparison concepts=ae-platform-abstraction

面向有一定系统编程基础的读者，对比 epoll (Linux)、kqueue (macOS/BSD)、select (POSIX) 三种 I/O 多路复用机制的核心区别：接口形态（epoll 分 create/ctl/wait 三步，kqueue 用 changelist 批量操作，select 用 fd_set 位图）、性能特征（epoll/kqueue 是 O(就绪数)，select 每次都要遍历全部监听的 fd，还受 `FD_SETSIZE` 限制）、适用场景。说明为什么 ae 选择按这个优先级排列它们。

:::

## 6. beforesleep / aftersleep 钩子

```c
void aeSetBeforeSleepProc(aeEventLoop *eventLoop, aeBeforeSleepProc *beforesleep) {
    eventLoop->beforesleep = beforesleep;
}

void aeSetAfterSleepProc(aeEventLoop *eventLoop, aeBeforeSleepProc *aftersleep) {
    eventLoop->aftersleep = aftersleep;
}
```

在 `aeProcessEvents` 的主执行流中，`beforesleep` 安排在调用 `aeApiPoll` 阻塞等待之前执行，而 `aftersleep` 则挂接在底层轮询返回之后立即触发。

这两个生命周期钩子是 Redis 单线程吞吐与低延迟设计的关键枢纽。在调用多路复用系统调用沉睡之前，系统通过 `beforesleep` 集中处理大量缓冲逻辑：主动遍历客户端就绪列表，将待发送的数据批量推入网络套接字（避免每次写入都陷入一次系统调用）；将 AOF 缓冲区的数据集中刷入磁盘；处理被阻塞键唤醒的客户端请求；同步集群内部的心跳信息等。而在系统调用醒来后，`aftersleep` 能够第一时间刷新当前的系统时间缓存与模块延迟统计，让后续的事件分发逻辑获得精度最高的运行环境。

## 7. Redis 网络层如何接入 ae

ae 自身仅提供抽象的文件描述符分发与时间事件轮询，并不直接承载任何网络协议解析与套接字管理细节。Redis 巧妙地将整套网络状态机架设在 ae 暴露的文件事件之上：

::: generate ae-redis-networking kind=example concepts=ae-file-event,ae-process-events

面向读者，描述一个客户端请求在 Redis 中从建立连接到收到回复的完整流程：Redis 启动时用 aeCreateFileEvent 把监听 socket 注册为可读事件，回调是 connSocketAcceptHandler；客户端连接到达时 connSocketAcceptHandler 被调用，它 accept 新连接、创建客户端，并通过 connSetReadHandler 为新连接注册可读事件，最终由 readQueryFromClient 处理；客户端发送命令时 readQueryFromClient 被调用，解析并执行命令，把回复写入输出缓冲区；beforesleep 中先直接尝试写出回复，写不完时才注册可写事件，回调是 sendReplyToClient；可写事件触发时剩余的回复被发送给客户端。整个过程都在单线程的 aeMain 循环中完成。

:::

## 8. 与通用事件库的对比

ae 的一切权衡都完全围绕 Redis 自身的特质展开：文件事件直接采用以描述符数值为下标的紧凑数组，时间事件仅维护简单的无序单链表，底层系统调用多路复用在编译期通过宏替换一锤定音。它没有附带异步 DNS 解析、跨平台工作线程池或异步文件系统 I/O 等重量级组件，而是将事件引擎的体量压缩到了千行以内。

::: generate ae-vs-libuv kind=comparison concepts=ae-process-events,ae-platform-abstraction

面向读者，简要对比 ae 与 libuv/libev 在设计哲学上的差异：ae 是 Redis 专用的、极简的、单线程的事件循环，不处理 DNS、线程池、文件系统操作等；libuv 是通用的跨平台异步 I/O 库，支持线程池、异步文件 I/O、信号处理等，但复杂度和代码量高出一个数量级。说明"专用 vs 通用"是两个库设计目标的差异，没有好坏之分。

:::
