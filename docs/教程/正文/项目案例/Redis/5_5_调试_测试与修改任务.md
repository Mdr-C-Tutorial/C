# 5.5 Redis：调试、测试与修改任务

[5.1](/教程/正文/项目案例/Redis/5_1_架构与请求生命周期) 到 [5.4](/教程/正文/项目案例/Redis/5_4_跳表) 读的是源码：请求从 `accept` 走到 `call`，SDS、dict、ae、跳表各自长什么样。这一页换一个方向，把同一棵 8.10.2 的源码树按用途编出来，跑它自带的 C 单元测试，读懂 Tcl 集成测试的组织，用服务器自己的诊断命令和崩溃报告回答「现在发生了什么」，最后做两件事：往核心里加一条写命令，再用模块 API 在不改核心的前提下加一条只读命令。

读完这一页，应当能按用途切换构建方式并清理干净；能跑 `redis-server test` 的单项测试，知道输出里的 `0 passed, 0 failed` 是什么意思；能说出 `tests/` 下 Tcl 用例的组织方式；能用 `INFO`、`CLIENT LIST`、`SLOWLOG`、`LATENCY`、`MONITOR` 和 `DEBUG` 的几个子命令查出运行中的实例在忙什么；能从崩溃报告和 ASan 输出里读出源码行；能按「JSON 描述 → 生成 `commands.def` → 实现函数 → 测试」的步骤加一条命令，并且知道写命令必须承担的三项义务。

读之前应当已经读过 [5.1](/教程/正文/项目案例/Redis/5_1_架构与请求生命周期)、[5.2](/教程/正文/项目案例/Redis/5_2_SDS与dict)、[5.3](/教程/正文/项目案例/Redis/5_3_ae事件循环) 和 [5.4](/教程/正文/项目案例/Redis/5_4_跳表)。测试的组织方式见[自动化测试](/教程/正文/开发与工程基础/11_自动化测试)，调试器见[调试器](/教程/正文/开发与工程基础/12_调试器)，sanitizer 与编译选项见[编译器诊断与程序检查](/教程/正文/开发与工程基础/13_编译器诊断与程序检查)，动态库与第三方依赖见[库与第三方依赖](/教程/正文/开发与工程基础/10_库与第三方依赖)。

所有实验在一台 Debian 13 机器上完成，gcc 14.2，Redis 固定为 8.10.2。实例只绑 `127.0.0.1`，端口用 27300 段，实验结束按启动时记下的 PID 关掉。配套文件在 `code/项目/Redis/` 下：`patches/` 里有 `setmax.json`、`setmax.patch` 和打补丁的 `apply_setmax.py`，`tests/setmax_test.sh` 是期望输出测试，`modules/` 下是 `mdrsum.c`、`mdrsetmax.c` 和 `mdrsetmax_norepl.c`。

## 1. 按用途构建

同一份源码要满足几种互相矛盾的用途：日常运行要 `-O3` 和链接时优化，调试要栈帧不被内联掉，查越界要 ASan，跑单元测试还得把测试代码编进去。`src/Makefile` 把这些做成几个可以在命令行上覆盖的参数，代价是切换时必须清理干净，否则改动悄悄不生效。

### 1.1 默认构建与选项的来源

优化级别的默认值写在 `src/Makefile:27`（8.10.2）：`OPTIMIZATION?=-O3`。当它等于 `-O3` 时，Makefile 追加 `-flto=auto -ffat-lto-objects`；当它不是 `-O0` 时，追加 `-fno-omit-frame-pointer`。调试信息来自 `DEBUG=-g -ggdb`（`src/Makefile:172`）。Linux 上的链接参数还有 `-rdynamic`（`src/Makefile:258`），它让动态符号表保留函数名，软件看门狗和崩溃报告打出来的调用栈才有名字可显示，否则只有一串地址。

redis.io 的调试文档说默认优化是 `-O2`，那是旧版本的说法。8.10.2 以 Makefile 为准，实际选项可以从 `src/.make-settings` 和调试信息里核对。

只编核心用 `build redis`。8.10 的顶层 `Makefile` 已经是调度脚本，直接 `make` 会连 `modules/` 下的 RedisBloom、RediSearch、RedisJSON、RedisTimeSeries 一起编，那一步要 CMake、LLVM 和 Rust；`build redis` 只进 `src/`，适合只读核心代码的场合。

### 1.3 分配器与 sanitizer

分配器由 `MALLOC` 控制，默认走 `deps/jemalloc`，`MALLOC=libc` 换成 C 库的 `malloc`。`SANITIZER=address` 会自动把分配器改成 libc（`src/Makefile:110` 起），因为 jemalloc 自己管理内存，ASan 看不到它分配和释放的块。ASan 构建在另一棵新解包的树上做：

::: terminal title="zsh - ASan 构建"

```console
$ nice -n 19 make -j2 build redis SANITIZER=address REDIS_CFLAGS="-DREDIS_TEST"
...
$ ./src/redis-server --version
Redis server v=8.10.2 sha=00000000:1 malloc=libc bits=64 build=196b29c6357bbcc9
$ grep -E '^(OPT|MALLOC|REDIS_CFLAGS)=' src/.make-settings
OPT=-O3 -flto=auto -ffat-lto-objects -fno-omit-frame-pointer
MALLOC=libc
REDIS_CFLAGS=-DREDIS_TEST
```

:::

176 秒，产物 31 406 544 字节，接近默认版的一倍半。优化级别仍是 `-O3`，`CFLAGS` 里多了 `-fsanitize=address -fno-sanitize-recover=all -fno-omit-frame-pointer`；`-fno-sanitize-recover=all` 让第一次出错就直接中止，而不是打印后继续。

各配置放在一起：

| 用途 | 命令 | 实测用时 | 产物字节 | 版本串里的分配器 |
| --- | --- | --- | --- | --- |
| 默认 | `make -j2 build redis` | 189 s | 21 931 056 | `jemalloc-5.3.0` |
| 跑单元测试 | `make -j2 build redis REDIS_CFLAGS="-DREDIS_TEST"` | 197 s | 23 171 016 | `jemalloc-5.3.0` |
| 断点调试 | `make distclean` 后 `make -j2 noopt REDIS_CFLAGS="-DREDIS_TEST"` | 73 s | 13 744 472 | `jemalloc-5.3.0` |
| libc 分配器 | `make distclean` 后 `make -j2 build redis MALLOC=libc` | 96 s | 16 157 568 | `libc` |
| ASan | 新解包后 `make -j2 build redis SANITIZER=address REDIS_CFLAGS="-DREDIS_TEST"` | 176 s | 31 406 544 | `libc` |

表里的命令都加了 `nice -n 19`，`-j2` 是这台机器的实测配置。用 `-O0` 版调试还有一层原因：默认的 `-O3` 加 LTO 会把 `processCommandAndResetClient` 这样的函数内联进调用者，看门狗和崩溃报告里的栈就少几帧，5.1 第 6.7 节已经遇到过这件事。

### 1.4 把单元测试编进二进制

Redis 的 C 单元测试不是独立的可执行文件，而是编进 `redis-server` 的一批函数，由 `test` 子命令调用。入口在 `main` 里，包在 `#ifdef REDIS_TEST` 中（`src/server.c:7996` 起）。没有定义这个宏时，`test` 就是一个普通参数，被当成配置文件路径：

::: terminal title="zsh - 未编入测试"

```console
$ ./src/redis-server test sds
1351519:C 21 Oct 2026 22:23:40.837 # Fatal error, can't open config file '.../redis-8.10.2/src/test': No such file or directory
```

:::

`server.c` 把 `test` 当成启动时读取的配置文件，找不到就退出。加上 `REDIS_CFLAGS="-DREDIS_TEST"` 重新构建，同一个命令才有意义。`REDIS_CFLAGS` 会追加到最终编译参数里（`src/Makefile:152`），不需要改任何文件。

### 2.1 测试表

`getTestProcByName`（`src/server.c:8040`）按名字不区分大小写地查表。查到就调用，查不到返回 `NULL`，`main` 直接返回 -1。调用之后统一执行 `test_report()`（`testhelp.h:35`），有失败项就打印警告并以 1 退出，全通过返回 0（`src/server.c:8103`）。

### 2.3 测试怎么写

`sdsTest`（`src/sds.c:1307`）的第一段就看得出全部写法：

```c
int sdsTest(int argc, char **argv, int flags) {
    UNUSED(argc);
    UNUSED(argv);
    UNUSED(flags);

    {
        sds x = sdsnew("foo"), y;

        test_cond("Create a string and obtain the length",
            sdslen(x) == 3 && memcmp(x,"foo\0",4) == 0);

        sdsfree(x);
        x = sdsnewlen("foo",2);
        test_cond("Create a string with specified length",
            sdslen(x) == 2 && memcmp(x,"fo\0",3) == 0);
```

`test_cond` 在 `src/testhelp.h:31`：

```c
#define test_cond(descr,_c) do { \
    __test_num++; printf("%d - %s: ", __test_num, descr); \
    if(_c) printf("\033[32mPASSED\033[0m\n"); else {printf("\033[31mFAILED\033[0m\n"); __failed_tests++;} \
} while(0)
```

两条全局计数 `__failed_tests` 和 `__test_num` 定义在 `server.c` 里，`test_report` 读它们。这个框架只有三十几行，没有夹具、没有 setup/teardown，测试之间共享进程状态。它的适用范围就是数据结构这种纯函数式的模块：建一个结构、做几步操作、用 `test_cond` 断言长度和内容，最后 `test_report()`。连接、协议、过期、事务这些集成层面的东西留给下一节的 Tcl 测试。

### 2.4 改坏之后测试能不能发现

单元测试的价值要看它能不能发现真实的改动。拿 5.2 讲过的 `_sdsMakeRoomFor` 做实验，在副本上改两处：

- 变异 A：删掉贪心预分配，`newlen` 不再翻倍也不再加 1MB；
- 变异 B：去掉 1MB 上限，任何长度都翻倍。

两次都重编并运行 `test sds`，结果是 72 条全部通过（副本树来自 libc 分配器的构建，所以是 72 条而不是 77 条）。现有的测试检查的是字符串内容和长度，没有一条检查扩容后的 `sdsavail`，所以两种错误都发现不了。

补两条直接检查扩容策略的 `test_cond`，插在 `sdsTest` 里已有测试之后：

```c
/* 检查贪心预分配策略本身。 */
{
    sds t = sdsnew("");
    t = sdsMakeRoomFor(t, 100);
    test_cond("sdsMakeRoomFor() doubles small requests",
              sdslen(t) == 0 && sdsavail(t) >= 200);
    t = sdsMakeRoomFor(t, 2 * 1024 * 1024);
    test_cond("sdsMakeRoomFor() adds 1MB for large requests",
              sdsavail(t) >= 2 * 1024 * 1024 &&
              sdsavail(t) < 4 * 1024 * 1024);
    sdsfree(t);
}
```

第一条要求 100 字节的请求至少拿到 200 字节的空闲；第二条要求 2MB 的请求至少多给 2MB，但不能翻倍到 4MB。补上后总数变 74 条，未变异的版本两条都通过；变异 A 下第 49 条失败，变异 B 下第 50 条失败：

::: terminal title="zsh - 补测试之后"

```console
--- 未变异 + 新测试：
49 - sdsMakeRoomFor() doubles small requests: PASSED
50 - sdsMakeRoomFor() adds 1MB for large requests: PASSED
  Tests:       74 passed, 0 failed, 74 total
--- 变异 A + 新测试：
49 - sdsMakeRoomFor() doubles small requests: FAILED
50 - sdsMakeRoomFor() adds 1MB for large requests: PASSED
  Tests:       73 passed, 1 failed, 74 total
--- 变异 B + 新测试：
```

这段实验说明两件事。测试通过不等于实现正确，只说明被检查到的那部分没变；以及，改实现之前先看有没有测试盯着要改的那条性质，没有就先补。补的时候照着 5.2 给出的规则写断言，而不是照着当前实现的数字写，否则测试只会把错误固定成新的基准。

## 3. Tcl 集成测试的组织

C 单元测试只覆盖数据结构。连接、协议、事务、过期、持久化这些要走完整请求路径的行为由 `tests/` 下的 Tcl 测试覆盖，它们启动真实的 `redis-server` 进程，用 Tcl 客户端发命令、读回复、比对期望值。

目录结构：

```text
tests/
├── unit/                  # 按模块划分的用例
│   ├── type/string.tcl
│   ├── type/zset.tcl
│   ├── expire.tcl
│   ├── multi.tcl
│   └── ...
├── integration/           # 启动多个实例，模拟重启与复制
├── cluster/               # 集群
├── sentinel/              # 哨兵
├── modules/               # 模块 API 的测试，源文件是 C
├── helpers/               # Tcl 辅助函数
├── support/               # 测试用的配置模板等
├── assets/                # 数据文件
├── instances.tcl          # 与外部实例、集群打交道的辅助脚本
├── test_helper.tcl        # 测试框架主体
└── README.md              # 标签与运行方式的说明
```

顶层的 `runtest` 是个包装脚本，先找 `tclsh8.5` 到 `tclsh9.0` 中的任意一个，找不到就退出：

::: terminal title="zsh - 没有 tclsh"

```console
$ ./runtest --single unit/type/string
You need tcl 8.5 or newer in order to run the Redis test
```

:::

这台机器没装 Tcl，所以本页只读不跑。CI 里装的是 `tcl8.6 tclx`，`tests/README.md` 列了运行方式：`--single` 只跑一个文件，`--tags` 按标签过滤，`--host` 和 `--port` 针对外部实例，`--external:skip` 之类的标签会自动生效。

一个完整的用例，取自 `tests/unit/type/string.tcl` 开头：

```tcl
start_server {tags {"string"}} {
    test {SET and GET an item} {
        r set x foobar
        r get x
    } {foobar}

    test {SET and GET an empty item} {
        r set x {}
        r get x
    } {}
```

`start_server` 起一个临时实例，`r` 是连到它的客户端句柄；`test` 的第一段是名字，第二段是命令序列，最后一段是期望值。`r get x` 的返回值与 `{foobar}` 比较，相等算通过，不等就把实际值打印出来。整个用例不到十行，起停实例、清库、端口分配都由框架处理。

标签用来分类和过滤。`tests/README.md` 的表里，`needs:debug` 表示用例用到 `DEBUG` 命令，`needs:repl` 表示需要能从服务器 `SYNC`，`external:skip` 表示不能对着一台外部实例跑。用例自己还可以用 `tags {"slow"}` 之类自定的分组名（`string.tcl` 里就有），`runtest --tags -slow` 按名字过滤，取负号表示排除。这个划分和 C 单元测试的分工很清楚：能在进程内调函数验证的放 `test`，必须走网络和事件循环的放 Tcl。

### 4.2 CLIENT LIST 与 client 成员


这一行就是 5.1 第 5.2 节那个 `struct client` 的现场快照，逐项对：

| 字段 | 值 | 对应 `client` 的成员 |
| --- | --- | --- |

### 4.3 SLOWLOG

把阈值设成 0，每条命令都会进慢查询日志：

::: terminal title="zsh - SLOWLOG"

```console
$ ./src/redis-cli -p 27310 --csv SLOWLOG GET 3
10,1792588034,30,"client","list","127.0.0.1:51728","",2
9,1792588034,72,"info","commandstats","127.0.0.1:51722","",2
8,1792588034,4,"incr","n","127.0.0.1:51714","",2
```

:::

每个条目的七个字段依次是：编号、Unix 时间戳、执行耗时（微秒）、命令与参数、客户端地址、客户端名、该命令的参数个数。耗时由 `call()` 在调用 `c->cmd->proc(c)` 前后取单调时钟算出（`src/server.c:4049` 取起点，`:4072` 求差），和 `INFO commandstats` 里的 `usec` 同源，只是后者是累计值。`SLOWLOG LEN` 给出当前条数，默认只保留 128 条（`slowlog-max-len`，`src/config.c:3568`）。

慢查询日志记录的是执行时间，不含排队和网络传输，所以一个客户端被阻塞时，它自己的命令会显得很快，慢的是同一时刻在等的那条。

### 4.4 LATENCY 与 MONITOR

`LATENCY` 记录的是事件级别的卡顿，要先用 `latency-monitor-threshold` 开一个门槛（单位毫秒），只记录超过门槛的事件。用 `DEBUG SLEEP` 制造一次 300 毫秒的阻塞：

::: terminal title="zsh - LATENCY"

```console
$ ./src/redis-cli -p 27310 DEBUG SLEEP 0.3
OK
$ ./src/redis-cli -p 27310 LATENCY LATEST
"command",1792588034,300,300
$ ./src/redis-cli -p 27310 LATENCY DOCTOR | head -6
Dave, I have observed latency spikes in this Redis instance. You don't mind talking about it, do you Dave?

1. command: 1 latency spikes (average 300ms, mean deviation 0ms, period 1.00 sec). Worst all time event 300ms.

I have a few advices for you:
```

:::

`LATENCY LATEST` 每行四项：事件名、最近一次发生的时间戳、最近一次的延迟、历史最大值。事件名 `command` 表示一条普通命令，被标了 `CMD_FAST` 的命令会记成 `fast-command`，两者分开统计，所以一条很慢的 `GET` 不会淹没在大量 `PING` 里。`LATENCY DOCTOR` 把样本翻译成建议，它按事件类型给通用建议，不一定对得上当前场景：上面这段里除了 `command` 事件本身，还附了一段关于透明大页的建议，那与这次 `DEBUG SLEEP` 造成的阻塞无关。`LATENCY RESET` 清空样本。

`MONITOR` 把之后执行的每条命令按收到的参数原样打印：

::: terminal title="zsh - MONITOR"

```console
$ ./src/redis-cli -p 27310 MONITOR
OK
1792588035.712961 [0 127.0.0.1:51800] "set" "mon" "hello"
1792588035.716667 [0 127.0.0.1:51810] "get" "mon"
```

:::

行首是时间戳，方括号里是数据库号和客户端地址，后面是命令与参数。`MONITOR` 会拖慢服务器，只在排查时短时间打开；它也不会显示 `ADMIN` 类命令和 `CMD_SKIP_MONITOR` 的命令。

### 4.5 OBJECT ENCODING 与 MEMORY USAGE

::: terminal title="zsh - 编码与内存"

```console
$ ./src/redis-cli -p 27310 SET n 12345
OK
$ ./src/redis-cli -p 27310 SET s hello

$ ./src/redis-cli -p 27310 OBJECT ENCODING n
```

### 4.6 用 DEBUG 看 5.2 的两个结构

`DEBUG SDSLEN` 打印一个键的键名和值各自的 SDS 长度与空闲空间。连续 `APPEND` 观察预分配：

::: terminal title="zsh - DEBUG SDSLEN"

```console
$ ./src/redis-cli -p 27310 SET foo bar
OK
$ ./src/redis-cli -p 27310 DEBUG SDSLEN foo
key_sds_len:3, key_sds_avail:0, key_zmalloc: 32, val_sds_len:3, val_sds_avail:3, val_zmalloc: 0
$ ./src/redis-cli -p 27310 APPEND foo 0123456789
13
$ ./src/redis-cli -p 27310 DEBUG SDSLEN foo
key_sds_len:3, key_sds_avail:0, key_zmalloc: 24, val_sds_len:13, val_sds_avail:15, val_zmalloc: 32
$ ./src/redis-cli -p 27310 APPEND foo 0123456789
23
$ ./src/redis-cli -p 27310 DEBUG SDSLEN foo
key_sds_len:3, key_sds_avail:0, key_zmalloc: 24, val_sds_len:23, val_sds_avail:5, val_zmalloc: 32
$ ./src/redis-cli -p 27310 APPEND foo 0123456789
33
$ ./src/redis-cli -p 27310 DEBUG SDSLEN foo
key_sds_len:3, key_sds_avail:0, key_zmalloc: 24, val_sds_len:33, val_sds_avail:43, val_zmalloc: 80
```

:::

`val_sds_len:3, val_sds_avail:3` 是 `SET` 之后的状态：`bar` 三字节，`embstr` 把键和值放在同一块内存里，多留了同样大小的空间。第一次 `APPEND` 之后长度 13、空闲 15：值从 `embstr` 变成独立的 `raw` SDS，`_sdsMakeRoomFor` 把 `newlen` 从 13 翻倍到 26，加上头部 3 字节和结尾的 `\0` 共 30 字节，jemalloc 给出 32 字节的块，去掉头部和结尾剩 28，逻辑长度 13，空闲就是 15。也正因为值搬了出去，`key_zmalloc` 从 32 降到 24，`val_zmalloc` 从 0 变成 32。第二次追加后长度 23、空闲 5，原有空闲 15 足够放下 10 字节，不需要重新分配。第三次追加 10 字节超过剩余 5，重新按 33 翻倍到 66，空闲 43。这三次正好演示了 5.2 第 1.4 节的规则，也说明 `sdsavail` 记的是分配器实际给出的块减掉头部、结尾和逻辑长度之后的剩余，不是按公式算出来的那个数。

`DEBUG HTSTATS 0` 打印 0 号库主字典和过期字典的状态：

::: terminal title="zsh - DEBUG HTSTATS"

```console
$ ./src/redis-cli -p 27310 DEBUG HTSTATS 0
[Dictionary HT]
Hash table 0 stats (main hash table):
 table size: 4
 number of elements: 1
Hash table 1 stats (rehashing target):
 table size: 8
 number of elements: 4
[Expires HT]
$ ./src/redis-cli -p 27310 DEBUG POPULATE 1000

$ ./src/redis-cli -p 27310 DEBUG HTSTATS 0
[Dictionary HT]

```

:::

第一次输出时字典正在从 4 个桶扩到 8 个桶，两张表同时存在，旧的 4 桶表上还剩 1 个元素，新的 8 桶表上已经有 4 个，这就是 5.2 讲的渐进式 rehash 中间状态。`DEBUG POPULATE 1000` 写入 1000 个键后只剩一张 1024 桶的表，rehash 已经做完：每次增删查都会顺手搬一个桶（`_dictRehashStep`，`src/dict.c:471`），1000 次操作足够把 4 个桶搬空。

::: concept redis-debug-module-disabled title="DEBUG 与 MODULE 默认禁用"

`enable-debug-command` 和 `enable-module-command` 的默认值都是 `no`，分别在 `src/config.c:3497` 与 `:3498` 注册为 `IMMUTABLE_CONFIG`：只能在启动时用命令行或配置文件打开，运行中 `CONFIG SET` 会失败。取值可以是 `no`、`yes`、`local`，`local` 只允许来自本机回环地址的连接使用。

:::

实测确认了不可运行时修改：

::: terminal title="zsh - 运行中尝试打开"

```console

$ ./src/redis-cli -p 27370 CONFIG SET enable-module-command local

```

:::

因此 `DEBUG` 系列命令都需要在启动参数里带 `--enable-debug-command local`，模块的加载同理，见第 7 节。

## 5. 崩溃报告与内存错误

服务器被信号终止时，Redis 的信号处理函数会先把现场写进日志，再退出。这段输出是定位问题的第一手材料。

::: warning 只对自己启动的实例使用 `DEBUG SEGFAULT`

`DEBUG SEGFAULT` 会让进程立刻收到 `SIGSEGV` 并退出，未落盘的 AOF 数据和内存里的改动全部丢失。只在本地启动的测试实例上用，且启动时不要指向任何有价值的数据目录。

:::

### 5.2 用 ASan 抓住越界与野指针

崩溃报告只告诉你死在哪个地址，不告诉你为什么会访问那个地址。要定位到具体的源码行，用 ASan 构建。下面这个 `setmaxCommand` 的错误版本故意写错一处：把整数编码的值当成 SDS 指针去读长度。

在 `--save ''` 的实例里，`SET counter 10` 之后 `counter` 是 `int` 编码，`robj` 的 `ptr` 存的是数字 10 本身，不是指针。错误版本直接对它调用 `sdslen`：

::: compare left-title="错误：不判断编码就读 SDS" right-title="正确：按对象解码"

```c
long long old = 0;
for (size_t i = 0; i < oldlen; i++) {
    old = old * 10 + (((char *)o->ptr)[i] - '0');

```

---

```c
long long old;
if (getLongLongFromObjectOrReply(c, o, &old, NULL) != C_OK) {
    return;

```

:::

`getLongLongFromObjectOrReply` 会先看编码，`int` 编码直接取值，`embstr`/`raw` 走字符串转换，最后一种情况才碰 `ptr` 指向的字节。错误版本编译通过：强制转换之后 `sdslen` 接受的确实是一个 `char *`，编译器没有理由报错。

## 6. 修改任务一：在核心新增 SETMAX

前面的内容都是观察，这一节动手改核心。目标命令的语义：

```text
SETMAX key value
```

键不存在时写入并返回 1；键存在且是整数、新值更大时写入并返回 1；否则返回 0，不修改。值不是整数或键的类型不是字符串时返回错误。这相当于一个原子的「取较大者」，常见的用法是记录某个指标的历史最大值。

### 6.3 三处改动

参照 `src/commands/incr.json` 写 `src/commands/setmax.json`：`arity` 是 3（命令名加两个参数），标志取 `WRITE`、`DENYOOM`、`FAST`，`function` 写 `setmaxCommand`，键规格是位置 1 开始的单键。下面省略了 `reply_schema`，完整文件在 `code/项目/Redis/patches/setmax.json`：


`WRITE` 把它归入写命令，`DENYOOM` 让它在内存不足时被拒绝（它可能分配新对象），`FAST` 表示执行时间与数据量无关，`LATENCY` 因此把它记进 `fast-command` 事件而不是 `command`。键规格里的 `RW`、`ACCESS`、`UPDATE` 分别表示可读写、会被访问、会被修改，集群的键定位和 ACL 的权限判断都要读它。

第二处是在 `src/t_string.c` 里加实现，放在 `psetexCommand` 之后：

```c
/* SETMAX key value
 *
 * Write `value` only if the key does not exist, or if its current integer
 * value is smaller. Returns 1 when the value is written, 0 otherwise. */
void setmaxCommand(client *c) {
    long long value;
    if (getLongLongFromObjectOrReply(c, c->argv[2], &value, NULL) != C_OK) return;

    dictEntryLink link;
    kvobj *o = lookupKeyWriteWithLink(c->db, c->argv[1], &link);
    if (checkType(c, o, OBJ_STRING)) return;

    if (o != NULL) {
        long long old;
        if (getLongLongFromObjectOrReply(c, o, &old, NULL) != C_OK) return;
        if (value <= old) {
            addReply(c, shared.czero);
            return;
        }
    }

    robj *new = createStringObjectFromLongLongForValue(value);
    if (o != NULL) {
        dbReplaceValueWithLink(c->db, c->argv[1], &new, link);
    } else {
        dbAddByLink(c->db, c->argv[1], &new, &link);
    }

    addReply(c, shared.cone);
    keyModified(c, c->db, c->argv[1], new, 1);
    notifyKeyspaceEvent(NOTIFY_STRING, "setmax", c->argv[1], c->db->id);
    server.dirty++;
}
```

逐段说：

- `getLongLongFromObjectOrReply`（`src/object.c:1241`）解析参数，失败时它自己已经把错误回复写进客户端，直接 `return` 即可。第二个参数是 `argv[2]`，不是 `argv[1]`。
- `lookupKeyWriteWithLink`（`src/db.c:381`）同时返回值和它在字典里的位置，`link` 后面写入时复用，避免再查一次。`checkType`（`src/object.c:897`）在类型不符时回复 `WRONGTYPE` 并返回 1。
- 旧值用同一个函数解析。字符串 `"hello"` 解析失败，命令返回错误而不是把它当 0，这是有意的，与 `INCR` 的行为一致。
- 写入分两种情况：键已存在用 `dbReplaceValueWithLink`（`src/db.c:724`），不存在用 `dbAddByLink`（`src/db.c:461`）。直接改指针绕过了字典的引用计数和过期处理，不要这么做。
- `addReply` 之后的三行是写命令的义务，下一小节展开。

第三处是在 `src/server.h` 加声明，紧挨着 `setnxCommand`：

```c
void commandDocsCommand(client *c);
void setCommand(client *c);
void setnxCommand(client *c);
void setmaxCommand(client *c);
void setexCommand(client *c);
```

`commands.def` 由 `commands.c:12` 的 `#include "commands.def"` 引进同一个翻译单元，生成的代码要能调用 `setmaxCommand`，这个声明不可少。忘了它，编译器会报隐式声明；gcc 14 把 `-Wimplicit-function-declaration` 从警告升成了错误，构建直接失败。

### 6.5 写命令要承担的义务

`setmaxCommand` 末尾那三行不是可选的装饰。去掉它们，命令在 redis-cli 里看起来完全正常，问题在别的路径上才暴露。

三项义务各管一条路径，缺哪一项，哪条路径上就出问题：

| 义务 | 由谁读 | 缺了会怎样 | 怎么验证 |
| --- | --- | --- | --- |
| `server.dirty++` | `call()` 的 `dirty = server.dirty-dirty` | 命令不进 AOF、不传给从库，RDB 也认为没有改动 | 打开 AOF，看增量文件里有没有 `SETMAX` |
| `keyModified(..., 1)` | `touchWatchedKey`、`trackingInvalidateKey` | `WATCH` 不失效、客户端缓存不失效 | 两个客户端做 `WATCH`/`MULTI`/`EXEC` |
| `notifyKeyspaceEvent` | 键空间通知的订阅者 | 订阅方收不到 `setmax` 事件 | `psubscribe` 后执行两次 |

**`server.dirty++` 与传播。** `call()` 在调用命令前记下 `server.dirty`，调用后求差（`src/server.c:4075` 的 `dirty = server.dirty-dirty;`）。只有差不为 0，才会给 `propagate_flags` 加上 `PROPAGATE_AOF|PROPAGATE_REPL`（`src/server.c:4174`）：

```c
if (dirty) propagate_flags |= (PROPAGATE_AOF|PROPAGATE_REPL);
```

少了这一行，命令在 redis-cli 里照常返回，但不会进 AOF，也不会传给从库。打开 AOF 做对照：

::: terminal title="zsh - 有无 server.dirty++ 的 AOF 对照"

## 7. 修改任务二：用模块扩展命令

改核心的代价是每次升级都要重新打补丁，还得自己维护。模块（module）走另一条路：用一组稳定的 C API 注册命令，编译成 `.so`，服务器启动或运行时加载，不必重编 Redis。这一节写一个只读命令。

### 7.1 模块的骨架

`code/项目/Redis/modules/mdrsum.c` 实现 `MDR.SUMLEN key [key ...]`，累加每个键的长度：字符串按字节数，集合、列表、哈希、有序集合按元素个数，键不存在按 0。完整代码见该文件，关键部分：

```c
static int mdr_sumlen(RedisModuleCtx *ctx, RedisModuleString **argv, int argc) {
    if (argc < 2) {
        return RedisModule_WrongArity(ctx);
    }

    long long total = 0;
    for (int i = 1; i < argc; i++) {
        RedisModuleKey *key = RedisModule_OpenKey(ctx, argv[i], REDISMODULE_READ);
        total += (long long)RedisModule_ValueLength(key);
        RedisModule_CloseKey(key);
    }
    return RedisModule_ReplyWithLongLong(ctx, total);
}

int RedisModule_OnLoad(RedisModuleCtx *ctx, RedisModuleString **argv, int argc) {
    REDISMODULE_NOT_USED(argv);
    REDISMODULE_NOT_USED(argc);

    if (RedisModule_Init(ctx, MDRSUM_MODULE_NAME, MDRSUM_MODULE_VERSION,
                         REDISMODULE_APIVER_1) == REDISMODULE_ERR) {
        return REDISMODULE_ERR;
    }

    if (RedisModule_CreateCommand(ctx, "mdr.sumlen", mdr_sumlen, "readonly fast",
                                  1, -1, 1) == REDISMODULE_ERR) {
        return REDISMODULE_ERR;
    }
    return REDISMODULE_OK;
}
```

入口函数名必须是 `RedisModule_OnLoad`，`RedisModule_Init` 必须最先调用。`CreateCommand` 的后三个参数是键的起止位置与步长，`1, -1, 1` 表示从第 1 个参数到最后一个都是键，步长 1；`readonly fast` 是标志串，写进命令表后 `COMMAND INFO` 会把它显示出来（加上模块命令自带的 `module`，共三个）。`RedisModule_WrongArity` 自动生成与内置命令同格式的参数个数错误。

### 7.3 两条路的取舍

| | 改核心（`SETMAX`） | 模块（`MDR.SUMLEN`） |
| --- | --- | --- |
| 实现位置 | `t_string.c` 与 `commands/setmax.json` | 独立的 `.so`，不改 Redis 源码 |
| 升级 Redis | 补丁要重新打，`commands.def` 重新生成 | 重新编译一次 `.so` 即可 |
| 名字 | 与内置命令同处一个命名空间，可能冲突 | 用 `MDR.` 前缀隔离 |
| 性能 | 直接操作内部结构，没有边界开销 | 每次调用过一次 API 边界 |
| 持久化 | `call()` 按 `dirty` 自动传播 | 自己调 `RedisModule_Replicate` 或 `ReplicateVerbatim` |
| 能用什么 | 全部内部结构：`db`、`dict`、SDS、对象编码 | 只有稳定 API 暴露的操作 |

判断标准很直接：需要碰内部结构、需要参与命令表的细节（例如 `DENYOOM`、键规格、ACL 分类）就改核心；只需要在已有键值之上做计算，用模块。`SETMAX` 属于前者：它要拿到 `dictEntryLink` 做一次定位两次写入，还要按整数解析的规则给出错误。`MDR.SUMLEN` 属于后者：它只读长度，用 `RedisModule_ValueLength` 一个调用就够。
