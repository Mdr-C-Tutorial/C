# 8.1 Mdr Lang 项目概述

源文件 `counter.mdr` 勾勒了一段精简的计数器逻辑：初始化状态、触发自增、累加偏移量、提取当前读数，末行注释赫然标注着作者预期的最终结果 5。然而，若将这段看似自洽的脚本递交给仓库自带的 C 语言实现编译器前端，控制台返回的响应仅仅是一行干脆利落的 `OK: counter.mdr`。

没有指令被实际执行，注释中推演的数字 5 也未曾在任何寄存器或标准输出流中被计算出来。这恰好定格了 Mdr Lang 当前真实的工程演进切面：无论是基于 Node.js 的参考前端，还是采用 C 语言编写的原生前端，实现焦点均止步于词法分析与语法分析阶段；C 语言版本在此基础上推进了一组静态语义与类型检查，但两套前端目前均未涉足代码生成与虚拟机执行环节。

探索这样一个处于“半成期”的语言工程，其价值正在于能够清晰拆解编译器前端在从无到有的生长过程中所必须跨越的技术阶梯。我们将从这门语言的语法外貌与核心设计切入，梳理双前端架构的代码组织与设计取舍，在 Windows 与类 Unix 环境下排查真实的跨平台构建阻碍，并透视现有自动化测试套件的盲区与演进方向。

## 1. Mdr Lang 是什么样的语言

从语言形态与语法范式来看，Mdr Lang 是一门兼具静态类型约束与脚本化表达习惯的编程语言。源码文件统一采用 `.mdr` 后缀，程序顶层允许直接书写可执行语句，函数、结构体与局部标识符绑定亦可并列驻留于全局顶层作用域；词法块以标准花括号界定，类型标注沿用现代系统级语言常见的后置语法，通过 `let` 与 `const` 关键字显式引入只读或可变绑定。

在项目的 `example/` 目录下收录了 10 份官方示例脚本。需要提前说明的是，这些脚本中以 `//` 开头的行注释多为语言设计者在设计阶段预先标注的类型推断或期望输出，用于锚定语言规范；现阶段的编译器前端并不会对其进行实际求值。

### 1.1 结构体、方法与 this

作为状态封装的基本单元，`counter.mdr` 完整演示了结构体声明、带接收者的方法定义以及实例初始化的典型范式：

```c
struct Counter(value: i32);

function Counter.inc() -> () {
    this.value = this.value + 1;
}

function Counter.add(n: i32) -> () {
    this.value = this.value + n;
}

function Counter.get() -> i32 {
    return this.value;
}

let c = Counter(0);
c.inc();
c.add(4);
print(c.get());
// 5
```

在语法表达上，Mdr 的结构体声明极其紧凑：字段列表直接嵌套在类型名后的圆括号内，整体以单行分号收尾。与 C++ 或 Java 将方法内嵌在类型声明体内部的传统做法不同，Mdr 采用了外部解耦的方法定义机制：通过 `function 接收者类型.方法名` 的语法糖将函数与特定类型绑定，方法体内的 `this` 关键字则隐式绑定至调用时传递的宿主对象实例。

在类型与方法的解耦设计上，不同现代语言做出了各有千秋的探索：Rust 要求在独立的 `impl` 块中集中陈列方法，Go 则在参数表前置专用的接收者语法槽；Mdr 则选择了更为直白的“类型前缀命名法”，把接收者类型直接视作方法签名命名空间的一部分。当代码发起 `c.inc()` 调用时，编译器前端会解析 `c` 的静态类型，进而到符号表中精确定位登记的 `Counter.inc`。从语义推演来看，`Counter(0)` 构造出初始值为 0 的实例，随后经历自增与累加逐步流转为 5，最终由 `get()` 返回——示例末尾的期望注释正是基于这套心智模型手工推导而来。

### 1.2 元组、复合赋值与 use

在多维空间向量的运算示例 `vec2.mdr` 中，展示了元组字面量、就地复合运算以及模块导入语法的雏形：

```c
struct Vec2(a: i32, b: i32);
function add(a: Vec2, b: Vec2) -> Vec2 {
    return (a.a + b.a, a.b + b.b);
}
function Vec2.add(other: Vec2) -> () {
    this.a += other.a;
    this.b += other.b;
}
function mul(a: Vec2, n: i32) -> Vec2 {
    return (a.a * n, a.b * n);
}
function Vec2.mul(n: i32) -> () {
    this.a *= n;
    this.b *= n;
}

use math; // i32.square() -> i64 和 i64.sqrt() -> f64 和 f64.floor() -> i32

function Vec2.mod() -> f64 {
    return (this.a.square() + this.b.square()).sqrt();
}

print(Vec2(4,5).mod().floor); // 6
```

在 `add` 函数的返回语句中，`(a.a + b.a, a.b + b.b)` 是一个匿名元组字面量。在 Mdr 的设计预设中，结构体与同构元组具备天然的互通性，字段依据位置顺序自左向右依次对应映射。与此同时，`+=` 与 `*=` 提供了熟悉的原地算术赋值，而顶层的 `use math;` 则标明了外部数学库的引入意图。

值得关注的是自由函数与成员方法之间的重名消歧机制：系统允许全局命名空间中并存自由函数 `add` 与类型方法 `Vec2.add`，语法解析器与语义分析器依据调用点前缀是否附带明确的接收者对象来从容仲裁。至于 `mod()` 内部展现的链式点调用（如 `.square()` 与 `.sqrt()`），则属于语言规范展望中的理想形态——现阶段的编译器前端在处理 `use math` 时仅是在 AST 中记录模块标识符，并未挂载真实的标准库符号表，因而并不会在编译期拦截针对未定义数学方法的调用。

### 1.3 范围

在现代语言中，范围运算符通常用于简洁构造数列或驱动循环。Mdr 在语法层面提供了高度集成的区间表达范式：`a..b` 对应半开半闭区间 $[a, b)$，`a...b` 对应完全闭合区间 $[a, b]$；在此基础上若继续追加 `..步长`，便能直接生成具备非单位步长跨度的离散序列。`range_open_closed.mdr` 与 `range_step.mdr` 全面枚举了这几类组合：

```c
let r_open = 3..8;
print(r_open);
// [3, 4, 5, 6, 7]

let r_closed = 3...8;
print(r_closed);
// [3, 4, 5, 6, 7, 8]

let r_small_open = 5..6;
print(r_small_open);
// [5]

let r_small_closed = 5...6;
print(r_small_closed);
// [5, 6]
```

```c
let step_open = 3..10..2;
print(step_open);
// [3, 5, 7, 9]

let step_closed = 3...10..2;
print(step_closed);
// [3, 5, 7, 9]

let step_hit_end = 2...10..4;
print(step_hit_end);
// [2, 6, 10]

let step_skip = 3..8..10;
print(step_skip);
// [3]
```

仔细对照各组期望输出，可以梳理出底层明确的数列生成逻辑：迭代自起始值 $a$ 出发，每轮循环递增指定的步长 $s$（省略步长时隐式默认为 1）；半开区间以 $i < b$ 为推进准绳，闭区间则放宽至 $i \le b$。需要特别澄清的是，“闭区间”仅保证上限阈值在逻辑上允许被触达，并不意味着终点数值一定会出现在离散序列中。例如在 `3...10..2` 中，序列生成依次为 3、5、7、9，紧接着的候选值 11 已突破 10 的截断边界，因此 10 本身并不会被纳入结果；而在 `2...10..4` 中，第 3 轮迭代恰好稳稳落在 10 上，故而将其完整保留。

若将 Mdr 的区间记号置于主流语言横向审视，其句法特征十分鲜明：Rust 采用 `a..b` 表示半开区间、`a..=b` 表示闭区间，且语言原生并不支持字面量步长语法，需借助迭代器适配器 `.step_by()` 实现；Swift 则使用 `a...b` 代表闭区间、`a..<b` 代表半开区间。Mdr 的 `...` 与 Swift 保持一致，而 `..` 则承袭了主流对半开区间的共识，并将步长参数直接升格为运算符语法槽，这种在字面量中直接集成步长维度的做法构成了 Mdr 独具特色的语法拓展。

::: concept mdr-range-semantics title="范围的取值规则"

按示例注释归纳，范围 `a..b` 依次取 `a`、`a + s`、`a + 2s`……其中 `s` 是步长（省略时为 1），只要当前值满足 `i < b` 就继续；`a...b` 把条件换成 `i <= b`。起点总是包含在内。

:::

::: generate mdr-range-walkthrough kind=example concepts=mdr-range-semantics

面向第一次见到 `..` 与 `...` 的读者，用 `3...10..2` 逐步列出候选值 3、5、7、9、11，说明 11 因为超过 10 而不被取；再用 `2...10..4` 列出 2、6、10、14，说明 10 恰好落在终点上所以被收进来。最后对照 Rust 的 `..`/`..=` 与 Swift 的 `...`/`..<`，指出 Mdr 的记号与 Swift 一致、与 Rust 差一个等号。不要讨论词法分析。

:::

### 1.4 loop、break 与 continue

`loop_break_continue.mdr` 只有一个 `loop`，靠 `break` 退出：

```c
let i = 0;
let acc = 0;

loop {
    i = i + 1;
    if (i == 3) {
        continue;
    }
    if (i > 5) {
        break;
    }
    acc = acc + i;
}

print(acc);
// 12
```

在控制流语法上，`loop { }` 提供了无条件无限循环的原语抽象，在语义上等价于传统 C 系语言中的 `while (true)`，控制流的跳出完全依托内部显式触发的 `break`。在循环体执行过程中，当累加对象 `i` 递增至 3 时，`continue` 语句跳过后续的求和逻辑；当 `i` 推进至 6 时，`break` 在求和指令前抢先切断循环。整个流转过程中，实际参与算术累加的离散值为 1、2、4、5，求和终值为 12。需要指出的是，`break` 与 `continue` 在语法规范上严格受限于循环体上下文，孤立出现在顶层或普通代码块中将直接触发静态语义诊断，这构成了后文对比双前端语义能力的一处典型切入点。

### 1.5 泛型参数

`generic.mdr` 演示类型参数与值参数的混用：

```c
function <T, N: i32> [T, N].get(n: i32) -> T {
    if( n < N && n >= 0 ){
        return this.n;
    }
    return null;
}
```

在函数签名的尖括号内陈列了泛型参数列表：裸标识符 `T` 代表泛化类型占位符；而附带类型标注的 `N: i32` 则属于常量值参数，能够在函数实现体内充当编译期已知的整型常量。方法的接收者类型被定义为复合元组 `[T, N]`；在 C 语言前端登记方法符号时，内部例程 `semantic_type_format` 负责将类型节点格式化为规范文本，所有元组类型统一折叠为 `tuple` 关键字，因此最终在方法表中登记的唯一检索键为 `tuple.get`。

需要说明的是，此处的示例主要用于锚定复杂的语法边界，其实现体本身具有一定的示意性质（例如在匿名元组上无法按名字访问 `.n` 成员），两套前端在当前阶段均不会深入求值该逻辑。关于尖括号包裹的泛型参数与普通圆括号参数表在递归下降中的冲突消歧，将在 8.2 节展开技术剖析。

### 1.6 类型规则的一个设想

`type.mdr` 没有函数，只有几行绑定和注释：

```c
let X = ('2', 3.5, 6800);
// X: tuple(char, f64, i32)
let A = ['2', 3.5] // error!
let A = [16, 12800];
// A: array[i32, 2]
let A = [-16, 12u]; // error!
```

开篇语句展示了异构元组的承载能力，注释推演其对应推断类型 `tuple(char, f64, i32)`。随后围绕标识符 `A` 的几组数组字面量声明中，标注有 `error!` 的两处案例展示了设计预期：当数组内部各元素的静态类型不一致时（如混入字符与浮点、或者有符号整型与无符号整型），静态类型系统应当在编译期及时拦截并报错。

然而在当下的工程实现切面中，两套前端实际上均能顺利放行该文件：C 语言版本直接报告 `OK`，JavaScript 前端亦输出了完整的 AST。这是因为现有前后端的数组类型抽象仅粗粒度标记了容器类别与元素长度，尚未对容器内部的元素类型施行同质性（Homogeneity）一致性校验。这种设计设想与现实实现之间的阶段性落差，为后文深入类型系统改造留下了清晰的演进靶标。

### 1.7 顶层语句与语句终结

与传统 C 语言强制要求将执行入口收敛于 `main` 函数不同，Mdr 允许在全局顶层作用域中直接平铺声明与表达式语句，无论是 `counter.mdr` 中的链式调用，还是 `range_step.mdr` 中的范围运算，均以顶层自由语句的形式自上而下展开。

在语句断句策略上，Mdr 采用了对开发者友好的自适应终结机制：显式分号是可选的。只要下一个词法记号跨越到了新的代码行，或者当前遇到闭花括号 `}` 及文件结束符（EOF），语法分析器便视当前语句已经自然终结。关键在于，分析器唯有在完整消费并闭合一个语法合法的完整表达式之后，才会发起断句判定，因此物理换行并不会鲁莽地割裂跨行表达式。例如跨越两行的加法绑定依然能够无缝拼接：

```text
let a = 1
+ 2;
```

相反，假若将两条语义独立的声明语句强行压缩在同一物理行内，且未用显式分号隔开，解析器在第一条声明消费完毕后无法探测到任何合法的终结标志，便会立即抛出语法异常：

::: terminal title="PowerShell - 同一行的两条绑定"

```text
> .\mdrcc.exe sameline.mdr
sameline.mdr:1:11: expected ';' after binding declaration
```

:::

这种语法机制在直觉体验上与 Go 语言的自动分号插入（ASI）颇为相似，但 Mdr 的内部实现并不在词法流中向记号队列无中生有地合成虚拟分号，而是在递归下降分析器的断句判定例程中，将“物理行号递增”作为一个正规合法的终结谓词进行模式匹配。

### 1.8 各特性的完成度

将前文涵盖的核心语法特性与双端编译器的实现状态汇总对照，能够帮助我们在宏观上建立清晰的工程坐标。在下述矩阵中，“解析”指分析器能够无歧义消费记号流并识别句法（C 版在解析的同时完成即时校验，并不持久化语法树，详见第 2 节）；“检查”指具备静态作用域判定与类型匹配能力；“执行”则代表指令真正落地并算出确定输出。

| 特性 | 示例文件 | JS 前端 | C 前端 | 执行 |
|:---|:---|:---|:---|:---|
| 结构体与方法 | `counter.mdr` | 解析 | 解析并检查 | 无 |
| 元组与复合赋值 | `vec2.mdr` | 解析 | 解析并检查 | 无 |
| `use` 声明 | `vec2.mdr` | 解析 | 解析 | 无 |
| 范围与步长 | `range_open_closed.mdr`、`range_step.mdr` | 解析 | 解析并检查 | 无 |
| `loop` 与跳转 | `loop_break_continue.mdr` | 解析 | 解析并检查 | 无 |
| 泛型参数 | `generic.mdr` | 解析 | 解析并检查 | 无 |
| 数组与范围转数组 | `arr_range.mdr`、`array_from_range.mdr` | 解析 | 解析并检查（元素类型不查） | 无 |
| 类型规则设想 | `type.mdr` | 解析 | 解析（规则未实现） | 无 |

矩阵中最引人注目的特征莫过于“执行”一列的全部留白。牢牢把握这一工程现状是理解当前代码库的基石：现存的双端代码聚焦于确立前端编译管道的合法性防线，着重判定“源程序是否符合词法、句法与静态类型契约”，而尚未向后端虚拟机与代码生成器迈进。

两套前端在架构设计哲学上走向了截然不同的分支：JavaScript 前端忠实构建并保留完整的抽象语法树，极其适合直观审视语法结构的层次拓扑；而 C 语言前端则贯彻了经典的单遍编译器（Single-Pass Compiler）思想，在自顶向下递归消费记号的同时，同步完成符号登记、作用域维护与类型校验，最终仅反馈全流程通过或首条精确的诊断错误。

::: concept mdr-c-single-pass title="C 版是单遍前端"

C 版不构造抽象语法树。`parser` 结构体里只有记号数组、当前位置、符号表和作用域标记栈；每个 `parse_*` 函数一边匹配记号，一边完成名称解析和类型检查，返回值是 `expr_result`（类型、能否赋值、被调用者信息），检查失败就立刻停下并返回第一条诊断。

:::

单遍架构以空间换速度，彻底省去了海量细粒度 AST 节点的动态内存申请与深层递归释放开销；但这一设计也带来了鲜明的约束：由于内存中不留存语法树中间表示，编译期无法直接向树遍历解释器或后端发射器移交代码结构；此外，单遍扫描天然受制于声明时序——它仅能感知此前已经物理登场的符号，任何针对后文实体的“前向引用”（Forward Reference）都将不可避免地被视作未声明标识符拦截。

项目未来的演进路线在参考文档中给出了清晰指引：规划在构建完整语义分析后引入线性或树状中间表示（IR），进而探索轻量解释执行器，最终对齐 C 代码生成或原生机器指令发射。而在当前的实现基准下，C 语言前端已稳健收敛了 10 项核心语义核验，覆盖作用域生命周期、循环跳转合法性、过程调用与参数类型协变、结构体成员访问以及方法签名一致性。

### 3.2 深度成因：格式化字符串的方言裂隙

在 C 语言演进史中，`%zu` 是 C99 规范专门为平台相关的 `size_t` 宽度量身定制的标准长度修饰符。然而在 MinGW-w64 工具链下，GCC 默认将其内置的 `printf` 家族函数调用映射至底层宿主运行库——即微软 MSVCRT/UCRT 约定的格式规则。在缺乏额外编译宏约束的缺省状态下，GCC 编译器前端会启用名为 `ms_printf` 的内置函数属性进行格式串类型静态匹配，而非遵循标准 Unix/C99 约定的 `gnu_printf` 规则。

微软传统的格式规范依赖专有的 `%Iu` 或 `%I64d` 表达平台字长整数，历史原生实现并未向标准 C99 的 `z` 修饰符开放兼容。因此，格式解析器在撞上 `%zu` 时，会将字母 `z` 视作未知非法字符；随后的字母 `u` 则被剥离出来视作独立的无符号十进制占位符，直接引发后续实参列表在静态类型层面的整体错位。由此触发了编译器接踵而来的三道连锁告警：

- `unknown conversion type character 'z' in format`：占位符语法非法；
- `format '%s' expects argument of type 'char *'`：后续格式参数由于错位而类型失配；
- `too many arguments for format`：多出的 `size_t` 实参被裁定为冗余实参。

在常规编译选项下，此类失配仅作为编译告警提示；但在高质量 C 工程的 `CMakeLists.txt` 中，通常配置了严苛的质量防护策略：

```cmake
target_compile_options(mdrcc PRIVATE -Wall -Wextra -Wpedantic -Werror)
```

标志 `-Werror` 无情地将任何编译警告直接提升为阻断级错误，导致构建流水线在遇到第一处格式警告时便强行熔断。相比之下，在具备原生 C99 支持的 Linux Glibc 环境下，由于标准 C 库早已天然支持 `%zu` 格式检查，相同的代码能够一路绿灯平稳编译。

### 3.3 架构修复：强制接入符合 C99 标准的 ANSI I/O

针对这一历史遗留的方言分歧，MinGW-w64 工具链提供了标准化解决开关 `__USE_MINGW_ANSI_STDIO`。当工程在编译期显式将其定义为 1 时，C 运行库头文件会在宏展开阶段把 `printf`、`fprintf` 及 `snprintf` 等符号重定向至 MinGW 自带的高保真 C99 实现分支（即 `__mingw_printf` 原语族）；与此同时，GCC 的格式静态检查引擎也会无缝切入 `gnu_printf` 属性，`z`、`j`（`intmax_t`）、`t`（`ptrdiff_t`）等 C99 长度修饰符随之被全量认可。

在通过 CMake 重新配置工程时，我们仅需在编译选项中注入该宏定义：

::: terminal title="PowerShell - 加上宏之后构建"

```text
> cmake -S compiler_c -B build -DCMAKE_C_FLAGS=-D__USE_MINGW_ANSI_STDIO=1
-- Configuring done (0.8s)
-- Generating done (0.0s)
-- Build files have been written to: D:/mdr/build

> cmake --build build
[1/3] Building C object CMakeFiles/mdrcc.dir/src/main.c.obj
[2/3] Building C object CMakeFiles/mdrcc.dir/src/mdr_compiler.c.obj
[3/3] Linking C executable mdrcc.exe
```

:::

三步编译链接一气呵成，终端未再出现任何警告杂音。需要强调的是，由于标准头文件的宏展开具有单向不可逆性，该宏定义必须严格抢在任何系统 I/O 头文件被引入之前确立生效。因此，通过命令行全局注入或挂载于 CMake 编译定义中是唯一的工程正解；若尝试在单个 `.c` 文件中按需补充，不仅繁琐易漏，且极易因前置系统头文件的间接引入而失效。

```cmake

```

:::

以包含类型冲突的反例 `bad.mdr` 为例：

```c
function main() -> () { let x: i32 = 1; x = true; }
```

诊断报告精准锁定了第 43 列处的赋值运算符 `=`。这一错误报告格式与 GCC、Clang 等现代主流编译器保持高度一致，能够被 VS Code 等编辑器或 IDE 的问题面板无缝捕获并支持一键点击源码跳转。在流处理设计上，合法的诊断通知严格定向至标准错误流（stderr），而正常响应则输出至标准输出流（stdout），便于自动化测试脚本进行管道分离捕获：

::: terminal title="PowerShell - 退出码与输出流"

```text
> ..\build\mdrcc.exe bad.mdr 2> err.txt
> $LASTEXITCODE
1
> Get-Content err.txt
bad.mdr:1:43: assignment type mismatch: expected i32, got bool
> ..\build\mdrcc.exe vec2.mdr
OK: vec2.mdr
> $LASTEXITCODE
0
```

:::

在进程退出协议上，C 前端严格遵守 Unix 工业惯例：全流程校验成功时退出码为 0，捕获任何异常时均以退出码 1 熔断退出，使得外部测试自动化 harness 无需脆弱地解析终端字符串即可判定编译成败。另外，解析器坚持即时短路原则：一旦侦测到首个不可恢复的语法或语义违规，立即中止向下解析并报告第一条诊断，不进行模糊的错误恢复尝试。

在复核整套语义检查链路时，我们捕获了一条极为隐蔽的内存踩踏崩塌路径：当发生过程调用实参与形参类型不匹配时，前端不仅未能平稳输出类型失配诊断，反而直接诱发了操作系统级的段错误崩溃。例如构造函数 `function foo(a: i32) -> () { }` 并在调用点传入布尔值 `foo(true);`，在 PowerShell 下进程直接退出并抛出异常代码 `-1073741819`（即十六进制 `0xC0000005`，访问违例 Access Violation）；挂载 GDB 调试器跟踪调用栈，程序在 `parse_postfix` 处戛然而止。

静态代码走查揭示了这一漏洞的致命成因：在 `mdr_compiler.c` 第 1681 行，代码提前调用了 `type_vec_free(&arg_types)` 释放了缓存实参类型的动态数组；紧接着在第 1683 行组装诊断错误信息时，控制流却再次去解引用已被释放并置空的 `arg_types.items[i]` 槽位，构成典型的释放后使用（Use-After-Free）。由于参数个数不符走的是另一条独立的长度判定分支，该路径上的格式化诊断尚能正常打印，因而未遮蔽常规的冒烟测试。这一深层缺陷将在 8.4 节作为实战演练被精准定位并修补。

::: tip 控制台代码页与中文路径兼容

在 Windows 系统的默认中文控制台环境下，活动代码页通常为 936（GBK 编码）。当编译器输出包含中文目录路径时，`OK:` 之后拼接的宽字符极易因终端流转产生乱码。切换至源码所在目录使用相对路径发起调用，或者将工程部署在全 ASCII 路径下，是规避平台编码干扰的推荐做法。

:::

在遇到句法异常时，JavaScript 前端展现出了极具现代交互感的美化诊断体验：除了常规的行列号与错误描述外，它还能精准重现发生错误的代码物理行，并利用插入符号 `^` 垂直锚定故障发生的具体列偏移：

::: terminal title="PowerShell - JS 的语法错误"

### 4.1 双端实现的两个关键分歧

通过对比两套前端在面对同一段边界代码时的反应，可以清晰提炼出二者在架构深度与词法边界上的关键分水岭。

**分歧一：语义拦截的落地深度。** 将一条孤立的 `break;` 语句直接写在顶层：

::: terminal title="PowerShell - 顶层 break"

```text
> ..\build\mdrcc.exe topbreak.mdr
topbreak.mdr:1:1: break is only allowed in loops
> $LASTEXITCODE
1

> node compiler\cli.mjs topbreak.mdr
{
  "kind": "program",
  "body": [
    {
      "kind": "break_stmt"
    }
  ]
}
> $LASTEXITCODE
0
```

:::

在 C 语言前端中，解析器内部实时维护着 `loop_depth` 循环嵌套计数器，在消费 `break` 语句的瞬间若发现深度为 0，便会当场判定语义越界并报错熔断；而在尚未引入语义检查层的 JavaScript 前端中，解析器仅按部就班地将其还原为一个单纯合法的 `break_stmt` 语法节点，予以顺畅放行。同理，像 `print()` 参数缺失、或者 `true + 1` 操作数类型失配等语义矛盾，单遍 C 前端均能在语法消费期予以强力阻断，而 JavaScript 前端在当前阶段均将其视作良构语法树全量接收。

**分歧二：类型标识符的词法地位。** C 语言前端在词法扫描器的保留字查找表中，将 `i8`、`i32`、`f64`、`char` 等内置标量类型名全量收录为 `keyword` 保留字；而 JavaScript 前端则仅将它们视作普通的 `identifier` 标识符：

::: terminal title="PowerShell - let a = i32;"

```text
> ..\build\mdrcc.exe typename.mdr
typename.mdr:1:9: expected expression
> $LASTEXITCODE
1

> node compiler\cli.mjs typename.mdr
{
  "kind": "program",
  "body": [
    {
      "kind": "binding_stmt",
      "bindingKind": "let",
      "name": "a",
      "type": null,
      "init": {
        "kind": "identifier",
        "name": "i32"
      }
    }
  ]
}
```

:::

在 C 前端的视角下，`let a = i32;` 中的 `i32` 属于保留字，在等号右侧期待值表达式的语法槽位撞见保留字，解析器自然抛出 `expected expression` 语法异常；用 `--tokens` 能看到这一行：

::: terminal title="PowerShell - C 版的记号分类"

```text
> ..\build\mdrcc.exe typename.mdr --tokens
    1:1    keyword    let
    1:5    identifier a
    1:7    operator   =
    1:9    keyword    i32
    1:12   operator   ;
    2:1    eof
```

:::

而在 JavaScript 前端中，`i32` 仅仅是一个普通标识符，该语句被合规解析为“用对象标识符 `i32` 初始化绑定 `a`”的语法结构。

关于孰优孰劣的架构裁决：翻阅两份参考文法草案 BNF，`i32` 均被明确收录在 `type` 规则而非通用 `id` 规则之中，从遵循语言规范草案的严谨度而言，C 版本的保留字处理更贴合原始初衷；然而将类型名硬性锁死为关键字，会导致开发者彻底丧失将类型名复用为普通局部标识符的自由度。这种语言设计中的微妙权衡，正是后文差分测试矩阵的核心验证素材。
