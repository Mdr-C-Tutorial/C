# 9.1 MdrOS 项目概述

构建一个操作系统内核是系统编程领域中极具挑战也最能洞察软硬件协同机制的工程实践。这一过程要求开发者对计算机体系结构、处理器运行模式、总线通信以及 C 语言与汇编语言的底层机制拥有扎实且连贯的理解。

本模块以面向 x86 架构的开源教学操作系统 MdrOS 为蓝本，梳理从处理器加电复位、引导加载、内核基础设施搭建，到多任务调度与硬件驱动集成的完整演进脉络。需要说明的是，本篇内容聚焦于关键架构设计决策、硬件交互规范与高频隐蔽陷阱的剖析，提供全局视野与工程参照，而非简单罗列代码拼图。

## 1. 核心概念与系统边界

从计算机系统的全局视角审视，操作系统的核心职责在于向下接管、抽象并调度底层硬件设施，向上为应用程序提供受控、统一执行环境。

一个完备的内核通常由若干协同运转的子系统有机聚合而成：

- **物理与虚拟内存管理**：负责管理物理内存页框分布，构建分层页表以支撑虚拟地址空间的隔离与保护；
- **中断与异常分发体系**：构建中断描述符表，建立统一的中断现场保护与服务例程调度机制；
- **设备驱动与总线交互**：经由端口 I/O 或内存映射 I/O（MMIO）与可编程外设控制器通信，驱动定时器、键盘及图形显示等部件；
- **抢占式多任务与上下文切换**：维护任务控制块（TCB），借助硬件时钟中断触发调度策略，平滑切换处理器上下文；
- **存储介质抽象与文件系统**：向上屏蔽块设备的物理寻址差异，提供层次化命名空间与文件组织能力；
- **系统调用与用户态隔离**：界定特权级边界，拦截并校验来自用户空间的系统请求，确保特权级转换的安全可控。

### 1.1 硬件加电至内核接管脉络

现代 x86 计算机从物理触发到内核完全接管控制权，需要经历跨越固件、引导程序与内核自身的精密时序转移：

1. **物理供电与加电自检（POST）**：电源接通后，主板电源管理芯片向 CPU 发出复位信号，处理器内部寄存器置为初始预设状态，执行固件内置的加电自检程序，探测并校验内存与核心外设。
2. **固件初始化与寻址**：主板固件（Legacy BIOS 或 UEFI）完成基本硬件枚举与运行时环境构建，依据非易失性配置中的启动顺序，在持久化存储介质上定位可引导扇区或 ESP 系统分区。
3. **加载次级引导程序（Bootloader）**：固件将预设存储块载入指定物理内存地址，完成基础完整性校验后，将执行权限递交给引导加载程序。
4. **运行环境跨越式配置**：引导程序负责探查物理内存布局图（Memory Map）、配置基础显示模式、启用 A20 地址线，并在必要时协助完成由实模式向保护模式或长模式的跃迁，随后自存储设备中读取内核可执行镜像（如 ELF 文件）并重定位至对应内存区间。
5. **控制权移交内核**：引导程序设置好初始栈与启动参数块，以跳转指令直接跃迁至内核入口符号，处理器控制权由此正式转交操作系统。

内核接管控制权后，将根据既定系统架构逐步解构硬件状态，初始化页表映射、重构特权描述符表，并分阶段激活核心驱动。

## 2. 工程环境与构建工具链

开发底层内核需要脱离标准 C 运行时库（Hosted Environment），采用支持自举与独立二进制生成的工具链：

- **[xmake](https://xmake.io)**：现代化的跨平台构建系统，通过简洁的声明式配置调度多语言编译过程，支持自动感知与拉取工具链依赖；
- **Clang / zig cc 编译器**：支持生成无外部运行时绑定的裸机独立目标文件（Freestanding），具备严格的类型检查与现代 C 语言标准支持能力；
- **[NASM](https://nasm.us/) 汇编器**：用于编写与处理器底层模式切换、中断上下文压栈及特殊控制寄存器操作直接绑定的微观汇编例程。

## 3. 源码工程组织建议

在内核开发过程中，为了维持模块高内聚与低耦合，应当严格划分公共接口头文件与具体硬件实现的存放目录。

后文中出现的代码片段，往往从实际工程目录中的特定驱动或体系结构组件中提炼而来。建议在搭建自己的代码树时，预先理清跨平台抽象、硬件相关代码（Arch-specific）以及独立内核库函数的物理存放边界，使通用算法与平台特性解耦，便于长期演进与逻辑复用。

- **[OSDEV Wiki](https://wiki.osdev.org/)**：由全球系统开发者共同沉淀的内核开发知识库，覆盖了 x86 平台绝大多数经典控制器与引导协议的实现细节；

## 6. 核心工程准则

在进入具体的代码实现之前，建立清晰的系统级预期与工程权衡具有长远价值：

- **聚焦核心机制的完备性与稳定性**：图形界面（GUI）仅仅是人机交互的外在呈现，内核的基石在于对物理硬件资源的严谨管控。优先保证物理与虚拟内存管理、中断响应、进程调度与基础驱动的健壮运转，远比过早铺陈视觉功能更为重要。
- **客观看待早期入门教程的设计折中**：部分经典入门读物（例如《30 天自制操作系统》）为了控制学习曲线，在内存保护、分页模型与异常隔离方面省略了诸多机制。在构建符合现代规范的系统时，应当以体系结构官方文档为基准，避免直接沿用简化的过渡方案。
- **充分评估目标运行模式的复杂度差异**：在 x86 架构下，32 位保护模式使用经典的二级页表即可覆盖 4 GiB 虚拟地址空间；而在 64 位长模式下，除了需要构建至少四级页表体系外，还必须严格遵循规范地址检查，上下文保存与深层页表维护的复杂度均显著提升。
- **正视不同体系结构间的底层语义分野**：x86、ARM 与 RISC-V 在内存一致性模型、异常分级以及特权切换指令上存在根本性差异。在移植或参考其他硬件平台的实现时，必须充分核实其底层硬件假设。
- **以真实物理机运行为系统成熟度检验标准**：模拟器（如 QEMU、Bochs）通常为了调试便利与执行效率，对部分非规范硬件行为展现出较高的容忍度（例如隐式清零或宽松的对齐检查）。唯有在真实物理主板上顺利引导并稳定调度的系统，才算真正经受住了硬件多样性与真实时序的考验。

## 7. 高频陷阱与硬件约束

::: warning

在操作系统内核的开发中，调试手段往往非常受限。此处梳理的注意事项均源于真实硬件与虚拟机调试中反复出现的关键陷阱，提前了解这些约束有助于规避难以排查的暗病。

:::

> 4 KiB 边界在十进制下对应 `4096` 字节，十六进制表示为 `0x1000`。

### 7.1 内存管理约束

- **控制寄存器 CR3 对齐**：CR3 寄存器用于保存当前顶级页表的物理基地址，其低 12 位保留用作属性配置，CPU 硬件在寻址时会自动屏蔽这些位。因此，装填进 CR3 的页表物理基地址必须严格满足 4 KiB 对齐。
- **物理页框分配基准**：物理页框分配器产出的每一个页框起始地址，都必须保证 4 KiB 对齐，方可直接装填到页表项（PTE）的高位地址字段中。
- **栈指针（RSP/ESP）对齐要求**：执行函数调用与系统调用时，栈指针通常要求满足 16 字节对齐。部分现代硬件指令（如涉及 SSE/AVX 向量计算的代码）若在未对齐的栈空间访问局部对象，将直接触发通用保护异常（#GP）。
- **引导器预留内存防覆写**：在使用 Limine、Multiboot 等现代引导器时，引导程序自身已在物理内存中建立了初始映射并占用了部分页框。实现物理页分配器时，必须解析引导器传递的内存映射图（Memory Map），将内核镜像所在区间、引导器保留区及页表本身彻底标记为已占用，避免重复分配引发静默覆写。
- **页表物理内存连续性**：单个页表结构（无论是 32 位的页目录、页表，还是 64 位的四级页表项集合）在物理内存上必须保持连续的 4 KiB 空间，且基址按 4 KiB 对齐。
- **TLB 缓存一致性刷新**：修改或撤除既有页映射后，必须通过 `invlpg` 指令或重载 CR3 刷新转换后援缓冲器（TLB），否则 CPU 仍会命中旧有的地址转换缓存，导致内存读写落入过时或无效的物理地址。

### 7.2 设备与中断驱动约束

- **MMIO 寄存器交互必须使用物理地址**：外设控制器内部通常缺乏系统级 MMU 支持，通过内存映射 I/O（MMIO）向设备下发命令或配置 DMA 缓冲区时，写入寄存器的地址必须是真实的物理地址，传入虚拟地址将导致设备寻址失败或破坏未定义内存。
- **中断结束信号（EOI）的及时应答**：处理外部硬件中断请求（IRQ）时，服务例程必须在处理完毕后向中断控制器（PIC 或 APIC）发送中断结束（EOI）指令。若未发 EOI，中断控制器的在服务寄存器将持续处于置位状态，后续该级别及更低级别的硬件中断都会被无限期阻塞。
- **PS/2 键盘缓冲区的时序交互**：PS/2 键盘控制器在扫描码被软件读取之前，不会产生后续的新中断。如果驱动在中断例程中遗漏了读取数据端口的操作，整个键盘子系统将陷入死锁。
- **中断退出与 EOI 发送顺序**：在 PS/2 等高频触发设备的处理中，EOI 的发送时机应当放在数据读取之后，若过早释放 EOI，外设新产生的脉冲可能导致当前中断上下文被不可控地嵌套重入。

### 7.3 CPU 与特权指令细节

- **段寄存器基址写入的兼容性**：在部分虚拟化平台与真机环境中，针对 `fs` 和 `gs` 寄存器的 `wrfsbase` 与 `rdgsbase` 扩展指令可能未被开启或支持不全。采用 `wrmsr` 与 `rdmsr` 指令直接操作对应的模型特定寄存器（MSR）是更为稳妥的兼容方案。
- **多核心环境下的核心拓扑识别**：不同代际的处理器在 `cpuid` 指令的枚举细节上存在差异。在多核（SMP）初始化的逻辑中，推荐直接自 ACPI MADT 静态表或各个核心的 Local APIC ID 获取 CPU 编号，避免依赖 `cpuid` 返回的非标准逻辑编号。
- **扩展指令的按核使能**：诸如快速系统调用（`syscall`/`sysret`）等高级特性，依赖于特定的 MSR 控制位。在多处理器体系下，这类控制寄存器的使能属于核内局部状态，必须在每个核心的自举例程中分别执行一次。
- **避免在核心循环中滥用低功耗指令**：在未进入空闲休眠阶段的业务循环中，随意插入 `pause` 或 `hlt` 会导致处理器调频策略发生偏移甚至陷入等待挂起，影响实时响应性能。

### 7.4 并发同步与调度时钟

- **锁粒度与加锁次序管控**：内核中的自旋锁与互斥锁应当严格遵循既定的依赖序，禁止交叉逆序加锁，在持有自旋锁期间必须禁用本地中断，防止中断服务例程重入导致死锁。
- **时钟中断频率与调度开销平衡**：可编程定时器（PIT 或 APIC Timer）的中断频率需要合理设定。频率过高会导致上下文切换占据过多 CPU 周期，甚至出现上一次调度例程尚未退出便被下一次时钟中断嵌套打断的情况。
- **异步临界区的全路径防护**：内核与中断例程共享的数据结构，必须在访问前关闭中断或获取自旋锁，防止并发执行流引发竞态条件导致结构损坏。

### 7.5 内核工程与鲁棒性实践

- **启用严格编译器诊断选项**：在裸机开发中，排错手段有限且断点难以稳定捕获。开启 `-Wall -Wextra -Wconversion` 并将警告视同错误（`-Werror`），能把绝大多数类型截断、有符号无符号混用及对象未初始化问题拦截在编译期。相关提问与排错准则也可参阅 [编程交流生存指南](/杂项/技术无关/1_编程交流群生存指南.md)。
- **对用户态输入践行零信任原则**：内核作为特权分界线，绝不能盲目信任来自用户空间的指针或长度。在处理系统调用参数时，必须严格校验指针是否处于用户合法地址范围之内，严防空指针引用或越界跨入内核特权空间。
- **前置防御性断言与自检**：在关键内存分配、物理寻址和模式转换接口内部，应积极嵌入编译期断言与运行时检查。一旦出现预设约束被打破，立即通过控制台输出确切上下文，缩短定位系统异常的反馈路径。

7.2 节列了两条设备侧的规定：中断处理结束要发 EOI，PS/2 键盘要取走扫描码才会发下一次中断。用一个主机上的小模型验证这两条各自独立。按下述语义实现 `irq.c`：

- `pic` 有 `bool pending[16]`、`int in_service`、`int delivered`，初始化时 `in_service = -1`。
- `pic_raise(irq)` 置 `pending[irq]`。
- `pic_ack()`：若 `in_service >= 0` 返回 -1；否则取编号最小的 pending 项，清掉它，记入 `in_service`，`delivered` 加 1，返回该编号。
- `pic_eoi(irq)`：若 `in_service == irq`，把它置回 -1。
- 键盘有 `int queued`、`bool data_ready`。`key_press()` 先 `queued++`；若 `data_ready` 为假，置真并向 1 号 IRQ 发请求。
- `key_read()`：若 `data_ready` 为真，`queued--` 并置假。
- `serve(read_data, send_eoi)`：先 `ack`；若拿到 1 号 IRQ，按两个布尔参数决定是否 `key_read` 和 `pic_eoi`。
- `run(name, read_data, send_eoi)`：按三次「按键、处理」循环，最后打印 `delivered` 与 `queued`。

四组参数依次为 `(true, true)`、`(true, false)`、`(false, true)`、`(false, false)`，输出应当如下：

```text
read+eoi  delivered=3 queued=0
read      delivered=1 queued=2
eoi       delivered=1 queued=3
neither   delivered=1 queued=3
```

逐行解释这四个结果。要求分别指出：哪一组被「没发 EOI」卡住，哪一组被「没读扫描码」卡住，为什么 `read` 与 `neither` 的 `delivered` 相同而 `queued` 不同。最后回答：现实中的 PS/2 控制器在数据未取走时，中断线上还会不会继续拉高？

验收：四行输出一致；解释里把 PIC 的 `in_service` 和键盘的 `data_ready` 当成两个独立条件，而不是笼统地说「中断没处理完」。

</Exercise>

7.5 节建议编译器开严格模式。把下面的 `strict.c` 用 `gcc -std=c17 -Wall -Wextra -Wconversion -Werror -c strict.c` 编译，恰好得到三条错误：
