# 9.1 MdrOS 项目概述

开发操作系统是一个漫长的过程，需要你有一定的计算机底层原理知识以及 C 和汇编语言的基础。
本章教程将教您如何开发一个 x86 平台的操作系统。

> 该教程有很多不详细之处，并不能直接作为保姆式教程使用
>
> - 实际上该项目为参考式项目，提供了一个大致的开发方向，以及标注了很多开发中可能遇到的问题

## 1. 概念

操作系统是一种系统软件，它是控制管理计算机系统的硬软件，分配调度资源的管理者\
其内部功能有：

- 内存管理
- 设备驱动
- 中断处理
- 任务调度
- 文件管理
- 网络处理

> 还有很多，此处不一一列举

### 1.1 计算机启动过程

1. 电源键按下
2. POST 加电硬件自检
3. 加载 BIOS
4. 加载引导程序
5. 计算机控制权移交给操作系统内核

这样，一个操作系统就算启动了。接下来内核会初始化各种功能以及加载一些必要的设备驱动，具体的启动方式还是要依据该操作系统的架构决定。

## 6. 告诫

- GUI 并不是操作系统必要的功能，一个操作系统可以没有 GUI, 但是其必须实现的功能要齐全且稳定
- 《30 天自制操作系统》这本书仅供 GUI 部分参考，其他功能实现并不是很好，不建议您全部借鉴
- 64 位长的操作系统会比 32 位保护模式的操作系统实现更难，比如 32 位只需要二级页表即可，64 位需要 4 级甚至更多才能管理所有内存
- ARM 等其他架构的 CPU 与 x86 平台的 CPU 实现截然不同，其中 x86 的很多机制在 ARM 是没有的，同理 ARM 某些机制 x86 也没有
- 本教程只是给予开发的一个大致方向与常见问题解答，注意事项提醒等
- 操作系统编写好都是要在实体机上测试的，无法在实体机上跑的操作系统就不是一个真正的操作系统

## 7. 注意事项

::: warning

笔者结合开发过程中发现的实际 BUG，对新手 OS 开发者起到警醒作用，避免重复犯同样的错误

:::

> 4Kib: 可以用十进制 `4096` 表示，也可以用十六进制 `0x1000` 表示

### 7.1 内存

- cr3 指向的页表基址，必须进行 `4k` 对齐
- 物理内存管理分配出来的页框基址，必须是 `4k` 对齐的再写入页
- `rsp` 的栈基址最好为 16 字节对齐，因为部分实体机机型对此有要求
- 对于物理页框分配器，在使用提供一个初始页表的引导器操作系统开发中 (如 Limine), 需要额外注意内核本身与页表本身的内存占用，否则容易覆写
- 页表本身需要在物理内存上具有连续性，且基址必须 4k 对齐
- 页映射释放后需执行一遍 `TLB` 快表刷新操作，防止缓存干扰映射规则

### 7.2 驱动

- 所有设备驱动需要往 `MMIO` 设备寄存器传入物理地址 (设备控制器没有 MMU, 传入虚拟地址无法处理)
- 设备 IRQ 中断请求必须要向中断控制器发送 `EOI` 代表请求处理完毕，不然下一次设备请求不会再次发送
- `PS/2` 键盘需要在你获取了扫描码后才会发送下一次中断，否则 `PS/2` 控制器会阻塞
- `PS/2` 设备中断处理需要在最后发送 `EOI`, 否则多个扫描码发送会造成中断嵌套

### 7.3 CPU

- `qemu` `VMware` 虚拟机对 `wrfsbase` `rdgsbase` 等扩展指令支持性较差，建议使用 `msr` 对 `fs` `gs` 段寄存器进行操作
- 部分实体机的机型对 `cpuid` 指令的实现有些许差异，编写多核 CPU 初始化等代码时候需要用 `ACPI` 或 `lapic_id` 获取核心的代号，不要用 `cpuid` 指令获取
- 特殊的扩展指令 (如 syscall) 需要特别设置控制寄存器或 `MSR`去启用，且多核环境下需要为每一个核心都执行一遍启用操作
- 内核中不要滥用 `pause` `hlt` 等指令，这些指令会造成 CPU 功耗、频率降低，从而影响性能。

### 7.4 并发 / 异步

- 锁不要滥用，否则会发生死锁
- 调度器时钟频率不要太高，否则调度器本身未执行完毕会再一次进入调度器造成中断嵌套
- 异步冲突临界区必须加锁，否则会造成资源竞争冲突

### 7.5 开发

- 编译器最好开一下严格模式，因为操作系统本身是非常不好调试的，而且 BUG 溯源极其困难，一个小小的错误会让你头疼一个星期甚至一个月
- 详见 [编程交流生存指南](/杂项/技术无关/1_编程交流群生存指南.md) 第 1 标题，第 40,41,43 条
- 作为内核，你永远要以最坏的情况去针对用户态程序，用户 `syscall` 传来的参数要严格检查是否是空指针以及地址合法性
- 对于内核中对参数有要求的接口，要对参数打好断言，这样可以在自己犯傻后可以快速找出问题

> 你要清楚自己写的是什么，有哪些不足，应该如何安排项目结构

写一个物理页框分配器 `frame.c`，按 7.1 节的要求保证分配出的页框基址都是 4 KiB 对齐。接口如下：

```c
void fb_init(uint32_t bytes);   /* 按字节数计算页框数，清空位图 */
```

```text
allocated=1000 last=999
after free=500
reuse=1 used=501
```

步骤是：以 16 MiB 初始化；连续分配 1000 次；释放编号为奇数的页框（1、3、…、999）；再分配一次。每次分配后检查 `frame * 4096` 能整除 4096，不满足就立刻退出。

2. 把 `fb_init` 的字节数改为 `0`，说明 `fb_alloc` 应当返回什么，你的代码是否做到了。这一条不要求修改代码，只记录实际行为。
3. 按 3 节的建议给这个分配器安排位置：画出你准备用的目录树，标出 `frame.c`、它的头文件、测试用的 `main.c` 各放哪，并说明 9.6 节的 `memory.c` 日后要复用它时，需要改哪几个文件的包含路径。

7.2 节列了两条设备侧的规定：中断处理结束要发 EOI，PS/2 键盘要取走扫描码才会发下一次中断。用一个主机上的小模型验证这两条各自独立。按下述语义实现 `irq.c`：

- `pic` 有 `bool pending[16]`、`int in_service`、`int delivered`，初始化时 `in_service = -1`。
- `pic_raise(irq)` 置 `pending[irq]`。
- `pic_ack()`：若 `in_service >= 0` 返回 -1；否则取编号最小的 pending 项，清掉它，记入 `in_service`，`delivered` 加 1，返回该编号。
- `pic_eoi(irq)`：若 `in_service == irq`，把它置回 -1。
- 键盘有 `int queued`、`bool data_ready`。`key_press()` 先 `queued++`；若 `data_ready` 为假，置真并向 1 号 IRQ 发请求。
- `key_read()`：若 `data_ready` 为真，`queued--` 并置假。
- `serve(read_data, send_eoi)`：先 `ack`；若拿到 1 号 IRQ，按两个布尔参数决定是否 `key_read` 和 `pic_eoi`。
- `run(name, read_data, send_eoi)`：按三次「按键、处理」循环，最后打印 `delivered` 与 `queued`。

四组参数依次为 `(true, true)`、`(true, false)`、`(false, true)`、`(false, false)`，输出应当如下：

```text
read+eoi  delivered=3 queued=0
read      delivered=1 queued=2
eoi       delivered=1 queued=3
neither   delivered=1 queued=3
```

逐行解释这四个结果。要求分别指出：哪一组被「没发 EOI」卡住，哪一组被「没读扫描码」卡住，为什么 `read` 与 `neither` 的 `delivered` 相同而 `queued` 不同。最后回答：现实中的 PS/2 控制器在数据未取走时，中断线上还会不会继续拉高？

验收：四行输出一致；解释里把 PIC 的 `in_service` 和键盘的 `data_ready` 当成两个独立条件，而不是笼统地说「中断没处理完」。

</Exercise>

7.5 节建议编译器开严格模式。把下面的 `strict.c` 用 `gcc -std=c17 -Wall -Wextra -Wconversion -Werror -c strict.c` 编译，恰好得到三条错误：

```c
#include <stdint.h>

static uint32_t page_directory[1024];

uint16_t low_flags(uint32_t entry) {
    return entry;
}

int sum(const uint16_t *p, int n) {
    int s = 0;
    for (unsigned i = 0; i < n; i++) {
        s += p[i];
    }
    return s;
}

void map_page(uint32_t *table, unsigned index, uint32_t frame, int user,
              int flags) {
    table[index] = (frame & 0xFFFFF000u) | 0x3u;
    if (user) {
        table[index] |= 0x4u;
    }
}

int main(void) {
    uint16_t v[3] = {1, 2, 3};
    map_page(page_directory, 3, 0x12345000u, 1, 0);
    return (low_flags(page_directory[3]) == 0x5007u && sum(v, 3) == 6) ? 0 : 1;
}
```

```text
error: conversion from 'uint32_t' {aka 'unsigned int'} to 'uint16_t' {aka 'short unsigned int'} may change value [-Werror=conversion]
error: comparison of integer expressions of different signedness: 'unsigned int' and 'int' [-Werror=sign-compare]
error: unused parameter 'flags' [-Werror=unused-parameter]
```

(1) 三条都改掉，要求这条命令无输出，且 `low_flags(0x5007u)` 仍返回 `0x5007`、`sum` 对 `{1,2,3}` 仍返回 6。`low_flags` 的形参类型不许改。

(2) 第三条有两种改法：删掉 `flags`，或用 `(void)flags;`。说明哪一种更适合这里，以及如果将来调用方真要传标志位，接口应该怎么改。

(3) 去掉 `-Werror` 只保留 `-Wall -Wextra` 编译：原样跑一次，再在 `main` 里把 `page_directory` 的引用临时删掉跑一次。对比两次的警告条数，说明为什么「变量没被引用」会在后一次里冒出来，而严格模式下的报错条数又为什么与这一次不同。

验收：`-Wconversion -Werror` 下无输出、退出码 0；第 (3) 问给出两次的条数并解释差异来源。

### 8.3 综合与挑战

(1) _[5.4]_ 写一个带 TLB 的分页模拟器 `tlb.c`。页表 1024 项，TLB 8 项，采用轮转替换；`translate` 命中 TLB 时直接返回，未命中则查页表，页表项为 0 表示未映射。按顺序执行并打印：

```text
first     VA 0x00300123 -> PA 0x00100123
stale     VA 0x00300123 -> PA 0x00100123
flushed   VA 0x00300123 -> unmapped
remapped  VA 0x00300123 -> PA 0x00200123
hits=1 misses=3
```

四步依次是：把虚拟页 0x00300000 映射到物理页 0x00100000 并访问；解除映射后不刷新 TLB 再访问；执行刷新后再访问；重新映射到 0x00200000 再访问。结合 7.1 节最后一条，说明第二步为什么仍然返回旧地址，以及真实 CPU 上不刷新会看到什么。

(2) _[4.3]_ 写一个页表开销计算器，按 32 位二级分页计算映射给定物理内存需要的页表页数：页目录 1 页，每 1024 个页表项占 1 页，向上取整。对 1、16、64、128、4096 MiB 各打印一行：

```text
    1 MiB: 32-bit     2 tables      8192 bytes
   16 MiB: 32-bit     5 tables     20480 bytes
   64 MiB: 32-bit    17 tables     69632 bytes
  128 MiB: 32-bit    33 tables    135168 bytes
 4096 MiB: 32-bit  1025 tables   4198400 bytes
```

再用同样方法算 64 位四级分页（PML4、PDPT、PD、PT，每级 512 项）在 64 MiB 下的页数，输出 `64 MiB: 64-bit 35 tables 143360 bytes (4 levels)`。对照 6 节第四条，说明为什么多一级页表会让 64 位系统更难写，而不只是多占几页内存。

(3) _[5.4]_ 7.5 节要求内核严格检查用户态传来的指针。实现并测试 `range_ok`：

```c
#define USER_START 0xB0000000u
#define USER_END 0xB0F00000u

int range_ok(uintptr_t src, size_t len);
```

规则：`src` 为 0 拒绝；`src` 不在 `[USER_START, USER_END)` 内拒绝；`len` 超过 `USER_END - src` 拒绝。对下列七组输入打印 `accepted` 或 `rejected`：
