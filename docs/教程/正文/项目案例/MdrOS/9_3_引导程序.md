# 9.3 引导程序与规范

引导程序（Bootloader）是介于底层主板固件与操作系统内核之间的承上启下之作。它的核心使命在于初始化关键总线与执行模式，探查并收集硬件拓扑与物理内存布局，继而将操作系统的内核映像从持久化存储介质安全地装载入物理内存，最终平稳转交处理器的控制权。

随计算机体系结构的演进，固件与硬件引导方式经历了从传统 BIOS 向现代 UEFI 的结构性升级，由此派生出截然不同的启动路径与磁盘组织规范。

## 1. 硬件固件与引导模型

### 1.1 Legacy BIOS 与 MBR 分区结构

Legacy BIOS 是 x86 个人计算机长期沿用的传统固件接口，广泛存在于早期机型以及现代主板的兼容支持模块（CSM）中。

在 Legacy BIOS 启动模型下，主板固件在完成基础的加电自检后，会按照启动设备序列依次轮询外部存储介质。对于每一个候选设备，BIOS 会读取其第 0 扇区（逻辑 LBA 0，大小为 512 字节）至内存物理地址 `0x7C00` 处。如果该扇区末尾两个字节包含有效的引导签名 `0x55 0xAA`，固件便判定该扇区包含可执行的主引导记录（Master Boot Record，简称 MBR），随即跳转到 `0x7C00` 开始执行其中的引导代码。由于 MBR 需同时容纳引导代码、4 个主分区项（每项 16 字节）与有效签名，留给引导代码的空间不足 446 字节，通常需要多阶段链式跳转才能完成内核的最终载入。

### 1.2 UEFI 固件与 GPT 分区体系

为了打破 MBR 寻址扇区上限（最大仅支持 2 TiB 寻址）以及实模式 16 位寻址的陈旧束缚，现代计算机普遍转向统一可扩展固件接口（UEFI）。与之配套的全局唯一标识分区表（GUID Partition Table，简称 GPT）将磁盘容量寻址上限拓展至 18 EB，并提供了主备双分区表与 CRC32 完整性校验机制。

UEFI 固件摆脱了对固定磁盘物理扇区代码的依赖，转而原生解析 FAT32 文件系统。固件从外部存储器的 EFI 分区中的以下路径 `EFI\BOOT` 根据计算机的架构去加载指定引导文件：

- 64 位计算机加载 `BOOTX64.efi`
- 32 位计算机加载 `BOOTIA32.efi`

UEFI 运行在处理器原生位宽下，提供丰富的引导期服务（Boot Services）与运行时服务（Runtime Services），在安全性上支持安全启动（Secure Boot），杜绝了传统 MBR 扇区易被恶意软件静默篡改的隐患。

## 2. 选择引导方式

在实际内核开发中，手动从实模式汇编编写一套支持复杂文件系统解析与内核重定位的引导程序耗时耗力。借助成熟的通用引导规范与现成引导程序，能够将注意力聚焦于内核本身的架构设计与核心组件实现。

### 2.1 Multiboot

Multiboot 规范是一个开放标准，它为内核提供了一种统一的方式，可以由符合 Multiboot 的引导加载程序引导。符合 Multiboot 规范的内核只需在编译出的映像前 8192 字节内嵌入一段特定的 Multiboot 头部结构，便能由 GRUB 等通用引导器直接识别。Multiboot 规范的参考实现由 GRUB 提供，著名的 Xen 虚拟机监视器就是使用的 Multiboot 引导。

在引导过程中，GRUB 会自动将 CPU 从实模式切换到 32 位保护模式，屏蔽底层 A20 地址线的细微差异，将内存信息、模块地址和命令行参数以标准结构体传入 `EBX` 寄存器。

### 2.2 Limine

Limine 是一个先进的、可移植的、多协议的引导加载程序，支持 Linux、原生 Limine 引导协议以及 multiboot1 和 2。Limine 非常适合作为一些自制操作系统的引导程序。

相比传统协议，Limine 原生协议专为 x86_64 等现代 64 位平台量身定制，通过结构体请求（Feature Request）机制，按需为内核提供高级特性：如直接建立高半核（Higher-half Kernel）虚拟映射、提供线性帧缓冲区（Framebuffer）信息、解析 ACPI RSDP 指针等，极大简化了 64 位长模式内核的自举负担。

开发者可依据目标平台的位宽与引导形态灵活选择。

1.1 节说 BIOS 把引导设备的第一个扇区读到内存并运行，这个扇区只有 512 字节，最后两字节必须是 `55 AA`。用 nasm 写一个最小的引导扇区 `boot.asm`，逐步验证这条约束。骨架如下：

```asm
BITS 16
ORG 0x7C00
start:
    xor ax, ax
    mov ds, ax
    mov si, msg
next:
    lodsb
    test al, al
    jz halt
    mov ah, 0x0E
    mov bx, 0x0007
    int 0x10
    jmp next
halt:
    hlt
    jmp halt
msg: db "boot ok", 0
times 510 - ($ - $$) db 0
dw 0xAA55
```

(1) `nasm -f bin boot.asm -o boot.bin` 之后用 `wc -c boot.bin` 确认是 512 字节，用 `od -A x -t x1 -j 0x1F0 -N 16 boot.bin` 确认末两字节是 `55 aa`。

(2) 删掉 `ORG 0x7C00` 重新汇编，用 `ndisasm -b 16 boot.bin` 看 `mov si, ...` 那条指令。两次的立即数分别是 `0x7C18` 和 `0x0018`。说明哪一个是对的，为什么错了的那一个在真机上会打印乱码或什么都不打印。提示：BIOS 把扇区装到物理地址 0x7C00，而 `ORG` 只影响汇编器算出的地址。

(3) 在 `start` 后面插入 `times 600 db 0x90` 再汇编。记录报错原文，并说明为什么 `times 510 - ($ - $$)` 会变成负数。

(4) 没有真机或虚拟机时，怎么确认这段代码的指令序列是对的？给出一种只靠 `ndisasm`，或 `objdump -D -b binary -m i8086 -M intel --adjust-vma=0x7C00` 的检查办法，并写出你实际看到的头四条指令。

验收：三组产物的字节数、末两字节、反汇编立即数都贴出来；第 (3) 问的报错是原文，不是转述。

(2) _[4.4]_ 写一个程序生成 1536 字节的 `disk.img`：第 0 扇区是保护性 MBR，第 1 扇区是 GPT 头，第 2 扇区留空。保护性 MBR 在 `0x1BE` 的类型填 `0xEE`、起始 LBA 填 1、扇区数填 `0x200000`，末两字节 `55 AA`。GPT 头按规范填：偏移 0 写 `EFI PART`，偏移 8 写 `0x00010000`，偏移 12 写头长度 92，偏移 24 写当前 LBA 1，偏移 32 写备份 LBA `0x1FFFFF`，偏移 40 写首个可用 LBA 34，偏移 48 写末个可用 LBA `0x1FFFDE`（总扇区数减 34），偏移 72 写分区项数组起始 LBA 2，偏移 80 写项数 128，偏移 84 写单项大小 128，其余为 0。
