# 9.8 多任务

是操作系统实现的必要功能，多任务部分负责创建/销毁/调度进程 or 线程

> 无论是宏内核还是微内核，其内核都必须具备多任务调度的机制

## 1. 系统进程

是运行在`R0` 特权级的进程，一般这类进程为 IDLE 进程，系统服务进程，拥有 PC 的最高操作权限

> IDLE 进程 \
> 是操作系统第一个创建的进程，唯一一个不通过`fork()`函数复制得来的进程，其 PID 为`0` \
> 该进程的调度优先级为最低，一般在调度队列为空时调度该进程 \
> 操作系统的初始化等工作由该进程完成 (在多核中由 CPU0 的 IDLE 进程完成，且有几个 CPU 核心就有几个 IDLE 进程) \
> 在操作系统内核初始化完成后该进程并不会销毁，而是循环执行`hlt`以降低 CPU 功耗

## 2. 用户进程

运行在 `R3` 特权级的进程，一般这类进程为应用程序的进程，只能访问特定内存区域且无法执行特权级指令 (如`hlt` `sti` `lgdt`等)

- 在 x86 平台下，CPU 无法从`R3`特权级直接切换到`R0`, 同时`R0`也无法直接切换至`R3`, 所以在 x86 中从`R0`切换至`R3`的常用方式是使用
  `iret`指令跳转
- 涉及特权级切换时，内核必须配置 TSS(Task State Segment : 任务状态段), 该结构是`GDT`的一个段描述符
- 每个用户进程会在内核有一块单独的栈，该栈用于用户进程系统调用时候存储`R0`特权级执行时产生的各种数据

> 在 CP_Kernel 内核中，用户进程在刚创建时是 R0 特权级，这时候内核会往该进程的栈中插入一个名为`switch_to_user_mode`
> 的函数并传入真正的用户程序入口地址 \
> `switch_to_user_mode`函数负责初始化进入`R3`前各种寄存器的值 \
> 最后使用`iret`指令跳转到用户程序入口地址，这个时候就切换至`R3`特权级了

### 2.1 TSS

任务状态段，负责存储一个任务的当前 CPU 状态，其包含了 CPU 所有的寄存器 (控制寄存器以及 GDTR IDTR 除外).
是旧版 x86 平台用于任务切换的一个数据结构。

在现代操作系统中并不会使用该数据结构去进行任务调度，因为 PCB(Process Control Block : 进程控制块) 取代了它。
PCB 相比 TSS 拥有更快的任务切换速度，且可以自定义多种进程私有的数据结构 (如 PID TTY 设备映射 调度时间片计数等)。

> 但这并不代表不需要配置 TSS, TSS 的作用仅限于切换内核栈地址

## 3. 任务调度

任务调度有很多方式，内核会使用合理的方式分配给这些任务一定的 CPU 时间片，一旦过了该任务的 CPU 时间片就会触发该任务调度。

一个好的任务调度器可以大幅度提高应用程序的运行速度，提高硬件资源的利用效率

进程切换过程中，需要切换的寄存器可以参考 TSS 的结构。

## 4. 补充

- 进程间的资源隔离 \
  因为不同的进程之间页目录不同，拥有不同的内存布局，不同进程间相同的线性地址指向的是不同的物理地址 \
  因此该地址获取的数据也不同

- 线程与进程的区别 \
  所以线程之间的资源可以共享，而进程因为切换了页表 (内存布局被切换), 所以资源不共享

## 5. 习题

这一页讲了三个层次：特权级（R0 与 R3 怎么切换）、进程的描述结构（TSS 与 PCB 的分工）、以及调度（时间片与上下文切换）。真机上验证这些要写引导程序和中断存根，代价太大；下面四道题把它们搬到主机上，用结构体和数组模拟 CPU 状态，照样练到切换路径上的每个细节。前两道读结构与算栈布局，后两道写能跑的调度器和地址空间隔离实验。

### 5.2 编程

<Exercise id="50048" :d="4" :w="4">

实现一个带睡眠与退出的轮转调度器：

- 4 个任务，`pid` 0～3，时间片分别为 1、2、2、3 个 tick；`pid 0` 是 IDLE，统计时单独标出；
- 每个 tick 开始时先唤醒睡眠到期的任务，醒来时间片重新计满；
- 当前任务可运行且时间片未用完就继续，否则沿环按 `pid` 递增找下一个可运行任务；
- 睡眠与退出由脚本触发：tick 2 结束时 `pid 1` 睡 4 个 tick，tick 4 结束时 `pid 2` 退出，tick 7 结束时 `pid 3` 睡 2 个 tick；
- 整轮只剩 IDLE 时继续执行 IDLE，不空转。

要求：

(1) 先手算 15 个 tick 的执行序列，写进报告。

(2) 实现并运行，打印每个 tick 运行的 `pid`，最后打印每个任务累计的 tick 数与切换次数。

(3) 手算结果与程序输出必须一致。实测序列为 `0 1 1 2 2 3 3 3 0 1 1 3 3 3 0`，累计 `3 4 2 6`，切换 8 次。对不上时先查「唤醒发生在选择下一个任务之前还是之后」，这是最常见的分歧点。

(4) 把 `pid 0` 的时间片改成 3 重跑，说明序列与切换次数各变成什么（实测为 `0 0 0 2 2 3 3 3 0 0 0 1 1 3 3`、5 次切换）。为什么 IDLE 的时间片会影响其他任务的响应时间？

(5) 退出时如果只把任务标成 `DEAD` 而不从环上摘掉，`next` 指针会怎样？给出一个会在这个实现里触发的死循环路径，并说明 `code/项目/mdrOS/task.c` 的 `task_kill` 里 `last->next = argv->next` 那一行为什么不能省。

(6) `code/项目/mdrOS/task.c` 里的 `schedule` 在 `io_cli()` 之后才读 `current`，`task_kill` 也在关中断的状态下改链表。说明为什么两者的改动必须在同一个关中断区间里完成，多核下还需要什么。

验收：第 (3) 问的序列、累计数、切换次数三项全部吻合；第 (5) 问给出的死循环路径能用改坏的代码复现。
