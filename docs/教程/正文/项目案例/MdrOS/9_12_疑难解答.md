# 9.12 典型异常排查与故障分诊指南

在操作系统内核自举与初始化的探索过程中，由于缺乏用户态那样成熟的调试器、符号回溯与核心转储支持，开发者常常面临“系统静默挂起”或“屏幕闪退黑屏后物理机瞬时冷重启”的严峻调试挑战。

这类看似毫无线索的灾难性故障，背后都有其严密的硬件状态机与异常级联逻辑。掌握 x86 体系结构下各类底层硬件异常的触发机理、提取关键控制寄存器的状态镜像，并建立自顶向下的分诊排查路径，是保证内核工程稳步推进的核心能力。

## 1. 虚拟机 / 实体机突然重启

当虚拟机或真实物理机在引导过程中未输出任何报警信息便瞬间发生黑屏重启时，在硬件底层几乎必然触发了**三重错误（Triple Fault）**。

在 x86 架构中，三重错误意味着异常分发体系自身的彻底崩溃。当遭遇此类问题时，应当沿着硬件异常捕获路径逐层反查：
- **IDT 描述符表的就绪状态**：确认内核是否已执行 `lidt` 指令加载中断描述符表；IDTR 寄存器中的基地址是否按 8 字节对齐且限长（Limit）是否足够覆盖 256 个向量；
- **异常门描述符的空缺与有效性**：当发生常规硬件异常时，CPU 查询 IDT 对应项，若该表项为空、存在位（Present）为 0 或选择子指向非法段，硬件无法完成跳转，将立即升级为 8 号双重错误（Double Fault）；
- **双重错误处理例程的健壮性**：若连 8 号异常的处理入口也无法正常执行（例如栈指针越界或页目录走查失败），CPU 硬件控制器将判定系统陷入死锁，主动向总线发出关机引脚信号强制主板复位。

## 2. DoubleFault 异常（#DF，向量 8）

双重错误发生在 CPU 尝试调用前一个异常的处理程序期间再次触发了另一个无法协同的次级异常。这通常意味着内核的执行基础设施已经出现局部破坏。

排查与处理双重错误的工程原则包括：
- **抓取原发异常的现场**：双重错误本身往往只是次生灾害，必须设法反查并记录引发连锁反应的第一现场向量号与错误码；
- **清查通用异常存根的缺陷**：检查常规中断入口是否存在栈对齐偏差、错误码弹出顺序颠倒等汇编错误；
- **预留专用自救执行环境**：双重错误发生时，原有的执行栈与内存环境通常已被破坏，常规异常处理程序极易再次崩溃引发三重错误。

::: warning 双重错误处理的防御性隔离准则

处理 #DF 时，必须假设当前上下文已处于高度不可靠状态：

- **设立独立的专属栈区**：在内核静态数据区开辟一块不小于 1 KiB 的专用栈（如 `df_stack`），并在 #DF 汇编存根入口处第一时间将 `esp`/`rsp` 指针强制重定向至该安全栈顶；
- **切换到恒等映射的安全页表**：若启用了虚拟分页，应准备一套仅映射基础运行环境的专用应急页表，发生双重错误时主动切入，规避因原页表损坏造成的走查崩溃；
- **收敛行为至现场转储与停机**：在双重错误处理函数内部，仅执行最关键的寄存器转储与屏幕/串口日志输出，切勿尝试调用睡眠、互斥锁或复杂格式化输出等高风险例程，输出完毕后立即执行 `cli; hlt` 挂起系统。

:::

## 3. PageFault（#PF，向量 14）

缺页异常是分页式虚拟内存系统中最常见也最关键的硬件异常。诊断缺页异常的核心依据是控制寄存器 `CR2`（硬件自动填入引发缺页的线性虚拟地址）以及栈上压入的 32 位**缺页错误码（PF Error Code）**。

### 3.1 NotPresent 场景分析

当错误码的 P 位（位 0）为 0 时，表明 CPU 访问了一个在页表项中标记为不存在（Present=0）的线性地址：
- **空指针解引用**：若 `CR2` 中记录的地址恰好为 `0x00000000`，或处于非常小的偏移范围（例如结构体基址为 NULL 时访问其字段，导致地址处于前几百字节），明确指示程序中发生了空指针解引用；
- **合法按需换页（Demand Paging）**：若 `CR2` 落在应用程序堆或栈的合法扩展区间内，且该区间由内核虚拟内存管理结构记录，此时该缺页属于正常系统行为，内核应当为其动态分配物理页框、填入页表项并刷新 TLB，随后恢复指令执行；
- **走查越界与执行流失控**：若 `CR2` 呈现出不可理喻的野指针数值，通常说明内核执行流或栈帧被破坏，函数返回地址被脏数据覆盖导致指令指针取指跑飞。

::: warning 执行流失控预警

当 `CR2` 频繁出现无法对应到任何已知符号或数据区间的离散地址时，重点排查缓冲区溢出、栈平衡破坏以及未初始化函数指针的调用。

:::

### 3.2 UserMode 特权违规

当错误码的 U 位（位 2）为 1、P 位（位 0）为 1 时，表示当前运行在 Ring 3 特权级的用户态程序企图读取或写入一个被页表项标记为特权级（Supervisor-only，U/S 位为 0）的内核空间内存。内核必须拦截该行为并向对应进程投递段错误信号。

## 4. GeneralProtectionFault（#GP，向量 13）

通用保护异常是 x86 体系中用于捕获所有未被其他专用异常覆盖的保护性违规：

- **非法或未就绪硬件访问**：在未完成设备 BAR 基址映射或外设总线未使能时，直接向设备 MMIO 地址执行非法对齐读写；
- **上下文切换寄存器损坏**：在任务调度执行上下文保存与恢复时，若从损坏的栈上弹出了非法的段选择子（如段索引超出 GDT 范围或段描述符存在位为 0）；
- **控制寄存器非法置位**：向控制寄存器（如 `CR0`、`CR4`）写入了保留位组合，或者在不支持的硬件上尝试启用扩展机制；
- **对齐违规**：现代 SIMD 向量指令（如 SSE/AVX）对操作数内存地址通常要求 16 字节或 32 字节严格对齐，访问未对齐的局部对象将直接引发 #GP。

## 5. InvalidOpcode（#UD，向量 6）

非法操作码异常发生在 CPU 指令译码阶段，当执行单元遇到无法识别的机器指令字节序列时触发：

- **数据段被误当代码执行**：程序计数器 EIP 错误跃迁至纯数据段、BSS 区或已被释放的内存块，将任意数据当成指令进行译码；
- **指令集架构不匹配**：编译工具链开启了当前物理 CPU 并不支持的高级扩展指令集（如在老旧核心或极简虚拟机上执行了 AVX 指令）；
- **扩展指令未在控制寄存器使能**：部分处理器指令虽然硬件支持，但处于默认禁用状态，必须由内核显式配置控制寄存器（如开启 `CR4.OSFXSR` 与 `CR4.OSXMMEXCPT` 支持 SSE 异常）；
- **快速系统调用未激活**：64 位下的 `syscall` 指令依赖于对扩展特性 MSR（如 `EFER.SCE` 位）的预先配置。在多处理器体系下，若主核心使能而从核心未使能，从核心执行系统调用时便会触发 #UD。

## 6. 部分实体机跑不起来我的 OS

在模拟器（如 QEMU、Bochs）中稳定运行的内核，在真实物理主板上启动却频遭卡死，这一现象广泛存在于自制内核开发中。这是由于虚拟机往往对非标准硬件行为有较高的宽容度，且启动时内存大多预先清零。

而在异构的真实物理机上：
- **固件行为与硬件拓扑差异**：不同主板制造商对规范的理解与非标准保留区的设置各异，绝不可盲目假设未初始化内存包含特定初值；
- **避免硬编码物理基地址**：切勿在源码中写死任何外设基址、帧缓冲地址或内存界限。所有硬件基址均应依托标准总线协议（如通过 ACPI 静态表解析 MADT/FADT、通过 PCI 枚举读取 BAR、通过引导器获取内存映射图）动态探查并验证其合法性后再行使用。

::: warning 物理机兼容性防线

凡是能够通过标准协议（ACPI、Multiboot/Limine 内存映射表、PCI 配置空间）动态获取的硬件资源，一律禁止硬编码为静态常量。系统必须防御性地假定任何特定物理地址均有可能已被硬件固件或总线控制器所保留。

:::
