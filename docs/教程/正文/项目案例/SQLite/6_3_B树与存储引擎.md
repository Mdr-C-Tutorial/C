# 6.3 源码阅读：SQLite B 树与存储引擎

SQLite 最为人称道的工程特质之一，便是“单文件承载整个数据库”。不管是庞大的数据表、复杂的二级索引，还是并发事务下的原子回滚与崩溃恢复，所有持久化状态最终都会自洽地收敛在一个普通的操作系统文件里。

在单文件容器的内部，SQLite 构建了一套层次分明、职责明确的存储引擎架构。本节将自顶向下层层拆解这套存储体系：首先是由 B 树负责的逻辑记录索引与导航；中间是由 Pager 层维护的页缓存（Page Cache）与原子事务安全；底层则是配合 WAL 模块实现的高性能并发读写机制。

> 源码仓库：<https://sqlite.org/src>，Public Domain。本文基于 SQLite 3.46 版本。

## 1. 存储栈

SQLite 的存储子系统遵循严密的分层架构，每一层仅通过明确定义的抽象接口与紧邻的下层进行交互：

```
┌─────────────────────────────────┐
│         B-tree 层               │  组织数据：查找、插入、删除、遍历
│   btree.c / btreeInt.h          │
├─────────────────────────────────┤
│         Pager 层                │  页缓存 + 事务安全
│   pager.c                       │
├─────────────────────────────────┤
│         OS 层 (VFS)             │  文件读写、锁、同步
│   os_unix.c / os_win.c         │
└─────────────────────────────────┘
```

各层之间的协作边界异常清晰：
- **B-tree 层**把数据库视作由固定大小的“页面”拼装而成的树状索引。当它需要读取某页时，调用 `sqlite3PagerGet()`；当它需要修改页内数据时，调用 `sqlite3PagerWrite()` 申请标记脏页。B 树完全不关心页面最终如何落盘，也不处理底层的文件锁与崩溃恢复。
- **Pager 层**把数据库视作一个由页号索引的页缓存池。它并不理解页内具体存放的是 B 树的键、指针还是单元格记录，只专注于维护页面的脏状态、事务生命周期以及写日志（Journal/WAL）的先后时序，确保在任何断电突发场景下数据都能回滚到一致状态。
- **OS 层（VFS）**则负责抹平不同操作系统间系统调用的差异，直接对物理文件实施读写、加锁与 `fsync` 刷盘。

在启用预写日志（WAL）模式时，Pager 会与 WAL 模块协同运作：写入操作产生的脏页会按顺序追加到独立的 WAL 文件中，主数据库文件在事务提交前保持原样；而当上层请求某一页时，WAL 模块会判定应从 WAL 文件拉取最新的修改帧，还是直接从主数据库文件读取基准页。

## 2. 页式存储

::: concept page-storage title="页式存储"

在物理层面上，整个 SQLite 数据库文件被严格划分为等长大小的数据块，称为**页**（Page）。在现代版本中，默认页大小通常为 4096 字节（且必须是 512 到 65536 之间 2 的幂次方）。

所有逻辑构件——不管是 B 树的内部寻址节点、叶节点单元格、超长记录的溢出链，还是未使用的空闲页链表——最终都规整地存放在这些页内。页号从 1 开始顺序编号（0 代表无效页号或空指针）。其中，**第 1 页**具有特殊的全局地位，其开头的 100 个字节被固定保留为整座数据库的文件头元数据：

```
OFFSET   SIZE    DESCRIPTION
  0       16     魔数: "SQLite format 3\000"
 16        2     页大小 (字节)
 24        4     文件更改计数器
 28        4     数据库总页数
 32        4     第一个空闲链表页
 40       60     15 个 4 字节的元数据
```

页大小在数据库初次创建并写入文件头后便被固化，后续读写都严格以此为对齐边界。

:::

在内核中，`BtShared` 结构体代表一个打开的 B 树存储实例，由属于同一物理文件的多个逻辑连接共享。它直接持有底层 Pager 的指针以及常驻内存的第 1 页句柄：

```c
struct BtShared {
  Pager *pPager;        /* 页缓存 */
  MemPage *pPage1;      /* 数据库第 1 页 */
  BtCursor *pCursor;    /* 所有打开的游标链表 */
  u32 pageSize;         /* 页大小 (字节) */
  u32 usableSize;       /* 每页可用字节数 */
  u16 maxLocal;         /* 索引 B 树的最大本地负载 */
  u16 minLocal;         /* 索引 B 树的最小本地负载 */
  u16 maxLeaf;          /* 表 B 树的最大本地负载 */
  u16 minLeaf;          /* 表 B 树的最小本地负载 */
  // ...
};
```

这里有一个不可忽视的字段：`usableSize = pageSize - nReserve`。SQLite 允许在每个页面的最末尾保留若干字节（`nReserve`）供第三方扩展使用（例如透明页面加密扩展）。因此，B 树层在计算页面内部剩余空间、分裂阈值以及单元格尺寸时，必须一律以 `usableSize` 为基准。

## 3. 两种 B 树

::: concept btree-types title="Table B-tree 与 Index B-tree"

在 SQLite 内部，数据库中的每一张数据表和每一个用户索引，都分别对应一棵完全独立的 B 树。它们虽然混杂在同一个物理文件中分配页面，但通过系统表 `sqlite_schema` 中登记的各自根页号（Root Page）完全隔离。

SQLite 针对数据存储和索引检索的差异，划分了两种形态的 B 树：

| 类型 | 键 | 数据 | 用途 |
|:---|:---|:---|:---|
| Table B-tree | 64 位整数（rowid） | 存放于叶节点 | 存储普通表的数据行记录 |
| Index B-tree | 任意长度的二进制有效载荷 | 无数据负载（键即完整信息） | 存储用户创建的索引键 |

在源码实现中，这两类 B 树并不依赖不同的结构体，而是通过页头中的标志位组合来明确其节点属性：

```c
#define PTF_INTKEY    0x01   /* 键是整数 */
#define PTF_ZERODATA  0x02   /* 无数据，只有键 */
#define PTF_LEAFDATA  0x04   /* 数据只存在叶节点 */
#define PTF_LEAF      0x08   /* 叶节点（无子页指针） */
```

Table B-tree 节点的页标志是 `PTF_INTKEY | PTF_LEAFDATA | PTF_LEAF`（叶节点）或 `PTF_INTKEY | PTF_LEAFDATA`（内部索引节点）。而 Index B-tree 节点的标志则是 `PTF_ZERODATA | PTF_LEAF`（叶节点）或 `PTF_ZERODATA`（内部节点）。

:::

::: generate btree-vs-bplus kind=comparison concepts=btree-types

面向有数据结构基础的 C 程序员，比较经典 B 树和 SQLite 的 B+ 树变体：经典 B 树在每个节点都存数据，而 SQLite 的 Table B-tree 只在叶节点存数据、内部节点只存键和子指针（这正是 B+ 树的特征）；但 Index B-tree 在每个节点都存键且无额外数据，更接近经典 B 树。指出 SQLite 根据用途选择不同变体是一个务实的工程决策。

:::

## 4. 页面格式

物理页面的内部布局是存储引擎最富巧思的环节之一。为了在单页内高效容纳大量变长记录并支持高速二分检索，SQLite 采用了经典的**槽式页面**（Slotted Page）架构。

::: concept page-format title="B 树页面的内部布局"

在内存与磁盘中，每个 B 树页面都由四个区域首尾相接地拼装而成。从低地址向高地址看，整体布局如下：

```
|----------------|
| 页头           |   叶节点 8 字节，内部节点 12 字节
|----------------|
| 单元格指针数组  |   每个 2 字节，按键排序，向下增长
|                |         ↓
|----------------|
| 未分配空间      |
|----------------|         ↑
| 单元格内容区    |   存放实际数据，向上增长，顺序任意
|                |
|----------------|
```

位于页面顶端的页头结构记录了该页面的关键几何尺寸：

```
OFFSET   SIZE     DESCRIPTION
  0       1      标志位 (PTF_INTKEY, PTF_LEAF 等)
  1       2      第一个空闲块的偏移
  3       2      本页单元格数量
  5       2      单元格内容区起始位置
  7       1      碎片字节总数
  8       4      最右子页指针 (仅内部节点)
```

这种布局的精妙之处在于**逻辑排序与物理存储解耦**。单元格指针数组（Cell Pointer Array）中的每个 2 字节指针都严格按照键的大小有序排列；但指针所指向的单元格真实数据，则是从页面最底端向上按需追加的。

当向页面中插入一条新记录时，存储引擎完全不需要搬移已有的庞大行数据，只需在顶部的指针数组中腾出 2 字节插入新偏移，并将实际数据塞入底部剩余空间即可。页内查找时，二分算法只在连续紧凑的 2 字节指针数组上快速寻址，兼顾了极高的插入效率与内存局部性。

:::

当物理页面被加载进内存后，SQLite 使用 `MemPage` 结构体来管理该页在内存中的运行时视图：

```c
struct MemPage {
  u8 isInit;           /* 是否已初始化 */
  u8 intKey;           /* True: table b-tree; False: index b-tree */
  u8 intKeyLeaf;       /* True: intkey 表的叶节点 */
  u8 leaf;             /* True: 叶节点 */
  u8 hdrOffset;        /* 页头偏移 (第 1 页为 100，其他为 0) */
  u8 childPtrSize;     /* leaf ? 0 : 4 */
  u16 nCell;           /* 本页单元格数量 */
  u16 cellOffset;      /* 单元格指针数组在 aData 中的偏移 */
  int nFree;           /* 空闲字节数 */
  u8 *aData;           /* 指向页面原始数据 */
  u8 *aCellIdx;        /* 单元格指针数组起始位置 */
  BtShared *pBt;       /* 所属的 BtShared */
  DbPage *pDbPage;     /* Pager 层的页面句柄 */
  // ...
};
```

这里 `hdrOffset` 字段精准映射了前文提到的特殊设计：对于普通数据页，页头从字节 0 处起始；而对于整座数据库的第 1 页，由于前 100 字节被全局文件头占据，B 树页头便顺延从偏移 100 处开始解析。

每个单元格（Cell）内部装载着一条完整的索引项或表记录：内部节点的单元格包含 4 字节的左子页号与分隔键；而叶节点的单元格则包含变长编码的键值、实际列数据以及在数据过长时指向的溢出页链表指针。这里的整数和长度广泛采用 SQLite 自研的 Varint 变长编码（最高位作为延续标志，最多 9 字节即可无损表达 64 位无符号整数），极大压榨了磁盘空间的有效载荷。

## 5. BtCursor：定位迭代器

在 B 树之上，所有上层子系统（包括 VDBE 的字节码指令）都必须通过**游标**（`BtCursor`）来感知和操纵底层记录。游标不仅是一个指向某页某单元格的指针，它完整封装了一次树遍历会话的上下文状态。

```c
struct BtCursor {
  u8 eState;            /* CURSOR_VALID, CURSOR_INVALID 等 */
  Btree *pBtree;        /* 所属连接 */
  BtShared *pBt;        /* 所属文件 */
  Pgno pgnoRoot;        /* B 树根页号 */
  i64 nKey;             /* 最后访问的整数键 */
  CellInfo info;        /* 当前单元格的解析结果 */
  MemPage *pPage;                        /* 当前页 */
  MemPage *apPage[BTCURSOR_MAX_DEPTH-1]; /* 祖先页栈 */
  u16 ix;               /* 当前页中的单元格索引 */
  u16 aiIdx[BTCURSOR_MAX_DEPTH-1];       /* 祖先页中的索引 */
  i8 iPage;             /* apPage 栈的当前深度 */
  // ...
};
```

这里展现了一个极具启发性的存储系统设计考量：在经典数据结构教材中，树节点往往包含指向父节点的指针。但若在物理磁盘页中固化“父页号”，一旦树发生分裂或再平衡，就会触发灾难性的级联修改——更新父节点会导致所有子节点的反向指针失效，造成大量无谓的脏页刷盘。

SQLite 的物理页面**完全不包含任何指向父页面的指针**。取而代之的是，游标在内存中维护了一组由当前路径构成的祖先调用栈（`apPage[]` 与 `aiIdx[]`）。当游标自顶向下遍历时，沿途访问的父级页面指针与槽位索引会被依次压入栈中。当需要向上回溯（例如跨页步进或触发分裂）时，调用 `moveToParent` 仅是一次纯内存的 $O(1)$ 出栈操作，彻底解除了物理页对父级元数据的耦合。

### 5.1 定位：sqlite3BtreeTableMoveto

在 Table B-tree 中依据整型 rowid 定位记录的核心函数是 `sqlite3BtreeTableMoveto`。它从树的根页出发，逐层向下执行页内二分：

```c
int sqlite3BtreeTableMoveto(BtCursor *pCur, i64 intKey,
                            int biasRight, int *pRes) {
  // 优化 1：若游标已然精准停留在目标键上，直接返回
  if( pCur->eState==CURSOR_VALID && (pCur->curFlags & BTCF_ValidNKey)!=0 ){
    if( pCur->info.nKey==intKey ){
      *pRes = 0;
      return SQLITE_OK;
    }
    // 优化 2：若目标键恰好是当前键 +1（顺序追加的典型场景），尝试单步步进
    if( pCur->info.nKey+1==intKey ){
      rc = sqlite3BtreeNext(pCur, 0);
      // ...
    }
  }

  rc = moveToRoot(pCur);  // 回到根页重新下潜
  for(;;){
    MemPage *pPage = pCur->pPage;
    int lwr = 0, upr = pPage->nCell - 1;

    // 页内二分搜索指针数组
    for(;;){
      int idx = (lwr + upr) / 2;
      i64 nCellKey;
      pCell = findCellPastPtr(pPage, idx);
      // 表 B 树的叶节点单元格需要跳过负载长度 varint 才能读到 rowid
      getVarint(pCell, (u64*)&nCellKey);

      if( nCellKey < intKey )      lwr = idx + 1;
      else if( nCellKey > intKey ) upr = idx - 1;
      else {
        if( !pPage->leaf ){ lwr = idx; break; } // 内部节点仅存分隔键，进入左子树
        *pRes = 0; return SQLITE_OK;             // 叶节点命中目标
      }

      if( lwr > upr ) break;  // 当前页未找到精确匹配
    }
    if( pPage->leaf ) break;          // 已达叶节点，搜索结束
    moveToChild(pCur, childPageNo);   // 压栈并下潜到子页
  }
}
```

该函数融入了两处价值极高的工程特化：
1. **位置缓存快检**：若游标当前指向的单元格键恰好等于目标键，无需任何遍历，直接返回成功。
2. **递增追加旁路**：在自增主键的大批量插入场景中，下一个待写入的键往往正是 `当前键 + 1`。SQLite 会优先尝试调用轻量的 `sqlite3BtreeNext()` 向后探一步；若命中，便完全绕过了自根节点层层下潜的整套对数开销。

### 5.2 步进：sqlite3BtreeNext

当执行全表扫描或范围查询时，`sqlite3BtreeNext()` 负责将游标推向物理拓扑中的下一条连续记录：

```c
int sqlite3BtreeNext(BtCursor *pCur, int flags){
  MemPage *pPage;
  pCur->info.nSize = 0;
  pCur->curFlags &= ~(BTCF_ValidNKey|BTCF_ValidOvfl);
  if( pCur->eState!=CURSOR_VALID ) return btreeNext(pCur);
  pPage = pCur->pPage;
  if( (++pCur->ix) >= pPage->nCell ){
    pCur->ix--;
    return btreeNext(pCur);  // 慢路径：当前页已读完，需跨页回溯
  }
  if( pPage->leaf ){
    return SQLITE_OK;         // 快路径：叶节点内递增单元格索引
  }else{
    return moveToLeftmost(pCur); // 内部节点：进入子树最左侧叶
  }
}
```

这里清晰地体现了快慢路径分离的优化哲学：
- **快路径**：绝大多数连续步进都发生在一个包含数十或上百个单元格的叶页面内部。此时仅需将局部索引 `ix` 自增 1，验证未超限后立即返回 `SQLITE_OK`，整个过程不过区区几条汇编指令。
- **慢路径**：当当前叶页面的单元格全部耗尽时，才回退触发复杂的 `btreeNext()`。它依靠游标内置的 `apPage[]` 祖先栈逐级向上回退到父节点，再转向右兄弟分支下探到新子树的最左叶节点（即标准 B 树的中序遍历）。直到回溯至根节点且再无可遍历分支时，向上返回 `SQLITE_DONE`。

## 6. 插入与分裂

数据写入最终通过 `sqlite3BtreeInsert()` 完成。它接收一个 `BtreePayload` 对象（打包了行记录或索引键），将其压入游标当前所指向的树位置：

```c
int sqlite3BtreeInsert(
  BtCursor *pCur,
  const BtreePayload *pX,  /* 要插入的行数据 */
  int flags,
  int seekResult
){
  // 1. 若当前存在多个并发游标，预先保存它们的位置（避免树形态调整后失效）
  if( pCur->curFlags & BTCF_Multiple ){
    saveAllCursors(p->pBt, pCur->pgnoRoot, pCur);
  }

  // 2. 原地覆盖优化：若为 table b-tree 且键已存在，且新旧数据长度完全一致
  if( pCur->info.nPayload == newPayloadSize ){
    return btreeOverwriteCell(pCur, pX);
  }

  // 3. 组装新单元格，插入当前页面的槽位数组
  // 4. 若当前页面空间耗尽发生溢出，触发再平衡
  rc = balance(pCur);
}
```

这里展现了一处针对更新操作的深度优化：当业务执行 `UPDATE` 修改某一行、且新旧数据的序列化字节数恰好相等时，底层会直接执行 `btreeOverwriteCell()` 原地覆写页面对应区间。这彻底免除了“删除旧单元格、插入新单元格、可能引爆页面分裂”的一连串繁琐连锁反应。

### 6.2 balance()：再平衡与三路调度

当向页面插入单元格导致未分配空间不足，或者因删除记录导致页内空闲空间超过可用大小的 $2/3$ 时，引擎会调用 `balance()` 实施再平衡。由于底层的变动可能向上蔓延导致父级节点同样超限，`balance()` 在实现上是一个依托游标祖先栈逐级向上追溯的驱动循环：

```c
static int balance(BtCursor *pCur){
  do {
    MemPage *pPage = pCur->pPage;

    // 终止条件：既无溢出单元格，且页内空闲空间尚未超过 2/3
    if( pPage->nOverflow==0
     && pPage->nFree*3 <= (int)pCur->pBt->usableSize*2 ){
      break;
    }

    if( pCur->iPage==0 ){
      // 场景 1：根节点溢出 → balance_deeper()：向下分裂，根节点拔高
      rc = balance_deeper(pPage, &pCur->apPage[1]);
    }else{
      if( /* 快速路径条件：intkey 叶节点且溢出发生在末尾 */ ){
        // 场景 2：顺序追加快速路径 → balance_quick()：直接开辟新右兄弟页
        rc = balance_quick(pParent, pPage, aBalanceQuickSpace);
      }else{
        // 场景 3：通用路径 → balance_nonroot()：在当前页与最多 2 个兄弟页间重平衡
        rc = balance_nonroot(pParent, iIdx, ...);
      }
    }
    // 游标出栈退回父节点，在下一轮循环中检查父节点是否也超限
    pCur->pPage = pCur->apPage[--pCur->iPage];
  } while( rc==SQLITE_OK );
}
```

SQLite 针对不同分裂形态设计了三个各具特长的平衡例程：

- **`balance_deeper()`**：专门用于处理根页溢出。在 SQLite 中，根页的页号是写入元数据系统表的固定标识，物理位置不可改变。因此当根页填满时，它不能像普通页那样分裂并产生一个新的独立根；相反，它会开辟一个全新的子页面，把自身所有单元格拷贝到子页中，自身则降级为一个仅包含子节点指针的内部导航节点。**这是 SQLite B 树层高增长的唯一方式**。
- **`balance_quick()`**：针对自增主键追加写入的专属快速路径。当一个整型主键表在页末尾追加记录并溢出时，完全没有必要将该页的历史数据打散重组；它直接分配一个全新的空白右兄弟页接收该单元格，原页面保持不动。
- **`balance_nonroot()`**：处理普通内部节点或叶节点分裂/合并的通用大一统例程。它会同时锁定当前页以及相邻的最多 2 个兄弟页，将这些页面的所有单元格聚合在一起，随后均摊写入新开辟或重排的页面中，并在父节点中同步更新或插入新的分隔键。

::: generate page-split kind=example concepts=page-format,btree-types

## 7. Pager 层：页缓存与崩溃安全

如果说 B 树层负责在内存中搭起数据的骨架，那么真正为 SQLite 构筑起事务原子性（Atomicity）与持久性（Durability）铁壁的，则是中间的 **Pager 层**。

Pager 是整个系统的守门人。它把物理磁盘文件抽象为一个能够按需换入换出的页面缓存池，并运用精密的有限状态机来严守事务的生命周期：

::: concept pager-state-machine title="Pager 状态机"

Pager 的运行严格受控于一组单向演进的状态迁移图：

```
OPEN → READER → WRITER_LOCKED → WRITER_CACHEMOD → WRITER_DBMOD → WRITER_FINISHED → READER
                                                                                      ↑
任何 WRITER 状态 ————→ ERROR ————→ OPEN ————————————————————————————————————————————————┘
```

每个状态对应着明确的文件锁权限与 I/O 行为：

| 状态 | 对应文件锁 | 行为与职责 |
|:---|:---|:---|
| OPEN | 无锁 | 初始空闲状态，未持有任何系统文件锁 |
| READER | SHARED（共享锁） | 允许并发读取页缓存或物理文件，禁止写入 |
| WRITER_LOCKED | RESERVED（保留锁） | 准备开启写事务，提示其他连接即将修改，但尚未动笔 |
| WRITER_CACHEMOD | EXCLUSIVE（排他锁） | 内存页缓存已被篡改，回滚日志文件已创建并同步 |
| WRITER_DBMOD | EXCLUSIVE（排他锁） | 脏页数据已开始刷入物理数据库文件 |
| WRITER_FINISHED | EXCLUSIVE（排他锁） | 数据库落盘完毕，等待提交或解除写状态 |
| ERROR | - | 遭遇不可恢复的底盘 I/O 错误，锁定拒绝后续操作直至回滚 |

在经典的传统回滚日志模式下，修改必须历经这一整套线性状态流转；而在 WAL 模式下，由于所有写入都流向了日志，Pager 根本不会触碰 `WRITER_DBMOD` 与 `WRITER_FINISHED`，大幅缩短了排他锁的持有周期。

:::

在物理对象上，`Pager` 结构体聚合了数据库主文件描述符 `fd`、回滚日志描述符 `jfd`、内存换入缓存句柄 `pPCache`，以及一张关键的位图 `Bitvec *pInJournal`。这张位图精准记录了在当前事务中，哪些页号的原始版本已经被安全沉淀到日志文件中。

### 7.1 获取页面：sqlite3PagerGet

当 B 树层欲探访某个具体页码时，它调用 `sqlite3PagerGet(pPager, pgno, &pPage, flags)`。Pager 内部通过函数指针分发，默认由 `getPageNormal()` 承接。它会优先在内存缓存哈希表 `PCache` 中搜寻；若未命中，则分配一个空闲的 `PgHdr` 槽位，并调用 VFS 的 `sqlite3OsRead()` 从磁盘文件中把整页数据拉入内存。

### 7.2 标记脏页：sqlite3PagerWrite 的前置日志铁律

在 B 树层对任何已载入内存的页面动哪怕一个字节之前，必须先显式调用 `sqlite3PagerWrite()` 申请写权限：

```c
static int pager_write(PgHdr *pPg){
  Pager *pPager = pPg->pPager;

  // 1. 若当前尚未打开日志文件，先创建日志
  if( pPager->eState==PAGER_WRITER_LOCKED ){
    rc = pager_open_journal(pPager);
  }

  // 2. 将页面挂载至脏页链表
  sqlite3PcacheMakeDirty(pPg);

  // 3. 回滚日志模式的核心守则：先写原始数据到日志（仅在首次修改该页时触发）
  if( pPager->pInJournal!=0
   && sqlite3BitvecTestNotNull(pPager->pInJournal, pPg->pgno)==0 ){
    if( pPg->pgno <= pPager->dbOrigSize ){
      rc = pagerAddPageToRollbackJournal(pPg);  // 写入原始页面
    }
  }

  // 4. 赋予 PGHDR_WRITEABLE 标记，上层此时方可安全修改
  pPg->flags |= PGHDR_WRITEABLE;
  return rc;
}
```

这段逻辑体现了数据库系统中最核心的**预写日志（Write-Ahead Logging / Undo Logging）铁律**：永远在内存修改真正发生之前，把受损前的“快照原貌”安全固化在磁盘日志中。如果系统随后发生突发断电，这些预存的旧页面就是唯一的救命解药。

### 7.3 崩溃恢复：pager_playback

::: concept rollback-journal title="回滚日志的崩溃恢复"

如果在事务提交前夕系统突然断电或崩溃，下一次任何连接尝试打开数据库时，Pager 会检测到文件系统残留的未解热日志（Hot Journal），并立即挂载 `pager_playback()` 启动逆向急救：

1. 打开残留的回滚日志文件，读取头部的全局快照尺寸与页数记录；
2. 顺着日志序列，逐一读出其中暂存的旧版原始数据页；
3. 将这些旧页原样覆盖写回物理数据库文件的对应偏移处；
4. 调用文件截断，将数据库物理大小复原至事务开启时的 `dbOrigSize`；
5. 最后，**安全删除日志文件**（或将其头部全置为 0）。

在传统的单文件日志模式下，**日志文件的物理删除或归零，正是整个 ACID 事务的原子提交点**。日志一旦消失，意味着上一任事务已合法生效；反之，只要日志依旧矗立在磁盘上，任何重启的节点都会强制回放日志、抹平未提交的痕迹。

:::

::: generate journal-vs-wal kind=comparison concepts=rollback-journal,pager-state-machine

面向有数据结构基础的 C 程序员，比较回滚日志（rollback journal）和 WAL 两种事务机制：回滚日志在写入前保存原始页面，崩溃后撤销修改（undo log）；WAL 把新版本追加到 WAL 文件，崩溃后丢弃未提交的 WAL 帧（redo log）。对比两者在写入放大、读并发、恢复速度方面的差异，解释为什么 WAL 模式在大多数场景下性能更好。

:::

## 8. WAL 模式

传统的回滚日志机制虽然逻辑直观，但其致命瓶颈在于**写操作与读操作的互斥性**：写者在将脏页刷盘时必须持有排他锁，所有读者必须完全退避等待。为了从根本上解锁高并发读写的潜能，SQLite 引入了预写日志（WAL，Write-Ahead Logging）模式。

### 8.1 核心机制：追加写与帧解耦

::: concept wal-protocol title="WAL 协议"

在 WAL 模式下，主数据库文件在日常修改中几乎退化为一个“只读基线镜像”，所有新产生的脏页都会以**帧**（Frame）为单位连续追加到独立的日志文件（`-wal`）尾部。

- **顺序追加写入**：脏页不覆写主数据库文件，而是顺序写入 WAL 末尾。每个帧由 24 字节的帧头（记录目标页号、提交时的数据库页数 `nTruncate`、盐值与校验和）及后续完整的页面数据组成。
- **快照读路由**：当读取某一页时，引擎会先去检索 WAL 中是否存在该页的更新版本。若存在且符合当前事务的可见性，则从 WAL 文件中提取；否则回退读取主数据库文件。
- **极速提交**：提交事务仅仅意味着向 WAL 追加一个带有 `nTruncate > 0` 标记的提交帧，并对 WAL 文件执行一次单向 `fsync`。完全省去了对主数据库文件的随机刷盘。
- **定期检查点**：当 WAL 累积到一定规模（默认 1000 帧）时，后台触发检查点，将 WAL 中的最新页按顺序回写覆写至主数据库，回收 WAL 空间。

:::

在内核中，`Wal` 结构体维系了数据库文件与 WAL 文件的双重句柄、多级读写锁，以及最关键的 WAL 索引（`WalIndexHdr` 与共享内存映射 `apWiData`）。

### 8.2 读写互不阻塞的并发奥秘

WAL 之所以能够做到“读者不阻塞写者、写者亦不阻塞读者”，核心在于其类似 MVCC（多版本并发控制）的快照隔离机制：

当一个读事务启动时（`walTryBeginRead`），它会探查当前 WAL 的最大有效提交帧号，并将其固化在自身的读标记 `mxFrame` 中。在整个读事务持续期间，该读者**仅能感知帧号小于等于 `mxFrame` 的历史版本**。后续即便有并发写者向 WAL 追加了成千上万个新帧，由于其帧号全部大于该读者的快照水位，对该读者完全不可见。

写者写入时，只需获取互斥的排他写锁以防止多个写者并发交错追加 WAL 尾部，完全无须等待正在阅读旧快照的读者退出。

```c
static int walFrames(Wal *pWal, int szPage,
                     PgHdr *pList, Pgno nTruncate,
                     int isCommit, int sync_flags) {
  // 1. 若 WAL 为空，初始化 32 字节的 WAL 文件头
  if( pWal->hdr.mxFrame==0 ){
    rc = sqlite3OsWrite(pWal->pWalFd, aWalHdr, sizeof(aWalHdr), 0);
  }

  // 2. 将脏页链表逐页组装为帧并顺序追加
  for(p=pList; p; p=p->pDirty){
    iFrame++;
    // 写 24 字节帧头与页面物理数据
    rc = walWriteOneFrame(&w, p, nTruncate, iOffset);
    iOffset += szFrame;

    // 同步更新共享内存（WAL Index）中的哈希查找表
  }

  // 3. 事务提交时，对 WAL 文件执行物理刷盘同步
  if( isCommit && sync_flags ){
    rc = sqlite3OsSync(pWal->pWalFd, sync_flags);
  }

  // 4. 原子更新共享内存中的全局最大帧号 mxFrame
}
```

为了避免读者每次查页时都要在长达数兆的 WAL 文件里顺序从后向前扫，SQLite 引入了 **WAL 索引**（通常映射在同名的 `.shm` 共享内存文件中）。这是一个基于哈希表的高性能内存索引，记录了“物理页号 $\to$ 其在 WAL 中的最新帧号”的映射。读者通过哈希查找即可在微秒级确认某一页在 WAL 中的具体落点。

::: generate wal-readers-writers kind=explanation concepts=wal-protocol

面向有数据结构基础的 C 程序员，解释 WAL 模式如何实现"读者不阻塞写者、写者不阻塞读者"：每个读者在开始读事务时记录当前 WAL 的 mxFrame（最大帧号），之后只看到该帧号及之前的数据，后续写者追加的帧对其不可见。写者只需获取排他的"写锁"来防止多个并发写入，但不需要等待读者完成。解释 wal-index（共享内存中的哈希表）如何让读者快速查找某页在 WAL 中的最新帧。

:::

### 8.3 检查点机制与四种回写策略

随着写入持续累积，WAL 文件不可能无节制膨胀。**检查点**（Checkpoint）的核心任务，就是把 WAL 中已经提交的数据页回刷到主数据库文件中。

SQLite 在 `sqlite3WalCheckpoint()` 中引入了优化的写盘策略：它并非按照帧的写入先后盲目回刷，而是通过 `WalIterator` 预先**按目标页号进行排序**，将零散的修改转化为对主数据库文件的纯线性顺序 I/O，极大释放了机械磁盘或 SSD 的吞吐潜能。

检查点支持四种灵活的运行策略：

| 模式 | 协作策略与行为 |
|:---|:---|
| PASSIVE | 尽力而为模式。不阻塞任何并发读写，仅回写当前不受活跃读者快照影响的帧，可能只完成部分同步 |
| FULL | 等待当前活跃写者结束，将所有提交帧回写至主库；但若有老读者仍在读取 WAL，则不等待其离开 |
| RESTART | 在 FULL 的基础上，阻塞等待所有慢读者彻底退出旧快照，随后将 WAL 的写入游标重置回第 1 帧 |
| TRUNCATE | 与 RESTART 一致，并在重置游标后调用文件系统接口将 WAL 文件物理截断为 0 字节 |

### 8.4 WAL 模式下的完整读取路径

理清上述组件后，WAL 模式下任意一个读页请求的决策链路便一览无余：
1. 提取当前读事务在启动时锁定的快照水位 `mxFrame`；
2. 在共享内存的 WAL 索引哈希表中，探查该 `pgno` 是否拥有最新帧号记录；
3. 若命中且其帧号 $\le \text{mxFrame}$，直接依据帧偏移从 `-wal` 文件中读取最新数据并返回；
4. 若未命中，或虽然命中但帧号大于该读者的快照水位，则安全穿透回主数据库文件，从基线物理页中提取数据。

### 9.2 编程

<Exercise id="50668" :d="4" :w="3">

不看 SQLite 的 `btree.c`，只用 §2、§3、§4 的格式说明写一个只读遍历器 `walk.c`，把一个 Table B 树的所有 rowid 按升序打印出来。

做一个崩溃恢复实验，验证 §7.2 与 §7.3 的「先写日志，再改数据」。

1. 写一个程序 `crash.c`：`BEGIN` 后插入若干行，写完但不 `COMMIT`，用 `_Exit(0)`（C11，`<stdlib.h>`）直接结束进程，让日志留在文件系统里。先不关数据库，也不要调用任何清理函数。
2. 在两种时机各做一次：插入少量行（脏页还在缓存里）、插入大量行并把 `cache_size` 调小、同时把页大小设成 512（脏页已溢出到主文件）。每种都保留 `-journal` 文件，用 `od` 看它开头 28 字节，记录魔数、`nRec`、原始页数。
3. 用命令行工具重新打开每个库，执行 `SELECT count(*)` 与 `PRAGMA integrity_check`。比较两种时机下结果与日志文件的状态，指出哪种情况日志真的是「热」的（提示：`hasHotJournal` 只看日志文件第 1 个字节是否为 0）。

### 9.3 综合与挑战

<Exercise id="50671" :d="6" :w="5">

用 `PRAGMA wal_checkpoint(mode)` 测量 §8.3 的四种模式，回答「谁在挡住检查点」。
