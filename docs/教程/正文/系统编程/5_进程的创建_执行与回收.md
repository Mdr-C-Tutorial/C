# 5. 进程的创建、执行与回收

## 1 进程创建

在 POSIX 中，进程的创建通常需要使用 fork 函数。它的语义简单来说是，将当前进程复制一份作为子进程。它返回一个值，如下：

- 在子进程中，返回 0
- 在父进程中，返回子进程的 pid
- 如果错误，返回一个负数值

### 1.1 fork 的资源和内存

进程之间不共享大部分内存，除了共享内存之外。fork 的语义表明，子进程拿到的是父进程完整的内存副本。为了保证内存之间的隔离，fork 的一个经典实现需要复制一份父进程所有的内存。在早期内存不大这么做尚可，但随着程序使用内存的增长，这么做会带来不小的开销。

实际上，现代实现（以 Linux 为例）使用的是一种 Copy on Write 的做法。具体来说，如此创建的子进程并不直接复制父进程所有的内存，为了保证内存之间的隔离，fork 会对相应的页做一些标记，使得当父进程或者子进程修改内存的时候，会触发缺页中断，将被修改的**内存页**复制一份（得益于分页式内存管理）。

对于其他的系统资源，如文件描述符，一般情况下子进程是继承父进程的（后续皆以文件描述符为例）。如下列代码：

```c
int fd=open(...);//打开文件
pid_t p=fork();
if(p==0){
    write(fd,...);//写入一些东西
}
```

是会成功的。基于这个原理，曾经在服务器领域有一个叫做 CGI 脚本的过时技术得以实现。读者可以自行去了解，它的一个原理是父进程和子进程共享 socket。但这也带来了一个问题：fork 之后通常跟着 exec 系列函数，实际上我们有很多文件描述符是不希望继承给子进程的，如不属于该进程的管道，如果出现这种情况，需要在子进程里面调用 close 函数，或者在父进程使用 fnctl 函数指定文件描述符的属性。

### 1.2 多线程程序的 fork

如果一个进程中有多个线程，则 fork 函数只会复制调用它的线程。这在多线程的程序里面，会引来一个需要注意的东西。先说结论：只有[可以在 signal handler 里面安全调用的函数](https://www.man7.org/linux/man-pages/man7/signal-safety.7.html)，可以在 fork 之后 exec 之前安全调用。具体来说，不妨设想一个场景:

- 进程 A 有两个线程，计为 B 和 C
- 线程 B 调用了 malloc，还没有返回
- Linux 此时调度到了线程 C，C 创建了一个子进程 D，然后子进程 D 也调用了 malloc

显然，为了优化，allocator 会维护一些可用内存，将释放的内存放到这里，而不是直接还给操作系统，这在频繁的内存分配中可以减少系统调用的开销。但是为了保证多线程下操作这些内存是安全的，这一些可用内存需要被 mutex 保护（该 mutex 在下文计作 M）。如果此时进程 A 的线程 B 恰好获取了 M，则线程 C 在调用 fork 的时候，创建出来的子进程 D 的内存中，显然也有 M，且 M 的状态是已经被获取了。则 D 在调用 malloc 的时候，尝试获取 M，由于 M 已经被获取，D 会暂停执行。但由于只有线程 C 被复制了一份，成为子进程 D，而线程 B 没有被复制，导致在子进程中，M 不会被释放，最终结果是死锁。

### 1.3 posix_spawn

实际上，由于上述的过程易于出错，POSIX 还提供了一个 posix_spawn 函数。它十分类似 Microsoft Windows 的 CreateProcess 函数。

### 1.4 进程树和孤儿进程

在 POSIX 里面，进程具有一个树状结构，被成为进程树。从结构上来看，除了 init 进程之外，任何一个进程都有唯一父进程。当一个进程的父进程结束后，而该进程没有结束，则该进程成为了孤儿进程。在通常的使用 systemd 作为 init 的 Linux 中，此时该进程的父进程会变为 init，这个过程被称为收养。

## 2 进程执行

进程是程序的一次执行。

### 2.1 exec 函数族

exec 函数族干的事情非常简单粗暴，它的作用是把当前进程的内容直接替换成指定的可执行文件。它有 execv、execl、execvp、execve 等不同的函数，分别表示着不同的命令行参数的提供方式和可执行文件的路径获取方式，大致如下：

- v 意味着命令行参数是通过一个字符串数组提供的，而 l 意味着命令行参数是通过可变参数逐个提供的
- e 意味着最后有一个传递环境变量的参数，通过字符串数组提供
- p 意味着会从 PATH 中搜索可执行文件的位置

当一个程序被启动的时候，exec 函数族中的某个函数都会被调用（这是因为 POSIX 创建一个新进程的方式，是复制一份自己，然后把复制出的自己替换掉），它会调用动态链接器（如 Linux 中最常见的 ld-linux）打开该可执行文件，并且完成符号解析等初始化过程，然后才执行对应的入口程序（通常来说，实际上并不是我们写的入口函数，而是一段由 libc 提供的入口程序，用来完成类似收集环境变量和命令行参数的过程）（一些非关键步骤已省去，例如 exec 本身作为一个系统调用所带来的用户态和内核态之间的切换过程）

在 exec 后，原有的非共享内存将会不可访问，设置为 FD_CLOEXEC 的文件描述符也会被关闭。

### 2.2 进程调度

由于一些历史原因，许多操作系统课程把调度相关的内容放到进程里面讲。但是由于调度的最小单元是线程，这部分内容将在第 8 章《操作系统线程与同步》中讲解。此处仅为本教程中“动态链接的 stub”。

### 2.3 进程退出

当一个进程执行结束后，它就会退出。在 C 中，我们已经学习了一个叫做 exit 的函数，我们还了解到了 atexit 可以注册进程退出时的处理函数。实际上，当 main 函数结束，或者调用 exit 函数后，程序通常并没有直接结束，而是进入一段 libc 的结束函数。它要负责一些清理工作，并且执行 atexit 注册的函数。如果读者熟悉 C++ 的话，还可以发现，C++ 中的 RAII 的实现也与这一行为有关，它保证了当 exit 函数被调用时，RAII 仍然生效。在这之后，libc 的结束函数还需要调用 exit 系统调用，来通知操作系统进程停止了执行。

这个 exit 系统调用是不可少的，读者如果熟悉 Assembly 可以尝试着用 Assembly 编写一个程序，不调用 exit 系统调用，那么会出现非法指令或者段错误，这是因为没有 exit 系统调用，操作系统并不知道这个进程已经结束了，故它的程序计数器仍然会增长，直到某次 CPU 取到了非法指令（显然我们不知道对应的页的剩余部分是什么，此时出现非法指令），或者程序计数器指向的内存是不可执行或者不可被该进程访问的（此时出现段错误）。同时该系统调用接受一个整数参数，实际上 main 函数要求返回一个 int 值，一个原因就是如此。

还有一种特殊的进程退出，是它被 SIGKILL 强制杀死。这个信号在 C 标准库的信号处理那里已经提及了，是一个不可捕获不可忽略的信号。它的作用是直接摧毁该进程，不走 libc 的那条释放资源的路线。其几乎相当于在程序内部直接以 137 作为参数调用 exit 系统调用，而不是调用 exit(137)。

## 3 进程回收

进程结束后，已经分配的系统资源必须回收，不然就是泄漏。

### 3.1 让我们继续讨论 exit 系统调用

exit 系统调用的作用是通知操作系统进程结束了。操作系统需要的操作是，对进程持有的一切资源（如文件描述符、内存和 CPU 时间片）进行释放。

进程需要返回一个有意义的值来表示进程的状态（实际上 exit 系统调用的参数就是该返回值），如返回 0 通常表示进程正常执行，而返回其他非 0 数表明进程的执行结构是异常（如接受了错误的输入）。基于这个原理，操作系统需要在进程结束之后仍然维护进程的部分信息。这些资源不能在 exit 的时候被释放，直到它被某个进程获取为止。

### 3.2 僵尸进程

实际上，3.1 节所述的过程隐含着一个新的状态：进程结束了，但是它仍需保留的信息没有被获取。在这个状态的进程被称为僵尸进程。在 ps 或者 top 等工具中，通常标记为状态 Z（即Zombie）。POSIX 规定了两个用于获取该资源的函数，分别是 waitpid 和 wait。其中，wait 的作用是阻塞，直到有一个子进程退出。而 waitpid 可以更细粒度的获取有权限的进程组的进程状态改变（如退出、挂起，且支持非阻塞的做法），并且当进程退出时，它们都可以获取到进程的返回值等信息，此时僵尸进程消失，pid 等资源也可以复用。

产生僵尸进程通常是因为编程错误，父进程忘记或者长时间没有调用 wait 或者 waitpid。实际上，当子进程结束时，父进程会收到一个 SIGCHLD 信号，父进程可以自定义该信号 handler 来在合适的时间内调用 waitpid。

如果需要 fire and forget 的那种完全不关心子进程状态的模型，则可以设置忽略 SIGCHLD 信号，此时内核会自动回收僵尸进程

如果只对部分进程的态度是 fire and forget，则实践中有一个双重 fork 技巧：
- 在父进程调用 fork
- 在子进程中再次调用 fork，在孙进程中执行对应的任务，然后子进程结束
- 父进程对子进程调用 waitpid

类似这样
```c
pid_t p=fork();
if(p==0){
    if(fork()==0){
        //执行逻辑上的子进程的操作
    }
    _exit(0);
}
waitpid(p,0,0);
```

这么做的理由是，子进程结束后，孙进程成为孤儿进程，被 init 收养，由 init 进程自动处理该进程结束后留下的资源。
