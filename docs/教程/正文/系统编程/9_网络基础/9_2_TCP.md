# 9.2 传输控制协议（TCP）

## 1. TCP 概述

### 1.1 核心特性

传输控制协议（Transmission Control Protocol, TCP）是一种面向连接的、可靠的、基于连续字节流的传输层协议。IP 协议负责将数据报尽力送达目标节点（Best-Effort），TCP 则在不可靠的网络层之上，为上层应用提供可靠的双向全双工字节流通信。

TCP 主要通过以下机制保证可靠传输与数据有序：

1. 端到端可靠性：TCP 依赖序号（Sequence Number）、累积确认（Acknowledgment）与动态自适应重传定时器。接收端在成功校验数据后按序回复确认号；若发送方在根据网络往返时间（RTT）动态估算的超时周期内未能等到特定区间的确认，便会主动触发重传。
2. 面向连接：通信双方在收发载荷数据之前，必须通过握手机制就初始序号、最大报文段大小（MSS）与窗口缩放等参数达成一致。连接是全双工的，收发两个方向的数据流各自独立推进，互不干扰。
3. 滑动窗口流量控制：TCP 首部内置 16 位窗口字段（Window Size），接收端通过该字段动态通告自身内核套接字缓冲区的剩余可用容量，发送端据此限制在途未确认字节的总量，防止接收端缓冲区溢出。
4. 严格全局有序：网络层 IP 数据报在传输过程中可能由于路由路径变动而发生乱序到达。TCP 接收端依据序列号在内核重组缓冲区中将报文碎片排序拼装，保证交付给应用层的数据顺序与发送端的写入顺序一致。
5. 传输完整性校验：每一个 TCP 报文段均携带涵盖伪首部、TCP 首部及载荷的 16 位反码和校验字段。发生校验失败或损坏的数据段会被接收端内核直接丢弃，进而转由超时重传机制自愈。

## 2. 连接生命周期

### 2.1 三次握手

TCP 连接的建立遵循经典的三次握手（Three-way Handshake）流程，通信双方通过该过程协商并确认各自的初始序列号（ISN, Initial Sequence Number）：

首先，客户端向服务端发送带有 SYN 标志位的报文段，并在序号字段中填入自身生成的初始序号 $ISN_c$；服务端接收后，在内核中为该半连接分配传输控制块（TCB），随后回送同时置位 SYN 和 ACK 的报文段，确认号为 $ISN_c + 1$，并携带服务端生成的初始序号 $ISN_s$；最后，客户端再度发送置位 ACK 的报文段，确认号为 $ISN_s + 1$。当该 ACK 报文被服务端接收后，内核已完成连接队列（accept queue）便记录下该就绪连接，双方正式进入 ESTABLISHED 状态。三次交互是双方在不可靠信道中确立双向连通性与序号基准的充要条件。

### 2.2 数据传输

在连接处于 ESTABLISHED 状态期间，应用程序调用 `send` 或 `write` 写入的数据在 TCP 层不保留业务消息边界。TCP 会根据路径 MTU 协商出的最大报文段大小（MSS）、网络拥塞窗口以及接收端通告窗口，将连续字节流在合适的时机切割为一个或多个数据段送入网络层。接收端内核按序号将到达的片段按序拼接至套接字接收缓冲区，应用程序通过 `recv` 或 `read` 即可按需提取连续字节流。

### 2.3 四次挥手与 RST 重置

由于 TCP 是全双工通信管道，两个方向上的数据流可以独立终止，因此正常的断开流程需要经历“四次挥手”：

当某一方应用层处理完毕、不再有新数据需要发送时（例如调用了 `close` 或 `shutdown(SHUT_WR)`），它会向对端发送一个置位 FIN 的报文段，宣告本方向的写入流终结。对端内核接收到 FIN 后自动回复 ACK 确认，此时连接进入半关闭（Half-Close）状态——发起方不可再写，但依然可以持续读取对端尚未发完的数据。随后，当对端也处理完剩余业务并决定关闭写通道时，同样会发送 FIN 报文段；发起方在接收到对端 FIN 后回复最后的 ACK。此时，主动发起关闭的一方必须在内核中保持在 `TIME_WAIT` 状态长达两个报文最大生存时间（2MSL，多数 Linux 系统为 60 秒），以确保最后发送的 ACK 若在网络中丢包，能够有足够的时间响应对端重传的 FIN；同时彻底耗尽线路上可能残存的一切属于该连接四元组的历史迟到报文，防止在后续复用相同端口的新连接中造成数据串扰。

除正常关闭外，TCP 还可以通过连接重置（Reset, RST）直接终止连接。当端点遭遇严重不可恢复异常时，协议栈会发出带有 RST 标志位的报文段。收到 RST 报文的一方，其内核套接字缓冲区内的现存数据将被立即清空，连接未经挥手流程直接关闭，相关的系统调用会立即返回 `ECONNRESET`。触发 RST 的常见场景包括：服务端目标端口未被任何进程监听、通信进程异常终止（如收到 `SIGKILL`）且缓冲区尚有未读数据、网络中间防火墙主动阻断，或是应用程序通过配置 `SO_LINGER` 强制将丢弃超时设为 0。

## 3. 流式传输与可靠性机制

### 3.1 字节流与应用层分帧

TCP 是面向字节流的协议，传输的是无边界的连续字节序列，协议层本身不维护业务消息边界。常被提及的“粘包”与“拆包”，源于应用层未自行实现消息分帧。

当应用层先后调用两次 `send` 分别写入 50 字节时，内核套接字发送缓冲区完全可能将这 100 字节汇聚在一个物理数据段中合并发出，导致接收端单次 `read` 直接读出 100 字节；反之，若单次写入 64 KiB 的载荷，由于受限于路径 MTU（如标准以太网下的 MSS 通常为 1460 字节），内核必然会将其拆分成几十个连续的 TCP 报文段发送，导致接收端需要历经多次 `read` 才能逐渐读取完整。这种合并与拆解由底层的 Nagle 算法（可通过 `TCP_NODELAY` 禁用）、套接字聚集选项（`TCP_CORK`）以及物理链路 MTU 共同主导。因此，应用程序不能依赖单次 `recv` 的返回长度来界定业务消息边界，必须由应用层协议自行承担消息分帧（Framing）职责——例如引入特定分隔符（如 `\r\n`），或是在消息头部开辟固定宽度的字段标明后续载荷长度。

### 3.2 序号与确认机制

TCP 采用以字节为基本刻度的双向序号体系。序列号（Sequence Number）代表当前报文段载荷中首个字节在整个流中的绝对偏移量；确认号（Acknowledgment Number）具有累积特性，代表接收方期望接收到的下一个字节编号，表明该编号之前的所有连续字节均已成功接收。如果序号发生空洞（如收到了 1～1000 与 2001～3000，但中间的 1001～2000 发生丢包），接收端的确认号将保持在 1001，直到缺失的数据段被重传补齐。

### 3.3 拥塞控制

流量控制用于防止发送方压垮接收方的缓冲区，而拥塞控制（Congestion Control）用于防止过多数据注入网络导致路由器与骨干链路过载。TCP 发送端维护一个动态的拥塞窗口（cwnd, Congestion Window），发送端在途未确认的字节上限受制于 $\min(\text{cwnd}, \text{rwnd})$。

在慢启动（Slow Start）阶段，窗口指数级扩张以快速试探可用带宽；一旦触及阈值便转为线性的拥塞避免（Congestion Avoidance）；当遭遇丢包时，经典算法大幅缩减拥塞窗口，这使得传统算法在公网发生偶发丢包时，传输速率会出现较大幅度的回落并随后逐步恢复。现代 Linux 默认采用基于往返时延（RTT）与带宽探测的 BBR（Bottleneck Bandwidth and RTT）拥塞控制算法，显著平滑了长肥管道（LFN）下的吞吐抖动。

## 4. 套接字编程接口

在 POSIX 环境下，C 语言通过统一的 BSD 套接字接口进行网络编程：

1. 创建套接字：调用 `socket(AF_INET, SOCK_STREAM, 0)` 创建流式套接字，获取对应的文件描述符；
2. 绑定与监听（服务端）：服务端调用 `bind` 将描述符与指定的本地 IP 地址和监听端口绑定，随后调用 `listen` 激活内核连接队列，开始等待外部连接接入；
3. 建立连接：客户端调用 `connect` 触发三次握手发起连接；服务端调用 `accept` 从已完成连接队列中移出就绪连接，并为其派生出新的已连接套接字描述符；
4. 数据传输：在已连接套接字上，程序既可以使用 `send` 与 `recv` 传递网络控制标志，也可以直接调用通用文件 I/O 接口（如 `read`、`write` 以及零拷贝系统调用 `sendfile`）；
5. 关闭连接：调用 `close` 释放套接字描述符并触发四次挥手；若需精细控制单向半关闭，可调用 `shutdown` 单独截断读流或写流。
