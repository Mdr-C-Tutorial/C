# 9.2 传输控制协议（TCP）

## 1. 什么是 TCP

### 1.1 TCP 的本质与核心能力

传输控制协议（Transmission Control Protocol, TCP）是整个现代互联网的基石协议之一。在系统架构的层级上，它被定义为一种面向连接的、可靠的、基于连续字节流的端到端传输层规约。如果说 IP 协议仅仅负责将孤立的报文尽可能送达目标物理节点（Best-Effort 尽力而为），那么 TCP 则是在这片不可靠的异构物理网络之上，为上层应用程序虚拟出一条宛如本地管道般严密、可靠的双向全双工字节流通道。

这一契约主要依托于以下核心工程机制维系：

1. 端到端可靠性：TCP 严格依赖序号（Sequence Number）、累积确认（Acknowledgment）与动态自适应重传定时器。接收端在成功校验数据后按序回复确认号；若发送方在根据网络往返时间（RTT）动态估算的超时周期内未能等到特定区间的确认，便会主动触发重传。
2. 面向逻辑连接：通信双方在真正收发载荷数据之前，必须经历严格的握手机制就双方的初始序号、最大报文段大小（MSS）与窗口缩放等参数达成一致。该连接是全双工的，收发两个物理方向的数据流各自独立推进，互不干扰。
3. 滑动窗口流量控制：网络协议不能脱离接收端的内存处理能力空转。TCP 首部内置 16 位窗口字段（Window Size），接收端通过该字段动态通告自身内核套接字缓冲区的剩余可用容量，发送端据此严格限制在途未确认字节的总量，杜绝将接收端内存撑爆的恶性溢出。
4. 严格全局有序：网络层 IP 数据报在穿越公网路由器时完全可能由于路径变动而发生乱序到达。TCP 接收端依据序列号在内核重组缓冲区中将碎片重新拼装排序，确保交付给应用层的数据顺序与发送端的写入顺序分毫不差。
5. 传输完整性校验：每一个 TCP 报文段均携带涵盖伪首部、TCP 首部及载荷的 16 位反码和校验字段。任何发生单比特翻转或内存损坏的数据段都会被接收端内核直接丢弃，进而转由超时重传机制自愈。

## 2. TCP 的生命周期与状态转换

### 2.1 三次握手：连接建立

TCP 逻辑连接的建立遵循经典的三次握手（Three-way Handshake）流程。其本质并非单纯的仪式，而是通信双方互相协商并确认各自初始序列号（ISN, Initial Sequence Number）的过程：

首先，客户端向服务端发送一个带有 SYN 标志位的报文段，并在序号字段中填入自身随机生成的初始序号 $ISN_c$；服务端接收到该报文后，在内核中为该半连接分配相应的传输控制块（TCB），随后回送一个同时置位 SYN 和 ACK 的报文段，确认号设定为 $ISN_c + 1$，并携带服务端自身生成的初始序号 $ISN_s$；最后，客户端再度发送一个置位 ACK 的报文段，确认号为 $ISN_s + 1$。当该 ACK 报文被服务端接收后，内核已完成连接队列（accept queue）便记录下该就绪连接，双方正式进入 ESTABLISHED 状态。三次交互是双方在不可靠信道中确证双向连通性与序号基准的最小充要条件。

### 2.2 数据传输与流式抽象

在连接处于 ESTABLISHED 状态的生命周期内，应用程序调用 `send` 或 `write` 写入的数据并不会被 TCP 视作具有独立业务边界的“消息”。TCP 会根据路径 MTU 协商出的最大报文段大小（MSS）、网络拥塞窗口以及接收端通告窗口，将连续的字节流在最合适的时机切割为一个或多个数据段送入网络层。接收端内核则按序号将到达的片段按序拼接至套接字接收缓冲区，应用程序通过 `recv` 或 `read` 即可像读取连续物理文件一样按需提取字节。

### 2.3 四次挥手与非正常中断

由于 TCP 是一条全双工通信管道，两个方向上的数据流可以独立终止，因此标准的断开流程需要经历“四次挥手”：

当某一方应用层处理完毕、不再有新数据需要发送时（例如调用了 `close` 或 `shutdown(SHUT_WR)`），它会向对端发送一个置位 FIN 的报文段，宣告本方向的写入流已经终结。对端内核接收到 FIN 后自动回复一个 ACK 确认，此时连接进入半关闭（Half-Close）状态——发起方已不可再写，但依然可以持续读取对端尚未发完的数据。随后，当对端也处理完剩余业务并决定关闭写通道时，同样会发送一个 FIN 报文段；发起方在接收到对端 FIN 后回复最后的 ACK。此时，主动发起关闭的一方并不能立即释放资源，而是必须在内核中强制滞留于 `TIME_WAIT` 状态长达两个报文最大生存时间（2MSL，在多数 Linux 系统上硬编码为 60 秒），以确保最后发送的 ACK 若在网络中丢包，能够有足够的时间响应对端重传的 FIN；同时彻底耗尽线路上可能残存的一切属于该连接四元组的历史迟到报文，防止它们在后续复用相同端口的新连接中造成数据串扰。

除了体面的挥手，TCP 还存在一种强制撕毁连接的异常路径：连接重置（Reset, RST）。当端点遭遇严重不可逆异常时，协议栈会直接发出一个带有 RST 标志位的报文段。收到 RST 报文的一方，其内核套接字缓冲区内的现存数据将立即被全部冲刷丢弃，连接在未经握手挥手的情况下瞬间暴毙，相关的系统调用会立即返回 `ECONNRESET`。触发 RST 的常见诱因包括：服务端目标端口未被任何进程监听、通信进程遭遇 `SIGKILL` 异常暴毙导致残留未读数据、网络中间防火墙主动阻断，或是应用程序通过配置 `SO_LINGER` 强制将丢弃超时设为 0。

## 3. 深入理解 TCP 的流式特性与抗抖动机制

### 3.1 连续流与应用层分帧：消除“粘包”误区

初涉网络编程的开发者最常遭遇的心理障碍是所谓的“粘包”与“拆包”。必须明确的是：在 TCP 协议规范与操作系统内核的字典里，压根不存在“包”（Packet）的概念，只有无边无际的连续字节序列。

当应用层先后调用两次 `send` 分别写入 50 字节时，内核套接字发送缓冲区完全可能将这 100 字节汇聚在一个物理数据段中合并发出，导致接收端单次 `read` 便直接读出 100 字节；反之，若单次写入 64 KiB 的巨额载荷，由于受限于路径 MTU（如标准以太网下的 MSS 通常为 1460 字节），内核必然会将其拆分成几十个连续的 TCP 报文段发送，导致接收端需要历经多次 `read` 才能逐渐汲取完整。这种合并与拆解由底层的 Nagle 算法（可通过 `TCP_NODELAY` 禁用）、套接字聚集选项（`TCP_CORK`）以及物理链路 MTU 共同主导。因此，试图依赖单次 `recv` 的返回长度来界定应用层业务消息的边界在原理上是注定失败的，必须由应用层协议自身承担消息分帧（Framing）职责——例如引入诸如 `\r\n` 的特定分隔符，或是在消息首部开辟固定宽度的字段标明后续载荷长度。

### 3.2 序号推进与累积确认

TCP 采用以字节为基本刻度的双向序号体系。序列号（Sequence Number）代表当前报文段载荷中首个字节在整个流中的绝对偏移量；确认号（Acknowledgment Number）则具有严格的累积性质：它代表接收方期望接收到的下一个字节编号，即向发送方宣告“该编号之前的所有连续字节均已安然收讫”。如果序号发生空洞（如收到了 1～1000 与 2001～3000，但中间的 1001～2000 发生丢包），接收端的确认号将顽固地停留在 1001，促使发送端聚焦补齐缺失的空洞。

### 3.3 拥塞控制：守护网络大动脉

如果说流量控制是保护接收端宿主机的内存，那么拥塞控制（Congestion Control）则是保护整个公网交换节点与骨干链路不致因过载而崩溃。TCP 的发送端维护一个动态的拥塞窗口（cwnd, Congestion Window），发送端在途未确认的字节上限受制于 $\min(\text{cwnd}, \text{rwnd})$。

经典 Reno/NewReno 算法通过慢启动（Slow Start）、拥塞避免（Congestion Avoidance）、快重传与快恢复四个阶段动态探测网络承载力。在早期慢启动阶段，窗口指数级扩张以快速试探可用带宽；一旦触及阈值便转为线性的拥塞避免；当遭遇丢包时，算法会惩罚性地将窗口急剧收缩，这也解释了为何在公网偶发丢包时，下载速率往往会呈现出断崖式下跌随后缓慢爬坡的锯齿状震荡。现代 Linux 默认采用基于延迟变化探测瓶颈容量的 BBR（Bottleneck Bandwidth and RTT）拥塞控制算法，显著平滑了跨洋长肥管道（LFN）下的吞吐抖动。

## 4. C 语言系统编程中的 TCP 接口全景

在基于 POSIX 标准的 C 语言系统编程中，操作系统的网络能力全部通过统一的 BSD 套接字接口抽象暴露：

1. 创建套接字端点：调用 `socket(AF_INET, SOCK_STREAM, 0)` 请求内核分配一个流式套接字，获取一个新打开的文件描述符；
2. 绑定网络地址与监听（服务端）：服务端通过 `bind` 将描述符与指定的本地 IP 地址和监听端口进行绑定，随后调用 `listen` 激活内核连接队列，开始等待外部连接接入；
3. 建立逻辑连接：在客户端侧，调用 `connect` 触发三次握手向目标主机发起连接，函数在握手成功后返回；而在服务端侧，通过调用 `accept` 从内核的已完成连接队列中移出一个已经完成握手的连接，并为该物理连接派生出一个崭新的已连接套接字描述符；
4. 数据全双工吞吐：在已连接的套接字上，程序既可以使用网络专用的 `send` 与 `recv` 系统调用传入高级控制标志，也可以完全依托 Linux“一切皆文件”的设计哲学，直接调用通用的 `read`、`write` 以及实现零拷贝传输的 `sendfile`；
5. 体面断开与资源回收：使用 `close` 关闭套接字，促使内核释放文件描述符引用计数并启动四次挥手；若需精细化管控单向半关闭，则调用 `shutdown` 单独截断读流或写流。
