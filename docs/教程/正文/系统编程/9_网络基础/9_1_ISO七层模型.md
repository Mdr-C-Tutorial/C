# 9.1 ISO 七层模型

## 1. 介绍 ISO 七层模型

### 1.1 七层模型的目的和历史

ISO 七层模型，也称为 OSI 模型 (Open Systems Interconnection)，是国际标准化组织 (International Organization for Standardization, ISO) 为网络通信制定的模型。它把网络通信划分为七个层次，每一层负责特定的功能，以便不同厂商的设备和协议能够按照同一框架互相通信。

这个模型诞生于 20 世纪七八十年代。当时计算机网络发展很快，但不同厂商的网络设备使用各自的协议和通信方式，彼此难以互联，ISO 为此提出了这一模型。

今天实际广泛使用的 TCP/IP 协议族并不严格按照七层划分，七层模型主要用作描述网络协议的参考框架。

### 1.2 七层模型的优势

分层之后，每一层只负责自己的功能，并通过约定的接口使用下一层提供的服务。只要接口不变，某一层的实现就可以单独替换，例如同一套 TCP/IP 协议既可以运行在以太网上，也可以运行在 Wi-Fi 上。分层也为讨论网络协议提供了统一的术语，例如说某个设备工作在“第三层”，就是指它按网络层的地址转发数据。

## 2. 每一层的功能

1. 物理层

   物理层负责传输比特流，它定义了传输介质、电压、连接器和物理拓扑。主要任务是将比特流从发送方传输到接收方，而不关心数据的含义。

2. 数据链路层

   数据链路层处理数据帧的传输和接收，它负责物理地址的识别、错误检测和纠正以及数据的流控制。

3. 网络层

   网络层负责数据包的路由和转发，它使用逻辑地址（如 IP 地址）来决定数据包的最佳路径。

4. 传输层

   传输层负责端到端的数据传输，提供了可靠性和数据流控制。常见的传输层协议包括 TCP（传输控制协议）和 UDP（用户数据报协议）。

5. 会话层

   会话层建立、管理和终止会话，它允许不同设备之间的通信建立会话并保持会话状态。

6. 表示层

   表示层负责数据的编码、解码和加密，以确保数据在不同系统之间的互操作性。

7. 应用层

   应用层直接为应用程序提供网络服务，HTTP、SMTP、FTP 等协议工作在这一层。Web 浏览器、电子邮件客户端等应用程序通过这些协议使用网络。

## 3. 举例说明七层模型的应用

以用 Web 浏览器访问网站为例。点击链接后，浏览器生成一个 HTTP 请求（应用层）。传输层的 TCP 给请求加上端口号等信息，封装成报文段；网络层再加上源 IP 地址和目的 IP 地址，封装成 IP 数据报；数据链路层加上下一跳设备的物理地址，封装成帧；物理层把帧转换为电信号或光信号发送出去。HTTP 通信中没有单独的会话层和表示层协议，这两层的功能通常由应用程序自己完成。

数据经过路由器时，路由器只处理到网络层：它取出 IP 数据报，根据目的 IP 地址选择下一跳，再重新封装成帧发出。因此帧中的物理地址在每一段链路上都会改变，而 IP 地址通常保持不变。数据到达服务器后，从物理层开始逐层向上解封装，最终由 Web 服务器程序处理 HTTP 请求。响应沿相反的方向返回浏览器，由浏览器解析并显示网页。

正文的封装例子只有一段链路。写一个 `path FRAMEFILE HOPS`：读入一个十六进制帧和一个逐跳的转发脚本，模拟它经过两台路由器到达目的主机，每一跳输出一行。

帧文件格式与第 9 章习题数据相同（每行 16 个十六进制字节）。转发脚本每行描述一段链路，写三个字段 `DEV SRC_MAC NEXTHOP_MAC`，表示这一跳从哪个接口发出、源 MAC 换成什么、目的 MAC 换成什么；单独一行 `local` 表示这一跳就是目的主机，不再转发。用下面这个帧（`192.168.1.10:40000` 发往 `203.0.113.5:9999`，负载 `ping`，46 字节）：

```text
02 00 00 00 00 01 02 00 00 00 00 02 08 00 45 00
00 20 2b 1c 40 00 40 11 11 f9 c0 a8 01 0a cb 00
71 05 9c 40 27 0f 00 0c 5f fd 70 69 6e 67
```

转发脚本：

```text
eth0 02:00:00:00:00:02 02:00:00:00:00:0b
eth1 02:00:00:00:00:0c 02:00:00:00:00:0d
local
```

程序的要求：

1. 每处理一行 `DEV SRC_MAC NEXTHOP_MAC`，先按**当前**的 TTL 打印一行 `hop N: dev DEV src SRC_MAC dst NEXTHOP_MAC ttl T`，再把源、目的 MAC 换成给定的值，TTL 减一，重算 IPv4 首部校验和；
2. TTL 已经是 0 时输出 `dropped: TTL exhausted` 并停止，不再写帧；
3. 遇到 `local` 时不再改写帧，直接输出 `local: delivered to UDP port 9999, ttl T`，`T` 是此刻帧里的 TTL（上一次转发已经减过），端口从 UDP 首部的目的端口字段读出；
4. 最后把每一跳改写后的完整帧按十六进制打印出来，便于核对。

验收：上面的输入应输出两行 `hop` 加一行 `local`；`hop` 两行的 TTL 是 64 和 63，`local` 那行是 62，因为第二行转发时把它减了一次；两个转发出去的帧里 IPv4 首部校验和分别是 `0x12f9` 与 `0x13f9`，把各自的首部字节重新求和都是 `0xffff`；目的端口打印 9999。再把输入帧的 TTL 改成 1 并重算它的 IPv4 首部校验和，重新运行：第一跳照常输出 `ttl 1` 并把 TTL 写到 0，第二跳应当输出 `dropped: TTL exhausted` 而不是继续转发。

最后一问：真实的路由器改写了帧里的哪些字段、没改哪些？NAT 设备把源地址换成公网地址时，为什么必须同时改 UDP 或 TCP 的校验和，只改 IPv4 首部校验和不够？

</Exercise>
