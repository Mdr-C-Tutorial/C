# B.5 辅助函数与上下文

[B.3](/教程/正文/系统编程/拓展B_eBPF/B_3_第一个eBPF程序) 的 hello 里有一行 `bpf_get_current_pid_tgid() >> 32`，当时只说它取到了进程号；[B.4](/教程/正文/系统编程/拓展B_eBPF/B_4_程序的解剖_受限的C) 在反汇编里看到这条调用变成 `call 0xe`，也只解释了编号是怎么读出来的。这两件事背后是同一套机制：BPF 程序不能链接 libc，也不能调用任意内核函数，它只能用内核预先准备好的一组辅助函数（helper function），按编号调用。

这一页把这套机制讲透，再讲它的另一面：这些函数读到的上下文（context，代码里写 ctx）到底是什么。写完一个记录每次 `exec` 的工具，需要同时用到进程身份、父进程、命令名、时间和一个长字符串。这几样数据分别来自辅助函数、ctx 和内核内存，读法互不相同。读完这一页，拿到一个内核里的对象，应该能立刻判断它该直接用、该用哪个辅助函数读，还是根本读不到。

本页的 BPF 程序用 zig 自带的 clang 编译，全部目标文件都核对过反汇编与十六进制字节；骨架在 SignalX 上用 `bpftool gen skeleton` 生成，用户态加载程序用 `gcc -fsyntax-only` 检查。凡是要加载进内核才有的输出，照权威资料写成「输出类似」并注明来源。完整程序在 `code/系统编程/拓展B_eBPF/B_5_辅助函数与上下文/` 下。

## 1. 辅助函数是按编号调用的内核函数

### 1.1 声明是一个装着编号的函数指针

libbpf 在 `bpf_helper_defs.h` 里为每个辅助函数写了一条声明。这个文件由内核的文档脚本生成，内容就是内核那份辅助函数表：

::: terminal title="zsh - bpf_helper_defs.h"

```text
$ grep -n 'bpf_get_current_pid_tgid)' bpf_helper_defs.h
378:static __u64 (* const bpf_get_current_pid_tgid)(void) = (void *) 14;
```

:::

读法是：`bpf_get_current_pid_tgid` 是一个 `const` 函数指针，指向地址 `(void *) 14`。这个地址没有任何意义，它不是内核里的真实地址，只是一个编号。调用它时，clang 生成一条 `call` 指令，立即数就是 14。下面这个最小程序只调用它和 `bpf_printk`：

```c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>

char LICENSE[] SEC("license") = "Dual BSD/GPL";

SEC("tp/syscalls/sys_enter_write")
int show_ids(void *ctx)
{
    __u64 id = bpf_get_current_pid_tgid();

    (void)ctx;
    bpf_printk("tgid=%d tid=%d\n", (int)(id >> 32), (int)id);
    return 0;
}
```

编译后用 `readelf -x` 把这个程序所在的节原样倒出来：

::: terminal title="zsh - readelf"

```text
$ clang -g -O2 -target bpf -mcpu=v3 -I. -c ids.bpf.c -o ids.bpf.o
$ readelf -x 'tp/syscalls/sys_enter_write' ids.bpf.o

Hex dump of section 'tp/syscalls/sys_enter_write':
 NOTE: This section has relocations against it, but these have NOT been applied to this dump.
  0x00000000 85000000 0e000000 bf030000 00000000 ................
  0x00000010 77030000 20000000 18010000 00000000 w... ...........
  0x00000020 00000000 00000000 b4020000 10000000 ................
  0x00000030 bc040000 00000000 85000000 06000000 ................
  0x00000040 b4000000 00000000 95000000 00000000 ................
```

:::

第一条指令的 8 个字节是 `85 00 00 00 0e 00 00 00`。按 B.4 讲过的格式拆开：opcode `0x85` 是 `call`，第二个字节 `0x00` 表示源寄存器为 0，也就是按编号调用辅助函数而不是跳到子程序；最低的 4 个字节是立即数 `0x0e`，即 14。第二条 `call 0x6` 是 `bpf_printk` 展开后的 `bpf_trace_printk`，它的编号是 6。

同一个程序用编译器的 `-S` 选项输出汇编，能直接看到这两条调用，其余指令是把 R0 右移 32 位、把两个值分别放进 R3 和 R4，再调用打印（clang 在 `w4 = w0` 后面还会留一行 `# kill: ...` 的寄存器别名注释，与语义无关，这里略去）：

::: terminal title="zsh - clang -S"

```text
show_ids:
	call 14
	r3 = r0
	r3 >>= 32
	r1 = show_ids.____fmt ll
	w2 = 16
	w4 = w0
	call 6
	w0 = 0
	exit
```

:::

`r1 = show_ids.____fmt ll` 是一条占用两个槽位的 64 位立即数加载，装载时由 libbpf 把 `.rodata` 里那个格式串的地址填进去；`w2 = 16` 是格式串的长度，含结尾的空字节。这些在 B.4 里已经逐条走过，这里只确认一点：辅助函数在字节码里没有名字，也没有地址，只有一个编号。

$ grep -o '= (void \*) [0-9]*' bpf_helper_defs.h | tail -1

### 1.2 为什么不能调用任意内核函数

BPF 程序运行在内核里，但它不能像内核模块那样链接并调用任意内核符号。原因有两层。

第一层是接口的稳定性。辅助函数的编号一旦分配就不再变动，参数个数和类型写在内核的 `bpf_func_proto` 结构里，成为内核与用户态之间少数几处明确承诺不变的东西。内核里普通函数的名字、参数和返回值随时可能改，辅助函数不能这样。B.4 讲过的 `bpf_map_lookup_elem` 是 1 号、`bpf_trace_printk` 是 6 号，十年前的程序今天仍然能用同一串编号跑起来。

第二层是加载时的检查能力。验证器（verifier）在加载时逐条检查程序，遇到 `call` 就按编号查到对应的原型，再按原型检查每个参数寄存器的类型。`bpf_probe_read_kernel` 的第一个参数必须是可写的栈或 map 值，第二个参数必须是常量大小（`ARG_CONST_SIZE_OR_ZERO`），第三个参数可以是任意值；`bpf_get_current_comm` 的第二个参数则是 `ARG_MEM_SIZE`，要能对上第一个参数所指缓冲区的大小。如果允许调用任意内核函数，验证器就没有原型可查，也就无法证明这次调用不会把内核写坏。

辅助函数的参数最多五个，这也是验证器与调用约定共同限制的结果：R1 到 R5 五个参数寄存器，R0 放返回值。

能调用哪些，取决于两件事。

一件是程序类型。`bpf-helpers(7)` 开头写得直白：这些函数是一份白名单，不同的程序类型跑在不同的上下文里，所以每种程序类型只能调用其中的一个子集。`bpf_xdp_adjust_head`（44 号）只在 XDP 程序里出现；`bpf_get_stackid`（27 号）只给跟踪、perf 这类程序用，XDP 不能用。哪一类能调哪些，在 [B.10 程序类型与附加类型](/教程/正文/系统编程/拓展B_eBPF/B_10_程序类型与附加类型) 里按类别整理。

另一件是许可证。一部分辅助函数带 GPL 标记，只对 GPL 兼容的程序开放。B.4 已经讲过 license 节，这里补上它的后果：`bpf_probe_read_kernel`、`bpf_probe_read_user`、`bpf_trace_printk` 这几个在 6.12 的内核源码里都是 `gpl_only = true`（`kernel/trace/bpf_trace.c`），许可证写成 `"Proprietary"` 的程序调用它们，加载时会被验证器拒绝，报错原文是 `cannot call GPL-restricted function from non-GPL compatible program`。本章所有例子都用 `"Dual BSD/GPL"`，属于兼容的几种写法之一。

查当前系统支持什么，有两个入口。`bpftool feature list_builtins helpers` 列出 bpftool 自己编译时知道的所有辅助函数，不探测内核，适合在脚本里遍历：

::: terminal title="zsh - bpftool feature list_builtins"

```text
$ bpftool feature list_builtins helpers | wc -l
212
$ bpftool feature list_builtins helpers | sed -n '1,3p'
bpf_unspec
bpf_map_lookup_elem
bpf_map_update_elem
$ bpftool feature list_builtins helpers | tail -3
bpf_user_ringbuf_drain
bpf_cgrp_storage_get
bpf_cgrp_storage_delete
```

:::

212 行里第一行 `bpf_unspec` 是 0 号占位，剩下 211 个与头文件里的声明一一对应。真正探测运行中的内核要用 `bpftool feature probe`，它按程序类型逐个尝试加载，输出哪些辅助函数可用，并跳过 `bpf_trace_printk` 这类会往内核日志里写警告的探测，除非加上 `full`。在程序里查询则用 libbpf 的 `libbpf_probe_bpf_helper(prog_type, helper_id, NULL)`：返回 1 表示这个组合可用，0 表示不可用，负数表示探测本身失败；它要求进程有相应的 `CAP_*` 权限。

常用的辅助函数按用途分成几类，本页用到的是前四类：

| 用途 | 代表 | 编号 |
| --- | --- | --- |
| 进程身份 | `bpf_get_current_pid_tgid`、`bpf_get_current_uid_gid`、`bpf_get_current_comm`、`bpf_get_current_task` | 14、15、16、35 |
| 时间 | `bpf_ktime_get_ns`、`bpf_ktime_get_boot_ns` | 5、125 |
| 读内存 | `bpf_probe_read_kernel`、`bpf_probe_read_kernel_str`、`bpf_probe_read_user`、`bpf_probe_read_user_str` | 113、115、112、114 |
| 调试输出 | `bpf_trace_printk`、`bpf_trace_vprintk` | 6、177 |
| map 访问 | `bpf_map_lookup_elem`、`bpf_map_update_elem`、`bpf_map_delete_elem` | 1、2、3 |
| 网络 | `bpf_xdp_adjust_head`、`bpf_skb_load_bytes` | 44、26 |

最后两类的用法分别在 [B.6](/教程/正文/系统编程/拓展B_eBPF/B_6_Map与数据交换) 和 [B.12](/教程/正文/系统编程/拓展B_eBPF/B_12_网络应用_XDP与tc)。

## 2. 进程身份与时间

任何一行跟踪输出都要标明「是谁」。用户态程序回答这个问题用 `getpid()`，在内核里则用 14 号辅助函数，它一次返回两个数：高 32 位是 tgid，低 32 位是 pid。这两个名字容易混，先把它定下来。

::: concept ebpf-b05-pid-tgid title="用户态的 PID 与内核里的 tgid、pid"

用户态程序调用 `getpid()` 得到的是内核里的 tgid，同一进程的所有线程共用这一个值。内核里的 pid 是线程 ID，也就是用户态 `gettid()` 的返回值。`bpf_get_current_pid_tgid()` 把两者打包进一个 `__u64`：高 32 位是 tgid，低 32 位是 pid。所以要得到用户态说的 PID，写 `>> 32`；要得到线程 ID，直接取低 32 位。

:::

这个说法可以直接在用户态验证。下面这个小程序，完整文件是 `code/系统编程/拓展B_eBPF/B_5_辅助函数与上下文/id_demo.c`，主线程再开一个工作线程，两边分别调用 `getpid()` 和 `gettid()`：

::: terminal title="zsh - id_demo"

```text
$ gcc -std=c17 -Wall -Wextra id_demo.c -o id_demo -pthread
$ ./id_demo
main:   getpid() = 322162, gettid() = 322162
thread: getpid() = 322162, gettid() = 322163
```

:::

每次运行的数值不同，形状不变。主线程的两个值相同，工作线程的 tgid 仍是 322162、tid 变成 322163。BPF 程序在任意一个线程里执行时，`>> 32` 得到的就是第一列，低 32 位是第二列。跟踪类程序按进程聚合时用高 32 位，按线程配对时用低 32 位。后者在 [B.11](/教程/正文/系统编程/拓展B_eBPF/B_11_跟踪与观测_kprobe_uprobe与tracepoint) 里统计单次调用耗时会用到；前者在 [B.6](/教程/正文/系统编程/拓展B_eBPF/B_6_Map与数据交换) 里作为 map 的键。

15 号 `bpf_get_current_uid_gid` 的打包方式相同，只是两半换成 uid 和 gid，低 32 位是 uid、高 32 位是 gid。16 号 `bpf_get_current_comm` 把当前任务的 comm 复制到调用者给的缓冲区，长度 16 字节（`TASK_COMM_LEN`），缓冲区必须在栈上或 map 值里，验证器要能确认它可写。

时间有两个来源。`bpf_ktime_get_ns`（5 号）返回开机以来的纳秒数，不含系统休眠的时间，对应 `CLOCK_MONOTONIC`；`bpf_ktime_get_boot_ns`（125 号）含休眠时间，对应 `CLOCK_BOOTTIME`。两个值都只适合算间隔，不表示具体时刻。要留一个绝对的时间戳，得再加上开机时刻或者别的基准，主线[第 6 章](/教程/正文/系统编程/6_信号_时间与定时器)讲过这几种时钟的区别，以及为什么测量间隔要用单调时钟。这两个辅助函数在 [B.6](/教程/正文/系统编程/拓展B_eBPF/B_6_Map与数据交换) 的进程存活时间统计和 [B.11](/教程/正文/系统编程/拓展B_eBPF/B_11_跟踪与观测_kprobe_uprobe与tracepoint) 的调用耗时统计里都会用到。

把这几样合起来，就是一个能用的身份记录：

```c
SEC("tp/syscalls/sys_enter_write")
int show_identity(void *ctx)
{
    __u64 id;
    __u64 ug;
    __u64 now;
    char comm[16];

    (void)ctx;
    id = bpf_get_current_pid_tgid();
    ug = bpf_get_current_uid_gid();
    now = bpf_ktime_get_ns();
    bpf_get_current_comm(comm, sizeof(comm));

    bpf_printk("tgid=%u tid=%u uid=%u gid=%u comm=%s t=%llu\n",
               (__u32)(id >> 32), (__u32)id, (__u32)ug, (__u32)(ug >> 32), comm,
               now);
    return 0;
}
```

它的调用序列在汇编里是 `call 14`、`call 15`、`call 5`、`call 16`、`call 177`：前四个分别取身份、用户、时间和命令名；最后一个不是 6 而是 177，因为 `bpf_printk` 这次带了六个参数，宏改用了 `bpf_trace_vprintk`。这个选择由参数个数决定，B.4 提过一句，第 5 节会再看一次。

## 3. 读内存：哪些能直接读

BPF 程序里的指针不是想解引用就能解引用。验证器在加载时检查每一次内存访问，能直接访问的只有它认得类型的几块内存；其余地址必须交给辅助函数，由内核在运行时检查地址是否可读，读失败也不会让程序崩溃。

| 内存 | 能不能直接读 | 读法 |
| --- | --- | --- |
| ctx 指向的记录 | 能 | `ctx->field`，验证器按程序类型检查字段 |
| 栈 | 能 | 局部数组，边界由验证器跟踪 |
| map 的值 | 判空后能 | `bpf_map_lookup_elem` 的返回值，B.6 |
| 带 BTF 类型的指针 | 能 | fentry 参数、`bpf_get_current_task_btf` 的返回值，B.8 |
| 其它内核内存 | 不能 | `bpf_probe_read_kernel`、`bpf_probe_read_kernel_str` |
| 用户空间内存 | 不能 | `bpf_probe_read_user`、`bpf_probe_read_user_str` |

前四种之所以能直接读，是因为验证器知道这块内存的来路：ctx 的类型由程序类型决定，栈是编译器分配并记录了长度的，map 值在判空之后大小已知，带 BTF 类型的指针则带着完整的类型信息。后两种不行：地址只是一个整数，验证器不知道它指向哪里、有多大、当前是否有效。

读内核内存的典型用法是沿着指针走两步。`bpf_get_current_task`（35 号）返回当前任务的地址，但它的返回值是一个整数，不是指针；要取父进程的 tgid，得先用 `bpf_probe_read_kernel` 把父进程指针读出来，再读一次拿到 tgid：

```c
struct task_struct *task;
struct task_struct *parent;
pid_t ppid;

task = (struct task_struct *)bpf_get_current_task();
bpf_probe_read_kernel(&parent, sizeof(parent), &task->real_parent);
bpf_probe_read_kernel(&ppid, sizeof(ppid), &parent->tgid);
```

这段代码编译出来是 `call 35`、`call 113`、`call 113`，两条读取之间没有别的指令。`BPF_CORE_READ` 把这两步写成一行：

```c
ppid = (pid_t)BPF_CORE_READ(task, real_parent, tgid);
```

它展开后仍然是一串 `bpf_probe_read_kernel`，编译出的调用序列与上面两种写法完全相同，都是 `call 35`、`call 113`、`call 113`。区别在于 `BPF_CORE_READ` 会为每个成员访问留下 CO-RE 重定位记录，换一台内核时 libbpf 按目标内核的 BTF 改写偏移；手写 `&task->real_parent` 在包含 `vmlinux.h` 时同样会产生重定位，效果一样，只是代码更长。重定位的原理在 [B.8](/教程/正文/系统编程/拓展B_eBPF/B_8_libbpf_BTF与CO_RE)。

写成直接解引用会怎样？把上面三行换成 `ppid = task->real_parent->tgid;`，编译照常通过，生成的是两条普通加载指令：

::: terminal title="zsh - 直接解引用"

```text
call 35
r1 = *(u64 *)(r0 + 2448)
w3 = *(u32 *)(r1 + 2436)
call 6
```

:::

加载时验证器在第二条指令上停下：R0 的类型是标量（`bpf_get_current_task` 的返回值在验证器眼里只是一个整数），拿它当地址去读内存，日志里是 `R0 invalid mem access 'scalar'`。`2448` 和 `2436` 是本机内核里 `real_parent` 与 `tgid` 的偏移，换一台机器就变，这也是不能写死的原因之一。

`_str` 后缀的版本用于字符串。它在遇到空字节时停止，返回值是写入的字节数（含结尾的空字节），字符串比缓冲区短时剩余部分不补零。读用户空间内存时把上面的 `_kernel` 换成 `_user`，其余写法不变。`openat` 的路径参数指向用户空间，在系统调用入口处还没有拷进内核，只能走 `bpf_probe_read_user_str`：

在 `sys_enter_openat` 的 tracepoint 程序里，要读出第二个参数指向的路径字符串，应该用哪个辅助函数？

</template>

正确答案是 **B**。`openat` 的第二个参数是用户空间地址，在系统调用入口处路径还没有复制进内核，所以要用读用户空间内存的版本。A 的 `_kernel` 版本读的是内核地址，用在这里会失败或读到无关内容。C 错在 ctx 里的字段可以直接读，但字段里装的指针指向哪里，验证器并不知道。D 的 `bpf_get_current_comm` 读的是进程名，与路径无关。更完整的例子见 [B.11](/教程/正文/系统编程/拓展B_eBPF/B_11_跟踪与观测_kprobe_uprobe与tracepoint)。

</Quiz>

## 4. 上下文就是 R1

程序入口处 R1 里放着上下文指针，这是 B.4 的寄存器表里写过的调用约定。这一节要说的是它指向什么。

ctx 的类型由程序类型和附加类型共同决定，验证器按这个类型检查每一次 `ctx->field`：字段的偏移对不对、读的长度有没有越界、这个类型能不能写。所以同一个 C 表达式在不同类型的程序里含义完全不同，把 `SEC("tp/...")` 改成 `SEC("xdp")` 之后再去读 `ctx->args[1]`，加载会被拒绝，原因见 [B.10](/教程/正文/系统编程/拓展B_eBPF/B_10_程序类型与附加类型)。

### 4.1 tracepoint 的 ctx

tracepoint 程序的 ctx 指向内核填好的一条跟踪记录。`vmlinux.h` 里为每个事件生成了一个 `struct trace_event_raw_<事件名>`，字段与 tracefs 中该事件的 `format` 文件一致：

::: terminal title="zsh - vmlinux.h"

```text
$ grep -A 5 'struct trace_event_raw_sys_enter {' vmlinux.h
struct trace_event_raw_sys_enter {
	struct trace_entry ent;
	long int id;
	long unsigned int args[6];
	char __data[0];
};

$ grep -A 6 'struct trace_event_raw_sched_process_exec {' vmlinux.h
struct trace_event_raw_sched_process_exec {
	struct trace_entry ent;
	u32 __data_loc_filename;
	pid_t pid;
	pid_t old_pid;
	char __data[0];
};
```

:::

系统调用类的记录是统一的：`id` 是系统调用号，`args[6]` 是六个原始参数，没有 `dfd`、`pathname` 这样的名字。`sched_process_exec` 则有一个 `__data_loc_filename`。名字里的「loc」表示这个字段存的不是字符串，而是字符串在这次跟踪记录里的位置：

- 低 16 位是相对于记录开头的偏移；
- 高 16 位是长度，包含结尾的空字节。

这个编码不是某个结构体的特殊设计，而是所有 `__dynamic_array` 字段的通用做法。内核的事件定义里，`__string(filename, bprm->filename)` 展开成 `__dynamic_array(char, filename, -1)`，再展开成 `u32 __data_loc_filename;`；记录大小在编译时定不下来，于是运行时把偏移塞进这个 32 位整数。内核源码的注释写得很清楚：`__dynamic_array` 为每个数组生成一个 u32，保存它相对事件开头的偏移，数组大小编码在这个 u32 的高 16 位。

所以读文件名要分两步：先算出地址 `(const char *)ctx + (ctx->__data_loc_filename & 0xFFFF)`，再把它交给 `bpf_probe_read_kernel_str`。这一段编译出来是：

::: terminal title="zsh - clang -S"

```text
r3 = r1
w1 = *(u32 *)(r3 + 8)
w1 &= 65535
r3 += r1
r1 = r6
w2 = 64
call 115
```

:::

`*(u32 *)(r3 + 8)` 读的是 `__data_loc_filename`，偏移 8 来自它前面那个 `struct trace_entry`；`&= 65535` 取低 16 位；`r3 += r1` 把偏移加到 ctx 上，得到字符串在记录里的地址。长度那一半这里没有用，`bpf_probe_read_kernel_str` 靠空字节自己判断何时停。

注意 `ctx` 里的字段本身可以直接读，指针指向的字符串不行。`ctx->pid`、`ctx->__data_loc_filename` 都由验证器按固定的编译期偏移检查；而字符串的位置存在低 16 位里，运行时才知道，验证器只能检查常量偏移的 ctx 访问，算不出这个偏移有没有越界，所以只能交给辅助函数。这段内存其实就在同一条记录里、紧跟在固定字段之后，用读内核内存的版本即可。

<Quiz
  type="single"
  :options="[
    { label: '它就是一个普通指针，直接解引用即可', value: 'A' },
    { label: '取低 16 位作为相对 ctx 的偏移，加上 ctx 后交给 bpf_probe_read_kernel_str', value: 'B' },
    { label: '取高 16 位作为偏移，低 16 位是长度', value: 'C' },
    { label: '它保存的是字符串的绝对内核地址，直接打印', value: 'D' }
  ]"
  answer="B"
>

<template #question>

tracepoint 结构体里的 `__data_loc_filename` 字段应该怎么读？

</template>

正确答案是 **B**。低 16 位是相对这条跟踪记录开头的偏移，高 16 位是长度（含结尾的空字节）。A 错在它存的是整数而不是指针；C 把两半的含义弄反了；D 错在偏移是相对的，不是绝对地址，而且即使拿到绝对地址也要用辅助函数读。

</Quiz>

### 4.2 kprobe 的 ctx

kprobe 程序的 ctx 是 `struct pt_regs`，内容是被探测函数入口处的寄存器快照。x86-64 上前六个整数参数放在 `di`、`si`、`dx`、`cx`、`r8`、`r9`，按这个顺序，它们在 `pt_regs` 里的偏移是 112、104、96、88、72、64 字节。偏移不与参数序号同向递增，因为 `struct pt_regs` 把寄存器按 r15 到 ax 倒着排在前面，`di` 排在 `si` 之后。

手写这些偏移太容易错，libbpf 的 `bpf_tracing.h` 提供了 `BPF_KPROBE` 宏：

```c
SEC("kprobe/do_unlinkat")
int BPF_KPROBE(unlink_ctx, int dfd, struct filename *name)
{
    bpf_printk("dfd=%d name=%s\n", dfd, BPF_CORE_READ(name, name));
    return 0;
}
```

宏把函数体包进一个接收 `struct pt_regs *ctx` 的包装函数，按参数位置从 `pt_regs` 里取值，再转成声明的类型。展开之后，`name` 来自 `r1 + 104`（`si`），`dfd` 来自 `r1 + 112`（`di`）：

::: terminal title="zsh - clang -S"

```text
r3 = *(u64 *)(r1 + 104)
r2 = 0
r3 += r2
r6 = *(u64 *)(r1 + 112)
r1 = r10
r1 += -8
w2 = 8
call 113
r4 = *(u64 *)(r10 - 8)
call 6
```

:::

`call 113` 就是 `BPF_CORE_READ(name, name)`：先读 `name->name` 这个指针到栈上，再交给后面的打印。为什么不能直接 `name->name`，第 3 节已经说了：`name` 在宏展开后只是一个从 `pt_regs` 里取出的整数，验证器不认为它是指针。

`BPF_KPROBE` 依赖目标架构的寄存器布局，所以编译时必须定义 `__TARGET_ARCH_x86`。漏掉这一项，编译直接失败，B.11 里有完整的报错。

### 4.3 fentry 的 ctx

fentry 和 fexit 程序走的是另一条路：BPF 蹦床在函数入口把参数按 BTF 里的函数原型打包成一个 `u64` 数组传进来。`BPF_PROG` 宏按声明的参数列表从这个数组里取，取出来的值带着类型：

```c
SEC("fentry/do_unlinkat")
int BPF_PROG(unlink_ctx, int dfd, struct filename *name)
{
    bpf_printk("dfd=%d name=%s\n", dfd, name->name);
    return 0;
}
```

`name->name` 是普通的成员访问，clang 生成一次带 CO-RE 重定位的加载，没有 `bpf_probe_read_kernel`。两个版本的汇编放在一起，差别一目了然：

::: compare vertical left-title="kprobe：从 pt_regs 取，读成员要辅助函数" right-title="fentry：参数带类型，可以直接读"

```text
r3 = *(u64 *)(r1 + 104)     # name，第二个参数（si）
r6 = *(u64 *)(r1 + 112)     # dfd，第一个参数（di）
call 113                    # BPF_CORE_READ 读 name->name
r4 = *(u64 *)(r10 - 8)      # 取回读到的指针
w3 = w6                     # dfd 作为第一个打印参数
call 6                      # bpf_printk
```

---

```text
r2 = *(u64 *)(r1 + 8)       # name
r4 = *(u64 *)(r2 + 0)       # name->name，直接加载
r3 = *(u64 *)(r1 + 0)       # dfd
call 6                      # bpf_printk
```

:::

两栏都略去了与取参数无关的指令：左边省掉了 `r2 = 0`、`r3 += r2` 这条把参数平移 0 字节的加法（`BPF_CORE_READ` 展开后固定会生成它），右边省掉了格式串与长度的装入。

fentry 的 ctx 数组里第 0 个元素就是第一个参数，所以 `dfd` 在 `r1 + 0`、`name` 在 `r1 + 8`，与 kprobe 的 112、104 完全是两套编号。这也是为什么同一个函数、同一件事，两种写法的取参部分不能互相抄。

网络程序的 ctx 又是另外两种结构：XDP 是 `struct xdp_md`，tc 是 `struct __sk_buff`，字段的用法在 [B.12](/教程/正文/系统编程/拓展B_eBPF/B_12_网络应用_XDP与tc)。

::: generate ebpf-b05-ctx-forms kind=explanation

面向刚学完 `pt_regs` 与寄存器传参、但还没写过 fentry 的读者，以同一个 `do_unlinkat` 为例，对比 tracepoint、kprobe、fentry 三种 ctx 的来源：tracepoint 的 ctx 是内核填好的字段记录，kprobe 的 ctx 是入口处的寄存器快照，fentry 的 ctx 是蹦床按 BTF 原型打包的参数数组。重点讲清三件事：为什么 kprobe 要指定 `__TARGET_ARCH_x86` 而 fentry 不用；为什么 kprobe 里 `name` 必须再走一次 `BPF_CORE_READ`；为什么 fentry 的 `r1 + 8` 和 kprobe 的 `r1 + 104` 指向同一个参数却差这么远，以及 `pt_regs` 的偏移为什么不按参数序号递增。不要展开 CO-RE 的重定位细节，那是 B.8 的内容。

:::

## 5. 完整示例：记录每次 exec

把前面几节拼起来，写一个记录每次 `exec` 的工具：进程号、父进程号、uid、命令名、完整路径，一样一行。完整的两个文件在 `code/系统编程/拓展B_eBPF/B_5_辅助函数与上下文/` 下，内核态部分照录：

```c
// SPDX-License-Identifier: GPL-2.0 OR BSD-3-Clause
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_core_read.h>

char LICENSE[] SEC("license") = "Dual BSD/GPL";

SEC("tp/sched/sched_process_exec")
int handle_exec(struct trace_event_raw_sched_process_exec *ctx)
{
    struct task_struct *task;
    char filename[256];
    char comm[16];
    __u64 id;
    __u32 uid;
    __u32 offset;
    pid_t pid;
    pid_t ppid;

    id = bpf_get_current_pid_tgid();
    pid = (pid_t)(id >> 32);
    uid = (__u32)bpf_get_current_uid_gid();
    bpf_get_current_comm(comm, sizeof(comm));

    task = (struct task_struct *)bpf_get_current_task();
    if (task == 0) {
        return 0;
    }
    ppid = (pid_t)BPF_CORE_READ(task, real_parent, tgid);

    offset = ctx->__data_loc_filename & 0xFFFF;
    bpf_probe_read_kernel_str(filename, sizeof(filename),
                              (const char *)ctx + offset);

    bpf_printk("EXEC pid=%d ppid=%d uid=%u comm=%s file=%s\n", pid, ppid, uid,
               comm, filename);
    return 0;
}
```

几个细节值得停一下。

`ctx` 的类型直接写成 `struct trace_event_raw_sched_process_exec *`，这样 `ctx->__data_loc_filename` 和 `ctx->pid` 都能直接用，验证器按 tracepoint 的规则检查。写 `void *ctx` 也行，只是每次访问都要自己加转换。

`bpf_get_current_task` 之后立刻判空，再交给 `BPF_CORE_READ`。辅助函数的返回值在验证器眼里是标量，判不判空不会影响它能否通过，这里判空是防止内核里真的拿到空指针。

`__data_loc_filename` 只取低 16 位。高 16 位的长度不用，因为 `bpf_probe_read_kernel_str` 遇到空字节就停，超长时把结果截断到缓冲区大小。缓冲区 256 字节，足以放下绝大多数可执行文件路径；更长的路径会显示成前 255 个字节。

最后一行 `bpf_printk` 带了五个参数，宏会选 `bpf_trace_vprintk`。这个目标文件里真正出现的调用序列是：

| 指令序号 | 调用 | 用途 |
| --- | --- | --- |
| 1 | `call 14` | `bpf_get_current_pid_tgid` |
| 3 | `call 15` | `bpf_get_current_uid_gid` |
| 8 | `call 16` | `bpf_get_current_comm` |
| 9 | `call 35` | `bpf_get_current_task` |
| 17 | `call 113` | `BPF_CORE_READ` 的第一步，读 `real_parent` |
| 24 | `call 113` | 第二步，读 `tgid` |
| 34 | `call 115` | `bpf_probe_read_kernel_str` |
| 53 | `call 177` | `bpf_trace_vprintk` |

序号不连续，是因为两次调用之间还有搬参数、算地址的指令。`call 115` 与 `call 177` 之间有五条 `*(u64 *)(r10 - N)` 写栈指令，把待打印的五个值逐个摆到栈上再整块传过去，这与 B.4 看到的现象一致。`call 177` 而不是 `call 6`，是参数超过三个的直接后果。

用户态加载程序沿用 B.3 的四步。骨架生成后，`progs` 结构里每个程序一个成员：

$ sed -n '13,24p' execlog.skel.h

## 6. kfunc

辅助函数的编号是固定的，增加一个新功能就要申请一个新编号，而编号一旦用掉就不能回收；参数类型也只能用验证器预先认识的几种。内核后来引入了另一套机制：kfunc（内核函数）。内核里普通的函数加上 `__bpf_kfunc` 标记，再注册进某个 kfunc 集合，BPF 程序就能直接调用它。`bpf_task_from_pid` 就是其中之一。

代价是稳定性。内核文档 *BPF kfuncs* 第一句就写明，kfunc 与普通辅助函数不同，没有稳定的接口，内核版本之间可以随时改；它属于内核与内核之间的接口，不受内核与用户态之间那些稳定性约束。换句话说，一个能加载的 kfunc 调用，换一个内核版本可能连名字都找不到。

用法上，kfunc 在 C 里就是一个普通的 `extern` 函数声明，加上 `__ksym` 属性。`vmlinux.h` 里已经写好了这些声明：

::: terminal title="zsh - kfunc 原型"

```text
$ grep -n 'bpf_task_from_pid\|bpf_task_release' vmlinux.h
127682:extern struct task_struct *bpf_task_from_pid(s32 pid) __weak __ksym;
127684:extern void bpf_task_release(struct task_struct *p) __weak __ksym;
```

:::

调用写起来和普通函数一样：

```c
struct task_struct *task;

task = bpf_task_from_pid(1);
if (task == 0) {
    return 0;
}
bpf_printk("tgid=%d\n", task->tgid);
bpf_task_release(task);
```

编译后这条调用不是 `call 编号`，而是 `call bpf_task_from_pid`，后面跟一条 `R_BPF_64_32` 重定位：

::: terminal title="zsh - readelf -r"

```text
$ readelf -r kf.o

Relocation section '.reltp/sched/sched_process_exec' at offset 0x8bae0 contains 3 entries:
  Offset          Info           Type           Sym. Value    Sym. Name
000000000008  000c0000000a R_BPF_64_32       0000000000000000 bpf_task_from_pid
000000000020  000500000001 R_BPF_64_64       0000000000000000 .rodata
000000000050  000d0000000a R_BPF_64_32       0000000000000000 bpf_task_release
```

:::

重定位类型是 `R_BPF_64_32`，和辅助函数调用的立即数不是一回事。libbpf 在加载时按名字查目标内核的 BTF，找到这个函数的 BTF 标识，再把指令的源寄存器改成 `BPF_PSEUDO_KFUNC_CALL`、立即数填成标识。找不到时它不会当场报错：libbpf 把指令改成一条编号为 `2002000000 + 序号` 的调用，验证器随后报 `invalid func unknown#...`。这个编号与 B.8 讲的 CO-RE 失败标记不是同一个值，后者用于内核数据访问，这里是解不开的 kfunc。

`bpf_task_from_pid` 返回的是一个引用，用完必须 `bpf_task_release`。这不是惯例，是内核在注册时标的：它的标记是 `KF_ACQUIRE | KF_RET_NULL`，验证器会跟踪这个引用的生命周期，漏掉释放的程序加载不过去。类似的还有 `bpf_task_acquire`、`bpf_cgroup_acquire`。

作者的建议很简单：能用辅助函数就用辅助函数。`bpf_get_current_task` 能拿到当前任务，就不必用 `bpf_task_from_pid` 再去查一次；只有当需要的功能确实只有 kfunc 提供时，才接受它随内核版本变化的代价。写跨内核版本分发的工具尤其如此，kfunc 的调用点要放在能检测存在性的分支后面，或者干脆不用。

### 7.1 巩固

下面这段十六进制是某次编译后 `tp/syscalls/sys_enter_write` 节的前 32 个字节：

0x00000000 85000000 0e000000 bf030000 00000000
