# B.2 环境准备与工具链

上一页说明了 eBPF 在系统中的位置：一段小程序经过验证，挂到内核的钩子上，和用户态交换数据。要把那张图变成一台能动手的机器，还差一套工具。它们分散在四个地方：内核里的配置、clang、libbpf 和 bpftool。少装一样，后面某一节就会卡住，而报错通常看不出缺的是哪一样。

这一页把 Debian 13 上的环境从头装一遍并逐项检查：确认内核带 BTF，装好 clang 与 LLVM、libbpf-dev、bpftool，生成 `vmlinux.h`，弄清每条命令前面的 `sudo` 是从哪里来的。做完之后，机器上应该能编译 BPF 程序、能生成骨架、能确认加载所需的条件。第一个完整程序留给 [B.3](/教程/正文/系统编程/拓展B_eBPF/B_3_第一个eBPF程序)。版本以 Debian 13（内核 6.12、clang 19、libbpf 1.5、bpftool 7.5）为准；Ubuntu 24.04 的包名和命令相同（libbpf-dev 是 1.3.0），WSL2 的差别在相应位置说明。

## 1. 需要准备什么

把 [B.1](/教程/正文/系统编程/拓展B_eBPF/B_1_eBPF概览) 的架构图按工具拆开，需要的东西不多，但每一样都有明确的分工。下表是 Debian 13 的清单，版本取自 trixie 软件源，可以用 `apt-cache policy` 逐条核对。

| 组件 | 作用 | Debian 13 的包 | 版本 |
| --- | --- | --- | --- |
| 内核 | 提供 `bpf()`、验证器、即时编译（just-in-time compilation，JIT）与各类钩子 | linux-image-amd64 | 6.12.113-1（本页的机器上跑的是 6.12.86+deb13-amd64） |
| 内核 BTF | 描述内核里的类型，是 `vmlinux.h` 与 CO-RE 的数据来源 | 随内核提供，没有单独的包 | — |
| clang | 把 `.bpf.c` 编译成 BPF 目标文件（object file，`.bpf.o`） | clang、clang-19 | 1:19.0-63、19.1.7-3+b1 |
| LLVM 工具 | `llc`、`llvm-objdump`、`llvm-readelf`，用来检查目标文件 | llvm、llvm-19 | 1:19.0-63、19.1.7-3+b1 |
| libbpf | 用户态加载库、BPF 侧头文件、`libbpf.pc` | libbpf-dev | 1:1.5.0-3 |
| bpftool | 生成 `vmlinux.h` 与骨架（skeleton），查看内核中已有的对象 | bpftool | 7.5.0+6.12.113-1 |
| libelf、zlib | libbpf 的依赖，编译用户态程序时要链接 | libelf-dev、zlib1g-dev | 0.192-4、1.3.1 |
| make、gcc、pkg-config | 构建并链接用户态程序 | make、gcc、pkg-config | 4.4.1、14.2.0、1.8.1 |
| bpftrace（可选） | 用一行命令做临时排查，[B.14](/教程/正文/系统编程/拓展B_eBPF/B_14_bpftrace与编程工具链) 用 | bpftrace | 0.23.2-1 |

这些部件在构建和运行中的位置可以用一张图说明：左边的 clang 负责编译，中间的 bpftool 从内核的 BTF 生成头文件，底部是运行时。

```mermaid
flowchart LR
    SRC["x.bpf.c"] -->|"clang -target bpf -g"| OBJ["x.bpf.o"]
    KBTF["/sys/kernel/btf/vmlinux"] -->|"bpftool btf dump"| VH["vmlinux.h"]
    VH --> SRC
    OBJ -->|"bpftool gen skeleton"| SKEL["x.skel.h"]
    SKEL -->|"cc + pkg-config libbpf"| BIN["./x"]
    BIN -->|"open / load / attach"| KER["内核：验证器、JIT、钩子"]
```

映射（map）和事件输出没有画出来，它们由内核态程序在运行时访问，属于 [B.6](/教程/正文/系统编程/拓展B_eBPF/B_6_Map与数据交换) 的内容。

::: concept ebpf-env-toolchain-roles title="四个部件各管一段"

clang 把 `.bpf.c` 编译成 BPF 目标文件，里面除了程序指令，还有 BTF 与重定位信息。libbpf 是用户态库，在运行时读取这个目标文件，按目标内核的 BTF 修正指令，再通过 `bpf()` 系统调用把它交给内核。bpftool 是命令行工具，用 `btf dump` 从内核 BTF 生成 `vmlinux.h`，用 `gen skeleton` 把目标文件转成 C 头文件。内核 BTF 在 `/sys/kernel/btf/vmlinux`，由内核自身构建时生成，是前面三者共同的类型来源。

:::

libbpf-dev 包里具体有什么，值得先知道，后面找头文件和查版本都靠它。Debian 13 的包中有 `/usr/include/bpf/` 下的一组头文件（`bpf.h`、`libbpf.h`、`bpf_helpers.h`、`bpf_tracing.h`、`bpf_core_read.h` 等）、`/usr/lib/x86_64-linux-gnu/libbpf.a`、`libbpf.so`，以及 `/usr/lib/x86_64-linux-gnu/pkgconfig/libbpf.pc`。而 bpftool 包只装一个 `/usr/sbin/bpftool` 和它的手册页。

::: tip bpftool 装在 `/usr/sbin`

普通用户的 `PATH` 通常不含 `/usr/sbin`，直接敲 `bpftool` 会提示找不到命令。用完整路径 `/usr/sbin/bpftool`，或者按本章的做法统一写成 `sudo bpftool`。

:::

## 2. 选择运行环境

eBPF 程序运行在 Linux 内核里，所以需要一台能拿到 root 的 x86-64 Linux。推荐用 Debian 13 的虚拟机：系统干净，内核和软件源的版本与本章一致，弄坏了直接重建。物理机也可以，但内核版本低于 6.6 时 [B.12](/教程/正文/系统编程/拓展B_eBPF/B_12_网络应用_XDP与tc) 的 tcx 用不了。

Windows 读者有两个选择。WSL2 的内核是微软自己构建的 6.6 内核，配置里 `CONFIG_BPF_SYSCALL`、`CONFIG_BPF_JIT`、`CONFIG_DEBUG_INFO_BTF`、`CONFIG_BPF_LSM`、`CONFIG_KPROBES`、`CONFIG_UPROBE_EVENTS`、`CONFIG_BPF_EVENTS` 都是 `y`，本章的例子大多能直接跑，差别只在 PID 命名空间，[B.3](/教程/正文/系统编程/拓展B_eBPF/B_3_第一个eBPF程序) 会用一句话说明。另一条路是在虚拟机里装 Debian 13，与本章环境完全一致。容器需要额外特权才能加载 BPF 程序，还要处理 BTF 的挂载，不适合初学时折腾。

::: warning 练习不要用生产服务器

加载 BPF 程序会影响整台机器的内核行为，写错的程序可能挂错钩子、打印海量日志，甚至让某个系统调用变慢。在本机或虚拟机里练，不要在跑着业务的生产服务器上试。

:::

## 3. 检查内核

先确认内核版本，它决定了哪些特性可用。

::: terminal title="bash - uname"

```console
$ uname -r
6.12.86+deb13-amd64
```

:::

内核是否带 BTF，看一个文件就够：`ls -l /sys/kernel/btf/vmlinux`。

文件存在且非空，说明内核构建时启用了 `CONFIG_DEBUG_INFO_BTF`，并把类型信息编进了内核镜像；内核启动时把它导出成这个只读文件（权限 `0444`，所有用户可读）。文件不存在，后面的 `bpftool btf dump` 就没有输入，CO-RE 也无从谈起。文件大小随内核版本和配置变化，几 MB 到十几 MB 都正常。

再查编译选项。Debian 13 的 amd64 内核配置里，与本章有关的几项是：

```text
CONFIG_BPF_SYSCALL=y
CONFIG_BPF_JIT=y
CONFIG_BPF_UNPRIV_DEFAULT_OFF=y
CONFIG_BPF_LSM=y
CONFIG_KPROBES=y
CONFIG_UPROBE_EVENTS=y
CONFIG_DEBUG_INFO_BTF=y
```

在自己的机器上用 `grep -E "CONFIG_(BPF_SYSCALL|BPF_JIT|DEBUG_INFO_BTF|BPF_UNPRIV_DEFAULT_OFF)=" /boot/config-$(uname -r)` 核对，命令里的 `$(uname -r)` 会展开成当前内核的版本号，输出应与上面前四项一致。

`CONFIG_BPF_SYSCALL` 是 `bpf()` 系统调用本身，没有它什么都做不了。`CONFIG_BPF_JIT` 让程序在加载后被翻译成本机指令，缺了它内核会退回解释执行，能跑但慢。`CONFIG_DEBUG_INFO_BTF` 决定 `/sys/kernel/btf/vmlinux` 是否存在。`CONFIG_BPF_UNPRIV_DEFAULT_OFF` 让 `kernel.unprivileged_bpf_disabled` 的默认值变成 2，也就是默认禁止非特权用户使用 BPF，第 6 节会用到。

::: tip tracefs 在哪

跟踪程序的输出可以从 `/sys/kernel/tracing/trace_pipe` 读。旧资料里写的 `/sys/kernel/debug/tracing/trace_pipe` 是 debugfs 挂载点的老路径，现在的内核把 tracefs 单独挂到 `/sys/kernel/tracing`，两个路径通常都能用，新代码写前者。

:::

  type="single"
  :options="[

    { label: '/sys/kernel/btf/vmlinux', value: 'B' },

    { label: '/sys/fs/bpf', value: 'D' }

  answer="B"
>

<template #question>

哪个文件存在，就说明当前内核带有 BTF？

</template>

正确答案是 **B**。`/sys/kernel/btf/vmlinux` 是内核把自己构建时生成的 BTF 导出成的只读文件，存在即说明 `CONFIG_DEBUG_INFO_BTF` 已启用。A 是内核配置文本，能看出选项但不能证明运行中的内核与它一致；C 是内核符号表；D 是 BPF 文件系统（bpffs），用来固定对象，与 BTF 无关。

</Quiz>

## 4. 安装工具链

Debian 13 上一条命令装齐（bpftrace 可选，本页用不到，[B.14](/教程/正文/系统编程/拓展B_eBPF/B_14_bpftrace与编程工具链) 会讲）：

::: terminal title="bash - apt install"

```console
$ sudo apt install clang llvm libbpf-dev bpftool libelf-dev zlib1g-dev make gcc pkg-config
$ sudo apt install bpftrace
```

:::

`clang` 和 `llvm` 这两个包是元包，实际装上的是 `clang-19` 与 `llvm-19`，可执行文件在 `/usr/lib/llvm-19/bin`，`/usr/bin/clang`、`/usr/bin/llc` 这些名字指向它们。`libelf-dev` 与 `zlib1g-dev` 不是可选项：libbpf 依赖它们，`libbpf.pc` 的 `Requires.private` 里写的就是 `libelf zlib`。动态链接时 pkg-config 只给出 `-lbpf`，libelf 和 zlib 随 `libbpf.so` 一起被载入；静态链接（`pkg-config --static --libs libbpf`）时才会补上 `-lelf -lz`。

装完先看 clang 的版本（输出类似，版本号后的修订号与 `InstalledDir` 随安装方式而变）：

::: terminal title="bash - clang --version"

```console
$ clang --version
Debian clang version 19.1.7
Target: x86_64-pc-linux-gnu
Thread model: posix
InstalledDir: /usr/lib/llvm-19/bin
```

:::

clang 要能生成 BPF，靠的是 LLVM 里的 BPF 后端。用 `llc --version` 确认，输出类似：

::: terminal title="bash - llc --version"

```console
$ llc --version
LLVM (http://llvm.org/):
  LLVM version 19.1.7
  Optimized build.
  Default target: x86_64-pc-linux-gnu
  Host CPU: skylake

  Registered Targets:
    aarch64    - AArch64 (little endian)
    ...
    bpf        - BPF (host endian)
    bpfeb      - BPF (big endian)
    bpfel      - BPF (little endian)
    ...
    x86-64     - 64-bit X86: EM64T and AMD64
```

:::

只要 `bpf`、`bpfeb`、`bpfel` 三行在列表里，clang 就能处理 BPF 目标。中间省略的其它目标与本章无关，列表内容随构建配置变化。Debian 13 的 `libLLVM.so.19.1` 里确实带这三个 BPF 目标：用 LLVM 的 C 接口（`LLVMGetFirstTarget` 遍历）枚举，返回 `bpfeb bpfel bpf` 三项，与 `llc` 的文本输出互相印证。

libbpf 的版本用 pkg-config 查：

::: terminal title="bash - pkg-config"

```console
$ pkg-config --modversion libbpf
1.5.0
```

:::

这一行同时说明三件事：libbpf-dev 装好了、`libbpf.pc` 在 pkg-config 的搜索路径里、以后在 Makefile 里可以用 `$(shell pkg-config --cflags --libs libbpf)` 拿到编译与链接参数。如果提示找不到包，先确认 `libbpf-dev` 真的装上了，而不是只装了运行时的 `libbpf1`。

bpftool 的版本输出有三行，第二行是它链接的 libbpf 版本，第三行列出编译时启用的功能：

::: terminal title="bash - bpftool version"

```console
$ sudo bpftool version
bpftool v7.5.0
using libbpf v1.5
features: llvm, skeletons
```

:::

`llvm` 表示可以用来反汇编 BPF 指令，`skeletons` 表示支持 `gen skeleton`。这两项是 [B.3](/教程/正文/系统编程/拓展B_eBPF/B_3_第一个eBPF程序) 的构建流程直接依赖的，缺哪一项都会在下一步报错。

## 5. 生成 vmlinux.h

内核态程序要访问 `task_struct`、`trace_event_raw_sys_enter` 这类内核类型，但不能包含内核头文件：那些头文件依赖内核内部的宏和配置，在用户态编不过，而且把某个版本的定义写死在程序里，换一台机器就对不上。做法是从目标内核的 BTF 里导出一份纯 C 的类型声明，这就是 `vmlinux.h`。

生成只需要一条命令：

::: terminal title="bash - btf dump"

```console
$ sudo bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
```

:::

在本页所用的 Debian 13 机器上，这份 `vmlinux.h` 有 127716 行、2666306 字节，约 2.6 MB；行数用 `wc -l vmlinux.h` 核对。文件开头几行长这样：

```c
#ifndef __VMLINUX_H__
#define __VMLINUX_H__

#ifndef BPF_NO_PRESERVE_ACCESS_INDEX
#pragma clang attribute push (__attribute__((preserve_access_index)), apply_to = record)
#endif

#ifndef __ksym
#define __ksym __attribute__((section(".ksyms")))
#endif
```

`#pragma clang attribute push` 那一行给文件里所有结构体类型加上 `preserve_access_index` 属性。带上这个属性，clang 每生成一次成员访问，就在 `.BTF.ext` 里记一条重定位：访问的是哪个类型的哪个成员。加载时 libbpf 拿这些记录去目标内核的 BTF 里按名字重新查偏移，这就是 CO-RE 能一次编译、到处运行的原因。机制在 [B.8](/教程/正文/系统编程/拓展B_eBPF/B_8_libbpf_BTF与CO_RE) 展开，这里只需知道：这行 pragma 不能删，删了在本机照样能编能跑，换到成员偏移不同的内核上就会读到错误的位置。

`vmlinux.h` 的具体内容随内核而变，所以它不进仓库。它由 Makefile 生成，`code/系统编程/拓展B_eBPF/B_2_环境准备与工具链/Makefile` 中的规则是：

```makefile
BPFTOOL ?= bpftool
VMLINUX_BTF ?= /sys/kernel/btf/vmlinux

vmlinux.h: $(VMLINUX_BTF)
	$(BPFTOOL) btf dump file $(VMLINUX_BTF) format c > $@
```

试运行时 make 打印出的命令是：

::: terminal title="bash - make -n"

```console
$ make -n vmlinux.h
bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h
```

:::

把 `VMLINUX_BTF` 换成另一个文件，就能从任意一份 BTF 生成头文件；调试 CO-RE 时常用这个办法拿别的内核的类型做实验，[B.8](/教程/正文/系统编程/拓展B_eBPF/B_8_libbpf_BTF与CO_RE) 会用到。注意 `bpftool btf dump` 的输入必须是 BTF 本身，直接给它 `vmlinux.h`（一个 C 头文件）会报 `failed to get EHDR`。

::: generate ebpf-vmlinux-h-walkthrough kind=explanation concepts=ebpf-env-toolchain-roles

面向刚接触 eBPF 的读者，解释为什么内核态程序不直接包含内核头文件，而是用 bpftool 从 /sys/kernel/btf/vmlinux 导出一份 vmlinux.h；说明这份文件里只有类型声明，没有函数实现，也没有宏；说明“同一份源码在不同内核上编译一次就能运行”与这份文件的关系；不要展开 CO-RE 重定位的实现细节，那是后面 [B.8](/教程/正文/系统编程/拓展B_eBPF/B_8_libbpf_BTF与CO_RE) 的内容。

:::

## 6. 权限

加载 BPF 程序不是一个普通用户能做的操作。内核按程序类型检查能力（capability）：

- 跟踪类程序（kprobe、tracepoint、fentry、perf_event、LSM 等）需要 `CAP_PERFMON` 与 `CAP_BPF`；
- 网络类程序（XDP、tc、cgroup 的套接字钩子等）需要 `CAP_NET_ADMIN` 与 `CAP_BPF`；
- `CAP_SYS_ADMIN` 是过去唯一的入口，现在仍然可以代替上面这些能力。

这两条规则在内核的 `include/uapi/linux/capability.h` 里写得很直接：`CAP_PERFMON and CAP_BPF are required to load tracing programs`，`CAP_NET_ADMIN and CAP_BPF are required to load networking programs`。`CAP_BPF`（编号 39）与 `CAP_PERFMON`（编号 38）都是 Linux 5.8 引入的，目的正是把 BPF 从权限过大的 `CAP_SYS_ADMIN` 里拆出来。

普通用户连查询内核能力都会被挡住。在没用 `sudo` 的账户下执行 `bpftool feature probe`，得到的是：

::: terminal title="bash - feature probe"

```console
$ bpftool feature probe
Error: missing CAP_SYS_ADMIN, CAP_BPF, CAP_NET_ADMIN, CAP_PERFMON, required for full feature probing; run as root or use 'unprivileged'
```

:::

另一道闸是 sysctl 开关 `kernel.unprivileged_bpf_disabled`。取值 0 表示允许非特权用户使用一部分 BPF 功能，1 表示禁止且不可恢复，2 表示禁止但管理员可以改回来。内核默认是 0，但如果构建时启用了 `CONFIG_BPF_UNPRIV_DEFAULT_OFF`，默认值就是 2。Debian 13 的内核配置里这一项是 `y`，所以 Debian 上默认就是 2，普通用户连创建 map 都不行。

因此本章所有需要加载程序、创建 map、读 `trace_pipe` 的命令统一写 `sudo`。用 root 运行最省事，也避开了「以为能力够、其实少一个」的排查。真要给某个程序单独授权，用 `setcap cap_bpf,cap_perfmon+ep ./tool` 把能力绑到可执行文件上，再以普通用户运行；这属于部署阶段的处理，[B.15](/教程/正文/系统编程/拓展B_eBPF/B_15_实战_系统观测工具) 之后才会碰到。

## 7. 两种项目起点

本章的示例放在 `code/系统编程/拓展B_eBPF/` 下，每页一个目录，结构一致：

```text:no-line-numbers
B_2_环境准备与工具链/
├── Makefile          # 生成 vmlinux.h、编译 .bpf.o、生成骨架、编译用户态程序
├── smoke.bpf.c       # 最小的内核态程序：一个空的 tracepoint 处理函数
├── btfstat.c         # 读 BTF 文件头的小工具，本页习题会用到
└── libbpfver.c       # 用 pkg-config 编译并打印 libbpf 版本
```

这种组织用系统装的 libbpf：`pkg-config` 拿到编译与链接参数，`bpftool` 生成骨架，Makefile 只管把几步串起来。好处是依赖清楚、每一步都能单独执行，适合学习。完整的 Makefile 在 [B.3](/教程/正文/系统编程/拓展B_eBPF/B_3_第一个eBPF程序) 给出，本页的版本只做检查。

本页目录里的 `libbpfver.c` 只有一个函数体，用来说明用户态程序怎么链接 libbpf：

```c
#define _POSIX_C_SOURCE 200809L

#include <bpf/libbpf.h>
#include <stdio.h>

int main(void) {
    printf("libbpf %s\n", libbpf_version_string());
    return 0;
}
```

在装有 libbpf-dev 的机器上，`make libbpfver && ./libbpfver` 输出 `libbpf v1.5`。整个文件的重点在编译命令：`$$(pkg-config --cflags --libs libbpf)` 在配方里展开，交给编译器的是 `-lbpf`（头文件在 `/usr/include/bpf`，本来就在默认搜索路径里），链接时 `libbpf.so` 还要在动态链接器的搜索路径里。本章后面的用户态程序都这样编译。

另一个起点是 libbpf-bootstrap。它把 libbpf、bpftool、blazesym 和预生成的 `vmlinux.h` 都作为子模块带在仓库里，用自己编译的静态 libbpf 链接，目标机器上不需要装 libbpf-dev：

::: terminal title="bash - libbpf-bootstrap"

```console
$ git clone --recurse-submodules https://github.com/libbpf/libbpf-bootstrap
$ cd libbpf-bootstrap/examples/c
$ make
$ sudo ./minimal
```

:::

发行版的 libbpf 太旧、或者要把工具拷到没有开发包的机器上运行时，选它更省事。学习阶段用哪个都行，两条路的编译命令和骨架用法是同一套，本章讲的东西可以直接搬过去。

Windows 上的情况要分开说。BPF 目标文件可以在 Windows 上编译出来，因为 clang 只是一个交叉编译器，`-target bpf` 不依赖宿主系统。下面的命令与 eBPF for Windows 官方教程一致，本机实测的输出是：

::: terminal title="PowerShell - bpf.o"

```console
PS> clang -target bpf -Werror -O2 -c bpf.c -o bpf.o
PS> llvm-objdump --triple=bpf -S bpf.o

bpf.o:  file format elf64-bpf

Disassembly of section .text:

0000000000000000 <func>:
       0:	b4 00 00 00 00 00 00 00	w0 = 0x0
       1:	95 00 00 00 00 00 00 00	exit
```

:::

两条指令：`r0 = 0` 把返回值寄存器清零，`exit` 结束程序。上面贴的是本机 LLVM 22 的输出，它把 32 位写入写成 `w0 = 0x0`；旧一些的 `llvm-objdump` 和官方教程里写成 `r0 = 0`，指的是同一条指令。加 `-g` 再编译，`llvm-objdump -S` 会在指令上方显示出对应的源码行：

::: terminal title="PowerShell - bpf-d.o"

```console
PS> clang -target bpf -Werror -g -O2 -c bpf.c -o bpf-d.o
PS> llvm-objdump --triple=bpf -S -l bpf-d.o

bpf-d.o:	file format elf64-bpf

Disassembly of section .text:

0000000000000000 <func>:
; func():
; C:\Users\29728\AppData\Local\Temp\p118a\bpf.c:1
; int func(void) { return 0; }
       0:	b4 00 00 00 00 00 00 00	w0 = 0x0
       1:	95 00 00 00 00 00 00 00	exit
```

:::

编译出来的 `.o` 也能拿到 Linux 上生成骨架。本页用同一个文件验证过：在 Windows 上编译一个带 `SEC("tp/syscalls/sys_enter_getpid")` 的目标文件，复制到 Debian 13 后执行 `bpftool gen skeleton`，得到 313 行的头文件，其中有：

```c
struct smoke_bpf {
	struct bpf_object_skeleton *skeleton;
	struct bpf_object *obj;
	struct {
		struct bpf_program *handle_getpid;
	} progs;
	struct {
		struct bpf_link *handle_getpid;
	} links;
```

但编译产物不能在 Windows 上加载。eBPF for Windows 有自己的执行环境、钩子和验证器，Linux 的 `.bpf.o` 拿过去不能直接用，这部分在 [B.16](/教程/正文/系统编程/拓展B_eBPF/B_16_eBPF_for_Windows与跨平台) 讲。

最后是一个容易白费时间的坑。LLVM 官方的 Windows 发行版在 19 及以前只编进了 AArch64、ARM、X86 三个后端，`clang -target bpf` 会报：

::: terminal title="PowerShell - no BPF target"

```console
PS> clang -target bpf -c bpf.c -o bpf.o
error: unable to create target: 'No available targets are compatible with triple "bpf"'
1 error generated.
```

:::

这不是命令写错了，是这个 clang 里没有 BPF 后端。LLVM 19 的官方 Windows 发行版只用 `LLVM_TARGETS_TO_BUILD="AArch64;ARM;X86"` 构建，包里也就没有 BPF；20 起这一行改成了 `AArch64;ARM;X86;BPF;WebAssembly;RISCV;NVPTX`，Visual Studio 附带的 LLVM 22 同样可用。用 `clang --print-targets` 能看到 `bpf` 三行就说明可用。反过来，Linux 发行版打包的 LLVM 一般都带全部常用后端，Debian 13 的 `libLLVM` 里就有。
