# 16. 可移植构建

wordfreq 有了一位新贡献者。他读 `src/counter.c` 时注意到 `dup_string` 不到十行，做的是 `strlen`、`malloc`、`memcpy` 三件事，标准库里明明有现成的 `strdup`，于是把那个函数删掉，调用处改成 `strdup(word)`，提交了一个拉取请求。

他在自己的 Windows 上构建，编译通过，`ctest` 三个测试全过；同一份提交在 Linux 上由另一位维护者拉起构建，`counter.c` 连编译都没过。这一章从这个事件出发，讲清楚同一份源码在不同编译器、不同系统上构建时会在哪些地方出问题，以及怎样把这些问题按可控的方式解决：标准模式与功能特性测试宏、配置时检测、按编译器选择选项、把平台相关代码集中到少数文件、处理文件系统与动态库的差异，最后用预设统一各平台的配置。

文中所有输出都来自两台机器：Windows 11 上的 MinGW-w64 GCC 13.2 与 MSVC 14.51，Debian 13 上的 GCC 14.2。每段都注明是哪一个。

第一条错误说得很直接：`strdup` 在这个翻译单元里没有声明，编译器按 C 的老规矩把它当成一个返回 `int` 的函数。第二条是同一条错误的下游产物：`int` 赋值给 `char *`，指针与整数不兼容。修第一条，第二条自然消失。

原因在标准与实现的关系上。`strdup` 属于 POSIX，C23 起才进入 ISO C 的标准库；第 9 章的工程设了 `CMAKE_C_EXTENSIONS OFF`，生成 `-std=c17`，glibc 在这个严格模式下只声明 ISO C 规定的名字，于是 `string.h` 里根本没有 `strdup`。MinGW 的 UCRT 头文件不管标准模式，照样声明，所以同一行代码在 Windows 上编译得通。第 21.5 节的探测表把这一点列得更全：`strdup`、`strndup`、`stpcpy` 一类函数的可见性，取决于库版本、标准模式与函数名三件事。

还有一处版本差异值得记住：GCC 13 对调用未声明函数只给 `-Wimplicit-function-declaration` 警告，真正的失败发生在链接期（`undefined reference`）；GCC 14 起这已经是错误，构建在编译阶段就停下。同一段错误代码，在旧编译器上可能带着警告跑得很正常，换个编译器就过不去。

`dup_string` 没有被这次改动波及，它在第 7 章是特意写出来的：不依赖任何扩展，几行代码换来在任何 C17 实现上都能编译。这不是保守，而是把「用不用系统扩展」当成一个需要单独决定的问题。换成 `strdup` 之后，同一份源码在三套工具链上的结果如下（同一快照，同一组测试）：

| 工具链 | `strdup` 版本 |
| --- | --- |
| Windows 11，MinGW-w64 GCC 13.2，Ninja | 构建通过，`ctest` 3/3 |
| Windows 11，MSVC 14.51，Ninja | 构建通过，`ctest` 3/3 |
| Debian 13，GCC 14.2，Unix Makefiles | 编译失败，`strdup` 未声明 |

三套环境里有两套放过它，一套拦下它。贡献者只在其中一套上验证过，这就是「一次失败的移植」的全部由来。

## 2. 不可移植从哪里来

「在我机器上能编译」这句话之所以不可靠，是因为构建结果由五层东西共同决定，任何一层换了，结论都可能翻转。

| 层 | 差异的例子 | 应对 |
| --- | --- | --- |
| 语言 | `int` 的宽度、`char` 是否有符号、`long` 在 64 位 Windows 上仍是 32 位 | 需要固定宽度时用 `<stdint.h>` 的 `int32_t`、`uint64_t`；要表示大小和差值时用 `size_t`、`ptrdiff_t`，不要用 `long` |
| 库 | `strdup`、`getline`、`fileno` 属于 POSIX，严格模式不声明；MSVC 的 C 运行库另有一套 `_` 开头的名字 | 明确声明要用的 POSIX 版本，或把扩展函数封装成自己的接口（21.5） |
| 编译器 | 选项名字不同（`-Wall` 与 `/W4`）、扩展不同、属性写法不同 | 在构建系统里按编译器分支，或用宏把编译器相关的写法包起来（21.6） |
| 系统 | 文件名大小写是否敏感、路径分隔符、换行符、动态库格式 | 统一写小写文件名与 `/`；文件按二进制打开；换行交给 `.gitattributes` |
| 构建工具 | Makefile 的配方在 shell 中执行，Windows 上要有 bash 才能跑；CMake 的生成器各平台不同 | 用 CMake 描述构建，把 shell 命令限制在少数脚本里 |

语言这一层的差异可以用一个十几行的小程序量出来。同一份源码在两台机器上各编译一次：

::: code-group

```c [limits.c]
#include <limits.h>
#include <stdio.h>

int main(void) {
    printf("sizeof(int) = %d, sizeof(long) = %d, sizeof(void *) = %d\n",
           (int)sizeof(int), (int)sizeof(long), (int)sizeof(void *));
    printf("CHAR_MIN = %d, CHAR_MAX = %d\n", CHAR_MIN, CHAR_MAX);
    printf("LONG_MAX = %ld\n", LONG_MAX);
    return 0;
}
```

```text [Windows，MinGW-w64 GCC 13.2]
sizeof(int) = 4, sizeof(long) = 4, sizeof(void *) = 8
CHAR_MIN = -128, CHAR_MAX = 127
LONG_MAX = 2147483647
```

```text [Linux，GCC 14.2]
sizeof(int) = 4, sizeof(long) = 8, sizeof(void *) = 8
CHAR_MIN = -128, CHAR_MAX = 127
LONG_MAX = 9223372036854775807
```

:::

`long` 在 64 位 Windows 上只有 4 字节，和 32 位系统一样；Linux 上则是 8 字节。把文件大小、时间差、数组下标之类的东西存进 `long`，再在两种系统之间交换数据或打印（`%ld` 对应的宽度也随之变化），结果就对不上。用 `<stdint.h>` 里的定宽类型，或者在只需要「装得下指针」时用 `size_t`、`ptrdiff_t`，这类问题从源头上就不存在。`char` 是否有符号在本次两台机器上恰好一致，但标准没有规定，把 `char` 当小整数用、又依赖它能表示 128 以上的值时，换一个编译器（ARM 上常见）就会出错；需要无符号字节时写 `unsigned char`。

::: tip 只写 ISO C 加明确声明的扩展

纯 ISO C 加标准库，在任何符合标准的实现上都能编译。需要 POSIX 的某个函数时，在用到它的源文件里明确写出需要哪一版 POSIX，而不是指望「在我这台机器上头文件里有」。系统相关的代码集中到两三个文件里，其余部分只依赖这些文件提供的接口，下面的第 6 节和第 8 节都按这个思路做。

:::

## 3. 标准模式与功能特性测试宏

第 9 章建工程时设了 `CMAKE_C_EXTENSIONS OFF`，当时只说「为了尽早暴露问题」。现在可以看清它具体改变了什么。同一个空工程，只差这一行设置，构建命令里的 `-std` 就不一样（Windows，MinGW）：

::: terminal title="zsh - cmake --build --verbose 中的 -std"

```console
$ cmake --build build-on --verbose
[1/2] D:\Software\Strawberry\c\bin\gcc.exe   -std=gnu17 -MD -MT CMakeFiles/on.dir/main.c.obj ...
$ cmake --build build-off --verbose
[1/2] D:\Software\Strawberry\c\bin\gcc.exe   -std=c17 -MD -MT CMakeFiles/off.dir/main.c.obj ...
```

:::

`gnu17` 是 GCC 的默认模式，在 C17 的基础上打开 GNU 扩展；`c17` 是严格模式，只接受 ISO C，并把 `__STRICT_ANSI__` 定义给头文件看。glibc 的头文件正是靠这个宏决定要不要声明 POSIX 函数：`gnu17` 下 `strdup`、`getline`、`fileno` 全都有，`c17` 下只剩 ISO C 的那部分。CMake 的 `C_EXTENSIONS` 默认是 `ON`，也就是说，一个没有写这一行的 CMake 工程，在 Linux 上默认拿到的是 `gnu17`，`strdup` 事件根本不会发生。第 9 章把它关掉，等于主动选择了严格模式，让这类依赖扩展的代码在开发阶段就暴露。

严格模式下要用 POSIX 函数，标准做法是告诉头文件「我要的是哪一版 POSIX」：

```c
#define _POSIX_C_SOURCE 200809L

#include <stdio.h>

int use_fileno(void) { return fileno(stdin); }
```

这个宏必须在包含任何头文件之前定义，因为它决定头文件里哪些声明会出现；写在 `#include` 后面，`stdio.h` 已经按旧的条件处理完了，再定义也没有用。实测两份只差定义位置的源文件（Linux，GCC 14.2，`-std=c17`）：

::: terminal title="zsh - 宏的位置决定成败"

```console
$ gcc -std=c17 -Wall -Wextra -c late.c -o late.o
late.c: In function ‘f’:
late.c:5:43: error: implicit declaration of function ‘strdup’; did you mean ‘strcmp’? [-Wimplicit-function-declaration]
    5 | int f(const char *s) { return (int)strlen(strdup(s)); }
      |                                           ^~~~~~
      |                                           strcmp
late.c:5:43: error: passing argument 1 of ‘strlen’ makes pointer from integer without a cast [-Wint-conversion]
$ gcc -std=c17 -Wall -Wextra -c early.c -o early.o
$ echo $?
0
```

:::

`late.c` 把 `#define _POSIX_C_SOURCE 200809L` 写在 `#include <string.h>` 之后，`early.c` 写在最前面，只有后者编译通过。wordfreq 的 `app/main.c` 在包含任何头文件之前定义了这个宏，还套了一层 `#if !defined(_WIN32)`，因为 Windows 上没有这套机制，MinGW 的头文件也不需要。

::: concept dev-portable-explicit-standard title="扩展接口必须由源文件显式打开"

一个源文件能用哪些接口，由它自己包含的头文件和它在包含之前定义的宏共同决定，与「这台机器的库里有没有这个函数」无关。严格模式下 glibc 不声明 POSIX 名字，不是缺陷，而是标准允许的实现选择；MinGW 在 `-std=c17` 下照样声明，同样只是它的选择。同一份源码在两边的可见接口不同，正是「能编译」不能作为可移植性证据的原因。

:::

MSVC 的头文件同时声明 `strdup` 和 `_strdup`，但前者会触发一条 C4996 弃用警告，官方推荐的名字是 `_strdup`；`fileno` 与 `_fileno`、`stricmp` 与 `_stricmp` 也都是这种关系。把名字统一成 `_strdup` 只是把问题换了个方向，Linux 上又没有 `_strdup`。对于几行就能写完的函数，最省事的做法是保留自己的实现：`dup_string` 不依赖任何扩展，在任何 C17 实现上都能编译，维护成本比构造一套跨平台的名字映射低得多。系统的做法见 [21.5 易于移植的扩展函数](/教程/正文/开发与工程基础/21_库接口实现练习/21_5_易于移植的扩展函数)，那里的 `mdr_strdup` 就是这个思路的完整版本。

## 4. 配置时检测

`_POSIX_C_SOURCE` 解决的是「我知道这个平台有这个函数」。有些函数在某个平台上就是没有，比如 `getline`：glibc 里有，MinGW 和 MSVC 都没有。这时不能靠宏写死，要在配置阶段问一句「这套工具链有没有它」，把答案写进一个生成的头文件。

CMake 的 `CheckSymbolExists` 模块做这件事：它编译一个只引用该名字的小程序，编译链接成功就算有。wordfreq 的 `CMakeLists.txt` 里相关的一段是：

```cmake
include(CheckSymbolExists)

option(WF_HAVE_GETLINE "Assume getline is available (set OFF to force the fgets path)" ON)

set(WF_CONFIG_HAVE_GETLINE OFF)
if(WF_HAVE_GETLINE)
    set(CMAKE_REQUIRED_DEFINITIONS -D_POSIX_C_SOURCE=200809L)
    check_symbol_exists(getline "stdio.h" WF_HAVE_GETLINE_FOUND)
    unset(CMAKE_REQUIRED_DEFINITIONS)
    if(WF_HAVE_GETLINE_FOUND)
        set(WF_CONFIG_HAVE_GETLINE ON)
    endif()
endif()

configure_file(src/config.h.in ${PROJECT_BINARY_DIR}/include/wf/config.h)
```

这里有一个容易漏掉的地方：检测本身也要在严格模式下进行。第 9 章设了 `C_EXTENSIONS OFF`，检测小程序拿到的是 `-std=c17`，glibc 不声明 `getline`，检测就会得到「没有」，尽管库里有这个函数。`CMAKE_REQUIRED_DEFINITIONS` 把 `-D_POSIX_C_SOURCE=200809L` 加进检测用的编译命令，结果才正确。同一台 Linux 机器上只差这一行，检测结论完全相反（Linux，GCC 14.2）：

::: terminal title="zsh - 检测 getline"

```console
$ cmake -S . -B b1      # 不带 CMAKE_REQUIRED_DEFINITIONS
-- Looking for getline
-- Looking for getline - not found
$ cmake -S . -B b2      # 带 -D_POSIX_C_SOURCE=200809L
-- Looking for getline
-- Looking for getline - found
```

:::

模板 `src/config.h.in` 只有一行有效内容：

```c
#cmakedefine WF_CONFIG_HAVE_GETLINE 1
```

`#cmakedefine` 在变量为真时生成 `#define WF_CONFIG_HAVE_GETLINE 1`，为假时生成 `/* #undef WF_CONFIG_HAVE_GETLINE */`。生成结果放在构建目录下与源码树同构的位置（`build/include/wf/config.h`），代码里写 `#include "wf/config.h"`，和包含 `wf/token.h` 的写法一致：

::: code-group

```c [Linux 生成的 build/include/wf/config.h]
#ifndef WF_CONFIG_H
#define WF_CONFIG_H

#define WF_CONFIG_HAVE_GETLINE 1

#endif
```

```c [Windows 生成的同名文件]
#ifndef WF_CONFIG_H
#define WF_CONFIG_H

/* #undef WF_CONFIG_HAVE_GETLINE */

#endif
```

:::

`app/main.c` 据此选择实现。两个版本都叫 `count_stream`，一次只编进去一个：

```c
#ifdef WF_CONFIG_HAVE_GETLINE
/*
 * 按行读入：getline 按需增长缓冲区。换行是分隔符，单词不会跨行，
 * 所以逐行分词与整文件分词的结果相同。
 */
static int count_stream(wf_counter *counter, FILE *in, const char *name) {
    char *line = NULL;
    size_t cap = 0;
    int status = 0;
    ssize_t got;
    while ((got = getline(&line, &cap, in)) >= 0) {
        if (count_text(counter, line, (size_t)got) != 0) {
            status = out_of_memory();
            break;
        }
    }
    if (status == 0 && ferror(in)) {
        fprintf(stderr, "wordfreq: %s: %s\n", name, strerror(errno));
        status = 1;
    }
    free(line);
    return status;
}
#else
/* 用 fgets 分块读入：缓冲区大小固定，长行会分成多段，结果仍然相同 */
static int count_stream(wf_counter *counter, FILE *in, const char *name) {
    char chunk[4096];
    int status = 0;
    while (fgets(chunk, sizeof chunk, in) != NULL) {
        size_t len = strlen(chunk);
        if (count_text(counter, chunk, len) != 0) {
            status = out_of_memory();
            break;
        }
    }
    if (status == 0 && ferror(in)) {
        fprintf(stderr, "wordfreq: %s: %s\n", name, strerror(errno));
        status = 1;
    }
    return status;
}
#endif
```

两条路径的分词结果必须相同：换行是分隔符，单词不会跨行，所以按行读和按块读得到的单词序列一致。这一点靠测试保证，而不是靠推理。`WF_HAVE_GETLINE` 这个缓存变量除了控制检测，还能用来强制走回退路径：把它设为 `OFF`，检测整个跳过，生成的宏是未定义，编译的就是 `fgets` 版本：

::: terminal title="zsh - 强制回退路径并运行全部测试"

```console
$ cmake -S . -B build-nogetline -DWF_HAVE_GETLINE=OFF -G "Unix Makefiles"
-- The C compiler identification is GNU 14.2.0
-- Detecting C compiler ABI info - done
-- Check for working C compiler: /usr/bin/cc - skipped
-- Detecting C compile features - done
-- Configuring done (0.3s)
-- Generating done (0.0s)
-- Build files have been written to: /home/minsecrus/tutorial/work/ch16/wordfreq/build-nogetline
$ cmake --build build-nogetline -j 2
[100%] Built target test_counter
$ ctest --test-dir build-nogetline
1/3 Test #1: token ............................   Passed    0.00 sec
2/3 Test #2: counter ..........................   Passed    0.00 sec
3/3 Test #3: e2e ..............................   Passed    0.01 sec

```

:::

Linux 上有 `getline`，正常配置走的是第一条路径；`-DWF_HAVE_GETLINE=OFF` 把第二条路径也编出来跑了一遍。Windows 上检测结果本来就是「没有」，平时跑的就是回退路径。两条路径各自至少在一台机器上被完整测试过，才谈得上「行为相同」。

::: concept dev-portable-test-both-paths title="配置检测出的每条路径都要有测试"

配置阶段检测出一个能力，代码里就多出一条分支。构建系统只测到当前平台选中的那一条，另一条在别的平台上才生效，往往到发布时才第一次被编译。给检测结果留一个强制开关（如 `WF_HAVE_GETLINE`），在开发机上把两条路径都配置、构建、测试一遍，是这类代码唯一可靠的验证方式。

:::

C23 起有了另一种更轻的写法：`__has_include` 在预处理阶段判断某个头文件在不在，GCC、Clang 早已把它当扩展支持，代码写成：

```c
#if defined(__has_include)
#if __has_include(<stdbit.h>)
#include <stdbit.h>
#define WF_HAVE_STDBIT 1
#endif
#endif
```

它只回答「头文件在不在」，不回答「里面的函数可不可用」，适合可选的整头文件能力，不适合 `getline` 这种「头文件在、函数可能不在」的情况。实测本机的 MinGW GCC 13.2 没有 `<stdbit.h>`，Debian 上的 GCC 14.2 有，用上面几行就能在两边各自选到正确的分支。

## 5. 编译器差异

GCC 与 Clang 认 `-Wall`，MSVC 认 `/W4`；`-std=c17` 与 `/std:c17` 是同一个意思的不同拼法；`-DNAME=VALUE` 在 MSVC 里写 `/DNAME=VALUE`。构建文件不可能为每个编译器写一份，CMake 的生成器表达式 (generator expression) 就是为此准备的：它在生成构建文件时才展开，可以按编译器、平台、构建类型取不同的值。

wordfreq 的工程里按编译器分警告选项：

```cmake
if(MSVC)
    set(WF_WARNINGS /W4)
else()
    set(WF_WARNINGS -Wall -Wextra -Wshadow -Wformat=2 -Wmissing-prototypes
        -Wstrict-prototypes -Wvla)
endif()
```

需要更细的条件时用 `$<...>`。下面这个小工程给 MSVC 加 `/W4`、`/utf-8`、`/D_CRT_SECURE_NO_WARNINGS`，给其他编译器加三个警告选项：

```cmake
add_executable(demo main.c)
target_compile_options(demo PRIVATE
    $<$<C_COMPILER_ID:MSVC>:/W4>
    $<$<C_COMPILER_ID:MSVC>:/utf-8>
    $<$<C_COMPILER_ID:MSVC>:/D_CRT_SECURE_NO_WARNINGS>
    $<$<NOT:$<C_COMPILER_ID:MSVC>>:-Wall>
    $<$<NOT:$<C_COMPILER_ID:MSVC>>:-Wextra>
    $<$<NOT:$<C_COMPILER_ID:MSVC>>:-Wpedantic>)
```

`--verbose` 能看到实际命令行。GCC 只拿到自己那一组（Windows，MinGW）：

::: terminal title="zsh - 生成器表达式展开后的编译命令"

```console
$ cmake --build build --verbose
[1/2] D:\Software\Strawberry\c\bin\gcc.exe   -Wall -Wextra -Wpedantic -MD -MT CMakeFiles/demo.dir/main.c.obj -MF CMakeFiles\demo.dir\main.c.obj.d -o CMakeFiles/demo.dir/main.c.obj -c C:/work/genexp/main.c
```

MSVC 只拿到 `/W4`、`/utf-8`、`/D_CRT_SECURE_NO_WARNINGS`（同一台机器，`cl.exe`）：

```console
[1/2] D:\Software\VS\1\VC\Tools\MSVC\14.51.36231\bin\Hostx64\x64\cl.exe  /nologo   /DWIN32 /D_WINDOWS /Zi /Ob0 /Od /RTC1 -MDd /W4 /utf-8 /D_CRT_SECURE_NO_WARNINGS /showIncludes /FoCMakeFiles\demo.dir\main.c.obj /FdCMakeFiles\demo.dir\ /FS -c C:\work\genexp\main.c
```

:::

一个表达式只能产生一个列表元素。上面把 `-Wall -Wextra -Wpedantic` 拆成三个表达式，就是为了让每个选项各自成为一个参数。合并成 `"$<$<NOT:$<C_COMPILER_ID:MSVC>>:-Wall -Wextra -Wpedantic>"` 时，CMake 会给整个字符串加引号传给编译器，构建这样失败：

::: terminal title="zsh - 一个表达式里塞多个选项"

```console
$ cmake --build build-q
[1/2] Building C object CMakeFiles/demo.dir/main.c.obj
FAILED: CMakeFiles/demo.dir/main.c.obj
D:\Software\Strawberry\c\bin\gcc.exe   "-Wall -Wextra -Wpedantic" -MD -MT CMakeFiles/demo.dir/main.c.obj ...
gcc.exe: error: unrecognized command-line option '-Wall -Wextra -Wpedantic'
```

:::

也可以在一个表达式里用分号分隔：`$<$<NOT:$<C_COMPILER_ID:MSVC>>:-Wall;-Wextra;-Wpedantic>` 会在展开时拆成三个参数。两种写法效果相同，前一种每行一个选项、读起来更清楚。

MSVC 有两个与可移植性直接相关的选项。`/utf-8` 让 cl 按 UTF-8 读源文件：wordfreq 的头文件里有中文注释，不写这个选项时 cl 按当前代码页（本机是 936）解释，对每个含中文的头文件报一条 C4819：

::: terminal title="PowerShell - cl 读含中文的头文件（MSVC 14.51）"

```text
report.c
include\wf/report.h(1): warning C4819: 该文件包含不能在当前代码页(936)中表示的字符。请将该文件保存为 Unicode 格式以防止数据丢失
include\wf/counter.h(1): warning C4819: 该文件包含不能在当前代码页(936)中表示的字符。请将该文件保存为 Unicode 格式以防止数据丢失
include\wf/export.h(1): warning C4819: 该文件包含不能在当前代码页(936)中表示的字符。请将该文件保存为 Unicode 格式以防止数据丢失
```

加上 `/utf-8` 后同一条命令只剩文件名，警告全部消失。源码本身是 UTF-8，这个选项让它按 UTF-8 理解，与 GCC 的习惯一致。

另一个是 C4996。MSVC 把一批 C 运行库函数标为不安全，`strerror` 也在其中：

```text
app\main.c(100): warning C4996: 'strerror': This function or variable may be unsafe. Consider using strerror_s instead. To disable deprecation, use _CRT_SECURE_NO_WARNINGS. See online help for details.
```

它给了两条路：换成 MSVC 专有的 `strerror_s`，或者定义 `_CRT_SECURE_NO_WARNINGS` 关掉这类警告。前者把代码锁死在一个编译器上，后者承认「这里用的是标准函数，我知道自己在做什么」。跨平台代码选后者，在 CMake 里只对 MSVC 加这个定义，与上面的 `/utf-8` 写在一起。

MinGW 的 GCC 有一个与 `%zu` 有关的误报。第 3 章第 7 节讲过原因：这台机器的 UCRT 运行库对 `%zu` 支持不完整，`-Wformat` 认不出 `z` 长度修饰符，`report.c` 里的 `printf("%7zu %s\n", ...)` 会报三条警告：

::: terminal title="zsh - MinGW 对 %zu 的 -Wformat 误报"

```console
$ gcc -std=c17 -Wall -Wextra -Iinclude -c src/report.c -o report.o
src/report.c: In function 'wf_report_print':
src/report.c:5:25: warning: unknown conversion type character 'z' in format [-Wformat=]
    5 |         fprintf(out, "%7zu %s\n", entries[i].count, entries[i].word);
      |                         ^
src/report.c:5:29: warning: format '%s' expects argument of type 'char *', but argument 3 has type 'size_t' {aka 'long long unsigned int'} [-Wformat=]
src/report.c:5:22: warning: too many arguments for format [-Wformat-extra-args]
```

加 `-D__USE_MINGW_ANSI_STDIO=1` 让 MinGW 用自己的格式化实现，警告全部消失，运行结果不变。CMake 里用 `if(MINGW)` 只在 MinGW 上加这个定义：

```cmake
if(MINGW)
    target_compile_definitions(wf PUBLIC __USE_MINGW_ANSI_STDIO=1)
endif()
```

`PUBLIC` 让链接 `wf` 的 `wordfreq`、测试程序也带上这个定义，否则测试程序里打印 `size_t` 的地方会重新出现同样的警告。CMake 预定义的 `MINGW` 变量只在 MinGW 上为真，MSVC 与 Linux 的 GCC 都不受影响。

编译器专有的属性也要包起来。`__attribute__((format(printf, 2, 3)))` 能让 GCC 检查自定义打印函数的格式串，MSVC 认的是另一套写法；用 `WF_PRINTF_LIKE` 之类的宏把两边包进同一个名字，调用处只写宏。[21.6 可回退的编译器内建功能](/教程/正文/开发与工程基础/21_库接口实现练习/21_6_可回退的编译器内建功能) 专门做这件事。

## 6. 隔离平台相关代码

平台差异不可能消灭，能做的是把它关进少数几个文件。假设要给 wordfreq 加一个「标准输出是否接在终端上」的判断：接终端时打印一行表头，重定向到文件时不打印。Linux 用 `isatty`，Windows 用 `_isatty`，两者的名字和头文件都不同。

一种写法是在调用处直接写条件编译：

::: compare left-title="条件编译散落在业务代码里" right-title="调用方只调用普通函数"

```c
#include <stdio.h>

#ifdef _WIN32
#include <io.h>
#else
#include <unistd.h>
#endif

static void print_header(void) {
#ifdef _WIN32
    int is_terminal = _isatty(_fileno(stdout));
#else
    int is_terminal = isatty(STDOUT_FILENO);
#endif
    if (is_terminal) {
        printf("-- wordfreq 结果 --\n");
    }
}
```

```c
/* app/main.c：调用方只看到这一个名字 */
static void print_header(void) {
    if (wf_stdout_is_terminal()) {
        printf("-- wordfreq 结果 --\n");
    }
}
```

:::

左栏的写法在只有一个调用点时还看得过去；调用点变成五个、十个，每个函数里都夹一段 `#ifdef`，读代码的人要在两套实现之间来回跳，改一处接口要翻遍全工程。右栏把判断变成一个普通函数，调用方只包含 `platform.h`，看到的永远是一个返回 `int` 的函数。

两个实现文件各写各的平台：

::: code-group

```c [src/platform.h]
#ifndef PLATFORM_H
#define PLATFORM_H

/* 标准输出是否接在终端上：接终端返回 1，重定向到文件或管道时返回 0 */
int wf_stdout_is_terminal(void);

#endif
```

```c [src/platform_posix.c]
#define _POSIX_C_SOURCE 200809L

#include "platform.h"

#include <unistd.h>

int wf_stdout_is_terminal(void) { return isatty(STDOUT_FILENO) != 0; }
```

```c [src/platform_win32.c]
#include "platform.h"

#include <io.h>
#include <stdio.h>

int wf_stdout_is_terminal(void) { return _isatty(_fileno(stdout)) != 0; }
```

:::

构建文件只决定编哪一个：

```cmake
add_executable(platform_demo main.c)
if(WIN32)
    target_sources(platform_demo PRIVATE platform_win32.c)
else()
    target_sources(platform_demo PRIVATE platform_posix.c)
endif()
```

`--verbose` 的输出确认了选择结果。Linux 上只有 `platform_posix.c` 进入编译：

::: terminal title="zsh - Linux 上编译的是 platform_posix.c"

```console
$ cmake --build build --verbose
[ 66%] Building C object CMakeFiles/platform_demo.dir/platform_posix.c.o
/usr/bin/cc   -std=c17 -MD -MT CMakeFiles/platform_demo.dir/platform_posix.c.o -MF CMakeFiles/platform_demo.dir/platform_posix.c.o.d -o CMakeFiles/platform_demo.dir/platform_posix.c.o -c /home/minsecrus/tutorial/work/ch16/platform/platform_posix.c
```

:::

Windows 上同一条命令只编 `platform_win32.c`：

::: terminal title="zsh - Windows 上编译的是 platform_win32.c"

```console
$ cmake --build build --verbose
[2/3] D:\Software\Strawberry\c\bin\gcc.exe   -std=c17 -MD -MT CMakeFiles/platform_demo.dir/platform_win32.c.obj -MF CMakeFiles\platform_demo.dir\platform_win32.c.obj.d -o CMakeFiles/platform_demo.dir/platform_win32.c.obj -c C:/work/platform/platform_win32.c
```

:::

另一个平台的文件根本没出现，也不需要它出现：它里面调用的 `_isatty` 在本平台的头文件里不存在，编进去反而会失败。

运行结果随输出去向变化。Linux 上在终端里运行时打印表头，重定向到文件时只有数据行：

::: terminal title="zsh - 在伪终端里运行与重定向"

```console

-- wordfreq 结果 --
the 4
$ ./build/platform_demo > out.txt
$ cat out.txt
the 4
```

:::

`script` 在这里的作用是给程序一个真正的终端；直接用 `> out.txt` 时标准输出是文件，`isatty` 返回 0。Windows 的 `platform_win32.c` 用 `_isatty(_fileno(stdout))` 做同样的事，两份实现只在函数名和头文件上不同，接口与调用方完全一致。把平台相关的代码集中起来，代价是多一个文件和一次条件判断，收益是业务代码里再也看不到 `#ifdef _WIN32`。

这个例子小到可以放在一节里；同样的做法适用于文件系统遍历、动态库加载、终端控制、时间函数。判断标准很简单：一段代码要用到某个平台专有的头文件或函数名，它就该待在一个按平台命名的 `.c` 文件里，通过 `platform.h` 暴露一个普通的函数。完整示例在 `code/开发与工程基础/16_可移植构建/platform/`。

## 7. 文件系统与文本

第一件容易被忽视的事是文件名的大小写。wordfreq 的公开头文件放在 `include/wf/` 下，文件名是小写的 `counter.h`。如果某个源文件里写成 `#include "wf/Counter.h"`：

::: terminal title="zsh - 大小写错误的包含"

```console
$ # Windows，MinGW-w64 GCC 13.2
$ gcc -std=c17 -Wall -Wextra -Iinclude -c icm.c -o icm.o
$ echo $?
0
$ # Linux，GCC 14.2
$ gcc -std=c17 -Wall -Wextra -Iinclude -c icm.c -o icm.o
icm.c:9:10: fatal error: wf/Counter.h: No such file or directory
    9 | #include "wf/Counter.h"
      |          ^~~~~~~~~~~~~~
compilation terminated.
```

:::

Windows 的文件系统（NTFS）不区分大小写，`Counter.h` 和 `counter.h` 指的是同一个文件；Linux 的 ext4 区分大小写，找不到就是找不到。macOS 默认的 APFS 也不区分大小写，所以这类错误常常在开发机上潜伏很久，直到第一次在 Linux 上构建才出现。规则很简单：头文件名一律小写，`#include` 里的拼写与磁盘上的文件名逐字符一致。`bugs/include_case_mismatch.c` 就是这份错误示例。

第二件事是路径分隔符。C 代码里写路径时统一用 `/`，Windows 的 C 运行库同样接受 `tests/data/sample.txt` 这种写法；只有需要调用 Win32 API 或把路径交给外部程序时才转成 `\`。`/` 在 Windows 上不会被当成分隔符以外的东西，反过来 `\` 在 C 字符串里是转义符。写 `"C:\work\f.txt"` 时，`\w` 是未知的转义序列，`\f` 是换页符，得到的字符串早已不是那个路径（Windows，MinGW）：

::: terminal title="zsh - 反斜杠当作转义符"

```console
$ gcc -std=c17 -Wall -Wextra esc.c -o esc.exe
esc.c: In function 'main':
esc.c:4:25: warning: unknown escape sequence: '\w'
    4 |     puts("C:\work\f.txt");
      |                         ^
$ ./esc.exe | od -c
0000000   C   :   w   o   r   k  \f   .   t   x   t  \r  \n
```

:::

写成 `"C:\\work\\f.txt"` 才能得到原来的路径。这是在两种系统上都容易踩的坑，路径一律用 `/` 就没有这个问题。

第三件事是换行符。同一份 `sample.txt` 在 Windows 上可能存成 CRLF（每行结尾 `\r\n`），在 Linux 上是 LF。wordfreq 把 `\r` 当作分隔符（规则本来就规定只有 ASCII 字母算单词），所以两种换行得到的结果相同：

::: terminal title="zsh - CRLF 文件与 LF 文件结果相同"

```console
$ # Linux，GCC 14.2：sample_crlf.txt 由 sample.txt 改成 CRLF 换行得到
$ ./build/wordfreq -n 3 tests/data/sample_crlf.txt
      4 the
      2 on
      2 sat
$ ./build/wordfreq -n 3 tests/data/sample.txt
      4 the
      2 on
      2 sat
```

:::

这里还有一个容易忽略的细节：读文件一律用 `"rb"` 打开。

::: compare left-title="文本模式读文件" right-title="二进制模式读文件"

```c
/* Windows 上 \r\n 被翻译成 \n，Linux 上不翻译：
   同一个文件在两个平台上拿到的字节序列不同 */
FILE *in = fopen(path, "r");
```

```c
/* 两个平台都按原始字节读入，分词结果只由字节决定 */
FILE *in = fopen(path, "rb");
```

:::

文本模式在 Windows 上会把 `\r\n` 翻译成 `\n`，Linux 上不翻译；用二进制模式读，两个平台拿到的字节序列完全一样。wordfreq 的 `count_file` 写的是 `fopen(path, "rb")`，原因就在这里。分词器把 `\r` 当作分隔符，所以即使不翻译，结果也一样；读进来的字节一致，调试时少一层解释。

输出侧的情况相反：Windows 上标准输出是文本模式，`\n` 会被写成 `\r\n`，Linux 上仍是 `\n`。端到端测试因此不能逐字节比较原始输出，`tests/run_e2e.cmake` 在比较前做了一次 `string(REPLACE "\r" "" actual "${actual}")`，把回车去掉再比。这不是放水，而是承认两个平台的文本输出在字节层面本来就不同，测试只关心可见的行内容。

仓库里的换行符由 `.gitattributes` 统一，谁在什么系统上检出都得到同一套字节，做法见 [第 17 章](/教程/正文/开发与工程基础/17_Git协作) 的最后一节。

## 8. 动态库

到目前为止 `wf` 一直是静态库，链接时目标文件被复制进可执行文件。`BUILD_SHARED_LIBS` 是 CMake 的一个全局开关，打开后 `add_library(wf ...)` 不加 `STATIC` 或 `SHARED` 就默认构建共享库 (shared library)：

```sh
cmake -S . -B build-shared -DBUILD_SHARED_LIBS=ON
cmake --build build-shared
```

产物在各平台上的名字和配套文件不同：

| 平台与工具链 | 共享库 | 导入库 (import library) | 可执行文件如何找到它 |
| --- | --- | --- | --- |
| Linux，GCC | `libwf.so` | 无 | 链接时记录 RUNPATH 或由 `LD_LIBRARY_PATH` 指定，运行时由动态链接器查找 |
| macOS，Apple Clang | `libwf.dylib` | 无 | 链接时记录安装名，运行时由 dyld 查找 |
| Windows，MinGW | `libwf.dll` | `libwf.dll.a` | 运行时按 DLL 搜索顺序查找 |
| Windows，MSVC | `wf.dll` | `wf.lib` | 运行时按 DLL 搜索顺序查找 |

Linux 上库只有一个文件，`lib` 前缀加上 `.so` 扩展名：

::: terminal title="zsh - Linux 的共享库产物"

```console
$ cmake -S . -B build-shared -DBUILD_SHARED_LIBS=ON -G "Unix Makefiles"
$ cmake --build build-shared -j 2
[100%] Built target test_counter
$ ls build-shared/libwf.so
build-shared/libwf.so
$ ./build-shared/wordfreq -n 3 tests/data/sample.txt
      4 the
      2 on
      2 sat
```

:::

MinGW 上多出一个导入库，名字带 `.dll.a`：

```text
build-shared/libwf.dll
build-shared/libwf.dll.a
```

导入库只有链接期有用，里面是「这些符号在哪个 DLL 里」的目录；运行时真正加载的是 `.dll`。MSVC 的命名去掉 `lib` 前缀，导入库扩展名是 `.lib`，和静态库同名，靠所在目录区分。

Windows 上的共享库有一个 Linux 没有的问题：符号默认不导出。MSVC 构建 `wf.dll` 时，只有带 `__declspec(dllexport)` 的函数才会出现在导出表里；一个都没有时，链接器根本不生成导入库。把 `export.h` 里的 `WF_API` 暂时改成空宏再构建，`wf.dll` 照常生成，但三个程序全部链接失败：

::: terminal title="PowerShell - MSVC 构建无导出的 DLL"

```text
[9/12] Linking C shared library wf.dll
[10/12] Linking C executable wordfreq.exe
FAILED: wordfreq.exe
LINK : fatal error LNK1104: 无法打开文件“wf.lib”
```

:::

后面的 `test_token`、`test_counter` 报同样的错误，这里省略。如果只是漏掉一处（留下一部分函数带 `WF_API`），导入库会生成，但里面没有那个符号，链接时报 LNK2019。把 `WF_API` 从 `include/wf/counter.h` 的 `wf_counter_top` 声明上删掉，其余不动：

::: terminal title="PowerShell - 漏掉一个导出标记"

```text
[9/12] Linking C shared library wf.dll
[10/12] Linking C executable wordfreq.exe
FAILED: wordfreq.exe
main.c.obj : error LNK2019: 无法解析的外部符号 wf_counter_top，函数 print_top 中引用了该符号
wordfreq.exe : fatal error LNK1120: 1 个无法解析的外部命令
```

:::

MinGW 没有这个问题：它构建 DLL 时默认导出所有非 `static` 函数。同一份源码去掉全部 `WF_API`，MinGW 的共享库构建和运行照常通过。这解释了为什么很多在 Linux、MinGW 上活得好好的库，第一次用 MSVC 构建就链接失败：问题不是代码写错，而是缺少 Windows 特有的导出标记。

解决办法是在公开头文件里定义一个宏，把「构建库时导出、使用库时导入」的差别包起来。wordfreq 的 `include/wf/export.h`：

```c
/*
 * wf 库的导出标记：共享库在 Windows 上默认不导出符号，
 * 需要 __declspec(dllexport) 声明哪些是公开接口。
 *
 * - 构建 wf 自身时定义 WF_BUILDING；
 * - 使用共享库时定义 WF_SHARED；
 * - 静态库构建两者都不需要，WF_API 展开为空。
 */
#ifndef WF_EXPORT_H
#define WF_EXPORT_H

#if defined(WF_SHARED) && defined(_WIN32)
#ifdef WF_BUILDING
#define WF_API __declspec(dllexport)
#else
#define WF_API __declspec(dllimport)
#endif
#elif defined(WF_SHARED) && defined(__GNUC__)
#define WF_API __attribute__((visibility("default")))
#else
#define WF_API
#endif

#endif
```

每个公开函数的声明前加上 `WF_API`，例如 `WF_API size_t wf_counter_top(...)`。`WF_BUILDING` 只在构建 `wf` 时定义（`target_compile_definitions(wf PRIVATE WF_BUILDING)`），`WF_SHARED` 只在 `BUILD_SHARED_LIBS` 打开时定义，并且用 `PUBLIC` 传给使用方：

```cmake
target_compile_definitions(wf PRIVATE WF_BUILDING)

if(BUILD_SHARED_LIBS)
    target_compile_definitions(wf PUBLIC WF_SHARED)
endif()
```

静态库构建时 `WF_SHARED` 未定义，`WF_API` 展开为空，声明与以前一模一样；共享库构建时，`wf` 自己看到 `dllexport`，使用方看到 `dllimport`，链接器就知道该从哪里找符号。GCC 的分支用 `visibility("default")`，在默认隐藏符号的设置下把公开接口重新暴露出来。加好之后，MSVC 的共享库构建通过，`wordfreq` 与测试都能链接运行：

::: terminal title="PowerShell - 加好导出标记后的 MSVC 共享库构建"

```text
[9/12] Linking C shared library wf.dll
[10/12] Linking C executable test_token.exe
[11/12] Linking C executable wordfreq.exe
[12/12] Linking C executable test_counter.exe
.\wordfreq.exe -n 3 ..\tests\data\sample.txt
      4 the
      2 on
      2 sat
```

:::

CMake 提供了两个减少手写的工具：`GenerateExportHeader` 模块按目标名自动生成一个类似 `export.h` 的头文件，`CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS` 让 CMake 扫描目标文件、自动为所有符号生成导出表。前者生成的头文件要包含进每个公开头文件，后者对带全局对象的库会出问题；wordfreq 的公开接口只有九个函数，手写一份 `export.h` 反而最清楚。

::: concept dev-portable-export-marker title="共享库的公开接口需要显式导出"

Windows 上共享库默认不导出符号，MSVC 没有导入库就无法链接；MinGW 默认导出全部符号，只是它的选择。可移植的写法是在公开头文件里用宏区分「构建库」「使用库」「静态链接」三种情形，让同一份声明在三种配置下都正确。Linux 上这个宏通常展开为空，不产生任何代价。

:::

最后一件事是运行时到哪里找库。CMake 在 Linux 上给可执行文件写 RUNPATH，指向构建目录，所以在构建目录里直接运行没问题。`readelf -d` 的输出里有一行：


## 9. 预设

同一份工程，开发时用 Debug 构建，发布时用 Release，检查内存错误时开 Sanitizer，在 Windows 上还要换成 MSVC，每种组合都对应一串 `cmake -S . -B ... -D...` 命令。这些命令写在 README 里容易抄错，写进 CI 脚本又和本地不一致。CMake 的预设 (preset) 把它们存进 `CMakePresets.json`，本地和 CI 用同一个名字调用。

wordfreq 的 `CMakePresets.json`（version 6，需要 CMake 3.25 以上）定义了四个配置预设：`dev-gcc`、`release`、`asan`、`msvc`，以及同名的构建预设和测试预设，再加一个把三者串起来的 `ci` 工作流预设。核心结构如下（省略了重复的构建与测试预设）：

```json
{
  "version": 6,
  "cmakeMinimumRequired": { "major": 3, "minor": 25, "patch": 0 },
  "configurePresets": [
    {
      "name": "dev-gcc",
      "displayName": "Debug (GCC/Clang)",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" }
    },
    {
      "name": "asan",
      "displayName": "Debug + Sanitizer",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build-asan",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "WF_SANITIZE": "ON"
      }
    },
    {
      "name": "msvc",
      "displayName": "MSVC (Ninja)",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build-msvc",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" },
      "condition": {
        "type": "equals",
        "lhs": "${hostSystemName}",
        "rhs": "Windows"
      }
    }
  ],
  "workflowPresets": [
    {
      "name": "ci",
      "steps": [
        { "type": "configure", "name": "dev-gcc" },
        { "type": "build", "name": "dev-gcc" },
        { "type": "test", "name": "dev-gcc" }
      ]
    }
  ]
}
```

`binaryDir` 里的 `${sourceDir}` 是预设变量，展开成源码目录；每个预设一个构建目录，互不干扰。`condition` 让 `msvc` 预设只在 Windows 上出现，Linux 上 `cmake --list-presets` 看不到它。工作流预设的 `steps` 依次执行配置、构建、测试，每一步引用同名的预设。

`cmake --list-presets` 列出可用的配置预设，`--list-presets=build`、`--list-presets=test`、`--list-presets=workflow` 分别列出另外三类（Windows）：

## 10. 交叉编译与工具链文件

前面所有配置都默认「在本机编译、在本机运行」。给另一种处理器构建时，编译器、头文件、库、运行环境都不在本机的默认位置，CMake 需要一份工具链文件 (toolchain file) 告诉它这些事。工具链文件本身也是一份 CMake 脚本，在配置阶段最开始被读入，只能设置跟编译器、系统相关的变量。

一个面向 64 位 ARM Linux 的工具链文件：

```cmake
# aarch64-linux-gnu.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

`CMAKE_SYSTEM_NAME` 设成目标系统的名字，CMake 据此判断这是交叉编译而不是本机编译；`CMAKE_C_COMPILER` 写交叉编译器在 `PATH` 里的名字或完整路径。`CMAKE_FIND_ROOT_PATH_MODE_*` 控制 `find_package`、`find_library` 去哪里找：程序（如 `cmake` 自己调用的工具）在本机找，库、头文件、包只在目标环境的根目录里找，避免把本机的 x86 库链接进 ARM 程序。

::: terminal title="zsh - 本机没有安装交叉编译器时"

```console
$ cmake --toolchain aarch64-linux-gnu.cmake -S . -B build-arm64
-- Building for: Ninja
-- The C compiler identification is unknown
CMake Error at CMakeLists.txt:2 (project):
  The CMAKE_C_COMPILER:

    aarch64-linux-gnu-gcc

  is not a full path and was not found in the PATH.  Perhaps the extension is
  missing?

  Tell CMake where to find the compiler by setting either the environment
  variable "CC" or the CMake cache entry CMAKE_C_COMPILER to the full path to
  the compiler, or to the compiler name if it is in the PATH.
```

:::

两台机器上都没有安装交叉编译器，所以这里只能给出文件与失败输出，构建产物无法验证。错误信息本身说明了工具链文件的工作方式：CMake 拿到 `CMAKE_C_COMPILER` 后去 `PATH` 里找，找不到就在配置阶段停下，不会生成一个用错编译器的构建目录。`--toolchain` 是 CMake 3.21 起的写法，旧版本用 `-DCMAKE_TOOLCHAIN_FILE=aarch64-linux-gnu.cmake`，两者等价。

工具链文件与预设可以组合：在 `CMakePresets.json` 的 `cacheVariables` 里写 `"CMAKE_TOOLCHAIN_FILE": "aarch64-linux-gnu.cmake"`，就得到一个专门做交叉构建的预设。XMake 里对应的是 `xmake f -p mingw -a x86_64` 这类平台参数，粒度比 CMake 的工具链文件粗，但常见的嵌入式与 MinGW 目标都覆盖到了。嵌入式部分的交叉编译在 [1.5 开发环境与交叉编译](/教程/正文/嵌入式/1_平台与工具链/1_5_开发环境与交叉编译) 里从工具链安装讲起，sysroot 与根文件系统的组织见 [5.3 交叉工具链、sysroot 与根文件系统](/教程/正文/嵌入式/5_嵌入式Linux/5_3_交叉工具链_sysroot与根文件系统)。
