# 13. 编译器诊断与程序检查

wordfreq 的测试全部通过，换一台机器却偶尔崩溃。同一份代码，测试时一切正常，交付后在某台机器上偶发段错误，这类问题最难查：错误确实存在，只是大多数时候不表现出来。少分配的一个字节落在分配器的填充区里，越界的读拿到的是别处残留的数据，有符号整数溢出算出来的结果恰好还能用。

编译器和运行时检查能把这些错误提前暴露。这一章讲四类工具：编译器的警告（warning）、GCC 的静态分析器、cppcheck 与 clang-tidy 这类独立检查工具，以及 AddressSanitizer、UndefinedBehaviorSanitizer 这类在程序运行时检查的 Sanitizer。读完能在项目里选定一组警告、把静态检查和 Sanitizer 接进构建，看懂它们的报告，并知道每种工具的代价。

文中的输出取自 Debian 13 上的 GCC 14.2 与 Windows 11 上的 MinGW-w64 GCC 13.2，每组输出都注明来源。两个版本的诊断格式相同，措辞和个别行为有差别时单独说明。正文里的小程序放在 `code/开发与工程基础/13_编译器诊断与程序检查/demos/`，注入缺陷的版本放在同目录的 `bugs/` 下。

## 1. 读懂一条诊断

编译器报告问题叫诊断（diagnostic）。一条诊断由几部分组成，以下面这段代码为例，`total` 拼成了 `totl`：

```c [typo.c]
#include <stdio.h>

int main(void) {
    int total = 0;
    printf("%d\n", totl);
    return 0;
}
```

::: terminal title="zsh - gcc -fsyntax-only typo.c"

```text
$ gcc -std=c17 -Wall -Wextra -fsyntax-only typo.c
typo.c: In function 'main':
typo.c:5:20: error: 'totl' undeclared (first use in this function); did you mean 'total'?
    5 |     printf("%d\n", totl);
      |                    ^~~~
      |                    total
typo.c:5:20: note: each undeclared identifier is reported only once for each function it appears in
typo.c:4:9: warning: unused variable 'total' [-Wunused-variable]
    4 |     int total = 0;
      |         ^~~~~
```

:::

第一行的 `typo.c: In function 'main':` 说明后面这条诊断属于哪个函数。真正的诊断行是 `typo.c:5:20: error: ...`，依次是文件名、行号、列号、级别和消息。级别有三种：`error` 表示翻译无法继续，不生成目标文件；`warning` 表示代码可以编译，但很可能有问题；`note` 是对前一条诊断的补充，本身不算问题。

方括号里的 `[-Wunused-variable]` 是这条警告所属的选项名。所有警告都可以用 `-Wno-选项名` 单独关闭，这是后面挑选警告选项的基础。

诊断下面三行是源代码摘录。`^~~~` 标出出错的位置，插入符正对上一条诊断里的列号。`did you mean 'total'?` 后面那行单独的 `total` 是编译器给出的修正建议，按它的提示改名即可。

`-fsyntax-only` 只做语法和语义检查，不生成目标文件，适合快速核对代码：

::: terminal title="zsh - 不生成目标文件"

```text
$ gcc -std=c17 -Wall -Wextra -fsyntax-only syntax.c
$ ls syntax.o
ls: cannot access 'syntax.o': No such file or directory
```

:::

文件本身没有问题，所以没有任何输出。编辑器插件在保存文件时用这个选项快速刷新诊断，不必等整个构建跑完。

一次编译出现多条错误时，先看第一条。后面的错误常常是第一条的连锁反应。漏写一个分号就能说明这一点：

```c [missing_semicolon.c]
#include <stdio.h>

int main(void) {
    int count = 0
    for (int i = 0; i < 3; i++) {
        count += i;
    }
    printf("%d\n", count);
    return 0;
}
```

::: terminal title="zsh - 第一条错误"

```text
$ gcc -std=c17 -Wall -Wextra -fsyntax-only missing_semicolon.c
missing_semicolon.c: In function 'main':
missing_semicolon.c:5:5: error: expected ',' or ';' before 'for'
    5 |     for (int i = 0; i < 3; i++) {
      |     ^~~
missing_semicolon.c:5:21: error: 'i' undeclared (first use in this function)
    5 |     for (int i = 0; i < 3; i++) {
      |                     ^
missing_semicolon.c:5:21: note: each undeclared identifier is reported only once for each function it appears in
missing_semicolon.c:5:31: error: expected ';' before ')' token
    5 |     for (int i = 0; i < 3; i++) {
      |                               ^
      |                               ;
missing_semicolon.c:5:31: error: expected statement before ')' token
```

:::

四条错误全指向第 5 行。第一条说 `for` 前面少一个分号，补上这一个字符，另外三条一起消失。盯着后面几条改，往往改不到点上。

GCC 还能把修正建议直接写成补丁。`-fdiagnostics-generate-patch` 在诊断之后打印一个 unified diff：

::: terminal title="zsh - 生成修正补丁"

```text
$ gcc -std=c17 -Wall -Wextra -fdiagnostics-generate-patch -fsyntax-only typo.c
typo.c: In function 'main':
typo.c:5:20: error: 'totl' undeclared (first use in this function); did you mean 'total'?
...
--- typo.c
+++ typo.c
@@ -2,6 +2,6 @@

 int main(void) {
     int total = 0;
-    printf("%d\n", totl);
+    printf("%d\n", total);
     return 0;
 }
```

:::

长输出里常把中间部分略去，写成 `...`，这一段是从完整输出里截取的开头和结尾。

## 2. 警告选项

GCC 默认只开很少的警告。`-Wall` 打开一组常用检查，`-Wextra` 再补上一些噪声稍大的检查。下面这个文件故意留了几处问题：

```c [warn.c]
#include <stdio.h>

static int classify(int value) {
    switch (value) {
    case 0:
        puts("zero");
        /* 这里漏了 break */
    case 1:
        puts("small");
        break;
    default:
        puts("other");
        break;
    }
    return value;
}

static int sum(const int *items, int n, int scale) {
    int total = 0;
    for (int i = 0; i < n; i++) {
        total += items[i];
    }
    return total;
}

int main(int argc, char *argv[]) {
    int items[] = {1, 2, 3};
    size_t count = sizeof items / sizeof items[0];
    int limit = argc;
    long wide = sizeof(int);
    int unused_local = 0;

    int flag = 0;
    if (flag = argc) {
        puts("flag is nonzero");
    }
    printf("%d\n", wide);
    if (count > limit) {
        puts("more items than limit");
    }
    printf("%d\n", classify(0) + sum(items, 3, limit));
    return 0;
}
```

先只看 `-Wall`：

::: terminal title="zsh - gcc -Wall（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -c warn.c -o warn.o
warn.c: In function 'main':
warn.c:34:9: warning: suggest parentheses around assignment used as truth value [-Wparentheses]
   34 |     if (flag = argc) {
      |         ^~~~
warn.c:37:14: warning: format '%d' expects argument of type 'int', but argument 2 has type 'long int' [-Wformat=]
   37 |     printf("%d\n", wide);
      |             ~^     ~~~~
      |              |     |
      |              int   long int
      |             %ld
warn.c:31:9: warning: unused variable 'unused_local' [-Wunused-variable]
   31 |     int unused_local = 0;
      |         ^~~~~~~~~~~~
```

:::

三条警告对应三种错误。`if (flag = argc)` 把赋值写进了条件，本意应是 `==`；`-Wparentheses` 要求加一层括号，加上的过程就是逼作者确认「这里确实是要赋值」。`%d` 配 `long`：在 64 位 Linux 上 `long` 占 8 字节，`%d` 只读 4 字节，格式串与实参类型必须严格对应，这里应写 `%ld`。声明了不用的对象占着名字，读代码的人会以为它有作用。

同一份代码在 Windows 的 MinGW-w64 GCC 13.2 上编译时，这条格式警告原样出现两遍，内容完全相同，按一条处理即可。少数版本会重复报告同一条诊断，数量不必当真。

加上 `-Wextra`：

::: terminal title="zsh - gcc -Wall -Wextra（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -c warn.c -o warn.o
warn.c: In function 'sum':
warn.c:18:45: warning: unused parameter 'scale' [-Wunused-parameter]
   18 | static int sum(const int *items, int n, int scale) {
      |                                         ~~~~^~~~~
warn.c: In function 'main':
warn.c:34:9: warning: suggest parentheses around assignment used as truth value [-Wparentheses]
   34 |     if (flag = argc) {
      |         ^~~~
warn.c:37:14: warning: format '%d' expects argument of type 'int', but argument 2 has type 'long int' [-Wformat=]
   37 |     printf("%d\n", wide);
      |             ~^     ~~~~
      |              |     |
      |              int   long int
      |             %ld
warn.c:38:15: warning: comparison of integer expressions of different signedness: 'size_t' {aka 'long unsigned int'} and 'int' [-Wsign-compare]
   38 |     if (count > limit) {
      |               ^
warn.c:31:9: warning: unused variable 'unused_local' [-Wunused-variable]
   31 |     int unused_local = 0;
      |         ^~~~~~~~~~~~
warn.c:26:26: warning: unused parameter 'argv' [-Wunused-parameter]
   26 | int main(int argc, char *argv[]) {
      |                    ~~~~~~^~~~~~
warn.c: In function 'classify':
warn.c:6:9: warning: this statement may fall through [-Wimplicit-fallthrough=]
    6 |         puts("zero");
      |         ^~~~~~~~~~~~
warn.c:8:5: note: here
    8 |     case 1:
      |     ^~~~
```

:::

`-Wextra` 新报出三类。`sum` 的 `scale` 参数没有用到，调用方传进来的值被悄悄忽略，这类问题在接口改动后很常见。`count > limit` 把无符号的 `size_t` 和有符号的 `int` 比较，`limit` 为负时会先转换成无符号数，比较结果与直觉相反。`case 0` 漏了 `break`，执行完会继续走进 `case 1`。`main` 的 `argv` 没用到则是无害的，`-Wunused-parameter` 不为 `main` 免除这项检查。

在 C 里，`-Wsign-compare`、`-Wunused-parameter`、`-Wimplicit-fallthrough` 都只在 `-Wextra` 下出现。这三个是 `-Wextra` 最值得打开的理由。

### 2.1 标准符合性与额外检查

`-Wpedantic` 报告 GNU 扩展和其他编译器接受、标准不允许的写法。下面这个文件用了零长度数组，GCC 作为扩展接受，标准不允许：

```c [zero_array.c]
#include <stdio.h>

int main(void) {
    int values[0];
    return (int)sizeof values;
}
```

::: terminal title="zsh - 标准模式下的扩展"

```text
$ gcc -std=c17 -Wall -Wextra -Wpedantic -c zero_array.c -o zero_array.o
zero_array.c: In function 'main':
zero_array.c:4:9: warning: ISO C forbids zero-size array 'values' [-Wpedantic]
    4 |     int values[0];
      |         ^~~~~~
```

:::

加 `-pedantic-errors` 后这条从警告升级为错误，编译直接失败。需要严格符合标准的代码（要交给别的编译器、要过评审）用后者，其余场合用 `-Wpedantic` 即可。

几组值得额外打开的检查。下面这个文件把这些选项各自能发现的问题放在一起：

```c [warn_more.c]
#include <stdio.h>

int open_file();

int double_value(int x) {
    return x * 2;
}

int open_file() {
    int count = 1;
    {
        int count = 2;
        printf("%d\n", count);
    }
    int values[count];
    for (int i = 0; i < count; i++) {
        values[i] = i;
    }
    return values[0];
}

static void log_value(const char *fmt, int value) {
    printf(fmt, value);
}

int main(void) {
    log_value("%d\n", double_value(open_file()));
    return 0;
}
```

编译结果：

::: terminal title="zsh - 补充的警告选项（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -Wshadow -Wformat=2 -Wmissing-prototypes \
      -Wstrict-prototypes -Wvla -c warn_more.c -o warn_more.o
warn_more.c:3:1: warning: function declaration isn't a prototype [-Wstrict-prototypes]
    3 | int open_file();
      | ^~~
warn_more.c:5:5: warning: no previous prototype for 'double_value' [-Wmissing-prototypes]
    5 | int double_value(int x) {
      |     ^~~~~~~~~~~~
warn_more.c:9:5: warning: function declaration isn't a prototype [-Wstrict-prototypes]
    9 | int open_file() {
      |     ^~~~~~~~~
warn_more.c: In function 'open_file':
warn_more.c:12:13: warning: declaration of 'count' shadows a previous local [-Wshadow]
   12 |         int count = 2;
      |             ^~~~~
warn_more.c:10:9: note: shadowed declaration is here
   10 |     int count = 1;
      |         ^~~~~
warn_more.c:15:5: warning: ISO C90 forbids variable length array 'values' [-Wvla]
   15 |     int values[count];
      |         ^~~
warn_more.c: In function 'log_value':
warn_more.c:23:5: warning: format not a string literal, argument types not checked [-Wformat-nonliteral]
   23 |     printf(fmt, value);
      |     ^~~~~~
```

:::

`-Wmissing-prototypes` 报出 `double_value` 没有在头文件里声明。这类函数在别的翻译单元里看不到原型，调用时参数类型只能靠调用方自觉，链接器也不检查。看到这条警告，要么给函数加 `static`，要么把它放进模块的头文件，[第 6 章](/教程/正文/开发与工程基础/6_头文件与接口边界)讲过这个判断。

`-Wstrict-prototypes` 要求声明写明参数类型，`int open_file()` 在 C 里表示「参数未知」，应写成 `int open_file(void)`。

`-Wshadow` 报出内层块里的 `count` 遮住了外层的同名对象。改内层名字就能消除，遮住之后外层对象的事很容易被误读。

`-Wformat=2` 在 `-Wformat` 之上增加了非字面量格式串的检查。`log_value` 把格式串作为参数传进来，编译器无法核对后续实参的类型，这本身就是一类设计问题。

`-Wvla` 报告变长数组，它在栈上按运行时长度分配，长度失控时直接栈溢出，嵌入式项目中一般禁用。

`-Wconversion` 检查隐式类型转换可能丢失信息的地方：

::: terminal title="zsh - -Wconversion（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -Wconversion -c conversion.c -o conversion.o
conversion.c: In function 'main':
conversion.c:5:13: warning: conversion from 'size_t' {aka 'long unsigned int'} to 'int' may change value [-Wconversion]
    5 |     int n = strlen(argv[0]);
      |             ^~~~~~
conversion.c:6:27: warning: conversion from 'int' to 'unsigned char' may change value [-Wconversion]
    6 |     unsigned char small = argc + 300;
      |                           ^~~~
```

:::

这条检查在旧代码上会报出成百上千条，其中大多数是已知安全的窄化。作者的用法是：新文件从一开始打开，旧文件按模块逐个打开并清理，不要求一次清完。

### 2.2 把警告当错误

`-Werror` 把所有警告升级为错误：

::: terminal title="zsh - -Werror（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -Werror -c warn.c -o warn.o
warn.c: In function 'sum':
warn.c:18:45: error: unused parameter 'scale' [-Werror=unused-parameter]
...
warn.c:6:9: error: this statement may fall through [-Werror=implicit-fallthrough=]
...
cc1: all warnings being treated as errors
```

:::

它的用途是防止新警告混进来：只要有一个警告就构建失败，提交前必然被发现。因此只放进持续集成和开发者自己的构建，不写进交给用户构建的发布文件。用户换一个编译器版本，新版本多出的一条警告就会让构建失败，而他改不了源码。[第 18 章](/教程/正文/开发与工程基础/18_持续集成)的 CI 会打开它。

Windows 上用 MSVC 时对应的选项是 `/W4`，警告编号形如 `C4100`，`/WX` 相当于 `-Werror`；[第 16 章](/教程/正文/开发与工程基础/16_可移植构建)讲按编译器选择选项的写法。

## 3. 静态分析

警告只看单个表达式和语句的局部形式。GCC 的静态分析器（`-fanalyzer`，GCC 10 引入）沿着函数的控制流走一遍，跟踪指针和资源在每条路径上的去向。它能发现跨语句的问题，例如某条错误路径上打开的 `FILE *` 没有关闭。

给 wordfreq 的 `app/main.c` 加一个 `load_file`，用 `fopen`、`fseek`/`ftell`、`malloc`、`fread` 读入整个文件。其中 `fseek` 失败的分支直接返回，忘了 `fclose`：

```c [bugs/main_load_file_leak.c]
static int load_file(const char *path, char **out, size_t *len) {
    FILE *in = fopen(path, "rb");
    if (in == NULL) {
        return -1;
    }

    if (fseek(in, 0, SEEK_END) != 0) {
        /* 缺陷：这里直接返回，没有 fclose(in) */
        return -1;
    }
    long size = ftell(in);
    /* ... */
}
```

::: terminal title="zsh - gcc -fanalyzer（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -fanalyzer -c bugs/main_load_file_leak.c
```

:::

报告的主体是一条事件路径，编号从 (1) 到 (7)，用来说明分析器是怎么走到这个结论的：文件在哪里打开、在哪个条件上选择了哪条分支、在哪一行漏掉关闭。读这类报告先看最后一条事件和警告行的行号，再倒回去核对路径是否成立。CWE-775 是这条缺陷的通用编号，可以据此查资料。

GCC 14.2 还会紧接着报一条 `[-Wanalyzer-malloc-leak]`：它把 `fopen` 得到的 `FILE *` 也当成一次分配。两条警告指向同一个问题，修一次即可；GCC 13.2 上只有第一条。

GCC 文档明确说分析器既不健全也不完备（neither sound nor complete）：它报出的是确实可能发生的错误，但它找不到的错误同样很多。它没有被报出，不等于程序没有泄漏。实测中下面几种写法不报：

- 指针被赋给文件作用域的对象之后，分析器不再跟踪它；
- 指针传给另一个翻译单元里的函数（只有声明、没有函数体）之后，同理；
- 泄漏发生在 `main` 末尾时；
- `load_file` 改写成返回 `char *`、长度通过指针送出后，同一条 `fseek` 错误路径不再被报告。

修好之后分析器不再有抱怨。按[第 14.5 节](/教程/正文/语法和标准库/14_文本转换_错误与程序生命周期/14_5_goto清理模式)的写法，把清理动作收拢到函数末尾的一个标签后面：

```c [load_file_fixed.c]
static int load_file(const char *path, char **out, size_t *len) {
    FILE *in = fopen(path, "rb");
    if (in == NULL) {
        return -1;
    }
    char *buf = NULL;
    int status = -1;
    if (fseek(in, 0, SEEK_END) != 0) {
        goto done;
    }
    long size = ftell(in);
    if (size < 0) {
        goto done;
    }
    rewind(in);
    buf = malloc((size_t)size + 1);
    if (buf == NULL) {
        goto done;
    }
    size_t got = fread(buf, 1, (size_t)size, in);
    buf[got] = '\0';
    *out = buf;
    *len = got;
    buf = NULL; /* 所有权已交给调用方，done 里不能再释放 */
    status = 0;

done:
    free(buf);
    fclose(in);
    return status;
}
```

`buf` 在离开前先置空，`done` 处的 `free(NULL)` 什么也不做，成功路径和失败路径共用同一段清理代码。`-fanalyzer` 对这个版本没有任何输出。这段代码在 `bugs/load_file_fixed.c`。

::: compare left-title="被跟踪：错误路径直接返回" right-title="不被跟踪：指针交给外部函数"

## 4. AddressSanitizer

前面三类工具都在编译前后工作。有些错误只在运行时才存在，例如写到分配区之外的一个字节。AddressSanitizer（ASan）在编译时给每次内存访问插入检查，在程序运行时抓住越界。

本章给 wordfreq 注入的缺陷在 `dup_string`：

```c [bugs/counter_dup_off_by_one.c]
/* 缺陷：少分配一个字节，memcpy 时写到缓冲区之外 */
static char *dup_string(const char *s) {
    size_t len = strlen(s);
    char *copy = malloc(len);
    if (copy != NULL) {
        memcpy(copy, s, len + 1);
    }
    return copy;
}
```

### 4.1 LeakSanitizer

泄漏检测由 LeakSanitizer（LSan）负责，它在 Linux 和 macOS 上随 ASan 一起启用，程序正常退出时检查有没有未释放的分配：

```text
    #0 0x7f1607ef4c57 in malloc ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:69
```

`leak.c` 只是 `malloc(64)` 之后忘了 `free`。LSan 给出泄漏的字节数、分配了几处，以及分配发生的位置和行号，足够定位。

默认情况下检测到泄漏会让进程以非 0 状态结束，测试框架据此判定失败。有些程序故意保留一些长期存活的分配，可以在运行时关掉泄漏检测：

::: terminal title="zsh - 关闭泄漏检测"

```text

$ echo $?

```

`ASAN_OPTIONS` 是 ASan 的运行时配置，`detect_leaks` 只是其中一个。其他常用的有 `halt_on_error=1`（第一次出错就停）、`abort_on_error=1`（以 abort 结束，便于拿到核心转储）。用 `ASAN_OPTIONS=help=1 ./prog` 可以列出全部选项。

### 4.2 编译选项与平台

ASan 的推荐组合是：

```text
-fsanitize=address -fno-omit-frame-pointer -g -O1
```

`-g` 让报告里的地址能还原成文件名和行号；`-fno-omit-frame-pointer` 保留帧指针，调用栈才完整；`-O1` 兼顾可读的栈和可用的速度，`-O0` 也能用，只是更慢。

平台方面：

- Linux 上 GCC 和 Clang 都支持，glibc 自带需要的运行库；
- macOS 上 Apple Clang 支持；
- Windows 上 MSVC（`/fsanitize=address`）和 Clang for Windows 支持，Visual Studio 的 CMake 工程打开一个选项即可；
- MinGW-w64 的 GCC 不提供 ASan 运行库，加 `-fsanitize=address` 编译能过，链接时报 `cannot find -lasan`。

::: concept dev-diag-sanitizer-executed-only title="Sanitizer 只发现执行到的路径"

AddressSanitizer 在每次内存访问处插入检查，只有程序真的执行到越界的那条语句才会报告。一份没被测试覆盖的代码，或者一个从未被调用的错误分支，Sanitizer 什么也发现不了。

:::

这条性质决定了 Sanitizer 的用法：它发现的错误是确实存在的，它没有报告不等于程序干净。所以[第 14 章](/教程/正文/开发与工程基础/14_覆盖率与模糊测试)还要用覆盖率找出没测到的分支，用模糊测试去走到那些分支。把 Sanitizer 构建挂到测试上跑，是让已有的测试顺带发挥检查作用，它不能替代测试本身。

## 5. UndefinedBehaviorSanitizer

未定义行为（undefined behavior）包括有符号整数溢出、移位位数超过类型宽度、除以零、`NULL` 解引用等。这些操作在某一台机器上可能算出「正常」的结果，标准却不保证任何行为。UndefinedBehaviorSanitizer（UBSan）在运行时检查这类操作。

两个小程序，第一个是有符号整数溢出：

```c [bugs/ub_overflow.c]
#include <limits.h>
#include <stdio.h>

int main(int argc, char *argv[]) {
    int value = INT_MAX;
    value += argc;
    printf("%d %s\n", value, argv[0]);
    return 0;
}
```

实参来自 `argc`，运行时才知道结果，编译器不能把整个表达式折叠掉。第二个是移位：

```c [bugs/ub_shift.c]
#include <stdio.h>

int main(void) {
    unsigned int shift = 40;
    unsigned int value = 1u << shift;
    printf("%u\n", value);
    return 0;
}
```

::: terminal title="zsh - UBSan（Debian 13，GCC 14.2）"

```text
$ gcc -std=c17 -Wall -Wextra -g -fsanitize=undefined -o ub_overflow bugs/ub_overflow.c
$ ./ub_overflow
bugs/ub_overflow.c:11:11: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648 ./ub_overflow
$ echo $?
0
$ gcc -std=c17 -Wall -Wextra -g -fsanitize=undefined -o ub_shift bugs/ub_shift.c
$ ./ub_shift
bugs/ub_shift.c:9:29: runtime error: shift exponent 40 is too large for 32-bit type 'unsigned int'
256
$ echo $?
0
```

:::

报告格式与编译器诊断相同：文件名、行号、列号、`runtime error`、具体说明。两次运行都继续执行到了结束，退出状态仍是 0，`printf` 还把溢出后的值打了出来。这正是未定义行为危险的地方：它看起来像正常工作。

默认设置下 UBSan 报告之后继续运行，适合先摸清有多少问题。放进测试时应该让它在第一次出错就终止，否则测试的退出状态无法反映问题：

::: terminal title="zsh - 报告后立即终止"

```text
$ gcc -std=c17 -Wall -Wextra -g -fsanitize=undefined \
      -fno-sanitize-recover=all -o ub_overflow_strict bugs/ub_overflow.c
$ ./ub_overflow_strict
bugs/ub_overflow.c:11:11: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
$ echo $?
1
```

:::

MinGW-w64 的 GCC 同样没有 UBSan 运行库。退一步可以用 `-fsanitize-trap=all`，它把检查变成一条非法指令，触发时进程直接终止，没有任何文字说明：

::: terminal title="zsh - MinGW 上的 UBSan（Windows，GCC 13.2）"

```text
$ gcc -std=c17 -Wall -Wextra -g -fsanitize=undefined -fsanitize-trap=all \
      -o ub_overflow_trap bugs/ub_overflow.c
$ ./ub_overflow_trap
bash: line 1: 80224 Illegal instruction        ./ub_overflow_trap
$ echo $?
132
```

:::

只知道「这里出过事」，不知道是哪一行、哪一类操作。所以 Windows 上的开发也用 MSVC 或 Clang 的 Sanitizer，MinGW 的 trap 模式只作为兜底。

## 6. Valgrind

Valgrind 是 Linux 上的动态分析工具，最常用的是 Memcheck，功能与 ASan 重叠：越界读写、释放后使用、泄漏、未初始化的读取。它的做法是在自己的虚拟处理器上运行程序，因此不需要重新编译：

::: terminal title="zsh - valgrind"

```text
$ valgrind --leak-check=full ./prog
==19182== Invalid write of size 4
==19182==    at 0x804838F: f (test.c:6)
==19182==    by 0x80483AB: main (test.c:11)
==19182==  Address 0x1BA45050 is 0 bytes after a block of size 40 alloc'd
==19182==    at 0x1B8FF5CD: malloc (vg_replace_malloc.c:130)
==19182==    by 0x8048385: f (test.c:5)
==19182==    by 0x80483AB: main (test.c:11)
```

（输出类似：上面这段取自 Valgrind 官方 Quick Start 的 `test.c` 示例，地址随运行环境变化。本机与实验机上都没有安装 Valgrind，未实测。）

代价是速度。每条指令都要经过 Valgrind 的翻译执行，官方文档给出的估计是慢二十到三十倍，内存占用也显著增加，建议只在调试时使用。大型程序在 Valgrind 下跑一遍测试要等很久，ASan 通常只慢两倍左右。

能重新编译时优先 Sanitizer。Valgrind 适合两种场合：拿到的只有可执行文件、没有源码和构建环境；或者需要 ASan 不提供的检查项（Memcheck 之外还有 Cachegrind、Callgrind、Helgrind 等工具）。macOS 上 Valgrind 的支持一直不完整，Windows 上没有。

## 7. 组合进构建

四类工具的定位可以放在一张表里：

| 工具 | 发现什么 | 代价 | 什么时候跑 |
| --- | --- | --- | --- |
| 警告（`-Wall -Wextra` 加补充项） | 可疑的表达式、类型不匹配、未使用名字 | 编译稍慢，几乎不影响运行 | 每次编译 |
| `-fanalyzer` | 跨语句的资源泄漏、空指针、释放后使用 | 编译明显变慢，单个文件数秒 | 开发构建与 CI |
| cppcheck、clang-tidy | 未初始化读取、越界、可移植性问题、风格 | 独立运行，分钟级 | CI，或改动后手动跑 |
| ASan、LSan、UBSan | 运行时真实发生的越界、泄漏、未定义行为 | 运行慢约两倍，内存增加 | 开发构建的测试、CI |

前面几节都是命令行单独调用。工程里把它们接进构建，开发者不必记这些命令。本章的 `CMakeLists.txt` 有两个选项：

```cmake
option(WF_SANITIZE "Build with AddressSanitizer and UndefinedBehaviorSanitizer" OFF)
option(WF_WERROR "Treat warnings as errors" OFF)

set(WF_WARNINGS -Wall -Wextra -Wshadow -Wformat=2
    -Wmissing-prototypes -Wstrict-prototypes -Wvla)
```

`WF_SANITIZE` 打开时，给库、程序、两个测试程序同时加编译和链接选项：

```cmake
if(WF_SANITIZE)
    foreach(target wf wordfreq test_token test_counter)
        target_compile_options(${target} PRIVATE
            -fsanitize=address,undefined -fno-omit-frame-pointer)
        target_link_options(${target} PRIVATE -fsanitize=address,undefined)
    endforeach()
endif()
```

::: concept dev-diag-sanitizer-options-both-phases title="Sanitizer 选项要同时出现在编译与链接命令中"

`-fsanitize=address`（或 `undefined`）在编译时插入检查代码，在链接时把对应的运行库接进来。编译和链接两处缺一不可：少了编译选项，代码里没有检查；少了链接选项，检查代码引用的 `__asan_*` 等符号无从解析。

:::

编译和链接都要加同一组 `-fsanitize`，用 `--verbose` 看一次实际命令就明白了：

::: terminal title="zsh - 编译与链接命令（Debian 13，GCC 14.2）"

```text
$ cmake --build build-asan --verbose
[  8%] Building C object CMakeFiles/wf.dir/src/counter.c.o
/usr/bin/cc -I/home/minsecrus/tutorial/work/p055/ch13/wordfreq/include -std=c17 \
  -Wall -Wextra -Wshadow -Wformat=2 -Wmissing-prototypes -Wstrict-prototypes \
  -Wvla -fsanitize=address,undefined -fno-omit-frame-pointer \
  -MD -MT CMakeFiles/wf.dir/src/counter.c.o -MF CMakeFiles/wf.dir/src/counter.c.o.d \
  -o CMakeFiles/wf.dir/src/counter.c.o -c .../src/counter.c
[ 91%] Linking C executable test_counter
/usr/bin/cc -fsanitize=address,undefined -Wl,--dependency-file=... \
  CMakeFiles/test_counter.dir/tests/test_counter.c.o \
  CMakeFiles/test_counter.dir/tests/check.c.o -o test_counter  libwf.a
```

:::

编译命令里的 `-fsanitize=address,undefined` 负责插入检查，链接命令里的同一组选项负责接上运行库。漏掉后者，链接器会报一堆找不到的符号：

::: terminal title="zsh - 只在编译时加了 -fsanitize"

```text
$ gcc -std=c17 -Wall -Wextra -fsanitize=address -c dup_demo.c -o dup_demo.o
$ gcc dup_demo.o -o dup_demo_plain
/usr/bin/ld: dup_demo.o: in function `_sub_D_00099_0':
dup_demo.c:(.text+0xa2): undefined reference to `__asan_unregister_globals'
/usr/bin/ld: dup_demo.o: in function `_sub_I_00099_1':
dup_demo.c:(.text+0xad): undefined reference to `__asan_init'
/usr/bin/ld: dup_demo.c:(.text+0xb2): undefined reference to `__asan_version_mismatch_check_v8'
/usr/bin/ld: dup_demo.c:(.text+0xc6): undefined reference to `__asan_register_globals'
collect2: error: ld returned 1 exit status
```

:::

`__asan_init` 这些符号就在 ASan 运行库里，链接命令行缺少 `-fsanitize=address`，运行库不会被自动加入。CMake 的 `target_link_options` 解决的就是这一步。

按用途分三种构建：

| 构建 | 打开的选项 | 用途 |
| --- | --- | --- |
| 开发 | `-Wall -Wextra -Wshadow -Wformat=2 -Wmissing-prototypes -Wstrict-prototypes -Wvla`、`WF_SANITIZE=ON` | 本地写代码、跑测试 |
| CI | 开发的一组，再加 `WF_WERROR=ON`、`-fanalyzer`、clang-tidy | 每次推送自动检查 |
| 发布 | 只保留基本警告，或完全不打开警告 | 交给用户构建 |

每个构建一个目录：`build/`、`build-asan/`、`build-ci/`，互不干扰（[第 9 章](/教程/正文/开发与工程基础/9_CMake与XMake)讲过一份配置一个构建目录）。Sanitizer 构建不要和发布构建混用，带检查的二进制运行慢、体积大，只能用来查错。

::: details `_FORTIFY_SOURCE`：另一层编译期与运行期之间的检查

glibc 提供一层轻量的检查：定义了 `_FORTIFY_SOURCE` 并打开优化时，`memcpy`、`strcpy`、`sprintf` 等函数会换成带长度检查的版本，固定的栈缓冲区被写穿时直接报告。它不是 Sanitizer，开销几乎为零，很多发行版在发布构建里默认打开。

```c
#include <stdio.h>
#include <string.h>

int main(int argc, char *argv[]) {
    char buf[8];
    if (argc > 1) {
        strcpy(buf, argv[1]);
        printf("%s\n", buf);
    }
    return 0;
}
```

同样的程序在 `-O2 -D_FORTIFY_SOURCE=2` 下用一个 22 字节的参数运行，输出是 `*** buffer overflow detected ***: terminated`，退出状态 134；不加这个宏时是段错误，退出状态 139。差别在于前者在写坏栈之前就发现并终止了进程。

它只检查编译时能确定大小的对象和少数函数，覆盖范围远小于 ASan，也不能替代 ASan。适合放进发布构建，作为一种低成本的兜底。

:::

用 sanitizer 把一个「测试全绿但实际越界」的缺陷抓出来。缺陷文件是 `bugs/counter_dup_off_by_one.c`：

1. 把它换进 `wordfreq/src/counter.c`，用普通构建跑 `ctest`，记录结果；再用 `-DWF_SANITIZE=ON -DCMAKE_BUILD_TYPE=Debug` 配一个 `build-asan`，跑 `./build-asan/test_counter`，把 ASan 报告的三个部分（错误类型与地址、越界处的调用栈、分配的调用栈）分别摘出一行；
2. 从报告里的 `0 bytes after N-byte region` 推出分配的字节数与写入的字节数，指出 `dup_string` 里哪一行少算了一个字节；
3. 修复后重跑两个构建，确认普通构建与 Sanitizer 构建都通过；
4. 把修复前的 `dup_string` 改成 `malloc(len + 1)` 但 `memcpy` 仍写 `len + 1`，再用 ASan 跑一次，说明为什么这一次不报——问题出在「哪一块内存被越界」上，而不是字节数算错。

写一个 `ub_report.c`，把未定义行为与「实现定义但合法」的行为放在一起对照：

1. 四段操作各做成一个单独的分支，用命令行参数选择要跑哪一段：有符号整数溢出（`INT_MAX + argc`）、移位位数等于类型宽度（`1u << (argc + 31)`）、无符号整数回绕（`UINT_MAX + argc`）、除数为零（`100 / (argc - 2)`）。分支用 `if`/`else` 分开，不要写成同一个表达式里连着算——前一段一旦停下，后面的就执行不到；
2. 在 Linux 上用 `-fsanitize=undefined` 编译运行，逐个分支记录哪几段报 `runtime error`、报完之后程序是否继续、退出状态是多少；
3. 加上 `-fno-sanitize-recover=all` 再跑一次，比较退出状态；再把同一份源码用 `-fsanitize=undefined -fsanitize-trap=all` 编译（MinGW 上只能用这种方式），记录进程被什么信号终止、退出状态是什么；
4. 结论回答两个问题：为什么无符号回绕不报、有符号溢出报；为什么默认的 UBSan 不适合直接放进测试流程。

(1) _[3.3]_ 开发构建：`-Wall -Wextra -Wshadow -Wformat=2 -Wmissing-prototypes -Wstrict-prototypes -Wvla`，加 `WF_SANITIZE=ON`，跑 `ctest`。记录配置命令、构建命令与测试结果。

(2) _[3.3]_ CI 构建：开发构建的一组加 `WF_WERROR=ON` 与 `-fanalyzer`，在另一个构建目录 `build-ci` 里配置与构建。记录 `-fanalyzer` 让整个构建慢了多少（用 `time` 或 PowerShell 的 `Measure-Command` 对比两个目录的构建时间）。

(3) _[4.4]_ 错误注入：把 `bugs/counter_dup_off_by_one.c` 换进 `src/counter.c`，用 `build-asan` 跑 `ctest`，要求脚本正确识别「哪一个测试失败、失败原因是什么」，并把 ASan 报告的 `SUMMARY` 行提取出来；然后恢复原文件。
