# 12. 调试器

给 wordfreq 加上「按最长单词对齐」的输出之后，`wordfreq -n 10 tests/data/sample.txt` 只回了一行 `Segmentation fault`，连哪个文件出错都没说。这次改动只碰了 `src/report.c` 的打印循环和 `app/main.c` 的一行调用，可光看这两处很难找出问题：report 的循环写得没有毛病，main 里的数值也是对的。

过去的办法是在可疑的地方加 `printf`，编译一遍，跑一遍，再删掉。程序小的时候可行，程序一大，每加一条打印就要重新编译、重新复现，遇到只在特定输入下崩溃的缺陷，几轮下来就不知道打印该加在哪了。调试器 (debugger) 让程序停在任何一行，不用改一个字符就能看到此刻的每个对象、每层调用和内存内容。

本章用 GDB 在 wordfreq 的崩溃版本上走一遍完整的定位过程，再依次讲断点与单步、条件断点与观察点、内存与寄存器、调试失败的测试，最后说明优化级别对调试的影响，以及图形前端和 LLDB 里的对应做法。示例在 Windows 上录制，命令本身在 Linux 和 macOS 上一样。

## 1. 准备

调试器读的是可执行文件里的调试信息，编译时要加 `-g`；优化关掉，`-O0` 或 `-Og`。[第 3 章](/教程/正文/开发与工程基础/3_从源文件到可执行文件)已经讲过 `-g` 的作用，这里只强调一点：没有 `-g` 时 GDB 仍然能运行程序、设置断点，但打印对象、列出源码、显示行号全部失效，剩下的只是一个汇编级别的调试器。

::: terminal title="bash - 确认 GDB 版本"

```console
$ gdb --version | head -1
GNU gdb (GDB for MinGW-W64 x86_64, built by Brecht Sanders, r8) 14.2
```

:::

GCC 的默认发行包通常不带 GDB，MinGW-w64 的发行版大多自带；Debian 上装 `gdb` 包，macOS 自带 LLDB，GDB 要另外安装。本章的会话来自 Windows 11 上的 MinGW-w64 GDB 14.2 与 GCC 13.2，被调试的程序是本章注入缺陷的 wordfreq。

带参数启动程序有两种写法。`gdb ./prog` 进入 GDB 再用 `run 参数` 传参，或者一步到位：

```sh
gdb --args ./build/wordfreq -n 10 tests/data/sample.txt
```

`--args` 之后的所有内容都原样传给被调试的程序，`-n 10` 不会被 GDB 当作自己的选项。进入 GDB 后，`show args` 可以核对记下的参数，`run` 启动，`quit` 退出。启动一个正常的程序是这样：

::: terminal title="bash - gdb wordfreq"

```console

(gdb) show args

(gdb) run

[New Thread 10504.0x1dc4]
      4 the
      2 on
      2 sat
[Thread 10504.0x1dc4 exited with code 0]
[Inferior 1 (process 10504) exited normally]
```

:::

会话在一个不含中文的目录里录制，下文统一写成 `C:\proj`；读者换成自己的项目目录即可。Windows 控制台按本地代码页显示中文路径时可能出现乱码，这也是录制时避开中文路径的原因。

Windows 上多出来的 `[New Thread …]` 是 GDB 报告进程里新建的线程，Linux 上不显示；Linux 的启动行是 `Starting program: /path/to/wordfreq -n 3 ...`。`inferior` 是 GDB 对被调试进程的称呼。

调试器与打印的关系值得说清楚。Kernighan 与 Pike 在《**_The Practice of Programming_**》第 5 章写过一句常被引用的话：最有效的调试工具仍然是仔细的思考，辅以审慎放置的打印语句。这句话不是贬低调试器，而是提醒两者的位置。读代码能想清楚的问题不必开调试器；一旦要在几十次循环里找出某一次的状态，或者在多层调用之间追踪一个指针的来历，调试器省下的时间远超过学它的成本。

## 2. 定位崩溃

本章的崩溃版本在 `code/开发与工程基础/12_调试器/bugs/` 下。两个缺陷各由一两个替换文件构成，把文件换进项目、重新编译就能复现，换回原文件即恢复。为了和正常版本对照，本章的会话在项目的几份副本里进行：`wordfreq` 是正常版本，`wordfreq-crash` 换入了崩溃的两个文件，`wordfreq-prefix` 换入了第 4 节的前缀缺陷，`wordfreq-test` 换入了第 11 章的注入缺陷，用来演示调试失败的测试。读者可以只保留一份项目，按节换文件、重新编译。

崩溃版本里，`src/report.c` 的 `wf_report_print` 换成了按最长单词对齐的写法：

```c
void wf_report_print(FILE *out, const wf_entry *entries, size_t n) {
    size_t width = 0;
    for (size_t i = 0; i < n; i++) {
        size_t len = 0;
        for (const char *p = entries[i].word; *p != '\0'; p++) {
            len++;
        }
        if (len > width) {
            width = len;
        }
    }

    for (size_t i = 0; i < n; i++) {
        fprintf(out, "%7zu %-*s\n", entries[i].count, (int)width,
                entries[i].word);
    }
}
```

程序收到 `SIGSEGV` 信号停了下来，GDB 自动显示停在哪个函数、哪一行，并给出当前这一行的源码。Linux 上第一行显示为 `Program received signal SIGSEGV, Segmentation fault.`，后面的结构相同。

`bt`（backtrace，回溯）列出调用栈 (call stack)：`#0` 是当前执行的函数，`#1` 是它的调用者，`#2` 再往上一层，一直到 `main`。每一行包含帧号、地址、函数名和实参、源文件与行号。从 `#0` 就能看出崩溃发生在 `wf_report_print` 求某个单词长度的循环里。

`frame` 切换当前帧，`up`、`down` 在相邻帧之间移动。切到 `#1` 之后，`print` 的是 `print_top` 里的对象：

::: terminal title="bash - 切到调用者查看对象"

```console
(gdb) frame 1

status = 0

(gdb) print n

(gdb) up
#2  0x00007ff701be24a3 in main (argc=4, argv=0x7bb9b0) at app/main.c:151
151	        status = print_top(counter, n);
(gdb) print n

(gdb) down
#1  0x00007ff701be232f in print_top (counter=0x7c1ed0, n=10) at app/main.c:120
```

:::

`info locals` 一次列出当前帧的局部对象。`written` 是 `wf_counter_top` 实际写入的项数，7；`n` 是调用方要求的 10。两个数不同，而下一行传给 `wf_report_print` 的是 `n`。回到 `#0`，看那个越界的条目：

::: terminal title="bash - 查看越界的条目"

```console
(gdb) frame 0
#0  0x00007ff701be1c7a in wf_report_print (out=0x7ffc519c8c98,
    entries=0x7c4c70, n=10) at src/report.c:12
12	        for (const char *p = entries[i].word; *p != '\0'; p++) {
(gdb) print i
$4 = 7
(gdb) print entries[i]
$5 = {word = 0x0, count = 0}
```

:::

`i` 正好是 7，即第一个没有写入的条目；它的 `word` 是空指针，`count` 是 0。`calloc` 把分配的内存全部清零，`wf_counter_top` 只写了前 7 项，第 8 项保持全零。对齐循环不看 `count` 是不是 0，直接把 `word` 交给内层循环解引用，空指针一读就崩。

根因在调用方：传给 `wf_report_print` 的应该是 `written`，不是 `n`。改完后重编，`-n 10` 输出 7 行，与 `-n 7` 的结果相同，状态 0。

::: concept dev-debug-call-stack title="调用栈的每一帧对应一次尚未返回的调用"

每次函数调用，运行环境都在栈上为它建立一帧 (frame)，保存返回地址、参数、局部对象和保存的寄存器。函数返回时帧被弹出。调试器遍历这条帧链得到回溯，`frame N` 切换到第 N 帧，此后 `print`、`info locals` 作用于该帧的对象。崩溃时最内层的帧是出错处，外层帧保存着导致这次调用的输入。

:::

崩溃定位到这里就够了。真实工程中，SIGSEGV 的原因远不止传错一个数：野指针、越界写、栈溢出都会以同一行 `Segmentation fault` 结束。回溯能告诉你是哪个函数、哪一行，再往下的判断仍然要靠读代码和实验。

## 3. 断点与单步

崩溃只在程序的最后一步发生，更多的时候程序能跑完，只是结果不对。这时要让程序停在中间，观察它一步步做了什么。

`break` 在指定位置设断点 (breakpoint)。位置可以写成 `文件:行`，也可以只写函数名：

```sh
break src/counter.c:85
break wf_counter_add
```

函数名形式在所有同名符号上都设，`文件:行` 更精确。带 `static` 的函数一样能用，GDB 读的是调试信息里的符号。

::: terminal title="bash - 在 wf_counter_add 上设断点"

```console
$ gdb --args ./build/wordfreq -n 3 tests/data/sample.txt
Reading symbols from ./build/wordfreq...
(gdb) break wf_counter_add
Breakpoint 1 at 0x14000191c: file src/counter.c, line 85.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 16404.0x64c0]

Thread 1 hit Breakpoint 1, wf_counter_add (c=0x7f1e10, word=0x5ffd70 "the")
    at src/counter.c:85
85	    struct item *e = find_entry(c, word);
(gdb) print c->size
$1 = 0
```

:::

断点把执行停在函数的第一条语句上。`c->size` 为 0 是因为这是第一个单词，`find_entry` 还没被调用。`next` 执行当前行，遇到函数调用时整个越过；`step` 则进入被调用的函数：

几个单步命令的区别值得一次分清：

| 命令 | 作用 |
| --- | --- |
| `next`（缩写 `n`） | 执行一行，函数调用整体越过 |
| `step`（缩写 `s`） | 执行一行，进入被调用的函数 |
| `finish` | 运行到当前函数返回，并打印返回值 |
| `continue`（缩写 `c`） | 继续运行到下一个断点或程序结束 |
| `until 行号` | 运行到当前函数的指定行，常用于跳过循环 |
| `nexti`、`stepi` | 按机器指令执行，源码行与指令不对应时使用 |

`next` 和 `step` 的区别只在当前行含函数调用时才有意义。上例 `next` 越过 `dup_string`，`step` 进入它的第一行；`finish` 从 `dup_string` 里出来，GDB 顺带打印返回值 `0x7f2710 "the"`，这比在函数里加一条打印再删掉方便得多。

::: concept dev-debug-next-vs-step title="next 越过调用，step 进入调用"

`next` 和 `step` 都执行一条源码语句。当前语句包含函数调用时，`next` 把整个调用当作一步执行完，停在下一条语句；`step` 进入被调函数的内部，停在该函数的第一条语句。调试自己的代码用 `step` 追进去，调试库函数或已经确认无误的模块用 `next` 跳过。

:::

## 4. 条件断点与观察点

第二个缺陷更隐蔽。`src/counter.c` 的 `find_entry` 换成了前缀比较。编译方式和上一节相同，只换这一个文件：

```c
static struct item *find_entry(const wf_counter *c, const char *word) {
    for (size_t i = 0; i < c->size; i++) {
        struct item *e = &c->items[i];
        if (strncmp(word, e->word, strlen(word)) == 0) {
            return e;
        }
    }
    return NULL;
}
```

`strncmp` 只比较 `strlen(word)` 个字节，短单词是长单词的前缀时被当成同一个。在 `wordfreq-prefix` 副本里换上这个文件，输入 `then the then the the`：正确结果是 `the` 3 次、`then` 2 次，缺陷版本把 5 次都记到 `then` 上：

::: terminal title="zsh - 前缀匹配缺陷"

```console
$ cp bugs/counter_prefix_match.c src/counter.c
$ gcc -std=c17 -Wall -Wextra -g -O0 -D__USE_MINGW_ANSI_STDIO=1 \
    -Iinclude src/*.c app/main.c -o build/wordfreq
$ printf 'then the then the the\n' > input.txt
$ ./build/wordfreq -n 5 input.txt
      5 then
```

:::

没有崩溃，也没有报错，只有统计结果偏了。这类缺陷靠打印很难找：程序在几百个单词里来回比较，你不知道哪一次比较出了错。

`break 位置 if 条件` 设条件断点 (conditional breakpoint)：只有条件为真时才停下。想知道「the 进来时，`find_entry` 比较到了什么」，可以只在 `word` 是 `the` 时停：

::: terminal title="bash - 条件断点"

```console
(gdb) break find_entry if (int)strcmp(word, "the") == 0
Breakpoint 1 at 0x14000173c: file src/counter.c, line 34.
(gdb) run
Starting program: C:\proj\wordfreq-prefix\build\wordfreq.exe -n 5 input.txt
[New Thread 18904.0x6650]

Thread 1 hit Breakpoint 1, find_entry (c=0x731e80, word=0x5ffd70 "the")
    at src/counter.c:34
34	    for (size_t i = 0; i < c->size; i++) {
(gdb) next
35	        struct item *e = &c->items[i];
(gdb) next
36	        if (strncmp(word, e->word, strlen(word)) == 0) {
(gdb) next
37	            return e;
(gdb) print i
$1 = 0
(gdb) print e->word
$2 = 0x734ac0 "then"
```

:::

断点停在第一次比较之前，`i` 为 0，`e->word` 是 `then`。执行完 `strncmp` 那一行，返回 `e`，`the` 就被记到了 `then` 上。输入里 `the` 一共出现 3 次，条件断点配合 `continue` 可以逐次确认每次都走了同一条路径。

条件里出现 `strcmp` 这样的库函数时，GDB 可能报错 `'strcmp' has unknown return type; cast the call to its declared return type`，这是它不知道 libc 的函数原型。在调用外面套一个强制转换即可：`if (int)strcmp(word, "the") == 0`。

条件断点的条件在每次命中位置时求值，代价比普通断点高：GDB 要让程序停下来执行条件表达式，命中次数多时程序会慢很多。条件简单（比较一个整数、检查一个指针是否为空）时没有明显影响，条件里调用函数、遍历链表时要留意。

::: tip 命中次数太多的条件换一种写法

一个循环跑一百万次、只想在第 1000 次停下时，与其让 GDB 每次都求值一次条件，不如在循环里找一个只在特定时刻经过的位置设普通断点，或者用 `ignore 编号 次数` 让断点跳过头若干次命中。前者不改变程序的执行速度，排查偶发问题更合适。

:::

条件断点解决「在什么位置停」，观察点 (watchpoint) 解决「谁改了这个对象」。`watch 表达式` 在表达式的值发生变化时停下，GDB 打印旧值、新值、修改发生的位置和调用栈。

用观察点找「哪一次调用把次数加错了」，可以先在 `then` 的计数上设点。输入的第一个单词是 `then`，第二个才是 `the`，所以先让断点跳过第一次命中：

`ignore 1 1` 让断点 1 跳过第一次命中，于是程序停在第二个单词 `the` 上，此时 `then` 的计数已经是 1。观察点设在 `c->items[0].count` 上，`continue` 之后，GDB 在计数被改成 2 的那一刻停下；回溯和 `print word` 说明正是 `the` 这一次调用改的。缺陷不言自明。

`watch -l 表达式` 中的 `-l` 表示按地址观察 (location)：先求出表达式所指的内存地址，之后监视这个地址上的值。不带 `-l` 时 GDB 监视的是表达式的值，每次停下来重新求值，经过指针的表达式在指针为空或对象被移动时会失效。上例在 `ignore` 之后、`items[0]` 已经存在时设观察点，两种写法都可以；观察点落在结构体内部成员上时，`watch -l` 更可靠。

含指针解引用的表达式在监视那一刻内存必须有效，否则 GDB 会拒绝设点，提示 `Cannot access memory at address 0x0`。上例里第一次命中 `wf_counter_add` 时 `c->items` 还是空指针，必须先跨过那一次再设。

观察点通常在硬件上实现。x86 和 ARM 都提供少量专用的比较器（观察点寄存器），GDB 用它们实现硬件观察点，上面的会话里就显示为 `Hardware watchpoint`。可用数量由处理器和架构决定，PC 上通常有 4 个，Cortex-M3 的 DWT 也是 4 个。数量不够时 GDB 退化为单步加比较的软件观察点，程序会慢很多。

::: tip 按地址设观察点

表达式里带着多层指针、类型又不好写时，可以把成员地址强转成它的类型再解引用：


:::

## 5. 查看内存与寄存器

`print` 按类型解释内存，有时需要看原始字节。`x`（examine）按指定格式和数量读内存，语法是 `x/数量格式单位 地址`：

## 7. 优化与调试信息

调试信息与优化是两件独立的事。`-g` 生成「机器指令对应哪一行源码、哪个对象在栈上还是寄存器里」的映射；优化会重排指令、把对象放进寄存器、把循环展开、把函数内联、把常量算好。两者叠加时，映射仍然存在，但机器码的行序与源码不再一一对应。

`-O2` 下 `n` 显示 `<optimized out>`：`n` 的两次使用（`calloc` 分配和取前 n 项）都已经过去，此后它的值不再需要，编译器让这份值随寄存器被复用一起消失。`info locals` 把 `entries`、`written`、`status` 各列了两遍，一遍有值一遍是 `<optimized out>`，这是编译器为同一对象在不同位置留下了多份映射，GDB 把能解析的都列出来。`-O0` 下每个对象都老老实实待在栈帧里，值一目了然。

单步也会受影响。`-O2` 下 `next` 可能一次跳过好几行源码，也可能在同一行上反复停；`step` 遇到被内联的函数时，有时能进入「逻辑上的」函数体，有时直接跟着调用者往下走。同一个函数名的断点可能落在多个地址上：

`-Og` 是 GCC 为调试体验设计的优化级别：保留一部分优化，同时尽量让源码行与指令保持对应。在同一个位置停下，`-Og` 的局部对象大多还在，但已经不再使用的参数同样可能被丢掉：

三个级别里，`-O0` 的调试体验最好，`-Og` 次之，`-O2` 下不要指望每个对象都能打印出来。日常开发推荐 `-O0 -g` 或 `-Og -g`。

发布构建用到 `-O2` 时，仍然要保留调试信息。CMake 的 `RelWithDebInfo` 构建类型就是 `-O2 -g`，出问题时用这个构建调试，比拿一个没有符号的发布版本碰运气强。`-g` 只增加文件大小，不影响运行速度。[第 9 章](/教程/正文/开发与工程基础/9_CMake与XMake)的构建类型一节会给出完整的选项表。

如果只改了源文件没重新编译，GDB 会提示 `warning: Source file is more recent than executable.`，行号与停在的代码对不上，`print` 的对象也可能错位。每次改完代码先重新编译，再重新加载。

:::

## 8. 其他前端与 LLDB

命令行不是使用 GDB 的唯一方式。VS Code、CLion、Qt Creator 这些 IDE 都在后台启动 GDB 或 LLDB，把断点、局部对象、调用栈显示成面板。它们的区别只在界面，底下的调试引擎和本章的命令一一对应。

VS Code 的 C/C++ 扩展用 `launch.json` 描述怎么启动调试会话：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "debug wordfreq",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/build/wordfreq",
      "args": ["-n", "10", "tests/data/sample.txt"],
      "cwd": "${workspaceFolder}",
      "MIMode": "gdb",
      "miDebuggerPath": "gdb",
      "setupCommands": [
        { "description": "pretty printing", "text": "set print pretty on" }
      ]
    }
  ]
}
```

`program` 是要调试的可执行文件，`args` 是传给它的参数，`cwd` 是工作目录（相对路径的 `tests/data/sample.txt` 按它解析），`MIMode` 选 `gdb` 还是 `lldb`，`miDebuggerPath` 指定调试器路径。`setupCommands` 在会话启动时执行 GDB 命令，`set print pretty on` 让结构体按成员分行显示，人工检查时更好读。

CLion 不需要手写这个文件：它从 CMake 读目标，在运行配置里改参数，调试按钮直接驱动 GDB 或 LLDB。设置里可以选调试器后端。

LLDB 是 LLVM 自带的调试器，命令名与 GDB 不同，功能一一对应：

| 操作 | GDB | LLDB |
| --- | --- | --- |
| 运行 | `run` | `run` |
| 设断点 | `break 文件:行` | `breakpoint set -f 文件 -l 行` |
| 按函数设断点 | `break 函数名` | `breakpoint set -n 函数名` |
| 条件断点 | `break 位置 if 条件` | `breakpoint set -n 函数 -c 条件` |
| 观察点 | `watch 表达式` | `watchpoint set expression 表达式` |
| 继续 | `continue` | `continue` |
| 下一步 | `next` | `next` |
| 进入函数 | `step` | `step` |
| 执行到返回 | `finish` | `finish` |
| 回溯 | `bt` | `bt` |
| 切换帧 | `frame N` | `frame select N` |
| 打印 | `print 表达式` | `expression 表达式`（`p` 亦可） |
| 局部对象 | `info locals` | `frame variable` |
| 内存 | `x/16xb 地址` | `memory read -f x -c 16 -s 1 地址` |

`frame variable` 一次列出当前帧的全部局部对象，比 GDB 的 `info locals` 更常用；`expression` 能执行任意表达式，包括函数调用。LLDB 也接受 `p` 作为 `expression` 的缩写，所以从 GDB 转过去时，`p`、`bt`、`next`、`step` 这些常用命令基本不用改。

macOS 上 LLDB 是系统自带的选择，GDB 需要另外安装并对二进制签名。Linux 上两者都能用，GDB 的支持面更广，内核和嵌入式的文档多以 GDB 为例。

Linux 上还有一样 Windows 不方便用的东西：核心转储 (core dump)。程序崩溃时内核把进程的内存镜像写成一个文件，用 GDB 打开就能像程序还在运行一样查看现场：

```console
$ ulimit -c unlimited
$ ./build/wordfreq_crash -n 10 tests/data/sample.txt
Segmentation fault (core dumped)
$ gdb ./build/wordfreq_crash core
(gdb) bt
```

`ulimit -c unlimited` 让当前 shell 不限制核心转储大小，默认值通常是 0，也就是不生成。转储文件的位置与文件名由 `/proc/sys/kernel/core_pattern` 决定，许多发行版把它交给 systemd 或 apport 管理，文件在 `/var/lib/systemd/coredump/` 或 `/var/crash/` 下。上面的输出与位置取自 GDB 手册和发行版文档的常规形式，本章没有在 Linux 上实测。Windows 上的对应物是崩溃转储（`.dmp`），生成的思路见 [Win32 的结构化异常处理](/教程/正文/系统编程/拓展A_Win32系统编程/A_5_错误处理与结构化异常处理)。

::: tip 用 -batch 把会话记录下来

调试过程本身也值得留档。`gdb -batch -ex 命令` 执行完自动退出，适合写进脚本或生成可重复的示例：

```console
$ gdb -q -batch -ex "break wf_counter_add" -ex "run" \
    -ex "print word" -ex "bt 2" --args ./build/wordfreq -n 3 tests/data/sample.txt
Breakpoint 1 at 0x14000191c: file src/counter.c, line 85.
[New Thread 20456.0x18f4]

Thread 1 hit Breakpoint 1, wf_counter_add (c=0x101e10, word=0x5ffd70 "the") at src/counter.c:85
85	    struct item *e = find_entry(c, word);
$1 = 0x5ffd70 "the"
#0  wf_counter_add (c=0x101e10, word=0x5ffd70 "the") at src/counter.c:85
#1  0x00007ff65ef5212b in count_stream (counter=0x101e10, in=0xfbda0, name=0xfbd50 "tests/data/sample.txt") at app/main.c:95
```

`-x 文件` 从文件读取命令序列，适合固定流程的排查。两个选项都不需要交互，可以放进缺陷报告或提交信息。

:::

1. 三个优化级别各编一份，在每个函数的入口、中部、返回前各设一个断点，记录每个断点上能成功 `print` 出的对象数；
2. `find_entry` 在 `-O2` 下被内联到两个调用点，`info breakpoints` 显示 `(2 locations)`，命中的编号是 `1.1`、`1.2`。把 `-O2` 下 `break find_entry` 的完整输出与 `-O0` 下的对比，说明多出来的那一处是哪里；
3. 用 `info line app/main.c:126` 与 `info line app/main.c:121` 比较三个级别下同一行源码对应的指令范围（输出形如 `starts at 0x… <print_top+119> and ends at 0x… <print_top+155>`），把三条指令范围的起点、终点与跨过的字节数抄成一张表。两个方向都要解释：`-O0` 下为什么一行能占几十个字节，`-O2` 下为什么有些行只剩几条指令、另一些行又把多个语句合在一起；
4. 写一份推荐表：什么场合用 `-O0 -g`、什么场合用 `-Og -g`、什么场合用 `-O2 -g`（后者对应 CMake 的 `RelWithDebInfo`），每一条给出理由与代价。

结论里要出现真实测量数字，不接受「大概是」这类描述。

</Exercise>
