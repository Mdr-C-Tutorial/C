# 12. 调试器

在为 wordfreq 扩充“按最长单词宽度对齐”的报表格式化功能后，在终端执行 `wordfreq -n 10 tests/data/sample.txt`，程序却突兀地中断，仅留下一行简短的 `Segmentation fault`，甚至未曾说明出错源文件与行号。这次功能迭代所涉及的改动范围极其有限，仅仅触及了 `src/report.c` 中的排版循环以及 `app/main.c` 中的一处接口调用。单纯依靠静态肉眼审阅这两处修改，往往极难察觉症结所在：排版循环在逻辑结构上挑不出破绽，主函数中传递的参数也符合常理。

在以往传统的排查手法中，开发者通常会在心存疑虑的代码段穿插几条 `printf`，重新编译、再次复现、查阅日志，确认后再将调试代码逐一抹去。这种“打印式调试”在数十行的小脚本中尚能应付，但随着工程规模逐步膨胀，每次插入打印都需要重走编译与链接流程；若遇到仅在特定稀有输入或深层调用链下才会偶发崩溃的缺陷，反复埋点不仅耗时费力，更会破坏原本的代码节奏。调试器（Debugger）则提供了截然不同的交互范式：它能够在不改动源码分毫的前提下，让正在执行的程序精确暂停在任意指定的机器指令或源码行上，赋予开发者随时检视当前作用域内的内存对象、回溯多层调用栈帧以及透视底层内存字节排布的完全控制权。

本章将以 GDB 为核心工具，在注入了实际缺陷的 wordfreq 崩溃版本上完整演示故障现场的诊断与逆向定位路径；随后系统梳理断点控制、单步执行、条件断点以及硬件观察点的工程用法；进而深入底层探讨内存字节与 CPU 寄存器的巡检技巧；在此基础上，还将演示如何借助调试器攻克上一章自动化测试抛出的未通过断言，并剖析编译器优化级别对调试体验带来的实际影响。

## 1. 准备与基本交互

调试器能够将底层的机器码地址逆向映射回人类可读的源码行号与符号名称，完全依赖于二进制产物中附带的调试信息（Debug Information）。因此，在使用 GCC 编译源代码时，必须显式附加 `-g` 编译选项；同时，应当显式关闭编译器优化，采用 `-O0` 或专为调试设计的 `-Og`。

[第 3 章](/教程/正文/开发与工程基础/3_从源文件到可执行文件)曾详细解析过 `-g` 生成 DWARF 调试节区的内部机制。若编译时遗漏了 `-g`，GDB 依然能够拉起进程并停留在底层地址断点上，但此时读取对象值、展示源码上下文、解析结构体定义以及映射精准行号的功能将全线瘫痪，调试器将被迫退化为纯汇编指令级别的单步跟踪器。

::: terminal title="bash - 确认 GDB 版本"

```console
$ gdb --version | head -1
GNU gdb (GDB for MinGW-W64 x86_64, built by Brecht Sanders, r8) 14.2
```

:::

主流 Linux 发行版通常可通过包管理器直接安装 `gdb`，MinGW-w64 工具链大多开箱自带，macOS 平台则原生搭载 LLDB（后文第 8 节将提供完整的对应命令表）。本章的实操会话录制于搭载 MinGW-w64 GDB 14.2 与 GCC 13.2 的环境，被调试的目标即为注入了经典缺陷的 wordfreq 二进制程序。

在命令行使用 GDB 拉起带有运行参数的可执行文件时，有两种常见的启动方式。一种是先执行 `gdb ./prog` 进入 GDB 提示符界面，随后在内部通过 `run 参数1 参数2` 注入参数；另一种更为高效的方式是使用 `--args` 选项一步到位：

```sh
gdb --args ./build/wordfreq -n 10 tests/data/sample.txt
```

在 `--args` 之后出现的所有字符串都会被完整透传给被调试程序，诸如 `-n 10` 这样的标记绝不会被 GDB 错误解析为其自身的命令行选项。进入 GDB 交互式 Shell 后，通过 `show args` 可以核实已捕获的入参清单，输入 `run`（可简写为 `r`）即可启动被测程序，调试完毕后输入 `quit`（简写为 `q`）安全退出。启动一个行为完全正常的程序，其交互过程如下：

```console

(gdb) show args

(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 10504.0x1dc4]
      4 the

[Thread 10504.0x1dc4 exited with code 0]
[Inferior 1 (process 10504) exited normally]
```

:::

本章的会话统一在纯英文路径 `C:\proj` 下展开录制，以防 Windows 终端在特定代码页下转义中文路径时产生乱码。在输出信息中，Windows 平台所出现的 `[New Thread …]` 是 GDB 捕获系统底层线程创建的通知；而 `inferior` 则是 GDB 体系中对正在被跟踪的被调试目标进程的通用技术称谓。

在此处理清调试器与打印语句的工程定位极有必要。Brian Kernighan 与 Rob Pike 在软件工程经典《**_The Practice of Programming_**》中写道：最有效的调试工具始终是周密的理性思考，辅以审慎放置的打印诊断。静态审阅能够一眼看透的逻辑问题，不必大费周章拉起调试器；但当需要在上千次循环迭代中捕获某一次边界异动，或是需要沿着曲折的多层调用栈追踪一个动态指针的生命周期时，熟练运用调试器所节省的排查时间将远远超越其学习成本。

## 2. 定位崩溃

本章所涉及的两组缺陷实现统一存放在 `code/开发与工程基础/12_调试器/bugs/` 目录下。每个缺陷都以模块化的替换源文件呈现，将其复制覆盖进项目并重新编译即可稳定重现，还原原文件即可恢复如初。为了与干净的工程基线形成鲜明对照，本章在不同测试目录间分步推进。

::: terminal title="zsh - 构建崩溃版本"

```console
$ cp bugs/report_alignment.c src/report.c
$ cp bugs/main_passes_n.c app/main.c
$ gcc -std=c17 -Wall -Wextra -g -O0 -D__USE_MINGW_ANSI_STDIO=1 \
    -Iinclude src/*.c app/main.c -o build/wordfreq_crash
$ ./build/wordfreq_crash -n 10 tests/data/sample.txt
Segmentation fault
```

:::

在这个崩溃版本中，`src/report.c` 中的 `wf_report_print` 被改写为先扫描全量条目获取最大单词字符宽度、再统一定宽对齐输出的实现：

```c
void wf_report_print(FILE *out, const wf_entry *entries, size_t n) {
    size_t width = 0;
    for (size_t i = 0; i < n; i++) {
        size_t len = 0;
        for (const char *p = entries[i].word; *p != '\0'; p++) {
            len++;
        }
        if (len > width) {
            width = len;
        }
    }

    for (size_t i = 0; i < n; i++) {
        fprintf(out, "%7zu %-*s\n", entries[i].count, (int)width,
                entries[i].word);
    }
}
```

而在主调用方 `app/main.c` 的 `print_top` 函数中，调用处传递的条目数直接选用了用户在命令行中请求的数字 `n`：

::: compare left-title="缺陷：传请求的项数" right-title="正确：传实际写入的项数"

```c
    size_t written = wf_counter_top(counter, entries, n);
    int status = 0;
    if (written == 0 && wf_counter_size(counter) > 0) {
        status = out_of_memory();
    } else {
        wf_report_print(stdout, entries, n);
    }
```

---

```c
    size_t written = wf_counter_top(counter, entries, n);
    int status = 0;
    if (written == 0 && wf_counter_size(counter) > 0) {
        status = out_of_memory();
    } else {
        wf_report_print(stdout, entries, written);
    }
```

:::

在示例文件 `sample.txt` 中，全文实际上总共仅有 7 个不同的英文单词。当命令行指定 `-n 10` 时，动态分配的条目数组中只有前 7 个条目被 `wf_counter_top` 赋予了合法的词频数据，后 3 个条目依然保持着 `calloc` 分配时的全零状态。此时对齐循环盲目遍历前 10 项，在第 8 项首次解引用空指针时，操作系统便立即拦截非法内存访问并触发段错误。实测在 `-n 7` 时程序运行平稳，而一旦输入 `-n 8` 及以上便瞬间崩溃。

面对这处突发崩溃，我们无须靠猜测去反推，直接让 GDB 接管运行并捕获异常现场：

::: terminal title="bash - gdb 崩溃版本"

```console

    n=10) at src/report.c:12

(gdb) bt

    entries=0x7c4c70, n=10) at src/report.c:12
#1  0x00007ff701be232f in print_top (counter=0x7c1ed0, n=10) at app/main.c:120
```

在发生非法的内存解引用时，操作系统会向进程发送 `SIGSEGV` 信号，并将控制权交还给挂载在此进程上的调试器。GDB 能够立即捕获该信号并暂停程序，控制台清晰展示了崩溃发生的函数名、当前入参、源码相对路径与行号（Linux 平台通常显示为 `Program received signal SIGSEGV, Segmentation fault.`，输出结构完全一致）。

命令 `bt`（即 backtrace，回溯）用于展开当前线程完整的调用栈（Call Stack）：栈帧编号 `#0` 代表发生崩溃的最内层函数，`#1` 代表它的直接调用者，`#2` 则再向外追溯一层，直至程序的最初入口 `main`。每一层栈帧都忠实呈现了帧编号、运行时指令指针地址、函数名称与当前实参、以及对应的源文件与行号。单从 `#0` 的信息即可判定，程序是在 `wf_report_print` 内部计算单词长度的循环中发生了异常解引用。

通过 `frame 帧号` 可以自如切换当前的观测上下文，`up` 与 `down` 则支持在相邻层级的调用帧之间逐层移动。我们将视角切换至外层调用帧 `#1`，此时使用 `print` 指令即可检视上层函数 `print_top` 内部的局部对象：

::: terminal title="bash - 切到调用者查看对象"

```console

(gdb) print n

(gdb) up
```

:::

指令 `info locals` 能够一次性列出当前活动帧中声明的所有局部对象。仔细比对输出可以发现关键出入：`written` 是由底层哈希表提取函数 `wf_counter_top` 实际填充并返回的有效词项数量，其值为 7；而 `n` 则是用户从外部命令行传来的期望排行榜长度 10。两个数值并不一致，但在第 120 行的代码中，传给打印函数 `wf_report_print` 的第三个参数却是请求数量 `n`。重新切换回 `#0` 帧，直接审阅那个越界的条目内容：

::: terminal title="bash - 查看越界的条目"

```console
(gdb) frame 0
#0  0x00007ff701be1c7a in wf_report_print (out=0x7ffc519c8c98,
    entries=0x7c4c70, n=10) at src/report.c:12
12	        for (const char *p = entries[i].word; *p != '\0'; p++) {
(gdb) print i
$4 = 7
(gdb) print entries[i]
$5 = {word = 0x0, count = 0}
```

:::

当前索引 `i` 恰好是 7，即数组中第 8 个（自 0 起算）未经填写的条目。该条目内部的 `word` 成员是一个空指针 `0x0`，频次计数值也为 0。`calloc` 在分配内存时将全部分配块清零，而 `wf_counter_top` 仅覆写了前 7 项，后 3 项保留为全零。打印模块的对齐循环在设计时未对 `count` 或 `word` 做空指针守卫，直接把未初始化的 `word` 传给内层循环执行 `*p != '\0'` 的字符求值，解引用空指针瞬间引爆了段错误。

故障根因因此昭然若揭：主调用方传递给报表模块的数组长度，应当是实际写入项数 `written`，而非外部盲目传入的上限 `n`。修正这一调用参数后重新编译运行，`-n 10` 能够稳定输出全部 7 行统计，进程以标准退出码 0 顺利结案。

::: concept dev-debug-call-stack title="调用栈的每一帧对应一次尚未返回的调用"

在程序运行期间，每次进入新的函数调用，操作系统与调用约定都会在调用栈上开辟出一块独立的栈帧（Stack Frame），用于保存调用返回地址、输入实参、函数内部的局部对象以及被调用者保护寄存器。当函数执行完毕返回时，该栈帧随即被出栈销毁。调试器通过逆向遍历栈帧链表重构出回溯视图。使用 `frame N` 可以自由跃迁至指定的调用上下文，后续的 `print` 与 `info locals` 操作也会严格绑定在所选栈帧的作用域内。在程序发生崩溃时，最内层的 `#0` 帧即为事发现场，而外层栈帧则完好封存了引发该次调用的业务输入。

:::

至此，崩溃定位已完整闭环。在真实的工业级 C 语言工程中，引发 `SIGSEGV` 的源头千差万别：野指针悬空、堆内存越界写入、栈缓冲区溢出等故障最终往往都表现为同一种崩溃信号。调用栈回溯能够迅速剥除表面迷雾，直接指出事发点代码行；而深层次的成因推演，依然需要依靠清晰的架构理解与严谨的代码逻辑梳理。

## 3. 断点与单步

崩溃通常发生在程序跑飞的最极端边缘；而在绝大多数日常开发中，程序往往能够“正常”跑完，只是最终输出的业务数据完全偏离了预期。此时盲目等待崩溃毫无意义，我们必须让程序在关键阶段受控停驻，动态巡视其状态变迁。

指令 `break`（简写为 `b`）用于在指定的代码锚点设置断点（Breakpoint）。锚点位置既可以指定为精准的 `文件名:行号`，也可以直接指定为函数符号名：

```sh
break src/counter.c:85
break wf_counter_add
```

以函数名形式设置断点时，若工程中存在多处同名符号，GDB 会在所有匹配符号上均挂接断点；而 `文件名:行号` 的形式则更为严谨。即使是带有 `static` 修饰的内部函数，只要编译时附带了调试符号，GDB 均可直接解析并下断。

::: terminal title="bash - 在 wf_counter_add 上设断点"

```console
$ gdb --args ./build/wordfreq -n 3 tests/data/sample.txt
Reading symbols from ./build/wordfreq...
(gdb) break wf_counter_add
Breakpoint 1 at 0x14000191c: file src/counter.c, line 85.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 16404.0x64c0]

Thread 1 hit Breakpoint 1, wf_counter_add (c=0x7f1e10, word=0x5ffd70 "the")
    at src/counter.c:85
85	    struct item *e = find_entry(c, word);
(gdb) print c->size
$1 = 0
```

:::

断点成功截获了进程的执行流，并在函数体的第一条有效语句执行前停驻。此时 `c->size` 尚且为 0，因为这是分词流水线送来的首个词条 `the`，内部的查找函数 `find_entry` 尚未被正式调用。

在断点暂停后，常用的单步执行指令分为两类：`next` 会单步执行当前代码行，若当前行包含函数调用，它会等待被调函数完整执行完毕，停在当前函数的下一行；而 `step` 则会直接步入被调函数内部的第一条有效语句：

::: terminal title="bash - next、step 与 finish"

```console
(gdb) next
86	    if (e != NULL) {
(gdb) next
91	    if (reserve_one(c) != 0) {
(gdb) print e
$2 = (struct item *) 0x0
(gdb) next
94	    char *copy = dup_string(word);
(gdb) step

(gdb) bt 2
#0  dup_string (s=0x5ffd70 "the") at src/counter.c:25
#1  0x00007ff65ef51978 in wf_counter_add (c=0x7f1e10, word=0x5ffd70 "the")
    at src/counter.c:94
(More stack frames follow...)
(gdb) finish
Run till exit from #0  dup_string (s=0x5ffd70 "the") at src/counter.c:25
0x00007ff65ef51978 in wf_counter_add (c=0x7f1e10, word=0x5ffd70 "the")
    at src/counter.c:94
94	    char *copy = dup_string(word);
Value returned is $3 = 0x7f2710 "the"

(gdb) info locals
e = 0x0

```

:::

常用控制执行流的单步指令语义如下：

| 命令 | 作用 |
| --- | --- |
| `next`（缩写 `n`） | 单步执行当前行，若遇函数调用则将其作为一个整体跨过 |
| `step`（缩写 `s`） | 单步执行当前行，若遇函数调用则步入被调函数内部 |
| `finish` | 持续执行，直至当前函数调用返回，并在终端打印该函数的返回值 |
| `continue`（缩写 `c`） | 恢复全速运行，直至命中下一个断点或整个进程执行完毕 |
| `until 行号` | 持续执行直到抵达当前函数内的指定行号，常用于跳出冗长循环 |
| `nexti`、`stepi` | 以单条机器汇编指令为步长执行，在缺乏源码或排查编译器优化时极为实用 |

在实际操作中，`next` 与 `step` 的语义分野只在当前行存在函数调用时才会体现。在上述会话中，我们在第 94 行使用 `step` 步入了内部的字符串复制辅助函数 `dup_string`；在确认其逻辑无碍后，输入 `finish` 指令即可让程序跑完该辅助函数并返回上一层，GDB 还会主动捕获并打印函数返回的指针地址 `$3 = 0x7f2710 "the"`。这比手动增加临时打印去观测返回值要优雅且高效得多。

::: concept dev-debug-next-vs-step title="next 越过调用，step 进入调用"

`next` 与 `step` 都以高级语言的源码语句为步长推进行程。当执行行包含函数调用时，`next` 将整个函数调用视作一个不可分割的单步，待其内部全部跑完后停在紧随其后的下一条语句；而 `step` 则会主动钻入被调函数的实现中，停留在该函数内部的第一条语句。在工程排查中，面对自己正在调试的核心业务代码通常使用 `step` 步入追踪，而面对成熟稳定的标准库函数（如 `strlen`、`memcpy`）或经充分验证的基础组件时，则应当使用 `next` 干净利落地越过。

:::

## 4. 条件断点与观察点

相比于显而易见的崩溃，逻辑层面的静默偏差往往更为棘手。我们在第二组缺陷中模拟了一种更为隐蔽的逻辑缺陷：`src/counter.c` 中的内部查找函数 `find_entry` 被错误地换成了前缀比对实现。编译配置保持不变，仅替换该文件：

```c
static struct item *find_entry(const wf_counter *c, const char *word) {
    for (size_t i = 0; i < c->size; i++) {
        struct item *e = &c->items[i];
        if (strncmp(word, e->word, strlen(word)) == 0) {
            return e;
        }
    }
    return NULL;
}
```

标准库函数 `strncmp` 仅比对前 `strlen(word)` 个字节。当一个较短的词恰好是已有长词的前缀时，比对逻辑就会得出两者相同的荒谬判定。在测试目录中应用这一改动，向程序投喂序列 `then the then the the`：按照正常逻辑，输出应为 `the` 出现 3 次、`then` 出现 2 次；但在前缀缺陷版下，全部 5 次计数都被错误归并到了 `then` 名下：

::: terminal title="zsh - 前缀匹配缺陷"

```console
$ cp bugs/counter_prefix_match.c src/counter.c
$ gcc -std=c17 -Wall -Wextra -g -O0 -D__USE_MINGW_ANSI_STDIO=1 \
    -Iinclude src/*.c app/main.c -o build/wordfreq
$ printf 'then the then the the\n' > input.txt
$ ./build/wordfreq -n 5 input.txt
      5 then
```

:::

程序全程执行平稳，未抛出任何操作系统信号或控制台警告，只有最终的统计报表出现了逻辑偏差。若试图通过在代码中加入 `printf` 去排查，面对成百上千次词汇哈希或数组线性遍历，繁冗的打印输出会迅速淹没排查者的视线，很难精准判定究竟是哪一次比对产生了偏航。

语法 `break 目标位置 if 条件表达式` 能够设立条件断点（Conditional Breakpoint）：GDB 仅在条件判定为真（非 0）时才会真正挂起进程。若我们希望洞察“当单词 `the` 到来时，`find_entry` 究竟比对到了什么已有条目”，可以精准配置仅在 `word` 等于 `"the"` 时触发的中断：

::: terminal title="bash - 条件断点"


在编写条件表达式时，若调用了 `strcmp` 等 C 标准库函数，GDB 有时会提示 `'strcmp' has unknown return type; cast the call to its declared return type`。这是由于调试符号库中可能缺乏该 libc 函数的原型声明，只需在函数调用前附加显式强制类型转换 `(int)strcmp(...)` 即可顺利求值。

需要指出的是，条件断点的内部开销显著高于无条件断点：CPU 每次命中该代码物理地址时都会产生软中断中断进程，随后由 GDB 负责计算并解析条件表达式。在循环内部若迭代次数极多，频繁求值会导致程序运行变慢。

::: tip 命中次数太多的条件换一种写法

当一段深层循环需要迭代数十万次、而故障仅在第 1000 次左右才会触发时，让 GDB 逐次评估条件开销极大。一种高效的做法是在代码中寻找仅在特定阶段才会被穿透的邻近路径设立断点；另一种方式是使用 `ignore 断点编号 触发次数`，指示 GDB 直接跳过前 N 次命中，全速执行至目标窗口附近。这种方式完全由调试器底层的指令计数器接管，不改变程序的正常运行节奏。

:::

条件断点回答了“在特定逻辑条件发生时停在何处”的问题，而观察点（Watchpoint）则专攻另一个经典难题：“究竟是谁在什么时机篡改了这个对象的内存值”。通过 `watch 表达式`，GDB 会在监视对象发生数值写入改变的瞬间中断执行，并精确打印出旧值、新值、引发写入的源文件行以及完整的调用栈帧。

:::

`ignore 1 1` 使得断点 1 忽略了第一次正常初始化 `then` 的流程，程序直接停留在处理第二个词条 `the` 的时刻，此时条目 0 的词频依然维持初始的 1。随后我们对 `c->items[0].count` 挂接观察点；执行 `continue` 后，GDB 在计数值被改写为 2 的瞬间立即中断。调用栈回溯与 `print word` 清晰证明，正是分词为 `the` 的调用链路错误写入了该项。

命令 `watch -l 表达式` 中的 `-l` 代表按内存物理地址监控（Location）：GDB 在下断瞬间先计算出目标对象所在的具体虚拟内存地址，随后持续盯紧该固定地址范围的写入事件。若省略 `-l`，GDB 会在每个单步周期尝试重新计算整个表达式树，当表达式中涉及指针解引用、且指针可能被释放或移动时，监控便会意外失效。因此，在监视结构体内部深层成员时，使用 `watch -l` 具有更高的鲁棒性。

需要提醒的是，涉及指针解引用的监视表达式必须在其指向的内存已经完成分配后才能设立，否则 GDB 会因无法解析底层地址而拒绝请求。

现代主流 CPU 架构（如 x86-64 的 DR0~DR3 调试寄存器、ARM Cortex-M 的 DWT 数据观察点单元）通常在芯片层面提供了 4 个专用的硬件观察点寄存器。GDB 会优先启用这些硬件寄存器实现无损的零开销监控（控制台显示为 `Hardware watchpoint`）。若设立的观察点数量超出了硬件支持上限，GDB 只能被迫退化为软件单步比对模式，此时程序的执行性能会出现断崖式下跌。

::: tip 按地址设观察点

当对象被隐匿在多层复杂的不透明结构体背后、缺乏直接的类型定义信息时，可以直接将目标成员的物理内存地址强制转换为对应类型的指针并解引用：

```console
(gdb) watch *(size_t *)&c->items[0].count
Hardware watchpoint 2: *(size_t *)&c->items[0].count
(gdb) continue
Continuing.

Thread 1 hit Hardware watchpoint 2: *(size_t *)&c->items[0].count

Old value = 1
New value = 2
wf_counter_add (c=0x6c1e80, word=0x5ffd70 "the") at src/counter.c:86
86	        return 0;
```

采用 `*(类型 *)地址` 的写法，能够精确约束硬件观察点监视的数据宽度（如 1、2、4 或 8 字节），在面对紧凑二进制协议与位字段布局时极具实战价值。

:::

## 5. 查看内存与寄存器

指令 `print` 严格依据编译期绑定的类型信息将内存还原为可读的数据；但在底层调试、排查内存损坏或跨平台对齐故障时，直接检视物理内存的原始字节往往能提供最确凿的证据。GDB 提供了原生的内存读取指令 `x`（即 examine），其标准语法格式为 `x/数量格式单位 内存地址`：

| 格式符 | 呈现含义 |
| --- | --- |
| `x` | 十六进制整数 |
| `d` | 有符号十进制整数 |
| `c` | ASCII 字符常量 |
| `s` | 以空字符结尾的 C 字符串 |
| `i` | 机器汇编指令（反汇编） |

| 宽度单位 | 对应物理字节跨度 |
| --- | --- |
| `b` | 1 字节（Byte） |
| `h` | 2 字节（Halfword） |
| `w` | 4 字节（Word） |
| `g` | 8 字节（Giant word） |

为了审视分词函数 `wf_tokenizer_next` 写入单词缓冲区的真实物理状态，我们可以使用 `x/16xb word` 逐字节展开查看连续 16 个字节的十六进制排布，或者使用 `x/s word` 直接按字符串规则求值：

::: terminal title="bash - x 命令"

```console
(gdb) break app/main.c:95
Breakpoint 1 at 0x14000211b: file app/main.c, line 95.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 26740.0x63b4]

Thread 1 hit Breakpoint 1, count_stream (counter=0x711e10, in=0x70bda0,
    name=0x70bd50 "tests/data/sample.txt") at app/main.c:95
95	        if (wf_counter_add(counter, word) != 0) {
(gdb) x/16xb word
0x5ffd70:	0x74	0x68	0x65	0x00	0x00	0x00	0x00	0x00
0x5ffd78:	0x00	0x80	0x00	0x00	0x01	0x00	0x00	0x00
(gdb) x/s word
0x5ffd70:	"the"
```

:::

前四个字节 `0x74 0x68 0x65 0x00` 准确对应着 ASCII 字符 `t`、`h`、`e` 以及起终止符作用的 `\0`；其后连续的几个 `0x00` 是定长数组 `char word[WF_WORD_MAX]` 中本次写入未触及的填充余量，更远处的离散数据则是栈帧中留存的其他局部状态。由于 `word` 是数组名，在表达式中求值自动退化为首元素地址；若手中持有的是裸指针对象，则可先通过 `print 指针` 获得其指向的虚拟地址，再传入 `x/16xb 0x...` 展开。

当审视复合数据结构时，`x` 命令能够穿透抽象层，将结构体内部各字段在内存中的真实对齐与填充状况完整暴露出来：

::: terminal title="bash - 按机器字看结构体"

```console
(gdb) break print_top
Breakpoint 1 at 0x140002224: file app/main.c, line 117.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 28548.0x5a0c]

Thread 1 hit Breakpoint 1, print_top (counter=0x6d1e10, n=3) at app/main.c:117
117	    wf_entry *entries = calloc(n, sizeof *entries);
(gdb) print *counter
$1 = {items = 0x6d4970, size = 7, capacity = 16}
(gdb) x/6xw counter->items
0x6d4970:	0x006d2710	0x00000000	0x00000004	0x00000000
0x6d4980:	0x006d4aa0	0x00000000
```

:::

在 64 位系统架构（x86-64）下，每个 `struct item` 占用 16 个字节：前 8 字节为指针类型成员 `char *word`（值为 `0x00000000006d2710`，在小端序下列印，指向字符串 `"the"`），后 8 字节为 `size_t count`（值为 4）。终端中每行按 4 个 32 位机器字排布，恰好一行完整映射一个结构体实例。这类对底层内存布局的直接观测，在判定内存对齐陷阱、结构体填充开销以及缓冲区溢出越界时是不可替代的坚固基石。

而在 CPU 架构层面，程序计数器（PC，Program Counter）与栈指针（SP，Stack Pointer）是状态排查中最核心的寄存器。通过 `info registers` 可以倾倒所有通用寄存器的实时快照，通过 `info registers pc sp` 可以精简列出关键状态，而通过 `$pc` 则可以在表达式中像使用局部对象一样直接引用寄存器：

::: terminal title="bash - 查看寄存器"

```console
(gdb) info registers pc sp
pc             0x7ff65ef5211b      0x7ff65ef5211b <count_stream+184>
sp             0x5ffd50            0x5ffd50
(gdb) print $pc
$1 = (void (*)()) 0x7ff65ef5211b <count_stream+184>
(gdb) print/x $pc
$2 = 0x7ff65ef5211b
(gdb) x/i $pc
=> 0x7ff65ef5211b <count_stream+184>:	lea    -0x70(%rbp),%rdx
```

:::

在 x86-64 体系下，`$pc` 对应物理寄存器 `rip`，`$sp` 对应 `rsp`；而在 ARM Cortex-M 体系下，GDB 统一映射为 `pc` 与 `sp`。`x/i $pc` 指令能够将当前指令指针所指的物理内存解码为反汇编指令。上面截获的 `lea` 指令正在将 `word` 缓冲区的栈偏置计算至寄存器 `rdx` 中，为即将调用的 `wf_counter_add` 准备传参。在汇编层面比对指令流，能清晰核验编译器究竟对源码做了何种变换，本章的这一技巧在后续嵌入式片上调试（[SWD/JTAG 调试](/教程/正文/嵌入式/1_平台与工具链/1_7_SWD_JTAG与片上调试)）中将完全通用。

## 6. 调试失败的测试

在持续集成与日常自动化测试中，当测试套件亮起红灯时，框架日志通常仅给出一行极为简短的报警，例如：`tests/test_token.c:44: word is "The", expected "the"`。这是第 11 章我们手工构建的测试框架，宏 `CHECK_STR_EQ` 在比对失败时调用了底层的格式化打印函数 `check_fail`。若希望沉浸式复查断言未通过瞬间的全景上下文，只需在 `check_fail` 函数入口处下断：

:::

## 7. 优化与调试信息

在现代工具链体系中，生成调试信息与开启编译器优化是两项正交独立的工程决策。选项 `-g` 的核心作用是在二进制产物中织入 DWARF 映射表，建立起“某段机器汇编指令对应哪一份源文件的哪一行代码、某个局部对象此刻被安放在哪一个物理寄存器或栈内存偏移处”的映射关系；而编译器优化选项（`-O1`、`-O2`、`-O3`）则会大刀阔斧地重排指令流水线、将短寿命对象尽可能固定在通用寄存器中、展开深层循环、实施跨函数内联并对编译期常量提前计算求值。当两者同时开启时，尽管调试映射关系依然尽力维系，但底层机器码的执行拓扑与高级源码的文本行序已不再呈现简单的线性对应。

为了直观体会优化对调试体验的剧烈改动，我们将同一份 wordfreq 源码分别以 `-O0`、`-Og` 与 `-O2` 编译，并在同一断点行 `app/main.c:123` 尝试使用 `print n` 观察状态。在关闭优化的 `-O0` 下：

::: terminal title="bash - -O0"

```console
(gdb) break app/main.c:123
Breakpoint 1 at 0x140002269: file app/main.c, line 123.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq.exe -n 3 tests/data/sample.txt
[New Thread 28892.0x4d24]

Thread 1 hit Breakpoint 1, print_top (counter=0x101e10, n=3) at app/main.c:123
123	    if (written == 0 && wf_counter_size(counter) > 0) {

$1 = 3
(gdb) info locals
entries = 0x104c20
written = 3
status = 0
```

:::

而在切换至 `-O2` 的二进制产物后，在完全相同的代码位置断下：

::: terminal title="bash - -O2"

```console
(gdb) break app/main.c:123
Breakpoint 1 at 0x1400094d2: file app/main.c, line 123.
(gdb) run

    at app/main.c:123
```

在 `-O2` 级别下，打印 `n` 时终端提示了 `<optimized out>`。这是由于在执行流到达该分支之前，参数 `n` 参与的两次核心运算（`calloc` 分配条目数组与 `wf_counter_top` 提取词频）已经圆满结束，后续控制流已无处需要再次引用 `n`。编译器在活跃性分析中识别到其生命周期完结，立即释放了原先装载 `n` 的寄存器供其他运算复用，导致该对象的瞬时值彻底从物理上下文中蒸发。与此同时，`info locals` 对同一个局部对象输出了多行不同状态（部分有值，部分显示 `<optimized out>`），这是由于深度优化导致同一源码对象在不同指令片段被映射至分散的寄存器或栈切片中，GDB 在符号重组时将所有生命周期记录全量呈现在控制台。

优化的介入同样会打破单步执行的直观心智模型。在 `-O2` 下执行 `next`，光标经常会在源码文本中忽前忽后地来回跳跃，或者单步一次直接跨越了数行无关代码；而在使用 `step` 步入时，若目标函数已被完全内联至调用点，GDB 只能在合成的虚拟内联栈帧中勉力还原上下文。当函数在多处被同时内联时，针对该函数名设置的断点甚至会直接分裂为多个地址位置：

```console
(gdb) break find_entry
Breakpoint 1 at 0x1400017a9: find_entry. (2 locations)
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq_o2.exe -n 3 tests/data/sample.txt

Thread 1 hit Breakpoint 1.1, find_entry (c=0x7f1e90, word=0x5ffd90 "the")
    at src/counter.c:35
35	    for (size_t i = 0; i < c->size; i++) {
```

由于 `find_entry` 源码体积短小，编译器在两处不同的调用点分别将其代码就地铺开，GDB 只能在两个物理机器码位置分别下断，断点编号被编码为分层形式 `1.1` 与 `1.2`。

为了化解性能优化与源码级可调试性之间的剧烈撕裂，GCC 专门提供了 `-Og` 优化级别。其设计宗旨在于保留基本冗余消除与常量传播等安全优化的同时，坚决抑制一切会导致源码行与汇编指令对应混乱的激进重排与内联：

::: terminal title="bash - -Og"

```console
(gdb) break app/main.c:123
Breakpoint 1 at 0x140001e2e: file app/main.c, line 123.
(gdb) run
Starting program: C:\proj\wordfreq\build\wordfreq_og.exe -n 3 tests/data/sample.txt
[New Thread 19332.0x18e8]

Thread 1 hit Breakpoint 1, print_top (counter=counter@entry=0x79f480,
    n=<optimized out>) at app/main.c:123
123	    if (written == 0 && wf_counter_size(counter) > 0) {
(gdb) print n
$1 = <optimized out>
(gdb) info locals
entries = 0x7a6fa0
written = 3
status = 0
```

:::

综合横向比对可知：在功能开发与故障攻坚期，`-O0 -g` 能够保留最真实无缺的栈帧对象与最纯粹的单步流向，排查体验最为顺畅；`-Og -g` 则在逼近实际运行性能的同时维系了绝大部分单步可读性。而在面对生产发布构建时，工程规范强烈建议采用带调试符号的优化配置（如 CMake 内置的 `RelWithDebInfo` 构建类型，对应 `-O2 -g`）：`-g` 所附加的调试节区只占据物理磁盘空间，完全不会增加程序运行时的内存常驻开销或削弱任何 CPU 指令执行性能，在生产环境突发崩溃时，这份符号将成为线上事后归因的救命稻草。

::: warning 源码改了要重新编译

当磁盘上的 C 源文件发生了更新而未重新执行编译链接时，GDB 在启动或加载符号时会警示 `warning: Source file is more recent than executable.`。此时调试器呈现的代码行与内存中实际跑飞的汇编指令可能出现不可调和的错位，单步断点与打印对象均会产生虚假读数。在每次调整功能源码后，必须先确认构建编译通过，再行启动调试会话。

:::

## 8. 其他前端与 LLDB

命令行终端交互是深入掌控 GDB 的最底座基石。在当今的图形化开发工具中，诸如 VS Code、CLion、Qt Creator 等现代集成开发环境（IDE），其底层原理均为在后台静默派生 GDB 或 LLDB 子进程，并通过机器接口协议（Machine Interface，即 GDB/MI）与调试引擎进行结构化通信，最终将断点标记、局部对象、调用栈帧映射至交互式可视化面板中。

以 VS Code 的 C/C++ 官方扩展为例，调试会话的启动与参数编排由 `.vscode/launch.json` 文件统一定义：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "debug wordfreq",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/build/wordfreq",
      "args": ["-n", "10", "tests/data/sample.txt"],
      "cwd": "${workspaceFolder}",
      "MIMode": "gdb",
      "miDebuggerPath": "gdb",
      "setupCommands": [
        { "description": "pretty printing", "text": "set print pretty on" }
      ]
    }
  ]
}
```

配置项中的 `program` 指向待调试的目标二进制路径，`args` 数组保存启动时透传的命令行参数，`cwd` 决定了程序执行时相对路径的解析根目录，`MIMode` 指定底层通信协议，而 `setupCommands` 允许在会话建立初始执行原生 GDB 命令。其中 `set print pretty on` 能够指示 GDB 将嵌套的复杂结构体按多行缩进分层格式化排版，极大提升人工审阅效率。

对于由 JetBrains 推出的专业 C/C++ IDE CLion，开发者无须手动维护类似配置：IDE 能够自动解析 `CMakeLists.txt` 构建图谱，界面上的调试按钮可直接驱动后端的 GDB 或 LLDB 引擎展开工作。

在 LLVM 编译器工具链生态中，原生的调试工具是 LLDB。尽管两者的命令行词汇存在差异，但其架构核心理念高度一致：

| 调试操作 | GDB 指令 | LLDB 对应指令 |
| --- | --- | --- |
| 启动并执行 | `run` | `run`（或 `r`） |
| 按文件行号设断点 | `break 文件:行` | `breakpoint set -f 文件 -l 行` |
| 按函数名称设断点 | `break 函数名` | `breakpoint set -n 函数名` |
| 设置条件断点 | `break 位置 if 条件` | `breakpoint set -n 函数 -c 条件` |
| 设立内存观察点 | `watch 表达式` | `watchpoint set expression 表达式` |
| 恢复全速继续运行 | `continue` | `continue`（或 `c`） |
| 单步越过函数调用 | `next` | `next`（或 `n`） |
| 单步步入函数内部 | `step` | `step`（或 `s`） |
| 执行至当前函数返回 | `finish` | `finish` |
| 打印完整调用栈回溯 | `bt` | `bt` |
| 跃迁活动栈帧 | `frame N` | `frame select N` |
| 格式化求值并打印 | `print 表达式` | `expression 表达式`（`p` 亦可） |
| 列出当前栈帧所有局部对象 | `info locals` | `frame variable` |
| 检视原始内存字节 | `x/16xb 地址` | `memory read -f x -c 16 -s 1 地址` |

在 macOS 平台上，基于操作系统内核权限与代码签名的约束，LLDB 是当之无愧的首选默认工具；而在主流 Linux 服务端与嵌入式交叉编译场景中，GDB 则凭借极其广泛的体系架构支持依然占据着不可动摇的中流砥柱地位。

在 Linux 运维与系统编程体系中，还有一项极为强大的事后归因机制：核心转储（Core Dump）。当未受捕获的非法内存信号击穿进程生命周期时，Linux 内核能够将该时刻整个进程的用户态虚拟内存映射全量镜像固化为磁盘文件。开发者随后可在完全不依赖原始运行环境的情况下，使用 GDB 静态加载该转储文件，完美重现崩溃事发那一瞬的完整现场：

```console
$ ulimit -c unlimited
$ ./build/wordfreq_crash -n 10 tests/data/sample.txt
Segmentation fault (core dumped)
$ gdb ./build/wordfreq_crash core
(gdb) bt
```

命令 `ulimit -c unlimited` 解除了当前终端对转储文件容量的限制。生成的 `.core` 文件在 GDB 中装载后，`bt`、`frame`、`print` 等全套排查指令皆可如在实机般顺畅运转。而在 Windows 操作系统上，对应的故障转储形式为 MiniDump（`.dmp` 文件），具体抓取与解析方案将在后续的 Windows 系统编程拓展中深入剖析。

::: tip 用 -batch 把会话记录下来

在向开源社区提交缺陷复现报告或在自动化持续集成中留存调试凭据时，交互式的提示符会阻断脚本。GDB 提供了批处理选项：通过附加 `-batch` 与若干 `-ex "GDB指令"`，可以在单行 Shell 指令中驱动 GDB 执行全套诊断并自动退出销毁：

```console
$ gdb -q -batch -ex "break wf_counter_add" -ex "run" \
    -ex "print word" -ex "bt 2" --args ./build/wordfreq -n 3 tests/data/sample.txt
Breakpoint 1 at 0x14000191c: file src/counter.c, line 85.
[New Thread 20456.0x18f4]

Thread 1 hit Breakpoint 1, wf_counter_add (c=0x101e10, word=0x5ffd70 "the") at src/counter.c:85
85	    struct item *e = find_entry(c, word);
$1 = 0x5ffd70 "the"
#0  wf_counter_add (c=0x101e10, word=0x5ffd70 "the") at src/counter.c:85
#1  0x00007ff65ef5212b in count_stream (counter=0x101e10, in=0xfbda0, name=0xfbd50 "tests/data/sample.txt") at app/main.c:95
```

若将命令组织在独立文本文件中，还可以直接使用 `-x 脚本文件` 进行批处理注入，为工程团队沉淀下高价值的确定性排查资产。
