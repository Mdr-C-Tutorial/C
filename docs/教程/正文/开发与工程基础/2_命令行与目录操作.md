# 2. 命令行与目录操作

同一个程序要对十个输入文件各跑一遍，还要把每次的结果存下来。在 IDE 里，这意味着改十次运行配置、点十次运行按钮、手动复制十次输出；在 shell 里，这是一条命令。下面用现成的 `wc` 代替那个程序，效果一样：

::: terminal title="zsh - wc"

```text
$ wc -l inputs/*.txt
   9 inputs/01.txt
  16 inputs/02.txt
  23 inputs/03.txt
   7 inputs/04.txt
  14 inputs/05.txt
  21 inputs/06.txt
   5 inputs/07.txt
  12 inputs/08.txt
  19 inputs/09.txt
   3 inputs/10.txt

$ wc -l inputs/*.txt > lines.txt
$ cat lines.txt
   9 inputs/01.txt
  16 inputs/02.txt
  23 inputs/03.txt
   7 inputs/04.txt
  14 inputs/05.txt
  21 inputs/06.txt
   5 inputs/07.txt
  12 inputs/08.txt
  19 inputs/09.txt
   3 inputs/10.txt
 129 total
```

:::

`inputs/` 是配套目录 `code/开发与工程基础/2_命令行与目录操作/inputs/` 下的十个文本文件，行数各不相同，`wc` 输出的最后一列是合计。把 `code/开发与工程基础/2_命令行与目录操作/` 当作工作目录，就能照着敲。

这一页讲的就是这类操作：在目录之间移动、整理文件、把程序连起来、判断每一步是否成功。后面的编译、测试、调试和构建，都是在终端里敲命令完成的，这些操作不熟练，后面每一步都会卡住。

本页的命令以 bash 为准。Linux 和 macOS 的终端默认就是 bash 或 zsh，两者的写法在这里通用；Windows 读者按[第 1 章](/教程/正文/开发与工程基础/1_开发环境与工具角色)装好 MSYS2 后，在「MSYS2 UCRT64」终端里操作。正文输出以 Linux（Debian 13，bash 5.2）的实测为准，Windows 上不同的地方单独说明。

## 1. 终端、shell 与命令

终端 (terminal) 是负责显示和接收键盘输入的窗口，shell 是运行在这个窗口里、读入命令并解释执行的程序。两者常出现在同一个窗口里，初学者容易把它们当成一回事：关掉窗口，终端和 shell 一起结束；在窗口里敲的每一行，都是交给 shell 处理的。

本教程使用 bash (Bourne Again Shell)。一条命令由三部分组成：命令名、选项 (option) 和参数 (argument)。下面是 `ls` 的用法说明，由 `ls --help` 打印：

::: terminal title="zsh - ls --help"

```text
$ ls --help | head -n 8
Usage: ls [OPTION]... [FILE]...
List information about the FILEs (the current directory by default).
Sort entries alphabetically if none of -cftuvSUX nor --sort is specified.

Mandatory arguments to long options are mandatory for short options too.
  -a, --all                  do not ignore entries starting with .
  -A, --almost-all           do not list implied . and ..
      --author               with -l, print the author of each file
```

:::

方括号里的 `OPTION`、`FILE` 表示可选，省略时按说明里的默认行为执行。选项有短选项和长选项两种写法，`-a` 和 `--all` 是同一个选项；短选项可以合并，`ls -l -a` 与 `ls -la` 等价。长选项需要取值时写成 `--color=auto` 或 `--color auto`。

`--help` 是大多数程序都提供的说明书入口。系统装了手册页时，`man ls` 会打开更完整的手册，按 `q` 退出；精简安装的系统可能没有 `man`，用 `--help` 即可。本页的实测环境就没有装 `man`。

bash 内建命令的说明还可以用 `help 名字` 查看，例如 `help cd`。

终端窗口里的 `$` 是提示符，表示 shell 等待输入，不是要敲的内容。后文的终端输出都用 `$` 开头表示输入行。命令名区分大小写，`LS` 和 `ls` 不是一回事。

## 2. 工作目录与路径

### 2.1 当前目录、绝对路径与相对路径

shell 任何时刻都有一个工作目录 (working directory)，不带路径的文件名都相对它解释。`pwd` 打印当前目录。

从根目录 `/` 开始写起的路径是绝对路径 (absolute path)，其余是相对路径 (relative path)。`.` 表示当前目录，`..` 表示上一级目录，`~` 由 shell 展开成用户的主目录。本页的演示都在这棵练习目录里进行：`src` 存放源文件，`include` 和 `build` 暂时是空的，根下另有 `text.txt` 和 `notes.txt` 两个数据文件。这些文件都在 `code/开发与工程基础/2_命令行与目录操作/` 下，复制过来就是这棵树。

::: terminal title="zsh - 目录与路径"

```text
$ cd /home/minsecrus/tutorial/work/p071/practice
$ pwd
/home/minsecrus/tutorial/work/p071/practice
$ ls
build  include  notes.txt  src  text.txt
$ ls -a
.  ..  build  include  notes.txt  src  text.txt
$ ls -l
total 20
drwxrwxr-x 2 minsecrus minsecrus 4096 Oct 21 02:22 build
drwxrwxr-x 2 minsecrus minsecrus 4096 Oct 21 02:22 include
-rw-r--r-- 1 minsecrus minsecrus   98 Oct 21 02:22 notes.txt
drwxrwxr-x 2 minsecrus minsecrus 4096 Oct 21 02:22 src
-rw-r--r-- 1 minsecrus minsecrus 315 Oct 21 02:22 text.txt
$ ls src
args.c  bad.c  hello.c  mix.c  upper.c
$ cd src
$ pwd
/home/minsecrus/tutorial/work/p071/practice/src
$ cd ../include
$ pwd
/home/minsecrus/tutorial/work/p071/practice/include
$ cd ..
$ pwd
/home/minsecrus/tutorial/work/p071/practice
$ cd -
/home/minsecrus/tutorial/work/p071/practice/include
$ cd ~
$ pwd
/home/minsecrus
```

:::

`ls` 默认不列出以 `.` 开头的文件（习惯上称为点文件 (dotfile)），`-a` 把它们一并列出，所以多出 `.` 和 `..` 两项。`ls -l` 每行开头的一个字符表示文件类型，`d` 是目录，`-` 是普通文件，后面九位是权限（[系统编程部分第 3 章](/教程/正文/系统编程/3_文件系统_目录与权限)会讲），再往后是链接数、属主、属组、大小、修改时间和文件名。

`cd` 不带参数时回到主目录，`cd -` 回到上一个工作目录并把它的路径打印出来，省去手敲长路径。`cd` 的目录不存在时命令失败，退出状态为 1，第 5 节会解释这个值的来源。

相对路径里的 `..` 可以连用，`../../include` 表示上两级再进入 `include`。`.` 常用于明确表示当前目录，例如运行当前目录下的程序要写 `./程序名`，原因见第 4 节。

::: generate dev-cmdline-path-walk kind=explanation concepts=dev-cmdline-path-search

面向第一次使用命令行的读者，用上面的练习目录逐步演示「工作目录 + 相对路径」如何定位到同一个目录：分别从 practice、从 src、从根目录出发，写出到达 include 的路径，并说明为什么 `cd ..` 之后 `pwd` 的结果会变，而绝对路径始终不变。

:::

### 2.2 含空格的路径与 Windows 盘符

路径里有空格时，必须用引号把整个路径包起来，否则 shell 会把它拆成两个参数。下面的目录名带一个空格：

::: terminal title="zsh - 含空格的目录"

```text
$ mkdir "my notes"
$ cd "my notes"
$ pwd
/home/minsecrus/tutorial/work/p071/practice/my notes
$ cd ..
$ ls
 build   include  'my notes'   notes.txt   src   text.txt
$ rmdir "my notes"
```

:::

`ls` 输出里那个目录带上了单引号，这是 `ls` 用引号标出名字中的空格，实际名字里没有引号。

Windows 的盘符在 MSYS2 和 Git Bash 里写成 `/c`、`/d` 这样的目录：`C:\Users\alice\proj` 对应 `/c/Users/alice/proj`。两种写法可以用 `cygpath` 互相换算：

::: terminal title="zsh - cygpath（Windows）"

```text
$ cygpath -w /c/Users/alice/proj
C:\Users\alice\proj
$ cygpath -u 'C:\Users\alice\proj'
/c/Users/alice/proj
$ cygpath -m /c/Users/alice/proj
C:/Users/alice/proj
```

:::

`-w` 给出 Windows 形式，`-u` 给出 UNIX 形式，`-m` 给出正斜杠的混合形式。把路径传给只认 Windows 写法的程序时用 `-w`，写进 Makefile 这类同时被两种工具读取的文件时用 `-m`。反斜杠在 bash 里是转义字符，`echo C:\Users` 打印出来是 `C:Users`，所以 Windows 路径要么加单引号，要么改用正斜杠。

## 3. 创建、复制、移动和删除

目录树的建立和整理靠五条命令：`mkdir` 建目录，`touch` 建空文件或更新文件时间，`cp` 复制，`mv` 移动或改名，`rm` 删除。下面的输出里用了 `ls -1`，它让每行只列一项，便于和后续输出对照。`mkdir -p` 会一次建出路径上缺少的所有目录，已经存在的目录不报错：

::: terminal title="zsh - 整理目录树"

```text
$ cd /home/minsecrus/tutorial/work/p071/practice
$ mkdir notes
$ touch notes/todo.txt
$ cp notes/todo.txt notes/todo.bak
$ mv notes/todo.bak notes/done.txt
$ ls -1 notes
done.txt
todo.txt
$ mkdir -p notes/2026/10
$ mv notes/todo.txt notes/2026/10/
$ ls -R notes
notes:
2026  done.txt

notes/2026:
10

notes/2026/10:
todo.txt
$ cp -r src src_copy
$ ls
build  include  notes  notes.txt  src  src_copy  text.txt
$ rm -r src_copy
$ ls
build  include  notes  notes.txt  src  text.txt
$ rmdir build
$ ls
include  notes  notes.txt  src  text.txt
$ mkdir build
$ rm -r notes
$ ls
build  include  notes.txt  src  text.txt
```

:::

`mv` 在同一个文件系统内只改目录项，不复制内容，所以移动大文件也是瞬间完成；`mv 旧名 新名` 就是改名。`cp` 复制目录必须加 `-r`，它表示递归；不加时 `cp` 拒绝执行并提示 `-r not specified`。删除目录也有两条命令：`rmdir` 只能删空目录，目录非空时报 `Directory not empty`；`rm -r` 连内容一起删。`rm` 不加 `-r` 删目录会报 `Is a directory`。

::: warning `rm` 不进回收站

`rm` 删除的文件无法从桌面回收站找回。用通配符批量删除之前，先用同一个模式跑一次 `ls`，确认匹配到的正是要删的东西，再把它换成 `rm`。

:::

查看文件内容用 `cat`，一次全部打印；文件很长时用 `less` 分页浏览，按 `q` 退出；只看开头或结尾若干行用 `head`、`tail`。`wc -l` 数行数：

::: terminal title="zsh - 查看文件"

```text
$ cat notes.txt
实验记录

第一行：建立目录树
第二行：复制与移动
第三行：删除与清理
$ head -n 2 notes.txt
实验记录

$ tail -n 2 notes.txt
第二行：复制与移动
第三行：删除与清理
$ wc -l notes.txt
5 notes.txt
```

:::

`head` 和 `tail` 不带 `-n` 时默认显示十行。`cat` 可以一次给多个文件，按顺序拼接输出，第 6 节用它和管道连起来。`less` 会占满整个屏幕并等待按键，交互性与前几条命令不同，在终端里用一次就熟悉了，本页不贴它的输出。

通配符 `*`、`?`、`[...]` 由 shell 展开，命令本身看到的已经是展开后的文件名列表。`*.c` 匹配所有以 `.c` 结尾的名字，`?.c` 匹配名字只有一个字符再加 `.c` 的文件，`[ah]*.c` 匹配以 `a` 或 `h` 开头的名字：

::: terminal title="zsh - 通配符"

```text
$ echo *.txt
notes.txt text.txt
$ echo "*.txt"
*.txt
$ ls -1 src/[ah]*.c
src/args.c
src/hello.c
```

:::

加了引号的 `*.txt` 原样输出，因为引号阻止了 shell 展开。这一点在第 5 节用程序再验证一次。

## 4. shell 怎样找到命令

`ls`、`gcc`、`git` 都是磁盘上的可执行文件，`cd`、`echo`、`pwd` 则是 shell 自带的内建命令 (builtin)。`type` 能区分这两类：

::: terminal title="zsh - type"

```text
$ type pwd
pwd is a shell builtin
$ type ls
ls is /usr/bin/ls
$ type cd
cd is a shell builtin
$ type gcc
gcc is /usr/bin/gcc
```

:::

内建命令由 shell 自己执行，不需要另起程序；外部命令则要按名字在磁盘上找到对应的文件。查找的范围由环境变量 (environment variable) `PATH` 决定，它是一个用冒号分隔的目录列表，shell 按顺序在每个目录里找同名文件，第一个找到的就是要执行的：

::: terminal title="zsh - PATH"

```text
$ echo "$PATH" | tr ':' '\n'
/usr/local/bin
/usr/bin
/bin
/usr/games
```

:::

`tr ':' '\n'` 把冒号换成换行，只是为了看得清楚。不同机器上的条目和条数都不相同，共同点是通常不含当前目录，所以编译出来的 `hello` 不能直接敲名字运行：

::: terminal title="zsh - command not found"

```text
$ gcc -std=c17 -Wall -Wextra -o build/hello src/hello.c
$ hello
bash: hello: command not found
$ echo "rc=$?"
rc=127
$ ./build/hello
Hello, C!
$ command -v hello
$ command -v gcc
/usr/bin/gcc
$ command -v ./build/hello
./build/hello
```

:::

`command -v` 按 `PATH` 查找并打印找到的路径，找不到时不输出、退出状态为 1。带上斜杠的 `./build/hello` 不走 `PATH`，直接按路径执行，所以 `command -v ./build/hello` 原样回显。在 Windows 上执行时可以省略 `.exe` 后缀，bash 会自动补上。

`PATH` 里加一个目录用 `export`，只在当前 shell 和它启动的子进程里有效：

::: terminal title="zsh - 把 build 目录加入 PATH"

```text
$ export PATH="$PATH:$PWD/build"
$ command -v hello
/home/minsecrus/tutorial/work/p071/practice/build/hello
$ hello
Hello, C!
```

:::

`$PWD` 是 shell 维护的当前目录，作用与 `pwd` 的输出相同。把新目录加在 `$PATH` 前面还是后面会影响查找结果：两个目录里都有同名程序时，先被找到的那个执行。

::: terminal title="zsh - PATH 的查找顺序"

```text
$ mkdir -p p1 p2
$ printf '#!/bin/sh\necho one\n' > p1/whichone
$ printf '#!/bin/sh\necho two\n' > p2/whichone
$ chmod +x p1/whichone p2/whichone
$ PATH="$PWD/p1:$PWD/p2:$PATH" whichone
one
$ PATH="$PWD/p2:$PWD/p1:$PATH" whichone
two
```

:::

::: concept dev-cmdline-path-search title="PATH 是按顺序搜索的目录列表"

shell 执行不带斜杠的命令名时，按 `PATH` 中目录的先后顺序逐个查找可执行文件，第一个匹配的生效；整个列表都找不到时报告 `command not found`，退出状态为 127。`PATH` 中一般不含当前目录，运行当前目录下的程序要写 `./程序名`。

:::

环境变量用 `名字=值` 的形式赋值。直接赋值只对当前 shell 有效，不会传给子进程；加 `export` 之后，子进程才能看到。写在命令前面的赋值只对这一条命令生效：

::: terminal title="zsh - 环境变量与 export"

```text
$ GREETING=hey
$ sh -c 'echo "[$GREETING]"'
[]
$ GREETING=hey sh -c 'echo "[$GREETING]"'
[hey]
$ export GREETING=hey
$ sh -c 'echo "[$GREETING]"'
[hey]
$ GREETING=bye sh -c 'echo "[$GREETING]"'
[bye]
$ echo "$GREETING"
hey
$ unset GREETING
$ echo "[$GREETING]"
[]
```

:::

第一次的 `GREETING=hey` 只是 shell 自己的对象，`sh` 启动时拿不到；命令前加 `GREETING=hey` 时，这条命令的环境里带着它；`export` 之后所有子进程都能看到；`GREETING=bye` 只覆盖这一条命令，下一条 `echo` 读到的仍是 `hey`。这些改动只活在当前会话里，关掉终端就消失。想长期保留，把 `export` 那一行写进 `~/.bashrc`。

<Quiz
  :options="[
    { label: 'p1 里那个，因为它在 PATH 里排在前面', value: 'A' },
    { label: 'p2 里那个，因为新加的目录优先', value: 'B' },
    { label: '两个都会执行一次', value: 'C' },
    { label: '报错，因为同名程序冲突', value: 'D' }
  ]"
  answer="A"
>

<template #question>

</template>

正确答案是 **A**。`PATH` 从左往右查找，先命中的目录生效，后面的同名文件不会被考虑。B 说反了，C 和 D 都没有这种机制。

</Quiz>

## 5. 命令行参数与退出状态

### 5.1 程序看到的参数

程序启动时，shell 把命令名和各个参数作为字符串交给它。C 程序从 `main` 的 `argc` 和 `argv` 取得这些字符串：`argc` 是参数个数，`argv[0]` 是程序名，`argv[1]` 起是用户写的参数。下面的程序把每个参数两边加上方括号打印，方便看清空白：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(int argc, char *argv[]) {
    printf("argc = %d\n", argc);
    for (int i = 0; i < argc; i++) {
        printf("argv[%d] = [%s]\n", i, argv[i]);
    }
    if (argc > 1 && strcmp(argv[1], "--fail") == 0) {
        return 3;
    }
    return EXIT_SUCCESS;
}
```

这个程序在 `code/开发与工程基础/2_命令行与目录操作/args.c`。编译后分别传入不同的写法：

::: terminal title="zsh - args 与引号"

```text
$ cd /home/minsecrus/tutorial/work/p071/practice
$ gcc -std=c17 -Wall -Wextra -o build/args src/args.c
$ ./build/args a b
argc = 3
argv[0] = [./build/args]
argv[1] = [a]
argv[2] = [b]
$ ./build/args "a b"
argc = 2
argv[0] = [./build/args]
argv[1] = [a b]
$ ./build/args src/*.c
argc = 6
argv[0] = [./build/args]
argv[1] = [src/args.c]
argv[2] = [src/bad.c]
argv[3] = [src/hello.c]
argv[4] = [src/mix.c]
argv[5] = [src/upper.c]
$ ./build/args 'src/*.c'
argc = 2
argv[0] = [./build/args]
argv[1] = [src/*.c]
$ ./build/args $HOME '$HOME'
argc = 3
argv[0] = [./build/args]
argv[1] = [/home/minsecrus]
argv[2] = [$HOME]
```

:::

`a b` 是两个参数，`"a b"` 是一个参数，引号阻止了 shell 在空格处分词。不加引号的 `src/*.c` 由 shell 展开成五个文件名，程序收到的是五个参数；加上单引号则原样传一个。`$HOME` 在双引号里和不在引号里都会展开成路径，单引号里的 `$HOME` 保持字面。引号和通配符的处理都发生在 shell 里，程序本身不参与。

::: tip Windows 上引号保不住 `*.c`

MinGW-w64 编译出的程序在启动时由 C 运行库再展开一次通配符，所以即使在 bash 里写了 `./args '*.c'`，程序收到的也可能是展开后的文件名。在本机的 MinGW-w64 程序上实测，加单引号的 `'*.c'` 仍然被展开成目录里全部 `.c` 文件名。判断参数到底由谁展开，要结合运行环境看。

:::

### 5.2 退出状态

程序结束时返回一个退出状态 (exit status)，shell 把它存在 `$?` 里。按约定，0 表示成功，非 0 表示失败。`main` 返回的值就是退出状态，`exit` 和 `return` 的关系在[14.3.1 终止程序](/教程/正文/语法和标准库/14_文本转换_错误与程序生命周期/14_3_程序生命周期/14_3_1_终止程序)里讲过；`argv` 和 `getenv` 的读取在[14.3.2 环境访问](/教程/正文/语法和标准库/14_文本转换_错误与程序生命周期/14_3_程序生命周期/14_3_2_环境访问)里讲过。

::: terminal title="zsh - 退出状态"

```text
$ ./build/args --fail
argc = 2
argv[0] = [./build/args]
argv[1] = [--fail]
$ echo $?
3
$ ./build/args x && echo "succeeded"
argc = 2
argv[0] = [./build/args]
argv[1] = [x]
succeeded
$ ./build/args --fail && echo "not printed"
argc = 2
argv[0] = [./build/args]
argv[1] = [--fail]
$ ./build/args --fail || echo "failed"
argc = 2
argv[0] = [./build/args]
argv[1] = [--fail]
failed
$ true && false || echo "third runs"
third runs
```

:::

`&&` 左边的命令成功才执行右边，`||` 左边的命令失败才执行右边。两者可以连用，`true && false || echo "third runs"` 按从左到右的顺序结合：`true && false` 的结果是失败，于是执行 `||` 后面的 `echo`。

`echo $?` 必须在目标命令之后立刻执行，中间再跑任何一条命令，`$?` 就换成了那条命令的状态。shell 自身对找不到的命令返回 127，对找到了但没有执行权限的文件返回 126，这两个数是 shell 约定，不是程序返回的。

::: concept dev-cmdline-exit-status title="退出状态是程序报告成败的标准渠道"

程序用退出状态向调用者报告成功或失败，0 为成功，非 0 为失败。构建工具、测试框架和持续集成都靠这个值判断下一步：Make 执行一条构建命令时，命令返回非 0 就停下，不再往下做；CTest 按测试程序的退出状态判定通过或失败；持续集成按整个作业最后一条命令的状态决定这次构建算不算成功。程序在自己的 `main` 里返回 `EXIT_FAILURE`，或者调用 `exit(1)`，就是在向这些工具报告失败。

:::

## 6. 重定向与管道

### 6.1 三个标准流

每个程序启动时都连着三个流：标准输入 (standard input)、标准输出 (standard output) 和标准错误 (standard error)，它们是 C 程序里 `stdin`、`stdout`、`stderr` 这三个 `FILE *` 的另一端（[13.1 I/O 流](/教程/正文/语法和标准库/13_输入输出/13_1_IO流)已经讲过这三者的用法）。按约定分别编号为 0、1、2。默认情况下三者都连在终端上：程序从键盘读，正常输出和错误信息都打印到屏幕。重定向 (redirection) 改变这些连接，管道 (pipe) 把一个程序的输出接到另一个程序的输入。

`>` 把标准输出写入文件，文件已存在时先清空；`>>` 追加到末尾；`<` 把文件接到标准输入；`2>` 把标准错误写入文件。`2>&1` 表示让标准错误指向标准输出当前所在的地方。

### 6.2 重定向

`upper.c` 从标准输入逐字节读取，转成大写后写到标准输出：

```c
#include <ctype.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int c;
    while ((c = getchar()) != EOF) {
        if (putchar(toupper((unsigned char)c)) == EOF) {
            perror("upper");
            return EXIT_FAILURE;
        }
    }
    if (ferror(stdin)) {
        perror("upper");
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

文件在 `code/开发与工程基础/2_命令行与目录操作/upper.c`。`toupper` 的实参先转成 `unsigned char`，因为字符分类函数对负值的行为没有保证，而 `getchar` 返回的 `EOF` 是负数。编译之后可以这样用：

::: terminal title="zsh - 重定向"

```text
$ gcc -std=c17 -Wall -Wextra -o build/upper src/upper.c
$ ./build/upper < text.txt | wc -l
15
$ ./build/upper < text.txt > build/out.txt
$ head -n 3 build/out.txt
THE CAT SAT ON THE MAT.
THE CAT SAT ON THE MAT.
THE CAT SAT ON THE MAT.
$ ./build/upper < text.txt >> build/out.txt
$ wc -l build/out.txt
30 build/out.txt
$ wc -l < text.txt
15
$ wc -l text.txt
15 text.txt
```

:::

第一次把 `text.txt` 接到标准输入，输出经管道交给 `wc -l`，得到 15 行。第二次写到 `build/out.txt`，第三次用 `>>` 追加，行数变成 30。最后两条对比了有无重定向的区别：`wc -l < text.txt` 只拿到标准输入，没有文件名可打印，只输出数字；`wc -l text.txt` 拿到的是参数，所以连名字一起打印。

::: warning 输入和输出写成同一个文件会清空它

`./upper < same.txt > same.txt` 里的 `>` 在命令启动前就把 `same.txt` 清空，程序随后读到的是空文件。实测这条命令之后 `same.txt` 的大小是 0。需要就地处理时先把结果写到另一个文件，再改名。

:::

### 6.3 诊断与 `2>&1` 的顺序

编译器把错误和警告写到标准错误。只写 `>` 时，诊断仍然出现在屏幕上，文件里什么也没有：

::: terminal title="zsh - 诊断写入文件"

```text
$ gcc -std=c17 -Wall -Wextra -o build/bad src/bad.c 2> build.log
$ grep -c error build.log
2
$ gcc -std=c17 -Wall -Wextra -o build/bad src/bad.c > stdout.log
src/bad.c: In function ‘main’:
src/bad.c:5:17: error: ‘count’ undeclared (first use in this function)
    5 |     int total = count + 1;
      |                 ^~~~~
src/bad.c:5:17: note: each undeclared identifier is reported only once for each function it appears in
src/bad.c:6:26: error: expected ‘;’ before ‘return’
    6 |     printf("%d\n", total)
      |                          ^
      |                          ;
    7 |     return 0;
      |     ~~~~~~
$ wc -c stdout.log
0 stdout.log
```

:::

第一次用 `2>` 把标准错误存进 `build.log`，`grep -c error` 数出两行含 `error` 的诊断（`note:` 那一行不含这个词）。第二次用 `>` 只改了标准输出，诊断照常打印在屏幕上，`stdout.log` 是空文件。编译器输出的完整诊断可以在 `bad.c` 上重跑一次得到，`bad.c` 在 `code/开发与工程基础/2_命令行与目录操作/bad.c`，里面故意留了两处错误，不要照抄。

要让标准输出和标准错误进同一个文件，必须把 `2>&1` 写在 `>` 后面。重定向按从左到右的顺序处理，顺序反过来效果就不同。用下面这个程序观察：

```c
#include <stdio.h>

int main(void) {
    printf("stdout line\n");
    fflush(stdout);
    fprintf(stderr, "stderr line\n");
    return 0;
}
```

这个程序在 `code/开发与工程基础/2_命令行与目录操作/mix.c`，先写标准输出并刷新，再写标准错误，两者的先后顺序是确定的。用 `gcc -std=c17 -Wall -Wextra -o build/mix src/mix.c` 编译之后，对比两种写法：

::: compare left-title="先复制标准输出再改向" right-title="先改标准输出再复制"

```text
$ ./build/mix 2>&1 > build/only.txt
stderr line
$ cat build/only.txt
stdout line
```

---

```text
$ ./build/mix > build/both.txt 2>&1
$ cat build/both.txt
stdout line
stderr line
```

:::

第一组先执行 `2>&1`，此时标准输出还指着终端，标准错误也复制成指向终端；随后 `>` 把标准输出改到文件，标准错误留在终端，所以屏幕上只剩 `stderr line`，文件里只有 `stdout line`。第二组先执行 `>`，标准输出指向文件，`2>&1` 再让标准错误复制标准输出的去向，于是两者都进文件。不写文件时，`2>&1 | cat` 先把标准错误并到标准输出，再整体接到管道，两行都打印出来。

`/dev/null` 是一个丢弃所有写入的设备文件，用来屏蔽不需要的输出。`./mix > /dev/null` 只留下标准错误，`./mix 2> /dev/null` 只留下标准输出，`./mix > /dev/null 2>&1` 则什么都不打印。屏蔽输出不会改变退出状态：`./args --fail > /dev/null 2>&1` 之后 `$?` 仍是 3。

### 6.4 管道

竖线 `|` 把左边程序的标准输出接到右边程序的标准输入。管道可以串联任意多段，每一段都以前一段的输出为输入。下面这条命令统计 `text.txt` 中出现次数最多的五个整行：

::: terminal title="zsh - 管道统计"

```text
$ cat text.txt | ./build/upper | sort | uniq -c | sort -rn | head -n 5
      5 THE CAT SAT ON THE MAT.
      4 THE DOG SAT ON THE LOG.
      3 A FOX RUNS FAST.
      2 A BIRD FLIES HIGH.
      1 BEES HUM.
```

:::

逐段看：`cat` 输出文件内容；`./build/upper` 转成大写（大写之后同样的行才会被算作同一行）；`sort` 把相同的行排到一起；`uniq -c` 合并相邻的重复行并计数；`sort -rn` 按计数从大到小排序；`head -n 5` 取前五行。去掉 `upper` 那一段，大小写不同的行会被分开统计，结果就不一样：

::: terminal title="zsh - 不转换大小写的结果"

```text
$ sort text.txt | uniq -c | sort -rn | head -n 5
      4 The dog sat on the log.
      4 The cat sat on the mat.
      3 A fox runs fast.
      2 A bird flies high.
      1 the cat sat on the mat.
```

:::

管道最后的退出状态是最后一条命令的状态，前面某一段失败不会自动让整条管道失败：

::: terminal title="zsh - 管道的退出状态"

```text
$ false | true
$ echo $?
0
$ true | false
$ echo $?
1
```

:::

需要检查整条管道的成败时，bash 提供 `set -o pipefail`，它让管道在任意一段失败时返回失败，后面的脚本会用 `set -eu` 配合它。本页的脚本示例只用到单条命令，暂不需要。

<Quiz
  :options="[
    { label: '编译器把诊断写到了标准错误，而 > 只改标准输出', value: 'A' },
    { label: '编译器忽略了重定向，直接写终端', value: 'B' },
    { label: 'gcc 在编译失败时不会创建文件', value: 'C' },

  ]"

>

<template #question>

</template>

正确答案是 **A**。诊断走标准错误（编号 2），`>` 只重定向标准输出（编号 1）。要把诊断也存进文件，写成 `2> out.txt` 或 `> out.txt 2>&1`。C 也错，文件在命令启动前就被创建了，只是没有内容写入。

::: generate dev-cmdline-redirect-order kind=explanation concepts=dev-cmdline-exit-status

面向刚接触重定向的读者，用 mix 程序的两次运行逐行解释 `2>&1` 与 `>` 的先后顺序：说明每个重定向符号执行时改变了哪个流、为什么左边的命令会把标准错误留在终端，并解释 `/dev/null` 只改变输出去向、不改变退出状态。

:::

## 7. 把命令写成脚本

反复执行的一串命令可以存进文件，交给 shell 一次执行。这样的文件称为脚本 (script)。脚本第一行的 `#!/bin/sh` 指定用哪个解释器运行它；`set -e` 让脚本在任意一条命令失败时立即停止，避免带着错误继续往下跑：

::: code-group

```text [build.sh]
#!/bin/sh
# build.sh：编译本目录下的两个程序并试运行
set -e
mkdir -p build
gcc -std=c17 -Wall -Wextra -o build/hello src/hello.c
gcc -std=c17 -Wall -Wextra -o build/args src/args.c
./build/hello
./build/args first "second argument"
```

```text [check.sh]
#!/bin/sh
set -e
gcc -std=c17 -Wall -Wextra -o build/bad src/bad.c
echo "编译成功"
```

:::

两个脚本都在 `code/开发与工程基础/2_命令行与目录操作/`。`build.sh` 用相对路径，必须在包含 `src` 和 `build` 的目录里运行。新建的文件默认没有执行权限，直接运行会得到 `Permission denied`，退出状态 126；`sh 脚本名` 让 shell 读文件执行，不需要执行权限：

::: terminal title="zsh - 运行脚本"

```text
$ cat build.sh
#!/bin/sh
# build.sh：编译本目录下的两个程序并试运行
set -e
mkdir -p build
gcc -std=c17 -Wall -Wextra -o build/hello src/hello.c
gcc -std=c17 -Wall -Wextra -o build/args src/args.c
./build/hello
./build/args first "second argument"
$ ./build.sh
bash: ./build.sh: Permission denied
$ echo "rc=$?"
rc=126
$ sh build.sh
Hello, C!
argc = 3
argv[0] = [./build/args]
argv[1] = [first]
argv[2] = [second argument]
$ chmod +x build.sh
$ ./build.sh
Hello, C!
argc = 3
argv[0] = [./build/args]
argv[1] = [first]
argv[2] = [second argument]
```

:::

`chmod +x` 加上执行权限之后，`./build.sh` 就能直接运行，脚本第一行的 `#!/bin/sh` 也随之生效。`set -e` 的作用在 `check.sh` 上看得清楚：编译失败，脚本立刻结束，后面的 `echo` 没有执行，脚本的退出状态是 1：

::: terminal title="zsh - set -e"

```text
$ sh check.sh
src/bad.c: In function ‘main’:
src/bad.c:5:17: error: ‘count’ undeclared (first use in this function)
    5 |     int total = count + 1;
      |                 ^~~~~
src/bad.c:5:17: note: each undeclared identifier is reported only once for each function it appears in
src/bad.c:6:26: error: expected ‘;’ before ‘return’
    6 |     printf("%d\n", total)
      |                          ^
      |                          ;
    7 |     return 0;
      |     ~~~~~~
$ echo "rc=$?"
rc=1
```

:::

把 `check.sh` 复制一份，删掉 `set -e` 那一行再运行，结果完全不同：编译照样失败，后面的 `echo` 照样执行，脚本最后返回 0，调用它的工具会以为构建成功。实测这次 `编译成功` 打印到标准输出，十一行诊断留在标准错误里，退出状态是 0。编译、测试、部署的脚本都应当加上 `set -e`。

脚本每次运行都重新编译全部文件，哪怕只改了一个。这段逻辑在工程里交给构建工具，[第 8 章](/教程/正文/开发与工程基础/8_构建图与Make)的 Make 会按文件时间决定哪些步骤需要重跑，不必每次从头来。

::: tip Windows 上保存脚本用 LF 换行

在 Windows 编辑器里把 `#!/bin/sh` 的脚本存成 CRLF，拿到 Linux 上执行会报 `cannot execute: required file not found`。第 1 章的 `.editorconfig` 里 `end_of_line = lf` 就是为这件事准备的；用 `sh 脚本名` 运行能绕过，但脚本里其他命令仍可能读到多余的 `\r`。

:::

## 8. PowerShell 对照

Windows 自带的 shell 是 PowerShell，命令名和选项与 bash 完全不同，但要做的事一一对应。下表是在本机 PowerShell 7.6 上逐条核对过的写法：

| 用途 | bash | PowerShell |
| --- | --- | --- |
| 打印当前目录 | `pwd` | `Get-Location`（别名 `pwd`） |
| 列出目录内容 | `ls`、`ls -a`、`ls -l` | `Get-ChildItem`（别名 `ls`）、`-Force`、`Format-List` |
| 切换目录 | `cd 目录` | `Set-Location 目录`（别名 `cd`） |
| 建目录（含多级） | `mkdir -p a/b` | `New-Item -ItemType Directory -Path a\b`（加 `-Force` 时已存在的也不报错） |
| 建空文件 | `touch f` | `New-Item -ItemType File -Path f` |
| 复制、移动、删除 | `cp`、`mv`、`rm -r` | `Copy-Item`、`Move-Item`、`Remove-Item -Recurse` |
| 查看文件 | `cat`、`head -n`、`tail -n` | `Get-Content`、`-TotalCount`、`-Tail` |
| 上次的退出状态 | `$?` | `$LASTEXITCODE`（`$?` 只有 True/False） |
| 环境变量 | `$PATH`、`export NAME=值` | `$env:PATH`、`$env:NAME = "值"` |
| 运行当前目录的程序 | `./hello` | `.\hello.exe`（PowerShell 不搜索当前目录） |
| 重定向 | `> f`、`2> f`、`2>&1` | `>`、`2>`、`2>&1`，写法相同 |

`mkdir`、`cp`、`mv`、`rm`、`cat`、`ls`、`cd`、`pwd`、`sort` 在 PowerShell 里都是别名或函数，敲起来和 bash 一样，但参数不同。`ls -a` 这种写法在 PowerShell 里会报错，要看隐藏文件得用 `-Force`。

退出状态的读法差别最大。bash 的 `$?` 直接是数字；PowerShell 的 `$?` 只表示上一条命令成功与否，原生程序（`.exe`）的退出码放在 `$LASTEXITCODE`：

::: terminal title="PowerShell - 退出状态"

```text
PS> .\args.exe --fail
argc = 2
argv[0] = [D:\demo\args.exe]
argv[1] = [--fail]
PS> $?
False
PS> $LASTEXITCODE
3
```

:::

管道的行为也不同。PowerShell 传的是对象，不是字节流：`Get-Content text.txt | .\upper.exe` 会把每一行作为文本写给程序，程序照常处理；但 `uniq -c`、`head` 这类工具在 PowerShell 里没有同名命令，要分别换成 `Group-Object` 和 `Select-Object -First`；`sort` 对应的是 `Sort-Object`。本教程的其余部分以 bash 为准，Windows 读者在 MSYS2 终端里完成这些练习，PowerShell 只用来处理必须用 Windows 工具的事情。
