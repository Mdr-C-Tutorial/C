# 21.7 差分测试与边界验证

`mdr_strspn` 通过了手写的 12 个检查：空串、集合为空、全部命中、前缀命中、一个都不命中，ASCII 范围内的常见情形都在里面。把同一个函数交给标准库对照，只扫 255 个单字节输入，就出来 128 处不一致。手写的用例没有问题，问题是它们全落在 ASCII 范围内，而缺陷恰好只在 0x80 以上的字节上发作。

```c
#include <stdbool.h>
#include <stdio.h>
#include <string.h>

/* 被测试的 mdr_strspn。作者假设「项目里的文本都是英文」，
 * 因而把查找表缩到 128 项，高半区一律当作集合外。 */
size_t mdr_strspn(const char *s, const char *accept) {
    bool in_set[128] = {false};
    size_t n = 0;

    while (*accept != '\0') {
        if ((unsigned char)*accept < 128) {
            in_set[(unsigned char)*accept] = true;
        }
        accept++;
    }
    while (s[n] != '\0' && (unsigned char)s[n] < 128 &&
           in_set[(unsigned char)s[n]]) {
        n++;
    }
    return n;
}
```

手写的 12 个 `expect` 调用全过，差分那一段扫 255 个单字节输入：

这一节把前几节零散的对照测试整理成一套方法：找一个可以依赖的参照实现，把两份结果规范化之后再比较，用穷举和边界值把输入空间铺开，用防护字节和 Sanitizer 抓住越界，失败之后把输入缩小到最小。做完这一节，`mdr_` 库里的每个函数都能有一条秒级跑完、随时可以重复的检验线。

## 1. 差分测试

差分测试（differential testing）的做法是把同一组输入交给两个应当等价的实现，比较输出。它不判断「正确结果是什么」，只判断「两份实现是否一致」。这个做法绕开了测试里最难的一环：测试预言（test oracle），也就是怎样知道期望值。判断两个 `strspn` 的结果是否相等，比判断某个结果是否等于 7 容易得多。

McKeeman 在 1998 年用这个方法测试 C 编译器：把同一份程序交给两个编译器，看生成的程序行为是否一致。Csmith 把思路推到极致，随机生成合法的 C 程序再喂给不同编译器，在 GCC 和 LLVM 里找出过几百个缺陷。这两个例子说明差分测试最擅长的场景：有一个可信的参照，被测对象复杂到难以逐条写期望值。

参照实现有三个来源，按可靠性从高到低排：

| 参照 | 例子 | 优点 | 局限 |
| --- | --- | --- | --- |
| 标准库 | `strspn`、`memcmp`、`memmove` | 经过长年检验，行为就是规格本身 | 只覆盖标准里的接口，扩展函数没有 |
| 显然正确的慢版本 | 逐位扫描的 `clz`、逐位置 `memcmp` 的 `memmem` | 任何函数都能写，逻辑一眼看到底 | 慢版本的错误会伪装成被测实现的错误 |
| 另一份构建 | 21.6 的内建版本对回退版本 | 检查两条代码路径结果一致 | 两份都错时查不出来 |

第三种在 [21.6](/教程/正文/开发与工程基础/21_库接口实现练习/21_6_可回退的编译器内建功能) 已经有了：`mdr` 和 `mdr_fallback` 两个库目标编译同一批源文件，一条走内建函数，一条走普通 C。把它们的结果互相比较，保证选择链没有改变语义。这种比较查不出「两条路径都算错了」的情况，但能查出手写回退分支时抄错常量、写反移位方向这类错误，而这正是选择链最容易出的问题。

::: concept mdr-diff-oracle title="差分测试用一致性代替期望值"

差分测试把同一组输入交给被测实现与参照实现，比较两者的输出。它检验的是一致性，不检验绝对正确性：参照实现错了，两份实现会「一致地错」，测试照样通过。选参照时优先用标准库和长期使用的实现；自己写的慢版本只适合标准库覆盖不到的扩展函数，并且要在注释里写清楚它凭什么可信。

:::

## 2. 先规范化再比较

两份实现的输出不能直接比。`strcmp` 的返回值在 glibc 和 UCRT 上就不同：前者返回两个字节之差，后者只返回 -1 和 1。用 `strcmp` 做过比较的人都见过这类问题，而差分测试里它会被误判成缺陷。

```c
#include <stdio.h>
#include <string.h>

static int sign(int value) {
    if (value < 0) {
        return -1;
    }
    if (value > 0) {
        return 1;
    }
    return 0;
}

int main(int argc, char *argv[]) {
    const char *lhs = argc > 1 ? argv[1] : "apple";
    const char *rhs = argc > 2 ? argv[2] : "apricot";

    printf("strcmp(\"%s\", \"%s\") = %d\n", lhs, rhs, strcmp(lhs, rhs));
    printf("sign                   = %d\n", sign(strcmp(lhs, rhs)));
    return 0;
}
```

```text
sign                   = -1
$ ./norm2 apricot apple
```

第一行两台机器一个是 -2、一个是 -1，第三行一个是 2、一个是 1，而 `sign` 那一行逐行相同。比较 `strcmp` 的返回值时只能比符号，规格只保证了这个。

实参必须从 `argv` 来，不能写成 `strcmp("apple", "apricot")` 这样的常量调用。常量实参上 GCC 在编译期就把结果折叠成 -1，两台机器看起来又一样了，负值的具体数值这个差异就躲过去了。[21.1](/教程/正文/开发与工程基础/21_库接口实现练习/21_1_范围_命名与契约) 里 `strlen("abc")` 被折叠成 3 是同一件事。差分测试的输入都来自运行时数据，就是为了不让编译器替你把两边「统一」掉；仍有疑问时给参照那一侧加 `-fno-builtin`。

规范化要处理的差异有四类：

| 差异 | 处理办法 |
| --- | --- |
| 比较函数的具体返回值 | 只比符号。`strcmp`、`strncmp`、`memcmp` 的规格只规定正负零 |
| 查找函数返回的指针 | 换成相对起点的偏移，`NULL` 换成 -1。`mdr_strstr`、`mdr_strchr`、`mdr_memchr`、`mdr_memmem` 都要这么处理 |
| 复制函数的目标缓冲区 | 比较整块缓冲区，不能只看到空字符为止。`strncpy` 补不补空字符、`strlcpy` 有没有多写一个字节，都藏在终止符后面 |
| `errno` 与未指定的内容 | 不比较。成功时 `errno` 不保证被清除；`strtok` 的内部状态地址、`qsort` 相等元素的顺序也不属于必须一致的部分 |

这些差异的写法集中放在 `tests/diff_util.h` 里：

```c
/* 把任意整数规范化成 -1、0 或 1，只保留符号。 */
int diff_sign(int value);

/* 把查找函数返回的指针换成相对 base 的偏移；NULL 返回 -1。 */
long diff_offset(const void *base, const void *found);

/* 报告一次不一致：打印说明、输入与期望/实际值，并计入失败数。 */
int diff_report(const char *what, const void *input, size_t input_len,
                long expected, long actual);

/* 打印「套件: 总数 comparisons, 失败数 failed」，有失败返回 1。 */
int diff_summary(const char *suite);
```

`diff_offset` 把指针和偏移的转换收在一处，`diff_report` 把失败信息收在一处。比较函数只需要写「期望是什么、实际是什么」，格式化留给工具。`diff_report` 只在前 5 次打印细节，之后只计数，因为一个系统性缺陷可能让上千个输入同时失败，全打出来反而看不清第一个。

## 3. 输入从哪里来

手写用例的问题是覆盖面取决于作者。生成输入有三个方向，代价和覆盖面各不相同。

### 3.1 穷举小输入空间

字符串函数只要字母表小、长度短，总数就完全可控。字母表取 `{'a','b','c'}`，haystack 长度不超过 4，needle 长度不超过 2：

```c
/* 在字母表上按字典序生成下一个等长字符串；全部回绕时返回 0。 */
static int next_string(char *buf, size_t len, const char *alphabet) {
    size_t alpha_len = strlen(alphabet);

    for (size_t i = len; i > 0; i--) {
        const char *pos = strchr(alphabet, buf[i - 1]);

        if ((size_t)(pos - alphabet) + 1 < alpha_len) {
            buf[i - 1] = pos[1];
            return 1;
        }
        buf[i - 1] = alphabet[0];
    }
    return 0;
}
```

haystack 有 1+3+9+27+81 = 121 个，needle 有 1+3+9 = 13 个，配对 1573 组，每组比较六个查找函数，一共 9438 次比较。`diff_string` 另外单独扫一遍全部 256 个单字节输入做 haystack（needle 取 `"abc"` 与 `"a"` 两种），再加 3072 次比较，总计 12510 次。这些数字来自测试程序自己的计数，不需要手工维护。

`mdr_memmove` 的重叠复制用 16 字节缓冲区穷举：目标偏移、源偏移、字节数各取 0 到 15，只保留两个区域都落在缓冲区内的组合，共 1751 组。每组先填成 `01 02 … 10`（第 i 个字节是 i+1），分别调用 `memmove` 和 `mdr_memmove`，再比较整块 16 个字节。

```c
for (size_t dest = 0; dest < 16; dest++) {
    for (size_t src = 0; src < 16; src++) {
        for (size_t count = 0; count < 16; count++) {
            unsigned char a[16];
            unsigned char b[16];

            if (dest + count > 16 || src + count > 16) {
                continue;
            }
            for (size_t i = 0; i < 16; i++) {
                a[i] = (unsigned char)(i + 1u);
                b[i] = a[i];
            }
            memmove(a + dest, a + src, count);
            mdr_memmove(b + dest, b + src, count);
            if (memcmp(a, b, 16) != 0) {
                diff_report("memmove", b, 16, (long)dest, (long)src);
            } else {
                diff_ok();
            }
        }
    }
}
```

这段循环把复制方向这个最容易写错的地方全展开了一遍。`mdr_memmove` 的实现在 `dest < src` 时从低地址往高地址复制，否则反过来；1751 组输入把两种方向、重叠与不重叠、零长度都覆盖到了。

### 3.2 按位穷举

位函数没有字符串那样的「长度」，但输入范围不大。`mdr_clz_u32`、`mdr_ctz_u32`、`mdr_popcount_u32` 用 0 到 0xFFFF 的 16 位输入各跑一遍：

```c
/* 参照：显然正确的慢版本，每一位单独看。 */
static unsigned slow_clz_u32(uint32_t x) {
    unsigned n = 0;

    if (x == 0) {
        return 32;
    }
    for (uint32_t bit = 0x80000000u; (x & bit) == 0; bit >>= 1) {
        n++;
    }
    return n;
}
```

65536 个输入各比较三次，196608 次比较在 MinGW 构建里占 0.04 秒，glibc 上是 0.02 秒。这里用慢版本而不用 `__builtin_clz`，是因为内建函数和 21.6 的选择链走的是同一条路，用它当参照查不出选择链本身的错误。慢版本每一位单独看，逻辑短到能一眼验证，这正是参照实现该有的样子。

### 3.3 固定种子的随机输入

长度、内容、改动位置都由种子决定的随机数生成。字符串穷举到不了的组合（长 haystack、needle 出现在末尾、大量重复字节）靠随机补上。随机测试的细节在第 6 节。

三个方向的取舍：穷举的覆盖面最大但受输入空间限制，边界值最省时间但只覆盖极值点，随机输入能铺满任意长度、代价是每次只抽样。

小范围穷举还有一个隐含假设：缺陷在短输入上就会出现。字符串函数确实如此，差一错误、终止条件、扫描边界在长度三五时都能触发。`mdr_memmem` 这类需要 needle 落在特定位置才出错的实现，穷举到 needle 长度为 2 还不够，这是第 8 节用模糊测试补位的原因。

## 4. 边界值

边界值分析（boundary value analysis）是另一条独立的思路：不等概率地铺输入空间，而是专门挑参数取极值、取相邻值的地方。长度参数取 0、1、`n-1`、`n`、`n+1`，数值取 0、1、2 的幂、2 的幂加减一、全 1，字符串取空串、单字符、终止符恰好在缓冲末尾。这些位置是循环条件和比较运算集中出错的地方。

| 函数 | 边界值 |
| --- | --- |
| `mdr_strncpy`、`mdr_strlcpy` | `count` 为 0、1；源串长度等于 `count-1`、`count`、`count+1` |
| `mdr_strncat`、`mdr_strlcat` | 目标已有内容恰好填满；剩余空间为 0、1、刚好装下源串 |
| `mdr_strspn`、`mdr_strcspn` | 集合为空；首字符在集合内外；整个串都在集合内 |
| `mdr_strstr`、`mdr_memmem` | needle 为空；needle 比 haystack 长；命中在开头、末尾、不命中 |
| `mdr_clz_u32`、`mdr_ctz_u32` | 0、1、最高位、最低位、`UINT32_MAX` |
| `mdr_bit_ceil_u32` | 0、1、2 的幂、2 的幂加一、`0x80000001` |
| `mdr_ckd_add_size` | 0、1、`SIZE_MAX`、`SIZE_MAX - 1`、两数之和恰好等于 `SIZE_MAX` |
| `mdr_align_up_size` | 已对齐、差一字节、`align` 为 1、`align` 为最大值 |

边界值与穷举是互补的。穷举保证常见情形不漏，边界值保证极端情形不漏，两者的运行时间都在毫秒级，没有理由只做一个。

### 4.1 边界值与内存布局

字符串函数读到哪里、写到哪里，只有把数据放在容器的边缘上才看得出来。缓冲区末尾留一个空字符的余量，越界读就会落进那块余量里，什么都不会发生；按实际长度精确分配，越界的那一个字节才会踩到不该踩的地方。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void) {
    char *p = malloc(5);

    memcpy(p, "hello", 5);
    printf("length = %zu\n", strlen(p));
    free(p);
    return 0;
}
```

`malloc(5)` 拿到 5 个字节，5 个字母刚好没有终止空字符。在 Linux 上用 ASan 构建：

```c [tests/diff_util.c]
int diff_guard_init(diff_guard *guard, size_t size) {
    guard->raw = (unsigned char *)malloc(size + 2 * DIFF_GUARD);
    if (guard->raw == NULL) {
        return -1;
    }
    for (size_t i = 0; i < DIFF_GUARD; i++) {
        guard->raw[i] = 0xA5;
        guard->raw[DIFF_GUARD + size + i] = 0xA5;
    }
    guard->data = guard->raw + DIFF_GUARD;
    guard->size = size;
    return 0;
}

int diff_guard_check(const diff_guard *guard, const char *what) {
    const unsigned char *front = guard->raw;
    const unsigned char *back = guard->raw + DIFF_GUARD + guard->size;

    diff_total++;
    for (size_t i = 0; i < DIFF_GUARD; i++) {
        if (front[i] != 0xA5) {
            diff_failed++;
            printf("GUARD %s: front[%zu] is %02X, expected A5\n", what, i,
                   front[i]);
            return 1;
        }
    }
    for (size_t i = 0; i < DIFF_GUARD; i++) {
        if (back[i] != 0xA5) {
            diff_failed++;
            printf("GUARD %s: data[%zu] is %02X, expected A5\n", what,
                   guard->size + i, back[i]);
            return 1;
        }
    }
    return 0;
}
```

## 5. 防护字节

ASan 需要编译器支持和运行库。写作时用到的 Windows 工具链里，MinGW-w64 GCC 13.2 没有 ASan 运行库，链接时报 `cannot find -lasan`；SignalX 上的 GCC 14.2 有，但它也不是每个开发环境都具备的。防护字节（guard bytes）不依赖任何工具，在纯标准 C 里就能用。

思路很简单：在数据区前后各放一段固定内容的哨字节，调用被测函数，再把哨字节逐个检查一遍。任何一段被改写，就说明函数写到了不该写的地方。判定值统一用 `0xA5`，这个字节既不是 0 也不是常见的可打印字符，被误写成什么都很显眼。这套东西封装在 `tests/diff_util.h` 的 `diff_guard` 里，实现在 4.1 节末尾的 code-group 中。

用它检查 `mdr_strlcpy` 时，数据区的长度按 `dsize` 精确分配，缓冲区末尾的哨字节紧贴着允许写入的最后一个位置。注入一个「多写一个字节」的缺陷：

```c
/* 注入的缺陷：多写一个字节。正确版本见 src/mdr_ext.c。 */
static size_t buggy_strlcpy(char *dst, const char *src, size_t dsize) {
    size_t len = strlen(src);

    if (dsize > 0) {
        size_t copy = len < dsize - 1 ? len : dsize - 1;

        memcpy(dst, src, copy);
        dst[copy] = '\0';
        dst[copy + 1] = '\0';
    }
    return len;
}
```

对五组目标长度分别调用，再对两组 `mdr_strlcat` 调用，每次调用后检查哨字节：

::: terminal title="zsh - diff_ext"

```text
$ ./diff_ext
GUARD strlcpy: data[1] is 00, expected A5
GUARD strlcpy: data[2] is 00, expected A5
GUARD strlcpy: data[6] is 00, expected A5
GUARD strlcpy: data[6] is 00, expected A5
diff_ext: 10 comparisons, 4 failed
```

:::

`data[1]` 是数据区里紧跟末尾的字节，对第一组 `dsize` 为 1 的调用来说，允许写的只有 `data[0]`。输出的位置直接告诉人缺陷在哪：多写的那个字节落在 `data[dsize]`，也就是 `dst[copy + 1]`。修好之后同一份测试报告 14 次比较全部通过。Windows 上的输出逐行相同。

计数从 14 掉到 10 的原因是防护检查失败后没有再比结果：四次失败的调用各少算一次结果比较。

防护字节和 ASan 的取舍很清楚：

| 手段 | 需要什么 | 能发现 | 发现不了 |
| --- | --- | --- | --- |
| 防护字节 | 标准 C，哪里都能编译 | 写到数据区前后的越界写 | 读取越界；落到更远处的写 |
| ASan | 编译器支持与运行库 | 任意地址的越界读和写 | 两块普通内存之间的逻辑错误 |

防护字节查不出越界读，因为数据后面的哨字节只在写越过末尾时才被碰到，而读越界不会改动任何字节。要让越界读暴露出来，只能靠 ASan 这样的影子内存，或者把数据放在恰好等长的分配里等它自己出错。两者叠在一起用：防护字节在日常构建里跑，ASan 构建（`build-asan/`）在提交前跑一遍。

正确答案是 **A、B**。数据区必须按实际允许的长度精确分配，多留一个字节的余量就会把越界写吸收掉；哨字节要在调用后检查，不检查等于没放。C 不够：`strlcpy` 的返回值是源串长度，多写的那一字节不影响返回值。D 是可选的加强手段，不是防护字节本身能工作的前提。

`mdr_strlcpy` 的测试也展示了「比较整个缓冲区」的用处。只比较返回值和字符串内容，多写的那一个字节永远看不见；内容检查到终止符就停了，终止符之后的东西不在视野内。

::: details diff_ext 的完整测试函数

```c
static void check_strlcpy(const char *dst0, const char *src) {
    size_t dsize = strlen(dst0) + 1;
    diff_guard guard;

    if (diff_guard_init(&guard, dsize) != 0) {
        return;
    }
    memcpy(guard.data, dst0, dsize);
    size_t n = mdr_strlcpy((char *)guard.data, src, dsize);

    if (diff_guard_check(&guard, "strlcpy") == 0) {
        size_t want = strlen(src) < dsize - 1 ? strlen(src) : dsize - 1;

        if (n == strlen(src) && memcmp(guard.data, src, want) == 0) {
            diff_ok();
        } else {
            diff_report("strlcpy result", guard.data, dsize, (long)strlen(src),
                        (long)n);
        }
    }
    diff_guard_free(&guard);
}
```

目标缓冲区的长度取 `strlen(dst0) + 1`，也就是恰好装下原来的内容。哨字节检查通过后，再比较返回值和复制的前 `min(strlen(src), dsize - 1)` 个字节。每次调用计两次比较，五组 `strlcpy` 加两组 `strlcat` 一共 14 次。哨字节检查失败的那一次只剩一次比较，所以注入缺陷后总数从 14 掉到 10。

## 6. 随机测试与可重现

穷举覆盖的是小空间，边界值覆盖的是极端点，剩下的大片区域交给随机输入。随机测试有两个必须解决的问题：随机数从哪来，以及失败之后怎么复现。

`rand()` 不能用于这个目的。标准只规定它返回 0 到 `RAND_MAX` 之间的值，序列完全由实现决定：同一份程序、同一个种子，在不同 C 库上得到的数列不同。在本机分别用 MinGW 的 UCRT 和 glibc 跑 `srand(1); rand()` 的前五个值：

自己实现一个小生成器就解决了。splitmix64 只有十几行，状态是一个 `uint64_t`：

```c
uint64_t diff_random(uint64_t *state) {
    uint64_t z = (*state += 0x9E3779B97F4A7C15ULL);

    z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9ULL;
    z = (z ^ (z >> 27)) * 0x94D049BB133111EBULL;
    return z ^ (z >> 31);
}
```

它只用 64 位无符号整数的加、乘、移位和异或，全部由 C 标准精确定义，任何平台上同一个种子给出同一串数。一个最小的驱动程序把种子和个数从命令行读进来，逐行打印：

```c
int main(int argc, char *argv[]) {
    uint64_t state = argc > 1 ? (uint64_t)strtoull(argv[1], NULL, 0) : 1u;
    int count = argc > 2 ? atoi(argv[2]) : 5;

    for (int i = 0; i < count; i++) {
        printf("%016llx\n", (unsigned long long)splitmix64(&state));
    }
    return 0;
}
```

随机测试程序的形式固定为：从命令行读种子，把种子打印出来，失败时把种子和输入一起打印。

```c
int main(int argc, char *argv[]) {
    uint64_t seed = 1;
    int rounds = 1000;
    uint64_t state;

    for (int i = 1; i < argc; i++) {
        if (strcmp(argv[i], "--seed") == 0 && i + 1 < argc) {
            seed = diff_parse_seed(argv[++i]);
        } else if (strcmp(argv[i], "--rounds") == 0 && i + 1 < argc) {
            rounds = atoi(argv[++i]);
        }
    }
    printf("seed = 0x%llX, rounds = %d\n", (unsigned long long)seed, rounds);

    state = seed;
    for (int round = 0; round < rounds; round++) {
        size_t len = (size_t)(diff_random(&state) % 65u);
        unsigned char lhs[64];
        unsigned char rhs[64];
        int want;
        int got;

        fill_random(lhs, len, &state);
        memcpy(rhs, lhs, len);
        if (len > 0 && diff_random(&state) % 3u == 0) {
            size_t pos = (size_t)(diff_random(&state) % len);

            rhs[pos] = (unsigned char)(rhs[pos] ^ 0x80u);
        }
        want = diff_sign(memcmp(lhs, rhs, len));
        got = diff_sign(mdr_memcmp(lhs, rhs, len));
        if (want != got) {
            diff_report("memcmp", lhs, len, want, got);
        } else {
            diff_ok();
        }
    }
    return diff_summary("diff_memory");
}
```

每轮先随机决定长度（0 到 64），再填内容，然后有三分之一的概率把一个字节的最高位翻转，制造不相等。内容生成里刻意安排 `0x00` 和 `0x80` 以上的字节：`fill_random` 每四个字节里固定放一个 `0x00`、一个 `0x80`，因为纯随机字节碰到这两类值的概率不足以稳定触发符号问题。

## 7. 失败报告与输入缩小

失败报告的目标是让人不进调试器就能判断缺陷位置。一条有用的报告至少要有四项：被比较的函数名、输入的完整字节、期望值、实际值。输入如果是一段文本，要同时给出可读形式和十六进制；可读形式能看出结构，十六进制能看出 0x80 以上的字节。

`diff_report` 的前 5 次调用打印细节，这正是为了让第一处失败足够显眼。后面几百条失败往往是同一个缺陷的不同表现，重复打印只会把第一条冲走。

原始输入通常比需要的长。一段 64 字节的随机数据触发的缺陷，可能一个字节就够重现。把输入缩小能让人看到缺陷的本质，也方便把它写进回归测试。缩小器的思路是反复做「删掉一个字节」和「把这个字节换成一个更简单的值」两种尝试，只要输入仍然触发失败就保留修改：

```c
size_t diff_shrink(unsigned char *data, size_t len, diff_fail_fn fails,
                   void *ctx) {
    size_t i = 0;

    while (i < len) {
        unsigned char saved = data[i];

        memmove(data + i, data + i + 1, len - i - 1);
        if (fails(data, len - 1, ctx) != 0) {
            len--;
            continue;
        }
        memmove(data + i + 1, data + i, len - i - 1);
        data[i] = 0x00;
        if (fails(data, len, ctx) != 0) {
            i++;
            continue;
        }
        data[i] = (unsigned char)'a';
        if (fails(data, len, ctx) != 0) {
            i++;
            continue;
        }
        data[i] = saved;
        i++;
    }
    return len;
}
```

`fails` 是调用方提供的判定函数，返回非零表示这份输入仍然让两份实现不一致。删除成功时长度减一、下标不动，因为新挪到 `i` 位置的字节还没试过；替换成功时下标前进一位。两次尝试都失败就恢复原值，去看下一个字节。

拿一段 64 字节、全部带最高位的输入，对第 6 节那个按 `char` 比较的 `memcmp` 缺陷调用缩小器。判定函数从输入派生出一份「翻转末字节最高位」的副本，再比较两份 `memcmp` 的符号：

```c
/* 判定：这份输入上两份实现是否仍不一致（只比符号）。 */
static int still_fails(const unsigned char *data, size_t len, void *ctx) {
    unsigned char rhs[256];
    size_t n = len < sizeof rhs ? len : sizeof rhs;

    (void)ctx;
    memcpy(rhs, data, n);
    if (n > 0) {
        rhs[n - 1] = (unsigned char)(rhs[n - 1] ^ 0x80u);
    }
    return diff_sign(memcmp(data, rhs, n)) != diff_sign(buggy_memcmp(data, rhs, n));
}
```

```text
$ ./shrink_demo
```

64 个字节缩到 1 个。缩短的过程很直接：每个字节的最高位都是 1，删掉哪一个都不影响判定，从头部一个个删下去，只剩最后一个字节时删除才失败，于是长度停在 1。接着替换阶段把最后那个字节换成 `0x00`，判定仍然失败：`0x00` 与翻转最高位后的 `0x80` 在无符号比较里是 `0 < 128`，按 `char` 比较却是 `0 > -128`，符号仍然相反。写回归测试时钉这个两字节的对照（`0x00` 与 `0x80`）比钉原来的 64 字节清楚得多。Windows 上的输出逐行相同。

缩小器本身也有代价。每次尝试都要跑一遍失败判定，字符串函数便宜，几千次试下来也是毫秒级；涉及大缓冲区或慢参照的实现要把次数算进去。`fails` 的判定必须和最初发现失败时完全一致，否则缩小器可能把输入改小到另一个缺陷上去，留下一个看着蹊跷、实际无关的用例。

## 8. 模糊测试目标

穷举和随机测试都要自己设计输入的形状。`mdr_memmem` 的缺陷只在 needle 恰好落在 haystack 末尾时才发作，随机生成时碰到的概率不高。[第 14 章](/教程/正文/开发与工程基础/14_覆盖率与模糊测试)介绍的模糊测试（fuzzing）把输入生成交给工具：它从覆盖率反馈里学习什么样的输入能走到更多分支，比随机生成更快地找到这类位置敏感的缺陷。

差分测试正好可以做成一个模糊测试目标（fuzz target）。同一个输入切成两半，前半当 haystack，后半当 needle，两份实现各查一次，比较命中的偏移：

```c
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    size_t haylen;
    size_t neelen;
    const void *got;
    const void *want;
    long got_off;
    long want_off;

    if (size < 2) {
        return 0;
    }
    haylen = size / 2;
    neelen = size - haylen;
    got = mdr_memmem(data, haylen, data + haylen, neelen);
    want = ref_memmem(data, haylen, data + haylen, neelen);
    got_off = got == NULL ? -1 : (long)((const uint8_t *)got - data);
    want_off = want == NULL ? -1 : (long)((const uint8_t *)want - data);
    if (got_off != want_off) {
        fprintf(stderr, "memmem mismatch: hay %zu bytes, needle %zu bytes, "
                        "want offset %ld, got %ld\n",
                haylen, neelen, want_off, got_off);
        abort();
    }
    return 0;
}
```

参照用的是逐位置 `memcmp` 的写法，短到可以逐个条件核对。两份实现的指针来自同一个 `data`，偏移可以直接相减，不需要 `diff_offset`。

Windows 上可以用 Visual Studio 自带的 clang 22（本机是 22.1.3，含 libFuzzer 与 ASan 运行库）。它不在 `PATH` 里，构建前把运行库目录加进去：

## 9. 接入构建

五个差分测试已经由 `file(GLOB ...)` 收进工程，只需要在 `CMakeLists.txt` 里给它们打上标签：

```cmake
file(GLOB MDR_DIFF_TESTS CONFIGURE_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/tests/diff_*.c")
set(MDR_DIFF_SUPPORT "${CMAKE_CURRENT_SOURCE_DIR}/tests/diff_util.c")
if(EXISTS "${MDR_DIFF_SUPPORT}")
    list(REMOVE_ITEM MDR_DIFF_TESTS "${MDR_DIFF_SUPPORT}")
    foreach(diff_src IN LISTS MDR_DIFF_TESTS)
        get_filename_component(diff_name "${diff_src}" NAME_WE)
        add_executable(${diff_name}
            "${diff_src}"
            "${CMAKE_CURRENT_SOURCE_DIR}/tests/check.c"
            "${MDR_DIFF_SUPPORT}"
        )
        target_include_directories(${diff_name} PRIVATE "${CMAKE_CURRENT_SOURCE_DIR}/tests")
        target_link_libraries(${diff_name} PRIVATE mdr)
        add_test(NAME ${diff_name} COMMAND ${diff_name})
        set_tests_properties(${diff_name} PROPERTIES LABELS diff)
    endforeach()
endif()
```

`LABELS diff` 让 `ctest -L diff` 只跑差分测试（[第 11 章](/教程/正文/开发与工程基础/11_自动化测试)的 `ctest` 用法在这里原样适用），单元测试和差分测试可以分开调用。在 Linux 上跑一遍：

五个测试合计 0.02 秒，196608 次比较的位函数测试也没有把总时间拉高。这个量级意味着差分测试可以挂在每次构建上，不必等到提交前才跑。

同一批测试还要在另外两种构建里各跑一次：

1. `-DMDR_SANITIZE=ON`，用 ASan 和 UBSan 的运行库。差分测试本来就是越界最集中的地方，Sanitizer 能在比较的过程中顺带抓住所有越界访问。
2. `-DMDR_NO_BUILTINS=ON`，让内建函数全部回退到普通 C。21.6 的选择链在两条路径上都要和参照实现一致。

```text
$ cmake -S . -B build-asan -DMDR_SANITIZE=ON
$ cmake --build build-asan -j2
$ ctest --test-dir build-asan -L diff
...
100% tests passed, 0 tests failed out of 5
```

MinGW 上没有 ASan 运行库，这一步要在 Linux 或 macOS 上做；普通构建和 `-DMDR_NO_BUILTINS=ON` 的构建在 Windows 上照常可用。

CI 里把这三个构建排进矩阵，[第 18 章](/教程/正文/开发与工程基础/18_持续集成)的做法是直接复制本地命令。不同 C 库提供的参照各不相同：Ubuntu 上是 glibc，Windows 运行器上是 UCRT，macOS 上是 Apple 的 libc。同一个种子在三个平台上跑同一份 `diff_memory`，如果某个库的 `memcmp` 对高位字节的处理和标准有出入，矩阵会立刻显出来。这也是把差分测试放进 CI 最重要的理由：本地永远只有一个参照，CI 才有三个。

::: details 五个差分测试各自覆盖什么

- `diff_string`：穷举长度不超过 4 的 haystack 与长度不超过 2 的 needle，逐个比较 `strchr`、`strrchr`、`strspn`、`strcspn`、`strpbrk`、`strstr`；再单独扫 256 个单字节输入。12510 次比较。
- `diff_memory`：种子驱动的随机长度与内容，比较 `memcmp` 的符号。1000 轮。
- `diff_memmove`：16 字节缓冲区上的重叠复制穷举，比较整块缓冲区。1751 次比较。
- `diff_bits`：0 到 0xFFFF 的 16 位输入，对照逐位扫描的慢版本比较 `clz`、`ctz`、`popcount`。196608 次比较。
- `diff_ext`：`strlcpy`、`strlcat` 的防护字节检查，数据区按 `dsize` 精确分配。14 次比较。

:::
