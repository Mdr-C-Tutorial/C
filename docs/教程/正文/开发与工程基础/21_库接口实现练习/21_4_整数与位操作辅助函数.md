# 21.4 整数与位操作辅助函数

分配器要为请求的字节数找到「不小于 n 的 2 的幂」，文件格式解析要从 4 个字节里组装出一个 32 位整数，往数组里追加元素前要判断 `n * size` 会不会溢出。这几个函数都只有十几行，却很容易落在未定义行为上：移位位数等于类型宽度、有符号数左移溢出、`uint8_t` 参与运算时先被提升成 `int`。这一节按统一规格实现它们，再用穷举、慢速参照实现和性质检查验证结果。

代码接着[21.1](/教程/正文/开发与工程基础/21_库接口实现练习/21_1_范围_命名与契约)搭好的工程写，文件在 `code/开发与工程基础/21_库接口实现练习/`。第一部分已经有的 `mdr_popcount_u32`、`mdr_bswap32` 继续复用，这一节新增的函数都加进 `mdr_bits.h` 和 `src/mdr_bits.c`。

## 1. 无符号运算与移位规则

这一节所有函数只处理无符号类型：`uint32_t`、`uint64_t` 和 `size_t`。无符号整数的算术按 2^N 取模，`UINT32_MAX + 1u` 的结果是 0，这个回落是标准规定的，不是未定义行为。正因如此，判断加法是否溢出不能看结果变没变，要拿加数和上限比。

移位就不一样了。移位位数等于或大于类型宽度是未定义行为，负数移位也是未定义行为；有符号数左移，如果结果超出类型能表示的范围，同样是未定义行为。右移一个负数在 C17 里由实现定义，GCC 和 MSVC 都做算术右移，但本节不依赖这条。

小类型还有一个容易忽略的地方：`uint8_t`、`uint16_t` 在表达式里先被提升为 `int`，运算按 `int` 做，结果也是 `int`。所以 `~x` 对一个 `uint8_t` 得到的是 32 位的取反结果，不是 8 位。

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t byte = 0x0Fu;
    uint16_t word = 0xFFFFu;

    printf("~byte       = %08X\n", (unsigned)~byte);
    printf("byte << 4   = %08X\n", (unsigned)(byte << 4));
    printf("word * word = %08X\n", (unsigned)(word * word));
    printf("sizeof(byte + byte) = %zu\n", sizeof(byte + byte));
    return 0;
}
```


:::

`~byte` 补出了高 24 位；`word * word` 的结果 0xFFFE0001 早就超出了 16 位，但因为它是在 `int` 里算的，没有回落到 16 位。如果把它存回 `uint16_t`，才会截断成 0x0001。Windows 上 MinGW-w64 GCC 13.2 与 Linux 上 GCC 14.2 的输出相同。

需要固定宽度的位运算时，先转换成 `uint32_t` 或 `uint64_t` 再算，别指望小类型保留自己的宽度。移位量也一样：`x << k` 里的 `k` 先用 `k &= 31` 之类的手段压回范围内，或者让规格明确写出调用方要保证什么。

::: concept mdr-unsigned-shift-rules title="无符号算术与移位的规则"

无符号整数的加、减、乘按 2^N 取模，结果总是有定义的。移位位数等于或大于类型宽度、负数移位、有符号左移溢出都属于未定义行为。`uint8_t`、`uint16_t` 参与算术或位运算前先提升为 `int`，结果的类型是 `int`。本节的函数一律在 `uint32_t`、`uint64_t`、`size_t` 上运算，移位量在函数内部压回范围。

:::

移位位数越界时，程序不会在编译期报错，只在运行时给出奇怪的结果。同一份代码在 Linux 上用 UBSan 构建运行：

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint32_t x = 0x80000000u;

    printf("%u\n", (unsigned)(x << 32));
    return 0;
}
```

## 2. 前导零、尾随零与计数

四个计数函数的规格先写清楚。C23 的 `<stdbit.h>` 规定 `stdc_leading_zeros`、`stdc_trailing_zeros` 对 0 返回位宽，本库跟着它走：`mdr_clz_u32(0)` 返回 32，`mdr_clz_u64(0)` 返回 64。这条规定不能省，它决定了后面 `mdr_bit_width_u32(0)` 返回 0 而不是未定义值。GCC 的 `__builtin_clz(0)` 是未定义行为，21.6 用它之前必须包一层。

头文件里的声明：

```c
/* 前导零、尾随零的个数；输入为 0 时返回位宽（32 或 64），与 C23 <stdbit.h> 一致。 */
unsigned mdr_clz_u32(uint32_t x);
unsigned mdr_clz_u64(uint64_t x);
unsigned mdr_ctz_u32(uint32_t x);
unsigned mdr_ctz_u64(uint64_t x);
```

最直观的实现是从最高位往下数，用左移把每一位送到最高位检查：

```c
unsigned mdr_clz_u32(uint32_t x) {
    unsigned n = 0;

    if (x == 0) {
        return 32;
    }
    while ((x & 0x80000000u) == 0) {
        x <<= 1;
        n++;
    }
    return n;
}
```

这段代码对最坏情况要循环 31 次。换个写法，每次把范围砍半，最多 5 次判断：

```c
unsigned mdr_clz_u32(uint32_t x) {
    unsigned n = 0;

    if (x == 0) {
        return 32;
    }
    if ((x & 0xFFFF0000u) == 0) {
        n += 16;
        x <<= 16;
    }
    if ((x & 0xFF000000u) == 0) {
        n += 8;
        x <<= 8;
    }
    if ((x & 0xF0000000u) == 0) {
        n += 4;
        x <<= 4;
    }
    if ((x & 0xC0000000u) == 0) {
        n += 2;
        x <<= 2;
    }
    if ((x & 0x80000000u) == 0) {
        n += 1;
    }
    return n;
}
```

:::

尾随零可以直接借前导零：`x & (0u - x)` 留下最低位的那个 1，其余位清零，这个 1 所在的位置就是尾随零的个数，换算过来是 `31 - clz(x & (0u - x))`。`0u - x` 是无符号取负，按 2^32 取模，标准保证结果有定义。

```c
unsigned mdr_ctz_u32(uint32_t x) {
    if (x == 0) {
        return 32;
    }
    return 31 - mdr_clz_u32(x & (0u - x));
}
```

把 `x & (0u - x)` 单独打印出来，能看清它取到的是哪一位：

```text

$ ./tz_demo

00000001  ctz  0  lowest bit 00000001
```

:::

最后一行值得停一下：0x60000000 的第 29 位是第一个 1，`x & (0u - x)` 得到 0x20000000，恰好是 2^29。

64 位版本把循环条件换成最高位掩码 `UINT64_C(0x8000000000000000)`，其余照抄。`UINT64_C` 把字面量定成 `uint64_t` 的类型：在 LP64 平台上它是 `unsigned long`，在 Windows 上是 `unsigned long long`。直接写 `0x8000000000000000` 时类型由实现按「能放下的第一个类型」挑，跟 `uint64_t` 未必一致，和 `%llu` 之类的格式串配合时容易出问题。

`mdr_popcount_u64` 沿用第一部分的 `x &= x - 1` 循环，每次消掉最低位的 1，循环次数就是 1 的个数。奇偶校验（parity）要的是 1 的个数的最低位，把高半部分反复折到低半部分，最后只看最低一位，不必真的数完：

```c
unsigned mdr_parity_u32(uint32_t x) {
    x ^= x >> 16;
    x ^= x >> 8;
    x ^= x >> 4;
    x ^= x >> 2;
    x ^= x >> 1;
    return x & 1u;
}
```

## 3. 2 的幂

四个判断和取整函数都建立在 `mdr_clz_u32` 上。`x != 0 && (x & (x - 1)) == 0` 判断 2 的幂：2 的幂只有一位是 1，减 1 之后低位全变 1、原来那位变 0，与自身按位与得 0。

```c
bool mdr_has_single_bit_u32(uint32_t x);

unsigned mdr_bit_width_u32(uint32_t x);   /* 表示 x 需要的最少位数，0 返回 0 */

uint32_t mdr_bit_floor_u32(uint32_t x);   /* 不超过 x 的最大 2 的幂，0 返回 0 */

uint32_t mdr_bit_ceil_u32(uint32_t x);    /* 不小于 x 的最小 2 的幂，放不下返回 0 */
```

`bit_width` 就是 32 减去前导零。`bit_floor` 把最高的那个 1 变成 2 的幂：`1u << (31 - clz(x))`。`bit_ceil` 稍麻烦，最省事的写法是先减一再看位宽，这样输入本身是 2 的幂时不会多加一位：

```c
uint32_t mdr_bit_ceil_u32(uint32_t x) {
    if (x <= 1) {
        return 1;
    }
    if (x > 0x80000000u) {
        return 0;
    }
    return 1u << (32 - mdr_clz_u32(x - 1));
}
```

`x > 0x80000000u` 那个分支处理放不下的情况：比 2^31 大的数，最近的上界 2^32 超出 `uint32_t`，按 C23 的规定返回 0。`stdc_bit_ceil_ui` 对 `0x80000001u` 也返回 0，glibc 2.41 实测。这比返回 `UINT32_MAX` 或让调用方自己判断都干净：0 不是任何数的 2 的幂上界，调用方一眼就能看出失败。

在支持 C23 的 Linux 机器上，把四个函数与 `<stdbit.h>` 逐个对照：

```c
for (uint32_t x = 0; x <= 0xFFFFu; x++) {
    bad += mdr_has_single_bit_u32(x) != stdc_has_single_bit_ui(x);
    bad += mdr_bit_width_u32(x) != stdc_bit_width_ui(x);
    bad += mdr_bit_floor_u32(x) != stdc_bit_floor_ui(x);
    bad += mdr_bit_ceil_u32(x) != stdc_bit_ceil_ui(x);
}
```

## 4. 循环移位与字节序

循环移位的难点在移位量为 0 的那一端。直接写 `(x << k) | (x >> (32 - k))`，`k` 为 0 时右移 32 位，正好踩中上一节的规则。两种改法：先把 `k` 压回 0–31，再把右移量也掩码一次。

```c
uint32_t mdr_rotl_u32(uint32_t x, unsigned k) {
    k &= 31;
    return (x << k) | (x >> ((32 - k) & 31));
}

uint32_t mdr_rotr_u32(uint32_t x, unsigned k) {
    k &= 31;
    return (x >> k) | (x << ((32 - k) & 31));
}
```

`k` 为 0 时，左移 0 位保留原值，右移 `(32 - 0) & 31` 即 0 位，结果还是原值。`k` 为 32 时先被 `& 31` 变成 0，同样安全。规格里写「移位量按 k % 32 处理」，调用方传 32、33 都行。

```c

}
```

---

```c
uint32_t mdr_rotl_u32(uint32_t x, unsigned k) {
```

同一个程序在 `-O2` 下还能被编译器认出来。把移位量固定成 7，生成的目标代码只有一条 `roll`：

```asm
mdr_rotl_u32:
	movl	%ecx, %eax
	movl	%edx, %ecx
	roll	%cl, %eax
	ret
```

这是 MinGW-w64 GCC 13.2、`-O2 -S` 的输出；Linux 上 GCC 14.2 生成同样的 `roll %cl, %eax`，只是参数寄存器换成 `%edi`、`%esi`。循环移位写成移位加或之后，不需要为它单独写内联汇编。

字节交换的 64 位版本由第一部分的 `mdr_bswap32` 拼出来，高低两半各换一次，再交换位置：

```c
uint64_t mdr_bswap64(uint64_t x) {
    return ((uint64_t)mdr_bswap32((uint32_t)x) << 32) |
           mdr_bswap32((uint32_t)(x >> 32));
}
```

读写文件格式用的四个函数与主机字节序无关：它们按字节下标组装或拆解，不经过 `uint32_t` 在内存里的布局。小端是先低字节后高字节，大端反过来。

```c
uint32_t mdr_load_le32(const void *src) {
    const unsigned char *p = (const unsigned char *)src;

    return (uint32_t)p[0] | ((uint32_t)p[1] << 8) | ((uint32_t)p[2] << 16) |
           ((uint32_t)p[3] << 24);
}

uint32_t mdr_load_be32(const void *src) {
    const unsigned char *p = (const unsigned char *)src;

    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}
```

`mdr_store_le32`、`mdr_store_be32` 反过来，先右移再用 `0xFF` 掩码，逐个写进字节数组。参数写成 `const void *` 是为了能从任何缓冲区读，函数内部必须转换成 `unsigned char *`，否则 `char` 为有符号的平台上，0x80 以上的字节会先补符号位再移位。

## 5. 带检查的算术

分配数组时最危险的一行是 `malloc(n * size)`。`n` 和 `size` 都是 `size_t`，乘积溢出时按 2^64 回落成一个很小的数，`malloc` 欣然接受，后面按 `n` 个元素写入就越界了。乘法的检查用除法：`b != 0` 时，只要 `a > SIZE_MAX / b`，乘积一定放不下。除法不会溢出，这一步是安全的。

```c
bool mdr_ckd_mul_size(size_t a, size_t b, size_t *res) {
    if (b != 0 && a > SIZE_MAX / b) {
        return true;
    }
    *res = a * b;
    return false;
}
```

加法用减法检查：`a > SIZE_MAX - b` 时溢出。`SIZE_MAX - b` 本身不会下溢，因为 `b <= SIZE_MAX`。

```c
bool mdr_ckd_add_size(size_t a, size_t b, size_t *res) {
    if (a > SIZE_MAX - b) {
        return true;
    }
    *res = a + b;
    return false;
}
```

返回值定为「溢出为 true」，与 C23 `<stdckdint.h>` 的 `ckd_add` 一致。那种接口返回一个布尔值，把结果写进指针；不少旧代码反过来用 0 表示成功，读的时候容易看错。

```text
large            n=1099511627776 size=16 -> 17592186044416 bytes
exact-max        n=9223372036854775807 size=2 -> 18446744073709551614 bytes
just-over        n=9223372036854775808 size=2 -> overflow
```

`exact-max` 一行的乘积是 2^64 - 2，离上限只差 1，没有溢出；元素数再多一个就报溢出了。`large` 一行是 16 TiB，照样算得出来——这个函数检查的只是乘积能不能用 `size_t` 表示，不是内存够不够。这两件事要分开：求出来的大小能不能分配由 `malloc` 回答，参数相乘会不会溢出由这个函数回答。

有符号加法的检查不能照搬上面的减法，因为 `SIZE_MAX - b` 那一步在有符号类型里可能已经越界。先拿 `INT_MAX - b` 比，比完再相加：

```c
#include <limits.h>

bool ckd_add_int(int a, int b, int *res) {
    if (b > 0 ? a > INT_MAX - b : a < INT_MIN - b) {
        return true;
    }
    *res = a + b;
    return false;
}
```

饱和加法是另一类需求：图形和音频里希望结果停在最大值，而不是回绕。先用 `uint64_t` 把和算出来，再与 `UINT32_MAX` 比：

```c
uint32_t mdr_sat_add_u32(uint32_t a, uint32_t b) {
    uint64_t sum = (uint64_t)a + b;

    return sum > UINT32_MAX ? UINT32_MAX : (uint32_t)sum;
}
```

`(uint64_t)a` 这个转换不能省：两个 `uint32_t` 直接相加会在 32 位里回绕。

## 6. 对齐与取整

对齐到 2 的幂的倍数，标准写法是加上 `align - 1` 再抹掉低位：

```c
size_t mdr_align_up_size(size_t x, size_t align) {
    return (x + align - 1) & ~(align - 1);
}
```

`~(align - 1)` 生成低位全 0、高位全 1 的掩码，`&` 之后只保留 `align` 的倍数部分。`align` 必须是 2 的幂，否则掩码不成立；这条写在规格的前置条件里。函数本身也不检查加法溢出，因为对齐值总是很小，真正需要防的是调用方传入的 `x`，这条同样由前置条件说明。

跑一组值：

已经对齐的值原样返回，多出一点就跳到下一个倍数。最后一行是向上取整除法不溢出的证据：`SIZE_MAX` 除以 2 得 2^63 - 1，余 1，于是结果加一，得到 2^63。用 `(a + b - 1) / b` 算，`a + b - 1` 在这一步回绕，结果完全不同。

向上取整除法有个常见但有隐患的写法 `(a + b - 1) / b`。它的结果是对的，可 `a + b - 1` 自己可能溢出。改成先除后补：

```c
size_t mdr_div_ceil_size(size_t a, size_t b) {
    return a / b + (a % b != 0);
}
```

::: compare left-title="先加后除，可能溢出" right-title="先除后补，不溢出"

```c
size_t div_ceil(size_t a, size_t b) {
    return (a + b - 1) / b;
}
```

---

```c
size_t mdr_div_ceil_size(size_t a, size_t b) {
    return a / b + (a % b != 0);
}
```

:::

左栏在 `a` 接近 `SIZE_MAX` 时，`a + b - 1` 回绕成一个很小的值，商也跟着变得毫无意义。右栏的每一步都在范围内：`a / b` 不超过 `a`，`a % b` 小于 `b`，`+ 1` 最多让商增加一。计算「需要多少块」「需要多少页」时，用右栏的写法。

二分查找的中点是同一个问题的另一个版本。`(lo + hi) / 2` 在 `lo`、`hi` 都很大时溢出，而 `lo + (hi - lo) / 2` 不会，因为 `hi - lo` 不超过区间长度，再加上 `lo` 也不会越过 `hi`。

```c
size_t mid = lo + (hi - lo) / 2;
```

这三处（对齐、取整、中点）的共同点是先把运算压到安全范围里，再组合。写这类辅助函数时，值得在规格注释里把「调用方保证什么」写清楚，例如 `mdr_align_up_size` 的「align 是 2 的幂」，别的读者才不会传 24 进来。

```c
uint32_t bit_ceil_bug(uint32_t x) {
    if (x == 0) {
        return 1;
    }
    if (x > 0x80000000u) {
        return 0;
    }
    return (uint32_t)(1ull << mdr_bit_width_u32(x));
}
```

用 `1ull` 而不是 `1u`，是为了让 `x` 为 `0x80000000` 时移位 32 位仍有定义（结果再截断到 32 位）。

(1) 对 `x = 0, 1, 2, 3, 4, 5, 0x80000000` 列出 `bit_ceil_bug` 与正确值的对照表，指出哪一类输入必然错。

(2) 在 `0..0xFFFF` 上穷举，统计与正确实现不一致的输入个数，并列出这些值。个数是 16；`x` 为 0 时两个实现都返回 1，所以 0 不在其中。解释为什么不一致的集合正好是「不大于 `0x8000` 的 2 的幂」。

(3) 用正文第 7 节的做法写一个完整的测试程序 `test_bit_ceil`：包含 16 位穷举、32 位边界值（`0`、`1`、`2`、`3`、`2^k`、`2^k ± 1`、`0xFFFFFFFF`）和性质检查 `mdr_bit_ceil_u32(x) >= x`、`mdr_has_single_bit_u32(mdr_bit_ceil_u32(x))`（返回值非 0 时）。要求错误版本至少被一组检查抓住，修好的版本全部通过。

(4) 把 `0xFFFFFFFF` 一组单独拿出来：正确版本返回 0，`bit_ceil_bug` 也返回 0。为什么这一组不能作为「实现正确」的证据？指出它掩盖了哪个分支的缺陷。

把本节的函数组合成一个分配大小计算工具，这是它们在工程里的典型用法。接口：

```c
/* 计算 n 个元素、每个 size 字节的分配请求。
 * 结果写入 *bytes（对齐后的字节数）与 *pages（页数）。
 * 乘法溢出、对齐加法溢出、页数溢出都返回 false，且不写入输出参数。 */
bool mdr_alloc_plan(size_t n, size_t size, size_t align, size_t page,
                    size_t *bytes, size_t *pages);

/* 把请求的字节数上调到不小于它的 2 的幂，已是对齐粒度的倍数；
 * 结果放不下时返回 0。 */
size_t mdr_alloc_round(size_t bytes);
```

要求：

1. 用 `mdr_ckd_mul_size`、`mdr_align_up_size`、`mdr_div_ceil_size`、`mdr_bit_ceil_u32` 组合实现，每一步的中间结果都检查。`align` 与 `page` 为 0 或不是 2 的幂时返回 `false`（写进规格注释）。
2. 验收表（在 64 位 `size_t` 的机器上）：

```text
n=40       size=16  align=8   page=4096 -> bytes=640        pages=1
n=65536    size=16  align=16  page=4096 -> bytes=1048576    pages=256
n=3        size=5   align=8   page=4096 -> bytes=16         pages=1
n=SIZE_MAX/2 size=4 align=8   page=4096 -> false，乘法溢出
n=SIZE_MAX-2 size=1 align=8   page=4096 -> false，对齐加法溢出
```

第三行的 16 来自「15 字节按 8 对齐」。逐行打印 `bytes` 与 `pages`，对返回 `false` 的行打印失败原因编号（乘法溢出、对齐溢出、页数溢出）。

3. `mdr_alloc_round` 对 `bytes` 为 0、1、4096、4097、`0x40000000`、`0x80000000` 各给出结果，并说明与 `mdr_bit_ceil_u32` 的关系。
4. 写一条命令行小程序 `alloc_plan n size align page`，从 `argv` 读四个数，打印工具的输出。用 `strtoull` 读数时要检查转换错误与负数输入，说明为什么 `(size_t)strtoull(...)` 不能直接信任。
5. 选做：把 `mdr_alloc_plan` 接进一个真实的分配包装 `void *xmalloc(size_t n, size_t size)`，要求乘法溢出时返回空指针而不是交给 `malloc`，并用 `n = SIZE_MAX / 2`、`size = 4` 演示不接检查时 `malloc` 会拿到什么参数。
