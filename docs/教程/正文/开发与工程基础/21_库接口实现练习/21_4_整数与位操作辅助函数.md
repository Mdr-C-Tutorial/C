# 21.4 整数与位操作辅助函数

在底层系统编程中，许多高频出现的整数与位运算需求看似代码量极小，例如为内存分配器寻找「大于等于 n 的最小 2 的整数次幂」、从跨平台网络报文中按大端或小端顺序拼接 32 位整数、或者在动态扩容数组前预测 `n * size` 乘积是否会越界溢出。这些核心算法往往只有寥寥十余行，但在编写时却极易触碰 C 语言标准中最幽深的未定义行为陷阱：移位位数大于等于对象类型的位宽、有符号整型在左移时发生数值溢出、或是宽度较窄的无符号整型（如 `uint8_t`、`uint16_t`）在参与运算前被编译器自动隐式提升为 `int`。

针对这些工程痛点，本节将严格遵循标准规格，从零构建一套高可靠的无符号整数与位操作辅助工具函数，并结合穷举比对、确定性慢速参照实现以及数学代数性质检查，全方位验证其正确性。相关代码紧随 [21.1 范围、命名与契约](/教程/正文/开发与工程基础/21_库接口实现练习/21_1_范围_命名与契约) 中搭建的工程组织方式，源码统一存放在 `code/开发与工程基础/21_库接口实现练习/` 中。第一部分中完成的 `mdr_popcount_u32` 与 `mdr_bswap32` 将继续直接复用，而本节新增的扩展函数均集中维护在 `include/mdr_bits.h` 与 `src/mdr_bits.c` 中。

## 1. 无符号运算与移位规则

为了从根本上规避有符号整数溢出带来的未定义行为，本节设计的所有位运算接口全部严格建立在固定宽度的无符号整型基础之上，具体选用 `uint32_t`、`uint64_t` 与标准的地址计量类型 `size_t`。在 ISO C 规范中，无符号整数算术遵循确定的模 2^N 进位回绕规则，例如 `UINT32_MAX + 1u` 的结果稳定回绕至 0，这一行为在所有合规的 C 编译器中均具备确切的语义保障。也正因如此，在判断无符号加法是否溢出时，绝不能通过观察相加后的数值是否发生突变来推断，而必须依靠操作数与极值上限之间的严格代数关系进行事前或事后校验。

然而，移位运算符 `<<` 与 `>>` 的语义规则却严苛得多。C 标准明确裁定：移位的位数若小于 0，或者大于等于被移位对象类型本身的有效位宽，均属于未定义行为；若对有符号数执行左移且计算结果超出了该有符号类型所能容纳的数值极限，同样构成未定义行为。至于对有符号负数执行右移操作，在 C17 中属于由实现定义的行为（各大主流编译器如 GCC、Clang 与 MSVC 默认均生成算术右移指令以保留符号位），但为了保证绝对的跨平台一致性，本节的位操作接口坚决不对此类平台特性产生任何依赖。

除了移位规则之外，窄整型隐式提升（Integer Promotion）是另一个极易引发隐蔽逻辑缺陷的语言特性：在 C 语言的求值规则中，任何位宽小于 `int` 的整型对象（例如 `uint8_t` 与 `uint16_t`）一旦出现在表达式中，都会在运算执行前被预先提升为有符号的 `int` 类型（若 `int` 足以完整容纳其取值空间），且中间表达式的求值均在 `int` 精度下完成。这导致对一个 `uint8_t` 对象执行按位取反 `~` 时，计算得到的并不是 8 位的局部反码，而是一个高 24 位全部被置为 1 的 32 位有符号整数：

```c
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint8_t byte = 0x0Fu;
    uint16_t word = 0xFFFFu;

    printf("~byte       = %08X\n", (unsigned)~byte);
    printf("byte << 4   = %08X\n", (unsigned)(byte << 4));
    printf("word * word = %08X\n", (unsigned)(word * word));
    printf("sizeof(byte + byte) = %zu\n", sizeof(byte + byte));
    return 0;
}
```

`~byte` 补出了高 24 位；`word * word` 的结果 0xFFFE0001 早就超出了 16 位，但因为它是在 `int` 里算的，没有回落到 16 位。如果把它存回 `uint16_t`，才会截断成 0x0001。Windows 上 MinGW-w64 GCC 13.2 与 Linux 上 GCC 14.2 的输出相同。

需要固定宽度的位运算时，先转换成 `uint32_t` 或 `uint64_t` 再算，别指望小类型保留自己的宽度。移位量也一样：`x << k` 里的 `k` 先用 `k &= 31` 之类的手段压回范围内，或者让规格明确写出调用方要保证什么。

::: concept mdr-unsigned-shift-rules title="无符号算术与移位的规则"

无符号整数的加、减、乘按 2^N 取模，结果总是有定义的。移位位数等于或大于类型宽度、负数移位、有符号左移溢出都属于未定义行为。`uint8_t`、`uint16_t` 参与算术或位运算前先提升为 `int`，结果的类型是 `int`。本节的函数一律在 `uint32_t`、`uint64_t`、`size_t` 上运算，移位量在函数内部压回范围。

:::


## 2. 前导零、尾随零与计数

在构建位计数接口之前，必须首先从规格层面明确界定输入为 0 时的边界返回值。在 C23 官方标准库 `<stdbit.h>` 中，标准明确规定 `stdc_leading_zeros` 与 `stdc_trailing_zeros` 在接收到 0 时，统一返回当前整型对象的物理位宽。本库完全采纳这一现代化契约：`mdr_clz_u32(0)` 返回 32，`mdr_clz_u64(0)` 返回 64。这一规定的必要性在于：后续实现的有效位宽计算接口 `mdr_bit_width_u32` 深度依赖它来得出 0 的位宽为 0；若此处留下未定义漏洞，整个工具链的逻辑自洽性将瞬间崩塌。需要警惕的是，GCC 与 Clang 的内建指令 `__builtin_clz(0)` 在硬件层面直接构成未定义行为，我们在 21.6 节调用它之前必须在此处的外围包装中严密拦截零输入。

头文件里的声明：

```c
/* 前导零、尾随零的个数；输入为 0 时返回位宽（32 或 64），与 C23 <stdbit.h> 一致。 */
unsigned mdr_clz_u32(uint32_t x);
unsigned mdr_clz_u64(uint64_t x);
unsigned mdr_ctz_u32(uint32_t x);
unsigned mdr_ctz_u64(uint64_t x);
```

最直观的实现是从最高位往下数，用左移把每一位送到最高位检查：

```c
unsigned mdr_clz_u32(uint32_t x) {
    unsigned n = 0;

    if (x == 0) {
        return 32;
    }
    while ((x & 0x80000000u) == 0) {
        x <<= 1;
        n++;
    }
    return n;
}
```

在上述朴素逐位扫描实现中，当输入仅有最低位为 1 时，代码最坏需要循环迭代 31 次。而在工业级位运算中，通常采用类似二分查找的分治策略：每次利用位掩码探测当前高半部分是否全为 0，若是则将计数器累加对应权重并将低半部分左移上来，从而在固定的 5 次二分判断内彻底完成 32 位整数的扫描：

```c
unsigned mdr_clz_u32(uint32_t x) {
    unsigned n = 0;

    if (x == 0) {
        return 32;
    }
    if ((x & 0xFFFF0000u) == 0) {
        n += 16;
        x <<= 16;
    }
    if ((x & 0xFF000000u) == 0) {
        n += 8;
        x <<= 8;
    }
    if ((x & 0xF0000000u) == 0) {
        n += 4;
        x <<= 4;
    }
    if ((x & 0xC0000000u) == 0) {
        n += 2;
        x <<= 2;
    }
    if ((x & 0x80000000u) == 0) {
        n += 1;
    }
    return n;
}
```

对于统计末尾连续零个数的 `mdr_ctz_u32`，我们甚至无需重复编写一套对称的分治循环，而是可以巧妙借用前导零的结果。在计算机位运算代数中，表达式 `x & (0u - x)`（即保留最低有效位的经典技巧）能够精准剥离并保留 `x` 中最低位的那颗孤立的 1，其余所有位全部归零。通过前导零函数计算出该孤立 1 在 32 位空间中的高位偏移后，用 31 减去该值即可精确换算出其低位尾随零的个数：`31 - mdr_clz_u32(x & (0u - x))`。其中 `0u - x` 是纯粹良定义的无符号补码取负，在模 2^32 下严格成立：

```c
unsigned mdr_ctz_u32(uint32_t x) {
    if (x == 0) {
        return 32;
    }
    return 31 - mdr_clz_u32(x & (0u - x));
}
```

把 `x & (0u - x)` 单独打印出来，能看清它取到的是哪一位：

在编写 64 位版本时，只需将最高位掩码替换为对应的 64 位无符号字面量宏 `UINT64_C(0x8000000000000000)`，逻辑结构完全一致。使用标准宏 `UINT64_C` 的关键在于确保常量具备与 `uint64_t` 完全一致的真实底层类型：在 64 位 Linux（LP64 数据模型）中该类型通常为 `unsigned long`，而在 64 位 Windows（LLP64 数据模型）中则被定义为 `unsigned long long`。如果随意在代码中硬编码原始字面量，其推导类型极易在不同操作系统间发生偏移，进而在配合 `%llu` 打印或参与泛型宏计算时引发级联编译告警。

对于统计算法，`mdr_popcount_u64` 继续延续我们在第一部分建立的经典 Brian Kernighan 算法，利用 `x &= x - 1` 每次从低向高精准剥离一个 1，循环次数严格等于输入中 1 的真实总数。而对于校验奇偶性（Parity）的接口，其核心目标是获取 1 的总数的最低有效位（即奇偶性），此时甚至无需完整数出数量，通过折半异或（Fold XOR）树状结构将高半部分比特逐级压缩折叠到低半部分，最终提取最低位即可：

```c
unsigned mdr_parity_u32(uint32_t x) {
    x ^= x >> 16;
    x ^= x >> 8;
    x ^= x >> 4;
    x ^= x >> 2;
    x ^= x >> 1;
    return x & 1u;
}
```

## 3. 2 的幂

在内存池管理与数据对齐中，针对 2 的整数次幂的判定与规整是出镜率极高的基础操作。上述四个核心接口全部优雅地建立在 `mdr_clz_u32` 这一基础设施之上。

首先，判定一个数是否恰好是 2 的整数次幂，可以通过位代数短语 `x != 0 && (x & (x - 1)) == 0` 在常数时间内裁定：因为 2 的幂在二进制表示中有且仅有一位是 1，对其减 1 之后，该位变为 0 且其下方所有低位全部翻转为 1，两者按位与的结果必然严格为 0。

接口原型声明如下：

```c
bool mdr_has_single_bit_u32(uint32_t x);

unsigned mdr_bit_width_u32(uint32_t x);   /* 表示 x 需要的最少位数，0 返回 0 */

uint32_t mdr_bit_floor_u32(uint32_t x);   /* 不超过 x 的最大 2 的幂，0 返回 0 */

uint32_t mdr_bit_ceil_u32(uint32_t x);    /* 不小于 x 的最小 2 的幂，放不下返回 0 */
```

在语义设计上：
- `mdr_bit_width_u32(x)` 计算表示数值 `x` 所必须的最少有效二进制位数，其值等价于 `32 - mdr_clz_u32(x)`；当输入为 0 时，自然得到 0。
- `mdr_bit_floor_u32(x)` 用于求出小于等于 `x` 的最大 2 的整数次幂，只需将最高位的那个 1 保留，其余低位全部抹零，即 `1u << (31 - mdr_clz_u32(x))`。
- `mdr_bit_ceil_u32(x)` 则用于向上寻找大于等于 `x` 的最小 2 的整数次幂。此处的实现边界最为微妙：为了防止当输入本身已经是 2 的整数次幂时错误地多算了一倍，最干净的做法是在进入计算前先执行减 1 预处理：

```c
uint32_t mdr_bit_ceil_u32(uint32_t x) {
    if (x <= 1) {
        return 1;
    }
    if (x > 0x80000000u) {
        return 0;
    }
    return 1u << (32 - mdr_clz_u32(x - 1));
}
```

在 `mdr_bit_ceil_u32` 中，`x > 0x80000000u` 这一显式分支至关重要：由于 32 位无符号整型能够表示的最大 2 的幂就是 2^31（即 `0x80000000`），一旦输入大于该极值，其数学上的最小 2 的幂上限为 2^32，已经彻底超出了 `uint32_t` 的物理表达上限。按照 C23 标准 `<stdbit.h>` 的规定，此时函数必须确定地返回 0。Linux glibc 2.41 提供的 `stdc_bit_ceil_ui(0x80000001u)` 同样严格返回 0。这种以 0 作为溢出哨兵的设计极其干净利落，因为 0 绝不可能是任何正整数向上取整后的有效 2 的幂，调用方仅凭单次非零判断即可立即洞察容量溢出。

在支持 C23 的 Linux 机器上，把四个函数与 `<stdbit.h>` 逐个对照：

```c
for (uint32_t x = 0; x <= 0xFFFFu; x++) {
    bad += mdr_has_single_bit_u32(x) != stdc_has_single_bit_ui(x);
    bad += mdr_bit_width_u32(x) != stdc_bit_width_ui(x);
    bad += mdr_bit_floor_u32(x) != stdc_bit_floor_ui(x);
    bad += mdr_bit_ceil_u32(x) != stdc_bit_ceil_ui(x);
}
```

## 4. 循环移位与字节序

在实现循环移位（Rotate Left / Rotate Right）时，最为棘手的边界恰恰发生在移位量为 0 的极端情形。如果按照直觉直接写出 `(x << k) | (x >> (32 - k))`，当传入的 `k` 为 0 时，表达式右半部分会演变为 `x >> 32`，这瞬间触发了我们在前文强调过的未定义行为法则——移位位数等于类型宽度。

为了彻底抹平这一未定义风险，稳健的做法分为两步：首先将外部传入的移位参数 `k` 通过 `k &= 31` 模归一化到 0 到 31 的有效位移区间内；其次，对反向移位的偏移量同样追加一次 `& 31` 掩码截断：

```c
uint32_t mdr_rotl_u32(uint32_t x, unsigned k) {
    k &= 31;
    return (x << k) | (x >> ((32 - k) & 31));
}

uint32_t mdr_rotr_u32(uint32_t x, unsigned k) {
    k &= 31;
    return (x >> k) | (x << ((32 - k) & 31));
}
```

在上述修正实现中，当 `k` 为 0 时，左半部分为 `x << 0` 保持原值，右半部分计算 `(32 - 0) & 31` 同样精确收敛为 0，从而安全求得 `x >> 0`，最终结果保持原值无损；当外部传入 32 时，第一行 `k &= 31` 同样将其规整为 0。在规格中，我们明确声明「移位量统一按 k % 32 映射」，因此调用方即便传入 32、33 甚至更大的正整数，函数也能平稳交出合规的循环移位值。

同一个程序在 `-O2` 下还能被编译器精准识别。把移位量固定成 7 时，生成的目标代码直接被合成为一条硬件循环移位指令 `roll`：

```asm
mdr_rotl_u32:
	movl	%ecx, %eax
	movl	%edx, %ecx
	roll	%cl, %eax
	ret
```

这是 MinGW-w64 GCC 13.2、`-O2 -S` 的输出；Linux 上 GCC 14.2 生成同样的 `roll %cl, %eax`，只是参数寄存器换成 `%edi`、`%esi`。循环移位写成移位加或之后，编译器能够自动将其重写为最简硬件指令，完全不需要为它单独编写晦涩的内联汇编。

字节交换的 64 位版本由第一部分的 `mdr_bswap32` 拼出来，高低两半各换一次，再交换位置：

```c
uint64_t mdr_bswap64(uint64_t x) {
    return ((uint64_t)mdr_bswap32((uint32_t)x) << 32) |
           mdr_bswap32((uint32_t)(x >> 32));
}
```

读写文件格式用的四个函数与主机字节序无关：它们按字节下标组装或拆解，不经过 `uint32_t` 在内存里的布局。小端是先低字节后高字节，大端反过来：

```c
uint32_t mdr_load_le32(const void *src) {
    const unsigned char *p = (const unsigned char *)src;

    return (uint32_t)p[0] | ((uint32_t)p[1] << 8) | ((uint32_t)p[2] << 16) |
           ((uint32_t)p[3] << 24);
}

uint32_t mdr_load_be32(const void *src) {
    const unsigned char *p = (const unsigned char *)src;

    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8) | (uint32_t)p[3];
}
```

`mdr_store_le32` 与 `mdr_store_be32` 逻辑相反，先逐级右移再用 `0xFF` 掩码，逐个写入字节缓冲区。参数写成 `const void *` 是为了能从任意物理缓冲区读取，函数内部必须转换成 `unsigned char *`，否则在 `char` 为有符号的平台上，`0x80` 以上的字节会先补符号位再移位。

写一串字节再读回来，两边机器给出同一个值：

## 5. 带检查的算术

在涉及堆内存分配的代码中，最为凶险的潜在漏洞往往潜伏在 `malloc(n * size)` 这一看似无害的乘法计算中。如果操作数 `n` 与单个结构体大小 `size` 均为 `size_t`，当两者乘积超出 2^64 时，算术运算会无声无息地回绕为一个极其微小的正整数。此时 `malloc` 会按照这个截断后的小尺寸成功分配缓冲区，而后续的循环却依然固执地按 `n` 次迭代向堆内存大肆写入，瞬间酿成致命的堆越界写破坏。

要在标准 C 中安全判定乘法溢出，必须逆向借助除法进行边界预判：只要乘数 `b != 0`，若有 `a > SIZE_MAX / b` 成立，则两者的乘积必然超出 `size_t` 的物理表达界限。由于除法计算绝不会引发溢出，这一预判逻辑在代数上具备坚固的安全性：

```c
bool mdr_ckd_mul_size(size_t a, size_t b, size_t *res) {
    if (b != 0 && a > SIZE_MAX / b) {
        return true;
    }
    *res = a * b;
    return false;
}
```

同理，无符号加法的溢出检测应当逆向借助减法来实现：若有 `a > SIZE_MAX - b`，则说明两者相加必然发生模进位溢出。由于此时必有 `b <= SIZE_MAX`，减法表达式 `SIZE_MAX - b` 绝不会发生下溢回绕，因而判断过程完全安全自洽：

```c
bool mdr_ckd_add_size(size_t a, size_t b, size_t *res) {
    if (a > SIZE_MAX - b) {
        return true;
    }
    *res = a + b;
    return false;
}
```

在接口返回值契约上，我们明确约定「发生溢出时返回 true，未发生溢出时返回 false」，这与 C23 标准正式引入的 `<stdckdint.h>` 头文件中的 `ckd_add` 族宏规范保持了高度同步。通过布尔值明确指示溢出状态、将计算结果通过指针参数安全传出的设计，能够有效避免旧式 C 库中混用 0 与 -1 充当状态标志所带来的可读性困扰。

用它检查几个分配大小：

::: terminal title="zsh - ckd_demo"

```text
$ gcc -std=c17 -Wall -Wextra -Iinclude ckd_demo.c src/mdr_bits.c -o ckd_demo
$ ./ckd_demo
small            n=40 size=16 -> 640 bytes
large            n=1099511627776 size=16 -> 17592186044416 bytes
exact-max        n=9223372036854775807 size=2 -> 18446744073709551614 bytes
just-over        n=9223372036854775808 size=2 -> overflow
```

:::

`exact-max` 一行的乘积是 2^64 - 2，离上限只差 1，没有溢出；元素数再多一个就报溢出了。`large` 一行是 16 TiB，照样算得出来——这个函数检查的只是乘积能不能用 `size_t` 表示，不是内存够不够。这两件事要分开：求出来的大小能不能分配由 `malloc` 回答，参数相乘会不会溢出由这个函数回答。

有符号加法的检查不能照搬上面的减法，因为 `SIZE_MAX - b` 那一步在有符号类型里可能已经越界。先拿 `INT_MAX - b` 比，比完再相加：

```c
#include <limits.h>

bool ckd_add_int(int a, int b, int *res) {
    if (b > 0 ? a > INT_MAX - b : a < INT_MIN - b) {
        return true;
    }
    *res = a + b;
    return false;
}
```

饱和加法是另一类需求：图形和音频里希望结果停在最大值，而不是回绕。先用 `uint64_t` 把和算出来，再与 `UINT32_MAX` 比：

```c
uint32_t mdr_sat_add_u32(uint32_t a, uint32_t b) {
    uint64_t sum = (uint64_t)a + b;

    return sum > UINT32_MAX ? UINT32_MAX : (uint32_t)sum;
}
```

`(uint64_t)a` 这个转换不能省：两个 `uint32_t` 直接相加会在 32 位里回绕。

## 6. 对齐与取整

在底层内存管理、页表映射与缓存行对齐的计算中，将一个数值向上规整到 2 的整数次幂的倍数是标准的惯用语法：先加上 `align - 1`，随后利用位与运算抹掉全部低位比特：

```c
size_t mdr_align_up_size(size_t x, size_t align) {
    return (x + align - 1) & ~(align - 1);
}
```

表达式 `~(align - 1)` 能够精准生成低位全为 0、高位全为 1 的位掩码，通过按位与运算便能只保留属于 `align` 整数倍的高阶成分。需要强调的是，这一位运算技巧严格要求基准对齐量 `align` 必须是 2 的整数次幂；若调用方传入任意奇数或其他非 2 的幂数值，掩码将彻底失效。我们在接口头文件的前置条件中明确写明了这一契约约束。

已经对齐的值原样返回，多出一点就跳到下一个倍数。最后一行是向上取整除法不溢出的证据：`SIZE_MAX` 除以 2 得 2^63 - 1，余 1，于是结果加一，得到 2^63。用 `(a + b - 1) / b` 算，`a + b - 1` 在这一步回绕，结果完全不同。

而在计算离散资源分配时，向上取整除法（Ceil Division）同样极易滋生溢出缺陷。初学者极其习惯于写出经典的 `(a + b - 1) / b` 宏，然而该公式潜藏着严重的安全死角：当被除数 `a` 本身已经极其接近 `SIZE_MAX` 时，括号内的 `a + b - 1` 会在进入除法之前率先发生模进位回绕，导致计算出的商沦为一个荒谬的微小数值。

为了杜绝此类隐患，应当改为在代数上完全杜绝加法溢出的「先整除后补余」策略：

```c
size_t mdr_div_ceil_size(size_t a, size_t b) {
    return a / b + (a % b != 0);
}
```

::: compare left-title="先加后除，可能溢出" right-title="先除后补，不溢出"

```c
size_t div_ceil(size_t a, size_t b) {
    return (a + b - 1) / b;
}
```

---

```c
size_t mdr_div_ceil_size(size_t a, size_t b) {
    return a / b + (a % b != 0);
}
```

:::

对比左右两栏的逻辑可知：左栏的写法将溢出风险完全暴露在事前加法中；而右栏的重构版本每一步都在安全范围内展开——整除 `a / b` 的结果必然不大于 `a`，取模余数 `a % b` 严格小于除数 `b`，末尾的三元增量最多使商增加 1。在计算分页系统中「容纳指定字节流需要多少物理页」时，必须坚决采用右栏这一不会引发溢出的稳妥算法。

二分查找中计算中点坐标的经典演进也是同一个原理的生动写照：写法 `(lo + hi) / 2` 在两个下标均处于大数值区间时极易遭遇加法溢出，而将其重写为 `lo + (hi - lo) / 2` 后，由于差值 `hi - lo` 严格局限在区间长度内，再加上基准 `lo` 也绝不会突破 `hi`，从而在根本上保障了算术的自洽与安全。

```c
size_t mid = lo + (hi - lo) / 2;
```

这三处（对齐、取整、中点）的共同点是先把运算压到安全范围里，再组合。写这类辅助函数时，值得在规格注释里把「调用方保证什么」写清楚，例如 `mdr_align_up_size` 的「align 是 2 的幂」，别的读者才不会传 24 进来。

## 7. 测试位操作函数

位操作函数具备一项独特的测试优势：对于 16 位及以下的输入空间，我们完全有能力进行全量穷举验证。编写一个逻辑极其直白、逐位展开处理的基准参考实现，虽然运算效率不高，但其正确性一目了然，非常适合拿来与高度优化的位运算函数逐一核对。

```c
/* 逐位循环的参照实现：慢，但一眼能看出对错 */
static unsigned ref_clz_u32(uint32_t x) {
    unsigned n = 0;

    for (int bit = 31; bit >= 0; bit--) {
        if (((x >> (unsigned)bit) & 1u) != 0) {
            break;
        }
        n++;
    }
    return n;
}
```

这种测试思路的核心在于“参照实现保真、目标实现求快”。全量遍历 16 位无符号整数全部 65536 种状态，现代处理器往往只需几毫秒即可验证完毕：

::: terminal title="zsh - exhaustive"

```text
$ gcc -std=c17 -Wall -Wextra -O2 exhaustive.c -o exhaustive
$ ./exhaustive
16-bit values: 65536, mismatches: 0
32-bit boundary values: 14, mismatches: 0
rotate properties: ok
```

:::

对于 32 位甚至 64 位无符号整数，遍历全部状态空间在时间上并不现实。此时测试策略主要转向两个方向：一是精心构造边界值集合，二是基于代数性质进行一致性校验。

边界集合通常选取 `0`、`1`、`2`、`3`、各类形如 $2^k$ 与 $2^k \pm 1$ 的数值，以及全 1 掩码（如 `0xFFFFFFFF`），这类数值能够精准覆盖条件分支与进位边界。而性质检查（Property-based testing）则不依赖逐项对照的参考实现，转而验证数学上恒成立的自洽关系：

- `mdr_rotl_u32(mdr_rotr_u32(x, k), k) == x`：左右旋转操作互为逆运算。
- `mdr_bswap64(mdr_bswap64(x)) == x`：连续进行两次字节序反转应当还原数值。
- `mdr_popcount_u64(x) + mdr_popcount_u64(~x) == 64`：任意数值与其按位取反值的置 1 位数之和恒等于总位宽。

在测试逻辑中用循环对海量数值验证上述代数恒等式，比起硬编码少量静态输入与期望输出，对边缘逻辑漏洞的捕捉能力要严密得多。

在工程实践中，测试源文件 `tests/test_bits.c` 沿用轻量断言宏 `check.h`，将这些特异值与性质验证组织成标准测试集：

```c
static void test_power_of_two(void) {
    CHECK(!mdr_has_single_bit_u32(0u));
    CHECK(mdr_has_single_bit_u32(1u));
    CHECK(mdr_has_single_bit_u32(0x80000000u));
    CHECK(!mdr_has_single_bit_u32(0x80000001u));

    CHECK(mdr_bit_ceil_u32(0u) == 1u);
    CHECK(mdr_bit_ceil_u32(0x80000000u) == 0x80000000u);
    CHECK(mdr_bit_ceil_u32(0x80000001u) == 0u);
}
```
