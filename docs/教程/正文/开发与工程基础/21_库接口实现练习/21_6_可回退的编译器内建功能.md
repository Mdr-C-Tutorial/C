# 21.6 可回退的编译器内建功能

21.4 的 `mdr_popcount_u32` 用 `x &= x - 1` 循环数 1 的个数，算法没问题，可在 x86-64 上它要循环几十次，而处理器有一条 `popcnt` 指令一次就能算出结果。能不能在支持的编译器上用上这条指令，在别的编译器上仍用那段循环，而且两边对所有输入给出相同的结果？

这一节把位计数、字节交换、溢出检查、分支提示和属性都放在一层可移植的宏后面：编译期检测当前环境支持什么，选一条路径；不支持时回退到 21.4 的普通 C 实现。最后用同一组测试把每条路径都跑一遍。

## 1. 内建函数与内部函数

GCC 和 Clang 把一组以 `__builtin_` 开头的函数（built-in function）交给编译器处理。调用 `__builtin_popcount` 时，编译器可能生成一条 `popcnt` 指令，也可能调用运行库里负责计数的那个函数，取决于目标处理器和编译选项。名字里虽然带「函数」，它既不需要头文件，也不一定真的生成一次函数调用。

MSVC 走另一条路，把这类东西放在 `<intrin.h>` 里，称为内部函数（intrinsic）：`_BitScanReverse` 找最高位的 1，`__popcnt` 数 1，`_byteswap_ulong` 交换字节。名字带下划线、参数形式也不同，例如 `_BitScanReverse` 通过指针返回位下标，再用返回值表示找没找到。

C23 的 `<stdbit.h>` 把其中一部分标准化了：`stdc_count_ones_ui`、`stdc_leading_zeros_ui` 这些函数在各实现上有统一的语义，遇到 0 时返回位宽。它不是编译器的扩展，用不用得上看标准库的版本。

第三条路最容易被忘掉：编译器自己认识常见的写法。21.4 那段 `x &= x - 1` 的循环，在 `-O2 -mpopcnt` 下会被整个换成一条 `popcntl`：

```c
unsigned pop_loop(uint32_t x) {
    unsigned n = 0;

    while (x != 0) {
        x &= x - 1u;
        n++;
    }
    return n;
}
```

::: terminal title="zsh - gcc -S"

```text
$ gcc -std=c17 -Wall -Wextra -O2 -mpopcnt -S pop_demo.c -o pop_mp.s
$ sed -n '/^pop_loop:/,/ret/p' pop_mp.s
pop_loop:
	xorl	%eax, %eax
	xorl	%edx, %edx
	popcntl	%ecx, %eax
	testl	%ecx, %ecx
	cmove	%edx, %eax
	ret
```

:::

这是 MinGW-w64 GCC 13.2 的输出。`cmove` 处理的是 `x` 为 0 的情况：`popcntl` 对 0 返回 0，正是循环版的结果。不加 `-mpopcnt` 时，同一段循环保持原样，逐位处理。也就是说，写对普通 C，再打开对应的指令集选项，编译器就能自己接上硬件。

::: concept mdr-builtin-same-results title="内建版本与回退版本的结果必须相同"

内建函数、内部函数和普通 C 回退只是三条通往同一个规格的路径。任何一条路径对任何一个输入给出的结果都要和另外两条一致，包括 0 这类特殊输入。某个内建函数对某个输入是未定义行为时（例如 `__builtin_clz(0)`），必须在包装层里先处理掉，不能让未定义漏到接口外面。

:::

## 2. 检测

选择路径要在预处理阶段完成，靠的是编译器提供的几个检测手段。

`__has_builtin(name)` 判断一个内建函数是否存在，GCC 10 起和 Clang 都支持。它本身可能不存在，所以要先用 `#if defined(__has_builtin)` 包一层，或者像本库这样给一个默认值：

```c
#ifndef __has_builtin
#define __has_builtin(x) 0
#endif

#define MDR_HAS_BUILTIN(x) __has_builtin(x)
```

`__has_include(<stdbit.h>)` 判断一个头文件能不能包含，C23 把它标准化，GCC 和 Clang 更早就有。本机的探测结果：

::: terminal title="zsh - detect"

```text
$ gcc -std=c17 -Wall -Wextra detect.c -o detect && ./detect
has_builtin defined
__builtin_popcount yes
__builtin_clzg no
__builtin_stdc_leading_zeros no
stdbit.h no
__GNUC__ 13
__STDC_VERSION__ 201710
$ gcc -std=c2x -Wall -Wextra detect.c -o detect2 && ./detect2
has_builtin defined
__builtin_popcount yes
__builtin_clzg no
__builtin_stdc_leading_zeros no
stdbit.h no
__GNUC__ 13
__STDC_VERSION__ 202000
```

:::

同一份程序拿到 Linux 的 GCC 14.2 上用 `-std=c23` 编，`__builtin_clzg`、`__builtin_stdc_leading_zeros`、`stdbit.h` 三行都变成 `yes`，`__GNUC__` 是 14，而 `__STDC_VERSION__` 仍然是 `202000L`。

最后这一点值得单独说。按标准，C23 的 `__STDC_VERSION__` 应该是 `202311L`，但 GCC 14 在 `-std=c23` 下报 `202000L`：

::: terminal title="zsh - ver"

```text
$ gcc -std=c23 -Wall -Wextra ver.c -o ver && ./ver
__STDC_VERSION__ = 202000L
does not reach 202311L
```

:::

所以拿 `#if __STDC_VERSION__ >= 202311L` 判断「有没有 C23 的库」会漏掉所有 GCC 14，包括已经提供 `<stdbit.h>` 的那些。可靠的做法是检测具体功能：头文件用 `__has_include`，内建函数用 `__has_builtin`，属性用 `__has_c_attribute`（见[属性](/教程/正文/语法和标准库/15_声明_名称与生存期/15_6_属性)）。版本号只在确知各实现取值的情况下才能用。

::: concept mdr-detect-features title="检测功能，不检测版本号"

判断某个 C23 特性能不能用，检测那个特性本身：头文件用 `__has_include`，内建函数用 `__has_builtin`，属性用 `__has_c_attribute`。`__STDC_VERSION__` 的取值在实现之间不一致（GCC 14 的 `-std=c23` 报 `202000L`），拿它当门槛会漏掉实现已经提供的功能。

:::

编译器身份的宏仍然有用，但只用于需要区分编译器家族的地方：`__GNUC__`（Clang 也定义它，所以判断 Clang 要放在前面）、`__clang__`、`_MSC_VER`。MSVC 的 `_MSC_VER` 是版本号，`cl 19.51` 对应 1951。

## 3. 一个可回退的 `popcount`

把上面的手段合起来，写成一个头文件 `include/mdr_compiler.h`。先决定是否允许使用内建功能：

```c
#if defined(MDR_NO_BUILTINS)
#define MDR_USE_BUILTINS 0
#else
#define MDR_USE_BUILTINS 1
#endif
```

然后是 C23 头文件的检测，只在允许用内建功能时做，并且用 `__has_include` 而不是版本号：

```c
#if MDR_USE_BUILTINS && defined(__has_include)
#if __has_include(<stdbit.h>)
#include <stdbit.h>
#define MDR_HAVE_STDBIT 1
#endif
#if __has_include(<stdckdint.h>)
#include <stdckdint.h>
#define MDR_HAVE_STDCKDINT 1
#endif
#endif
#ifndef MDR_HAVE_STDBIT
#define MDR_HAVE_STDBIT 0
#endif
#ifndef MDR_HAVE_STDCKDINT
#define MDR_HAVE_STDCKDINT 0
#endif
```

`mdr_bits.c` 里的 `mdr_popcount_u32` 依次选择四条路径：

```c
unsigned mdr_popcount_u32(uint32_t value) {
#if MDR_HAVE_STDBIT
    return (unsigned)stdc_count_ones_ui(value);
#elif MDR_USE_BUILTINS && MDR_HAS_BUILTIN(__builtin_popcount)
    return (unsigned)__builtin_popcount(value);
#elif MDR_USE_BUILTINS && defined(_MSC_VER)
    return (unsigned)__popcnt(value);
#else
    unsigned count = 0;

    while (value != 0) {
        value &= value - 1u;
        count++;
    }
    return count;
#endif
}
```

顺序有意义：最标准的（`<stdbit.h>`）放最前，其次 GCC/Clang 的内建，再次 MSVC 的内部函数，最后是普通 C。MSVC 的 `__popcnt` 要求目标机有 `popcnt` 指令，32 位 x86 上还要额外判断 CPU 支持，这是选择 `__popcnt` 时要清楚的一点；`__builtin_popcount` 在编译时没有开 `-mpopcnt` 会退化成库函数调用，所以它本身是安全的。

`MDR_NO_BUILTINS` 让上面四个分支全部走最后一条。默认构建和 `-DMDR_NO_BUILTINS` 构建编出来的是同一个库的两种版本，两者用同一组测试。

生成的代码能直接看出走的是哪条路。用 21.4 的库源码分别以四种配置编译成汇编：

::: terminal title="zsh - gcc -S"

```text
$ gcc -std=c17 -Wall -Wextra -Iinclude -O2 -S src/mdr_bits.c -o lib_builtin.s
$ gcc -std=c17 -Wall -Wextra -Iinclude -O2 -mpopcnt -S src/mdr_bits.c -o lib_builtin+mpopcnt.s
$ gcc -std=c17 -Wall -Wextra -Iinclude -O2 -DMDR_NO_BUILTINS -S src/mdr_bits.c -o lib_fallback.s
$ sed -n '/^mdr_popcount_u32:/,/ret/p' lib_builtin.s
mdr_popcount_u32:
	subq	$40, %rsp
	movl	%ecx, %ecx
	call	__popcountdi2
	addq	$40, %rsp
	ret
$ sed -n '/^mdr_popcount_u32:/,/ret/p' lib_builtin+mpopcnt.s
mdr_popcount_u32:
	xorl	%eax, %eax
	popcntl	%ecx, %eax
	ret
```

:::

四种组合的结论：

| 配置 | 生成代码 | 原因 |
| --- | --- | --- |
| 默认（`-O2`） | `call __popcountdi2` | 内建函数没有对应指令时交给运行库 |
| 默认 + `-mpopcnt` | `popcntl` 一条 | 目标指令集允许，内建直接落成指令 |
| 回退（`-O2`） | 循环，`andl`/`addl`/`jne` | 编译器没有把这段模式认成 popcount |
| 回退 + `-mpopcnt` | `popcntl`、`test`、`cmove` | 编译器自己认出了循环，还要处理 0 |

Linux 上 GCC 14.2 的结果与上表前两行一致，`lib_builtin.s` 同样是调用 `__popcountdi2`，加 `-mpopcnt` 后是一条 `popcntl`；差别只在调用约定（参数寄存器是 `%edi`）和 `__popcountdi2@PLT` 的写法。

第三、四行的细节随编译器版本变。本机 GCC 13.2 的「回退 + `-mpopcnt`」多出一条 `testl` 和一条 `cmove`：它把这个循环替换成 `popcntl` 之后，还要单独补回「输入为 0 时返回 0」的分支；Linux 上 GCC 14.2 编同一份源码只留下一条 `popcntl`，省掉了那个分支。同一段普通 C 在两个版本上编出的指令条数不同，这正是「别靠读汇编推断性能，要实测」的一个例子。要追求极致，可以在回退版外面加判断，但那多半不值得。

::: tip 内建函数不一定更快

上表第一行说明，`__builtin_popcount` 在没有指令支持时只是把循环换成了库函数调用，反而多一次函数调用开销。用内建函数的收益取决于目标指令集；查看生成的汇编才知道它到底落成了什么。

:::

## 4. 包住语义差异

四个计数函数在 C23 里对 0 返回位宽，`__builtin_clz(0)` 却是未定义行为。不包一层，程序在输入为 0 时结果不可预测：

::: terminal title="zsh - clz0"

```text
$ gcc -std=c17 -Wall -Wextra -O0 clz0.c -o clz0 && ./clz0
__builtin_clz(0) = 31
__builtin_ctz(0) = 32
$ gcc -std=c17 -Wall -Wextra -O2 clz0.c -o clz0o2 && ./clz0o2
__builtin_clz(0) = -1290901457
__builtin_ctz(0) = 32
$ ./clz0o2
__builtin_clz(0) = 1839312102
__builtin_ctz(0) = 32
```

:::

`-O0` 下 `__builtin_clz(0)` 恰好给出 31，看起来像是对的；`-O2` 下同一个表达式给出一个随每次运行变化的数——连跑两次，两次的值不一样，下次编译又是另一回事。两个结果都「对」，因为它们都是未定义行为允许的。这里用 `volatile` 让 0 来自运行时，避免编译器把整个表达式当成常量折叠掉。`__builtin_ctz(0)` 在这台机器上几次都是 32，同样不可依赖。

包装只有一行，把规格写进去：

::: compare left-title="直接暴露内建函数" right-title="先处理 0 再调用"

```c
unsigned mdr_clz_u32(uint32_t x) {
    return (unsigned)__builtin_clz(x);
}
```

---

```c
unsigned mdr_clz_u32(uint32_t x) {
    return x == 0 ? 32u : (unsigned)__builtin_clz(x);
}
```

:::

判断只多一条分支，而且编译器常常能把它和后面的指令合并。看两种写法的 `-O2` 汇编：

::: terminal title="zsh - clzasm"

```text
$ gcc -std=c17 -Wall -Wextra -O2 -S clzasm.c -o clzasm.s
$ sed -n '/^clz_builtin:/,/ret/p' clzasm.s
clz_builtin:
	bsrl	%ecx, %eax
	xorl	$31, %eax
	ret
$ sed -n '/^clz_wrapped:/,/ret/p' clzasm.s
clz_wrapped:
	movl	$32, %eax
	testl	%ecx, %ecx
	je	.L3
	bsrl	%ecx, %eax
	xorl	$31, %eax
.L3:
	ret
```

:::

`bsrl` 本身就会把结果留在目标寄存器里，输入为 0 时目标寄存器不变，所以 GCC 用 `bxor` 换算成前导零个数的写法（`bsr` 给出最高位位置，32 位下前导零等于 31 减去它）。包装版多两条指令和一个分支，这是保证 0 的规格必须付出的代价。

同一个道理适用于其余三个函数：

- `__builtin_ctz` 对 0 未定义，包装成返回 32。
- `__builtin_clzll`、`__builtin_ctzll` 对 0 未定义，包装成返回 64。
- MSVC 的 `_BitScanReverse`、`_BitScanForward` 通过返回值表示「找没找到」，`x == 0` 时返回 0，包装成 32。

MSVC 的写法：

```c
unsigned mdr_clz_u32(uint32_t x) {
    unsigned long index;

    return _BitScanReverse(&index, x) ? 31u - (unsigned)index : 32u;
}
```

`_BitScanReverse` 找到最高位 1 时把它的下标写进 `index` 并返回非 0，没找到（`x` 为 0）时返回 0。`31 - index` 换成前导零个数。这段代码在 MSVC 14.51 上与 21.4 的回退版逐个对照，几个典型 32 位取值的结果一致。

字节交换和溢出检查也是同样的处理。`__builtin_bswap32`、`__builtin_bswap64` 对任何输入都有定义，不需要包装；MSVC 用 `_byteswap_ulong`、`_byteswap_uint64`。溢出检查用一个宏三选一：

```c
#if MDR_HAVE_STDCKDINT
#define MDR_CKD_ADD_SIZE(a, b, res) (ckd_add((res), (a), (b)))
#elif MDR_USE_BUILTINS && MDR_HAS_BUILTIN(__builtin_add_overflow)
#define MDR_CKD_ADD_SIZE(a, b, res) __builtin_add_overflow((a), (b), (res))
#else
#define MDR_CKD_ADD_SIZE(a, b, res)                                            \
    ((a) > SIZE_MAX - (b) ? true : (*(res) = (a) + (b), false))
#endif
```

`ckd_add` 与 `__builtin_add_overflow` 都返回「溢出为真」，结果写进第三个参数指向的对象，两者语义一致，直接互换。宏的第三条分支把 21.4 的写法内联展开，`a`、`b` 各求值一次，`res` 只在没溢出时写一次。三条路径的返回值都符合 `mdr_ckd_add_size` 的规格，用同一组测试跑一遍即可确认。

## 5. 优化提示

分支提示告诉编译器哪个方向更可能发生，让它把常见的路径排成直线、少一次跳转：

```c
#if MDR_USE_BUILTINS && (defined(__GNUC__) || defined(__clang__))
#define MDR_LIKELY(x) __builtin_expect(!!(x), 1)
#define MDR_UNLIKELY(x) __builtin_expect(!!(x), 0)
#define MDR_UNREACHABLE() __builtin_unreachable()
#elif MDR_USE_BUILTINS && defined(_MSC_VER)
#define MDR_LIKELY(x) (x)
#define MDR_UNLIKELY(x) (x)
#define MDR_UNREACHABLE() __assume(0)
#else
#define MDR_LIKELY(x) (x)
#define MDR_UNLIKELY(x) (x)
#define MDR_UNREACHABLE() abort()
#endif
```

`!!(x)` 把任意非 0 值压成 1，因为 `__builtin_expect` 的第二参数是 `long`，比较的是取值而不是真值。没有内建函数时回退成 `(x)`，括号保证宏在 `if (MDR_LIKELY(a) && b)` 这类上下文里不被拆开。

`MDR_UNREACHABLE()` 表示「控制流不会到这里」，编译器据此删掉后面的分支。C23 有 `unreachable()`，GCC/Clang 用 `__builtin_unreachable()`，MSVC 用 `__assume(0)`；没有这些手段时回退成 `abort()`。最后这条差别很关键：真的执行到那一刻，`__builtin_unreachable()` 让程序继续跑下去，行为未定义；`abort()` 让它当场终止。调试构建用 `abort()` 更容易发现错误，发布构建用未定义来换优化。

作者的建议：分支提示只在剖析（[第 15 章](/教程/正文/开发与工程基础/15_测量_分析与优化)）证明有用时写，`unreachable` 只在确实不可能到达的地方写。现代处理器的分支预测和编译器的 profile 引导往往比手写的 `MDR_LIKELY` 更准，乱加反而可能让代码变慢。

## 6. 属性的回退

属性（attribute）是给编译器看的附加信息，GCC、Clang 和 C23 的写法各不相同。本库用一组宏包住三个常用的：

```c
#if (defined(__GNUC__) || defined(__clang__)) && !defined(MDR_NO_ATTRIBUTES)
#define MDR_NODISCARD __attribute__((warn_unused_result))
#define MDR_MAYBE_UNUSED __attribute__((unused))
#define MDR_FALLTHROUGH __attribute__((fallthrough))
#define MDR_PRINTF_LIKE(fmt, args) __attribute__((format(printf, fmt, args)))
#else
#define MDR_NODISCARD
#define MDR_MAYBE_UNUSED
#define MDR_FALLTHROUGH
#define MDR_PRINTF_LIKE(fmt, args)
#endif
```

`MDR_PRINTF_LIKE(fmt, args)` 是这四个里最有用的。它告诉编译器「第 `fmt` 个参数是 printf 风格的格式串，第 `args` 个参数起是它的实参」，于是对调用点的检查与调用 `printf` 一样严格。给一个日志函数加上它：

```c
MDR_PRINTF_LIKE(1, 2)
static void mdr_log(const char *fmt, ...) {
    va_list ap;

    va_start(ap, fmt);
    vfprintf(stderr, fmt, ap);
    va_end(ap);
}

MDR_NODISCARD
static int mdr_write_all(const char *path, const char *data);

int main(void) {
    mdr_write_all("out.bin", "abc");
    mdr_log("value = %d\n", "text");
    return 0;
}
```

编译时两条警告一起出现：


`MDR_PRINTF_LIKE` 的属性语法里，`format(printf, 1, 2)` 的两个数字分别是格式串在参数表中的位置和第一个可变参数的位置，对 `mdr_log(fmt, ...)` 是 1 和 2。写错这两个数字，编译器的检查会对错参数，甚至给出莫名其妙的警告。

`MDR_NODISCARD` 让忽略返回值的调用点产生警告，适合「返回值必须看」的函数：分配、写入、打开。它不能强制处理错误，只是把漏掉的地方暴露出来。

定义 `MDR_NO_ATTRIBUTES` 后，四个宏展开为空，同一份源码照样编译，只是不再有这两条警告。在 MSVC 上也是同理：它的 `_Check_return_` 之类的标注写法不同，本库干脆留空。没有属性时代码必须能干净编译，这是「可回退」的另一半。

## 7. 两条路径都要测

`mdr_compiler.h` 的检测只在编译期做一次，编出来的库要么用内建，要么用回退。要保证两条路径结果一致，就得编出两个库，分别链接同一组测试。

构建文件里加一个目标：

```cmake
if(NOT MDR_NO_BUILTINS)
    add_library(mdr_fallback STATIC ${MDR_SOURCES})
    target_include_directories(mdr_fallback PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}/include")
    target_compile_definitions(mdr_fallback PUBLIC MDR_NO_BUILTINS=1)
endif()
```

测试的注册也跟着多一份，`tests/test_*.c` 每个都链接两个库，注册成 `test_bits` 和 `test_bits_fallback` 两个 ctest 测试：

```cmake
foreach(test_src IN LISTS MDR_UNIT_TESTS)
    get_filename_component(test_name "${test_src}" NAME_WE)
    add_executable(${test_name} "${test_src}" tests/check.c)
    target_link_libraries(${test_name} PRIVATE mdr)
    add_test(NAME ${test_name} COMMAND ${test_name})

    if(TARGET mdr_fallback)
        add_executable(${test_name}_fallback "${test_src}" tests/check.c)
        target_link_libraries(${test_name}_fallback PRIVATE mdr_fallback)
        add_test(NAME ${test_name}_fallback COMMAND ${test_name}_fallback)
    endif()
endforeach()
```

第一，换一个编译器看同样的源码。Clang 22 以 `-O2` 编 `mdr_bits.c`，`__builtin_popcount` 在没开 `-mpopcnt` 时没有调用运行库，而是就地展开成一组移位和掩码（每次处理若干位、把相邻位段相加的写法），比 GCC 的 `call __popcountdi2` 少一次函数调用；加了 `-mpopcnt` 之后两者都只剩一条 `popcntl`。回退版在 Clang 下同样是一条循环。三个编译器的共同点是：`MDR_NO_BUILTINS` 一定给出循环，`-mpopcnt` 一定给出 `popcntl`，差别只在「内建函数没有指令可落」时各自怎么办。

第二，MSVC 路径要单独编一次。cmake 在 Windows 上可以用 `-G Ninja` 配 `cl`，或者直接调用 `cl` 编 `mdr_bits.c`：

```text
cl /nologo /W4 /std:c17 /utf-8 /Iinclude src\mdr_string.c src\mdr_memory.c ^
   src\mdr_bits.c src\mdr_ext.c tests\check.c tests\test_bits.c /Fe:test_bits_msvc.exe
.\test_bits_msvc.exe
test_bits: 99 checks, 0 failed
```

`/utf-8` 是必需的，源文件里的中文注释在 MSVC 默认代码页下会被误读。这一步在 MSVC 14.51 上实测通过，`mdr_clz_u32`、`mdr_ctz_u32` 走的是 `_BitScanReverse`、`_BitScanForward`，结果与 GCC 的回退版一致。

CI 里加 MSVC 作业的做法见[第 18 章](/教程/正文/开发与工程基础/18_持续集成)。一条原则：**两个库、同一组测试**。只测默认构建的话，回退分支可能在某次改动后就悄悄坏了，直到有人在一台没有内建函数的平台上编译才暴露。

### 8.3 综合与挑战

<Exercise id="22168" :d="6" :w="4" scope="**">
