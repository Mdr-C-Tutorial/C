# 21.3 内存函数

把一个数组的五个元素整体后移一位，最省事的写法是 `mdr_memcpy(a + 1, a, 5 * sizeof a[0])`。不加优化选项编译运行，打印出来的却是 `1 1 1 1 1 1`：每个元素都被第一个元素覆盖了。源区域和目标区域重叠在一起，从前向后一个字节一个字节地复制，刚写下去的值马上又被当成源读了出来。`memcpy` 的规格里写着「两个区域不重叠」，这一行违反了前置条件。

这一节实现五个内存函数：`mdr_memmove`、`mdr_memcmp`、`mdr_memchr`、`mdr_memccpy`、`mdr_memset_explicit`。它们和字符串函数的区别只有一个：不看终止空字符，长度由参数给出，因此可以处理二进制数据和没有终止符的缓冲区。写完之后还会看两件编译器做的事：把逐字节的循环换成对 `memcpy` 的调用，以及把「清空密码缓冲区」的写入整个删掉。

## 1. 按字节访问对象

内存函数的参数是两个 `void *` 和一个 `size_t`。`void *` 可以接收任何对象指针，函数内部把它转成 `unsigned char *`，逐字节读写。为什么是 `unsigned char` 而不是 `char`：`char` 可能有符号，做下标或参与算术时会出现负值；`unsigned char` 保证每个字节是 0 到 255 的值，并且 C 规定任何对象都可以通过 `unsigned char` 的指针访问它的对象表示（object representation），规则见[对象表示](/教程/正文/语法和标准库/16_对象与内存模型/16_2_对象表示)。

第一部分的两个函数已经在这个库里：`mdr_memset` 把 `ch` 转成 `unsigned char` 后重复写入，`mdr_memcpy` 从源到目标逐字节复制。这一节的五个函数接着它们在同一个文件里写。

```c
void *mdr_memset(void *dest, int ch, size_t count) {
    unsigned char *p = (unsigned char *)dest;
    unsigned char byte = (unsigned char)ch;

    MDR_ASSERT(dest != NULL || count == 0);
    for (size_t i = 0; i < count; i++) {
        p[i] = byte;
    }
    return dest;
}
```

`ch` 的类型是 `int` 而不是 `char`，这与标准库一致：传 `0xA5` 这样的值进去，只有低 8 位被写入；传 `0x1FF` 进去，写入的是 `0xFF`。测试里专门有一条检查这一点。

## 2. 重叠与 memmove

回到开头那行代码。源和目标都在 `a` 里，目标比源高一个元素，两者重叠。用 `mdr_memcpy` 逐字节从前向后复制，每一步读到的源字节可能已经被前一步写坏。设源区间是 `[s, s+n)`，目标区间是 `[d, d+n)`，两个区间有交叠时，只有一种复制顺序不会让写操作踩到还没读的源字节：`d < s` 时目标在源的低地址一侧，从前向后复制，写到的位置总在还没读到的位置之前；`d > s` 时目标在高地址一侧，从后向前复制；`d == s` 时什么也不用做。

`mdr_memmove` 按这个判断分两个方向：

```c
void *mdr_memmove(void *dest, const void *src, size_t count) {
    unsigned char *d = (unsigned char *)dest;
    const unsigned char *s = (const unsigned char *)src;

    MDR_ASSERT(dest != NULL || count == 0);
    MDR_ASSERT(src != NULL || count == 0);
    if ((uintptr_t)d < (uintptr_t)s) {
        for (size_t i = 0; i < count; i++) {
            d[i] = s[i];
        }
    } else if ((uintptr_t)d > (uintptr_t)s) {
        for (size_t i = count; i > 0; i--) {
            d[i - 1] = s[i - 1];
        }
    }
    return dest;
}
```

比较两个指针时先转成 `uintptr_t`。两个指针指向同一个数组的元素时可以直接比大小；指向不同对象时，标准 C 没有规定比较的结果。转成整数之后比较的是地址值，含义明确，各家实现普遍这么做。

用 `mdr_memcpy` 和 `mdr_memmove` 做同一件事，结果一眼能分开：

```c
#include "mdr_memory.h"
#include <stdio.h>
#include <string.h>

static void show(const char *label, const char *buf, size_t n) {
    printf("%-32s%.*s\n", label, (int)n, buf);
}

int main(void) {
    char buf[16];

    memcpy(buf, "abcdef", 7);
    mdr_memcpy(buf + 1, buf, 5);
    show("mdr_memcpy(buf + 1, buf, 5):", buf, 6);

    memcpy(buf, "abcdef", 7);
    mdr_memmove(buf + 1, buf, 5);
    show("mdr_memmove(buf + 1, buf, 5):", buf, 6);

    memcpy(buf, "abcdef", 7);
    memmove(buf + 1, buf, 5);
    show("memmove(buf + 1, buf, 5):", buf, 6);
    return 0;
}
```

```text

$ ./ov
```

:::

`mdr_memcpy` 把 `"abcdef"` 的前 5 个字节复制到偏移 1 处，第一个字节 `'a'` 写进去之后，第二步读源的第 2 个字节时读到的已经是刚写的 `'a'`，于是后面的每一步都复制出 `'a'`，最终得到 `aaaaaa`。`mdr_memmove` 发现目标地址更高，从后向前复制，得到正确的 `aabcde`。

标准没有要求 `memcpy` 按哪个方向复制，换一台机器、换一个运行库、换一个优化级别，结果都可能变。违反前置条件的程序得到任何结果都在允许范围内，其中最坏的一种是「碰巧看起来正确」，它会让人以为代码没有问题。

```c

/* 前置条件要求两个区域不重叠 */

```

---

```c
int a[6] = {1, 2, 3, 4, 5, 0};

/* 允许重叠，内部按方向选择复制顺序 */
mdr_memmove(a + 1, a, 5 * sizeof a[0]);
```

:::

::: concept mem-memcpy-vs-memmove title="memcpy 与 memmove 的唯一区别是能否重叠"

`memcpy` 要求源和目标区域不重叠，违反时行为未定义；`memmove` 允许重叠，当目标位于源之后时从后向前复制，其余情况从前向后复制。两者的参数、返回值和复制结果在区域不重叠时完全相同。`memmove` 通常稍慢，因为它要先比较两个地址。

:::

验证这种「所有偏移组合都对」的函数，逐条写测试不如穷举。16 字节的缓冲区里，源偏移、目标偏移、长度三个参数各取 0 到 15，只保留两个区域都落在缓冲区里的组合，一共 1751 种，全部跑一遍用不了几毫秒：

```c
#include "mdr_memory.h"
#include <stdio.h>
#include <string.h>

int main(void) {
    unsigned char a[16];
    unsigned char b[16];
    unsigned long cases = 0;
    unsigned long bad = 0;

    for (size_t src_off = 0; src_off < 16; src_off++) {
        for (size_t dst_off = 0; dst_off < 16; dst_off++) {
            for (size_t len = 0; len < 16 && len + src_off <= 16 && len + dst_off <= 16;
                 len++) {
                for (size_t i = 0; i < 16; i++) {
                    a[i] = (unsigned char)(i * 7u + 3u);
                    b[i] = a[i];
                }
                mdr_memmove(a + dst_off, a + src_off, len);
                memmove(b + dst_off, b + src_off, len);
                cases++;
                if (memcmp(a, b, 16) != 0) {
                    bad++;
                }
            }
        }
    }
    printf("cases = %lu, mismatches = %lu\n", cases, bad);
    return 0;
}
```

1751 种组合，与标准库的 `memmove` 逐字节相同。这个程序也在 Linux 上用 `-fsanitize=address,undefined` 编译运行过，结果一样，没有越界报告。穷举的思路和防护缓冲区的做法在 21.7 展开。

## 3. 比较与查找

`mdr_memcmp` 与 `mdr_strcmp` 的差别只在「什么时候停」：字符串版本遇到终止空字符就停，内存版本只看长度：

```c
int mdr_memcmp(const void *lhs, const void *rhs, size_t count) {
    const unsigned char *p1 = (const unsigned char *)lhs;
    const unsigned char *p2 = (const unsigned char *)rhs;

    MDR_ASSERT(lhs != NULL || count == 0);
    MDR_ASSERT(rhs != NULL || count == 0);
    for (size_t i = 0; i < count; i++) {
        if (p1[i] != p2[i]) {
            return (int)p1[i] - (int)p2[i];
        }
    }
    return 0;
}
```

因此它能比较中间夹着零字节的数据。返回值和 `mdr_strcmp` 一样只保证符号，测试里写 `< 0` 而不是 `== -1`。

`mdr_memchr` 是同样的道理：

```c
void *mdr_memchr(const void *ptr, int ch, size_t count) {
    const unsigned char *p = (const unsigned char *)ptr;
    unsigned char c = (unsigned char)ch;

    MDR_ASSERT(ptr != NULL || count == 0);
    for (size_t i = 0; i < count; i++) {
        if (p[i] == c) {
            return (void *)(p + i);
        }
    }
    return NULL;
}
```

它在前 `count` 个字节里找 `(unsigned char)ch`，遇到零字节不停止。这正是它与 `mdr_strchr` 的分界：后者把零字节当作字符串的结尾，前者把它当作普通数据。

```c
#include "mdr_memory.h"
#include <stdio.h>
#include <string.h>

int main(void) {
    const unsigned char data[] = {'a', 'b', 0, 'c', 'd'};
    const unsigned char *m = mdr_memchr(data, 'c', sizeof data);
    const char *s = strchr((const char *)data, 'c');

    printf("区域: a b NUL c d\n");
    printf("mdr_memchr 找到 'c' 的偏移: %d\n", m != NULL ? (int)(m - data) : -1);
    printf("strchr 找到 'c' 的偏移:     %d\n",
           s != NULL ? (int)(s - (const char *)data) : -1);
    return 0;
}
```

```text
$ ./mc
区域: a b NUL c d

```

两个函数都在 `'c'` 上找，前者找到了偏移 3 的那个字节，后者在中途的零字节处就停下了，报告「没找到」。解析二进制格式、在网络缓冲区里找标记字节，都该用 `memchr`。

## 4. memccpy

`mdr_memccpy` 复制到遇见指定字节或复制满 `count` 个字节为止：

```c
void *mdr_memccpy(void *restrict dest, const void *restrict src, int c,
                  size_t count) {
    unsigned char *d = (unsigned char *)dest;
    const unsigned char *s = (const unsigned char *)src;
    unsigned char byte = (unsigned char)c;

    MDR_ASSERT(dest != NULL || count == 0);
    MDR_ASSERT(src != NULL || count == 0);
    for (size_t i = 0; i < count; i++) {
        d[i] = s[i];
        if (d[i] == byte) {
            return d + i + 1;
        }
    }
    return NULL;
}
```

返回的是目标区域中**紧跟**那个字节的指针，没遇到时返回 `NULL`。这个返回值可以直接当作下一次写入的位置：复制一段以 `':'` 结尾的文本，把返回的指针减一，就得到了终止空字符该放的地方。

标准库的 `memccpy` 在 C23 之前是 POSIX 的东西。用 `-std=c17` 在 glibc 上编译时，头文件不会声明它，得到的是 `implicit declaration of function 'memccpy'`；改用 `-std=gnu17`、定义 `_DEFAULT_SOURCE`，或者按 C23 编译就能通过。MinGW 的 UCRT 不管标准模式都声明它。这种「同一份源码换个编译模式就找不到函数」的情况，是 21.5 的主题，也是本章为每个函数准备 `mdr_` 版本的理由之一。

它能不重复扫描地拼接多个字符串。下面这个函数用空格连接一个单词数组，总时间与总长度成正比：

```c
#include "mdr_memory.h"
#include <stdio.h>

/* 用空格连接 n 个单词，返回写入的字符数；放不下时返回 -1。 */
static int join_words(char *dst, size_t size, const char *const words[],
                      size_t n) {
    char *p = dst;

    if (size == 0) {
        return -1;
    }
    *p = '\0';
    for (size_t i = 0; i < n; i++) {
        char *after;

        if (i > 0) {
            after = mdr_memccpy(p, " ", '\0', size - (size_t)(p - dst));
            if (after == NULL) {
                dst[size - 1] = '\0';
                return -1;
            }
            p = after - 1;
        }
        after = mdr_memccpy(p, words[i], '\0', size - (size_t)(p - dst));
        if (after == NULL) {
            dst[size - 1] = '\0';
            return -1;
        }
        p = after - 1;
    }
    return (int)(p - dst);
}

int main(void) {
    const char *words[] = {"alpha", "beta", "gamma", "delta"};
    char buf[64];
    int r;

    r = join_words(buf, sizeof buf, words, 4);
    printf("size=64: r=%d, \"%s\"\n", r, buf);

    r = join_words(buf, 12, words, 4);
    printf("size=12: r=%d, \"%s\"\n", r, buf);

    r = join_words(buf, 6, words, 4);
    printf("size=6:  r=%d, \"%s\"\n", r, buf);
    return 0;
}
```

这里用 `'\0'` 当 `mdr_memccpy` 的分隔字节：每个单词在终止空字符处停下，函数返回它后面的位置，减一就是新的末尾。剩余空间用 `size - (p - dst)` 算出来，复制永远不会越过 `dst` 的末尾。

::: terminal title="zsh - join"

```text
$ gcc -std=c17 -Wall -Wextra -O2 -Iinclude -o join join.c src/mdr_memory.c
$ ./join
size=64: r=22, "alpha beta gamma delta"
size=12: r=-1, "alpha beta "
size=6:  r=-1, "alpha"
```

:::

第三次调用只剩 6 个字节，`alpha` 加终止符刚好用掉 6 个，再多一个字符都放不下，返回 `-1`。缓冲区里保留的是截断处之前的内容，并且一定有终止符。

## 5. 清除敏感数据

下面这个函数把一个口令复制到栈上的缓冲区，比较完之后清零，看起来没问题：

```c
size_t copy_and_wipe(const char *input) {
    char buf[32];
    size_t n = (size_t)snprintf(buf, sizeof buf, "%s", input);

    memset(buf, 0, sizeof buf);
    return n;
}
```

用 `-O2` 生成汇编，`memset` 那一行不见了：

::: terminal title="zsh - gcc -S"

```text
$ gcc -std=c17 -Wall -Wextra -O2 -fno-asynchronous-unwind-tables -S wipe_plain.c
$ sed -n '/copy_and_wipe:/,/ret/p' wipe_plain.s
copy_and_wipe:
	subq	$40, %rsp
	movq	%rdi, %rcx
	leaq	.LC0(%rip), %rdx
	xorl	%eax, %eax
	movq	%rsp, %rdi
	movl	$32, %esi
	call	snprintf@PLT
	addq	$40, %rsp
	cltq
	ret
```

:::

这里加了 `-fno-asynchronous-unwind-tables`，只是把与本次讨论无关的 `.cfi_*` 行去掉，生成的指令不受影响。这段汇编来自 Debian 13 上的 GCC 14.2，寄存器名和调用约定是 x86-64 Linux 的；Windows 上的 MinGW-w64 GCC 13.2 用 `rcx`、`rdx`、`r8` 传递前三个参数，生成的代码思路相同。`snprintf` 之后直接返回，一个字节都没写。编译器认为 `buf` 随后不再被读取，这次写入不影响程序的任何可观察结果，于是把整段删除。

`mdr_memset_explicit` 让这次写入不可删除：

```c
void *mdr_memset_explicit(void *dest, int ch, size_t count) {
    volatile unsigned char *p = (volatile unsigned char *)dest;
    unsigned char byte = (unsigned char)ch;

    MDR_ASSERT(dest != NULL || count == 0);
    for (size_t i = 0; i < count; i++) {
        p[i] = byte;
    }
    return dest;
}
```

指针带上 `volatile`，每一次写入都是一次可观察的访问，编译器不能把循环删掉，也不能合并掉其中任何一步。同一份程序换上这个函数，汇编里就多出了清零的代码：

```text

	movq	%rdi, %rcx
	leaq	.LC0(%rip), %rdx
	xorl	%eax, %eax
	movq	%rsp, %rdi
	movl	$32, %esi

	addq	$40, %rsp

```

```text
	movq	%rdi, %rcx
	leaq	.LC0(%rip), %rdx
	movl	$32, %esi
	pushq	%rbx

	movl	%eax, %ebx
	call	mdr_memset_explicit@PLT

```

:::

两份汇编都用 GCC 14.2 在 Debian 13 上以 `-O2 -fno-asynchronous-unwind-tables` 生成。右栏的 `call mdr_memset_explicit` 后面紧跟着返回，说明这次调用被完整保留。

::: concept mem-volatile-observable title="volatile 访问是可观察行为"

`volatile` 告诉编译器：这个对象的每一次读或写都必须按程序写的次数、顺序真正发生，不能省略、合并或重排。清除敏感数据正是需要这种保证的场合：写入之后没有任何代码再读这块内存，对普通对象来说这次写入没有可观察效果，编译器有权删除；换成 `volatile` 访问之后，删除它就改变了程序的可观察行为。

:::

标准库的对应函数叫 `memset_explicit`，C23 才有；此前各家提供了自己的版本，glibc 和 BSD 的 `explicit_bzero`、Windows 的 `SecureZeroMemory`，语义相同。glibc 2.41 的头文件里既没有 `memset_explicit` 的声明，libc 里也没有这个符号；MinGW-w64 的 UCRT 同样没有。本章的 `mdr_` 版本不是练习品，而是这两个平台上真能用的实现。

## 6. 编译器眼中的内存函数

`mdr_memcpy` 的循环在 `-O2` 下会变成一次库调用。查看它编出来的汇编（用 `-DNDEBUG` 关掉断言以简化输出，MinGW-w64 GCC 13.2）：

::: details `mdr_memcpy` 在 -O2 下的汇编

```text
mdr_memcpy:
	subq	$40, %rsp
	.seh_stackalloc	40
	.seh_endprologue
	testq	%r8, %r8
	je	.L8
	call	memcpy
	movq	%rax, %rcx
.L8:
	movq	%rcx, %rax
	addq	$40, %rsp
	ret
	.seh_endproc
```

:::

函数体里自己写的逐字节循环不见了，取而代之的是一条 `call memcpy`。GCC 有一个优化遍叫 loop distribution，专门把逐字节的复制、填充循环识别成库调用。

用一个独立的函数观察这件事，看得更清楚：

```c
#include <stddef.h>

void *byte_copy(void *restrict dest, const void *restrict src, size_t count) {
    unsigned char *d = dest;
    const unsigned char *s = src;

    for (size_t i = 0; i < count; i++) {
        d[i] = s[i];
    }
    return dest;
}
```

`restrict` 在这里不是装饰：只有它能告诉编译器两个区域不重叠，循环才会被替换。去掉它，同样的循环原样保留。`while (count-- > 0) { *d++ = *s++; }` 和下标循环两种写法都能识别。关掉这个优化遍：

::: terminal title="zsh - gcc -S"

```text
$ gcc -std=c17 -Wall -Wextra -O2 -S bytecopy.c
$ grep -E 'call|movb' bytecopy.s
	call	memcpy
$ gcc -std=c17 -Wall -Wextra -O2 -fno-tree-loop-distribute-patterns -S bytecopy.c
$ grep -E 'call|movb' bytecopy.s
	movb	%r10b, (%rax,%r9)
```

:::

输出来自 Windows 上的 MinGW-w64 GCC 13.2；Linux 上的 GCC 14.2 两行分别是 `call memcpy@PLT` 与 `movb %r8b, (%rax,%rcx)`，结论相同，寄存器名随调用约定变化。第一行里循环被换成了 `call memcpy`，第二行加了 `-fno-tree-loop-distribute-patterns` 之后，逐字节的 `movb` 回到循环里。这正是 `mdr_` 前缀的价值之一：函数名不叫 `memcpy`，编译器换成的库调用指向标准库，`mdr_memcpy` 自己不会卷进去。

如果函数本身就叫 `memcpy` 呢？编译器把函数体内的循环也当成一次 `memcpy` 调用，生成一条指向 `memcpy` 的 `call`，也就是指向函数自己：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* 与标准库同名；长度来自命令行，编译期无法确定 */
void *memcpy(void *restrict dest, const void *restrict src, size_t count) {
    unsigned char *d = dest;
    const unsigned char *s = src;

    while (count-- > 0) {
        *d++ = *s++;
    }
    return dest;
}

int main(int argc, char *argv[]) {
    char buf[64];
    size_t n = argc > 1 ? (size_t)atoi(argv[1]) : 6;

    memcpy(buf, "hello", n);
    printf("%s\n", buf);
    return 0;
}
```

复制长度从命令行读进来，编译器没法把它优化成常数，函数体里的循环照常参与识别。编译出来是这样的（Windows，GCC 13.2，`-O2`）：

```text

	.seh_endprologue
	testq	%r8, %r8
	je	.L2

	movq	%rax, %rcx
.L2:
	movq	%rcx, %rax
	addq	$40, %rsp
	ret
	.seh_endproc
```

修法有两个：`-fno-builtin` 关掉全部内建函数识别，`-ffreestanding` 声明这是独立实现环境，编译器不再假定标准库存在。C 库和嵌入式固件用这两个选项编译自己的字符串、内存函数，原因就在这里。本章的 `mdr_` 版本不需要它们，因为名字避开了标准库。

21.1 里 `strlen("abc")` 在编译期被折叠成 3，是同一类现象的另一个方向：编译器按内建语义理解标准库名字，把调用替换成自己生成的代码。内存函数这边更隐蔽，替换发生在**函数体内部**，写循环的人看不出问题，直到运行起来栈溢出。

## 7. 标准库为什么更快

同一台机器上，glibc 的 `memcpy` 处理大块数据时比逐字节循环快得多。原因不神秘：

1. 按机器字复制。一次搬 8 个字节，而不是 1 个。开头和结尾不足一个字的部分单独处理。
2. 处理对齐。源或目标没有按字对齐时，先复制到对齐，中间用字复制，尾巴再逐字节收尾。
3. 使用 SIMD 指令。现代实现一次搬 16、32 甚至 64 个字节。
4. 编译器专用的别名属性。标准库实现内部常用带 `__may_alias__` 属性的整数类型按字读写，告诉编译器这些访问可以与别的类型别名，避免生成保守的代码。这个属性是 GCC 扩展，不属于标准 C。

本章的 `mdr_` 版本全部保持逐字节写法。这不是偷懒：用指针类型转换按字读写，会让程序违反有效类型规则（effective type），在严格别名分析下产生未定义行为，规则见[对象表示](/教程/正文/语法和标准库/16_对象与内存模型/16_2_对象表示)。逐字节通过 `unsigned char` 访问对象表示，是标准保证可行的写法。

需要按字读取时有一个标准允许的捷径：用 `memcpy` 把一个字复制进整型对象。

```c
#include <stdint.h>
#include <string.h>

uint32_t load_word(const void *p) {
    uint32_t w;

    memcpy(&w, p, sizeof w);
    return w;
}
```

编译器知道 `memcpy` 的语义，对这种小固定长度的复制直接生成一条载入指令：

::: terminal title="zsh - gcc -S"

```text
$ gcc -std=c17 -O2 -S wordload.c
$ sed -n '/load_word:/,/ret/p' wordload.s
load_word:
.LFB0:
	.cfi_startproc
	movl	(%rdi), %eax
	ret
```

:::

这是 Debian 13 上 GCC 14.2 的输出；Windows 上的 GCC 13.2 生成 `movl (%rcx), %eax`，差别只在参数寄存器的名字。没有函数调用，没有逐字节循环，就是一条 32 位载入。想从缓冲区里读一个整数，这样写既符合标准，又和直接访问一样快。

逐字节的 `mdr_memmove` 比标准库慢，原因之一是每次只搬一个字节。按机器字搬的版本可以这样写，既保持标准允许的访问方式，又利用 `memcpy` 生成单条载入指令：

```c
/* 每次把一个 size_t 大小的块经 memcpy 读出再写入，尾部不足一块的逐字节处理。 */
void *mdr_memmove_words(void *dest, const void *src, size_t count);
```

要求：

1. 保持 `mdr_memmove` 的方向判断：目标地址更低时从前向后，更高时从后向前，相等时直接返回。前后两个方向的块内复制也必须遵守这个方向，不能只对整块调 `memcpy`。
2. 用第 2 节的 1751 组穷举与标准库 `memmove` 对照，`mismatches` 必须为 0。
3. 测三种实现的吞吐：逐字节版、按字版、库函数 `memmove`。缓冲区取 1 MiB，重复搬移 200 次，用 `clock()` 计时，各跑 5 次取中位数，报告以库函数为 1 的相对速度。同一台机器上重复测量，结果允许有百分之几的波动。
4. 解释按字版在源和目标都没有对齐时为什么不会变慢得离谱，以及为什么块内复制必须用 `memcpy` 而不是 `*(size_t *)d = *(size_t *)s`。

验收：穷举 0 处不一致；三种实现的相对速度有数字；第 4 问的答案里提到有效类型与对齐两条理由。
