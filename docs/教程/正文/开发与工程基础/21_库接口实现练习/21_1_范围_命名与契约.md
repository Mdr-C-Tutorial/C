# 21.1 范围、命名与契约

把一个自己写的 `strlen` 加进项目，编译没有警告，运行结果却分成两半：`strlen("abc")` 得到 3，`strlen(argv[0])` 得到 42。两个调用看起来一样，问题不在循环写错了，而在函数的名字。这一节说明本章练哪些接口、为什么不能沿用标准库的名字、怎样把一份规格拆成能照着实现和测试的条目，最后把后面六节共用的工程骨架搭起来。

## 1. 为什么自己实现

标准库的实现是长期优化的产物。glibc 的 `strlen` 按机器字读取，musl 的 `memcpy` 按对齐和长度分出几条路径，glibc 的 `strstr` 对较长的模式串用 Two-Way 算法。这些实现值得读，但读之前要先把接口本身弄清楚。

自己写一遍的用处是练两件事：按字节推理，和读规格。写 `mdr_strnlen` 时要回答「最多读几个字节」「范围内没有空字符时返回什么」；写 `mdr_memmove` 时要判断源区域和目标区域谁在前。每个问题都能在规格里找到答案，答错有测试兜底。这种训练直接服务于以后读任何库的文档。

生产代码里的原则相反：标准库已经提供的功能优先调用标准库，理由见[标准库的使用契约](/教程/正文/语法和标准库/18_标准库的使用契约)。标准库的实现经过更多平台和更多输入的检验，还能被编译器针对当前机器优化，自己写一份很难在正确性和速度上同时超过它。

有两种情况值得自己写。一是目标平台缺少的扩展函数：Windows 的 C 运行库没有 `strlcpy`、`strsep`、`memmem`，跨平台项目往往自带实现，21.5 就做这件事。二是独立实现（freestanding implementation）：嵌入式环境里没有完整的标准库，字符串和内存函数通常由项目自己提供。

本章的 mdr 库不打算发布。它的用途是把规格、实现、测试和构建完整走一遍，代码放在 `code/开发与工程基础/21_库接口实现练习/`。

## 2. 本章的范围

选进本章的接口要同时满足三条：

1. 只用普通 C 能写出来，不依赖编译器扩展或内建函数。
2. 不需要操作系统提供服务，例如取得存储、读写文件、查询区域设置。
3. 不依赖 ABI 或无法用普通 C 替代的编译器机制，例如遍历可变参数、保存寄存器。

第 3 条最容易被忽略。`setjmp` 和 `longjmp` 看起来只是两个普通函数，实际上要保存调用点的寄存器和栈帧，普通 C 没有表达这件事的手段。

| 接口组 | 小节 | 代表函数 |
| --- | --- | --- |
| `<string.h>` 中与区域设置无关的字符串函数 | 21.2 | `strcpy`、`strcat`、`strstr`、`strtok` |
| 内存函数 | 21.3 | `memmove`、`memcmp`、`memchr`、`memccpy` |
| C23 `<stdbit.h>` 对应的位操作 | 21.4 | `clz`、`ctz`、`bit_ceil`、`bswap` |
| 各平台命名不统一的扩展函数 | 21.5 | `strlcpy`、`strlcat`、`strsep`、`memmem` |
| 有普通 C 回退的内建功能 | 21.6 | `__builtin_popcount`、`__builtin_expect` |

排除在外的接口和原因：

| 接口 | 不纳入的原因 |
| --- | --- |
| `malloc`、`free` | 存储要从操作系统取得，纯 C 无法凭空造出内存 |
| `printf` 家族 | 依赖可变参数机制与区域设置，规模也远超其他函数 |
| `setjmp`、`longjmp` | 保存和恢复寄存器与栈帧，依赖 ABI |
| `va_arg` | 编译器内建，无法用普通 C 遍历参数 |
| 原子操作 | 需要硬件指令或编译器支持，C11 起由 `<stdatomic.h>` 提供 |
| `strcoll`、`toupper`、`isalpha` | 结果取决于当前区域设置 |
| `sin`、`sqrt`、`pow` | 数值精度是另一门学问 |

## 3. 命名

### 3.1 标准库的名字是保留的

在宿主实现（hosted implementation）中，标准库提供的外部标识符是保留的，无论程序包含了哪个头文件。再定义一份同名的外部函数属于未定义行为（undefined behavior），规则见[保留标识符](/教程/正文/语法和标准库/2_值_对象_类型与声明/2_5_保留标识符)。

编译器不一定报错。下面这份程序编译时一声不吭，只是结果不对。

```c
#include <stdio.h>
#include <string.h>

/* 自己定义的 strlen：总是返回 42，以便看出调用的是哪一份代码 */
size_t strlen(const char *s) {
    (void)s;
    return 42;
}

int main(int argc, char *argv[]) {
    (void)argc;
    printf("strlen(\"abc\")   = %d\n", (int)strlen("abc"));
    printf("strlen(argv[0]) = %d\n", (int)strlen(argv[0]));
    return 0;
}
```

在 Linux 上用 GCC 14.2 分别以 `-O0`、`-O2` 和 `-O2 -fno-builtin` 构建：

::: terminal title="zsh - mystrlen"

```text
$ gcc -std=c17 -Wall -Wextra -O0 -o mystrlen mystrlen.c
$ ./mystrlen
strlen("abc")   = 3
strlen(argv[0]) = 42
$ gcc -std=c17 -Wall -Wextra -O2 -o mystrlen mystrlen.c
$ ./mystrlen
strlen("abc")   = 3
strlen(argv[0]) = 42
$ gcc -std=c17 -Wall -Wextra -O2 -fno-builtin -o mystrlen mystrlen.c
$ ./mystrlen
strlen("abc")   = 42
strlen(argv[0]) = 42
```

:::

Windows 上的 MinGW-w64 GCC 13.2 输出逐行相同。`-O0` 下结果照样是 3，说明这件事和优化级别无关。

### 3.2 编译器按内建函数处理这些名字

GCC 把许多标准库函数名认作内建函数（built-in function）。遇到 `strlen("abc")`，实参是编译期就能确定的字符串字面量，它直接算出 3，根本不生成调用。`strlen(argv[0])` 的值要到运行时才知道，编译器于是生成一次调用，落到自定义的那份实现上，得到 42。加上 `-fno-builtin` 关闭这层识别，两个调用才都走自定义函数。

`-fno-builtin` 关闭全部识别，`-fno-builtin-strlen` 只关闭 `strlen` 一个。这不是编译器的疏漏：C 标准把这些名字保留给标准库，编译器因此有权假定 `strlen` 指的是标准库的 `strlen`，并按它的语义做优化。

即使在 `-O2` 下通过函数指针间接调用，也挡不住这层替换。同一份程序里加一行把 `strlen` 的地址存进函数指针再调用，`-O0` 得到 42，`-O2` 得到 3。编译器知道这个指针只能指向 `strlen`，就把调用折叠成了内建求值。

::: concept mdr-reserved-library-names title="标准库的名字不能用来自定义函数"

标准库提供的外部标识符在宿主实现中是保留的，重新定义同名函数属于未定义行为。编译器还常把这些名字当作内建函数处理，使调用在编译期就被替换成内建语义。给练习实现加 `mdr_` 前缀，可以同时避开保留名和内建处理，读代码的人也能一眼看出调用的是哪一份实现。

:::

### 3.3 前缀留给标准库

C 标准在「Future library directions」一节里规定，以 `str`、`mem`、`wcs` 加一个小写字母开头的函数名留给 `<string.h>` 将来添加新函数，并且这些外部名字不论程序包含哪个头文件都是保留的。C23 把这类名字改称可能保留（potentially reserved）：实现提供了这个名字，它就是保留的；没有提供时，用户声明它不构成未定义行为，但程序换一个实现就可能撞上。

这条规则有真实的案例。glibc 2.38 把 OpenBSD 的 `strlcpy` 和 `strlcat` 加进了自己的 `string.h`。direwolf 等一批项目此前自带同名实现，升级后构建失败。失败的直接原因不是链接冲突，而是项目为了让自带实现多带调试信息，把 `strlcpy` 定义成了宏：

```c
/* 仿照 direwolf 1.6 的 direwolf.h：把 strlcpy 重命名到自己的实现 */

#define strlcpy(dst, src, siz) strlcpy_debug(dst, src, siz, __FILE__, __LINE__)

#include <stddef.h>
#include <stdio.h>
#include <string.h>
```

glibc 的 `string.h` 声明了 `strlcpy`，宏把这条声明也改了名，于是 `char *` 后面跟上了 `__FILE__` 这样的字符串常量。在这台 Linux 机器上（glibc 2.41，`-std=gnu17`）：

::: terminal title="zsh - gcc"

```text
$ gcc -std=gnu17 -Wall -Wextra -o names names.c
names.c:3:61: error: expected declaration specifiers or ‘...’ before string constant
    3 | #define strlcpy(dst, src, siz) strlcpy_debug(dst, src, siz, __FILE__, __LINE__)
      |                                                             ^~~~~~~~
names.c:3:71: error: expected declaration specifiers or ‘...’ before numeric constant
```

:::

同一个文件在 MinGW-w64 GCC 13.2 上正常编译运行，因为 Windows 的 C 运行库没有声明 `strlcpy`。在 Linux 上改用 `-std=c17` 也能编译，严格模式不声明 `strlcpy`，宏没有东西可改。同一份源码忽而通过忽而报错，取决于库的声明和功能测试宏，这类问题在第 16 章展开。

按 C17 的规则，direwolf 自带 `strlcpy` 这个外部函数名本来就是保留的，冲突只是把一处隐藏的未定义行为变成了编译错误。加前缀的练习实现没有这个问题。

### 3.4 本章的命名约定

- 函数名是 `mdr_` 加标准名：`mdr_strlen`、`mdr_memcpy`、`mdr_strtok`。
- 位操作函数带宽度后缀 `_u32`、`_u64`，与第一部分已经写过的 `mdr_popcount_u32` 一致：`mdr_clz_u64`、`mdr_bswap32`。
- 头文件不叫 `string.h`、`memory.h`，而是 `mdr_string.h`、`mdr_memory.h`、`mdr_bits.h`、`mdr_ext.h`、`mdr_compiler.h`。
- 只在模块内部使用的函数声明为 `static`，不进入头文件。

头文件名也要避开标准库的。把项目头文件命名成 `string.h`，再用 `-I` 把它所在目录加进包含路径，`#include <string.h>` 会优先找到项目这一份，标准声明全部消失。下面是在包含路径里放了一个自制 `string.h` 之后的结果（Windows，MinGW-w64 GCC 13.2）：

## 4. 读懂一份规格

一节标题里的「契约」借自契约式设计（Design by Contract）：前置条件（precondition）是调用方的义务，后置条件（postcondition）是函数给出的保证。后文统一用「规格」（specification）、「前置条件」、「后置条件」这几个词。

一份能照着实现的规格包含五项：参数、前置条件、效果、返回值、后置条件。以 `memcpy` 为例：

```c
void *memcpy(void *restrict dest, const void *restrict src, size_t count);
```

- 参数：`dest` 是目标区域，`src` 是源区域，`count` 是要复制的字节数。
- 前置条件：两个区域各有至少 `count` 个可访问的字节，且互不重叠。`restrict` 只是把「不重叠」写进了类型，重叠时行为未定义。
- 效果：把 `src` 开头的 `count` 个字节复制到 `dest` 开头。
- 返回值：`dest`。
- 后置条件：`dest` 的前 `count` 个字节等于 `src` 原来的内容。

`strncpy` 的规格常被读错，逐项拆开就清楚了：

```c
char *strncpy(char *restrict dest, const char *restrict src, size_t count);
```

- 参数：`dest`、`src`、`count`。
- 前置条件：`dest` 至少 `count` 个可写字节；`src` 至少可读 `min(strlen(src) + 1, count)` 个字节；两个区域不重叠。
- 效果：最多复制 `count` 个字节。`src` 作为字符串短于 `count` 时，复制完后继续补空字符，直到写满 `count` 个字节。
- 返回值：`dest`。
- 后置条件：`src` 短于 `count` 时，`dest` 是一个内容等于 `src` 的字符串，后面补满空字符；`src` 不短于 `count` 时，`dest` 的前 `count` 个字节等于 `src` 的前 `count` 个字节，但不带终止空字符。

| 项目 | `memcpy` | `strncpy` |
| --- | --- | --- |
| 前置条件 | 两个区域各至少 `count` 字节且不重叠 | `dest` 至少 `count` 字节，源可读范围足够，不重叠 |
| 效果 | 复制 `count` 个字节 | 最多复制 `count` 个字节，源较短时补空字符到 `count` 个 |
| 返回值 | `dest` | `dest` |
| 后置条件 | 前 `count` 个字节与源相同 | 源较短时得到字符串，否则前 `count` 个字节与源相同且无终止空字符 |

这里能看出前置条件和后置条件的分工。`strncpy` 的后置条件在两种情况下差别很大，而它到底落在哪种情况，取决于调用方传进来的 `src` 有多长。把三种长度各跑一遍，目标缓冲区先填满 `#`（0x23），再按字节打印：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void dump(const char *label, const unsigned char *p, size_t n) {
    printf("%-24s", label);
    for (size_t i = 0; i < n; i++) {
        printf(" %02X", p[i]);
    }
    printf("\n");
}

int main(int argc, char *argv[]) {
    unsigned char buf[8];
    const char *src = argc > 1 ? argv[1] : "abcdefghij";
    size_t n = (size_t)(argc > 2 ? atoi(argv[2]) : 8);
    size_t len = 0;

    memset(buf, '#', sizeof buf);
    strncpy((char *)buf, src, n);
    dump("result:", buf, sizeof buf);
    while (len < sizeof buf && buf[len] != 0) {
        len++;
    }
    printf("terminating null in buffer: %s\n", len < sizeof buf ? "yes" : "no");
    return 0;
}
```

::: terminal title="zsh - strncpy"

```text
$ gcc -std=c17 -Wall -Wextra -o sc sc.c
$ ./sc ab 8
result:                  61 62 00 00 00 00 00 00
terminating null in buffer: yes
$ ./sc abcdefgh 8
result:                  61 62 63 64 65 66 67 68
terminating null in buffer: no
$ ./sc abcdefghij 8
result:                  61 62 63 64 65 66 67 68
terminating null in buffer: no
```

:::

第二、三种情况写满了 8 个字节，一个空字符也没有。拿这样的缓冲区当字符串用，会一直读到后面碰巧出现的空字符为止。Windows 上 MinGW-w64 GCC 13.2 的输出逐行相同。

两份规格里，「不重叠」都写在调用方的义务一边。标准库函数不检查这一条，违反了会得到什么结果由实现和优化级别决定。下面这份程序故意违反 `memcpy` 的前置条件：

```c
#include <stdio.h>
#include <string.h>

int main(void) {
    char buf[16] = "0123456789abcdef";

    /* 源区域与目标区域重叠：调用 memcpy 违反前置条件 */
    memcpy(buf + 2, buf, 10);
    printf("%.16s\n", buf);
    return 0;
}
```

在 Linux 上用 GCC 14.2 构建，两个优化级别给出不同的字符串：

::: terminal title="zsh - gcc"

```text
$ gcc -std=c17 -Wall -Wextra -O0 -o ov ov.c
$ ./ov
010123456789cdef
$ gcc -std=c17 -Wall -Wextra -O2 -o ov ov.c
ov.c: In function 'main':
ov.c:8:5: warning: 'memcpy' accessing 10 bytes at offsets 2 and 0 overlaps 8 bytes at offset 2 [-Wrestrict]
$ ./ov
010123456767cdef
```

:::

`-O0` 生成一次对库函数 `memcpy` 的调用，结果与从低地址往高地址逐字节复制相同。`-O2` 把这次复制在编译期折叠成了几条常量存值指令，汇编里连 `memcpy` 的调用都没有了，结果由编译器如何解释这次重叠决定。两个结果都是未定义行为允许的，都不能依赖。需要允许重叠时应调用 `memmove`，它给出 `010123456789cdef`；21.3 会实现它。Windows 上 MinGW-w64 GCC 13.2 的结果与上面逐行相同，`-O2` 的警告也相同。

::: concept mdr-precondition-is-caller-duty title="前置条件由调用方保证，函数不检查"

前置条件写在规格里，是调用方的义务；标准库函数不检查它，违反后行为未定义。省略数组大小检查、传入重叠区域、传空指针，都属于这一类错误。函数的保证只覆盖前置条件成立的情形，所以阅读规格时要先确认调用点满足前置条件，再看返回值和后置条件。

:::

## 5. 为 mdr_ 函数写规格注释

头文件里的注释按固定顺序写：一句话功能、前置条件、返回值与后置条件。本章的写法如下：

```c
/*
 * 一句话说明功能。
 * 调用方保证：前置条件。
 * 返回：返回值与后置条件；与标准函数有差别时写在这里。
 */
```

第一部分做过的 `mdr_strnlen` 完整地写成：

```c
/*
 * 返回 s 开头连续非空字符的个数，最多检查 maxlen 个字节。
 * 调用方保证：s 指向的区域至少有 min(strlen(s) + 1, maxlen) 个可读字节。
 * 返回：范围内遇到空字符时为它之前的字节数，否则为 maxlen；
 *       不读取第 maxlen 个字节之后的内容。
 */
size_t mdr_strnlen(const char *s, size_t maxlen);
```

最后一句既不是前置条件也不是返回值，它是函数的效果，必须写进来：调用方靠这句话判断能不能把缓冲区截到 `maxlen` 个字节而不读越界。

`mdr_strchr` 的规格注释：

```c
/*
 * 在 s 中查找 (char)ch 首次出现的位置，终止空字符也算字符串的一部分。
 * 调用方保证：s 指向以空字符结尾的字符串。
 * 返回：指向该字符的指针；没有找到时返回 NULL。
 */
char *mdr_strchr(const char *s, int ch);
```

「终止空字符也算字符串的一部分」这一句决定了 `mdr_strchr(s, '\0')` 的返回值，漏掉就会少写一个测试。

::: compare left-title="含糊的注释" right-title="完整的规格"

```c
/* 在 s 中查找 c。 */
char *mdr_strchr(const char *s, int ch);
```

---

```c
/*
 * 在 s 中查找 (char)ch 首次出现的位置，
 * 终止空字符也算字符串的一部分。
 * 调用方保证：s 指向以空字符结尾的字符串。
 * 返回：指向该字符的指针；没有找到时返回 NULL。
 */
char *mdr_strchr(const char *s, int ch);
```

:::

左栏的注释没有告诉调用方三件事：找不到时返回什么、空字符算不算、`s` 必须是什么。读注释的人只能去翻实现，而实现可能还没写。

注释里写「调用方保证」，不等于函数什么都不做。调试构建里可以用断言检查其中便宜的部分，发布构建里断言消失，前置条件仍然有效。后半句决定了注释不能写成「函数检查 s 非空」。

## 6. 在调试构建中检查前置条件

`MDR_ASSERT` 定义在 `mdr_compiler.h` 中，直接借用 `assert`，定义了 `NDEBUG` 时展开为空：

```c
#define MDR_ASSERT(cond) assert(cond)
```

`assert` 的用法见[断言](/教程/正文/语法和标准库/14_文本转换_错误与程序生命周期/14_1_assert)。把它放在函数的开头，前置条件一旦被违反，程序停在出错的那一行，而不是过一会儿在别处崩溃：

```c
#include "mdr_compiler.h"
#include <stdio.h>
#include <stdlib.h>

static size_t count_bytes(const char *s) {
    size_t n = 0;

    MDR_ASSERT(s != NULL);
    while (s[n] != '\0') {
        n++;
    }
    return n;
}

int main(void) {
    const char *arg = getenv("DEMO_ARG");
    printf("%lu\n", (unsigned long)count_bytes(arg));
    return 0;
}
```

在 Linux 上，带断言和不带断言的两个构建分别运行：

::: terminal title="zsh - demo"

```text
$ gcc -std=c17 -Wall -Wextra -g -o demo demo.c
$ DEMO_ARG=hello ./demo
5
$ ./demo
demo: demo.c:8: count_bytes: Assertion `s != ((void *)0)' failed.
Aborted
$ echo $?
134
$ gcc -std=c17 -Wall -Wextra -g -DNDEBUG -o demo_nd demo.c
$ ./demo_nd
Segmentation fault
$ echo $?
139
```

:::

断言失败时程序以 134 退出，`-DNDEBUG` 的构建直接触发段错误，退出状态 139。Windows 上 MinGW-w64 GCC 13.2 的断言信息格式不同，内容是 `Assertion failed: s != ((void *)0), file demo.c, line 8`。

断言只在调试构建中存在，所以要有选择地放：

- 查便宜的、常见的错误，例如空指针、`maxlen` 与缓冲区大小的明显矛盾。
- 不查需要遍历才能确认的条件，例如「目标区域足够大」。这类条件在调试构建里也查不起，仍然由调用方保证。
- 检查不得改变前置条件满足时的行为，也不能引入新的可观察输出。

::: compare left-title="发布构建里自动改用 memmove" right-title="调试断言，发布保持原样"

```c
void *mdr_memcpy(void *dest, const void *src, size_t count) {
    if (overlap(dest, src, count)) {
        return mdr_memmove(dest, src, count);
    }
    /* 逐字节复制 */
}
```

---

```c
void *mdr_memcpy(void *dest, const void *src, size_t count) {
    MDR_ASSERT(!ranges_overlap(dest, src, count));
    /* 逐字节复制，与标准库一致 */
}
```

:::

左栏的做法看起来友好，实际把调用方的错误藏了起来：一份违反前置条件的程序会继续运行，结果还和 `memmove` 一样，测试再也发现不了问题。同时 `mdr_memcpy` 与标准 `memcpy` 的行为出现了差异，函数名不再说明它做什么。正确做法是调试构建里断言，发布构建里保持与标准库一致。

`tests/check.h` 沿用[自动化测试](/教程/正文/开发与工程基础/11_自动化测试)里的框架：`CHECK` 判断一个条件，`CHECK_EQ_SIZE` 比较两个 `size_t`，`CHECK_STR_EQ` 比较两个字符串，`check_report` 打印「套件名: 总数 checks, 失败数 failed」并返回退出状态。这一章的三个测试文件各用一次这套框架，说明它不依赖 `wordfreq` 的任何代码。

构建文件里与收集文件有关的部分如下，其余是编译选项和 Sanitizer 开关：

```cmake
file(GLOB MDR_SOURCES CONFIGURE_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/src/*.c")

add_library(mdr STATIC ${MDR_SOURCES})
target_include_directories(mdr PUBLIC "${CMAKE_CURRENT_SOURCE_DIR}/include")

file(GLOB MDR_UNIT_TESTS CONFIGURE_DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/tests/test_*.c")
foreach(test_src IN LISTS MDR_UNIT_TESTS)
    get_filename_component(test_name "${test_src}" NAME_WE)
    add_executable(${test_name} "${test_src}" tests/check.c)
    target_include_directories(${test_name} PRIVATE tests)
    target_link_libraries(${test_name} PRIVATE mdr)
    add_test(NAME ${test_name} COMMAND ${test_name})
endforeach()
```

`CONFIGURE_DEPENDS` 让 CMake 在每次构建前重新检查目录，后面各节新加的 `tests/test_ext.c`、`tests/diff_string.c` 会被自动收进来，不需要重新运行配置。`mdr` 是静态库（static library），测试程序链接它；差分测试按 `tests/diff_*.c` 收集，多链接一份 `tests/diff_util.c`。CMake 本身的用法见 [CMake 与 XMake](/教程/正文/开发与工程基础/9_CMake与XMake)。

第一部分已经实现的七个函数按模块放进了库里：`mdr_strlen`、`mdr_strcmp`、`mdr_strnlen` 在 `mdr_string.c`，`mdr_memset`、`mdr_memcpy` 在 `mdr_memory.c`，`mdr_popcount_u32`、`mdr_bswap32` 在 `mdr_bits.c`。测试文件按模块分开，每个函数至少三个检查：

```c
static void test_strnlen(void) {
    const char non_terminated[4] = {'a', 'b', 'c', 'd'};

    CHECK_EQ_SIZE(mdr_strnlen("", 4u), 0u);
    CHECK_EQ_SIZE(mdr_strnlen("hello", 0u), 0u);
    CHECK_EQ_SIZE(mdr_strnlen("hello", 3u), 3u);
    CHECK_EQ_SIZE(mdr_strnlen("hello", 10u), 5u);
    CHECK_EQ_SIZE(mdr_strnlen(non_terminated, 4u), 4u);
}
```
