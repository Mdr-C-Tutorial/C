# 21.5 易于移植的扩展函数

[第 16 章](/教程/正文/开发与工程基础/16_可移植构建)里，`wordfreq` 的贡献者把 `dup_string` 换成了 `strdup`，在 Windows 上编译通过，拿到 Linux 上用 `-std=c17` 构建却报错，因为严格模式下 glibc 根本不声明 `strdup`。`strlcpy`、`memmem`、`strsep` 是同一类东西：用起来顺手、实现也不复杂，却不在 ISO C 的字符串函数里（其中一部分后来进了 C23），各平台的声明条件、名字甚至语义都不统一。

这一节把这些函数实现成 `mdr_` 前缀的版本，放进 `mdr_ext.h` 和 `src/mdr_ext.c`。目标不是背下每个平台有什么，而是学会判断：一个函数能不能直接用、不能时怎么用普通 C 补上、补上之后怎么保证与系统版的行为一致。

## 1. 扩展函数为什么带来移植问题

这些函数有三个来源。POSIX 定义了一批，例如 `strdup`、`strndup`、`stpcpy`、`strtok_r`；BSD 贡献了一批，例如 `strlcpy`、`strlcat`、`strsep`；GNU 和其他实现也有自己的版本，例如 `memmem`。它们进标准的时间参差不齐：`stpcpy` 在 POSIX.1-2008 里就有；`strdup`、`strndup` 直到 C23 才进入 ISO C；`strlcpy`、`strlcat` 和 `memmem` 由 POSIX.1-2024（Issue 8）收录。

进没进标准，和「现在能不能用」是两件事。下面这张表是在三套环境上逐项编译探测的结果，探测方法是用 `-Werror=implicit-function-declaration` 编译一个只引用函数名的文件，声明缺失即失败：

| 函数 | 来源 | 现状 | glibc 2.41 `-std=c17` | glibc 2.41 `-std=gnu17` | MinGW-w64 UCRT 13.2 | MSVC 14.51 |
| --- | --- | --- | --- | --- | --- | --- |
| `strdup` | POSIX | C23 起进标准 | 不声明 | 声明 | 声明 | 声明（另有 `_strdup`） |
| `strndup` | POSIX | C23 起进标准 | 不声明 | 声明 | 不声明 | 不声明 |
| `stpcpy` | POSIX 2008 | 非 ISO C | 不声明 | 声明 | 不声明 | 不声明 |
| `strlcpy` | OpenBSD | POSIX Issue 8 | 不声明 | 声明（2.38 起） | 不声明 | 不声明 |
| `strlcat` | OpenBSD | POSIX Issue 8 | 不声明 | 声明（2.38 起） | 不声明 | 不声明 |
| `memmem` | GNU/BSD | POSIX Issue 8 | 不声明 | 声明 | 不声明 | 不声明 |
| `strsep` | BSD | 非标准 | 不声明 | 声明 | 不声明 | 不声明 |
| `strtok_r` | POSIX | 非 ISO C | 不声明 | 声明 | 声明 | 不声明 |
| `strcasecmp` | POSIX/BSD | 非 ISO C | 不声明 | 声明 | 声明 | 不声明（用 `_stricmp`） |

同一份源码在同一个 glibc 上，`-std=c17` 和 `-std=gnu17` 的结果整张表翻转，原因是严格模式定义了 `__STRICT_ANSI__`，glibc 的 `string.h` 据此只声明 ISO C 的函数；`strlcpy`、`memmem` 这些还要额外打开 `_DEFAULT_SOURCE` 之类的功能特性宏。机制见[功能特性测试宏](/教程/正文/语法和标准库/18_标准库的使用契约/18_3_功能特性测试宏)。

::: concept mdr-ext-portability title="扩展函数的可用性由三件事共同决定"

一个扩展函数在某平台能不能直接调用，取决于三件事：头文件里有没有声明（库版本）、当前的标准模式是否允许声明（严格模式与功能特性宏）、以及这个平台用的是什么名字（MSVC 用 `_strdup`、`_stricmp`、`_strnicmp` 这类下划线名字）。三者全满足才叫「可用」，只看库版本不够。

:::

这张表还说明了另一件事：`-std=gnu17` 只是 GCC 的默认扩展模式，不是所有编译器都有。MSVC 既没有 `gnu17`，也没有 `_DEFAULT_SOURCE`，把上表第五列和第七列并排看，就是跨平台项目每天要面对的情形。

## 2. `strdup` 与 `strndup`

`strdup` 的工作是分配一块刚好放下字符串的存储并复制过去：

```c
char *mdr_strdup(const char *s) {
    size_t len = mdr_strlen(s);
    char *copy = (char *)malloc(len + 1);

    if (copy == NULL) {
        return NULL;
    }
    mdr_memcpy(copy, s, len + 1);
    return copy;
}
```

`len + 1` 里的那个 1 是终止空字符。[第 13 章](/教程/正文/开发与工程基础/13_编译器诊断与程序检查)的 `dup_string` 少分配这一字节，ASan 报 heap-buffer-overflow，这是这类函数最常见的错误。

`strndup` 多一个上限 `n`，最多复制 `n` 个字节，然后补终止空字符。关键在「源串可能没有终止空字符」：POSIX Issue 8 明确规定，`strndup` 的实参只需要可读 `min(strlen(s) + 1, n)` 个字节，换句话说，传一个长度恰好为 `n`、没有结尾的字符数组是合法的。

```c
char *mdr_strndup(const char *s, size_t n) {
    size_t len = mdr_strnlen(s, n);
    char *copy = (char *)malloc(len + 1);

    if (copy == NULL) {
        return NULL;
    }
    mdr_memcpy(copy, s, len);
    copy[len] = '\0';
    return copy;
}
```

这里用的是 `mdr_strnlen` 而不是 `mdr_strlen`。换成 `mdr_strlen` 就会读越过数组末尾，直到碰巧遇到一个空字符为止。测试里专门放了一个没有终止空字符的数组：

```c
const char raw[5] = {'a', 'b', 'c', 'd', 'e'}; /* 没有终止空字符 */
char *p = mdr_strndup(raw, sizeof raw);

printf("\"%s\" length %zu\n", p, strlen(p));
free(p);
```

在 Linux 上用 ASan 构建运行：

:::

`raw` 有 5 个可读字节，`mdr_strndup` 只读这 5 个，然后分配 6 字节，最后一个放空字符。返回的存储由调用方 `free`，这一点和 `strdup` 一样。

## 3. `stpcpy`

`stpcpy` 与 `strcpy` 的唯一差别是返回值：`strcpy` 返回目标的开头，`stpcpy` 返回目标里终止空字符的位置。有了这个位置，拼接可以一路接着写，不必每一步都从头找末尾。

::: compare left-title="strcat 链：每步重新找末尾" right-title="stpcpy：接着上一次的末尾写"

```c
strcat(buf, "log/");
strcat(buf, "2026/");
strcat(buf, "app.log");
```

---

```c
char *end = mdr_stpcpy(buf, "log/");
end = mdr_stpcpy(end, "2026/");
end = mdr_stpcpy(end, "app.log");
```

:::

三次拼接，`strcat` 后两次分别要把 `"log/"` 和 `"log/2026/"` 各扫一遍找末尾，`stpcpy` 一次也不用扫。段数越多，差距越明显：`strcat` 的总代价随段数平方增长，`stpcpy` 是线性。

::: terminal title="zsh - cat_chain"

```text
$ gcc -std=c17 -Wall -Wextra -Iinclude cat_chain.c src/mdr_ext.c src/mdr_string.c \
    src/mdr_memory.c -o cat_chain
$ ./cat_chain
strcat chain: "log/2026/app.log"
stpcpy chain: "log/2026/app.log" (16 chars)
```

:::

`end - b` 正好是写进去的字节数，不包含终止空字符，可以直接当下一次写入的起点。实现只有三行：

```c
char *mdr_stpcpy(char *restrict dest, const char *restrict src) {
    while ((*dest = *src) != '\0') {
        dest++;
        src++;
    }
    return dest;
}
```

循环条件里既做了赋值又做了判断，循环结束时 `dest` 正停在终止空字符上。`restrict` 的约束和 `strcpy` 一样：两个区域不能重叠。

## 4. `strlcpy` 与 `strlcat`

`strlcpy` 是 OpenBSD 为固定大小缓冲区设计的。它的规格有三条：最多写 `dsize - 1` 个字符，`dsize` 大于 0 时总是写终止空字符，返回值是 `strlen(src)`。第三条最关键：返回值与 `dsize` 无关，所以用「返回值不小于 `dsize`」就能判断是否发生了截断。

```c
size_t mdr_strlcpy(char *restrict dst, const char *restrict src, size_t dsize) {
    size_t len = mdr_strlen(src);

    if (dsize > 0) {
        size_t copy = len < dsize - 1 ? len : dsize - 1;

        mdr_memcpy(dst, src, copy);
        dst[copy] = '\0';
    }
    return len;
}
```

`dsize` 为 0 时一个字节都不写，但照样返回源串长度，调用方可以据此重新分配。这个分支不能省：`dsize - 1` 在 `dsize` 为 0 时下溢成 `SIZE_MAX`。

`strlcat` 在目标末尾追加，最多写满 `dsize` 个字节，返回「初始目标长度 + 源串长度」。如果目标本身没有终止空字符（说明它已经被截断过），返回 `dsize + strlen(src)`，这个值必然不小于 `dsize`。

```c
size_t mdr_strlcat(char *restrict dst, const char *restrict src, size_t dsize) {
    size_t dlen = mdr_strnlen(dst, dsize);
    size_t slen = mdr_strlen(src);
    size_t copy;

    if (dlen == dsize) {
        return dsize + slen;
    }
    copy = dsize - dlen - 1;
    if (copy > slen) {
        copy = slen;
    }
    mdr_memcpy(dst + dlen, src, copy);
    dst[dlen + copy] = '\0';
    return dlen + slen;
}
```

实际用起来是这样：

```c
char path[16];
size_t need;

/* strlcpy 检测截断：返回值不小于缓冲区大小 */
need = mdr_strlcpy(path, "/usr/local/share/mdr", sizeof path);
printf("strlcpy -> \"%s\", need %zu, truncated %s\n", path, need,
       need >= sizeof path ? "yes" : "no");

need = mdr_strlcpy(path, "/etc/mdr", sizeof path);
printf("strlcpy -> \"%s\", need %zu, truncated %s\n", path, need,
       need >= sizeof path ? "yes" : "no");

/* strlcat 追加并检测截断 */
mdr_strlcpy(path, "/etc", sizeof path);
need = mdr_strlcat(path, "/mdr.conf", sizeof path);
printf("strlcat -> \"%s\", need %zu, truncated %s\n", path, need,
       need >= sizeof path ? "yes" : "no");
```

第一行目标缓冲区 16 字节，源串 20 字节，写进去 15 个字符加空字符，返回 20，调用方一眼看出被截断了，还知道完整长度是多少。第二行 8 字节刚好放得下。第三行 `/etc` 加 `/mdr.conf` 共 13 个字符，16 字节的缓冲区容得下。

这个返回值设计是 `strlcpy` 相比 `strncpy` 最大的改进。`strncpy` 不告诉调用方有没有截断，返回的还是目标开头，结果是必须自己数。两种写法放在一起比较：

::: compare left-title="strncpy 的误用" right-title="strlcpy 加截断检查"

```c
char buf[16];
strncpy(buf, src, sizeof buf);   /* 可能不带终止空字符 */
/* 不知道有没有截断，也不知道完整长度 */
```

---

```c
char buf[16];
if (strlcpy(buf, src, sizeof buf) >= sizeof buf) {
    /* 发生了截断，缓冲区里是前 15 个字符 */
    fprintf(stderr, "path too long, need %zu bytes\n", strlen(src) + 1);
}
```

:::

左栏的 `strncpy` 在源串长度不小于 16 时不写终止空字符，`buf` 不能当字符串用。右栏一定能安全地当字符串用，还多拿到一个判断。

需要格式化（数字、宽度、多个参数）时用 `snprintf`，它同样返回「假如空间足够会写多少」，也用返回值与缓冲区大小比较来判断截断。选择规则可以简化成一句：拼接固定字符串、只想检测截断时用 `strlcpy` 和 `strlcat`；需要格式化或长度变化大时用 `snprintf`，或者先算长度再分配。`strlcpy` 也有批评意见：截断时它仍然要把整个源串读完才能算出返回值，对超长输入并没有省下代价。

## 5. `memmem`

`strstr` 只能找字符串，一旦待查找的序列里有空字符就失效。`memmem` 接受两个「指针 + 长度」，可以在任意字节序列里查找，例如在文件头里找 PNG 的签名：

```c
void *mdr_memmem(const void *haystack, size_t haystacklen, const void *needle,
                 size_t needlelen) {
    const unsigned char *h = (const unsigned char *)haystack;
    const unsigned char *n = (const unsigned char *)needle;
    size_t remaining = haystacklen;

    if (needlelen == 0) {
        return (void *)haystack;
    }
    while (remaining >= needlelen) {
        const unsigned char *p = (const unsigned char *)mdr_memchr(
            h, n[0], remaining - needlelen + 1);
        size_t skipped;

        if (p == NULL) {
            break;
        }
        if (mdr_memcmp(p, n, needlelen) == 0) {
            return (void *)p;
        }
        skipped = (size_t)(p - h) + 1;
        h += skipped;
        remaining -= skipped;
    }
    return NULL;
}
```

朴素但够用的做法：用 `memchr` 找首字节，找到后拿 `memcmp` 比整段。首字节的搜索范围是 `remaining - needlelen + 1`，再往后就不可能有完整匹配了。`needlelen` 为 0 时返回 `haystack`，与 `strstr` 对空串的处理保持一致；这条规则不写进规格，调用方就会在空模式上得到意料之外的结果。

## 6. `strtok_r` 与 `strsep`

[21.2](/教程/正文/开发与工程基础/21_库接口实现练习/21_2_字符串函数)里的 `mdr_strtok` 把进度存在内部静态对象里，规格写着「不嵌套、不并发」。嵌套切分时它会坏掉：切外层的过程中再切内层，内层的进度覆盖了外层的。那里承诺过会用 `mdr_strtok_r` 把同一段程序重跑一遍，现在补上。程序还是两行文本、每行三个字段，只把 `mdr_strtok` 换成 `mdr_strtok_r`，每次切分各带一个 `save`：

```c
const char text[] = "red,green,blue\ncyan,magenta,yellow";
char copy[sizeof text];
char *save_line = NULL;
char *line;
unsigned long lines = 0;
unsigned long fields = 0;

memcpy(copy, text, sizeof text);
printf("按行切分，再对每一行按逗号切分：\n");
for (line = mdr_strtok_r(copy, "\n", &save_line); line != NULL;
     line = mdr_strtok_r(NULL, "\n", &save_line)) {
    char *save_field = NULL;
    char *field;

    lines++;
    printf("  行 %lu: %s\n", lines, line);
    for (field = mdr_strtok_r(line, ",", &save_field); field != NULL;
         field = mdr_strtok_r(NULL, ",", &save_field)) {
        fields++;
        printf("    字段: %s\n", field);
    }
}
printf("共 %lu 行、%lu 个字段（期望 2 行、6 个字段）\n", lines, fields);
```

```c
        printf(" [%s]", inner);
        inner = mdr_strtok(NULL, ",:");
    }

}
```

坏版本只输出了一组就停了：内层切完后，`mdr_strtok` 的内部状态是「`alpha:1,2` 已切完」，外层下一次调用拿到 `NULL`，`beta` 那一组再也没被处理。`nested_tok.c` 与 `nested_tok_bad.c` 只差在 `mdr_strtok_r` 和每个循环各自的 `save` 指针。

`mdr_strtok_r` 把进度放在调用方提供的 `char *save` 里，每次调用传同一个指针，嵌套时各用各的：

```c
char *mdr_strtok_r(char *restrict str, const char *restrict delim,
                   char **restrict saveptr) {
    char *start;

    if (str != NULL) {
        *saveptr = str;
    }
    if (*saveptr == NULL) {
        return NULL;
    }
    start = *saveptr + mdr_strspn(*saveptr, delim);
    if (*start == '\0') {
        *saveptr = NULL;
        return NULL;
    }
    *saveptr = start + mdr_strcspn(start, delim);
    if (**saveptr != '\0') {
        **saveptr = '\0';
        (*saveptr)++;
    } else {
        *saveptr = NULL;
    }
    return start;
}
```

`mdr_strsep` 解决的是另一个问题。`strtok` 一族会把连续分隔符当成一个，`"a,,b"` 只切出 `a` 和 `b` 两个；`strsep` 每遇到一个分隔符就切一刀，中间的空字段保留。用它解析配置行：

::: terminal title="zsh - sep_demo"

```text
$ gcc -std=c17 -Wall -Wextra -Iinclude sep_demo.c src/mdr_ext.c src/mdr_string.c \
    src/mdr_memory.c -o sep_demo
$ ./sep_demo
strtok: "name=wf;;level=;mode=fast" -> [name=wf] [level=] [mode=fast]
strsep: "name=wf;;level=;mode=fast" -> [name=wf] [] [level=] [mode=fast]  (4 fields)
```

:::

同一行输入，`strtok` 切出 3 段，`strsep` 切出 4 段。`strsep` 的结果里 `name=wf` 后面那个空字段正是原文里 `;;` 造成的，调用方看到它就知道这里少了一项；`strtok` 把这一信息丢掉了。配置文件的格式要求字段与位置一一对应时，`strsep` 是对的；格式本来就允许重复分隔符时，`strtok` 更省事。

`strsep` 的实现比 `strtok_r` 短一半：它不改写调用方传进来的指针以外的东西，每次从 `*stringp` 开头切一刀，把它推进到分隔符之后，切完最后一个字段后把 `*stringp` 置空。

MSVC 提供的是 `strtok_s`，参数与 `strtok_r` 相同：待切分串、分隔符集合、调用方提供的上下文指针，返回值也相同。C11 附录 K 里另有一个同名的 `strtok_s`，参数顺序与这两个都不一样，看到这个名字时要先确认是哪一个，别把两者的调用写混。

## 7. 只按 ASCII 不区分大小写的比较

`strcasecmp` 的语义依赖区域设置：在某些区域设置下，它会把 `'i'` 和 `'I'` 之外的一些字母也视为相等。做协议关键字、命令行选项这类比较时，需要的是固定的 ASCII 规则。

```c
static unsigned char ascii_lower(unsigned char c) {
    if (c >= 'A' && c <= 'Z') {
        return (unsigned char)(c - 'A' + 'a');
    }
    return c;
}

int mdr_ascii_casecmp(const char *s1, const char *s2) {
    const unsigned char *p1 = (const unsigned char *)s1;
    const unsigned char *p2 = (const unsigned char *)s2;

    while (*p1 != '\0' && ascii_lower(*p1) == ascii_lower(*p2)) {
        p1++;
        p2++;
    }
    return (int)ascii_lower(*p1) - (int)ascii_lower(*p2);
}
```

不用 `tolower` 的理由有两条：`tolower` 的结果由当前区域设置决定，而且它的实参必须是 `unsigned char` 值或 `EOF`，直接传 `char` 在 `char` 为有符号的平台上会越界。自己写映射只有两个比较，把语义钉死在 ASCII 上。函数名里写 `ascii`，读代码的人一看就知道不受区域设置影响。

验证办法是对全部 256×256 个字节对跑一遍，比较「两个串是否相等」的判定与映射后逐个字节相等是否一致：

::: terminal title="zsh - casecmp256"

```text
$ gcc -std=c17 -Wall -Wextra -O2 casecmp256.c -o casecmp256
$ ./casecmp256
checked 65025 byte pairs, mismatches 0
('A','a')=0 ('a','A')=0 ('Z','[')=31 ('@','`')=-32
```

:::

65025 是 255×255，去掉了空字符（它表示串结束，不能作为一个字节参与比较）。最后一行说明映射只覆盖 `A`–`Z`：`'Z'` 和 `'['` 不相等，`'@'` 和 `` '`' `` 也不相等，中间那 6 个非字母字符没有被卷进来。

`mdr_ascii_ncasecmp` 加上「最多比较 n 个字节」的限制，`n` 为 0 时直接返回 0。POSIX 的 `strcasecmp`、`strncasecmp` 和 MSVC 的 `_stricmp`、`_strnicmp` 做的是同一件事，只是后者的区域设置依赖程度因实现而异。

## 8. 在项目中提供这些函数

有了 `mdr_` 版本，项目里的用法有两种选择。

第一种是永远编译并调用 `mdr_` 版本。这些函数都很小，编进项目不增加多少体积，各平台行为完全一致，调用点也不必关心当前平台有没有。本节的库就是这么做的，推荐给 `strlcpy`、`strsep`、`memmem` 这类平台差异大的函数。

第二种是配置时检测，系统有就用系统的。适合性能敏感、系统实现明显更快的函数（`memmem` 在 glibc 里用了 Two-Way 算法，长模式串上比朴素实现快很多）。做法是在构建系统里检测符号，见[第 16 章](/教程/正文/开发与工程基础/16_可移植构建)的 `check_symbol_exists`，再用一个配置宏在编译期二选一。

::: concept mdr-ext-no-system-names title="回退实现不要用系统函数名"

自己写的回退版本必须用 `mdr_strlcpy` 这样的名字，不能叫 `strlcpy`。系统的 `string.h` 一旦声明了同名函数，你的定义就与它冲突；如果像 direwolf 那样把 `strlcpy` 定义成宏，系统的声明会被宏改写，编译直接失败。即使没有冲突，编译器也常把标准名当作内建函数处理。理由在 [21.1](/教程/正文/开发与工程基础/21_库接口实现练习/21_1_范围_命名与契约) 已经展开过，这里的结论一样：加前缀。

:::

两种配置都要测。系统的 `strlcpy` 和 `mdr_strlcpy` 在被截断时的行为必须一致，比较办法见 [21.7](/教程/正文/开发与工程基础/21_库接口实现练习/21_7_差分测试与边界验证) 的差分测试：同一组输入分别喂给两个实现，比较返回值和缓冲区内容。

配置检测本身也有坑。本机 MinGW-w64 没有 `<stdbit.h>`，Linux 上有；一个写死「MinGW 就没有 `strlcpy`」的检测在别的 MinGW 发行版上可能就错了。检测要针对符号和头文件，不要针对平台名。


4. 说明这个函数与 `strcasestr` 的区别：后者受区域设置影响，前者不受，函数名里的 `ascii` 就是为了让调用方一眼看出这一点。

没有 GNU 扩展环境的读者可以只做前两问；有 `strcasestr` 的读者可以顺带跑一遍差分，把在 `en_US.UTF-8` 下两者不一致的输入记下来。

</Exercise>
