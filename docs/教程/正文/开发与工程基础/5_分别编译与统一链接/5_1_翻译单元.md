# 5.1 翻译单元

在前面的章节中，我们的注意力大多集中在单个源文件的编译与运行上。然而在真实的工程实践中，几乎没有哪个严肃的 C 语言项目会将成千上万行代码堆砌在一个单独的 `.c` 文件中。随着工程规模的扩大，将系统按业务领域或功能逻辑拆分成多个源文件，是保证代码可维护性与协作效率的必由之路。

然而，C 语言的编译模型与许多现代语言截然不同：编译器在编译阶段从不以「项目目录」或「工程全局」为单位吞吐代码，而是以一个一个独立的**翻译单元（Translation Unit）**为基本处理粒度。搞清翻译单元的构成及其生命周期，是理清「声明应该写在何处、定义应当放在哪里」这一多文件组织核心问题的认知基石。

## 1. 基本定义

::: concept translation-unit-definition title="翻译单元的定义"

预处理完成后得到的源文件称为一个翻译单元 (Translation Unit)。它由外部声明序列组成，例如函数定义、对象定义、`typedef` 声明和 `extern` 声明。编译器先分别处理各翻译单元生成目标文件，再由链接器把目标文件与库连接为最终程序。

:::

当编译器启动编译任务时，首先由预处理器负责处理源文件中的所有预处理指令：宏被原样展开、条件编译分支被计算裁剪，所有被 `#include` 引入的头文件内容被逐字逐句递归粘贴进源码中。这一系列纯文本替换全部落定后，所产生的完整独立文本流便构成了一个翻译单元。

随后的语法分析、中间代码生成与机器码汇编，都完全局限在这个翻译单元内部进行。编译器对该文件外部的现实世界一无所知；直到所有翻译单元各自编译成目标文件（`.o` 或 `.obj`）后，链接器才登场将分散的符号引用与实际定义逐一绑定起来。

::: generate translation-unit-intro kind=explanation concepts=translation-unit-definition

面向刚开始接触多文件 C 项目的读者，讲解从源文件到可执行文件的整体路径——预处理、逐翻译单元编译、链接；说明为什么“翻译单元”是理解“声明写在哪、定义放在哪”的基本单位。

:::

## 2. 为什么它是模块边界

在缺少模块（module）概念的经典 C 语言体系中，翻译单元扮演着最重要的模块隔离边界。同名标识符能否和平共处、某个函数或对象能否被其他源文件查阅与调用，完全受制于翻译单元的边界以及符号所附带的链接属性（Linkage）。

理解这个边界有助于建立清晰的组织直觉：
- **边界内的自治性**：在同一个翻译单元内，标识符遵循标准的作用域与可见性规则。如果借助 `static` 关键字将符号限定在当前翻译单元内部（内部链接属性），那么该符号的名字在编译成目标文件后便会被隐藏起来，绝不会与外部其他源文件产生命名冲突。
- **跨边界的协作约定**：如果需要调用另一个翻译单元中实现的函数，当前翻译单元并不需要包含该函数的完整实现细节，只需要一份形式契约——即函数声明。声明向当前编译器承诺该函数的签名与调用约定，而将寻找函数实体的具体任务推迟到链接阶段完成。
- **边界对接的媒介**：头文件正是横跨不同翻译单元的纽带。它负责向各调用者广播公共契约，确保调用者与提供者在各自独立的翻译过程中始终看到完全一致的数据类型与接口约定。

::: generate translation-unit-boundary kind=explanation concepts=translation-unit-definition

面向刚开始接触多文件 C 项目的读者，解释翻译单元为什么是模块边界：`static` 如何影响可见性、头文件如何保证声明一致、链接器如何把调用点与定义点绑定。围绕“声明写在哪、定义放在哪”这个组织问题展开。

:::

## 3. 一个最小示例

为了观察翻译单元在工程中的实际运作，我们搭建一个由三个文件构成的最小工程：头文件 `math_ext.h` 负责对外声明算术接口，实现文件 `math_ext.c` 给出具体逻辑，而主程序 `main.c` 负责消费该接口。

::: tip 关于 `#ifndef` / `#define` / `#endif`

这三行是“头文件包含保护”的标准写法，属于预处理器的条件编译指令，目的是防止头文件被重复包含。第一部分第 17 章已经系统说明预处理与条件编译；这里关注它在头文件边界中的作用。

:::

::: code-group

```c [math_ext.h]
/* math_ext.h */
#ifndef MATH_EXT_H
#define MATH_EXT_H

int add(int lhs, int rhs);

#endif
```

```c [math_ext.c]
/* math_ext.c */
#include "math_ext.h"

int add(int lhs, int rhs) {
    return lhs + rhs;
}
```

```c [main.c]
/* main.c */
#include <stdio.h>
#include "math_ext.h"

int main(void) {
    printf("%d\n", add(3, 4));
    return 0;
}
```

:::

输出：

::: terminal

7

:::

在构建该程序的过程中，`math_ext.c` 与 `main.c` 分别经过预处理扩展成两个截然不同的翻译单元。在 `main.c` 对应的翻译单元里，编译器只看到 `add` 函数的签名声明，它根据签名生成传参和调用指令，并在生成的目标文件中留下一处未解引用的外部符号标记；而在 `math_ext.c` 的翻译单元里，编译器生成了 `add` 的机器指令序列并对外导出该符号。最后，链接器把两者拼接合并，把调用点与定义点牢固锁定在一起。

::: generate translation-unit-example kind=explanation concepts=translation-unit-definition

借助上面的三文件示例，面向刚开始接触多文件 C 项目的读者分步说明：`main.c` 和 `math_ext.c` 经预处理后成为两个翻译单元；两者包含同一个头文件，从而共享一致的声明；链接阶段把 `add` 的调用点和定义点连起来。预处理指令的语言规则已经在第一部分第 17 章说明，这里只把它用于工程组织。

:::

## 4. 头文件重复包含

在具备一定规模的真实工程中，头文件之间往往会形成网状的依赖关系。例如模块的基础类型定义在 `common.h` 中，而业务模块 `parser.h` 与 `emitter.h` 均需要引用基础类型，因而都在各自开头包含了 `common.h`。当顶层的业务逻辑 `main.c` 同时引入了 `parser.h` 与 `emitter.h` 时，`common.h` 的全文就会被预处理器先后两次原封不动地复制进同一个源文件中。

::: concept header-repeat-include title="重复包含破坏翻译单元语义"

头文件会被预处理器按文本插入，同一头文件可能被多次包含。如果缺少包含保护，头文件中的结构体定义等内容会在同一翻译单元中重复出现，导致编译错误。包含保护（或 `#pragma once`）就是用来避免这种重复的。

:::

在 C 语言语法规则中，函数与对象的纯声明（只要类型保持兼容）在同一个作用域内重复书写多次是合法的；但是，结构体（struct）、联合体（union）或枚举（enum）的类型定义，在同一个翻译单元内却被严格禁止出现多次。一旦缺少头文件保护机制，重复展开的类型定义就会直接触发编译器的「类型重定义」（redefinition of struct）致命错误。通过 `#ifndef` 宏保护或非标准但被广泛支持的 `#pragma once`，可以确保同一个头文件的实体内容在一个翻译单元内仅被展开一次，从而保证包含操作的幂等性。

## 5. 声明一致性约束

在多文件协作中，一个最容易引发隐蔽灾难的误区，是调用方为了省事而脱离头文件自行书写 `extern` 声明。

::: concept cross-tu-declaration-consistency title="跨翻译单元声明必须一致"

多个翻译单元若都引用同一个外部符号，就必须看到彼此一致的声明。若某个源文件里声明写错了类型，即使能编译通过，也可能在链接后产生难以定位的运行错误。

:::

这种隐蔽性根源于 C 语言链接器的运作机制：传统的 C 链接器主要是基于名字匹配的无类型符号绑定器。在标准 C 中，函数符号通常不会像 C++ 那样在符号名中编码参数与返回值类型（即 Name Mangling）。若实现文件 `impl.c` 中实现的函数原本返回浮点数 `double average(int, int)`，而调用方 `app.c` 却凭记忆手工写下了 `int average(int, int)` 的声明：
1. `app.c` 在编译期会根据 `int` 声明生成从整型通用寄存器读取返回值的机器码指令；
2. `impl.c` 在编译期会按照 `double` 逻辑将计算结果放置在浮点寄存器中；
3. 两者在单文件编译时各自都能毫无警告地通过；
4. 链接器在链接期仅按名字 `average` 强行将两处绑定在一起；
5. 直到程序运行时，调用方读取了完全错误的寄存器数据，导致结果失真甚至内存崩溃。

要彻底杜绝这类风险，唯一的工程实践就是：**任何跨翻译单元共享的符号，其声明必须集中在唯一的头文件中；实现文件必须包含该头文件以接受编译期自检，调用文件也必须通过包含该头文件获取权威声明。**

## 6. 内部符号收敛

在拆分模块时，并非所有函数与数据都需要开放给外部世界。模块内部往往包含大量辅助性的计算过程、内部状态缓存以及实现细节。

如果放任所有内部函数与全局对象使用默认的存储说明符，它们在编译后都会被赋予外部链接属性（External Linkage），成为目标文件中暴露在外的全局符号。这不仅会污染全局命名空间，极易与同伴编写的代码或第三方库发生名字冲突（Name Collision），还会破坏模块的封装性，使调用者误调本不该公开的私有逻辑。

因此，所有不需要跨翻译单元访问的函数与具有静态存储期的对象，都应当显式使用 `static` 关键字加以修饰。这会使符号收敛为内部链接属性（Internal Linkage）：
- 在当前翻译单元之外，该符号完全不可见，其他源文件即使定义了同名符号也能和平共处、互不干扰；
- 编译器由于明确知悉该符号不可能被外部目标文件引用，能够大胆施加激进的优化（例如直接将小型辅助函数内联展开，甚至彻底消除未被实际调用的死代码）；
- 最终目标文件的全局符号表将保持极度清爽，仅保留真正对外提供公共服务的接口符号。

## 7. 暂定定义与链接结果

在 C 语言的文件作用域下，对象的声明与定义存在一种特殊的中间过渡形态——暂定定义（Tentative Definition）。

::: concept tentative-definition-linkage title="暂定定义与多重定义"

文件作用域下形如 `int g;` 的声明在没有初始化器时可能形成暂定定义。单个翻译单元内可以出现多次同名暂定定义，最终会合并为一个定义；但跨翻译单元若都给出外部定义，就会在链接阶段产生多重定义冲突。

:::

如果在全局作用域书写 `int counter;` 且不附带初始化表达式（例如 `= 0`），也不附加 `extern` 关键字，它在语法上便构成暂定定义。在单个翻译单元内部，标准允许连续出现多行同名的暂定定义，编译器在语法分析完成后，会自动将它们折叠归并为唯一的实际对象定义。

然而，一旦开发者误将这种未带 `extern` 的对象声明写进了头文件中，灾难便会发生：当该头文件被工程中多个 `.c` 文件同时包含时，每个翻译单元在编译完成后都会各自生成一个强符号（或公共符号）。现代主流编译器（如 GCC 10 以后默认启用的 `-fno-common` 规范）在链接阶段执行严格的单一定义规则（One Definition Rule 类似约束），面对多个目标文件中同名的全局对象，会立即报错中断构建并输出 `multiple definition of 'counter'`。

正确的工程规矩因而非常明确：**头文件中永远只能放置附带 `extern` 说明符的纯声明（`extern int counter;`），而该对象的唯一定义与初始化实体，必须严格存放在某一个特定的 `.c` 实现文件中。**

::: generate multi-file-rules kind=explanation concepts=header-repeat-include,cross-tu-declaration-consistency,tentative-definition-linkage

面向开始编写多文件 C 项目的读者，把上面几条规则串成一套可执行的多文件工程纪律：头文件必须有包含保护；公共声明集中在头文件，所有调用点只通过头文件获取声明；不需要跨文件暴露的函数和对象用 `static` 限定；只声明放头文件、唯一定义放实现文件。逐条说明每条规则防的是什么错、违反了会在哪个阶段暴露。

:::

### 8.2 编程

<Exercise id="20505" :d="3" :w="3">

把一个单文件程序拆成三个翻译单元。原程序如下，保存为 `textstat.c` 并确认它输出 `words: 9` 和 `longest: 5`：

```c
#include <stdio.h>

int is_delimiter(char c) {
    return c == ' ' || c == '\t' || c == '\n';
}

int word_count(const char *text) {
    int count = 0;
    int in_word = 0;
    for (const char *p = text; *p != '\0'; p++) {
        if (is_delimiter(*p)) {
            in_word = 0;
        } else if (!in_word) {
            in_word = 1;
            count++;
        }
    }
    return count;
}

int longest_word(const char *text) {
    int longest = 0;
    int current = 0;
    for (const char *p = text; *p != '\0'; p++) {
        if (is_delimiter(*p)) {
            current = 0;
        } else {
            current++;
            if (current > longest) {
                longest = current;
            }
        }
    }
    return longest;
}

int main(void) {
    const char *text = "the quick brown fox jumps over the lazy dog";
    printf("words: %d\n", word_count(text));
    printf("longest: %d\n", longest_word(text));
    return 0;
}
```

要求：

1. 拆成 `textstat.h`、`textstat.c`、`report.c`。头文件里只放 `word_count` 与 `longest_word` 的声明和包含保护；实现文件里把 `is_delimiter` 加上 `static`；`main` 移进 `report.c`。
2. `report.c` 里再写一个同名的 `static int is_delimiter(char c)`，只把空格当分隔符。最终程序的标准输出必须仍然只有 `words:` 与 `longest:` 两行，和拆分前逐字节相同。为了确认两份实现确实各自生效，可以临时加一行打印做对照（对照完删掉）：对 `"a\tb"` 调用 `word_count` 得到 2（`textstat.c` 的那份把制表符当分隔符），而 `report.c` 自己的 `is_delimiter('\t')` 返回 0。
3. 分别用 `-c` 编译两个 `.c`，再链接。运行确认输出 `words: 9` 和 `longest: 5`。
4. 用 `nm -g --defined-only textstat.o` 列出导出符号，确认只有 `word_count` 和 `longest_word`；再用 `nm textstat.o` 找到 `is_delimiter`，说明它为什么是小写字母。
5. 把两个文件里的 `static` 都去掉，重新链接，记录诊断；改回 `static` 后确认恢复通过。

验收：`nm -g --defined-only textstat.o` 只出现两个 `T`；两个 `is_delimiter` 同时存在且互不干扰；去掉 `static` 后链接器报 `multiple definition`。

</Exercise>

下面的三个文件用 `static` 让两个模块各自维护一份状态：

#include <stdio.h>

1. 编译运行，记录输出。解释为什么两个模块累加的是各自的 `counter`。

### 8.3 综合与挑战

<Exercise id="20508" :d="5" :w="4">

下面的多文件工程中预先埋下了三处相互交织的构建隐患，在排查时会按编译器与链接器的执行阶段依次暴露。请先原样直接尝试构建，切勿提前猜测修改：

```c
/* scale.h */
#ifndef COMMON_H
#define COMMON_H

int scale(int x);

#endif
```

```c
/* counter.h */
#ifndef COMMON_H
#define COMMON_H

int counter;

void bump(void);

int get_counter(void);

#endif
```

```c
/* scale.c */
#include "scale.h"

int scale(int x) {
    return x * 10;
}
```

```c
/* counter.c */
#include "counter.h"

void bump(void) {
    counter++;
}

int get_counter(void) {
    return counter;
}
```

```c
/* main.c */
#include <stdio.h>
#include "scale.h"
#include "counter.h"

int scale(int x) {
    return x + 1;
}

int main(void) {
    bump();
    bump();
    printf("%d %d %d\n", get_counter(), scale(2), counter);
    return 0;
}
```

要求：

1. 用 `gcc -std=c17 -Wall -Wextra *.c -o app` 编译，记录第一条错误和第一条警告，指出它们属于哪个阶段。然后用 `gcc -std=c17 -E main.c | grep -c "void bump(void);"` 统计声明出现的次数，解释这个 0 说明了什么，以及为什么诊断里没有直接出现「保护宏重复」这类消息。
2. 只改两个头文件的保护宏，重新编译。记录链接器的两条 `multiple definition` 诊断，分别指出它们由哪条规则造成。
3. 修掉 `counter` 的多重定义：头文件只留 `extern int counter;`，定义放进 `counter.c`。再处理 `scale`：把 `main.c` 里的同名函数改名为 `local_scale` 并加上 `static`。说明为什么不能只加 `static` 而不改名（实际试一次，记录诊断）。改完后把 `printf` 改成打印四项：`get_counter()`、`local_scale(2)`、`scale(2)`、`counter`。
4. 全部修好后运行，确认输出 `2 3 20 2`。对三个目标文件运行 `nm -g --defined-only`，列出导出的符号。解释为什么 `main.o` 里的 `counter` 是 `U`，而 `counter.o` 里是 `B`。
5. 写一个 `check.sh`：依次用 `-c` 编译三个源文件，每次检查退出状态，任何一步失败就打印是哪一步并以非 0 退出；全部成功后链接并运行。脚本要能在故意改坏任意一个文件时指出失败发生在哪一步。

验收：输出 `2 3 20 2`；三个目标文件的导出符号分别只有 `scale`、`counter` 与 `bump`/`get_counter`、`main`（MinGW 上 `main.o` 还会多出 `.refptr.counter` 一类的重定位辅助符号，可以指出它并在报告里说明）；`check.sh` 在改坏 `counter.c` 时报告编译失败而不是链接失败。

</Exercise>
