# 5.1 翻译单元

## 1. 基本定义

::: concept translation-unit-definition title="翻译单元的定义"

预处理完成后得到的源文件称为一个翻译单元 (Translation Unit)。它由外部声明序列组成，例如函数定义、对象定义、`typedef` 声明和 `extern` 声明。编译器先分别处理各翻译单元生成目标文件，再由链接器把目标文件与库连接为最终程序。

:::

::: generate translation-unit-intro kind=explanation concepts=translation-unit-definition

面向刚开始接触多文件 C 项目的读者，讲解从源文件到可执行文件的整体路径——预处理、逐翻译单元编译、链接；说明为什么“翻译单元”是理解“声明写在哪、定义放在哪”的基本单位。

:::

## 2. 为什么它是模块边界

同名标识符能否共存、某个符号能否被其他源文件访问，都取决于翻译单元边界和链接属性。

::: generate translation-unit-boundary kind=explanation concepts=translation-unit-definition

面向刚开始接触多文件 C 项目的读者，解释翻译单元为什么是模块边界：`static` 如何影响可见性、头文件如何保证声明一致、链接器如何把调用点与定义点绑定。围绕“声明写在哪、定义放在哪”这个组织问题展开。

:::

## 3. 一个最小示例

::: tip 关于 `#ifndef` / `#define` / `#endif`

这三行是“头文件包含保护”的标准写法，属于预处理器的条件编译指令，目的是防止头文件被重复包含。第一部分第 17 章已经系统说明预处理与条件编译；这里关注它在头文件边界中的作用。

:::

::: code-group

```c [math_ext.h]
/* math_ext.h */
#ifndef MATH_EXT_H
#define MATH_EXT_H

int add(int lhs, int rhs);

#endif
```

```c [math_ext.c]
/* math_ext.c */
#include "math_ext.h"

int add(int lhs, int rhs) {
    return lhs + rhs;
}
```

```c [main.c]
/* main.c */
#include <stdio.h>
#include "math_ext.h"

int main(void) {
    printf("%d\n", add(3, 4));
    return 0;
}
```

:::

输出：

::: terminal

7

:::

::: generate translation-unit-example kind=explanation concepts=translation-unit-definition

借助上面的三文件示例，面向刚开始接触多文件 C 项目的读者分步说明：`main.c` 和 `math_ext.c` 经预处理后成为两个翻译单元；两者包含同一个头文件，从而共享一致的声明；链接阶段把 `add` 的调用点和定义点连起来。预处理指令的语言规则已经在第一部分第 17 章说明，这里只把它用于工程组织。

:::

## 4. 头文件重复包含

::: concept header-repeat-include title="重复包含破坏翻译单元语义"

头文件会被预处理器按文本插入，同一头文件可能被多次包含。如果缺少包含保护，头文件中的结构体定义等内容会在同一翻译单元中重复出现，导致编译错误。包含保护（或 `#pragma once`）不是风格问题，而是构建正确性问题。

:::

## 5. 声明一致性约束

::: concept cross-tu-declaration-consistency title="跨翻译单元声明必须一致"

多个翻译单元若都引用同一个外部符号，就必须看到彼此一致的声明。若某个源文件里声明写错了类型，即使能编译通过，也可能在链接后产生难以定位的运行错误。

:::

## 6. 内部符号收敛

不需要跨翻译单元暴露的函数和对象，建议使用 `static` 限定在当前翻译单元。这样它们的名字不会成为外部符号，也不会与其他源文件中的同名符号冲突；剩下没有 `static` 的外部符号，就是模块真正对外提供的接口。

## 7. 暂定定义与链接结果

::: concept tentative-definition-linkage title="暂定定义与多重定义"

文件作用域下形如 `int g;` 的声明在没有初始化器时可能形成暂定定义。单个翻译单元内可以出现多次同名暂定定义，最终会合并为一个定义；但跨翻译单元若都给出外部定义，就会在链接阶段产生多重定义冲突。

:::

::: generate multi-file-rules kind=explanation concepts=header-repeat-include,cross-tu-declaration-consistency,tentative-definition-linkage

面向开始编写多文件 C 项目的读者，把上面几条规则串成一套可执行的多文件工程纪律：头文件必须有包含保护；公共声明集中在头文件，所有调用点只通过头文件获取声明；不需要跨文件暴露的函数和对象用 `static` 限定；只声明放头文件、唯一定义放实现文件。逐条说明每条规则防的是什么错、违反了会在哪个阶段暴露。

:::

### 8.1 巩固

<Exercise id="20502" :d="1" :w="2">

用正文第 3 节的三文件示例做一遍翻译与链接的观察：

1. 建 `math_ext.h`、`math_ext.c`、`main.c`，内容照抄正文。分别执行 `gcc -std=c17 -E main.c -o main.i` 和 `gcc -std=c17 -E math_ext.c -o math_ext.i`，用 `wc -l` 记录四个文件的行数。
2. 在 `main.i` 和 `math_ext.i` 里各用 `grep -c` 数两样东西：声明 `int add(int lhs, int rhs);` 和函数体 `return lhs + rhs;`。把两边的计数记下来。
3. 分别用 `-c` 生成 `main.o` 与 `math_ext.o`，对两个目标文件运行 `nm`。指出 `add` 在哪个文件里是 `U`、在哪个里是 `T`，`main` 和 `printf` 各是什么。
4. 先只把 `main.o` 交给链接器，记录诊断和它所属的阶段；再把 `math_ext.o` 加进去，运行程序确认输出 `7`。

最后回答：`main.i` 里为什么找不到 `add` 的函数体；两个目标文件里那些 `U` 符号是在哪一步、被什么填上的。

包含保护防的到底是哪一种重复，做三组实验来分清。

先建一个没有包含保护的头文件：

```c
/* point.h */
struct point {
    int x;
    int y;
};
```

1. 写 `twice.c`，连续两次 `#include "point.h"`，然后使用 `struct point`。编译，记录诊断，指出它出现在哪个阶段。用 `gcc -std=c17 -E twice.c | grep -c "struct point {"` 数结构体定义出现的次数。
2. 给 `point.h` 加上 `#ifndef POINT_H` 形式的包含保护，重新数一次，再编译一次，确认通过。换成 `#pragma once` 再数一次。
3. 把 `twice.c` 拆成 `one.c` 和 `two.c`：两个翻译单元各包含一次没有保护的 `point.h`，各自使用 `struct point`，然后链接。记录结果并解释：为什么这次没有报重复定义？
4. 写一个只含 `int add(int lhs, int rhs);` 的头文件，在同一个源文件里包含两次，不加保护，编译。解释这次为什么也不需要保护。

验收：第 1 步的计数是 2、第 2 步是 1；第 3、4 步都能正常编译链接。

</Exercise>

下面三个文件合起来能编译、能链接、能运行，但结果是错的。

```c
/* api.h */
#ifndef API_H
#define API_H

double average(int lhs, int rhs);

#endif
```

```c
/* impl.c */
int average(int lhs, int rhs) {
    return (lhs + rhs) / 2;
}
```

```c
/* app.c */
#include <stdio.h>
#include "api.h"

int main(void) {
    printf("%f\n", average(3, 4));
    return 0;
}
```

1. 编译运行，记录输出。说明编译器和链接器为什么都没有报错：`impl.c` 里没有包含 `api.h`，它看不到那份写错的声明，链接器又只按名字绑定符号。
2. 在 `impl.c` 开头加上 `#include "api.h"`，重新编译，记录完整诊断。指出它来自哪个阶段，诊断里两个类型分别是什么。
3. 把声明和定义改成一致的正确版本（返回 `double`，除数为 `2.0`），确认输出 `3.500000`。
4. 回答：如果 `impl.c` 一直不包含自己的头文件，这种不一致还有哪些办法能在构建时暴露？至少说出一种，并实际试一次。

验收：修改前输出 `0.000000`，修改后输出 `3.500000`，第 2 步出现 `conflicting types` 一类错误。

</Exercise>

### 8.2 编程

<Exercise id="20505" :d="3" :w="3">

把一个单文件程序拆成三个翻译单元。原程序如下，保存为 `textstat.c` 并确认它输出 `words: 9` 和 `longest: 5`：

```c
#include <stdio.h>

int is_delimiter(char c) {
    return c == ' ' || c == '\t' || c == '\n';
}

int word_count(const char *text) {
    int count = 0;
    int in_word = 0;
    for (const char *p = text; *p != '\0'; p++) {
        if (is_delimiter(*p)) {
            in_word = 0;
        } else if (!in_word) {
            in_word = 1;
            count++;
        }
    }
    return count;
}

int longest_word(const char *text) {
    int longest = 0;
    int current = 0;
    for (const char *p = text; *p != '\0'; p++) {
        if (is_delimiter(*p)) {
            current = 0;
        } else {
            current++;
            if (current > longest) {
                longest = current;
            }
        }
    }
    return longest;
}

int main(void) {
    const char *text = "the quick brown fox jumps over the lazy dog";
    printf("words: %d\n", word_count(text));
    printf("longest: %d\n", longest_word(text));
    return 0;
}
```

要求：

1. 拆成 `textstat.h`、`textstat.c`、`report.c`。头文件里只放 `word_count` 与 `longest_word` 的声明和包含保护；实现文件里把 `is_delimiter` 加上 `static`；`main` 移进 `report.c`。
2. `report.c` 里再写一个同名的 `static int is_delimiter(char c)`，只把空格当分隔符。最终程序的标准输出必须仍然只有 `words:` 与 `longest:` 两行，和拆分前逐字节相同。为了确认两份实现确实各自生效，可以临时加一行打印做对照（对照完删掉）：对 `"a\tb"` 调用 `word_count` 得到 2（`textstat.c` 的那份把制表符当分隔符），而 `report.c` 自己的 `is_delimiter('\t')` 返回 0。
3. 分别用 `-c` 编译两个 `.c`，再链接。运行确认输出 `words: 9` 和 `longest: 5`。
4. 用 `nm -g --defined-only textstat.o` 列出导出符号，确认只有 `word_count` 和 `longest_word`；再用 `nm textstat.o` 找到 `is_delimiter`，说明它为什么是小写字母。
5. 把两个文件里的 `static` 都去掉，重新链接，记录诊断；改回 `static` 后确认恢复通过。

验收：`nm -g --defined-only textstat.o` 只出现两个 `T`；两个 `is_delimiter` 同时存在且互不干扰；去掉 `static` 后链接器报 `multiple definition`。

</Exercise>

下面的三个文件用 `static` 让两个模块各自维护一份状态：

```c
/* counter_a.c */
static int counter = 0;

static void step(void) {
    counter++;
}

void bump_a(void) {
    step();
}

int value_a(void) {
    return counter;
}
```

```c
/* counter_b.c */
static int counter = 0;

static void step(void) {
    counter++;
}

void bump_b(void) {
    step();
}

int value_b(void) {
    return counter;
}
```

```c
/* main.c */
#include <stdio.h>

void bump_a(void);
void bump_b(void);
int value_a(void);
int value_b(void);

int main(void) {
    bump_a();
    bump_a();
    bump_b();
    printf("%d %d\n", value_a(), value_b());
    return 0;
}
```

1. 编译运行，记录输出。解释为什么两个模块累加的是各自的 `counter`。
2. 对 `counter_a.o` 运行 `nm` 与 `nm -g --defined-only`，指出 `counter`、`step`、`bump_a`、`value_a` 的符号字母，说明哪些对外可见。
3. 只去掉 `counter` 的 `static`（两个文件都去），链接，记录诊断；只去掉 `step` 的 `static` 再试一次，记录诊断。说明这两次失败的共同原因。
4. 把设计改成两个模块共享同一个计数器：新建 `counter.h` 放 `extern int counter;` 与四个函数声明，把两个实现合并进 `counter.c`，`main.c` 不变。运行确认输出 `3 3`；用 `nm -g counter.o` 确认 `counter` 是 `B`，再用 `nm main.o` 说明文件里为什么找不到 `counter` 这个符号（`main` 只通过函数访问它，没有直接引用）。最后在 `main` 的 `printf` 里直接读一次 `counter`，重新编译，确认 `main.o` 里出现 `U counter`。

验收：原程序输出 `2 1`，共享版本输出 `3 3`；第 3 步两次都出现 `multiple definition`；改完后 `counter.o` 里是 `B`、`main.o` 里是 `U`。

</Exercise>

下面的写法把定义放进了头文件，这是多文件工程里最常见的一类链接错误：

```c
/* counter.h */
int counter;
```

```c
/* counter.c */
#include "counter.h"

void bump(void) {
    counter++;
}
```

```c
/* main.c */
#include <stdio.h>
#include "counter.h"

void bump(void);

int main(void) {
    bump();
    printf("%d\n", counter);
    return 0;
}
```

1. 按默认选项编译链接，记录诊断。指出 `counter` 在两个翻译单元里各是什么，违反的是哪一条规则。
2. 加上 `-fcommon` 再链接一次，运行并记录输出；用 `nm counter.o` 看 `counter` 的符号字母。说明公共符号是怎样让两个暂定定义合并的。查一下 GCC 10 起 `-fcommon` 为什么不再默认开启，用一句话概括。
3. 把 `counter.h` 改成 `int counter = 0;`，仍然加 `-fcommon`，重新链接，记录诊断。说明带初始化器的定义与暂定定义在链接行为上有什么区别。
4. 改成标准做法：头文件写 `extern int counter;`，在 `counter.c` 里写 `int counter = 0;`。确认程序输出 `1`；对两个目标文件运行 `nm`，指出 `counter` 的 `B` 与 `U` 分别在哪里。
5. 另写一个单文件程序，文件作用域下写三次 `int g;`、再写一次 `int g = 3;`，编译运行，记录输出与 `nm` 里的符号。说明这与跨翻译单元的多重定义为什么不冲突。

验收：第 2 步输出 `1` 且符号为 `C`；第 3 步仍报 `multiple definition`；第 4 步符号为 `B` 与 `U` 各一处；第 5 步输出 `3`，符号为 `D`。

</Exercise>

### 8.3 综合与挑战

<Exercise id="20508" :d="5" :w="4">

下面五个文件的工程里埋了三处问题，它们按顺序暴露，修好一处才会看到下一处。先原样编译，不要提前改。

```c
/* scale.h */
#ifndef COMMON_H
#define COMMON_H

int scale(int x);

#endif
```

```c
/* counter.h */
#ifndef COMMON_H
#define COMMON_H

int counter;

void bump(void);

int get_counter(void);

#endif
```

```c
/* scale.c */
#include "scale.h"

int scale(int x) {
    return x * 10;
}
```

```c
/* counter.c */
#include "counter.h"

void bump(void) {
    counter++;
}

int get_counter(void) {
    return counter;
}
```

```c
/* main.c */
#include <stdio.h>
#include "scale.h"
#include "counter.h"

int scale(int x) {
    return x + 1;
}

int main(void) {
    bump();
    bump();
    printf("%d %d %d\n", get_counter(), scale(2), counter);
    return 0;
}
```

要求：

1. 用 `gcc -std=c17 -Wall -Wextra *.c -o app` 编译，记录第一条错误和第一条警告，指出它们属于哪个阶段。然后用 `gcc -std=c17 -E main.c | grep -c "void bump(void);"` 统计声明出现的次数，解释这个 0 说明了什么，以及为什么诊断里没有直接出现「保护宏重复」这类消息。
2. 只改两个头文件的保护宏，重新编译。记录链接器的两条 `multiple definition` 诊断，分别指出它们由哪条规则造成。
3. 修掉 `counter` 的多重定义：头文件只留 `extern int counter;`，定义放进 `counter.c`。再处理 `scale`：把 `main.c` 里的同名函数改名为 `local_scale` 并加上 `static`。说明为什么不能只加 `static` 而不改名（实际试一次，记录诊断）。改完后把 `printf` 改成打印四项：`get_counter()`、`local_scale(2)`、`scale(2)`、`counter`。
4. 全部修好后运行，确认输出 `2 3 20 2`。对三个目标文件运行 `nm -g --defined-only`，列出导出的符号。解释为什么 `main.o` 里的 `counter` 是 `U`，而 `counter.o` 里是 `B`。
5. 写一个 `check.sh`：依次用 `-c` 编译三个源文件，每次检查退出状态，任何一步失败就打印是哪一步并以非 0 退出；全部成功后链接并运行。脚本要能在故意改坏任意一个文件时指出失败发生在哪一步。

验收：输出 `2 3 20 2`；三个目标文件的导出符号分别只有 `scale`、`counter` 与 `bump`/`get_counter`、`main`（MinGW 上 `main.o` 还会多出 `.refptr.counter` 一类的重定位辅助符号，可以指出它并在报告里说明）；`check.sh` 在改坏 `counter.c` 时报告编译失败而不是链接失败。

</Exercise>
